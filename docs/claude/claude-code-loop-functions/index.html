    Claude Code /loop 내부 동작 — 루프를 떠받치는 함수들 (ScheduleWakeup · Cron · Monitor)

    2026-06-25

    Claude Code /loop 내부 동작 — 루프를 떠받치는 함수들 (ScheduleWakeup · Cron · Monitor)

    Claude Code의 /loop은 "프롬프트를 주기적으로 / 또는 스스로 속도를 조절하며 반복"하게 해주는 스킬이다. 겉보기엔 단순한 "N분마다 실행"이지만, 실제로는 세 가지 모드와 그 모드를 떠받치는 여러 함수(tool)가 맞물려 돌아간다. 이 글은 실제 API 요청 캡처에서 /loop 스킬 본문과 관련 tool 정의를 추려, 루프가 어떻게 스케줄링·웨이크업·종료되는지를 정리한 것이다.

    출처: /loop 1m 1분마다 ls 를 치자 세션의 POST /v1/messages 요청 캡처 (model claude-opus-4-8, 70개 tool 중 루프 관련 함수만 발췌).

    한눈에 보기 — 루프를 구성하는 함수들

    함수 역할 언제 쓰이나
    CronCreate 고정 주기 스케줄 등록 (5-field cron) 고정 간격 모드 (rule 1·2)
    CronList / CronDelete 등록된 cron 조회 / 취소 관리·중단
    ScheduleWakeup 다음 깨어날 시점을 스스로 정함 (cache-aware) 동적 모드 (rule 3)
    Monitor 이벤트 스트림으로 루프를 즉시 깨움 이벤트 게이트 동적 모드
    PushNotification 루프 종료 시 결과 한 줄 알림 자리 비운 사용자에게 완료 통지

    1. /loop 스킬 — 입력 파싱과 모드 분기

    /loop은 입력을 [interval] <prompt…> 로 파싱한다. 우선순위는 다음과 같다.

    1. 선두 토큰: 첫 토큰이 ^\d+[smhd]$(예: 5m, 2h)에 맞으면 그게 간격, 나머지가 프롬프트.
    2. 후행 "every" 절: 입력이 every <N><unit>(예: every 20m, every 5 minutes)로 끝나면 그걸 간격으로 떼어낸다. 단 every 뒤가 시간 표현일 때만 — check every PR은 간격이 아니다.
    3. 간격 없음: 그 외에는 입력 전체가 프롬프트이고, 스스로 속도를 정하는 동적 모드로 간다.
    5m /babysit-prs          → 간격 5m,  프롬프트 /babysit-prs        (rule 1)
check the deploy every 20m → 간격 20m, 프롬프트 check the deploy   (rule 2)
run tests every 5 minutes  → 간격 5m,  프롬프트 run tests          (rule 2)
check the deploy         → 간격 없음 → 동적 모드                  (rule 3)
check every PR           → 간격 없음 → 동적 모드 ("every"+비시간)  (rule 3)
5m                       → 프롬프트 비어있음 → usage 출력

    클라우드 우선 제안 (Offer cloud first)

    스케줄링 전에 간격이 60분 이상이거나 입력이 일 단위 표현("every morning", "daily", "each night" 등)이면, 로컬 세션 루프 대신 클라우드 스케줄을 먼저 권한다. 세션을 닫으면 로컬 루프는 멈추기 때문이다. 사용자가 클라우드를 고르면 CronCreate가 아니라 schedule 스킬로 넘긴다.

    2. 고정 간격 모드 — CronCreate

    rule 1·2로 간격이 잡히면 그 간격을 cron 식으로 변환해 CronCreate에 등록한다.

    간격 패턴 Cron 식 비고
    Nm (N ≤ 59) */N * * * * N분마다
    Nm (N ≥ 60) 0 */H * * * 시간으로 반올림 (H = N/60, 24를 나눠야)
    Nh (N ≤ 23) 0 */N * * * N시간마다
    Nd 0 0 */N * * N일마다 자정(로컬)
    Ns ceil(N/60)m 취급 cron 최소 단위는 1분

    간격이 단위를 깔끔히 나누지 못하면(7m → :56→:00에서 간격이 튐, 90m → cron 표현 불가) 가장 가까운 깔끔한 간격으로 반올림하고 무엇으로 바꿨는지 사용자에게 알린다.

    CronCreate의 설계 포인트

    • 로컬 타임존 5-field cron — "0 9 * * *" = 로컬 9am, 타임존 변환 불필요.
    • one-shot 지원 (recurring: false) — "2:30pm에 알려줘" 같은 1회성은 분/시/일/월을 고정값으로 핀하고 한 번 발사 후 자동 삭제.
    • :00·:30 분각을 피하라 — "9am"을 요청한 전 세계 사용자가 모두 0 9로 몰리면 같은 순간 API에 부하가 쏠린다. 요청이 근사치면 57 8이나 3 9처럼 어긋난 분을 고른다. ("hourly" → `7 * * * *")
    • 세션 한정 — job은 이 Claude 세션 메모리에만 있고 디스크에 안 써진다. Claude 종료 시 사라짐.
    • 라이브 감시용 아님 — 고정 벽시계 간격으로 재실행할 뿐. 로그/프로세스를 실시간 감시하려면 Monitor를 쓴다.
    • 런타임 동작 — REPL이 idle일 때만 발사. 작은 결정적 jitter가 더해지고(recurring은 주기의 최대 10%, 최대 15분 늦게), recurring은 7일 후 자동 만료(마지막 1회 발사 후 삭제). 반환된 job ID는 CronDelete로 취소.

    CronList는 현재 세션의 cron job 목록, CronDelete는 job ID로 취소(인메모리 스토어에서 제거)다.

    3. 동적 모드 — ScheduleWakeup (이 글의 핵심)

    간격이 없으면(rule 3) Claude가 스스로 다음 실행 시점을 정한다. 매 턴 마지막 행동으로 ScheduleWakeup을 호출해 "몇 초 뒤에 다시 깨어날지"를 지정하고, 같은 /loop 프롬프트를 그대로 넘겨 다음 발사가 이 스킬로 재진입하게 한다. 호출을 생략하면 루프가 끝난다.

    스키마

    {
  "delaySeconds": "number — 지금부터 몇 초 뒤 깨어날지. 런타임이 [60, 3600]으로 clamp",
  "reason":       "string — 그 지연을 고른 이유 한 문장. 텔레메트리+사용자에게 노출",
  "prompt":       "string — 깨어날 때 발사할 /loop 입력. 매 턴 같은 입력을 verbatim으로"
}

    delaySeconds 고르기 — 프롬프트 캐시가 기준

    여기가 /loop 설계에서 가장 영리한 부분이다. Anthropic 프롬프트 캐시 TTL이 5분이라, 300초를 넘겨 자면 다음 웨이크업이 전체 대화 컨텍스트를 캐시 미스로 읽는다 — 느리고 비싸다. 그래서 자연스러운 분기점이 생긴다.

    • 5분 미만 (60–270s): 캐시가 따뜻하게 유지됨. 하네스가 알려줄 수 없는 외부 상태(CI, 배포, 원격 큐)를 능동적으로 폴링할 때 적합.
    • 5분–1시간 (300–3600s): 캐시 미스를 감수. 더 일찍 볼 이유가 없을 때 — 분 단위로 바뀌는 걸 기다리거나, 진짜 idle이거나, 다른 신호가 주 깨움이고 이건 긴 fallback heartbeat일 때.

    300초를 고르지 마라. worst-of-both — 캐시 미스를 내면서도 그걸 분할상환하지 못한다. "5분쯤 기다리자" 싶으면 270s로 내려 캐시에 머물거나, 1200s+로 올려 한 번의 캐시 미스로 훨씬 긴 대기를 사라. 라운드 분 단위가 아니라 캐시 윈도우로 생각하라.

    특정 신호 없이 그냥 idle하게 도는 틱이면 기본값 1200–1800s(20–30분). 8분짜리 CI를 폴링하는데 60s마다 깨면 끝나기 전 캐시를 8번 태운다 — 270s로 두 번 자는 게 낫다.

    폴링하지 말아야 할 것

    네가 띄운 background 작업을 폴링하려고 짧은 간격 웨이크업을 걸지 마라 — 하네스가 추적하는 작업이 끝나면 자동으로 재호출되므로 폴링은 낭비다. 대신 작업이 멈추거나 알림이 안 와도 루프가 살아남도록 긴 fallback(1200s+)을 건다. 예외는 하네스가 추적 못 하는 외부 작업(CI·배포·원격 큐).

    자율 루프 sentinel

    사용자 프롬프트가 없는 자율 /loop에서는 prompt에 리터럴 <<autonomous-loop-dynamic>>을 넘긴다 (런타임이 발사 시점에 자율 루프 지시문으로 치환). CronCreate용 <<autonomous-loop>>와 혼동 금지 — ScheduleWakeup은 항상 -dynamic 변종을 쓴다.

    reason 필드

    지연을 고른 이유 한 문장. 텔레메트리로 가고 사용자에게도 보인다. "watching CI run"이 "waiting"보다 낫다 — 구체적으로.

    4. 이벤트 게이트 — Monitor

    동적 모드에서 다음 실행이 시간이 아니라 관측 가능한 이벤트(CI 완료, 로그 라인 매칭, 파일 변경, PR 코멘트)에 걸려 있으면, Monitor를 persistent: true로 한 번 무장한다. 이벤트는 <task-notification> 메시지로 도착해 ScheduleWakeup 데드라인을 기다리지 않고 즉시 루프를 깨운다. 이때 ScheduleWakeup의 delaySeconds는 "이벤트가 안 오면 얼마나 기다릴지"의 fallback heartbeat(1200–1800s)가 된다.

    알림 개수로 도구를 고른다

    • 한 번 ("서버 뜨면/빌드 끝나면 알려줘") → Monitor가 아니라 Bash run_in_background + 조건 충족 시 종료하는 명령(until grep -q "Ready in" dev.log; do sleep 0.5; done). 종료 알림 1회.
    • 발생할 때마다 무한 ("ERROR 뜰 때마다") → tail -f, inotifywait -m, while true 같은 무한 명령으로 Monitor.
    • 발생할 때마다, 알려진 끝까지 ("각 CI 스텝 결과, 런 완료되면 종료") → 라인을 emit하다 종료하는 명령으로 Monitor.

    단일 알림에 무한 명령(tail -f 등)을 쓰지 마라 — 이벤트가 발사된 뒤에도 timeout까지 무장 상태로 남는다. tail -f log | grep -m 1도 해결책이 아니다(매칭 후 로그가 조용해지면 SIGPIPE가 안 와 파이프라인이 hang). "X 준비되면 알려줘"는 Bash run_in_background + until 루프로.

    후속 반복에서는 TaskList를 먼저 확인해 이미 Monitor가 돌면 다시 무장하지 않는다.

    5. 루프 종료 — PushNotification

    루프를 멈추려면 ScheduleWakeup 호출을 생략하고, 무장했던 Monitor를 TaskStop으로 정리한다 (task ID는 TaskList로 찾는다). 멈추기 전에 PushNotification으로 결과 한 줄을 보낸다 — 사용자가 자리를 비운 채 완료를 기다릴 수 있기 때문. 단, 사용자가 방금 멈추라고 해서 멈추는 경우엔 생략(이미 여기 있으니까).

    정리 — 루프의 두 축

    /loop은 결국 "누가 다음 틱을 결정하는가" 로 갈린다.

    • 고정 간격 모드: 벽시계가 결정한다 → CronCreate(+CronList/CronDelete). 세션 한정, 7일 만료, :00/:30 회피.
    • 동적 모드: Claude가 결정한다 → ScheduleWakeup(시간 기반, 캐시 윈도우로 사고) + Monitor(이벤트 기반, 즉시 깨움). 종료 시 PushNotification으로 통지.

    핵심 통찰은 ScheduleWakeup의 캐시 인지 지연 선택이다 — "몇 분마다"라는 인간적 직관 대신 프롬프트 캐시의 5분 TTL을 비용 모델로 삼아, 270s(캐시 유지) 또는 1200s+(미스를 긴 대기로 분할상환) 중 하나로 수렴시킨다. 300초 같은 어중간한 값은 가장 비효율적이다.
