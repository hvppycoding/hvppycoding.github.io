    오프라인 Qt 라이브러리 설치 & 배포

    2025-09-04

    redhat 8.x 에서 오프라인(sudo 권한 없이) Qt library를 설치하고 있어. installer로 설치하는데, 다음과 같은 에러가 나 XCB cursor platform library was not found dnf install xcb-util-cursor xcb-util-cursor-devel

    문제 상황을 정확히 짚으면, Qt가 X11에서 쓰는 xcb 플랫폼 플러그인 이 실행 중
    libxcb-cursor.so.0(= xcb-util-cursor 런타임 라이브러리) 를 찾지 못해서 실패하는 겁니다. Qt 6.5+ 부터 이 의존성이 사실상 필수가 되었고, RHEL8 계열에선 EPEL 저장소에 들어있는 경우가 많습니다. Qt 문서

    아래 두 가지 중 하나로 해결할 수 있어요. (sudo 없이 진행 가능)

    방법 A) 루트 없이 “필요 라이브러리만” 로컬에 풀어서 실행 (권장)

    개념: 필요한 RPM들을 다른 곳에서 받아와서, 대상 머신의 $HOME 아래에 풀고 LD_LIBRARY_PATH로만 읽히게 합니다. 시스템 전역 설치가 아니므로 sudo가 필요 없습니다.

    1. (네트워크 되는 RHEL8/Alma8 등에서) 필요한 RPM 내려받기

      • 꼭 필요한 건 xcb-util-cursor(= libxcb-cursor.so.0) 이고, 종종 libXcursor(= libXcursor.so.1)도 같이 필요합니다.

      • dnf 플러그인을 쓸 수 있으면:

        dnf download --resolve xcb-util-cursor libXcursor

    이렇게 하면 의존 패키지까지 같이 받아옵니다. Notes to self
    (RHEL 8에선 xcb-util-cursor가 EPEL 에 있습니다. 직접 받는다면 EPEL 8 저장소에서 xcb-util-cursor-0.1.3-9.el8.x86_64.rpm를 확인할 수 있어요. libXcursor는 AppStream에 있습니다.) dl.fedoraproject.orgrpm.pbone.netYum.oracle

    1. 대상(오프라인) 머신으로 RPM 파일들을 복사

    2. RPM을 사용자 디렉터리에 추출 (설치 아님)

      mkdir -p $HOME/.local/qt-xcb-deps && cd $_
# RPM들이 있는 디렉터리에서:
for r in /path/to/rpms/*.rpm; do rpm2cpio "$r" | cpio -idmv; done

    이렇게 하면 각 RPM의 파일이 $HOME/.local/qt-xcb-deps/usr/lib64/ 등에 풀립니다. Stack OverflowBaeldung on Kotlin

    1. 라이브러리 검색 경로 추가 후 실행 
      export LD_LIBRARY_PATH=$HOME/.local/qt-xcb-deps/usr/lib64:$LD_LIBRARY_PATH
# (배포판에 따라 usr/lib 일 수도 있습니다. 둘 다 추가해도 무방)
export QT_DEBUG_PLUGINS=1   # 문제시 로딩 로그 확인용
./qt-unified-linux-*.run

    QT_DEBUG_PLUGINS=1을 켜면 어떤 플러그인/라이브러리를 찾다가 실패하는지 자세히 출력됩니다. Qt 문서

    참고: Qt 문서의 “Linux/X11 의존성 표”에도 xcb-cursor(= libxcb-cursor0)가 xcb 플러그인의 의존성으로 명시돼 있으며, RHEL에서는 일부 패키지가 EPEL에 있을 수 있다고 안내합니다. Qt 문서

    방법 B) XCB를 아예 우회해서 설치(Headless/임시)

    환경에 GUI/X서버가 전혀 없고, 일단 설치만 진행하려면 xcb 대신 다른 QPA 를 강제로 쓰게 할 수 있습니다.

    • 가장 간단히: 
      QT_QPA_PLATFORM=minimal ./qt-unified-linux-*.run
# 또는
./qt-unified-linux-*.run -platform minimal

    QT_QPA_PLATFORM(또는 -platform)으로 Qt의 플랫폼 플러그인을 바꿀 수 있습니다. minimal/offscreen은 X 의존성이 없습니다. Qt 문서Ubuntu Manpages

    • 완전 무인 설치 가 필요하면 Qt Installer Framework의 headless(스크립트) 모드 를 사용합니다: 
      ./qt-unified-linux-*.run --script /path/to/control.qs

    IFW는 --script / --start-server 등으로 UI 없이 동작시킬 수 있습니다(설치 흐름은 .qs 스크립트에서 정의). Qt 문서GitHub

    주의: minimal/offscreen으로 띄우면 창이 안 보이는 대신 스크립트로 조작하는 방식이 안정적입니다. GUI로 조작하려면 방법 A처럼 xcb 의존 라이브러리를 갖추는 편이 낫습니다.

    빠른 체크리스트 (step-by-step)

    1. (가능하면) QT_DEBUG_PLUGINS=1로 실행해 실제로 어떤 .so가 없다는 메시지가 뜨는지 확인. Qt 문서

    2. GUI로 설치하고 싶다 → 방법 A 로 xcb-util-cursor(그리고 필요시 libXcursor)만 로컬에 풀고 LD_LIBRARY_PATH 추가. Qt 문서

    3. 헤드리스/자동화가 목적이다 → 방법 B 에서 QT_QPA_PLATFORM=minimal 또는 -platform minimal + --script로 진행. Qt 문서+1Ubuntu Manpages

    필요하시면, 현재 환경에서 정확히 어떤 .so 가 빠졌는지 진단 로그를 함께 분석해 드리고(예: QT_DEBUG_PLUGINS=1 출력), 오프라인 설치용으로 받아야 할 정확한 el8 RPM 목록 도 정리해 드릴게요.

    특정 Release라는 폴더에 직원들이 접속해서 toolchain, bin 등을 사용해. 이 때 이런 lib도 필요한데 폴더 구조를 어떻게 가야하지?

    좋아요—“Release” 공유 폴더 하나만으로 툴체인/바이너리와 필요한 런타임 라이브러리(lib, Qt plugins)까지 함께 배포하는 포터블 레이아웃 을 제안할게요. sudo 없이 쓰는 전제라 LD_LIBRARY_PATH, $ORIGIN(RPATH), qt.conf로 경로를 컨트롤합니다.

    권장 폴더 구조 (RHEL8, x86_64 예시)

    Release/
└── current -> 2025.09.03/                 # 최신 릴리스 심볼릭 링크
    ├── bin/                               # 최종 실행 스크립트/런처
    ├── toolchain/                         # gcc/clang, cmake 등 (선택)
    │   └── gcc-11.4/
    │       ├── bin/
    │       ├── lib/                       # 툴체인 자체 런타임
    │       └── include/
    ├── qt/                                # Qt 런타임 (설치본/압축풀기)
    │   ├── 6.6.3/                         # 버전 폴더
    │   │   ├── bin/
    │   │   ├── lib/
    │   │   ├── plugins/                   # Qt 플러그인 (platforms, styles 등)
    │   │   │   └── platforms/
    │   │   │       └── libqxcb.so
    │   │   ├── qml/
    │   │   ├── translations/
    │   │   └── qt.conf                    # (아래 예시)
    │   └── installer/                     # 오프라인 설치러(.run) 원본 보관용 (선택)
    ├── runtime/                           # 시스템에 없는 “외부 의존 lib”를 모아둠
    │   ├── lib/                           # ★ xcb-util-cursor, Xcursor 등 .so 배치
    │   └── licenses/                      # 서드파티 라이선스 텍스트
    ├── include/                           # (필요 시)
    ├── share/                             # 아이콘/테마/데이터 (필요 시)
    └── scripts/
        ├── env.sh                         # 환경 변수 세팅
        ├── run-qt-installer.sh            # Qt 인스톨러 실행 래퍼
        └── run-myapp.sh                   # 사내 앱 실행 래퍼(여러 개 가능)

    핵심 아이디어: 실행은bin/의 래퍼 스크립트로 하되, 실제 라이브러리는 runtime/lib와 qt/<ver>/lib, 플러그인은 qt/<ver>/plugins에만 넣고, 환경변수/qt.conf/RPATH로 경로를 “Release 폴더 안”으로만 고정합니다.

    반드시 들어가야 하는 것들

    1) runtime/lib에 “시스템에 없을 수 있는” lib 배치

    • libxcb-cursor.so.0 (→ xcb-util-cursor)

    • (상황에 따라) libXcursor.so.1, libxkbcommon.so.*, libxcb-util.so.*, libxcb-icccm.so.*, libxcb-image.so.*, libxcb-keysyms.so.*, libxcb-render-util.so.* 등
      → 오프라인 RPM을 풀어온 경우 usr/lib64/*.so.*가 생기는데, 심볼릭 링크 포함 그대로 runtime/lib/로 옮기거나 runtime/lib64/를 함께 추가하세요.

    2) Qt 플러그인

    • qt/<ver>/plugins/platforms/libqxcb.so 반드시 존재해야 함.

    • (Wayland가 필요 없다면 생략 가능) plugins/wayland-* 등은 용도에 따라.

    환경변수/설정 (step-by-step)

    scripts/env.sh

    #!/usr/bin/env bash
# Release/current/scripts/env.sh

# 루트 경로 계산
ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"

# 공용 PATH
export PATH="$ROOT/bin:$ROOT/toolchain/gcc-11.4/bin:$ROOT/qt/6.6.3/bin:$PATH"

# 런타임 라이브러리 경로 (배포한 .so 우선)
export LD_LIBRARY_PATH="$ROOT/runtime/lib:$ROOT/qt/6.6.3/lib:$LD_LIBRARY_PATH"

# Qt 플러그인/QML 경로 (qt.conf로 대체 가능하지만 명시해두면 편함)
export QT_PLUGIN_PATH="$ROOT/qt/6.6.3/plugins"
export QML2_IMPORT_PATH="$ROOT/qt/6.6.3/qml"

# (문제 추적용) 필요 시만 켜세요
# export QT_DEBUG_PLUGINS=1

    qt//qt.conf (Qt가 자기 폴더 안에서만 찾게)

    [Paths]
Prefix=..
Plugins=plugins
Libraries=lib
Translations=translations
Qml2Imports=qml
    • qt.conf는 해당 Qt로 빌드된 앱 이 상대경로로 플러그인/라이브러리를 찾게 해 줍니다.

    실행 래퍼 스크립트

    Qt 인스톨러 (GUI 또는 minimal)

    #!/usr/bin/env bash
# Release/current/scripts/run-qt-installer.sh
set -euo pipefail
ROOT="$(cd "$(dirname "$0")/.." && pwd)"
source "$ROOT/scripts/env.sh"

# GUI로 띄우고 싶으면 기본값(xcb), X 없는 서버면 minimal
: "${QT_QPA_PLATFORM:=xcb}"   # 필요 시 minimal 로 바꿔 실행
exec "$ROOT/qt/installer/qt-unified-linux-x64.run" "$@"

    사내 앱/툴 실행 (예: myapp)

    #!/usr/bin/env bash
# Release/current/bin/myapp
set -euo pipefail
ROOT="$(cd "$(dirname "$0")/.." && pwd)"
source "$ROOT/scripts/env.sh"
exec "$ROOT/apps/myapp/bin/myapp" "$@"

    포인트: 모든 실행은 래퍼를 통해서만 하여 환경이 일관되게 세팅되도록 합니다. 사용자는 Release/current/bin/*만 실행하면 됩니다.

    RPATH로 더 깔끔하게(선택, 고급)

    LD_LIBRARY_PATH 없이도 돌아가게 하려면, 자체 제공 실행파일에 런타임 검색 경로를$ORIGIN 기준으로 박아두기:

    patchelf --set-rpath '$ORIGIN/../runtime/lib:$ORIGIN/../qt/6.6.3/lib' \
  Release/current/apps/myapp/bin/myapp

    • $ORIGIN은 실행파일 위치 기준.

    • 이렇게 하면 사용자가 env를 안 읽어도 필요한 .so를 “Release 안”에서만 찾습니다.

    • 외부(시스템) lib와 섞이지 않아 재현성이 올라갑니다.
      (glibc 같은 코어 라이브러리는 절대 동봉하지 마세요.)

    릴리스 관리 팁

    • 날짜 버전 폴더(2025.09.03/) 아래에 모든 것을 넣고, current 심볼릭 링크로 운영 → 롤백 쉬움.

    • runtime/lib에 무엇을 넣었는지 runtime/manifest.txt로 기록: 
      arduino
    
# from epel8: xcb-util-cursor-0.1.3-9.el8.x86_64
libxcb-cursor.so.0 -> libxcb-cursor.so.0.0.0
...
    • 새 서버에 배치할 때는 ldd bin/…로 누락 여부를 체크: 
      ldd Release/current/apps/myapp/bin/myapp | awk '/=> not found/ {print $1}'

    요약

    1. Release 안에 모든 실행/의존을 모으는 레이아웃 을 쓰세요: bin/, qt/<ver>/, runtime/lib/.

    2. 부족한 XCB 관련 .so 는 전부 runtime/lib/에 동봉.

    3. 실행은 반드시 래퍼 스크립트 로: env.sh에서 LD_LIBRARY_PATH/QT_PLUGIN_PATH 세팅.

    4. 가능하면 RPATH($ORIGIN)까지 설정해 환경변수 의존 줄이기.

    5. 버전 폴더 + current 심볼릭 링크로 배포/롤백 단순화.

    원하시면, 지금 쓰고 계신 파일 목록(특히 빠진 .so) 기준으로 맞춤 트리 와 env.sh/qt.conf를 바로 만들어 드릴게요.

    xcb util cursor 를 소스에서 빌드하는건 어때

    좋은 선택이에요. 소스에서 빌드 는 가능하고, “Release 폴더만으로 배포” 전략과도 잘 맞습니다. 다만 RHEL 8에서 sudo 없이 하려면 어디에서 빌드하느냐 가 핵심이에요. 아래를 단계별로 따라오세요.

    0) 빠른 판단 (어디서 빌드할지)

    • 추천: RHEL 8(혹은 호환) 빌드용 머신(네트워크/OEPL 사용 가능)에서 빌드 → 결과물(libxcb-cursor.so.* 등)만 Release에 넣기
      → 의존 체인이 길어서, 완전 오프라인 환경에서 전부 소스로 빌드하는 것보다 훨씬 가볍습니다.

    • 완전 오프라인·무sudo 환경에서 직접 빌드: 아래 3단계처럼 의존 라이브러리까지 전부 사용자 영역에 순서대로 빌드해야 합니다(가능은 함).

    xcb-util-cursor는 런타임 기준으로 libxcb , xcb-util-image , xcb-util-renderutil 에 의존합니다. 배포판 패키지 메타정보도 이렇게 명시돼요. archlinux.org

    1) 소스 내려받기 (빌드 머신에서)

    공식 배포 tarball(autotools의 configure 포함)을 쓰면 추가 bootstrap이 거의 필요 없습니다. 최신은 0.1.5. 필요한 보조 유틸은 아래와 같습니다. xcb.freedesktop.org

    • xcb-util-cursor-0.1.5.tar.*

    • xcb-util-image-0.4.1.tar.*

    • xcb-util-renderutil-0.3.10.tar.* xcb.freedesktop.org

    만약 git 소스에서 바로 빌드한다면 autoconf/automake/libtool, pkg-config, xorg-macros 등이 추가로 필요합니다. xcb.freedesktop.org

    2) “포터블” 프리픽스에 설치 (sudo 불필요)

    빌드 머신에서 사용자 쓰기 경로로 설치해, 나중에 해당 디렉터리만 통째로 Release에 넣습니다.

    # 공통 전역 (빌드 머신에서)
export PREFIX=$HOME/portable-xcb        # 임의의 경로(사용자 쓰기 가능)
export PKG_CONFIG_PATH=$PREFIX/lib/pkgconfig
export LD_LIBRARY_PATH=$PREFIX/lib:$LD_LIBRARY_PATH
mkdir -p "$PREFIX"

# (1) renderutil
tar xf xcb-util-renderutil-0.3.10.tar.* && cd xcb-util-renderutil-0.3.10
./configure --prefix="$PREFIX" --disable-static
make -j"$(nproc)" && make install
cd ..

# (2) image
tar xf xcb-util-image-0.4.1.tar.* && cd xcb-util-image-0.4.1
PKG_CONFIG_PATH=$PKG_CONFIG_PATH ./configure --prefix="$PREFIX" --disable-static
make -j"$(nproc)" && make install
cd ..

# (3) cursor (목표물)
tar xf xcb-util-cursor-0.1.5.tar.* && cd xcb-util-cursor-0.1.5
PKG_CONFIG_PATH=$PKG_CONFIG_PATH ./configure --prefix="$PREFIX" --disable-static
make -j"$(nproc)" && make install
cd ..

    빌드 후 확인:

    # 빌드 산출물 확인
ls $PREFIX/lib/libxcb-cursor.so*
# 의존 .so 확인해서 같이 가져가기
ldd $PREFIX/lib/libxcb-cursor.so.0.0.0

    중요(호환성): RHEL 8용 바이너리를 배포하려면 반드시 RHEL 8(또는 ABI 호환 기반)에서 빌드 하세요. 더 최신 glibc로 빌드하면 RHEL 8에서 안 돌아갈 수 있습니다.

    3) Release 폴더에 반영 (런타임 구성)

    앞서 제안한 레이아웃 기준:

    Release/current/
├─ runtime/
│  └─ lib/        ← 아래 파일들을 복사
└─ scripts/env.sh ← LD_LIBRARY_PATH 설정(이전 답변 예시)

    복사해야 할 것(최소):

    • $PREFIX/lib/libxcb-cursor.so*

    • $PREFIX/lib/libxcb-image.so*

    • $PREFIX/lib/libxcb-render-util.so*

    그리고 env.sh에 런타임 경로를 추가:

    export LD_LIBRARY_PATH="$ROOT/runtime/lib:$LD_LIBRARY_PATH"

    Qt 인스톨러/앱은 이전에 안내드린 래퍼 스크립트로 실행하면 됩니다(QT_PLUGIN_PATH, LD_LIBRARY_PATH가 항상 셋업되도록). 필요하면 실행 파일에 RPATH($ORIGIN)도 박아 두면 더 견고해요.

    완전 오프라인 + 무sudo에서 “전부” 소스 빌드해야 한다면 (상세 순서)

    의존 헤더가 없으니 libxcb까지 포함한 체인 빌드가 필요합니다(시간 좀 걸립니다).

    권장 빌드 순서:

    1. xorgproto → 2) libXau → 3) libXdmcp → 4) xcb-proto → 5) libxcb
      → 6) xcb-util-renderutil → 7) xcb-util-image → 8) xcb-util-cursor

    모두 --prefix=$PREFIX --disable-static로, PKG_CONFIG_PATH/LD_LIBRARY_PATH를 그때그때 $PREFIX로 이어붙여 가며 빌드하세요. freedesktop XCB 개발 가이드가 필요한 도구들과 절차를 잘 정리합니다. xcb.freedesktop.org

    왜 소스 빌드가 “가능하지만 무겁다” 고 했나요?

    • xcb-util-cursor 자체는 가벼우나, RHEL 8에서 sudo 없이 개발 헤더들을 못 깔면 연쇄적으로 여러 패키지를 직접 빌드해야 합니다.

    • 반대로, 빌드 가능한 머신에서 한 번 빌드 → 필요한.so만 동봉하면, 운영 서버/개발자 PC에선 그냥 Release만 받으면 끝입니다.

    RHEL 8의 CMake RPM들을 받아 설치하지 않고 사용자 디렉터리에 풀어 쓰는 방식.

    1. (온라인 머신) 의존성까지 RPM 다운로드

    1. (오프라인 대상 머신) Release에 추출

# 결과: usr/bin/cmake, usr/share/cmake-*/..., usr/lib64/*.so ... 가 펼쳐짐

      (일부 시스템에 없는 라이브러리가 포함될 수 있으므로 lib도 경로 추가)

export LD_LIBRARY_PATH="$ROOT/toolchain/cmake-rpm/usr/lib64:$LD_LIBRARY_PATH"
cmake --version

      -DCMAKE_MAKE_PROGRAM="$ROOT/toolchain/ninja/bin/ninja"

      → CMAKE_PREFIX_PATH가 Qt 설치 루트(예: .../6.6.3/gcc_64)인지 확인. 경로 끝에 lib/cmake/Qt6를 붙이지 마세요. GitHub

    • Clang 플러그인 관련 에러
      → LLVM을 쓰려면 CMAKE_PREFIX_PATH에 LLVM 설치 루트를 추가. 미사용이면 생략 하거나 관련 플러그인을 꺼도 됩니다. (ClangFormat/Code Model은 LLVM C++ API에 묶임) GitHub

    • xcb 관련 런타임 에러
      → 이전에 준비한 runtime/lib(예: libxcb-cursor.so.0 등)과 Qt의 plugins/platforms/libqxcb.so가 보이는지 확인. (Qt/xcb 의존성은 Qt 쪽 요구 사항) GitHub

    • RHEL 8의 GCC 버전
      → Qt를 빌드한 GCC와 호환 되어야 합니다(최소 GCC 10+ 권장). 툴체인을 Release/toolchain에 두고 env-build.sh 로 PATH만 바꿔서 쓰면 충돌이 적습니다. GitHub

# export LD_LIBRARY_PATH="$ROOT/runtime/lib:$LD_LIBRARY_PATH"  # 필요시

    좋아요—같은 OS(RHEL 8.x 가정)에서 “압축(tar.gz)으로 툴만 풀어서 실행”되는 포터블 배포 절차를 단계별로 정리했어요. 핵심은 앱 + 필요한 Qt 라이브러리/플러그인만 한 폴더에 모으고, $ORIGIN 기반 RPATH 또는 런처 스크립트 로 그 폴더만 보게 만드는 겁니다.

    1) 스테이징(모으는) 폴더 만들기

    APP=myapp
VER=1.0.0
STAGE="$PWD/${APP}-${VER}-rhel8-x86_64"   # 최종 배포 폴더
mkdir -p "$STAGE"/{bin,lib,plugins,qml,translations,resources}

    • bin/ : 실행파일/런처

    • lib/ : Qt *.so 및 추가 .so

    • plugins/ : Qt 플러그인들(platforms, imageformats 등)

    • qml/, translations/ : QML/번역 쓰면 포함

    • resources/ : 앱 리소스(아이콘, 데이터 등)

    2) 내 앱과 리소스 복사

    # 당신의 빌드 산출물에서

# 리소스/설정 파일 등도 필요에 따라
cp -r /path/to/resources/* "$STAGE/resources/" 2>/dev/null || true

    3) 필요한 Qt 라이브러리 모으기

    Qt 설치 루트(예: ~/Qt/6.6.3/gcc_64 또는 당신의 Release/current/qt/6.6.3)를 QT_PREFIX로 둡니다.

    QT_PREFIX="$HOME/Qt/6.6.3/gcc_64"  # 환경에 맞게 수정
cp -a $QT_PREFIX/lib/libQt6Core.so*       "$STAGE/lib/"
cp -a $QT_PREFIX/lib/libQt6Gui.so*        "$STAGE/lib/"
cp -a $QT_PREFIX/lib/libQt6Widgets.so*    "$STAGE/lib/"
# 네트워크/JSON/Concurrent 등 앱이 쓰는 모듈만 추가 복사
# cp -a $QT_PREFIX/lib/libQt6Network.so*  "$STAGE/lib/"
# cp -a $QT_PREFIX/lib/libQt6Qml*.so*     "$STAGE/lib/"   # QML/Quick 쓰는 경우

    무엇이 필요한지 애매하면 ldd bin/myapp 출력에서 libQt6* 항목을 보고 해당 .so만 lib/로 복사하세요.

ldd "$STAGE/bin/${APP}" | awk '/not found/{print $1}'
# 누락된 .so 들을 $STAGE/lib/ 로 복사 (심볼릭 링크 포함해서)

    절대 동봉하지 마세요 : libc, libm, libpthread, librt, libdl, ld-linux-*.so*(glibc 계열 핵심).
    상황에 따라 동봉 고려 : libstdc++, libgcc_s(툴체인과 OS 차이로 충돌 날 때는 동봉 + RPATH로 우선 사용).

    7) 런처 스크립트 or RPATH 설정 (둘 중 하나)

    A) 간단: 런처 스크립트

    cat > "$STAGE/bin/run-${APP}.sh" <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
HERE="$(cd "$(dirname "$0")" && pwd)"
export LD_LIBRARY_PATH="$HERE/../lib:${LD_LIBRARY_PATH:-}"
# 디버깅 시 도움
# export QT_DEBUG_PLUGINS=1
exec "$HERE/${APP}" "$@"
EOF
sed -i "s/\${APP}/${APP}/" "$STAGE/bin/run-${APP}.sh"
chmod +x "$STAGE/bin/run-${APP}.sh"

    사용자는 bin/run-myapp.sh만 실행하면 됩니다.

    B) 깔끔: RPATH로 고정(런처 없이도 실행)

    patchelf --set-rpath '$ORIGIN/../lib' "$STAGE/bin/${APP}"
# (선택) 플러그인 .so 들에도 RUNPATH 설정
find "$STAGE/plugins" -name '*.so' -exec patchelf --set-rpath '$ORIGIN/../../lib' {} +

    $ORIGIN은 실행/플러그인 파일 위치 기준 이라 경로가 다릅니다.
    RPATH를 쓰면 LD_LIBRARY_PATH 없이도 동작해 배포가 단순해집니다.

    8) 용량 줄이기(선택)

    # 심볼 제거 (디버그 심볼은 따로 보관 권장)
strip --strip-unneeded "$STAGE/bin/${APP}" || true
find "$STAGE/lib" -maxdepth 1 -type f -name '*.so*' -exec strip --strip-unneeded {} + 2>/dev/null

    내 계정에서 일부러 그룹 권한을 삭제하거나 할 순 없어?

    짧게 말하면 계정 자체에서 “그룹 멤버십을 빼는” 건 관리자 없이 못 합니다.
    리눅스 커널은 프로세스가 보조 그룹(supplementary groups)을 바꾸려면 CAP_SETGID 권한이 있어야 해서, 일반 사용자로는 setgroups()/setpriv --clear-groups가 EPERM 로 실패해요. Linux Dieman7.org

    다만 “그룹이 없는 것처럼” 테스트 하는 우회 방법은 있습니다—권한 없이도요.

    1) rootless Podman로 보조 그룹 없이 실행 (추천)

    Podman은 기본적으로 rootless 컨테이너에 호스트의 보조 그룹을 넘기지 않습니다.
    즉 --group-add keep-groups를 안 쓰면 , 컨테이너 안 프로세스는 보조 그룹이 비어있는 상태 로 돌아가요. 이게 “그룹 권한 제거”를 사실상 재현합니다.

    # 깨끗한 Alma 8 컨테이너에서 앱 실행 (보조 그룹 전달 안 함 = 기본값)
podman run --rm -it --userns=keep-id \
  -v "$PWD:/app:Z" -w /app almalinux:8 \
  bash -lc 'id; ./myapp-1.0.0-rhel8-x86_64/bin/run-myapp.sh'

    참고: --group-add keep-groups를 주면 호스트의 보조 그룹을 유지 합니다. 우리가 원하는 건 “없애기”이므로 붙이지 마세요. docs.podman.ioRed Hat

    2) newgrp/sg는 주 그룹만 바꿉니다 (보조 그룹은 그대로)

    newgrp somegroup은 primary GID만 바꿔요. 보조 그룹은 유지되기 때문에 “그룹 제거” 재현 용도로는 불충분합니다. man7.org+1

    3) 디렉터리 단위로 권한 테스트(ACL/권한비트)

    계정의 그룹을 못 빼는 대신, 특정 테스트 폴더에서 그룹 권한을 제거 해 상호작용을 검증할 수 있습니다.

    • 권한비트로: chmod g-rwx /path/to/testdir

    • ACL로 특정 그룹/마스크 차단: setfacl -m g:<grp>:- /path/to/testdir
      (이건 “계정”이 아니라 “해당 폴더”에만 영향)

    요약 (step-by-step)

    1. 진짜로 그룹 멤버십을 빼려면 관리자 작업이 필요합니다. 일반 사용자로는 불가. Linux Dieman7.org

    2. 테스트 목적 이라면 rootless Podman 에서 --group-add keep-groups 없이 실행 → 보조 그룹 없는 상태로 동작. docs.podman.io

    3. 보조로 newgrp은 주 그룹만 바꿀 뿐이고, 디렉터리 권한/ACL로도 상황별 검증이 가능합니다. man7.org

    1. 같은 경로로 매핑
    udocker run -v=/data  <컨테이너이름>  bash

    (udocker 매뉴얼 예시 그대로입니다.) indigo-dc.github.io

    1. 다른 경로로 매핑 + 작업 디렉터리 지정
    udocker run -v="$PWD:/work" -w=/work  <컨테이너이름>  bash
# 현재 폴더 → /work

    (매뉴얼의 -v=$HOME:/home/user -w=/home/user 예시와 동일한 방식입니다.) indigo-dc.github.io

    1. 여러 개를 반복해서 매핑
    udocker run \
  -v=/opt/toolchain:/opt/toolchain \
  -v=/release/2025.09:/opt/release \
  -w=/opt/release \
  <컨테이너이름>  bash

    (--volume/-v는 여러 번 줄 수 있습니다.) cs.tau.ac.il

    1. 단일 파일 매핑
    udocker run -v="$PWD/config.ini:/app/config.ini"  <컨테이너이름>  bash

    --volume=호스트경로:컨테이너경로 형식이며 파일 또는 디렉터리 모두 가능합니다. (udocker 문서에 “host file or directory”로 명시) indigo-dc.github.io

    1. 홈 디렉터리 통째로 보이게

    원래 docker에서도 run할 때 volume 설정을 했었나?

    네—Docker도run 할 때 볼륨 설정합니다. 두 가지 방법이 있어요: 옛날식 -v/--volume와 더 명확한 --mount.

    핵심 정리 (step-by-step)

    1. 바인드 마운트(호스트 ↔ 컨테이너)
    docker run --rm -it \
  -v "$PWD:/work" -w /work \
  ubuntu:22.04 bash
# 또는(더 읽기 쉬움)
docker run --rm -it \
  --mount type=bind,src="$PWD",target=/work \
  ubuntu:22.04 bash
    1. 읽기 전용으로 마운트
    docker run --rm -it \
  -v "$PWD:/work:ro" ubuntu:22.04 bash
# 또는
docker run --rm -it \
  --mount type=bind,src="$PWD",target=/work,readonly \
  ubuntu:22.04 bash
    1. SELinux 있는 RHEL/Alma/Rocky 환경이면 라벨 옵션 추가
    docker run --rm -it \
  -v "$PWD:/work:Z" ubuntu:22.04 bash   # 컨테이너 전용 라벨
# (여러 컨테이너가 같은 경로를 공유하면 :z)
    1. 네임드 볼륨(호스트 경로 대신 Docker가 관리)
    docker volume create mydata
docker run --rm -it -v mydata:/var/lib/myapp ubuntu:22.04 bash
    1. 익명 볼륨(컨테이너 생명주기와 연동)
    docker run --rm -it -v /cache ubuntu:22.04 bash
# (호스트 경로 지정 안 하면 Docker가 임시 볼륨을 만듭니다)
    1. 여러 개 동시에
    docker run --rm -it \
  -v "$PWD:/src" \
  --mount type=bind,src=/opt/toolchain,target=/toolchain \
  ubuntu:22.04 bash
    1. 메모리 기반 tmpfs
    docker run --rm -it \
  --tmpfs /run \
  # 또는
  --mount type=tmpfs,target=/run,tmpfs-size=64m \
  ubuntu:22.04 bash

    -v vs --mount 언제 쓰나?

    • -v는 짧고 익숙함(스크립트 한 줄 테스트에 좋음).

    • --mount는 type/src/target/readonly 가 분리돼 가독성/오타 방지 에 유리(프로덕션/문서화 추천).

    udocker와의 차이 한 줄 요약

    • udocker도 -v host:cont로 바인드 마운트를 지원하지만 :ro, :Z/:z, 네임드 볼륨/플러그인 같은 고급 옵션은 제한 적입니다. Docker 쪽이 기능이 더 많아요.

    기존 있는 container를 런할때도?

    짧게 요약:

    • Docker: 이미 만들어둔(container created) 컨테이너를 docker start로 다시 띄울 땐 새로운 볼륨(-v/–mount) 추가/변경 불가 예요. → 컨테이너를 새로 만들기(re-create) 해야 합니다.

    • udocker: udocker run 할 때마다 -v host:cont를 그때그때 줄 수 있습니다(컨테이너 메타데이터에 영구 저장되는 게 아니라, 실행 시 옵션으로 적용).

    아래를 그대로 따라 해보세요.

    Docker에서 “기존 컨테이너”에 볼륨 추가하려면 (re-create)

    1. 현재 컨테이너 확인
    docker ps -a
docker inspect myctr --format ''
    1. 중지
    docker stop myctr
    1. (선택) 데이터 보존 방법 결정

    • 이미 네임드 볼륨 을 쓰고 있으면 그대로 재사용 가능

    • 컨테이너 내부 데이터가 필요하면:

      • docker cp myctr:/path/in/container ./backup/ 로 빼두거나

      • docker commit myctr myimg:withdata 로 이미지에 굽기

    1. 새 컨테이너로 재생성(여기에 -v 추가)
    docker rm myctr
docker run -d --name myctr \
  -v /host/data:/app/data:Z \   # 여기서 원하는 볼륨/마운트 전부 지정
  <기존에 쓰던 이미지 혹은 myimg:withdata> \
  <기존 CMD/옵션들>

    Compose 쓰는 경우엔 docker-compose.yml의 volumes:를 수정하고:

    docker compose up -d --force-recreate

    udocker에서 “이미 만들어 둔 컨테이너” 실행 시 볼륨 추가

    udocker는 실행할 때마다 -v를 붙이면 됩니다.

    # c8 라는 이름의 컨테이너를 이미 만들어 두었다고 가정
udocker run \
  -v "$PWD:/work" \
  -v /opt/toolchain:/opt/toolchain \
  -w /work \
  c8 bash

    매번 쓰기 번거로우면 작은 래퍼 스クリپ트 를 만들어 두세요.

    cat > run-c8.sh <<'EOF'
#!/usr/bin/env bash
udocker run -v "$PWD:/work" -w /work c8 "$@"

chmod +x run-c8.sh

    한 줄 요약 (step-by-step)

    1. Docker: docker start로는 불가 → stop → rm → run(-v …)으로 재생성

    2. udocker: udocker run 때마다 -v를 그냥 추가 하면 됨(필요시 스크립트로 고정)

    옮겼는데 libgl이 없다네 필요한거 한번에 다 못찾나?

    맞아요—libGL.so.1가 없다는 건 Qt가 GLX/EGL 경로로 그리려고 하면서 Mesa 런타임(예: mesa-libGL)을 못 찾는 상황이에요. “필요한 걸 한 번에” 모으려면 아래 순서로 자동 스캔 → 패키지 매핑 → 묶음 추출 을 쓰면 됩니다.

    1) 오프라인(대상)에서: 누락된 .so 한 번에 스캔

    배포 폴더 루트에서 실행하세요.

    # 누락된 so만 뽑아내기 (앱/플러그인 전부)
find bin plugins lib -type f \( -perm -111 -o -name '*.so*' \) -print0 |
xargs -0 -r ldd 2>/dev/null |
awk -vF=" " '
  /=> not found/ {print $1}                     # 형식: libX.so.Y => not found
  /^[[:space:]]*[^[:space:]]+ \(\)/ {print $1}  # 형식: libX.so.Y (0x....) 누락 대응
' | sort -u > missing-so.txt

echo "[missing]"; cat missing-so.txt

    생성된 missing-so.txt를 온라인 머신으로 가져갑니다.

    2) 온라인 머신에서: SONAME → RPM 패키지 이름 매핑

    (가능하면 x86_64 기준)

    # dnf repoquery가 있으면 더 정확
while read so; do
  dnf repoquery --qf '%{name}.%{arch}' --whatprovides "*/$so" --arch=x86_64 | head -n1
done < missing-so.txt | sort -u > rpms.txt

echo "[packages]"; cat rpms.txt

    dnf repoquery가 없다면(plugins 미설치) 다음처럼 해도 됩니다:

    while read so; do
  dnf -q provides "*/$so" | awk -F: '/:/{print $1}' | grep '\.x86_64$' | head -n1
done < missing-so.txt | sort -u > rpms.txt

    3) 온라인 머신에서: 의존까지 한 방에 다운로드

    # rpms.txt에 적힌 이름들을 --resolve로 의존까지 수집
dnf download --resolve $(cat rpms.txt) -y
# 결과 .rpm들을 한 폴더에 전부 내려받음

    4) 오프라인(대상)에서: RPM을 설치 없이 추출 해 lib에 투입

    mkdir -p lib.tmp && cd lib.tmp
for r in /path/to/downloaded/*.rpm; do rpm2cpio "$r" | cpio -idmv; done

# 실제 필요한 .so(.so.N 링크 포함)를 배포 lib/로 복사
mkdir -p /your/app/lib
cp -a usr/lib64/*.so* /your/app/lib/ 2>/dev/null || true
cp -a usr/lib/*.so*   /your/app/lib/ 2>/dev/null || true

    필수 링크가 없으면 만들어 주세요(예: libGL.so.1 -> libGL.so.1.7.0).

    libGL가 필요한 경우 자주 따라오는 패키지(예시)

    • libGL.so.1 → mesa-libGL

    • libEGL.so.1 → mesa-libEGL (EGL 경로일 때)

    • libglapi.so.0 → mesa-libglapi

    • libxshmfence.so.1 → libxshmfence

    • libX11.so.6, libXext.so.6, libXfixes.so.3, libXdamage.so.1 → libX11 , libXext , libXfixes , libXdamage

    • (이미 처리하셨겠지만) libxcb-*.so.0, libxkbcommon.so.0, libXcursor.so.1 등

    정확한 목록은 스캐너 출력 이 정답입니다. 그 리스트로 위 자동화 루틴을 돌리면 한 번에 모아집니다.

    실행 안정화 팁

    • RPATH 권장 : 실행파일에 한 번만 설정하면 LD_LIBRARY_PATH 없이도 동작 
      patchelf --set-rpath '$ORIGIN/../lib' /your/app/bin/yourapp
find /your/app/plugins -name '*.so' -exec patchelf --set-rpath '$ORIGIN/../../lib' {} +
    • GL 피하기(가능할 때만) : 앱이 OpenGL을 안 쓰고 Qt Widgets만 쓴다면 
      nginx
    
export QT_XCB_GL_INTEGRATION=none

    로 GL 통합을 비활성화해 libGL 의존을 줄일 수 있습니다. (OpenGL/Qt Quick 씬그래프를 사용한다면 끄지 마세요.)

    # 누락 .so 재확인
find bin plugins -type f \( -perm -111 -o -name '*.so*' \) -print0 |

# 문제 디버깅
export QT_DEBUG_PLUGINS=1
bin/run-yourapp.sh

    GLIBCXX_3.4.30 not found

    에러 GLIBCXX_3.4.30 not found는 대상 머신의 libstdc++가 너무 오래돼서(RHEL8 기본) 당신이 빌드한 바이너리가 요구하는 심볼(= GCC 12 세대에서 추가된 심볼)을 못 찾는 상황입니다. GLIBCXX_3.4.30은 GCC 12.1 에서 처음 도입된 버전이고, RHEL8 기본 libstdc++은 보통 3.4.25 전후 까지만 제공합니다. gcc.gnu.orgcommunity.cadence.com

    아래 중 편한 걸로 바로 처리하세요 (sudo 불필요).

    빠른 해결 3가지 (step-by-step)

    A) 빌드에 쓴 툴체인의 libstdc++을 같이 동봉 (가장 쉬움, 권장)

    1. 빌드 머신 에서, 당신이 쓴 g++의 libstdc++/libgcc 경로를 알아내 복사: 
      # 빌드 머신에서 실행
echo "$(g++ -v 2>&1 | tail -1)"     # 사용한 gcc 버전 기록용
cp -a "$(g++ -print-file-name=libstdc++.so.6)"*  Release/current/runtime/lib/
cp -a "$(gcc -print-libgcc-file-name)"          Release/current/runtime/lib/
    2. (옵션) 심볼이 있는지 확인: 
      strings Release/current/runtime/lib/libstdc++.so.6 | grep GLIBCXX_3.4.30

    3. 런타임이 이 사본을 우선 사용 하도록 설정:

      • 이미 제가 제안한 레이아웃을 쓰고 있으면 env.sh 또는 RPATH가 runtime/lib를 가리키게 되어 있을 겁니다.

      • 확실히 하려면 실행파일에 RPATH를 박아둡니다:

        patchelf --set-rpath '$ORIGIN/../runtime/lib' Release/current/bin/yourapp

    이렇게 하면 시스템의 오래된 /lib64/libstdc++.so.6 대신 동봉한 libstdc++가 사용됩니다. (C++ ABI는 툴체인과 짝 이 되어야 한다는 게 공식 가이드입니다.) gcc.gnu.org

    장점: 재빌드 불필요. 단, 다른 프로세스에 영향 없도록 앱 폴더 안에서만 보이게(RPATH/$ORIGIN) 하는 게 포인트.

    B) 대상 OS 수준에 맞춰 재빌드 (보수적 방식)

    • RHEL8의 기본 libstdc++ 범위(대개 GLIBCXX_3.4.25 근방)를 타겟으로 구버전 GCC(예: GCC 8/9/10)로 빌드하면 심볼 요구치가 내려갑니다.

    • C++20 최신 기능을 많이 썼다면 제약이 있을 수 있습니다.

    • 어떤 GCC가 어떤 GLIBCXX를 내는지 요약:
      GCC 10 → 3.4.28, GCC 11 → 3.4.29, GCC 12 →3.4.30, GCC 13 → 3.4.31/32, GCC 14 → 3.4.33. gcc.gnu.org

    C) 정적 링크 로 libstdc++만 묶기 (상황 따라 유용)

    • 빌드 옵션에 추가: 
      -static-libstdc++ -static-libgcc
    • 그러면 동적 libstdc++.so.6가 필요 없어집니다(여전히 glibc는 동적). 크기가 늘고, 드물게 로더/플러그인 상호작용이 까다로울 수 있습니다. 그래도 배포 단순화가 목적이면 고려 가치 있습니다. (libstdc++는 GPL+예외로 정적 링크 허용)

    진단·검증 체크리스트

    1. 대상 머신의 libstdc++가 어디까지 지원하는지 확인 
      strings /lib64/libstdc++.so.6 | grep GLIBCXX_ | tail

    (RHEL8 계열은 보통 ...3.4.25에서 끝납니다.) community.cadence.com

    1. 앱이 요구하는 심볼 버전 확인 
      strings Release/current/bin/yourapp | grep GLIBCXX_ | sort -u | tail
    2. 실행 전후 확인 
      ldd Release/current/bin/yourapp | grep libstdc++
# → Release/current/runtime/lib/libstdc++.so.6 를 가리키는지 확인

    (보너스) 오프라인에서도 “한 방에” 모아오기

    만약 libGL 같은 다른 누락도 함께 보이면, 아까 드린 방법대로 ldd 스캔 → rpms 매핑 → dnf download --resolve로 필요한 RPM을 한 번에 모아 rpm2cpio로 풀어 runtime/lib/에 넣으면 됩니다. (이미 위에서 진행하신 흐름과 호환)

    원하시면, 현재 빌드에 쓴 g++ 버전 과 ldd yourapp/strings libstdc++.so.6 | grep GLIBCXX 결과를 주시면, 당신 레이아웃에 맞춘 복사·RPATH 명령 을 딱 맞게 써서 드릴게요.
