    Farad 사내 메신저 Relay 및 Remote 모드 구현 계획

    2026-07-16

    Farad 사내 메신저 Relay 및 Remote 모드 구현 계획

    기준 스펙: Farad 사내 메신저 Relay 및 Remote 모드 통합 스펙

    기준일: 2026-07-16

    구현 단위: 각 phase는 독립 검증·commit 가능한 vertical slice

    1. 현재 기준선

    1.1 구현된 것

    • 독립 packages/farad-relay package, CLI와 Uvicorn 실행
    • bounded POST /message, GET /healthz
    • strict Base64, AES-256-CBC/PKCS#7 codec, startup key fetch
    • Messenger official inbound field 검증과 TEXT 원문 폐기
    • exact optional Knox ID allowlist
    • VM-local SQLite WAL inbound_events, HOME deliveries, dedupe/lease/retry
    • HOME Adaptive Card renderer와 Back/Home action
    • encrypted Stage/Production v2 ChatRequest client
    • Farad SYSTEM/USER startup-only features.remoteControl provider
    • fixed /appl/LINUX/Hyper/utils/singleid adapter

    현재 자동 검증 기준:

    • packages/farad-relay/tests: 95 passed
    • Farad feature exposure + singleid focused tests: 21 passed

    1.2 아직 연결되지 않은 것

    현재 ChatRequest client와 HOME renderer는 있지만 outbound delivery worker가 없어 실제 카드를 보내지 않는다. Relay ASGI route도 /message, /healthz뿐이다. Farad에는 Relay client, credential state, Long Poll, Remote UI, Remote runtime hook이 없다.

    따라서 현재 구현은 안전한 foundation이며 end-to-end 원격 제어는 아직 동작하지 않는다.

    2. 구현 원칙

    1. Relay와 Farad를 독립 package/process로 유지한다.
    2. 실제 작업 권위는 Farad에 둔다. Relay는 routing, durability, Messenger adapter다.
    3. 각 phase는 inbound commit → outbox/command → result의 crash boundary를 테스트한다.
    4. 일반 CHAT과 SCHEDULED가 같은 Remote runtime 정책을 사용한다.
    5. Remote는 SessionType이나 permission mode가 아니다. session-scoped execution mode다.
    6. 메신저에 구체 텍스트를 보내지 않는다. emoji key, 안전 별칭, keyword, opaque ref만 허용한다.
    7. Qt UI signal을 backend authority로 사용하지 않는다. asyncio service/hook에서 post-commit event를 Relay client로 보낸다.
    8. 반복 경로는 O(1) 또는 bounded batch다. Long Poll, click, turn Stop에서 전체 table/session scan 금지.
    9. 먼저 문서 계약을 갱신한다. Remote는 Goal에 이어 두 번째 turn lifecycle contributor이므로 실제 구현 전에 docs/layers.md와 docs/agent.md의 hook arbitration 계약을 정식화한다.
    10. Messenger 발신과 update는 각각 비용이 드는 delivery다. 즉시 필요한 질문만 보내고, desktop-first 선택은 stale Messenger card를 실제로 클릭할 때까지 update하지 않는다.

    5. Phase 1 — Relay 안전 foundation

    상태: 완료

    구현 내용

    • independent package/process
    • inbound decrypt/normalize/DLP
    • SQLite WAL transaction, dedupe, HOME outbox
    • bounded body/claim/retry
    • HOME renderer
    • ChatRequest client
    • Farad feature exposure와 singleid adapter

    유지할 회귀 gate

    • raw inbound text가 domain type, SQLite/WAL, log에 존재하지 않는다.
    • duplicate inbound는 HOME delivery를 하나만 만든다.
    • crash after commit과 expired delivery lease를 복구한다.
    • production client가 plaintext dev mode로 시작하지 않는다.

    6. Phase 2 — versioned SQLite와 outbound delivery

    목표

    HOME semantic delivery를 실제 Messenger ChatRequest로 보내고 정확한 card identity를 저장한다.

    구현

    Relay:

    • SQLite schema version 2 migration
    • message_cards, 확장된 deliveries, 최소 action_routes 추가
    • CreateChatroomRequest, UpdateMessageRequest typed client 추가
    • outbound worker
      • bounded claim
      • OutboundCostPolicy: SEND_NEW, UPDATE_EXISTING, STORE_ONLY, DROP_DUPLICATE
      • semantic card render
      • action route를 send 전에 commit
      • ChatRequest response의 msgId/msgKey commit
      • retry와 DELIVERY_UNKNOWN 분리
    • worker lifecycle을 ASGI process composition root에서 시작/종료
    • request/message ID generator의 signed-int64, process restart, collision 테스트
    • cardRef + targetRevision + semanticKind logical cost key와 logical/provider-attempt counter

    예상 변경 위치:

    • packages/farad-relay/farad_relay/store.py
    • packages/farad-relay/farad_relay/messenger_client.py
    • packages/farad-relay/farad_relay/cards.py
    • 신규 delivery_worker.py, schema.py
    • packages/farad-relay/tests/

    transaction 순서

    semantic delivery + action routes commit
→ Messenger API call
→ response card identity commit
→ delivery delivered

    Messenger 응답이 불명확하면 자동 중복 전송하지 않고 DELIVERY_UNKNOWN으로 남긴다.

    검증

    • Create/Chat/Update stage/prod URL과 암호화 request contract
    • send 전 crash, response 전/후 crash, card identity commit 실패
    • stale revision update가 최신 카드를 덮지 못함
    • 동일 logical cost key의 retry/중복 enqueue가 새 과금 delivery를 만들지 않음
    • claim query가 requested batch 이상 row를 materialize하지 않음

    완료 조건

    • TEXT/INTRO inbound 뒤 실제 HOME card가 전송된다.
    • DB의 message_cards에서 정확한 room/msgId/msgKey/revision을 조회할 수 있다.

    7. Phase 3 — proactive pairing과 fallback

    목표

    Farad가 pairing을 시작하면 봇이 먼저 연결 확인 카드를 보내고 사용자 클릭으로만 binding을 활성화한다.

    Relay 구현

    • schema version 3
      • client_installations
      • messenger_bindings
      • pairing_attempts
    • POST /v1/clients/register
    • client token slow hash와 constant-time verify
    • Knox ID → numeric Messenger user ID provider Protocol
    • CreateChatroomRequest(chatType=0)와 room reuse
    • 연결/취소 action route
    • INTRO fallback matching
    • pending client용 activation Long Poll 또는 register wait contract

    Farad 구현

    • client token 생성
    • singleid는 최초 pairing/명시적 repair에서만 실행
    • pending/accepted/rejected/repair-required 상태 projection
    • token을 일반 state와 분리한 sensitive store에 atomic write

    검증

    • 선제 연결 성공
    • directory lookup/CreateChatroom/card send 부분 실패
    • INTRO fallback
    • wrong sender/room/Knox ID
    • duplicate connect/cancel click
    • Farad가 token을 저장했지만 Relay binding이 없는 repair

    완료 조건

    • 사용자가 봇을 미리 열지 않아도 확인 카드를 받고 연결할 수 있다.
    • 승인 전에는 Schedule/Session command가 생성되지 않는다.

    8. Phase 4 — runtime lease와 Long Poll command queue

    목표

    동일 client의 Farad 여러 instance 중 하나만 command를 받으며, command를 잃지 않고 재전달한다.

    Relay 구현

    • schema version 4
      • runtime_leases
      • commands
      • command_results
    • API
      • POST /v1/runtime/claim
      • GET /v1/commands?waitSeconds=25
      • POST /v1/commands/{id}/result
      • POST /v1/runtime/release
    • client-scoped waiter registry
      • SQLite가 command authority
      • in-memory waiter는 wake-up 최적화만 담당
      • process restart 후 polling만으로 correctness 유지
    • response당 command 최대 1개
    • command lease, result-as-ACK, generation fencing
    • takeover request와 Messenger confirmation

    Farad 구현

    • async Relay client와 bounded retry/backoff
    • runtime claim → Long Poll → dispatch → result loop
    • shutdown release는 best effort
    • reconnect 후 미완료 command idempotent 재처리

    검증

    • empty 25초 poll, command wake-up, client 격리
    • Farad A/B 동시 claim
    • expired lease와 generation rollover
    • response 유실, result 유실, duplicate result
    • 10,000 command fixture에서 client-scoped indexed query

    완료 조건

    • 두 Farad가 떠도 한 instance만 command를 받는다.
    • command는 result commit 전까지 삭제되지 않는다.

    9. Phase 5 — Farad Remote state와 세 UI surface

    목표

    사용자가 연결과 Remote 대상 노출을 명시적으로 제어한다.

    domain/state

    신규 Farad 경계:

    • RemoteControlService: enable/disable/rename intent owner
    • RemoteConnectionClient: Relay HTTP boundary
    • RemoteTargetIndex: Session/Schedule local ID ↔ emoji key/alias/enabled
    • RemoteCorrelationIndex: run/interaction ref ↔ exact session locator
    • RemoteModeState: session-scoped runtime snapshot

    저장 원칙:

    • client token은 sensitive store
    • Remote target/correlation은 <farad-data>/state/의 bounded 단일 index
    • 실제 transcript는 기존 Session transcript
    • startup은 remote target별 파일을 읽지 않는다.
    • in-app mutation은 atomic persist 후 exact in-memory entry와 해당 session snapshot만 갱신한다.

    UI

    1. Settings Remote 연결 row
    2. Schedule create/edit의 메신저에서 사용 toggle
    3. /remote command와 session-scoped dialog
    4. 공용 RemoteAliasEditor
      • catalog emoji 1개 선택 필수
      • emoji search/recent/category picker
      • text field 12 display cells
      • duplicate/name validation
      • [emoji alias] Messenger preview
    5. 활성 session prompt의 Goal-like Remote status strip
      • prompt container 최상단에 초록색 Remote + [emoji alias]
      • Goal strip과 동시에 표시하지 않음
    6. Remote 전용 local question
      • 기존 AskUserQuestion과 같은 prompt-area 배치와 선택 경험
      • RemoteReport(NEEDS_FEEDBACK)의 고정 keyword 선택지만 사용
      • 일반 AskUserQuestion은 Messenger로 mirror하지 않음
      • 선택 출처가 desktop인지 Messenger인지 표시

    Qt 구현 시:

    • InputDialog/StandardDialog 계열 사용; QInputDialog 금지
    • user-visible 문자열 en/ko catalog 동시 추가
    • clickable control에 pointing hand cursor
    • font-aware geometry와 Light source-of-truth
    • emoji picker는 standard QWidget/QListView 기반; QPainter custom grid는 피한다.

    /remote command

    • command registry에 feature-flag 조건부 등록/노출
    • pending New Session에서는 materialize 안내
    • real CHAT에서 dialog open
    • Goal active면 명확한 local error, mutation 없음
    • 성공은 transcript bubble 없이 조용히 UI state만 반영

    검증

    • alias width: Korean 6, ASCII 12, mixed, whitespace/control/duplicate
    • emoji catalog 외 값 거부
    • feature off일 때 command/UI 미노출
    • session/schedule type routing
    • NFS hot path에서 target별 content read가 실행되면 fail
    • Qt i18n, theme, font 12/14/18, keyboard focus
    • Remote/Goal strip mutual exclusion과 Messenger post-commit UI synchronization

    완료 조건

    • 연결, Schedule, 일반 Session 세 surface에서 동일 emoji/alias 계약을 사용한다.
    • /remote 성공이 모델 입력이나 transcript bubble을 만들지 않는다.

    10. Phase 6 — 안전 Remote 목록과 Schedule Run now

    목표

    메신저 HOME에서 Remote-enabled Schedule을 조회하고 실행한다.

    Relay 구현

    • schema version 5
      • remote_views
      • remote_items
    • HOME Farad 예약 작업 조회 action → LIST_REMOTE_ITEMS command
    • result의 emoji key/alias/state keyword만 검증·저장
    • bounded pagination card
    • Action.ShowCard inline confirmation과 별도 confirmation fallback
    • 실행 click transaction → RUN_SCHEDULE command

    Farad 구현

    • existing Scheduler store/index에서 remote-enabled 항목만 O(visible) projection
    • item token/view token을 실제 Schedule로 해석하는 bounded runtime map
    • command 수신 시 remote-enabled와 single-flight 재검사
    • existing SessionWorkflowService.submit_scheduled_run 경로 사용
    • same Schedule max 1, different Schedule concurrent

    검증

    • 실제 Schedule 이름/ID/prompt/path가 wire·Relay DB에 없음
    • stale view, token swapping, wrong client/generation
    • A와 B 연속 click 후 둘 다 실행
    • A 두 번 click → 하나 accepted, 하나 already running
    • cron/local/remote 실행 간 same-Schedule single-flight

    완료 조건

    • HOME에서 Schedule 목록·확인·실행·상태 갱신이 Stage에서 왕복한다.

    11. Phase 7 — 통합 Remote runtime mode

    목표

    일반 CHAT과 SCHEDULED가 보고 없이 Stop하면 자동 계속하고, durable report 뒤에만 기다린다.

    architecture 선행 변경

    현재 TurnLifecycleHook의 contributor는 Goal 하나다. Remote가 두 번째 실제 contributor가 되므로:

    1. docs/layers.md에 runtime contributor/arbitration 계약을 정식화한다.
    2. docs/agent.md에 Stop precedence를 기록한다.
    3. Goal과 Remote의 상호 배타를 application service에서 enforce한다.
    4. AsyncSession은 concrete Goal/Remote 타입을 import하지 않는다.

    구현

    • RemoteTurnHook
    • RemoteReport built-in/internal tool
    • RemoteInteractionCoordinator
      • Farad asyncio runtime의 유일한 interaction 응답 권위
      • desktop/Messenger ingress가 같은 resolve(interactionRef, keyword, source, expectedRevision) 호출
      • first commit만 PostBox/Future와 transcript tool result를 정확히 한 번 완료
    • per-run report receipt state
    • remote_continue transcript note
    • Stop policy
      • report receipt 없음 → RuntimeStopDecision(allow=False)
      • receipt 있음 → allow
    • Remote keyword catalog와 card payload codec
    • continuation count/wall-clock guard
    • limit reached runtime-generated event
    • feedback PostBox ingress
    • post-commit UI event
      • Messenger가 이기면 desktop question에 같은 선택 표시 + 전 버튼 잠금
      • desktop이 이기면 local UI 즉시 잠금 + Relay safe resolution event; Messenger update 없음

    예상 변경 위치:

    • packages/farad/farad/app/runtime/turn_hooks.py
    • packages/farad/farad/app/runtime/async_session.py
    • packages/farad/farad/app/runtime/config_factory.py
    • 신규 packages/farad/farad/remote_control/turn_hook.py
    • 신규 packages/farad/farad/remote_control/report_tool.py
    • transcript UI factory/i18n의 remote_continue presentation

    failure boundary

    RemoteReport tool call
→ safe payload validate
→ Relay event idempotent commit
→ receipt 반환
→ tool result transcript commit
→ Stop 허용

    Relay commit 전 오류는 receipt가 아니며 Stop을 허용하지 않는다. 무한 retry는 runtime limit guard가 고정 failure event와 abort로 끝낸다.

    검증

    • plain assistant Stop이 같은 run ID로 continuation
    • report receipt 후 Stop 허용
    • report HTTP failure 후 continuation
    • duplicate event idempotency
    • desktop/Messenger 동시 선택에서 first commit 하나만 agent 입력이 됨
    • Messenger 선택 뒤 desktop UI가 같은 결과로 즉시 잠김
    • desktop 선택 뒤 Relay event는 저장되지만 outbound delivery가 생성되지 않음
    • pending user input/abort/shutdown 우선
    • Goal + Remote 동시 활성화 거부
    • Remote mode off ordinary CHAT behavior 불변
    • SCHEDULED와 CHAT 같은 policy contract test

    완료 조건

    • 모델이 보고하지 않고 조용히 끝날 수 없다.
    • 보고한 session은 불필요한 추가 LLM call 없이 메신저 응답을 기다린다.

    12. Phase 8 — 카드 correlation, progress와 feedback

    목표

    각 카드와 버튼을 정확한 run/session interaction에 연결하고, 응답 출처와 비용 정책에 따라 같은 카드를 필요할 때만 안전하게 갱신한다.

    Relay 구현

    • schema version 6
      • 확장 action_routes
      • remote_events
      • interactions
      • revisioned message_cards
    • POST /v1/remote-events
    • RemoteReport keyword → card renderer
    • 질문은 ChatRequest로 즉시 전송
    • Messenger click transaction은 action을 reserve하고 provisional command만 생성
    • Farad resolution result 뒤 interaction final state/source commit
    • Messenger-first 선택 후 UpdateMessage delivery 1건
    • desktop-first safe resolution event는 state projection만 갱신하고 delivery를 만들지 않음
    • desktop-first stale card가 실제 클릭될 때 warning UpdateMessage delivery 최대 1건
    • current revision compare-and-set
    • consumed/expired/stale card response

    Farad 구현

    • RemoteCorrelationIndex
      • runRef/interactionRef → SessionLocator
      • SCHEDULED lookup에는 schedule_id hint 필수
    • REMOTE_FEEDBACK → exact session PostBox
    • processed interaction dedupe
    • live session이 없어도 locator로 정상 runtime open
    • RemoteInteractionCoordinator result code를 Relay command result로 반환

    카드 동작

    • 본문과 과거 상태 유지
    • Messenger-first는 선택: ... body 추가
    • desktop-first stale click은 이미 데스크톱에서 처리된 응답입니다 warning body 추가
    • 선택 submit action 전부 제거
    • Back/Home만 fresh token으로 재발급
    • stale worker가 newer card revision을 덮지 않음
    • 별도 ACK/warning 새 메시지는 만들지 않음

    검증

    • 두 session이 같은 keyword/card kind를 동시에 사용
    • 같은 session의 연속 interaction 두 개
    • old card click, duplicated click, wrong room, wrong generation
    • desktop-first 뒤 card 미클릭: update delivery 0건
    • desktop-first 뒤 첫 stale click: warning update 1건; 이후 중복 click: 추가 0건
    • Messenger-first: selected update 1건과 desktop UI synchronization
    • desktop/Messenger race: Farad first commit만 유효하고 패자는 already-resolved
    • app/Relay restart 뒤 feedback routing
    • session 10,000개 fixture에서 glob fallback이 실행되면 fail

    완료 조건

    • 어떤 action도 다른 session/run으로 전달되지 않는다.
    • Messenger-first 카드는 선택 결과로, desktop-first stale card는 warning으로 이력을 보존하며 재클릭 불가능 상태가 된다.
    • desktop-first 응답만으로 Messenger update 비용이 발생하지 않는다.

    13. Phase 9 — 보안·retention·관측성 hardening

    보안

    • credential/token/key redaction
    • action token hash at rest
    • sender/room/client/generation binding
    • RemoteReport schema에 자유 텍스트 필드가 추가되지 않는 gate
    • Messenger payload, DB, WAL, structured log DLP scan test
    • remote approval/Full Access 차단 contract test

    retention

    • expired action/view/item bounded cleanup
    • completed command/result/event/interaction/delivery retention
    • active/pending/in-flight 제외
    • cleanup index와 EXPLAIN QUERY PLAN regression

    관측성

    본문 없는 counter/latency/error-code만 기록한다.

    • inbound accepted/duplicate/rejected
    • delivery pending/in-flight/unknown
    • active/pending client와 runtime lease
    • command age/retry/result
    • event/card update latency
    • stale/expired action count
    • Messenger logical send/update cost와 provider attempt count
    • desktop-first deferred update 절약 건수와 stale warning update 건수
    • Remote continuation count와 limit reached

    운영

    • graceful shutdown과 lease release
    • SQLite backup/restore runbook
    • schema migration failure rollback/backup
    • VM disk pressure와 WAL checkpoint policy
    • health/readiness를 분리할 필요가 있는지 Stage 자료로 결정

    14. Phase 10 — Stage E2E와 production rollout

    Stage 검증 시나리오

    1. proactive pairing
    2. INTRO fallback pairing
    3. Farad restart without re-pairing
    4. two Farad instance conflict and approved takeover
    5. HOME and unauthenticated LLM usage card
    6. Schedule list, nested/fallback confirmation, Run now
    7. two different Schedule concurrent execution
    8. same Schedule duplicate rejection
    9. general CHAT /remote and alias dialog
    10. plain Stop → automatic continuation
    11. RemoteReport → desktop + Messenger feedback card → Messenger choice → exact PostBox + desktop sync
    12. desktop choice → no Messenger update → later stale click → one warning update
    13. desktop/Messenger simultaneous choice → one first commit
    14. network disconnect at every commit boundary

    • webhook non-200 retry 정책

    배포 문서

    production gate

    16. 구현 완료 판정

    기능이 “구현됨”으로 표시되려면 다음이 모두 충족돼야 한다.

    • code path와 schema가 존재한다.
    • happy path만이 아니라 duplicate/crash/stale generation 테스트가 있다.
    • 실제 이름·자유 텍스트가 boundary를 넘지 않는 DLP 테스트가 있다.
    • N=10,000 hot-path guard가 있다.
    • relevant docs와 deployment guide가 source와 일치한다.
    • Stage에서 실제 Messenger 왕복을 검증했다.

    현재 완료 범위는 Phase 1까지다. Phase 2~8이 product vertical slice, Phase 9~10이 production gate다.
