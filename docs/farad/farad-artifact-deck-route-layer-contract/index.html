    farad-artifact 덱 루트 검증 — 서브에이전트가 스킬만 읽고 만든 Farad 레이어 규약 덱

    farad-artifact 덱 루트 검증 — 서브에이전트가 스킬만 읽고 만든 Farad 레이어 규약 덱

    이번에도 사람이 슬라이드나 문단을 짜지 않았다. 서브에이전트(Sonnet)에게 Farad farad-artifact 스킬의 SKILL.md만 읽히고, 주제와 자료 경로, "자료에 없는 내용은 쓰지 마라"는 제약만 줬다. 스킬을 어떻게 쓰는지는 한마디도 알려주지 않았다 — 라우트 선택, 템플릿 사용법, 검사기 실행은 전부 에이전트가 스킬을 읽고 스스로 판단한 것이다.

    이전 AI 에이전트의 미래 덱과 다른 점은 대조군을 뒀다는 것이다. 같은 주제·같은 자료를 두 에이전트에게 각각 다른 목적지로 주문했다. 하나는 Confluence 페이지에서 발표할 슬라이드, 하나는 브라우저로 읽을 문서다. 콘텐츠 변수를 고정했으니 차이는 온전히 라우트 처리에서 나온다.

    주제는 Farad의 레이어 규약이다. 자료는 저장소의 docs/layers.md(616줄) 하나뿐이고, 독자는 Python/Qt는 알지만 이 코드베이스는 처음인 신규 입사자로 잡았다.

    이 글은 그중 덱 루트 결과다. 문서 루트 결과는 따로 정리했다.

    보는 법:

    • 페이지에서는 슬라이드가 세로로 쌓인 스택으로 읽힌다.
    • 오른쪽 위 Present를 누르면 덱이 검은 화면을 덮는다. ← → 또는 우측 하단 ‹ › 로 넘기고, Esc 또는 우측 상단 ✕ 로 나온다. 브라우저 크롬까지 지우려면 그 옆 확대 아이콘을 한 번 더 누른다.
    • 키보드가 듣지 않으면 덱을 한 번 클릭해서 포커스를 준다. Present는 이걸 알아서 해준다.

    Farad 레이어 규약

    Made with Farad

    신규 팀원 온보딩 · 2026-09-16

    Farad는 왜 다섯 레이어로 나뉘어 있는가

    다섯 레이어가 각각 무엇을 소유하고, 어디서 자주 헷갈리며, 규약과 코드가 어긋났을 때 무엇을 먼저 고치는지 30분 안에 본다.

    왜 나누는가

    레이어가 없으면 이렇게 자란다

    SidebarPanel은 이미 6,722줄·383개 정의 — attention 신호 600줄의 11배 넘게 자랐다

    • 레이어 표는 계약이지 사후 카탈로그가 아니다, 경계에 안 맞으면 코드보다 문서를 먼저 고친다
    • Attention Signal은 LOC 600줄 또는 정의 30개, 분리 목표가 아니라 검토를 시작하라는 신호다
    • 신호를 넘겼다고 무조건 쪼개지 않는다, 바뀔 이유가 여러 개인지부터 본다

    파일당 LOC(줄), 상위 hotspot

    레이어 계약

    다섯 레이어가 소유하는 것, 하면 안 되는 것

    레이어 대표 파일 소유 하면 안 되는 것
    Loader / Scanner / File Adapter extension_metadata.py, skills/loader.py 등 파일시스템 읽기·쓰기, JSON 파싱, 스키마 없는 추출, 순수 데이터 변환 Qt import, app 이벤트 발행, UI 동작 결정
    Registry / Store / Provider app/registry.py, capability_catalog.py 등 관찰 가능한 discovery 상태, provider facade, 캐시 무효화, "무엇이 있고 켜져 있나" 응답 UI 위젯 호출, UI 전용 상태 보관, archived record를 살아있는 actor로 되살리기
    Factory / Service session/factory.py, services_factory.py 등 서브시스템 간 조립, 세션 생성, turn 준비, settings 쓰기 facade 위젯에 직접 접근, UI가 저장 위치를 정하게 두기
    Runtime Contributor turn_hooks.py, goals/turn_hook.py 등 공유 hook 프로토콜로 immutable turn 스냅샷에 반응, 주입된 서비스로만 도메인 상태 소유 UI import/변경, core turn loop 소유, 다른 contributor와 mutable scratch 공유
    UI ui/panels/*, ui/widgets/*, ui_session.py 위젯, presentation 상태, 사용자 제스처, Qt-thread 세션 projection config 파일 직접 읽기/쓰기, loader/scanner 직접 호출, registry discovery 결과를 로컬 캐시로 보관

    Source: docs/layers.md "The Five Layers" 표

    자주 헷갈리는 판단 지점

    살아있는 액터와 죽은 기록은 다른 레이어

    SubAgentManager는 실행 중인 액터, SubAgentRosterIndex는 끝난 액터의 기록만 가진다

    • archived SubAgent를 여는 것도 평범한 세션 UI projection일 뿐 — 선택·보존이 액터 수명을 늘리면 안 된다

    SubAgentManager — Factory/Service

    SubAgentRosterIndex — Registry

    자주 헷갈리는 판단 지점

    폴더 이름이 아니라 스레드로 분류한다

    ui_session.py는 app/runtime/ 안에 있어도 UI 레이어다

    • asyncio 스레드의 async_session.py, turn_context_provider.py 등은 Factory/Service이고 Qt를 import하면 안 된다
    • Qt 스레드의 ui_session.py(QObject)는 UI 레이어이고, MessageItemFactory로 MessageItem을 만드는 유일한 자리다
    • ui_session.py → ui/models 의존을 잡아내는 dependency scan은 false positive다

    app/runtime/ 폴더, 안은 두 레이어

    자주 헷갈리는 판단 지점

    전역(singleton)은 원칙 금지, 예외는 근거가 있다

    Theme와 LocalizationService만 sanctioned singleton, AppSignals는 root에서 조립해 주입한다

    Theme.instance() — 허용된 예외

    LocalizationService.instance() — 허용된 예외

    AppSignals — 예외 아님

    자주 헷갈리는 판단 지점

    UI는 의도만 말하고, 저장 위치는 서비스가 정한다

    두 경로뿐이다 — App/global은 ConfigProvider·SettingsService, Runtime/session은 SettingsCascadeBuilder·SettingsStore·SharedSettingsCache다

    • UI는 AppServices.apply_* 또는 UiSession.add_*로 의도만 표현한다
    • 어느 파일·scope에 쓸지는 서비스 레이어가 정한다
    • 기존 지름길이 있어도 새 코드의 선례가 되지 않는다, 만질 때 서비스 경계로 옮긴다

    쓰기 경로

    규약과 코드가 어긋났을 때

    실제 사례: 3초 타이머가 명시적 refresh 원칙을 어겼다

    CapabilityHotReloadService가 잠깐 돌린 3초 QTimer가 매 tick마다 fingerprint 서브프로세스를 스윕해 규약을 어겼다

    • 정식 refresh 경로는 명시 트리거와 20분 DeploymentStatePoller tick, 둘뿐이어야 한다
    • 3초 타이머는 network home에서 tick마다 전체 스윕 비용을 물렸다, 코드가 계약을 어긴 사례다
    • 제거 후 20분 tick으로 되돌아갔고, 3초 tick 대비 약 400배 더 저렴해졌다

    시간당 스윕 횟수(회)

    규약과 코드가 어긋났을 때

    "코드가 틀렸다" 아니면 "계약이 틀렸다", 둘 중 하나다

    새 기능이 표에 안 맞으면 코드보다 docs/layers.md를 먼저 고친다

    • architecture.md는 아직 "4-layer"라고 쓰지만 layers.md는 Runtime Contributor를 "이제 formal layer"라고 못박는다 — 기준은 layers.md의 5개, 이럴 때도 문서부터 맞춘다

    코드가 틀렸을 때

    계약이 틀렸을 때

    레이어가 헷갈리면: 표 → layers.md → 문서부터

    오늘 가져갈 것 — 소유/금지 표를 먼저 보고, 안 맞으면 코드가 아니라 docs/layers.md를 먼저 고친다.

    에이전트가 스스로 한 일

    슬라이드 수(10장)는 에이전트가 정했다. 문서를 통째로 옮기지 않고 "슬라이드마다 결론 한 문장 + 그걸 뒷받침하는 시각자료 하나" 구조로 짰고, 화면에 안 띄우고 말로 풀 내용은 별도 발표 노트 파일로 분리했다.

    exhibit은 전부 inline SVG로 11개를 직접 그렸다. 좌표는 실제 수치에서 다시 계산했고, 색은 한 번도 리터럴로 쓰지 않고 테마 토큰만 참조해서 다크 모드를 따라간다.

    시각 QA도 실제로 했다. 스크린샷 19장을 찍어가며 차트 화살표가 값 라벨을 가리는 문제와 연결선 라벨이 박스와 겹치는 문제 2건을 발견하고, SVG 좌표를 고쳐 재검증까지 마쳤다.

    내가 직접 재검증한 것

    에이전트의 자기 보고를 믿지 않고 산출물을 직접 감사했다.

    항목 덱 문서
    check_html.py OK: 0 warning(s) OK: 0 warning(s)
    render_check.py (1280/768/375px) 통과 통과
    라우트 선택 정확 정확
    템플릿 미개봉 · --skeleton에서 시작 준수 준수
    허용 외 클래스 · 인라인 style 0건 0건
    SVG 리터럴 색상 0건 (전부 var(--accent) 등 토큰) 해당 없음
    지어낸 수치 · 출처 0건 0건

    날조 검사는 전수로 돌렸다. LOC > 600, definitions > 30, 20분 reconcile tick, SidebarPanel 6,722줄, ~3s QTimer — 전부 docs/layers.md와 docs/architecture.md 원문에 실재하는 값이다. 덱에 나오는 1,200/시간 → 3/시간, 약 400배만 원문에 없는 수치인데, 캡션에 근거식(3600s÷3s=1,200)을 함께 적어 파생값임을 밝혔다. 이건 deck.md가 "캡션은 출처와, 필요하면 근거를 명시하라"고 요구한 그대로다.

    그런데 스킬에 구멍이 있었다

    결과물이 좋았던 것과 별개로, 이 테스트의 실제 수확은 스킬 자체의 결함이다.

    SKILL.md는 덱 루트에 대해 "references/deck.md만 읽어라(read only)"라고 지시한다. 그런데 정작 그 deck.md는 본문 두 곳에서, 읽지 말라고 한 confluence-html-macro.md의 내용을 전제한다 — §Host Contract("Everything in confluence-html-macro.md §Host Contract applies")와 §Hand Off("Follow the paste steps in confluence-html-macro.md §Hand Off")다.

    작업이 끝난 뒤 에이전트에게 직접 물어봤다.

    읽음: deck.md (1회, 전체). 안 읽음: confluence-html-macro.md — SKILL.md의 "read only" 지시를 따라 deck.md만 열었습니다.

    §Hand Off가 규정하는 붙여넣기 단계를 작성하지 않았습니다. 그 절차는 confluence-html-macro.md에만 있고 저는 그걸 안 읽었습니다.

    §Host Contract 항목들을 직접 대조 확인하지 않았습니다 — 그 문서를 안 읽었으니 자동 검사가 못 잡는 항목이 있는지는 확인하지 못했습니다.

    즉 85KB짜리 완성된 덱을 받았는데, 이걸 Confluence에 어떻게 넣는지가 산출물 어디에도 없다. 검사기는 전부 통과하니 아무도 눈치채지 못한다. 위에 적은 "보는 법"은 내가 deck.md와 confluence-html-macro.md를 직접 읽고 채워 넣은 것이다.

    고약한 건 이게 지시를 잘 지킬수록 손해를 보는 구조라는 점이다. "read only"를 무시하고 옆 파일을 읽은 에이전트는 온전한 결과를 내고, 고분고분한 에이전트는 조용히 절반짜리를 낸다. 프롬프트에서 "only"는 비싼 단어다.

    고치는 방향은 둘이다. SKILL.md의 해당 줄을 두 파일 다 읽게 바꾸거나(confluence-html-macro.md가 63줄뿐이라 싸다), deck.md가 필요한 내용을 자기 안에 복제해 진짜로 self-contained하게 만들거나. "read only"의 원래 의도는 design-language.md·review.md를 읽지 않게 막는 것이었을 텐데, 문구가 의도보다 넓게 잡혔다.
