    Farad 사내 메신저 Relay 및 Remote 모드 통합 스펙

    2026-07-16

    Farad 사내 메신저 Relay 및 Remote 모드 통합 스펙

    문서 상태: 구현 기준 스펙

    기준일: 2026-07-16

    대상: packages/farad/, packages/farad-relay/

    관련 설계 보기: 구현 계획

    1. 목적

    Farad 사용자는 각자 사내망의 Linux 호스트에서 Farad 데스크톱 앱을 실행한다. 사내 메신저 OpenAPI는 중앙 VM에서만 호출할 수 있다. 따라서 중앙 VM의 Relay가 메신저와 Farad 사이에서 다음 역할을 맡는다.

    • 메신저의 암호화된 수신 이벤트를 받고 중복을 제거한다.
    • 사용자 연결, 카드, action, command를 VM 로컬 SQLite에 안전하게 보관한다.
    • 한 사용자에게 활성 Farad runtime 하나만 명령 수신 권위를 부여한다.
    • Farad에 Schedule 조회·실행·피드백 명령을 Long Poll로 전달한다.
    • 일반 CHAT과 SCHEDULED 세션이 동일한 Remote 대화 모드로 자율 진행하고, 필요할 때만 안전한 상태 요약과 선택 버튼을 메신저로 보낸다.
    • 실제 세션 제목, Schedule 이름, prompt, 경로, transcript, 도구 결과 같은 구체 텍스트는 메신저와 Relay로 보내지 않는다.

    Relay는 Farad 실행기가 아니다. 실제 모델 호출, 도구 실행, Schedule 단일 실행 판정과 세션 transcript의 권위는 항상 사용자 호스트의 Farad에 있다.

    2. 범위와 비범위

    2.1 포함 범위

    • 봇이 먼저 보내는 연결 확인 카드와 사용자가 봇을 먼저 여는 fallback
    • Farad client credential, 사용자 binding, runtime lease와 generation
    • 메신저 수신 POST /message
    • Messenger v2 CreateChatroomRequest, ChatRequest, UpdateMessageRequest
    • HOME, LLM 사용량, Remote 항목 목록, 실행 확인, 진행, 피드백 카드
    • Remote-enabled Schedule의 조회와 Run now
    • 일반 CHAT의 /remote 명령과 안전한 별칭
    • Goal과 같은 Stop 경계 기반 Remote 자율 진행
    • 클릭 후 기존 카드 이력 보존과 선택 버튼 제거
    • 다중 사용자, 동일 사용자의 Farad 다중 instance, command 재전달

    2.2 초기 비범위

    • 메신저에서 자유 텍스트를 일반 Farad prompt로 전달하는 기능
    • 모델 응답, transcript, 도구 입력·출력의 원문 미러링
    • 원격 Full Access 활성화 또는 위험 도구 승인
    • Remote와 Goal의 동시 활성화
    • 여러 선택지를 조립하는 복합 응답; V1은 한 번에 하나만 선택
    • Relay에서 LLM을 실행하거나 Schedule 정본을 저장하는 기능
    • 그룹 채팅 기반 원격 제어; V1 사용자 binding은 1:1 방 기준

    3. 핵심 결정

    4.1 권위

    데이터 단일 권위
    Session, transcript, model/tool 실행 상태 Farad Session/AsyncSession
    Schedule 정의와 실행 중 여부 Farad Scheduler
    Remote-enabled 대상과 실제 로컬 ID 매핑 Farad Remote state
    사용자와 메신저 방 binding Relay SQLite
    활성 runtime owner와 generation Relay SQLite
    inbound 중복 제거, action route, command, delivery Relay SQLite
    메신저에 보낸 카드의 msgId/msgKey Relay SQLite

    UI의 UiSession과 카드 화면은 projection일 뿐 실행 상태의 권위가 아니다.

    5. 제품 노출과 Farad UI

    5.1 기능 노출

    Remote UI는 SYSTEM/USER settings.json에서 아래 값이 true일 때만 보인다.

    {
  "features": {
    "remoteControl": true
  }
}
    • lowerCamelCase JSON boolean만 허용한다.
    • 미지정, 파싱 오류, folder/session/plugin/env 값은 false다.
    • 앱 시작 시 한 번 snapshot한다. 외부 파일 편집은 Farad 재시작 후 반영한다.
    • 이것은 UI 노출 조건이며 Relay 인증이나 실행 권한을 대신하지 않는다.

    5.2 일반 세션의 /remote

    일반 CHAT에서 /remote를 실행하면 모델에게 메시지를 보내지 않고 로컬 명령으로 처리한다.

    1. 현재 대상이 아직 materialize되지 않은 New Session이면 먼저 일반 메시지로 세션을 만들도록 안내한다.
    2. 실제 CHAT이면 Farad 표준 InputDialog로 원격 별칭 입력 창을 연다.
    3. 사용자는 고정 catalog에서 이모지 하나를 고르고 실제 세션 제목과 별개인 안전 별칭을 입력한다.
    4. Relay 연결이 없으면 pairing을 시작하고, 승인된 뒤 해당 세션을 Remote로 전환한다.
    5. 이미 연결돼 있으면 Remote binding을 commit한 뒤 즉시 Remote 모드로 전환한다.
    6. 성공한 로컬 명령은 transcript에 user/assistant bubble을 만들지 않는다.
    7. 이미 Remote인 세션에서 다시 /remote를 실행하면 현재 별칭이 채워진 관리 창을 열어 이름 변경 또는 Remote 해제를 제공한다.

    /remote는 permission_mode를 변경하지 않는다. Remote 상태는 session-scoped 실행 모드다.

    5.3 안전 별칭 규칙

    Remote 표시는 [이모지 별칭] 한 쌍이다. Session과 Schedule 모두 같은 입력 컴포넌트와 검증을 사용하며, 실제 Session/Schedule 이름에서 자동 생성하거나 잘라내지 않는다.

    • 이모지는 반드시 하나를 선택한다.
    • 임의 Unicode 붙여넣기, icon, 이미지 upload는 V1에서 허용하지 않고 Farad의 고정 emoji catalog와 검색 가능한 picker만 사용한다.
    • wire와 SQLite에는 임의 문자 대신 catalog의 emojiKey를 보내고 Relay renderer가 같은 catalog로 실제 이모지를 결정한다.
    • 최대 표시 폭은 12칸이다.
    • 한글·한자 등 전각 문자는 2칸, 영문·숫자·공백은 1칸으로 센다.
    • 따라서 한글은 최대 6자, 영문·숫자는 최대 12자다.
    • 혼합 문자열은 같은 폭 계산을 적용한다.
    • 같은 client의 활성 Remote 대상 안에서 중복을 허용하지 않는다.
    • 금지 제어문자, 줄바꿈, 양끝 공백은 거부한다.
    • 실제 이름이 비어 있거나 사용자가 기본값을 선택하면 안정적인 순번 별칭을 쓴다.

    기본값:

    • 일반 세션: [💬 세션 01], [💬 세션 02], …
    • Schedule: [🗓 예약 작업 01], [🗓 예약 작업 02], …

    5.4 Remote 설정 UI

    세 종류의 설정 surface를 둔다.

    1. Settings의 원격 연결
      • 현재 연결 안 됨, 연결 확인 대기, 연결됨, 다른 Farad가 사용 중 상태를 한 행으로 보여준다.
      • primary action은 메신저 연결, 연결 후에는 연결 관리다.
      • 연결 버튼은 pairing을 시작할 뿐 자동 승인하지 않는다. 메신저의 확인 카드 클릭이 필요하다.
    2. Schedule Remote 설정
      • Schedule 생성/편집 dialog의 기본 설정에 메신저에서 사용 toggle을 둔다.
      • toggle을 켜면 emoji picker와 별칭 입력이 같은 행에 나타난다.
      • 실제 Schedule 이름은 옆 설명과 메신저 preview에 노출하지 않는다.
    3. 일반 Session Remote 설정
      • /remote가 여는 session-scoped dialog다.
      • emoji picker + 별칭 입력, 안전 경계 한 줄, 취소/Remote 켜기를 제공한다.
      • 활성화 뒤 prompt 영역에는 작은 Remote 상태 affordance를 표시하되 permission mode와 섞지 않는다.

    입력 조합은 첨부된 picker 참고처럼 왼쪽의 정사각형 emoji button과 오른쪽의 일반 rounded-rectangle text field를 한 줄에 둔다. picker는 검색, 최근 사용, category와 emoji grid를 제공한다. upload와 custom icon tab은 V1에 넣지 않는다.

    6. 사용자 연결

    6.1 Farad가 준비하는 값

    • /appl/LINUX/Hyper/utils/singleid를 shell 없이 정확히 한 번 실행해 senderKnoxId 후보를 얻는다.
    • 명령은 bounded timeout과 출력 크기 제한을 갖고, 검증된 UTF-8 한 줄만 허용한다.
    • Farad는 client token을 생성해 Relay 등록 요청에 한 번 보낸다.
    • Farad는 장기 상태에 relayOrigin과 client token만 저장한다.
    • Linux ID, Knox ID, Messenger numeric user ID, binding ID, runtime ID는 Farad에 중복 저장하지 않는다.
    • client token은 일반 state JSON이나 transcript가 아닌 민감값 저장 경계에 둔다.

    6.2 봇이 먼저 연결 카드를 보내는 기본 경로

    사내 조회 수단으로 Knox ID에서 numeric Messenger userId를 얻을 수 있다고 전제한다.

    Farad                         Relay                         Messenger
  │ POST /v1/clients/register  │                               │
  │ knoxId + clientToken       │                               │
  ├───────────────────────────►│ pairing PENDING commit        │
  │                            ├─ CreateChatroomRequest ──────►│
  │                            │◄─ chatroomId ─────────────────┤
  │                            ├─ 연결 확인 카드 ─────────────►│
  │                            │                               │
  │                            │◄─ "연결하기" actionToken ───┤
  │                            │ binding ACTIVE commit         │
  │◄─ CLIENT_ACTIVATED ────────┤                               │
    • 1:1 CreateChatroomRequest가 기존 방을 반환할 수 있으므로 chatroomId를 저장해 재사용한다.
    • 방과 카드가 만들어졌다는 사실만으로 연결을 활성화하지 않는다.
    • 사용자가 연결하기 버튼을 눌러 sender, room, action route가 모두 일치한 transaction이 commit된 순간만 ACTIVE다.
    • 취소를 누르면 pending credential hash와 pairing attempt를 폐기한다.

    6.3 사용자가 봇을 먼저 여는 fallback

    선제 방 생성이나 directory lookup이 실패하면 사용자가 메신저에서 봇을 한 번 연다.

    • msgType=TEXT, chatMsg=INTRO도 일반 TEXT와 같은 inbound envelope로 온다.
    • Relay는 outer sender, senderKnoxId, chatroomId로 pending pairing 후보를 찾는다.
    • 같은 연결 확인 카드를 보내고 사용자 클릭 뒤 기본 경로와 같은 transaction으로 합류한다.

    6.4 재시작과 끊어진 binding

    • Farad 재시작 시 저장한 client token으로 runtime claim을 시도한다.
    • token은 있는데 Relay에 binding이 없거나 폐기됐다면 Relay가 명확한 REPAIR_REQUIRED를 반환한다.
    • Farad는 stale token을 제거하고 최초 pairing을 다시 시작한다.
    • 정상 binding이면 singleid를 다시 실행하지 않는다.

    7. 다중 instance와 runtime lease

    NFS에서는 동일 사용자의 여러 호스트가 같은 Farad client token을 볼 수 있다. token은 사용자 연결을 증명하지만 현재 command consumer를 결정하지 않는다.

    • Relay는 client마다 활성 runtime lease를 최대 하나만 둔다.
    • Farad 시작 시 POST /v1/runtime/claim으로 runtimeId, generation, leaseUntilMillis를 받는다.
    • Long Poll과 event/result 제출이 lease를 갱신한다.
    • 다른 Farad가 활성 lease 동안 claim하면 409 ACTIVE_RUNTIME_EXISTS를 받는다.
    • 명시적 takeover는 메신저 확인 카드로 사용자 승인을 받은 뒤 generation을 증가시킨다.
    • 이전 generation의 Long Poll, result, event, action route는 거부한다.
    • takeover는 기존 Farad의 로컬 실행을 강제 종료하지 않지만 더는 원격 command를 주지 않는다.

    8. Messenger API 계약

    8.1 환경별 base URL

    • Stage: https://openapi.stage.samsung.net
    • Production: https://openapi.samsung.net
    • 메시지 경로 prefix: /messenger/message/api/v2.0/message/
    • Stage key URL: https://openapi.stage.samsung.net/messenger/msgctx/api/v2.0/key/getkeys
    • Production key URL은 배포 설정의 명시값으로 받고 운영 확정 전 추정하지 않는다.

    8.2 공통 요청 헤더

    Authorization: Bearer {messenger-api-token}
x-device-id: {registered-device-id}
x-device-type: relation
Content-Type: text/plain
Accept: text/plain
System-ID: {integration-account-id}

    Messenger API token, device ID와 System ID는 Relay 배포 입력이다. 로그, SQLite, 카드 data에 넣지 않는다.

    8.3 암호화

    • 알고리즘: AES-256-CBC
    • padding: PKCS#7
    • key endpoint 응답: 정확히 96 hex 문자, 총 48 bytes
    • 앞 32 bytes: AES key
    • 뒤 16 bytes: IV
    • wire: JSON bytes → AES 암호화 → Base64 text
    • inbound: Base64 strict decode → AES 복호화 → PKCS#7 검증 → JSON 검증
    • key/IV는 메모리에만 둔다.
    • key fetch 또는 형식 검증 실패 시 Relay는 fail closed로 시작하지 않는다.

    8.4 CreateChatroomRequest

    POST /messenger/message/api/v2.0/message/createChatroomRequest
    필드 타입 필수 설명
    requestId int64 M ms 기반 unique ID
    chatType int M 0 1:1, 1 그룹, 2 그룹 Noti, 5 1:1 Noti
    receivers int64[] M numeric user ID 목록
    chatroomTitle string O 그룹 계열만 허용

    V1 pairing은 chatType=0을 사용한다. 동일 방장과 수신자의 기존 1:1 방이 있으면 기존 방을 재사용한다.

    8.5 ChatRequest

    POST /messenger/message/api/v2.0/message/chatRequest
    필드 타입 설명
    requestId int64 요청 unique ID
    chatroomId int64 대상 방
    chatMessageParams array 한 요청에 최대 10개
    msgId int64 client message unique ID
    msgType int 0 TEXT, 1 MEDIA, 7 RTF, 19 ADAPTIVE_CARD
    chatMsg string 최대 3,300자

    최대 10개는 한 HTTP 요청의 메시지 batch 크기다. Relay가 command를 10개만 저장한다는 뜻이 아니다.

    응답의 processedMessageEntries[].msgKey와 msgId를 저장해 이후 카드 갱신에 사용한다.

    8.6 UpdateMessageRequest

    POST /messenger/message/api/v2.0/message/updateMessageRequest
    • chatroomId, 원래 msgKey, 갱신용 msgType=20, 새 Adaptive Card JSON을 보낸다.
    • 선택 이후 기존 카드의 내용을 유지하면서 선택 결과와 utility action을 남기는 데 사용한다.
    • 서버가 보고한 updateTime을 카드 projection에 기록할 수 있다.

    8.7 Message Receiving API

    POST http://{relay-ip}:{port}/message
Content-Type: text/plain

    선택 header:

    • botUserEmail
    • botNotiType, 예: INTRO

    복호화된 body 필드:

    필드 타입 설명
    sender int64 numeric user ID
    senderName string 표시 이름; 저장·로그하지 않음
    senderKnoxId string Knox ID
    sentTime int64 전송 시각
    chatType string SINGLE, GROUP, BROADCAST GROUP, BROADCAST SINGLE
    chatroomId int64 방 ID
    msgId int64 메시지 ID
    msgType string TEXT, MEDIA, RTF, ADAPTIVE_CARD, UPDATED_ADAPTIVE_CARD
    chatMsg string 메시지 또는 action echo

    Relay는 정상 이벤트를 SQLite에 commit한 뒤 빈 HTTP 200 OK를 반환한다.

    일반 TEXT 예:

    <!-- {"COMMAND":"SNDCL","SNDCL":{"KND":"CLDT"}} -->안녕

    Action echo 예:

    <!-- {"COMMAND":"SNDCL","SNDCL":{"KND":"CLDT"}} -->
{"chatroomId":"...","userId":123,"messageId":456,"msgKey":"...",
 "localDate":"2026-07-15","localTime":"15:16","timeZone":"+09:00",
 "language":"ko","actionToken":"opaque-value"}

    Relay는 leading messenger comment를 제거한 뒤 자기 actionToken만 신뢰한다. chatMsg 안에 echo된 chatroomId, userId, messageId, msgKey는 routing 권위가 아니며 outer envelope와 DB route를 다시 대조한다. requestUrl은 callback URL이 아니라 평범한 data 문자열로 취급하고 사용하지 않는다.

    9. Adaptive Card 계약

    • 카드 버전은 1.3이다.
    • 현재 사내 Messenger 계약에 맞춰 submit action type은 ActionSubmit을 사용한다.
    • 중첩 실행 확인에는 host 지원 검증 후 Action.ShowCard를 사용한다.
    • 모든 실제 서버 동작은 opaque actionToken을 가진 submit action으로 시작한다.
    • URL, Knox ID, numeric user ID, local ID, Schedule ID, Session ID를 card data에 넣지 않는다.

    9.1 HOME

    첫 화면의 primary action:

    1. 📊 LLM 사용량 조회
    2. 🗓 Farad 예약 작업 조회

    LLM 사용량은 Farad pairing 없이 Relay가 미리 만든 안전한 카드로 응답할 수 있다. Schedule 조회와 Remote 대상 제어는 활성 Farad binding과 runtime lease가 필요하다.

    9.2 utility action

    모든 탐색·상태·선택 카드 마지막에는 전용 utility row를 둔다.

    • ↩️ 뒤로
    • 🏠 홈으로

    Back stack이 없거나 route가 만료됐으면 Back은 HOME으로 안전하게 이동한다. utility action도 매번 새 opaque token을 사용한다.

    9.3 실행 확인

    목록의 항목을 누르면 가능하면 같은 카드 안에서 Action.ShowCard로 확인 영역을 펼친다.

    • 펼치기 자체는 서버 왕복을 만들지 않는다.
    • 내부 실행하기만 ActionSubmit으로 Relay에 전달된다.
    • 취소는 카드 내부 상태를 닫거나 이전 view로 돌아간다.
    • host가 Action.ShowCard를 지원하지 않으면 별도 확인 카드 fallback을 사용한다.

    9.4 클릭 후 카드 이력

    Adaptive Card 1.3에는 일반적인 disabled action이 없다고 가정한다.

    • 사용자가 선택하면 기존 카드 본문은 그대로 남긴다.
    • 선택: 다시 하기처럼 실제 선택 결과를 body에 추가한다.
    • 기존 선택용 submit action은 모두 제거해 재클릭을 막는다.
    • Back/Home에는 새 token을 발급해 계속 사용할 수 있게 한다.
    • 동일 action의 중복 webhook은 같은 결과를 반환하고 command를 추가하지 않는다.

    10. Farad–Relay API

    다음은 새로 구현할 내부 계약이다. 모든 client API는 client credential을 인증하고, runtime 전용 API는 추가로 runtimeId와 generation을 검증한다.

    Method Path 역할
    POST /v1/clients/register pending client와 pairing 생성
    POST /v1/runtime/claim 활성 runtime lease 획득
    GET /v1/commands?waitSeconds=25 command 최대 1개 Long Poll
    POST /v1/commands/{commandId}/result 처리 결과를 durable ACK로 제출
    POST /v1/remote-events 진행·보고·카드 갱신 event 제출
    POST /v1/runtime/release 정상 종료 시 lease best-effort 반납

    Long Poll 규칙:

    • 빈 queue면 최대 25초 기다린 뒤 empty response를 반환한다.
    • command가 생기면 즉시 하나만 반환한다.
    • response 전송은 ACK가 아니다.
    • Farad result가 commit돼야 command가 COMPLETED가 된다.
    • 연결이 끊기거나 lease가 만료되면 같은 commandId를 재전달할 수 있다.
    • Farad는 commandId별 최근 결과를 idempotently 재제출할 수 있어야 한다.
    • generation이 바뀌면 이전 runtime의 미완료 claim은 해제되며 새 runtime이 안전하게 재처리한다.

    주요 command kind:

    • CLIENT_ACTIVATED
    • LIST_REMOTE_ITEMS
    • RUN_SCHEDULE
    • REMOTE_FEEDBACK
    • REMOTE_STOP

    11. Remote 대상 projection

    Relay는 실제 Session/Schedule ID를 알지 않는다.

    Farad가 목록 요청마다 보내는 안전 projection:

    {
  "viewId": "opaque-view",
  "items": [
    {
      "itemToken": "opaque-item",
      "kind": "schedule",
      "emojiKey": "calendar",
      "remoteDisplayName": "예약 작업 01",
      "stateKeyword": "READY"
    },
    {
      "itemToken": "opaque-item-2",
      "kind": "chat",
      "emojiKey": "speech",
      "remoteDisplayName": "세션 01",
      "stateKeyword": "WAITING"
    }
  ]
}
    • itemToken은 한 view/generation에서만 유효하다.
    • Relay는 token과 승인된 emojiKey·별칭·고정 상태만 저장한다.
    • 실제 local ID 매핑은 Farad의 Remote state가 소유한다.
    • stale view, 만료 token, 다른 client/room/generation token은 거부한다.
    • 목록은 카드 host 제한에 맞춰 bounded page로 나누며 실제 page size는 Stage 검증으로 확정한다.

    12. Schedule 원격 실행

    12.1 목록

    • Remote-enabled Schedule만 보인다.
    • 실제 이름, description, prompt, working folder는 보내지 않는다.
    • 상태는 READY, RUNNING, PAUSED, DISABLED, OFFLINE 같은 고정 keyword만 보낸다.

    12.2 실행

    사용자 실행 클릭
→ Relay가 RUN_SCHEDULE command commit
→ Long Poll로 Farad에 전달
→ Farad가 itemToken을 local Schedule로 해석
→ Remote-enabled 여부와 single-flight 재검사
→ ACCEPTED 또는 ALREADY_RUNNING result
→ Relay가 카드 갱신
    • 같은 Schedule은 cron, 로컬 Run now, Remote Run now를 합쳐 활성 실행 최대 1개다.
    • 다른 Schedule은 동시에 실행할 수 있다.
    • 사용자가 A와 B를 연달아 누르면 Relay queue에는 두 command가 순서대로 쌓이고 Farad가 하나씩 result를 제출한다. A와 B가 모두 승인되면 실행은 동시에 진행할 수 있다.
    • 실행 command가 오래 대기해도 수신 시점에 Farad가 권한과 상태를 다시 검사한다.

    13. 통합 Remote 실행 모드

    13.1 적용 대상

    • 일반 CHAT에서 /remote로 활성화한 세션
    • Remote로 실행된 SCHEDULED 세션
    • Remote-enabled Schedule의 정책상 메신저 보고가 필요한 cron/로컬 실행

    CHAT과 SCHEDULED는 시작점만 다르고 동일한 RemoteTurnHook, RemoteReport, Relay event 경계를 사용한다. 일반 세션은 계속 SessionType.CHAT, Schedule run은 계속 SessionType.SCHEDULED다.

    13.2 Stop 계약

    모델이 자연스럽게 Stop
        │
        ▼
이번 cycle에 Relay가 접수한 RemoteReport receipt가 있는가?
        ├─ 아니오: Stop 거부 → remote_continue append → 같은 AgentRun 재진입
        └─ 예:     Stop 허용 → AgentRun 종료 → 메신저 피드백 또는 다음 입력 대기

    구현 의미:

    • “끝난 턴을 새로 살린다”는 UX 표현이다.
    • 실제 구현은 AgentRun이 끝난 뒤 별도 run을 만드는 것이 아니라 Stop 직전에 가로챈다.
    • RuntimeStopDecision(allow=False)와 고정 continuation feedback으로 같은 run_id의 다음 model cycle을 실행한다.
    • continuation user entry는 transcript에 metadata.note_kind="remote_continue"로 영속한다.
    • UI는 일반 user bubble이 아니라 Remote continuation system-note row로 렌더한다.
    • Remote report 없이 assistant 최종 text만 작성해도 실행은 끝나지 않는다.

    13.3 RemoteReport

    모델이 작업을 멈추고 사용자를 기다리려면 명시적으로 RemoteReport를 호출해야 한다.

    {
  "status": "needs_feedback",
  "summaryKey": "SIMULATION_FAILED",
  "choices": ["RETRY", "STOP", "TRY_DIFFERENTLY"]
}

    V1 입력 계약:

    • status: progress, needs_feedback, completed, failed
    • summaryKey: allowlist된 안전 keyword 하나
    • choices: allowlist된 keyword 0~3개, 한 번에 하나만 선택
    • 선택적 숫자 진행률: current, total; 음수, 과도한 범위, 임의 문자열 금지
    • 자유 텍스트 summary, prompt, path, tool output 필드는 제공하지 않는다.

    RemoteReport 성공의 기준은 Messenger 전송 완료가 아니라 Relay의 durable event/outbox 접수다. Relay가 같은 eventId를 이미 받았다면 idempotent success receipt를 반환한다. 네트워크 오류나 검증 실패는 tool error이며 report receipt로 인정하지 않는다.

    13.4 사용자 피드백

    메신저 선택은 Relay에서 REMOTE_FEEDBACK command로 commit한 뒤 Farad에 전달한다.

    • Farad는 interaction, target, generation, allowed choice를 다시 검증한다.
    • 유효한 선택을 기존 session PostBox에 machine-origin user entry로 넣는다.
    • 이 입력은 새 outer AgentRun을 깨우며, Remote Stop 계약은 그대로 유지된다.
    • 중복 선택은 기존 result를 반환하고 PostBox에 다시 넣지 않는다.
    • 만료, 이미 소비됨, 다른 run의 선택은 안전한 EXPIRED_INTERACTION 카드로 응답한다.

    13.5 자율 진행 안전장치

    • Remote와 Goal은 모두 Stop 경계 owner이므로 V1에서는 동시에 켤 수 없다.
    • Goal이 켜진 session에서 /remote는 로컬 안내와 함께 거부한다. 먼저 Goal을 종료해야 한다.
    • Remote continuation은 기존 AgentRun의 max rerun, abort, pending input, context recovery 규칙을 따른다.
    • 별도의 연속 continuation 상한과 wall-clock 상한을 둔다.
    • 상한 도달 시 LLM을 다시 호출하지 않고 Farad runtime이 고정 REMOTE_LIMIT_REACHED event를 만들고 실행을 중단한다.
    • 사용자 Stop, 앱 종료, runtime takeover는 continuation보다 우선한다.

    13.6 승인과 질문

    • Remote 모드는 permission mode를 우회하지 않는다.
    • 위험 도구 승인 요청은 메신저에서 승인할 수 없다.
    • 승인 필요 시 LOCAL_CONFIRMATION_REQUIRED 고정 카드만 보내고 로컬 Farad에서 처리한다.
    • AskUserQuestion은 V1에서 Remote keyword catalog로 변환 가능한 single-select 질문만 메신저로 보낼 수 있다. 변환할 수 없으면 로컬 확인으로 남긴다.

    14. 고정 keyword와 카드 문구

    V1은 keyword 기반이다. 이모지는 고정 UI 문구에서만 소량 사용하며 의미의 유일한 전달 수단으로 사용하지 않는다.

    상태 예:

    • STARTED → 실행을 시작했어요
    • IN_PROGRESS → 작업을 진행하고 있어요
    • SIMULATION_RUNNING → 시뮬레이션을 진행하고 있어요
    • SIMULATION_FAILED → 시뮬레이션에 실패했어요
    • COMPLETED → 작업을 완료했어요
    • FAILED → 작업에 실패했어요
    • LOCAL_CONFIRMATION_REQUIRED → 로컬 Farad에서 확인이 필요해요

    선택 예:

    • RETRY → 🔄 다시 하기
    • STOP → ⏹ 그만하기
    • TRY_DIFFERENTLY → 🧭 다르게 시도하기
    • CONTINUE → ▶ 계속하기
    • BACK → ↩️ 뒤로
    • HOME → 🏠 홈으로

    표현할 수 없는 상황은 임의 문자열을 보내지 않고 일반 확인이 필요해요 상태와 안전한 선택으로 축소한다. 자유 조립 방식은 스키마 확장점으로 남기지만 V1 UI는 한 선택만 허용한다.

    15. 카드·세션·응답 correlation

    Messenger 카드 하나가 어느 Farad client, 어느 Remote 대상, 어느 run, 어느 질문의 응답인지 정확히 연결해야 한다. 이 매핑은 한 프로세스의 범용 dict 하나로 합치지 않고 네트워크 경계에 따라 두 권위로 나눈다.

    15.1 Relay의 CardInteractionStore

    Relay SQLite가 Messenger identity와 opaque Remote identity의 연결을 소유한다.

    outer sender + outer room
        │
        ▼
actionToken hash
        │
        ▼
cardRef + cardRevision + interactionRef + choiceKeyword
        │
        ▼
clientId + runtimeGeneration + runRef

    필수 관계:

    • message_cards.card_ref → room_id, msg_id, msg_key, card_kind, card_revision, state
    • action_routes.token_hash → card_ref, card_revision, interaction_id, choice_keyword, expires_at
    • interactions.interaction_id → client_id, run_ref, state, selected_keyword
    • commands.command_id → interaction_id, run_ref, generation, state

    클릭 transaction은 다음을 원자적으로 처리한다.

    1. token hash lookup
    2. outer sender/room, client, TTL, current card revision 검증
    3. action route ACTIVE → CONSUMED
    4. interaction WAITING → SELECTED
    5. REMOTE_FEEDBACK command insert
    6. 기존 카드의 update delivery insert

    UpdateMessageRequest는 card_ref의 현재 msgKey와 revision을 사용한다. 오래된 update worker가 최신 선택 결과를 덮지 못하도록 expected revision이 일치할 때만 다음 revision을 commit한다.

    15.2 Farad의 RemoteCorrelationIndex

    Farad는 Relay가 모르는 실제 local target과 session locator를 소유한다.

    runRef / interactionRef / targetRef
        │
        ▼
RemoteCorrelationIndex
        │
        ├─ CHAT session locator
        └─ SCHEDULED session locator + schedule_id hint
    • Relay command에 실제 session_id나 schedule_id를 넣지 않는다.
    • Farad가 만든 runRef, interactionRef, targetRef만 Relay와 공유한다.
    • index value는 SessionType과 정확한 lookup hint를 포함해 NFS glob fallback을 피한다.
    • active lookup은 O(1) dict이며, restart에 필요한 bounded projection은 Farad data dir의 단일 Remote index 파일로 저장한다. Remote 대상마다 작은 파일을 startup에 읽지 않는다.
    • transcript가 대화 정본이고 index는 locator projection이다. 손상 시 전체 session scan을 시작 시점에 수행하지 않고 명시적으로 열린 Remote session이나 Relay reconcile 대상만 복구한다.
    • REMOTE_FEEDBACK을 받으면 runRef와 interactionRef가 같은 session의 현재 waiting interaction인지 확인한 뒤 그 session PostBox에 넣는다.

    15.3 mapping lifecycle

    Farad RemoteReport
→ eventId + runRef + interactionRef
→ Relay interaction/card/action rows commit
→ ChatRequest 또는 UpdateMessageRequest
→ msgId/msgKey 저장
→ 사용자 actionToken 클릭
→ Relay command commit
→ Farad RemoteCorrelationIndex lookup
→ 정확한 AsyncSession PostBox

    card, action, interaction, command, local session 중 하나라도 현재 generation과 일치하지 않으면 추측해서 전달하지 않고 stale/expired 결과로 끝낸다.

    16. Relay SQLite

    16.1 현재 구현된 schema

    테이블 역할
    inbound_events inbound dedupe, TEXT→HOME 또는 action pending
    deliveries HOME semantic outbox, claim lease, retry

    현재 schema version은 1이고 deliveries.kind는 home만 지원한다.

    16.2 목표 schema

    테이블 핵심 값 역할
    client_installations client ID, credential hash, state Farad client identity
    messenger_bindings client, sender, Knox ID, room 승인된 사용자·방 binding
    pairing_attempts state, request IDs, expiry 선제/fallback pairing 재시작
    runtime_leases runtime ID, generation, expiry client당 활성 command consumer 하나
    inbound_events event ID, room, sender, kind webhook dedupe
    action_routes token hash, client, room, kind, expiry 버튼 권한·TTL·single-use
    remote_views view ID, client, generation, expiry 목록 generation
    remote_items view, item token, kind, emoji key, alias, state 안전 projection; local ID 없음
    commands command ID, client, kind, state, lease Long Poll queue
    command_results command ID, result code, safe payload durable ACK·idempotency
    remote_events event ID, run ref, keyword 진행·보고 dedupe
    interactions interaction ID, run ref, state 피드백 single-consume
    message_cards room, msg ID/key, card kind, revision, state 정확한 기존 카드 갱신
    deliveries semantic kind, state, retry lease outbound outbox

    모든 사용자별 hot query는 client_id가 선두인 index와 bounded limit을 사용한다. 사용자별 DB 파일을 만들지 않는다.

    16.3 저장하지 않는 값

    • Messenger API token
    • AES key와 IV
    • raw Farad client token; Relay에는 slow hash만 저장
    • senderName
    • 실제 Session/Schedule ID와 이름
    • prompt, working folder, transcript
    • 자유 텍스트 chatMsg
    • exception message와 Messenger response body

    16.4 retention

    SQLite는 무한히 쌓지 않는다.

    • expired action route와 remote view/item은 주기적인 bounded batch로 삭제한다.
    • 완료 command/result, delivered delivery, consumed interaction/event는 운영 기본 보존 기간 뒤 bounded batch로 정리한다.
    • 기본 보존 기간은 배포 설정으로 두고, Stage 운영 자료로 production 값을 확정한다.
    • cleanup은 HTTP handler나 Long Poll hot path에서 전체 scan하지 않는다.
    • active/pending/in-flight 행은 retention 대상이 아니다.

    17. 중복·실패·비정상 신호

    상황 처리
    같은 inbound msgId 재전송 200, 새 action/command 없음
    action을 두 번 클릭 기존 command/result 반환, 새 command 없음
    Long Poll 응답 유실 lease 만료 후 같은 command 재전달
    result 응답 유실 같은 commandId result idempotent 재제출
    stale view/item token 거부 후 목록 새로고침 안내
    sender/room 불일치 200 또는 안전한 거부, mutation 없음
    이전 runtime generation 409/401 계열 safe code, mutation 없음
    Farad offline command는 SQLite pending 유지, 카드에 offline 표시
    local Farad는 token 보유, Relay binding 없음 REPAIR_REQUIRED, stale token 제거 후 재연결
    Relay crash after commit before 200 webhook retry dedupe, outbox 유지
    delivery claim 중 crash lease 만료 후 재claim
    Messenger delivery 결과 불명 공급자 idempotency 확인 전 DELIVERY_UNKNOWN, 무조건 재전송 금지
    Remote report 없이 모델 Stop 같은 AgentRun 자동 continuation
    Remote continuation 상한 도달 runtime 고정 failure event 후 abort

    18. 다중 사용자 예시

    사용자 A / client_A / room_A / runtime generation 4
  ├─ 세션 01       WAITING
  └─ 예약 작업 01 READY

사용자 B / client_B / room_B / runtime generation 2
  └─ 예약 작업 01 RUNNING

사용자 C / client_C / room_C / runtime 없음
  └─ command RUN_SCHEDULE PENDING
    • A와 B의 예약 작업 01은 표시 문자열이 같아도 client scope가 달라 충돌하지 않는다.
    • action token은 client, sender, room, view/card generation에 묶인다.
    • C가 offline이어도 command는 다른 사용자의 Long Poll에 노출되지 않는다.
    • C가 정상 runtime lease를 얻으면 자기 pending command 하나부터 받는다.

    19. 전체 시나리오

    19.1 일반 세션 /remote

    사용자: 일반 CHAT에서 /remote
Farad:  emoji + 별칭 입력 창("[💬 세션 01]")
사용자: 확인
Farad:  연결이 없으면 pairing, 있으면 Remote mode commit
사용자: 로컬에서 작업 요청
모델:   한 cycle 작업 후 그냥 Stop
Farad:  remote_continue를 append하고 같은 AgentRun 계속
모델:   사용자 판단 필요 → RemoteReport(NEEDS_FEEDBACK)
Relay:  event + card update를 commit하고 receipt
Farad:  Stop 허용, session은 feedback 대기
사용자: 메신저에서 "다르게 시도하기"
Relay:  REMOTE_FEEDBACK command commit
Farad:  PostBox에 feedback append, 새 AgentRun 시작

    19.2 Schedule 목록부터 피드백까지

    HOME → Farad 예약 작업 조회
→ LIST_REMOTE_ITEMS command
→ Farad가 안전 별칭 목록 반환
→ 사용자가 예약 작업 01 펼침
→ 같은 카드의 실행 확인
→ 실행하기
→ RUN_SCHEDULE command
→ Farad single-flight 검사 후 SCHEDULED session 시작
→ Remote mode가 보고 없는 Stop을 계속 진행
→ RemoteReport(SIMULATION_FAILED, RETRY/STOP/TRY_DIFFERENTLY)
→ 사용자가 RETRY
→ 기존 카드는 선택 결과를 남기고 버튼 제거
→ REMOTE_FEEDBACK command
→ 같은 SCHEDULED session PostBox에 전달
→ 재실행 진행 후 RemoteReport(COMPLETED)

    19.3 A와 B를 연달아 실행

    • Relay는 A, B command를 각각 commit한다.
    • Long Poll은 A 하나를 주고 result를 받은 뒤 B를 준다.
    • Farad가 A와 B를 각각 승인하면 서로 다른 Schedule이므로 동시 실행한다.
    • 진행 event와 카드는 runRef/cardRef로 분리한다.
    • A가 피드백을 기다려도 B 실행은 계속할 수 있다.

    20. 성능과 운영

    • Long Poll은 (client_id, state, available_at_ms) index로 자기 command 최대 1개만 찾는다.
    • delivery claim과 cleanup은 configured batch 상한을 넘지 않는다.
    • inbound HTTP handler는 Messenger API를 동기 호출하지 않는다.
    • Relay SQLite는 초기에는 process 하나가 소유하고 async request concurrency만 허용한다.
    • Farad startup은 remote-enabled target마다 작은 파일을 읽지 않는다. 하나의 bounded Remote index를 순차 read하고 local ID를 O(1)로 조회한다.
    • ordinary turn마다 NFS 파일 scan, singleid 실행, Relay 목록 재동기화를 하지 않는다.
    • Remote mode 상태 변경은 commit 후 해당 session runtime snapshot만 invalidate한다.

    21. 현재 구현 상태

    구현됨

    • 독립 farad-relay package와 Uvicorn entry point
    • bounded POST /message, GET /healthz
    • strict Base64 inbound adapter와 AES-256-CBC/PKCS#7 codec
    • Stage key fetch와 Messenger 공통 인증 header
    • official inbound field 검증과 TEXT 원문 폐기
    • exact optional senderKnoxId allowlist
    • SQLite WAL inbound_events/HOME deliveries, dedupe, lease, retry
    • HOME Adaptive Card renderer와 Back/Home action
    • encrypted Stage/Production v2 ChatRequest client
    • Farad startup-only features.remoteControl 노출 provider
    • /appl/LINUX/Hyper/utils/singleid 안전 실행 adapter

    아직 구현되지 않음

    • CreateChatroomRequest, UpdateMessageRequest
    • delivery worker와 action route 발급
    • pairing, client credential 저장, runtime lease
    • Farad–Relay Long Poll/result/event API
    • /remote command, 별칭 dialog와 Remote state
    • Schedule safe projection과 Run now command adapter
    • RemoteTurnHook, RemoteReport, remote_continue
    • progress/feedback card, 선택 후 카드 갱신
    • retention, multi-instance takeover, production 운영 gate

    22. 완료 조건

    다음 조건을 모두 만족해야 기능 완료로 본다.

    1. 사용자가 봇을 먼저 열지 않아도 연결 확인 카드를 받고 승인할 수 있다.
    2. fallback INTRO 연결도 같은 binding transaction으로 합류한다.
    3. Farad 재시작 후 정상 token이면 재pairing 없이 Long Poll을 재개한다.
    4. 같은 사용자의 Farad 두 개가 동시에 command를 소비하지 않는다.
    5. 일반 CHAT에서 /remote로 별칭을 입력하고 Remote 모드를 켤 수 있다.
    6. Remote report 없이 Stop한 모델은 같은 AgentRun에서 계속 진행한다.
    7. Remote report가 durable 접수된 경우에만 session이 피드백을 기다린다.
    8. 메신저 선택이 정확한 session PostBox에 한 번만 전달된다.
    9. 같은 Schedule은 중복 실행되지 않고 다른 Schedule은 동시 실행된다.
    10. 실제 Session/Schedule 이름, prompt, path, transcript, 도구 결과가 Relay DB·로그·카드에 없다.
    11. 클릭한 카드는 이력을 보존하면서 선택 결과를 표시하고 재클릭할 수 없다.
    12. webhook, Long Poll, result, event의 중복과 crash 경계를 통합 테스트가 검증한다.
    13. Stage에서 암호화 key fetch, proactive pairing, 카드 send/update, inbound action 왕복을 검증한다.
    14. Relay/Farad focused tests, Ruff, strict mypy와 관련 architecture gate가 통과한다.
