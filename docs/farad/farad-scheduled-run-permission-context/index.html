    Farad 스케줄 실행에 허용 도구 알려주기 — Claude Code 벤치마크와 구현 계획

    2026-07-03

    Farad 스케줄 실행에 허용 도구 알려주기 — Claude Code 벤치마크와 구현 계획

    Farad의 스케줄 실행(예약 작업)은 사람이 지켜보지 않는 무인 실행이다. 그래서 도구 승인 프롬프트를 띄울 수 없고, 미리 승인해 둔 패턴(permissions.allow)에 맞는 도구만 자동으로 실행된다. 문제는 모델이 이 사실을 전혀 모른 채 실행된다는 것. 이 글은 그 문제를 정리하고, Claude Code(CC) 원본 소스를 벤치마크한 결과와 Farad에 넣을 변경 두 가지를 설명한다.

    1. 지금 무슨 문제가 있나

    스케줄 태스크가 실행되면 Farad는 이렇게 동작한다.

    1. 격리된 SCHEDULED 세션을 만들고 권한 모드를 dont_ask로 연다 (전체 권한 태스크면 bypass).
    2. 태스크의 settings.json에 미리 승인해 둔 permissions.allow 패턴 (예: Bash(git status:*))에 맞는 도구 호출만 자동 허용. 나머지 승인 필요 도구는 자동 거부.
    3. 모델에게 가는 첫 메시지는 "You are executing a scheduled task" + 태스크 이름/설명뿐. 무인 실행이라는 것도, 어떤 도구가 허용돼 있는지도 알려주지 않는다.

    그리고 거부당했을 때 모델이 받는 문구가 이게 전부다:

    DONT_ASK mode blocked tool requiring user approval.

    이 한 줄에는 (a) 뭐가 허용돼 있는지, (b) 재시도해 봐야 소용없다는 것, (c) 그럼 뭘 해야 하는지가 전부 빠져 있다. 그 결과 모델은 이런 삽질을 한다:

    • git push 거부 → git push origin main으로 바꿔서 재시도 → 또 거부 → 또 변형…
    • 승인이 필요 없는 순수 read-only 작업으로 끝낼 수 있는데도 엉뚱한 우회를 시도
    • 매 거부가 LLM 왕복 하나씩을 태움 — 30분 hard timeout 예산과 토큰을 낭비

    아이러니하게 이 낭비는 이미 측정까지 되고 있다. 실행 기록에 거부된 도구 호출 수(denied_tool_count)가 amber 칩으로 표시된다. 측정만 하고 예방은 안 하고 있는 셈.

    2. Claude Code는 어떻게 하나 (벤치마크)

    Farad는 도구 이름·스키마·동작을 CC 스펙에 맞추는 걸 원칙으로 하므로, 구현 전에 CC 원본 소스(ref_src/claude-code-sourcemap/restored-src/)를 확인했다. 요약:

    질문 CC의 답
    허용 규칙을 프롬프트에 미리 열거하나? 안 한다
    거부 메시지는? 도구명 + 이유 + 행동 지침이 담긴 정교한 문구
    권한 모드를 프롬프트로 알려주는 선례는? 있다 (plan/auto 모드 지시 블록)
    "부족한 권한을 마지막에 보고하라"는 지시? 있다 (auto 모드 거부 메시지)

    사전 열거는 안 한다

    getAllowRules()가 모으는 허용 규칙은 권한 판정과 설정 UI에서만 쓰이고, 시스템 프롬프트나 리마인더 텍스트 어디에도 들어가지 않는다. CC의 headless 실행(-p/SDK)은 호출자가 --allowedTools로 도구를 직접 큐레이션하는 사용 사례라, 모델에게는 거부 메시지로만 알려준다.

    대신 거부 메시지에 전부 건다

    CC의 don't ask 모드 거부 문구 (utils/messages.ts:237):

    Permission to use ${toolName} has been denied because Claude Code is running
in don't ask mode. IMPORTANT: You *may* attempt to accomplish this action
using other tools that might naturally be used to accomplish this goal, e.g.
using head instead of cat. But you *should not* attempt to work around this
denial in malicious ways ... If you believe this capability is essential to
complete the user's request, STOP and explain to the user what you were
trying to do and why you need this permission.

    포인트가 세 개다.

    • 어떤 도구가, 왜 거부됐는지 명시한다.
    • 합리적 우회는 허용, 의도를 뚫는 우회는 금지를 구분해 준다.
    • 사용자가 없는 컨텍스트(서브에이전트)용 변형은 어미가 바뀐다: "Try a different approach or report the limitation to complete your task" — 멈추고 기다리는 대신 보고하고 계속하라는 것.

    auto 모드 거부 메시지에는 이런 지시까지 있다 (messages.ts:273):

    At the end of your session, recommend what permission rules to add
so you don't get blocked again.

    그리고 "read-only 작업은 여전히 쓸 수 있다"고 명시해 주는 선례도 있다 (messages.ts:296): "reading files, searching code, and other read-only operations … can still be used."

    3. 그래서 Farad에는 이렇게 넣는다

    변경은 두 곳이다.

    변경 1 — 스케줄 시작 프롬프트에 무인 실행 + 권한 안내 (확장)

    _compose_prompt()가 만드는 첫 메시지에 이런 섹션을 붙인다 (시안):

    This is an unattended scheduled run. No user is available to approve
tool calls or answer questions (interactive tools like AskUserQuestion
will fail immediately).

Tool permissions for this run:
- Read-only tools (Read, Grep, ...) are always available.
- These patterns are pre-approved and run automatically:
    Bash(git status:*)
    Bash(pytest:*)
- Any other tool call that would need approval is denied automatically.
  Do not retry a denied call with variations. If a missing permission
  blocks the task, note it in your final summary so the user can
  pre-approve it for future runs.

    전체 권한(bypass) 태스크면 목록 대신 "모든 도구가 사전 승인됨" 한 줄만.

    이건 CC에는 없는 의도적 확장이다. 근거:

    • CC headless는 호출자가 도구를 직접 고르는 SDK 사용 사례지만, Farad 스케줄은 최종 사용자가 만든 태스크 + 태스크별로 누적된 패턴이라 fire 시점에 정확한 목록이 공짜로 나온다.
    • Farad의 주 사용 모델(GLM-5.1, Kimi K2.6)은 Claude보다 암묵적 제약 추론이 약해서 명시적 열거의 이득이 크다.
    • 문구 재료(read-only 안내, "pre-approved" 뉘앙스)는 전부 CC 선례에서 조달했다.

    주의해서 지킬 것: "목록에 있는 것만 쓸 수 있다"고 쓰면 안 된다. dont_ask에서도 read-only 도구는 패턴 없이 항상 허용이라, 잘못 쓰면 모델이 멀쩡한 Read/Grep까지 피하는 반대 방향 삽질이 생긴다. 그래서 3단(read-only 자유 / 패턴 사전 승인 / 나머지 자동 거부) 구조가 필수다.

    변경 2 — 거부 메시지를 CC 수준으로 (매칭)

    core/permission.py의 두 문구를 CC 패턴으로 교체한다. Before:

    DONT_ASK mode blocked tool requiring user approval.

    After (시안 — 도구명 포함 + 이유 + 행동 지침):

    Permission to use Bash has been denied: this is an unattended scheduled
run and no user is available to approve it. You may accomplish the goal
with other permitted tools in reasonable ways, but do not retry the same
call or bypass the intent of this restriction. If this capability is
essential, note it in your final summary and recommend what permission
rules the user should pre-approve for future runs.

    어미는 CC의 STOP-and-wait("멈추고 사용자에게 물어라")가 아니라 서브에이전트/auto 모드 계열("보고하고 계속하라")을 쓴다 — 스케줄 실행에는 기다릴 사용자가 없기 때문이다. 이 "요약에 보고 + 규칙 추천" 지시는 기존 UX와 정확히 맞물린다: 사용자는 실행 기록에서 거부 칩을 보고 → 요약에서 뭐가 필요했는지 읽고 → "Run now to pre-approve"로 그 패턴을 승인해 주면 다음 실행부터 안 막힌다.

    안 하기로 한 것

    • 거부 N회 누적 시 run abort: CC도 don't ask 모드 거부에는 한도를 안 건다 (auto 모드 classifier 거부에만 연속 3회/총 20회). Farad에는 이미 30분 watchdog + 거부 수 집계 + 연속 실패 자동 비활성화가 있어서 지금은 불필요.
    • 매 턴 리마인더 재주입: CC의 plan/auto 모드는 매 턴 full/sparse 지시 블록을 주입하지만, 스케줄 run은 단일 submit이라 시작 프롬프트 1회로 충분하다.

    4. 변경 지점 요약

    항목 위치
    시작 프롬프트 preamble farad/scheduler/executor.py — _compose_prompt()
    사전 승인 패턴 조회 ScheduleStore.permission_allow(task_id)
    거부 메시지 2종 farad/core/permission.py (ask→deny 변환부)
    CC 근거 restored-src/src/utils/messages.ts:216-298, utils/permissions/permissions.ts:503-517, 944-951
