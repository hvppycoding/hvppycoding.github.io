    경량 HTML 뷰어 검토 — 에이전트 HTML 산출물용 별도 프로세스 뷰어 (가칭 hview)

    경량 HTML 뷰어 검토 — 에이전트 HTML 산출물용 별도 프로세스 뷰어 (가칭 hview)

    2026-07-04. 발단: GeekNews 29347 — "에이전트 산출물은 Markdown보다 HTML이 낫다" (표·SVG·JS 인터랙션·일회용 도구). Farad가 이 방향을 쓰려면 HTML을 여는 경로가 필요한데, Farad 내장(QWebEngineView in-process)은 성능 부담으로 배제(사용자 결정). 별도 프로세스로 뜨는 경량 뷰어를 만들어 hrun 커맨드(hrag 패턴)로 배포하는 안을 검토한다.

    TL;DR

    • 엔진을 새로 만드는 선택지는 없다. HTML 산출물의 핵심 가치가 JS 인터랙션(탭·슬라이더·캔버스) 이므로 진짜 엔진이 필요하고, no-JS 경량 렌더러(litehtml 등)는 목적 자체를 잃는다. "가벼운 브라우저를 만든다" = 기존 엔진 + 미니멀 뷰어 셸 + 상태(프로필) 정책이 작업의 본체다. "가벼움"은 엔진이 아니라 셸·상태·수명주기에서 온다 — 엔진 프로세스 비용은 어차피 크롬급이다 (§4 "크롬급의 범위").
    • 권장: PySide6 + QtWebEngine 단일창 뷰어 hview. 결정적 이유는 배포 채널 적합성 — pip wheel만으로 완결되는 유일한 실엔진이라 hrun python toolkit + wheelhouse 모델에 그대로 실리고, PySide6(Addons 포함) wheel은 farad 때문에 이미 망내에 반입돼 있어 새 외부 패키지 승인·반입이 없다. 단 별도 venv 디스크(수백 MB)는 실비용 — farad 설치 머신에선 farad venv 공유로 줄일 수 있다(최적화이지 전제는 아님). 스택이 같아 유지보수 지식도 재사용된다.
    • Chrome/Firefox의 NFS 프로필 락 문제는 "상태를 없애서" 구조적으로 제거한다. off-the-record 프로필(디스크 무기록)이 기본 — 상태가 없으면 락도 없다. 상태가 꼭 필요해지면 host-local($XDG_RUNTIME_DIR, /tmp)에만 두고 NFS 홈에는 절대 두지 않는다.
    • 소스는 hrag처럼 독립 pip 패키지(farad·hrun 의존 없음), hrun 저장소에는 toolkits/hview/ 래퍼만 추가. farad는 detached 프로세스로 spawn.
    • 차별화 기능: --watch live-reload — 에이전트가 HTML을 고치는 동안 뷰어가 자동 갱신. 기사에서 말하는 "spec 목업 반복", "일회용 도구" 워크플로우가 이걸로 완성된다.
    • Plan B: ① firefox 임시 프로필 래퍼(zero-install 폴백), ② pywebview(WebKitGTK) — 각각 한계가 명확해 후순위 (§6).

    1. 문제 정의 — 기존 브라우저가 안 맞는 이유

    주 환경: 여러 사용자가 공유하는 저사양 HPC(RHEL 8.10, NFS 공유 홈, 원격 X11/VNC) + Windows.

    1. 무게. Chrome/Firefox는 뷰어 용도 대비 과체중 — 다만 정확히 하면, 페이지 렌더링 자체의 비용이 아니라 브라우저 인프라의 비용이다: 백그라운드 서비스·업데이터·확장· 세션 복원·탭 프로세스 트리·프로필 초기화. 뷰어는 이 중 아무것도 필요 없는데 전부 딸려온다. 공유 장비에서 사용자당 이 상주 비용이 크다. (렌더링 엔진 자체의 RAM은 어떤 선택을 해도 비슷하다 — §4 "크롬급의 범위" 참고.)
    2. 프로필 관리. 사용자의 "진짜" 브라우징 프로필과 에이전트 산출물 뷰잉이 섞인다. 산출물 뷰잉은 세션성(열고-보고-닫기)인데 브라우저는 영속 프로필을 전제로 설계돼 있다.
    3. 멀티호스트 프로필 락 (실제 겪은 pain). NFS 공유 홈에서 호스트 A에 firefox가 떠 있으면 호스트 B에서 열 때 프로필 락(~/.mozilla/.../lock·.parentlock, Chrome은 SingletonLock)에 걸려 "already running" 에러. 단일 머신 가정의 설계가 HPC 멀티호스트 사용과 충돌한다.
    4. Farad 내장 배제. QtWebEngine을 farad 프로세스에 올리면 상주 RAM·기동 시간이 늘고 메인 UI 응답성 리스크가 생긴다. 뷰잉은 간헐적 작업이므로 별도 프로세스가 맞다 — 닫으면 메모리가 온전히 반환된다.

    2. 요구사항

    기능

    • file:// HTML 렌더 (self-contained 파일이 기본 대상), 내부망 http(s) URL도 허용
    • 최신 CSS + JS 실행 (인터랙션이 핵심 가치)
    • 뷰어 UX: 명령 한 번에 창 하나, ESC/Ctrl+W로 닫기, zoom(Ctrl±), find(Ctrl+F)
    • --watch: 파일 변경 감지 자동 reload (에이전트 반복 루프 지원)

    비기능

    • RHEL 8.10(glibc 2.28) + Windows, 동일 코드
    • 저사양 공유 HPC — 상주 데몬 없음, 닫으면 자원 반환, 원격 X11/VNC에서 소프트웨어 렌더 동작
    • NFS 공유 홈 + 멀티호스트 동시 실행 안전 (락 파일 금지)
    • 폐쇄망 — 외부 CDN 접근 불가 전제 (→ §5.5 self-contained 규약)
    • 배포: hrun toolkit 커맨드 + pip 패키지 (Windows/개발 환경)

    3. 접근 재정의 — 만드는 것은 "셸 + 상태 정책"

    렌더링 엔진(Chromium/WebKit) 개발·포크는 논외다. 실제로 만들 것은:

    ┌───────────────────────────────────────────────┐
│ hview 셸 (수백 줄 규모)                          │
│  CLI 파싱 / 단일창 / 단축키 / watch-reload       │
├───────────────────────────────────────────────┤
│ 상태 정책 ← 여기가 기존 브라우저와의 진짜 차별점    │
│  off-the-record 기본 (디스크 무기록 → 락 없음)    │
│  잔여 상태는 host-local만, NFS 홈 금지            │
├───────────────────────────────────────────────┤
│ 렌더링 엔진 (기성품 선택)                         │
│  QtWebEngine(Chromium) / WebKitGTK / 기성 브라우저│
└───────────────────────────────────────────────┘

    기존 브라우저의 문제(§1의 2·3번)는 엔진 문제가 아니라 영속 프로필 전제의 문제다. 뷰어는 프로필이 필요 없으므로, 상태를 갖지 않는 셸을 만들면 문제가 소멸한다.

    4. 스택 옵션 비교

    옵션 렌더 충실도 RAM(추정)* 추가 배포 비용 멀티호스트 Windows 비고
    A. PySide6 QtWebEngine ✅ Chromium 그대로 ~200–350MB/창 pip wheel만 (이미 망내 반입); 전용 venv 디스크는 실비용 off-the-record로 해결 동일 코드 LGPL-3
    B. pywebview (WebKitGTK/WebView2) OS마다 다른 엔진 ~150–300MB GTK+PyGObject rpm 의존 해결 가능 엔진이 달라짐 렌더 결과 diverge
    C. 기성 브라우저 래퍼 (firefox -no-remote -profile <tmp>) 최상 ~400MB+ 0 (설치돼 있으면) 임시 프로필로 우회 별도 처리 뷰어 UX 아님, 기동 느림
    D. no-JS 렌더러 (QTextBrowser/litehtml) CSS 부분집합, JS 없음 <50MB 0 해당 없음 동일 목적 상실 — 탈락
    E. Electron / CEF / Tauri Chromium/WebView 200MB+ 별도 런타임 반입 해결 가능 가능 폐쇄망 배포·스택 이질성 — 탈락

    * 실측 필요 항목 (§7). 다중 프로세스 합산 RSS 기준 추정치.

    A를 권장하는 결정적 이유 — 선택의 주체는 PySide6가 아니라 엔진이다. hview는 별도 프로세스이므로 farad와 UI 스택을 맞추는 것 자체에는 아무 가치가 없다(공유 위젯·테마 없음). 결정 순서는 이렇다: ① 인터랙티브 HTML에는 실엔진(Chromium/WebKit)이 필요하고, ② 폐쇄망에서 pip wheel만으로 반입되는 실엔진은 QtWebEngine이 유일하며(PySide6-Addons wheel이 Chromium을 통째로 담고 있다), ③ QtWebEngine을 고르는 순간 셸은 Qt가 된다 — PySide6는 엔진의 배송 수단 이다. 나머지 실엔진은 전부 pip 밖 반입 경로가 필요하다: WebKitGTK는 시스템 rpm(wheelhouse로 못 나름), CEF 파이썬 바인딩(cefpython3)은 사실상 unmaintained, Electron/Tauri는 별도 런타임 바이너리 반입. 부수 이점 — 같은 노드에서 farad가 같은 Qt 기반으로 이미 동작(플랫폼 리스크 기검증), PySide6 wheel이 이미 망내 반입돼 신규 승인 불요, 팀 숙련도 — 은 보너스지 근거의 본체가 아니다.

    B는 "가볍다"는 장점이 있지만 Linux(WebKitGTK)/Windows(WebView2) 엔진이 달라 에이전트가 만든 HTML이 환경마다 다르게 깨질 수 있고, RHEL 8의 webkit2gtk3 버전 리스크 + GTK/PyGObject 의존이 Qt 단일 스택에 이질 계층을 더한다. C는 폴백으로만 가치 있다(§6).

    반입 vs 설치 — 진짜 제약의 위치. 폐쇄망 반입 자체는 일회성 작업이라 결정 게이트가 아니다 (사용자 확인). 진짜 제약은 배포 모델: hrun은 NFS 공유 스토리지에 파일을 놓는 방식이라 노드별 root 설치가 필요 없는데, pip wheel은 이 모델에 그대로 맞고 시스템 rpm(webkit2gtk3, gtk3 등)은 전 노드 설치가 필요하다(이미 깔려 있지 않는 한 — §7 확인 항목). 반입이 자유로워도 이 구도는 유지되고, OS 간 엔진 일관성 논거도 그대로다.

    "크롬급"의 범위 — 충실도와 무게 양쪽 다 크롬급이 맞다. QtWebEngine은 Chromium (Blink+V8) 그 자체다. 충실도: 렌더링·JS·Canvas·WebGL(원격에선 SwiftShader 소프트웨어 폴백) 모두 Chrome과 동일 계열. 차이는 ① Chromium 버전이 Qt 릴리스에 고정된 스냅샷 + 보안 백포트라 최신 Chrome 대비 1년 안팎 랙(표준 HTML/CSS/JS 리포트에는 실질 무영향), ② Google 서비스·확장· Widevine 없음, ③ 공식 바이너리에 독점 코덱(H.264/AAC) 미포함 — mp4 재생만 안 되고 WebM은 된다. LLM이 생성하는 HTML은 사실상 Chrome 기준으로 만들어지므로 호환성 면에선 오히려 최적. 무게: 엔진 프로세스 비용도 크롬급이다 — 창 하나가 Chrome 탭 몇 개 수준의 RAM(추정 200–350MB)을 쓴다. 즉 hview의 "가벼움"은 더 가벼운 엔진에서 오는 게 아니라 브라우저 인프라 제거(서비스·업데이터·확장·탭 트리·프로필 없음), 수명주기(열고-보고-닫으면 0으로 복귀), 상태 정책(무기록)에서 온다. 엔진 자체까지 가볍길 원하면 선택지는 WebKitGTK(소폭) 아니면 no-JS 렌더러(대폭, 목적 상실)뿐이라는 트레이드오프를 §4 표가 보여준다.

    5. 권장안 — hview 설계

    5.1 프로세스·상태 모델

    • 창 하나 = 프로세스 하나 (MVP). 뷰어 시맨틱(evince처럼) — 닫으면 전부 반환.
    • off-the-record 프로필 기본: QWebEngineProfile() 기본 생성자가 off-the-record — 쿠키·캐시·스토리지 전부 메모리, 디스크 무기록. 락 파일이 생길 곳이 없다.
    • 영속 상태(창 geometry, zoom 기억 등)는 MVP에서 넣지 않는다(YAGNI). 필요해지면 $XDG_RUNTIME_DIR(host-local) 아래에만 — NFS 홈(~/.hview 같은 것) 금지.
    • 상주 데몬·single-instance 서버 없음 (MVP). RAM 절약용 per-host 단일 인스턴스는 Phase 2(§8).

    5.2 UX 최소 스펙

    • 창: 슬림 헤더 1줄(문서 <title> 또는 파일명, reload 버튼, watch 상태 표시) + WebView. 탭·주소창·북마크·히스토리 없음 — 브라우저가 아니라 뷰어다.
    • 단축키: ESC/Ctrl+W 닫기, Ctrl+R reload, Ctrl+F find(QWebEnginePage.findText), Ctrl+±/0 zoom, Ctrl+P PDF 저장(Phase 2, printToPdf).
    • 링크: 같은 창에서 이동(문서 내 앵커·상대 경로), 외부 스킴은 무시 또는 명시 허용 목록.

    5.3 CLI

    hview report.html                 # 파일 열기
hview --watch report.html         # 변경 감지 자동 reload (mtime, QFileSystemWatcher)
hview http://internal-host/dash   # 내부망 URL
hview --title "Review" a.html     # 창 제목 오버라이드

    --watch reload 시 스크롤 위치 보존(reload 전 scrollY 저장 → 복원). 에이전트가 파일을 수십 번 고쳐 쓰는 동안 사용자는 창을 띄워두기만 하면 된다 — 기사 활용처 5가지(스펙 목업, 코드 리뷰 시각화, 프로토타입, 리포트, 일회용 편집기)를 그대로 커버.

    5.4 배포 — 소스 위치와 hrun 통합

    • 소스: 독립 pip 패키지 (hrag 패턴 — 자체 repo, [project.scripts] hview = ..., 의존은 PySide6>=6.6 하나). farad·hrun 어디에도 의존하지 않는다.
      • hrun repo에 소스를 넣지 않는 이유: hrun은 C++ 라우터 + POSIX 셸 인프라 저장소라 Python GUI 앱이 들어가면 이질적이고, python·hrag도 toolkit 래퍼만 두는 기존 패턴과 어긋난다.
    • hrun 통합: toolkits/hview/ — commands/hview 래퍼가 hrun_enter_tool hview 후 python toolkit 런타임 + wheelhouse로 설치/실행. env 오버라이드는 $HYPERRUN_DATA_DIR/env/tools/hview.env.
    • Windows/개발 환경: farad venv에 pip 설치 → hview 콘솔 스크립트 또는 python -m hview.

    5.5 farad 통합

    • 실행 해석 순서: ① 같은 인터프리터에서 hview importable하면 [sys.executable, "-m", "hview"] (farad venv 재사용 — QtWebEngine 이미 있음) → ② PATH의 hview → ③ hrun hview.
    • detached spawn: QProcess.startDetached — farad 수명과 무관, 종료 대기 없음.
    • 에이전트 산출물 계약 — self-contained HTML: 폐쇄망이라 CDN 참조는 그냥 깨진다. HTML 산출 스킬/프롬프트에 "인라인 CSS/JS, 외부 호스트 참조 금지, 이미지는 data: URI" 규약을 명시한다 (Claude Code Artifact의 CSP 정책과 같은 원리). 산출 위치는 세션 아티팩트 폴더.
    • UI 아이디어(후속): 타임라인의 .html 파일 경로에 "Open in hview" 액션.

    5.6 저사양·원격 X11 대응

    • QTWEBENGINE_CHROMIUM_FLAGS="--disable-gpu" — 원격 X11/VNC에서 GPU 경로 차단, 소프트웨어 래스터라이저 사용. 래퍼(toolkits/hview/env/hview.env)에 기본값으로 굽는다.
    • Chromium 샌드박스는 user namespaces 필요 — HPC 커널 설정에 따라 막혀 있으면 QTWEBENGINE_DISABLE_SANDBOX=1 폴백 (내부 신뢰 콘텐츠 전용 뷰어이므로 수용 가능). §7 확인.
    • 신뢰 모델: 에이전트가 만든 HTML의 JS를 로컬 실행하는 것은 에이전트가 만든 코드를 실행하는 것과 동일한 신뢰 수준. off-the-record라 영속 흔적도 없다.

    6. Plan B 상세

    B1. firefox 임시 프로필 래퍼 (zero-install 폴백)

    profile=$(mktemp -d) && firefox -no-remote -profile "$profile" "file://$PWD/report.html"
    • 장점: 설치할 것이 없다 (RHEL에 firefox ESR 기본 존재). 락 문제도 임시 프로필로 우회.
    • 단점: 기동 느림(프로필 초기화 포함), RAM 큼, 브라우저 UI 그대로(뷰어 UX 아님), 임시 프로필 정리 책임, Windows 별도 처리. → hview 배포 전 임시 브리지 스크립트로만 가치.

    B2. pywebview — §4 참조. WebKitGTK(RHEL 8은 2.4x대 백포트)로 A보다 가볍지만, OS별 엔진 분화 + GTK 의존이 결정적 감점. QtWebEngine 배포가 불가능해질 때만 재검토.

    7. 리스크 / 확인 필요

    • farad 실배포 환경에서 QtWebEngine import 확인: ./.venv/bin/python -c "from PySide6.QtWebEngineWidgets import QWebEngineView" — 메타패키지가 Addons를 실제로 끌고 왔는지, wheelhouse에 Addons wheel이 있는지.
    • HPC 원격 X11/VNC에서 --disable-gpu 렌더 확인 (검은 화면·크래시 여부).
    • sysctl user.max_user_namespaces — Chromium 샌드박스 동작 여부, 폴백 필요성.
    • off-the-record 실행 중 NFS 홈에 잔여 쓰기 없는지 확인 (fontconfig/dconf 캐시 등, strace -e trace=file 샘플링).
    • RAM 실측: 창 1개/3개 동시, 콜드 스타트 시간 (NFS 위 Python+PySide6 import 비용 포함 — farad와 같은 조건이므로 대략 예측 가능하나 뷰어는 lazy import로 최소화).
    • wheelhouse에 PySide6-Addons wheel 존재 확인 (farad용으로 이미 반입돼 있으면 신규 반입 0).
    • QtWebEngine wheel의 시스템 라이브러리 전제(nss, libxkbcommon, xcb 계열) 노드 존재 확인 — firefox가 깔린 노드면 대부분 충족. (참고: webkit2gtk3/gtk3 존재 여부도 확인해두면 Plan B 실현 가능성 판단에 유용.)
    • hview 전용 venv 디스크 실측(수백 MB 예상) + farad 설치 머신에서 farad venv 공유 설치로 갈지 결정 (공유 시 디스크 절약 vs 버전 커플링).

    8. 로드맵

    • MVP: 단일창 뷰어 + off-the-record + --watch + 단축키(zoom/find/close) + hrun toolkit.
    • Phase 2: per-host 단일 인스턴스(로컬 소켓 $XDG_RUNTIME_DIR/hview.sock — host-local이라 멀티호스트 안전; 창 N개가 엔진 1개 공유 → RAM 절약), Ctrl+P PDF 내보내기(printToPdf), farad 타임라인 "Open in hview" 액션.
    • Phase 3 (아이디어만): QWebChannel 브릿지로 "회신 가능한 HTML" — 에이전트가 만든 폼에서 사용자가 선택하면 JSON으로 저장 → 에이전트가 읽는 interactive AskUserQuestion식 워크플로우.
    • Non-goals: 탭, 주소창, 북마크, 히스토리, 확장, 일반 웹 브라우징. 뷰어의 선을 지킨다.

    유지보수 모델 — 일회성 빌드에 가깝다. 셸은 안정 API 위의 수백 줄이라 만들고 나면 손댈 일이 거의 없다. 엔진 업데이트는 farad의 PySide6 범프에 편승하므로 별도 케이던스가 없고, 폐쇄망에서 자기 에이전트 산출물만 여는 뷰어라 Chromium 보안 패치를 급하게 쫓을 이유도 없다. 이 "일회성"이 유지되는 조건은 Non-goals를 지키는 것 — Phase 3 브릿지처럼 프로토콜 표면이 생기는 기능은 필요가 증명될 때 별도 결정으로.

    9. 결론

    "가벼운 브라우저"의 실체는 엔진 선택이 아니라 상태 정책이다. 엔진은 폐쇄망 pip 배포 채널에 실리는 유일한 실엔진인 QtWebEngine으로 사실상 결정되고(PySide6는 그 배송 수단), off-the-record 셸로 감싸면 Chrome/Firefox의 무게·프로필·NFS 락 문제가 전부 설계 수준에서 소거된다. hrag 패턴의 독립 pip 패키지 + hrun toolkit 래퍼로 배포하면 HPC(hrun hview)와 Windows(farad venv) 양쪽을 같은 코드로 커버한다. MVP는 수백 줄 규모 — 가장 큰 선행 작업은 §7의 배포 환경 검증이다.
