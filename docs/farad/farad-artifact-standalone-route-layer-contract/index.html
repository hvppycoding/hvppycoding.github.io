    farad-artifact standalone 루트 검증 — 서브에이전트가 스킬만 읽고 만든 Farad 레이어 규약 문서

    2026-09-16

    farad-artifact standalone 루트 검증 — 서브에이전트가 스킬만 읽고 만든 Farad 레이어 규약 문서

    이번에도 사람이 슬라이드나 문단을 짜지 않았다. 서브에이전트(Sonnet)에게 Farad farad-artifact 스킬의 SKILL.md만 읽히고, 주제와 자료 경로, "자료에 없는 내용은 쓰지 마라"는 제약만 줬다. 스킬을 어떻게 쓰는지는 한마디도 알려주지 않았다 — 라우트 선택, 템플릿 사용법, 검사기 실행은 전부 에이전트가 스킬을 읽고 스스로 판단한 것이다.

    이전 AI 에이전트의 미래 덱과 다른 점은 대조군을 뒀다는 것이다. 같은 주제·같은 자료를 두 에이전트에게 각각 다른 목적지로 주문했다. 하나는 Confluence 페이지에서 발표할 슬라이드, 하나는 브라우저로 읽을 문서다. 콘텐츠 변수를 고정했으니 차이는 온전히 라우트 처리에서 나온다.

    주제는 Farad의 레이어 규약이다. 자료는 저장소의 docs/layers.md(616줄) 하나뿐이고, 독자는 Python/Qt는 알지만 이 코드베이스는 처음인 신규 입사자로 잡았다.

    이 글은 그중 문서 루트 결과다. 덱 루트 결과는 따로 정리했다.

    아래는 에이전트가 만든 HTML 문서를 그대로 붙여 넣은 것이다. 원래는 한 파일로 떨어지는 독립 문서이고, 브라우저로 읽다가 그대로 인쇄하거나 PDF로 뽑는 것까지 계산에 들어가 있다. 블로그에 넣으면서 바꾼 것은 문서 바깥을 칠하던 html·body 규칙 두 줄을 빼고 CSS 변수를 문서 안쪽으로 가둔 것뿐이며, 본문과 레이아웃은 손대지 않았다.

    내 코드는 어느 레이어인가

    Farad 레이어 규약 입문 · docs/layers.md 보완 자료

    이 문서는 docs/layers.md를 대신하지 않는다. 그 문서가 실제 계약이고 규칙의 최종 근거다. 이 문서는 그 표를 처음 봤을 때 "그래서 내가 지금 짜는 이 함수는 어느 레이어냐"를 스스로 판단할 수 있게 만드는 게 목적이다. 다 읽고 나서도 실제 규칙 문구가 필요할 때는 항상 docs/layers.md로 돌아가면 된다.

    왜 레이어를 나누는가

    Farad는 다섯 패키지로 나뉘어 있고, 그중 packages/farad/가 실제 앱이다 — 에이전트 루프, 세션, 도구, UI가 모두 이 패키지 하나에 들어 있다. 하나의 앱 안에서 "누가 파일을 읽는지", "누가 상태를 캐시하는지", "누가 화면을 그리는지"가 뒤섞이기 시작하면, 여러 유저가 공유하는 저사양 HPC 환경이 감당하지 못하는 재스캔·재폴링·전량 스캔이 슬금슬금 늘어난다. 레이어 규약은 "누가 무엇을 소유하는가"를 코드 리뷰 없이도 파일 경로만 보고 짐작할 수 있게 고정해 둔 것이다.

    docs/layers.md는 스스로를 이렇게 규정한다: "계약이지 구현 카탈로그가 아니다. 예시는 대표일 뿐이고, 규칙 자체가 근거다."

    다섯 레이어 훑어보기

    아래 다섯 개가 전부다. 이름이 비슷해 보여도 서로 넘나들지 않는다 — 각 레이어마다 "이게 뭘 하는 자리인가"와 "이 코드가 여기 속하는지 스스로 물어볼 질문"을 붙였다.

    1. Loader / Scanner / File Adapter

    디스크나 네트워크의 바이트를 읽어 순수한 데이터 구조로 바꾸는 자리다. 대표 파일: extension_metadata.py, skills/loader.py, plugins/loader.py, marketplace/scanner.py, core/settings_store.py, i18n/catalog.py, keybindings/defaults.py.

    • 소유: 파일시스템 읽기/쓰기, JSON 파싱, 스키마 없는 추출, 순수 데이터 변환
    • 하면 안 되는 것: Qt import, 앱 이벤트 발행, UI 동작 결정

    판단 질문: 디스크나 네트워크의 바이트를 파싱해서 순수 데이터 구조로 바꾸는 일만 하는가? 그렇다면 여기다. Qt를 import하거나 "이게 켜져 있다/꺼져 있다"를 판단하기 시작하는 순간 이미 다음 레이어로 넘어간 것이다.

    2. Registry / Store / Provider

    "지금 무엇이 존재하는가, 무엇이 켜져 있는가"에 답하는 관찰 가능한 상태를 쥐고 있는 자리다. 대표 파일: app/registry.py, plugins/registry.py, skills/registry.py, connectors/registry.py, config/provider.py, app/settings_service.py, app/capability_catalog.py, subagents/roster_index.py.

    • 소유: 관찰 가능한 discovery 상태, provider facade, 캐시 무효화, 압축된 영속 read model
    • 하면 안 되는 것: UI 위젯 호출, UI 전용 상태 보유, 저장돼 있던(archived) 기록을 살아 있는(live) 런타임 액터로 되살리는 것

    판단 질문: "지금 무엇이 존재/활성 상태인가"라는 질문에 답하는 관찰 가능한 상태이고, 그 답이 화면을 만들거나 액터를 되살리는 부작용을 절대 내지 않는가? 예를 들어 SubAgentRosterIndex는 위치·상태·이름을 답할 뿐 transcript 내용을 갖지도, 종료된 SubAgent 액터를 되살리지도 않는다.

    3. Factory / Service

    여러 서브시스템을 가로질러 실제로 뭔가를 조립해 내는 자리다. 대표 파일: session/factory.py, app/services.py, app/services_factory.py, core/settings_cascade.py, app/runtime/turn_context_provider.py, app/session_workflow.py, memory/service.py, scheduler/executor.py.

    • 소유: 서브시스템 간 조합, 세션 생성, 턴 준비, settings 쓰기 facade, 런타임 워크플로
    • 하면 안 되는 것: 위젯에 직접 손대는 것, UI가 저장 위치를 결정하게 두는 것

    판단 질문: 두 개 이상의 서브시스템(예: 세션 + capability, 설정 + 캐시)을 하나의 유스케이스로 조립하는가? Registry들이 "무엇이 있는지" 답을 준 다음, 그걸 실제로 엮어 뭔가를 만들어내는 자리라면 여기다.

    4. Runtime Contributor

    턴이 멈출지 계속될지 판단에 끼어드는 선택적 참가자다. 대표 파일: app/runtime/turn_hooks.py, goals/turn_hook.py, remote_control/turn_hook.py. 지금 이 레이어에는 GoalTurnHook과 RemoteTurnHook 둘뿐이다.

    • 소유: 공유 hook 프로토콜로 불변 세션/턴 라이프사이클 스냅샷에 반응, 도메인 상태는 주입된 서비스로만 소유, 선택적으로 제한된(bounded) 모델 continuation 요청
    • 하면 안 되는 것: UI를 import하거나 바꾸는 것, 코어 턴 루프 자체를 소유하는 것, 다른 컨트리뷰터와 mutable 상태를 공유하는 것, 자신이 유일한 훅이라고 가정하는 것

    판단 질문: 턴 라이프사이클 훅으로 반응만 하고, 자기 도메인 상태를 직접 들고 있지 않고 주입된 서비스에 위임하는가? 그렇다면 Runtime Contributor다.

    5. UI

    위젯, presentation 상태, 사용자 제스처, 그리고 Qt 메인스레드에서 도는 세션 투영이 사는 자리다. 대표 파일: ui/panels/*, ui/widgets/*, i18n/service.py, app/main_window/*, app/runtime/ui_session.py(및 ui_session_bubbles.py, ui_session_events.py).

    • 소유: 위젯, presentation 상태, 사용자 제스처, refresh용 signal 연결, Qt-thread 세션 투영 — UiSession이 채팅 뷰가 바인딩하는 Qt signal을 소유하고, MessageItemFactory로 MessageItem을 만드는 유일한 곳이다
    • 하면 안 되는 것: config 파일을 직접 read/write, loader/scanner를 직접 호출, SettingsStore를 직접 인스턴스화하거나 SettingsLocation을 직접 resolve, registry discovery 결과를 로컬 진리로 캐시(self._skills = ... 같은 패턴)

    판단 질문: 화면을 그리거나 사용자 입력을 받는가, 혹은 Qt 메인스레드에서 세션을 투영하는가? 그런데 그 안에서 설정 파일을 직접 열거나 discovery 결과를 필드에 저장해 두고 있다면, 그건 UI가 아니라 이미 Registry의 일을 몰래 대신하고 있는 것이다. 허용된 유일한 예외는 item_exposure_changed(kind, key, state)가 준 값으로 항목 하나만 in-place로 패치하는 경우다.

    표를 읽을 때 자주 헷갈리는 지점

    Mermaid 아키텍처 다이어그램에 보이는 B1~B7 같은 "visual band"는 코드 레이어가 아니다. 코드 레이어는 위 다섯 개뿐이며, 다이어그램의 밴드 구분과 혼동하지 않는다.

    이름이 Registry 같아 보여도 실제로 턴이나 세션 단위 view를 조립하는 로직을 담고 있으면 그건 Factory / Service다. 예를 들어 capability catalog는 "무엇이 있는가/켜져 있는가"에 답할 때만 Registry이고, 턴이나 세션마다 그 결과로 뭔가를 조립하는 헬퍼는 Factory / Service에 속한다.

    SubAgentManager(Factory / Service, 큐잉·시작·실행 중인 액터를 관리)와 SubAgentRosterIndex(Registry, 저장된 SubAgent 세션 메타데이터의 read model)가 대비되는 예다. Index는 위치·상태·이름 질의에 답할 뿐 transcript를 소유하지도, 액터를 되살리지도 않는다. 저장돼 있던 SubAgent를 여는 것은 평범한 세션 UI 투영일 뿐, UI에서 그걸 선택했다고 액터의 생명주기가 늘어나서는 안 된다.

    app/runtime/은 폴더이지 레이어가 아니다

    같은 폴더 안에서도 asyncio 스레드에서 도는 파일(예: async_session.py, turn_context_provider.py)은 Factory / Service이고, Qt 스레드에서 도는 파일(ui_session.py 등)은 UI다. 폴더 이름만 보고 같은 레이어라고 넘겨짚지 말고, 그 파일이 어느 스레드에서 실행되는지로 분류한다. 세부 규칙은 docs/layers.md "app/runtime/ Is Split By Thread" 절을 그때 가서 읽는다.

    Qt Adapter Boundary

    Service가 진짜 로직을 갖고 있는데 Qt identity(signal)도 필요하면, 하나의 QObject로 합쳐 쓰지 않는다. 로직은 Qt를 전혀 모르는 core 클래스에 담고, Qt 연결은 그 core를 감싸는 얇은 QObject adapter에만 둔다. 스레드를 넘는 통신은 core가 직접 하지 않고, 주입된 dispatcher(fire-and-forget용 post(work), request/response용 await call(work))를 통해서만 오간다. Signal 구독은 항상 adapter 쪽에 남긴다 — 구독을 plain 객체로 옮기면 어느 스레드에서 배달될지 보장할 수 없어지기 때문이다. 참고 구현은 SessionWorkflowCore / SessionWorkflowService다. 모든 QObject에 강제하는 규칙이 아니라, 그 로직을 QApplication 없이 테스트하거나 Qt 스레드 밖에서도 재사용하고 싶을 때 쓰는 패턴이다.

    Composition root와 예외로 허용된 전역

    새로운 cross-subsystem 상태는 대부분 build_app_services()(composition root)에서 만들어 명시적으로 주입한다. 예외로 허용된 전역 싱글턴은 단 둘뿐이다: Theme.instance()와 LocalizationService.instance(). 둘 다 read-mostly이고, Qt 메인스레드 전용이며, 테스트에서 리셋할 수 있다는 조건을 만족해서 예외로 남아 있다. 새로 뭔가를 "그냥 전역으로 두면 편하니까" 만들고 싶어지면, 이 두 개가 왜 예외로 허용됐는지부터 보고 같은 조건을 만족하는지 따져봐야 한다.

    이벤트와 무효화 경계

    중심에는 하나의 공유 이벤트 버스 AppSignals가 있다. 서비스 간 배선은 app/services_factory.py에, 창/위젯 refresh 배선은 app/main_window/* 같은 UI 모듈에 둔다. 구독이 기본값이다 — 어떤 서브시스템이 변화에 반응해야 한다면 signal을 구독한다. publisher가 subscriber를 직접 호출하는 건, 그게 바로 그 오퍼레이션의 공식 서비스 API인 경우가 아니면 피한다.

    capability discovery(플러그인·스킬·에이전트·커넥터)는 턴마다 다시 스캔하지 않는다. 갱신은 세 경로뿐이다.

    1. 명시적 refresh — /reload, Customize Refresh, Settings Refresh, capabilities MCP tool
    2. 레지스트리 캐시 미스
    3. DeploymentStatePoller의 20분 tick에 얹힌 coarse background reconcile — 운영자가 공유 마켓플레이스 소스를 바꿨을 때를 위한 것이다. 파일 내용이 아니라 lstat만 확인하고, 바뀐 루트의 capability closure만 국소적으로 무효화하며, 조용히 적용되고 알림도 없다

    반면 앱 안에서 사용자가 직접 바꾼 설정(권한, 커넥터 overlay 등)은 다르다: 쓰기 시점에 그 캐시를 즉시 reset해서 바로 다음 read에 반영한다(예: SettingsStore.write → SharedSettingsCache.reset). 스킬/ 에이전트/커넥터 노출을 하나 바꾸면 그 항목 하나만(item_exposure_changed) 패치되고, 활성화 여부 토글은 파생 캐시만 지운다 — 디스크 재스캔이 아니다. 전량 batch_invalidate(all kinds)는 명시적 refresh-all 경로에만 쓴다.

    새 캐시를 만들 때 스스로에게 물을 질문

    이 캐시는 언제 무효화되는가 — 명시적 트리거인가, 쓰기 시점의 즉시 reset인가, 아니면 그 어느 쪽도 아니고 그냥 다음 턴에 다시 읽히기를 바라고 있는가? 세 번째 답이면 레이어 규약을 어기고 있을 확률이 높다.

    Remote Control 경계나 single-instance lease/spool처럼 훨씬 좁은 영역의 이벤트 규칙도 있다. 이 문서에서는 다루지 않는다 — 존재한다는 것만 알아 두고, 실제로 그 영역을 건드릴 일이 생기면 그때 docs/layers.md의 해당 절을 읽는다.

    문서와 코드가 어긋날 때

    docs/layers.md는 이 상황을 정확히 두 가지로만 정리한다.

    1. 코드가 틀렸다 — 계약에 맞게 리팩터한다.
    2. 계약이 틀렸다 — 이 문서를 먼저 고치고 나서 코드를 쓴다.

    신규 입사자에게 중요한 함의는 이거다: 표에 딱 맞는 레이어가 안 보인다고 그냥 가까운 곳에 아무렇게나 끼워 넣거나 조용히 새 레이어를 만들어 버리면 안 된다. 표가 실제로 안 맞는다고 판단되면, 먼저 리뷰에서 docs/layers.md를 어떻게 고칠지 논의하고, 문서가 바뀐 다음에 코드를 쓴다.

    파일 하나가 점점 커지는 것도 신호다. LOC 600줄 또는 정의(definition) 30개를 넘기면 scripts/architecture_hotspots.py가 신호를 준다. 이건 "무조건 쪼개라"가 아니라 "여기서 책임 경계를 다시 봐야 한다"는 뜻이다 — 바꿀 이유가 여러 개인지, 테스트하기 힘든 로직이 섞여 있는지, 낮은 레이어가 높은 레이어를 너무 많이 알고 있는지를 따져 본다. 응집도가 높은 파일은 명시적 예외로 남겨 둘 수도 있다.

    새 코드를 놓을 때 순서대로 물어보기

    1. 디스크/네트워크 바이트를 순수 데이터로 바꾸기만 하는가? → Loader
    2. "무엇이 있는가/켜져 있는가"에 부작용 없이 답하는 관찰 가능한 상태인가? → Registry
    3. 여러 서브시스템을 엮어 세션·턴 같은 걸 실제로 조립해 내는가? → Factory / Service
    4. 턴 라이프사이클 훅으로 반응만 하고, 상태는 주입된 서비스에 맡기는가? → Runtime Contributor
    5. 위젯·제스처를 다루거나 Qt 메인스레드에서 세션을 투영하는가? → UI

    다섯 질문 중 하나에 명확히 "예"가 나오면 그 레이어다. 두 개에 걸쳐 있는 것 같다면 대개는 책임을 나눠야 한다는 신호이지, 애매하게 걸쳐 둬도 된다는 신호가 아니다.

    다음 단계

    이 문서는 시작점이다. 실제 규칙 문구, 예외 조건, 최근에 반영된 설계 판단은 항상 docs/layers.md가 최종 근거이고, 전체 시스템 배경은 docs/architecture.md에 있다.

    Made withFarad

    에이전트가 스스로 한 일

    주목할 건 절제다. standalone 템플릿은 클래스가 아니라 요소를 스타일한다 — 평범한 <h2>, <p>, <table>을 쓰면 알아서 저렇게 나온다. 에이전트는 이 계약을 정확히 지켜서, 템플릿이 허용한 3종의 클래스 중 2종(__kicker, __note)만 4번 쓰고 그 외에는 클래스도 인라인 style도 단 한 번도 붙이지 않았다.

    제목도 규칙대로다. SKILL.md는 "문서를 장르가 아니라 주제로 이름 지어라 — 분석 보고서는 아무 문서에나 붙지만 좋은 제목은 그 문서 하나를 가리킨다"고 한다. 에이전트가 고른 제목은 내 코드는 어느 레이어인가로, 장르명이 아니라 독자가 실제로 품고 있는 질문이다. 부제에 해당하는 kicker는 h1 아래에 붙었는데, 이것도 "제목이 독자가 찾는 것이니 그 위에 한 줄을 끼워 지연시키지 마라"는 명시적 규칙이다.

    내가 직접 재검증한 것

    에이전트의 자기 보고를 믿지 않고 산출물을 직접 감사했다.

    항목 덱 문서
    check_html.py OK: 0 warning(s) OK: 0 warning(s)
    render_check.py (1280/768/375px) 통과 통과

    날조 검사는 전수로 돌렸다. LOC > 600, definitions > 30, 20분 reconcile tick, SidebarPanel 6,722줄, ~3s QTimer — 전부 docs/layers.md와 docs/architecture.md 원문에 실재하는 값이다. 덱에 나오는 1,200/시간 → 3/시간, 약 400배만 원문에 없는 수치인데, 캡션에 근거식(3600s÷3s=1,200)을 함께 적어 파생값임을 밝혔다. 이건 deck.md가 "캡션은 출처와, 필요하면 근거를 명시하라"고 요구한 그대로다.

    두 루트를 나란히 놓으니 드러난 것

    이 대조 실험에서 나온 두 번째 수확은 스킬 안에서 규칙끼리 충돌한다는 사실이다.

    SKILL.md의 §Diagram Medium은 이렇게 지시한다. "text-led 다이어그램은 semantic HTML과 scoped CSS로 그려라. 라벨은 가능한 한 진짜 HTML 텍스트로 유지하고, 텍스트가 많은 구역을 단지 시각적으로 보이려고 수동 배치된 graphic text로 옮기지 마라."

    그런데 두 템플릿 루트 어느 쪽에서도 이걸 문자 그대로 실행할 수 없다.

    • standalone: <style> 블록은 assembler 소유이고, 평범한 콘텐츠에 클래스나 인라인 style을 붙이는 것이 금지돼 있다. CSS가 배포본과 다르면 check_html.py가 아예 실패시킨다. scoped CSS 다이어그램을 그릴 방법이 없다.
    • 덱: 콘텐츠 파일에 <style>이 들어 있으면 assembler가 거부한다. 그리고 deck.md는 정반대로 "다이어그램은 inline SVG로 그려라"라고 명령한다.

    두 에이전트가 정확히 반대 방향으로 갈라진 게 그 증상이다. 이쪽 문서 에이전트는 5레이어 스택이라는, 그림 그리기 좋은 주제에서 다이어그램을 하나도 그리지 않고 표 하나로 처리했다. 덱 에이전트는 <text> 66개짜리 수동 배치 SVG 다이어그램을 그렸다 — §Diagram Medium이 하지 말라는 바로 그것이다.

    둘 다 자기 루트의 레퍼런스를 충실히 따른 올바른 판단이었다. 즉 §Diagram Medium은 사실상 Custom HTML 루트에서만 유효한 규칙인데, 문서 최상단에 모든 루트의 기본값처럼 적혀 있다. 여기에 "템플릿 루트에서는 해당 루트 레퍼런스의 다이어그램 매체를 따른다" 한 줄만 있으면 충돌이 사라진다.

    덱 루트에서 발견한 더 큰 구멍은 덱 쪽 글에 적었다.
