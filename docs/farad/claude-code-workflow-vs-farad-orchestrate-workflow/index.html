    여러 서브에이전트를 결정적으로 오케스트레이션하는 워크플로 스크립트를 실행한다. 워크플로는 백그라운드에서 실행된다. 이 도구는 task ID와 함께 즉시 반환하고, 워크플로가 완료되면 <task-notification>이 도착한다. 실시간 진행 상황은 /workflows로 본다.

    Execute a workflow script that orchestrates multiple subagents deterministically. Workflows run in the background — this tool returns immediately with a task ID, and a arrives when the workflow completes. Use /workflows to watch live progress.

    워크플로는 많은 에이전트에 걸쳐 작업을 구조화한다. 포괄성을 위해 병렬로 분해·커버하고, 신뢰도를 위해 커밋 전에 독립 관점과 적대적 검증을 수행하며, 마이그레이션·감사·광범위한 탐색처럼 한 컨텍스트가 감당할 수 없는 규모를 처리한다. 무엇을 fan-out하고, 무엇을 검증하고, 무엇을 종합할지는 스크립트에 인코딩한다.

    A workflow structures work across many agents — to be comprehensive (decompose and cover in parallel), to be confident (independent perspectives and adversarial checks before committing), or to take on scale one context can't hold (migrations, audits, broad sweeps). The script is where you encode that structure: what fans out, what verifies, what synthesizes.

    사용자가 멀티에이전트 오케스트레이션을 명시적으로 선택한 경우에만 이 도구를 호출한다. 워크플로는 수십 개의 에이전트를 생성하고 많은 토큰을 소비할 수 있으므로, 이 규모를 추론해서는 안 되고 사용자가 요청해야 한다. 명시적 opt-in은 다음 중 하나다.

    ONLY call this tool when the user has explicitly opted into multi-agent orchestration. Workflows can spawn dozens of agents and consume a large amount of tokens; the user must request that scale, not have it inferred. Explicit opt-in means one of:

    • 사용자가 workflow 또는 workflows 키워드를 포함했다. 이를 확인하는 system-reminder가 보인다.
    • The user included the "workflow" or "workflows" keyword (you'll see a system-reminder confirming it).
    • Ultracode가 켜져 있고 system-reminder가 이를 확인한다. 아래 Ultracode 절을 참고한다.
    • Ultracode is on (a system-reminder confirms it) — see Ultracode below.
    • 사용자가 자신의 말로 워크플로 실행 또는 멀티에이전트 오케스트레이션을 직접 요청했다. 요청은 사용자의 말이어야 하며, 단지 워크플로가 도움이 될 만한 작업이라는 이유는 해당하지 않는다.
    • The user directly asked you to run a workflow or use multi-agent orchestration in their own words ("run a workflow", "fan out agents", "orchestrate this with subagents"). The ask must be in the user's words — a task that would merely benefit from a workflow does not count.
    • 사용자가 Workflow 호출을 지시하는 skill 또는 slash command를 실행했다.
    • The user invoked a skill or slash command whose instructions tell you to call Workflow.
    • 사용자가 특정 named workflow 또는 saved workflow 실행을 요청했다.
    • The user asked you to run a specific named or saved workflow.

    그 외 작업에서는 병렬화의 이점이 명백해도 이 도구를 호출하지 않는다. 개별 서브에이전트에는 Agent 도구를 쓰거나, 멀티에이전트 워크플로가 무엇을 하고 비용이 대략 얼마나 될지 짧게 설명한 뒤 실행 여부를 묻는다. 다음 메시지에 workflow를 포함하면 질문을 생략할 수 있다고 알려준다.

    For any other task — even one that would clearly benefit from parallelism — do NOT call this tool. Use the Agent tool for individual subagents, or briefly describe what a multi-agent workflow could do and how much it would roughly cost, and ask the user whether to run it. Mention they can include "workflow" in a future message to skip the ask.

    호출할 때는 흔히 하이브리드가 적절하다. 먼저 인라인으로 정찰해 파일을 나열하고, 채널을 찾고, diff 범위를 확정하여 작업 목록을 발견한 다음, Workflow를 호출해 그 목록을 pipeline으로 처리한다. 작업 전에 모양을 알 필요는 없고 오케스트레이션 단계 전에만 알면 된다.

    When you do call it, the right move is often hybrid: scout inline first (list the files, find the channels, scope the diff) to discover the work-list, then call Workflow to pipeline over it. You don't need to know the shape before the task — only before the orchestration step.

    턴을 가로질러 연결할 수 있는 흔한 단일 단계 워크플로는 다음과 같다.

    Common single-phase workflows you can chain across turns:

    • 이해 — 관련 서브시스템을 병렬로 읽고 구조화된 맵을 만든다.
    • Understand — parallel readers over relevant subsystems → structured map
    • 설계 — N개의 독립 접근법을 judge panel로 평가하여 점수화된 종합안을 만든다.
    • Design — judge panel of N independent approaches → scored synthesis
    • 리뷰 — 차원별 탐색 후 발견하고 적대적으로 검증한다.
    • Review — dimensions → find → adversarially verify (example below)
    • 리서치 — 다중 방식으로 탐색하고 깊이 읽은 뒤 종합한다.
    • Research — multi-modal sweep → deep-read → synthesize
    • 마이그레이션 — 대상 위치를 찾고 worktree 격리 상태에서 각각 변환한 뒤 검증한다.
    • Migrate — discover sites → transform each (worktree isolation) → verify

    더 큰 작업은 여러 워크플로를 순서대로 실행한다. 다음 phase를 결정하기 전에 각 결과를 읽는다. 메인 에이전트는 루프 안에 머물고, 각 워크플로는 범위가 명확한 하나의 fan-out이다.

    For larger work, run several in sequence — read each result before deciding the next phase. You stay in the loop; each workflow is one well-scoped fan-out.

    Ultracode. system-reminder가 ultracode 활성 상태를 확인하면 그 opt-in은 계속 유효하다. 기본적으로 모든 실질적인 작업에 워크플로를 작성하고 실행한다. 목표는 가장 빠르거나 저렴한 답이 아니라 만들 수 있는 가장 포괄적이고 정확한 답이며, 토큰 비용은 제약이 아니다. 이해 → 설계 → 구현 → 리뷰 같은 다단계 작업에서는 루프 안에 머물기 위해 phase마다 하나씩 여러 워크플로를 순서대로 실행하는 경우가 많다. 아래의 품질 패턴, 즉 적대적 검증, 다중 방식 탐색, 완전성 비평가, 새로운 결과가 없을 때까지 반복하기를 작업에 맞게 고른다. 작업이 사소하거나 이미 검증된 경우가 아니면 워크플로 오케스트레이션과 적대적 검증 쪽으로 기운다. 대화성 턴이나 사소한 기계적 수정만 단독으로 수행한다. reminder가 ultracode 비활성화를 알리면 위의 표준 opt-in 규칙으로 돌아간다.

    Ultracode. When a system-reminder confirms ultracode is on, that opt-in is standing: author and run a workflow for every substantive task by default. The goal is the most exhaustive, correct answer you can produce — token cost is not a constraint. For multi-phase work (understand → design → implement → review), that often means several workflows in sequence — one per phase — so you stay in the loop between them. The quality patterns below (adversarial verify, multi-modal sweep, completeness critic, loop-until-dry) are the tools; pick what fits the task. Lean toward orchestrating with workflows and adversarially verifying your findings — unless the work is trivial or already verified. Solo only on conversational turns or trivial mechanical edits. When a reminder says ultracode is off, revert to the opt-in rule above.

    스크립트는 script로 인라인 전달하며 먼저 파일로 쓰지 않는다. 호출할 때마다 세션 디렉터리 아래에 스크립트가 자동 저장되고 도구 결과로 그 경로가 반환된다. 워크플로를 수정할 때는 전체 스크립트를 다시 보내지 말고 그 파일을 Write/Edit한 다음 {scriptPath: "<path>"}로 Workflow를 다시 호출한다.

    Pass the script inline via script — do not Write it to a file first. Every invocation automatically persists its script to a file under the session directory and returns the path in the tool result. To iterate on a workflow, edit that file with Write/Edit and re-invoke Workflow with {scriptPath: "<path>"} instead of resending the full script.

    모든 스크립트는 export const meta = {...}로 시작해야 한다.

    Every script must begin with export const meta = {...}:

    export const meta = {
  name: 'find-flaky-tests',
  description: 'Find flaky tests and propose fixes',   // one-line, shown in permission dialog
  phases: [
    { title: 'Scan', detail: 'grep test logs for retries' },
    { title: 'Fix', detail: 'one agent per flaky test' },
  ],
}
// script body starts here — use agent()/parallel()/pipeline()/phase()/log()
phase('Scan')
const flaky = await agent('grep CI logs for retry markers', {schema: FLAKY_SCHEMA})
...

    meta 객체는 변수, 함수 호출, spread, template interpolation이 없는 순수 리터럴이어야 한다. 필수 필드는 name과 description이고, whenToUse와 phases는 선택이다. meta.phases와 phase() 호출에 같은 phase title을 사용한다. 제목은 정확히 일치시킨다. meta 항목이 없는 phase() 호출은 자체 progress group을 만든다. 특정 모델 override를 사용하는 phase 항목에는 model을 추가한다.

    The meta object must be a PURE LITERAL — no variables, function calls, spreads, or template interpolation. Required fields: name, description. Optional: whenToUse (shown in the workflow list), phases. Use the SAME phase titles in meta.phases as in phase() calls — titles are matched exactly; a phase() call with no matching meta entry just gets its own progress group. Add model to a phase entry when that phase uses a specific model override.

    스크립트 본문 hook은 다음과 같다.

    Script body hooks:

    • agent(prompt, opts)는 서브에이전트를 생성한다. schema가 없으면 최종 텍스트 문자열을 반환하고, JSON Schema가 있으면 StructuredOutput 도구 호출을 강제하여 검증된 객체를 반환하므로 별도 파싱이 필요 없다. 사용자가 실행 중 agent를 skip하면 null을 반환하므로 .filter(Boolean)으로 거른다. label은 표시명을, phase는 progress group을, model은 해당 agent 모델을 override한다. 모델은 기본적으로 생략해 main-loop 모델을 상속한다. 확신할 때만 다른 tier를 지정한다. isolation: 'worktree'는 병렬 수정 충돌을 막아야 할 때만 새 git worktree에서 실행한다. agent마다 약 200–500ms와 디스크 비용이 드는 비싼 옵션이다. agentType은 기본 workflow subagent 대신 Explore나 code-reviewer 같은 custom subagent type을 사용하며 schema와 조합할 수 있다.

    • agent(prompt: string, opts?: {label?: string, phase?: string, schema?: object, model?: string, isolation?: 'worktree', agentType?: string}): Promise — spawn a subagent. Without schema, returns its final text as a string. With schema (a JSON Schema), the subagent is forced to call a StructuredOutput tool and agent() returns the validated object — no parsing needed. Returns null if the user skips the agent mid-run (filter with .filter(Boolean)). opts.label overrides the display label. opts.phase explicitly assigns this agent to a progress group (use this inside pipeline()/parallel() stages to avoid races on the global phase() state — same phase string → same group box). opts.model overrides the model for this agent call. Default to omitting it — the agent inherits the main-loop model (the resolved session model), which is almost always correct. Only set it when you're highly confident a different tier fits the task; when unsure, omit. opts.isolation: 'worktree' runs the agent in a fresh git worktree — EXPENSIVE (~200-500ms setup + disk per agent), use ONLY when agents mutate files in parallel and would otherwise conflict; the worktree is auto-removed if unchanged. opts.agentType uses a custom subagent type (e.g. 'Explore', 'code-reviewer') instead of the default workflow subagent — resolved from the same registry as the Agent tool; composes with schema (the custom agent's system prompt gets a StructuredOutput instruction appended).

    • pipeline(items, stage1, stage2, ...)은 각 item을 모든 stage에 독립적으로 통과시키며 stage 사이에 barrier가 없다. A가 stage 3에 있을 때 B는 stage 1에 있을 수 있다. 이것이 다단계 작업의 기본값이다. wall-clock은 각 stage의 최장 시간 합이 아니라 가장 느린 단일 item chain이다. 모든 callback은 이전 결과, 원본 item, index를 받는다. stage가 throw하면 해당 item은 null로 떨어지고 남은 stage를 건너뛴다.

    • pipeline(items, stage1, stage2, …): Promise<any[]> — run each item through all stages independently, NO barrier between stages. Item A can be in stage 3 while Item B is still in stage 1. This is the DEFAULT for multi-stage work. Wall-clock = slowest single-item chain, not sum-of-slowest-per-stage. Every stage callback receives (prevResult, originalItem, index) — use originalItem/index in later stages to label work without threading context through stage 1's return value. A stage that throws drops that item to null and skips its remaining stages.

    • parallel(thunks)는 task를 동시에 실행하는 barrier로 모든 thunk를 기다린 뒤 반환한다. throw 또는 agent error가 난 thunk는 null로 resolve되고 호출 자체는 reject되지 않는다. 전체 결과가 정말 함께 필요할 때만 사용한다.

    • parallel(thunks: Array<() => Promise>): Promise<any[]> — run tasks concurrently. This is a BARRIER: awaits all thunks before returning. A thunk that throws (or whose agent errors) resolves to `null` in the result array — the call itself never rejects, so `.filter(Boolean)` before using the results. Use ONLY when you genuinely need all results together.

    • log(message)는 progress tree 위 narrator line으로 사용자에게 진행 메시지를 보낸다.

    • log(message: string): void — emit a progress message to the user (shown as a narrator line above the progress tree)

    • phase(title)은 새 phase를 시작하고 이후 agent 호출을 해당 progress group에 넣는다.

    • phase(title: string): void — start a new phase; subsequent agent() calls are grouped under this title in the progress display

    • args는 Workflow 호출의 args 입력값을 그대로 받는다. 배열과 객체는 JSON 값 자체로 전달하고 JSON 문자열로 다시 인코딩하지 않는다. named workflow에 리서치 질문, 대상 경로, 설정 객체 등을 side-channel 파일 없이 전달할 때 쓴다.

    • args: any — the value passed as Workflow's args input, verbatim (undefined if not provided). Pass arrays/objects as actual JSON values in the tool call, NOT as a JSON-encoded string — args: ["a.ts", "b.ts"], not args: "[\"a.ts\", ...]" (a stringified list reaches the script as one string, so args.filter/args.map throw). Use this to parameterize named workflows — e.g. pass a research question, target path, or config object directly instead of via a side-channel file.

    • budget은 사용자의 +500k 스타일 지시에서 온 turn token target이다. target이 없으면 total은 null이다. spent()는 main loop와 모든 workflow의 이번 turn 출력 토큰을 합산하고, remaining()은 남은 양 또는 target이 없을 때 Infinity를 반환한다. target은 권고가 아닌 hard ceiling이다. 도달하면 이후 agent()가 throw한다.
    • budget: {total: number null, spent(): number, remaining(): number} — the turn's token target from the user's "+500k"-style directive. budget.total is null if no target was set. budget.spent() returns output tokens spent this turn across the main loop and all workflows — the pool is shared, not per-workflow. budget.remaining() returns max(0, total - spent()), or Infinity if no target. The target is a HARD ceiling, not advisory: once spent() reaches total, further agent() calls throw. Use for dynamic loops: while (budget.total && budget.remaining() > 50_000) { ... }, or static scaling: const FLEET = budget.total ? Math.floor(budget.total / 100_000) : 5.
    • workflow(nameOrRef, args)는 다른 workflow를 inline sub-step으로 실행하여 결과를 반환한다. name으로 saved workflow를 실행하거나 scriptPath로 앞서 저장한 스크립트를 실행한다. 자식은 부모의 concurrency cap, agent counter, abort signal, token budget을 공유한다. nesting은 한 단계만 허용되며 자식 안의 workflow()는 throw한다. 알 수 없는 이름, 읽을 수 없는 경로, syntax error도 throw한다.
    • workflow(nameOrRef: string {scriptPath: string}, args?: any): Promise — run another workflow inline as a sub-step and return whatever it returns. Pass a name to invoke a saved workflow (same registry as {name: "..."}), or {scriptPath} to run a script file you Wrote earlier. The child shares this run's concurrency cap, agent counter, abort signal, and token budget — its agents appear under a "▸ name" group in /workflows and its tokens count toward budget.spent(). The args param becomes the child's `args` global. Nesting is one level only: workflow() inside a child throws. Throws on unknown name / unreadable scriptPath / child syntax error; catch to handle gracefully.

    서브에이전트는 최종 텍스트가 곧 반환값이라는 지시를 받으므로 사람에게 보내는 메시지가 아닌 raw data를 반환한다. structured output에는 schema를 사용한다. validation은 tool-call layer에서 이루어져 불일치 시 모델이 재시도한다.

    Subagents are told their final text IS the return value (not a human-facing message), so they return raw data. For structured output, use the schema option — validation happens at the tool-call layer so the model retries on mismatch.

    Workflow agent는 ToolSearch를 통해 세션에 연결된 모든 MCP 도구에 접근하며 schema는 agent마다 on-demand로 로드된다. 대화형 인증을 거친 MCP 서버는 headless 또는 cron 실행에서 없을 수 있다.

    Workflow agents can reach all session-connected MCP tools via ToolSearch — schemas load on demand per agent. Caveat: interactively-authenticated MCP servers (e.g. claude.ai) may be absent in headless/cron runs.

    스크립트는 TypeScript가 아닌 일반 JavaScript다. type annotation, interface, generic은 parsing에 실패한다. 본문은 async context에서 실행되므로 await를 직접 쓴다. 표준 JavaScript built-in은 사용할 수 있지만 Date.now(), Math.random(), 인자 없는 new Date()는 resume을 깨므로 throw한다. timestamp는 args로 넣고 결과가 반환된 뒤 찍으며, randomness는 index별 prompt나 label을 달리해 만든다. filesystem과 Node.js API는 사용할 수 없다.

    Scripts are plain JavaScript, NOT TypeScript — type annotations (: string[]), interfaces, and generics fail to parse. The script body runs in an async context — use await directly. Standard JS built-ins (JSON, Math, Array, etc.) are available — EXCEPT Date.now()/Math.random()/argless new Date(), which throw (they would break resume); pass timestamps in via args, stamp results after the workflow returns, and for randomness vary the agent prompt/label by index. No filesystem or Node.js API access.

    기본은 pipeline이다. stage 사이 barrier는 다음 stage가 모든 이전 stage 결과를 정말로 함께 필요로 할 때만 사용한다.

    DEFAULT TO pipeline(). Only reach for a barrier (parallel between stages) when you genuinely need ALL prior-stage results together.

    barrier가 옳은 경우는 stage N이 stage N-1 전체 item의 교차 context를 필요로 할 때뿐이다.

    A barrier is correct ONLY when stage N needs cross-item context from all of stage N-1:

    • 비싼 downstream 작업 전에 전체 결과를 dedup/merge한다.
    • Dedup/merge across the full result set before expensive downstream work
    • 총 개수가 0이면 일찍 종료한다.
    • Early-exit if the total count is zero ("0 bugs found → skip verification entirely")
    • stage N prompt가 비교를 위해 다른 finding을 참조한다.
    • Stage N's prompt references "the other findings" for comparison

    다음 이유는 barrier를 정당화하지 않는다.

    A barrier is NOT justified by:

    • 먼저 flatten/map/filter가 필요하다는 이유. pipeline stage 안에서 한다.
    • "I need to flatten/map/filter first" — do it inside a pipeline stage: pipeline(items, stageA, r => transform([r]).flat(), stageB)
    • stage가 개념적으로 분리돼 있다는 이유. pipeline이 바로 그것을 모델링한다. 분리된 stage가 동기화된 stage를 뜻하지 않는다.
    • "The stages are conceptually separate" — that's what pipeline() models. Separate stages ≠ synchronized stages.
    • 코드가 더 깔끔하다는 이유. barrier latency는 실제다. finder 5개 중 가장 느린 것이 가장 빠른 것보다 세 배 걸리면 빠른 finder 유휴시간의 3분의 2가 낭비된다.
    • "It's cleaner code" — barrier latency is real. If 5 finders run and the slowest takes 3× the fastest, a barrier wastes 2/3 of the fast finders' idle time.

    다음과 같은 smell이 있다면 중간 변환은 barrier가 필요하지 않다. 변환을 stage 안에 넣은 pipeline으로 다시 쓴다. 의심스러우면 pipeline을 선택한다.

    Smell test: if you wrote

    const a = await parallel(...)
const b = transform(a)        // flatten, map, filter — no cross-item dependency
const c = await parallel(b.map(...))

    that middle transform doesn't need the barrier. Rewrite as a pipeline with the transform inside a stage. When in doubt: pipeline.

    동시 agent() 호출은 workflow마다 min(16, cpu cores - 2)로 제한되고 초과 호출은 slot이 빌 때까지 queue된다. parallel()이나 pipeline()에 100개 item을 넣어도 모두 완료되며 한 순간에는 약 10개만 실행된다. workflow 수명 전체의 agent 수는 runaway loop 방지용으로 1000개까지다.

    Concurrent agent() calls are capped at min(16, cpu cores - 2) per workflow — excess calls queue and run as slots free up. You can still pass 100 items to parallel()/pipeline() and they all complete; only ~10 run at any moment. Total agent count across a workflow's lifetime is capped at 1000 — a runaway-loop backstop set far above any real workflow.

    정본 다단계 패턴은 pipeline을 기본으로 하고, 각 dimension의 review가 끝나는 즉시 그 dimension을 검증한다.

    The canonical multi-stage pattern — pipeline by default, each dimension verifies as soon as its review completes:

    export const meta = {
  name: 'review-changes',
  description: 'Review changed files across dimensions, verify each finding',
  phases: [{ title: 'Review' }, { title: 'Verify' }],
}
const DIMENSIONS = [{key: 'bugs', prompt: '...'}, {key: 'perf', prompt: '...'}]
const results = await pipeline(
  DIMENSIONS,
  d => agent(d.prompt, {label: `review:${d.key}`, phase: 'Review', schema: FINDINGS_SCHEMA}),
  review => parallel(review.findings.map(f => () =>
    agent(`Adversarially verify: ${f.title}`, {label: `verify:${f.file}`, phase: 'Verify', schema: VERDICT_SCHEMA})
      .then(v => ({...f, verdict: v}))
  ))
)
const confirmed = results.flat().filter(Boolean).filter(f => f.verdict?.isReal)
return { confirmed }
// Dimension 'bugs' findings verify while dimension 'perf' is still reviewing. No wasted wall-clock.

    비싼 검증 전에 모든 finding을 dedup해야 할 때는 barrier가 올바르다.

    When a barrier IS correct — dedup across all findings before expensive verification:

    const all = await parallel(DIMENSIONS.map(d => () => agent(d.prompt, {schema: FINDINGS_SCHEMA})))
const deduped = dedupeByFileAndLine(all.filter(Boolean).flatMap(r => r.findings))  // <-- genuinely needs ALL at once
const verified = await parallel(deduped.map(f => () => agent(verifyPrompt(f), {schema: VERDICT_SCHEMA})))

    목표 개수에 도달할 때까지 누적하는 loop-until-count 패턴은 다음과 같다.

    Loop-until-count pattern — accumulate to a target:

    const bugs = []
while (bugs.length < 10) {
  const result = await agent("Find bugs in this codebase.", {schema: BUGS_SCHEMA})
  bugs.push(...result.bugs)
  log(`${bugs.length}/10 found`)
}

    사용자의 +500k 지시에 맞춰 깊이를 조절하는 loop-until-budget 패턴은 budget.total을 guard해야 한다. target이 없으면 remaining은 Infinity라서 guard가 없을 경우 agent 1000개 cap까지 곧장 실행된다.

    Loop-until-budget pattern — scale depth to the user's "+500k" directive. Guard on budget.total: with no target set, remaining() is Infinity and the loop would run straight to the 1000-agent cap.

    const bugs = []
while (budget.total && budget.remaining() > 50_000) {
  const result = await agent("Find bugs in this codebase.", {schema: BUGS_SCHEMA})
  bugs.push(...result.bugs)
  log(`${bugs.length} found, ${Math.round(budget.remaining()/1000)}k remaining`)
}

    패턴을 조합한 exhaustive review는 찾기, 전체 seen 대비 dedup, 다양한 lens panel, 두 번 연속 새 결과가 없을 때까지 반복하는 순서다.

    Composing patterns — exhaustive review (find → dedup vs seen → diverse-lens panel → loop-until-dry):

    const seen = new Set(), confirmed = []
let dry = 0
while (dry < 2) {
  const found = (await parallel(FINDERS.map(f => () =>
    agent(f.prompt, {phase: 'Find', schema: BUGS})))).filter(Boolean).flatMap(r => r.bugs)
  const fresh = found.filter(b => !seen.has(key(b)))
  if (!fresh.length) { dry++; continue }
  dry = 0; fresh.forEach(b => seen.add(key(b)))
  const judged = await parallel(fresh.map(b => () =>
    parallel(['correctness','security','repro'].map(lens => () =>
      agent(`Judge "${b.desc}" via the ${lens} lens — real?`, {phase: 'Verify', schema: VERDICT})))
      .then(vs => ({ b, real: vs.filter(Boolean).filter(v => v.real).length >= 2 }))))
  confirmed.push(...judged.filter(v => v.real).map(v => v.b))
}
return confirmed
// dedup vs `seen`, NOT `confirmed` — else judge-rejected findings reappear every round and it never converges.

    품질 패턴은 흔한 형태이며 작업에 맞게 자유롭게 고르고 조합한다.

    Quality patterns — common shapes; pick by task and compose freely:

    • 적대적 검증: finding마다 N명의 독립 skeptic을 생성하고 각각 REFUTE하도록 지시한다. 과반이 반박하면 제거하여 그럴듯하지만 틀린 finding의 생존을 막는다.
    • Adversarial verify: spawn N independent skeptics per finding, each prompted to REFUTE. Kill if ≥majority refute. Prevents plausible-but-wrong findings from surviving.
    const votes = await parallel(Array.from({length: 3}, () => () =>
  agent(`Try to refute: ${claim}. Default to refuted=true if uncertain.`, {schema: VERDICT})))
const survives = votes.filter(Boolean).filter(v => !v.refuted).length >= 2
    • 관점 다양화 검증: 하나의 finding이 여러 방식으로 실패할 수 있으면 동일한 refuter N명 대신 correctness, security, performance, reproduction 여부처럼 서로 다른 lens를 부여한다. 다양성은 중복성이 잡지 못하는 failure mode를 찾는다.
    • Perspective-diverse verify: when a finding can fail in more than one way, give each verifier a distinct lens (correctness, security, perf, does-it-reproduce) instead of N identical refuters — diversity catches failure modes redundancy can't.
    • Judge panel: MVP-first, risk-first, user-first처럼 다른 각도에서 N개의 독립 시도를 생성하고 병렬 judge로 채점한 뒤, 승자를 기반으로 종합하되 차점자의 좋은 아이디어를 접목한다. solution space가 넓을 때 하나의 시도를 반복 개선하는 것보다 낫다.
    • Judge panel: generate N independent attempts from different angles (e.g. MVP-first, risk-first, user-first), score with parallel judges, synthesize from the winner while grafting the best ideas from runners-up. Beats one-attempt-iterated when the solution space is wide.
    • 새 결과가 없을 때까지 반복: 크기를 모르는 버그·이슈·edge case 탐색은 K회 연속 새로운 결과가 없을 때까지 finder를 계속 생성한다. 단순 개수 counter는 tail을 놓친다.
    • Loop-until-dry: for unknown-size discovery (bugs, issues, edge cases), keep spawning finders until K consecutive rounds return nothing new. Simple counters (while count < N) miss the tail.
    • 다중 방식 탐색: agent마다 container, content, entity, time 등 서로 다른 방식으로 병렬 검색한다. 각 agent는 다른 agent의 결과를 모르므로 한 가지 검색 방식으로 모든 것을 찾기 어려울 때 유용하다.
    • Multi-modal sweep: parallel agents each searching a different way (by-container, by-content, by-entity, by-time). Each is blind to what the others surface; useful when one search angle won't find everything.
    • 완전성 비평가: 마지막 agent가 실행하지 않은 방식, 검증되지 않은 주장, 읽지 못한 source 등 빠진 것을 묻는다. 발견한 것은 다음 작업 round가 된다.
    • Completeness critic: a final agent that asks "what's missing — modality not run, claim unverified, source unread?" What it finds becomes the next round of work.
    • 조용한 cap 금지: top-N, no-retry, sampling 등 coverage를 제한했다면 log()로 무엇을 버렸는지 알린다. 조용한 truncation은 실제로는 그렇지 않은데도 모든 것을 커버한 것처럼 보인다.
    • No silent caps: if a workflow bounds coverage (top-N, no-retry, sampling), log() what was dropped — silent truncation reads as "covered everything" when it didn't.

    사용자의 요청에 맞춰 규모를 조절한다. find any bugs에는 소수 finder와 단일 vote 검증을, thoroughly audit this 또는 be comprehensive에는 더 큰 finder pool, 3–5 vote adversarial pass, synthesis stage를 쓴다. 확신이 없으면 research/review/audit에는 철저함을, 빠른 확인에는 간결함을 택한다.

    Scale to what the user asked for. "find any bugs" → a few finders, single-vote verify. "thoroughly audit this" or "be comprehensive" → larger finder pool, 3–5 vote adversarial pass, synthesis stage. When unsure, lean toward thoroughness for research/review/audit requests and toward brevity for quick checks.

    이 패턴이 전부는 아니다. 작업에 맞으면 tournament bracket, self-repair loop, staged escalation 등 새로운 harness를 조합한다.

    These patterns aren't exhaustive — compose novel harnesses when the task calls for it (tournament brackets, self-repair loops, staged escalation, whatever fits).

    이 도구는 loop, condition, fan-out처럼 control flow가 모델 주도가 아니라 결정적이어야 하는 다단계 오케스트레이션에 사용한다.

    Use this tool for multi-step orchestration where control flow should be deterministic (loops, conditionals, fan-out) rather than model-driven.

    Workflow Orchestration

    당신이 orchestrator다. fan-out마다 하나의 shared prompt template, agent마다 하나의 output file, parallel Agent call로 join되는 phase로 구성된 workflow folder를 통해 multi-phase subagent 작업을 실행한다. subagent output은 disk에 저장되고 현재 context에는 path와 짧은 summary만 들어온다.

    You are the orchestrator. Run multi-phase subagent work through a workflow folder: one shared prompt template per fan-out, one output file per agent, phases joined by parallel Agent calls. Subagent outputs land on disk — your context only carries paths and short summaries.

    필요하지 않은 의식을 치르지 않는다. 질문 하나, 파일 하나, one-shot task 하나는 prompt만 쓰고 output_file은 쓰지 않는 direct Agent call 하나로 처리한다. 병렬 target이 둘 이상이거나 진짜 multi-phase pipeline일 때 folder protocol을 사용한다.

    Skip the ceremony when it isn't earned: a single question, file, or one-shot task is one direct Agent call (prompt only, no output_file). Reach for the folder protocol at ≥2 parallel targets or a real multi-phase pipeline.

    1. workflow folder 설정

    1. Set up the workflow folder

    workflow root는 <session_dir>/workflows/이며 <session_dir>는 system prompt에 표시된 Session storage path다. 이번 run의 kebab-case slug를 정하고 <session_dir>/workflows/<slug>/ 안에서 작업한다. write 시 parent directory가 생성되므로 mkdir은 필요 없다.

    Your workflow root is <session_dir>/workflows/ where <session_dir> is the "Session storage" path shown in your system prompt. Pick a kebab-case slug for this run and work inside <session_dir>/workflows/<slug>/ (parent directories are created on write — no mkdir).

    <session_dir>/workflows/<slug>/state.md를 먼저 만들고 모든 phase boundary에서 갱신한다. conversation이 compact되거나 interrupt될 때 이것이 single source of truth다.

    Create <session_dir>/workflows/<slug>/state.md FIRST and keep it current at every phase boundary. It is the single source of truth if this conversation is compacted or interrupted:

    # <slug> — workflow state
Goal: <one line>
## Plan
- Phase 1: <what> → outputs: phase1-discover/alpha.md, phase1-discover/beta.md
- Phase 2: <what> → outputs: phase2-synthesize/report.md
## Status
- [x] phase1-discover/alpha.md (done)
- [ ] phase1-discover/beta.md (background, agent_id a1b2c3)

    workflow root 아래의 Write/Edit은 orchestrator와 subagent에게 미리 승인된다. 이 승인은 workflow folder만 포함한다. subagent가 실제 project file을 수정하거나 바깥에서 command를 실행하면 정상 permission을 거친다. unattended 또는 background phase 전에 바깥 작업 permission을 미리 확보하지 않으면 아무도 보고 있지 않은 approval에서 phase가 멈춘다.

    Write/Edit under the workflow root are pre-authorized for you and your subagents. That covers ONLY the workflow folder: a subagent editing real project files or running commands outside it goes through normal permissions — before an unattended or background phase, make sure that outside work is already permitted, or the phase stalls on an approval nobody is watching.

    2. Path rules

    • 모든 file path는 <session_dir>/workflows/<slug>/... 형태의 absolute path다. output_file은 반드시 <session_dir>/workflows/ 내부에 있어야 한다. 최종 산출물이 project folder 같은 다른 위치에 속한다면 subagent가 자신의 도구로 그곳에 Write하게 하거나 deliver 단계에서 직접 복사한다.
    • Every file path is ABSOLUTE — <session_dir>/workflows/<slug>/..., one rule everywhere — and output_file must additionally stay inside <session_dir>/workflows/. If a final deliverable belongs elsewhere (e.g. the project folder), have a subagent Write it there with its own tools, or copy it yourself in the deliver step.
    • phase output folder는 phase1-discover/, phase2-refute/, phase3-synthesize/처럼 phaseN-purpose/로 이름 지어 listing만 봐도 순서와 역할을 알 수 있게 한다. 주변 workflow에서 목적이 분명한 경우가 아니면 bare phase1/은 피한다.
    • Name phase output folders as phaseN-purpose/ (for example phase1-discover/, phase2-refute/, phase3-synthesize/) so listings show both order and role. Avoid bare phase1/ unless the phase purpose is obvious from the surrounding workflow.
    • prompt와 template_vars 안의 path는 orchestrator가 resolve하지 않고 subagent가 자신의 도구로 resolve한다. 따라서 같은 absolute path를 전달한다.
    • Paths inside prompt and template_vars are not resolved by you — the subagent resolves them with its own tools, so pass the same absolute paths there too.
    • subagent의 system prompt에는 orchestrator가 아니라 자기 session storage가 표시된다. workflow folder에 추가 artifact를 쓰게 하려면 absolute folder path를 명시적으로 전달하고 스스로 유도하게 하지 않는다.
    • A subagent's own system prompt shows ITS session storage, not yours. If a subagent should write extra artifacts into the workflow folder, pass it the absolute folder path explicitly — never tell it to derive the path itself.

    3. shared prompt template

    3. Shared prompt templates

    여러 agent가 같은 긴 지시를 받으면 Jinja syntax를 사용해 template을 <session_dir>/workflows/<slug>/templates/<name>.md에 한 번만 쓰고 각 agent를 다음 값으로 생성한다.

    When several agents get the same long instructions, write the template ONCE to <session_dir>/workflows/<slug>/templates/<name>.md using Jinja syntax ({{ variable }}, {% if %}, {% for %}), then spawn each agent with:

    • prompt는 agent별 짧은 지시다. template이 self-contained면 생략할 수 있다. 둘 다 주면 rendered template이 prompt 뒤에 붙는다. prompt_file만 Jinja render되고 prompt는 verbatim 전달되므로 prompt에 {{ }}를 넣지 않고 template_vars로 차이를 준다.
    • prompt: a short per-agent directive. Optional when the template is self-contained; when both are given the rendered template is appended after prompt. Only prompt_file is Jinja-rendered — prompt is passed verbatim, so never put {{ }} in it; vary each agent through template_vars.
    • prompt_file은 absolute template path다.
    • prompt_file: the absolute template path
    • template_vars는 {"target": "alpha"} 같은 agent별 fill 값이다.
    • template_vars: the per-agent fill, e.g. {"target": "alpha"}

    누락 variable이나 render error는 Agent call을 즉시 실패시키며 아무 agent도 생성되지 않는다. template에는 전달한 list를 대상으로 한 variable, conditional, loop만 사용한다. single-agent phase는 template이 선택이며 prompt에 전부 inline해도 된다.

    A missing variable or render error fails the Agent call immediately — fix the call, nothing was spawned. Keep templates to variables, conditionals, and loops over the lists you pass in. For a single-agent phase a template is optional — inlining everything in prompt is fine.

    prompt와 template을 어떻게 나누든 모든 fan-out agent에 명시적 objective, expected output format, source/tool guidance, task boundary의 네 가지를 준다. 모호한 brief는 병렬 agent가 중복 작업하거나 lane을 벗어나게 한다.

    Whatever the split between prompt and template, give every fan-out agent four things — an explicit objective, the expected output format, source and tool guidance (where to look, what to trust), and task boundaries (out of scope). Vague briefs make parallel agents duplicate work or drift out of their lane.

    4. output을 file로 pipe

    4. Pipe outputs to files

    모든 fan-out agent에 output_file을 준다. phase마다 이름 있는 folder를 쓰면 listing이 읽기 쉽다. harness는 agent 완료 시 최종 메시지를 그 file에 쓰고 orchestrator에는 path + size + first lines만 보낸다.

    Give every fan-out agent an output_file (e.g. <session_dir>/workflows/<slug>/phase1-discover/alpha.md — a named folder per phase keeps listings legible). The harness writes the agent's final message to that file on completion; you receive only path + size + first lines. Contract:

    • file 존재는 성공이고 <file>.error.md sibling은 failure record다. 둘은 동시에 존재하지 않는다. harness 자체가 disk error로 file을 쓰지 못하면 run은 여전히 성공하며 output은 [output_file capture failed: ...] prefix와 함께 inline으로 온다. resume할 때 이미 inline output을 받은 neither-file agent를 다시 생성하지 않는다.
    • File exists = success; <file>.error.md sibling = failure record (status, reason, last assistant text) — never both. Third case: if the harness itself cannot write the file (disk error), the run still SUCCEEDED and its output arrives inline prefixed [output_file capture failed: ...] — record that result; on resume, don't respawn a neither-file agent whose inline output you already have.
    • 모든 live agent에는 서로 다른 output_file이 필요하다. 같은 path를 두 번째로 동시에 claim한 Agent call은 실패한다. 이전 run이 끝난 뒤 respawn할 때만 path를 재사용한다.
    • Every live agent needs a DISTINCT output_file — a second concurrent claim on the same path fails that Agent call. Reuse a path only when respawning after the prior run ended.
    • 각 subagent에게 최종 메시지가 곧 deliverable이며 2–3줄 TL;DR로 시작해야 한다고 지시한다. agent가 artifact를 직접 Write하면 최종 메시지는 TL;DR만 담아도 된다. 어느 쪽이든 file이 작업 내용을 가진다. 빈 최종 메시지도 0-byte success file을 쓰므로 envelope의 0 bytes는 red flag다.
    • Instruct each subagent (in the template or prompt) that its final message IS the deliverable — full content, starting with a 2–3 line TL;DR (the preview you see). If the agent instead Writes its artifacts itself, its final message is the TL;DR alone; either way the files carry the work. An empty final message still writes a 0-byte "success" file; treat 0 bytes in the envelope as a red flag.
    • .error.md로 끝나는 output_file 이름은 failure record용 reserved suffix이므로 거부된다.
    • Don't name an output_file ending in .error.md — that suffix is reserved for failure records and is rejected.

    5. phase 실행: parallel과 barrier

    5. Run a phase (parallel + barrier)

    한 phase의 모든 Agent call을 다른 내용 없이 하나의 assistant message에 넣는다. 동시에 실행되며 foreground call은 batch 전체가 완료될 때 turn이 재개된다. 이것이 automatic barrier다. phase template을 쓰고 state.md를 갱신하는 일은 fan-out 이전 메시지에서 끝낸다. Agent call 사이의 Write/Edit는 batch를 분리한다. concurrency cap과 LLM admission이 자동으로 queue하므로 넓은 phase도 error 대신 대기하며 직접 throttle하지 않는다. 모든 fan-out은 orchestrator가 담당한다. depth cap 때문에 subagent는 다시 spawn할 수 없으므로 worker에게 delegate하라는 template을 쓰지 않는다.

    Issue ALL of a phase's Agent calls in ONE assistant message with nothing else in it — they run concurrently, and for foreground calls your turn resumes when the whole batch is done (the automatic barrier). Write the phase's template(s) and update state.md in messages BEFORE the fan-out, never alongside it (a Write/Edit interposed among the Agent calls splits the batch). Queuing is automatic — concurrency caps and LLM admission pace execution, so a wide phase queues rather than erroring; do not throttle the phase size yourself. All fan-out stays with you: subagents cannot spawn their own (depth cap), so never write a template that tells a worker to delegate.

    각 phase의 전후를 사용자에게 알린다. chat이 유일한 progress view다. fan-out 직전에 어떤 phase인지, 어떤 agent를 몇 개 시작하는지, 각각 무엇을 만드는지 말한다. barrier와 file verification 뒤에는 N-of-N 완료, failure 처리, 다음 작업을 한두 줄로 정리한다.

    Bookend each phase for the user — the chat is their only progress view. Right before the fan-out, say in your visible text what the phase does: which agents you are launching, the total count, and what each produces. After the barrier (files verified), wrap up in a line or two: N-of-N done, any failures and how you handled them, and what comes next.

    • foreground wait 기본값은 agent마다 1시간이며 늘리면 turn 전체를 block한다. 장시간 build에는 run_in_background: true를 쓴다.
    • Foreground wait defaults to 1 hour per agent and blocks your whole turn if raised; for known-long work (builds, hours-scale jobs) use run_in_background: true.
    • automatic barrier는 foreground call만 포함한다. 명시적으로 background로 보냈거나 foreground batch에 섞였거나 wait deadline에 자동 승격된 agent는 notification으로 완료된다. 이때 barrier는 orchestrator 책임이며 첫 notification 뒤가 아니라 N-of-N output file을 확인한 뒤 다음 phase를 시작한다. background launch나 promotion notice에서 task/agent id를 받으면 state.md에 즉시 기록한다. TaskStatus와 TaskStop은 그 id만 받으며 compaction 뒤에는 남지 않는다.
    • The automatic barrier covers foreground calls only. Agents running in background — sent there explicitly, mixed into a foreground batch, or promoted (auto-converted at the wait deadline) — complete via notifications instead, and the barrier is YOURS: confirm N-of-N output files exist before starting the next phase, never after the first notification. When a call returns a task/agent id (background launch, promotion notice), record it in state.md immediately — TaskStatus and TaskStop take only that id, and it does not survive compaction.
    • promoted agent는 여전히 실행 중이며 완료 시 output file을 만든다. 다시 spawn하지 않고 live 여부가 불확실하면 TaskStatus부터 확인한다.
    • A promoted agent is still running and its output file still appears on completion — do NOT respawn it. If unsure whether a run is live, check TaskStatus first.
    • subagent tool call에는 별도 timeout이 있다. multi-hour command는 하나의 blocking call로 실행하지 말고 subagent 자신의 tool로 detach/background 실행한 뒤 poll하게 한다.
    • A subagent's own tool calls have their own timeouts: for a multi-hour command, tell the subagent to run it detached/backgrounded with its own tools and poll, not as one blocking call.

    6. 다음 phase에 입력 전달

    6. Feed the next phase

    이전 phase의 output path를 content 대신 template_vars로 다음 agent에 전달하고 template에서 그 file을 Read하게 한다. 각 agent는 fresh context에서 직접 읽는 비용을 부담한다. 그것이 목적이다.

    Pass the previous phase's output paths (not contents) to the next phase's agents via template_vars — absolute paths, per the path rules — and have the template tell them to Read those files. Each agent pays for reading in its own fresh context — that is the point.

    7. failure와 restart

    7. Failures and restart

    • 각 phase 뒤 live Agent tool result 또는 durable <file>.error.md를 확인한다. error record를 읽고 원인을 고친 뒤 그 agent만 같은 output_file로 respawn한다. 수정 후 다시 실패하면 loop하지 말고 멈춰서 blocker를 사용자에게 알린다.
    • After each phase, check results: a failed Agent tool result (seen live) or a <file>.error.md on disk (the durable record) means that agent failed. Read the error record, fix the cause, respawn ONLY that agent (same output_file — reclaimable once the run ended). If it fails again after a fix, stop and surface the blocker to the user instead of looping.
    • 완료한 작업을 수정하거나 확장하려면 existing output을 먼저 Read하라는 self-contained prompt의 fresh Agent를 만들고 같은 output_file을 재사용한다. completed run은 path를 release했으므로 새 run이 revised deliverable로 덮어쓴다. follow-up이 실패하면 old file은 남고 .error.md sibling이 생긴다. sibling 존재가 마지막 run의 authoritative status다.
    • To revise or extend finished work, launch a fresh Agent with a self-contained prompt that tells it to Read the existing output first, then reuse the same output_file. The completed run has released that path, and the fresh run overwrites it with the revised deliverable. If the follow-up fails, the older file stays AND an .error.md sibling appears — a present sibling is the authoritative status of the last run.
    • interruption/compaction 뒤 resume할 때는 state.md를 읽고 workflow folder를 list한다. output file이 있으면 skip, error sibling이면 위 방식으로 처리, 둘 다 없으면 respawn한다. run이 live일 수 있으면 TaskStatus부터 확인한다.
    • Resuming after interruption/compaction: read state.md, then list the workflow folder. Output file present → skip that agent. Error sibling → handle as above. Neither → respawn (check TaskStatus first if a run might still be live).
    • agent name이 아니라 output_file로 추적한다. respawn agent는 새 identity를 얻고 이름은 name-2처럼 drift할 수 있다.
    • Track work by output_file, not by agent name — a respawned agent gets a new identity (names can drift to name-2).

    8. deliver

    8. Deliver

    마지막 phase 뒤 최종 artifact를 직접 Read하고 실제 summary와 file path를 사용자에게 준다. envelope의 첫 줄은 preview일 뿐 deliverable이 아니므로 결과로 전달하지 않는다. coverage가 top-N target, sample subset, time-box 등으로 제한됐으면 summary와 state.md에 밝힌다. 조용한 cap은 실제로 완전하지 않은 작업을 완전하게 보이게 한다.

    After the last phase, Read the final artifact(s) yourself and give the user a real summary plus the file path. The envelope's first lines are a preview, not the deliverable — never forward them as the result. If coverage was bounded (top-N targets, sampled subset, time-boxed), say so in the summary and state.md — a silent cap reads as completeness it isn't.

    9. 흔한 형태

    9. Common shapes

    작업에 맞게 형태를 선택하고 자유롭게 조합한다. lookup은 agent 하나, comparison은 2–4개, 분해 가능한 research/audit/migration만 10개 이상을 쓴다. 보통 2–3 phase, fan-out phase마다 3–8 agent이며 target·dimension·finding 같은 실제 독립 unit 수로 정하고 quota로 정하지 않는다. 각 agent는 context를 처음부터 다시 읽으므로 width가 cost를 곱한다. 한 phase가 약 15 agent를 넘거나 4 phase 이상이면 over-orchestration을 의심한다. 좁은 target list나 잘 정의된 agent 하나가 더 넓은 net보다 나을 수 있다.

    Pick the shape by task and compose freely; scale to the ask — a lookup is one agent, a comparison 2–4, only decomposable research/audit/migration work 10+. Typical: 2–3 phases, 3–8 agents per fan-out phase, sized by the number of real independent units (targets, dimensions, findings) — never a quota. Width multiplies cost (each agent re-reads context from scratch); past ~15 agents in a phase or 4+ phases, suspect over-orchestration — a narrower target list or one well-scoped agent may beat a wider net.

    • 조사 → 종합: phase 1은 dependency, subsystem, file, question 등 target마다 agent 하나를 쓴다. coverage보다 discovery가 중요하면 서로 다른 search angle로 나눈다. phase 2 synthesizer 하나가 모든 phase 1 output file을 읽고 report를 쓴다.

    • Investigate → synthesize — the worked example below. Phase 1 (phase1-investigate/): one agent per target (dependency, subsystem, file, question); when discovery matters more than coverage, split by search angle instead — each agent hunts a different way. Phase 2 (phase2-synthesize/): one synthesizer reads every Phase 1 output file and writes the report.

    • Code review: diff, branch, PR과 audit·bug hunt에 같은 skeleton을 쓴다. phase 1에서 exact diff command, changed-file list, change summary, governing convention doc를 scope.md에 고정하고 empty diff면 멈춘다. phase 2는 correctness lens별 finder로 line-by-line hunk, removed behavior, cross-file caller/callee, language pitfall을 검사하며 cleanup lens는 하나의 finder가 맡는다. 모든 candidate는 file:line과 이름 붙일 수 있는 failure scenario를 포함하고 반신반의하는 candidate도 다음 독립 검증으로 넘긴다. phase 3는 location별 fresh verifier가 각 claim을 CONFIRMED, PLAUSIBLE, REFUTED로 판정한다. realistic하지만 불확실한 race·rare error·boundary는 PLAUSIBLE로 남기고 코드가 반증할 때만 REFUTED로 버린다. thorough 요청만 phase 4 gap sweep을 수행하고 새 결과가 없으면 빈 결과를 낸다. phase 5는 같은 root finding을 merge하고 correctness와 CONFIRMED를 우선해 severity순으로 종합한다. exhaustive hunt는 두 round 연속 새 finding이 없을 때까지 반복하며 high-stakes finding은 서로 다른 lens의 verifier 2–3명과 majority vote를 쓴다.

    • Code review — a diff, branch, or PR; the same skeleton serves audits and bug hunts. Phase 1 (phase1-scope/): one agent fixes scope into scope.md — the exact diff command, changed-file list, change summary, and which convention docs govern it; empty diff → stop and report, no fan-out. Phase 2 (phase2-find/): parallel finders. One finder per correctness lens (pick per review size) — line-by-line hunk scan (what input, state, or timing makes this line wrong), removed-behavior audit (every guard or invariant the diff deletes must be re-established somewhere, else it's a candidate), cross-file tracer (callers and callees of each changed function: new preconditions, changed return shapes, ordering), language-pitfall scan; the cleanup lenses (reuse, simplification, efficiency, conventions) share ONE finder. Each candidate is file:line plus a nameable failure scenario — pass each through, never silently drop half-believed ones (independent verification is the next phase's job), cap per finder. Phase 3 (phase3-verify/): group candidates by location (same file, overlapping lines), one fresh verifier per group judging each on its own claim — CONFIRMED (names the triggering input/state and wrong output, quotes the line), PLAUSIBLE (mechanism real, trigger uncertain on timing/env/config, says what would confirm it), REFUTED (factually wrong or already guarded, quotes the disproving line). Reviews are recall-biased: realistic-but-uncertain findings (races, rare error paths, boundaries) stay PLAUSIBLE — refute only what the code disproves; drop REFUTED. Phase 4, thorough asks only (phase4-sweep/): one fresh finder sees the verified list and hunts ONLY gaps — no re-deriving or re-confirming what's listed; nothing new → return empty, don't pad — then verify the same way. Phase 5 (phase5-synthesize/): merge same-root findings, rank most-severe first (correctness over cleanup, CONFIRMED over PLAUSIBLE), cap the report and note what dropped. Exhaustive bug hunts repeat find/verify until TWO consecutive rounds add nothing new (one dry round can be noise) — track seen in state.md; high stakes, 2–3 verifiers per finding with different lenses, majority wins.

    • Deep research: breadth와 verification이 필요한 source-backed report이며 local-first로 읽는다. phase 1은 질문을 code, doc, log, test data, user file 같은 서로 다른 local evidence lane 3–6개로 나눈다. web은 환경이 제공할 때만 bonus lane이다. phase 2는 lane별 agent가 path/URL을 normalize하고 budget 때문에 skip한 것을 기록한다. cross-lane duplicate는 synthesis에서 merge한다. phase 3는 source path와 evidence가 있는 falsifiable claim을 뽑는다. phase 4는 high-value claim마다 2–3 skeptic이 cited source를 다시 읽고 REFUTE한다. 두 반박이면 claim을 제거하고 uncertain도 refuted다. verifier 실행 실패는 refutation이 아니라 unverified로 보고한다. phase 5는 semantic duplicate를 merge하고 source strength와 vote에 따라 high/medium/low confidence를 부여하며 citation, caveat, unanswered open question 2–4개를 포함한 report.md를 쓴다.

    • Deep research — source-backed reports needing breadth plus verification; reads local-first. Phase 1 (phase1-scope/): decompose the question into 3–6 evidence angles, each a different LOCAL lane (code, docs, logs, test data, user-provided files) — web search is a bonus lane only when the environment provides it, never the assumed default; write scope.md. Phase 2 (phase2-discover/): one agent per lane gathers its evidence — lanes are disjoint by Phase 1 design, so dedup is within-lane: normalize each path (and URL, when web is available) once before reading, and log anything skipped for budget; cross-lane duplicates merge later, in synthesis. Phase 3 (phase3-extract/): pull concrete, falsifiable claims with source paths and evidence. Phase 4 (phase4-verify/): 2–3 independent skeptics per high-value claim, each prompted to REFUTE by re-reading the cited source — is the claim actually supported by the quoted evidence, or an overreach? — two refutations kill a claim, uncertain = refuted; a skeptic that fails to RUN is not a refutation, so a claim whose panel errored is unverified and the report says "unverified (verifier failed)", never counted confirmed or refuted. Phase 5 (phase5-synthesize/): merge semantic duplicates, assign per-finding confidence (high = multiple strong sources + unanimous votes, medium = secondary or split votes, low = single/weak source), cite sources, state caveats and 2–4 open questions that emerged unanswered, write report.md.

    • Design panel: spawn 전에 scoring criteria를 state.md에 써서 designer와 judge가 같은 rubric을 보게 한다. phase 1은 MVP-first, risk-first, user-first 등 다른 angle의 N designer가 서로의 draft를 보지 않고 같은 brief를 푼다. fresh context로 anchoring을 막고 disagreement를 보존한다. phase 2 judge는 rubric으로만 모든 design을 채점한다. phase 3은 winner를 기반으로 종합하고 점수가 좋은 runner-up idea를 접목한다.

    • Design panel — wide solution spaces. Write the scoring criteria into state.md BEFORE spawning, so designs and judges target one rubric. Phase 1 (phase1-design/): N designers attack the same brief from deliberately different angles (MVP-first, risk-first, user-first), working blind to one another — the fresh contexts are the point: they block anchoring and preserve genuine disagreement, so never feed one designer another's draft. Phase 2 (phase2-judge/): judges score every design against the rubric only. Phase 3 (phase3-synthesize/): synthesize from the winner, grafting runner-up ideas that scored well.

    • Sweep / migrate: 먼저 inline으로 work-list를 scout하고 item마다 break risk와 test를 tag한다. 위험 item은 개별 agent에, trivial item은 batch에 준다. phase 1은 item 또는 small batch별 agent가 같은 template으로 적용한다. phase 2 verifier 하나가 실제 test, lint, leftover grep을 실행하고 worker self-report가 아닌 fresh command output을 신뢰하며 miss만 respawn한다.

    • Sweep / migrate — many similar mechanical changes. Scout the work-list yourself first (cheap, inline), tagging each item with a risk note (what could break, what to test) so risky items get their own agent and trivial ones batch. Phase 1 (phase1-apply/): one agent per item or small batch, same template. Phase 2 (phase2-verify/): one verifier runs the real gates (tests, lint, grep for leftovers) and trusts fresh command output, never the workers' self-reports; respawn only the misses.

    • Completeness critic: deliver 전에 critic 하나가 synthesis와 phase output을 대조해 unverified claim, unread source, unswept dimension을 찾는다. 완료 주장은 disk output이나 rerun gate 같은 fresh evidence가 필요하며 worker의 self-reported done은 근거가 아니다. 실제 gap만 targeted round 하나로 처리하고 전체를 다시 하지 않는다.
    • Completeness critic — a finisher for any shape. Before delivering, one critic reads the synthesis against the phase outputs and asks what is missing: unverified claim, unread source, dimension never swept. Completion claims need fresh evidence — an output file on disk, a gate rerun — a worker's self-reported "done" counts for nothing. Real gaps become one more targeted round, not a redo.

    3. barrier가 반환되면 세 file을 확인하고 state.md를 갱신한 뒤 세 phase 1 output path를 template_vars로 받은 phase 2 synthesizer를 생성해 phase2-synthesize/report.md에 쓴다.
    4. 최종 report를 읽고 path와 함께 사용자에게 요약한다.

    1. Write <wf>/templates/investigate.md: You are investigating exactly one dependency: {{ target }}. ... Your final message is the deliverable — start it with a 2-3 line TL;DR.

    2. One message, three Agent calls, varying only template_vars and output_file: prompt: "Investigate one dependency per the appended instructions. Research only — do not edit files.", prompt_file: "<wf>/templates/investigate.md", template_vars: {"target": "httpx"}, output_file: "<wf>/phase1-investigate/httpx.md".

    3. When the barrier returns, verify the three files, update state.md, then spawn the Phase 2 synthesizer with the three phase1-investigate/ output paths in template_vars and output_file: "<wf>/phase2-synthesize/report.md".

    4. Read <wf>/phase2-synthesize/report.md and summarize it for the user with the path.

    3. Comparative synthesis

    같은 목표

    Shared objective

    두 문서는 모두 큰 작업을 독립 unit으로 분해하고, 병렬 agent가 fresh context에서 작업하며, 별도 검증과 synthesis를 거쳐 main context의 비대를 막는 것을 목표로 한다. adversarial verification, diverse lens, judge panel, loop-until-dry, completeness critic, no silent caps 같은 품질 패턴도 공유한다.

    Both documents aim to decompose large work into independent units, let parallel agents work in fresh contexts, add separate verification and synthesis, and prevent main-context bloat. They also share quality patterns such as adversarial verification, diverse lenses, judge panels, loop-until-dry, completeness critics, and no silent caps.

    가장 큰 차이: control flow의 권위

    Primary difference: authority over control flow

    Claude Workflow는 JavaScript script가 control flow의 권위다. pipeline, parallel, loop, conditional, budget, nested workflow가 VM 안에서 결정적으로 실행된다. Farad 스킬은 main agent가 reasoning loop로 phase 전환, barrier 확인, retry, synthesis를 직접 결정한다.

    Claude Workflow makes the JavaScript script authoritative over control flow. pipeline, parallel, loops, conditionals, budgets, and nested workflows execute deterministically inside a VM. The Farad skill makes the main agent decide phase transitions, barrier completion, retries, and synthesis through its reasoning loop.

    실행 substrate

    Execution substrate

    Claude Workflow는 dedicated Workflow tool, JavaScript VM, progress event model, journal/cache/resume, named workflow registry를 가진 별도 runtime이다. Farad는 새 runtime 없이 기존 Agent call의 same-message concurrency, foreground barrier, background notification, session storage를 조합한다.

    Claude Workflow has a dedicated Workflow tool, JavaScript VM, progress event model, journal/cache/resume machinery, and named-workflow registry. Farad composes existing same-message Agent concurrency, foreground barriers, background notifications, and session storage without adding a new runtime.

    데이터 전달과 context 보호

    Data transfer and context protection

    Claude Workflow의 agent()는 final text 또는 schema-validated object를 script에 반환한다. 결과는 runtime의 journal과 transcript에 연결된다. Farad는 agent final message를 output_file에 pipe하고 parent에는 path, size, first lines만 돌려준다. 다음 phase는 이전 content를 inline하지 않고 path를 전달해 fresh agent가 직접 Read한다.

    Claude Workflow's agent() returns final text or a schema-validated object to the script, with results tied to the runtime journal and transcript. Farad pipes each agent's final message to an output_file and returns only the path, size, and first lines to the parent. The next phase passes paths rather than inlining prior content, and fresh agents Read those files themselves.

    병렬성과 barrier

    Concurrency and barriers

    Claude Workflow는 item별 stage가 서로 앞서갈 수 있는 true pipeline과 모든 결과를 기다리는 explicit parallel barrier를 구분한다. Farad는 한 assistant message의 Agent call batch를 foreground barrier로 사용한다. background나 promoted agent가 섞이면 자동 barrier가 아니므로 orchestrator가 N-of-N file을 직접 확인한다.

    Claude Workflow distinguishes true per-item pipelines, where items can advance independently, from explicit parallel barriers that wait for all results. Farad uses a batch of Agent calls in one assistant message as a foreground barrier. If background or promoted agents are involved, the orchestrator must manually confirm N-of-N files because the automatic barrier no longer covers them.

    progress UX

    Progress UX

    Claude Workflow는 phase()와 log() event를 progress tree 및 /workflows UI에 보낸다. Farad에는 dedicated progress tree가 없으므로 phase 직전 launch 계획과 phase 직후 N-of-N 결과를 chat에서 bookend하고, durable 상태는 state.md에 기록한다.

    Claude Workflow emits phase() and log() events into a progress tree and the /workflows UI. Farad has no dedicated progress tree, so it bookends each phase in chat with a pre-launch plan and a post-barrier N-of-N result, while recording durable state in state.md.

    failure와 resume

    Failure and resume

    Claude Workflow는 동일 script와 args의 unchanged agent-call prefix를 journal/cache에서 재사용하고 resumeFromRunId 이후 처음 변경된 call부터 live 실행한다. Farad는 state.md와 file 존재 여부를 completion marker로 사용한다. output file은 success, .error.md sibling은 failure이며 neither 상태는 live status 확인 후 respawn 대상이다. 따라서 Claude 방식은 replay-aware resume이고 Farad 방식은 artifact-aware restart다.

    Claude Workflow reuses the unchanged prefix of agent calls from its journal/cache for the same script and args, then runs live from the first changed call after resumeFromRunId. Farad uses state.md and file existence as completion markers: an output file means success, an .error.md sibling means failure, and neither means the agent may need respawning after checking live status. Claude therefore provides replay-aware resume, while Farad provides artifact-aware restart.

    structured output

    Structured output

    Claude Workflow는 JSON Schema를 agent option으로 받아 StructuredOutput tool을 강제하고 검증된 object를 script로 반환한다. Farad 스킬의 중심 계약은 Markdown/text artifact이며 output_file이 raw final message를 저장한다. 구조가 필요하면 template과 output format 지시로 만들지만 Workflow VM 수준의 schema return contract는 아니다.

    Claude Workflow accepts a JSON Schema as an agent option, forces the StructuredOutput tool, and returns a validated object to the script. The Farad skill centers on Markdown/text artifacts, with output_file storing the raw final message. Templates and output-format instructions can impose structure, but this is not a VM-level schema-return contract.

    permission과 isolation

    Permissions and isolation

    Claude Workflow는 inline script 승인, named workflow rule, worktree isolation, subagent tool permission을 runtime contract로 다룬다. Farad는 harness write를 session workflow folder 안으로 제한하고 그 안의 Write/Edit만 pre-authorize한다. project file 수정과 외부 command는 정상 permission을 그대로 거친다. 즉 Claude는 execution isolation을, Farad는 artifact containment를 더 강하게 전면에 둔다.

    Claude Workflow treats inline-script approval, named-workflow rules, worktree isolation, and subagent tool permissions as runtime contracts. Farad confines harness writes to the session workflow folder and pre-authorizes only Write/Edit operations inside it; project-file edits and outside commands still use normal permissions. Claude foregrounds execution isolation, while Farad foregrounds artifact containment.

    규모와 비용

    Scale and cost

    Claude Workflow는 workflow당 동시 agent cap, 전체 1000 agent cap, hard token budget, budget-scaled loop를 제공하므로 매우 큰 deterministic fleet을 표현할 수 있다. Farad 스킬은 일반적으로 2–3 phase, phase마다 3–8 agent를 권장하고 약 15 agent 또는 4 phase를 넘으면 over-orchestration을 의심한다. 이것은 기능 부족을 숨기는 제한이 아니라 main-agent-driven orchestration의 신뢰성과 비용에 맞춘 의도적 operating envelope다.

    Claude Workflow exposes per-workflow concurrency limits, a 1,000-agent lifetime cap, hard token budgets, and budget-scaled loops, allowing very large deterministic fleets. The Farad skill normally recommends two to three phases with three to eight agents per fan-out and treats roughly 15 agents in one phase or four-plus phases as an over-orchestration signal. This is not a hidden limitation but a deliberate operating envelope matched to the reliability and cost of main-agent-driven orchestration.

    Ultracode와의 관계

    Relationship to Ultracode

    Claude Workflow description에서 Ultracode는 모든 substantive task에 workflow를 기본 사용하고 token cost를 constraint로 보지 않는 standing opt-in이다. Farad orchestrate-workflow에는 세션 전체를 강제하는 ultracode mode가 없다. 대신 단일 작업이 folder protocol을 정당화하는지 먼저 판단하고, 작은 작업은 direct Agent call 하나로 끝낸다.

    In the Claude Workflow description, Ultracode is a standing opt-in that defaults every substantive task to a workflow and does not treat token cost as a constraint. Farad's orchestrate-workflow has no session-wide ultracode mode; it first asks whether a single task earns the folder protocol and keeps small work to one direct Agent call.

    계보와 의도적 편차

    Lineage and deliberate divergence

    Farad 스킬의 investigate/synthesize, code review, deep research, design panel, sweep/migrate, completeness critic은 Claude Workflow의 quality pattern과 뚜렷한 계보를 공유한다. 그러나 Claude의 deterministic JS runtime을 복사하지 않고, 같은 품질 전략을 file handoff와 기존 Agent runtime 위의 모델 주도 protocol로 다시 표현한다. 따라서 Farad 구현은 Workflow tool의 축소 복제본이 아니라, 운영 지침은 계승하고 execution engine은 교체한 재설계다.

    Farad's investigate/synthesize, code review, deep research, design panel, sweep/migrate, and completeness-critic shapes clearly share lineage with Claude Workflow's quality patterns. However, Farad does not copy the deterministic JavaScript runtime; it re-expresses the same quality strategy as a model-driven protocol built on file handoffs and the existing Agent runtime. The Farad implementation is therefore not a reduced clone of the Workflow tool, but a redesign that inherits the operating guidance while replacing the execution engine.

    결론

    Conclusion

    Claude Workflow가 강한 곳은 결정적 control flow, true pipeline, schema return, budget, journal/cache resume, 대규모 fleet이다. Farad orchestrate-workflow가 강한 곳은 낮은 구현 복잡도, 기존 runtime 재사용, disk artifact의 직접 inspectability, session lifecycle에 묶인 containment와 GC, main agent가 phase 사이에서 판단을 바꿀 수 있는 유연성이다.

    Claude Workflow is strongest in deterministic control flow, true pipelines, schema returns, budgets, journal/cache resume, and large fleets. Farad's orchestrate-workflow is strongest in low implementation complexity, reuse of the existing runtime, directly inspectable disk artifacts, containment and garbage collection tied to the session lifecycle, and flexibility for the main agent to revise its judgment between phases.

    둘의 핵심 trade-off는 기능 개수가 아니라 결정적 script가 control을 소유하는가, reasoning agent가 control을 소유하는가다. Farad는 현재 규모에서 후자를 선택하고, 전자의 품질 패턴을 가능한 범위까지 흡수했다.

    The central trade-off is not feature count but whether deterministic scripts own control or reasoning agents own control. Farad currently chooses the latter for its operating scale while absorbing as many of the former's quality patterns as practical.
