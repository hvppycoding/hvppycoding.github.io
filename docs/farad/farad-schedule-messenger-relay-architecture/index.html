    Farad 예약 작업 사내 메신저 연동 아키텍처

    중앙 VM, Long Poll, 인증서, NFS, SQLite가 각각 왜 필요한지 대학 신입생도 따라올 수 있게 설명한 설계 초안입니다.

    설계 초안 v0.1 범위: Schedule 원격 1회 실행 작성일: 2026-07-14
    공개 문서이므로 실제 회사명·호스트명·사용자 ID·credential·Schedule 내용은 포함하지 않았습니다. 예시는 모두 가상 값입니다.

    01

    먼저 한 문장으로

    사용자의 Farad는 중앙 VM에 “내 메신저 버튼 명령이 오면 알려 달라”는 연결을 하나 유지합니다. 사용자가 휴대폰에서 버튼을 누르면 중앙 VM이 그 명령을 안전하게 저장했다가 해당 Farad에 전달하고, Farad가 로컬 Schedule을 검증한 뒤 실행합니다.

    사용자 호스트의 Farad

    실제 Schedule, prompt, 작업 폴더, 권한을 알고 실행하는 주체입니다. 중앙 VM은 이 정보를 알 필요가 없습니다.

    중앙 VM Relay

    메신저 API와 통신하고, 버튼 명령을 잠깐 보관하고, 올바른 사용자 Farad로 전달하는 우체국 역할입니다.

    사내 메신저

    사용자에게 Adaptive Card를 보여주고 버튼 클릭을 중앙 VM의 수신 API로 전달합니다.

    v1에서 할 일과 하지 않을 일

    구분v1 결정이유
    허용Farad에서 미리 선택한 Schedule을 1회 실행사용자가 회사 PC에서 범위를 미리 고정할 수 있습니다.
    허용[실행] → [확인] / [취소]휴대폰 오조작을 줄이는 2단계 확인입니다.
    허용준비됨 / 실행 중 / 완료 / 데스크톱 확인 필요민감한 세부 내용을 보내지 않고도 상태를 알 수 있습니다.
    제외Schedule 생성·수정·전체 목록 조회원격 권한이 지나치게 커지는 것을 막습니다.
    제외자유 텍스트, 결과 본문, 로그, 경로, prompt정보 유출과 prompt injection 통로를 닫습니다.
    후속실행 중 취소중간 상태와 정리 정책을 별도로 설계해야 합니다.
    02

    인증서는 무엇인가?

    인증서(certificate)는 인터넷에서 쓰는 사원증이라고 생각하면 됩니다. Farad가 중앙 VM에 연결할 때 “나는 kim 계정의 정식 Farad다”라고 주장하는 것만으로는 부족합니다. 누구나 요청 본문에 user=kim이라고 적을 수 있기 때문입니다.

    사원증사진, 이름, 사번이 있고 회사가 발급했다는 표시가 있습니다.
    ≈
    클라이언트 인증서계정 이름, 유효기간, 공개키가 있고 사내 CA의 전자서명이 있습니다.
    +
    개인키사원증 소유자만 가진 비밀 도장입니다. 호스트 밖으로 보내지 않습니다.

    CA는 누구인가?

    CA(Certificate Authority)는 인증서를 발급하고 서명하는 사내 신분증 발급 부서입니다. 중앙 VM은 “이 인증서가 우리가 신뢰하는 사내 CA가 서명한 것인가, 만료되지 않았는가, 취소되지 않았는가”를 검사합니다.

    mTLS는 무엇인가?

    보통 HTTPS에서는 브라우저가 서버 인증서만 검사합니다. mTLS(mutual TLS)는 서로 검사합니다. Farad는 중앙 VM이 진짜인지 확인하고, 중앙 VM도 Farad의 사용자 인증서를 확인합니다.

    인증서 확인 흐름비밀키는 네트워크로 전송되지 않습니다.
    사내 인증서 인프라가 아직 없다면? v1에서는 사용자별 긴 랜덤 API token을 0600 권한 파일에 저장하는 방법도 가능합니다. 다만 계정 폐기·만료·호스트 식별·키 회전을 운영하기에는 mTLS 인증서가 더 명확합니다.
    03

    전체 시스템 구조

    세상에 하나뿐인 “모든 것을 아는 중앙 서버”를 만들지 않습니다. 실제 Schedule과 실행 권한은 사용자 호스트의 Farad가 갖고, 중앙 VM은 메신저와 Farad 사이에서 봉투만 옮깁니다.

    논리 아키텍처실선: 데이터 흐름 · 점선: 인증/신뢰 · 주황: 명령 queue

    누가 무엇을 결정하는가?

    사실 또는 동작단일 권위중앙 VM이 아는가?
    Schedule prompt, 작업 폴더, 모델, 권한사용자 Farad아니오
    Schedule을 지금 실행해도 되는가Farad의 RemoteScheduleService + Scheduler아니오. 전달만 함
    계정 kim의 메신저 userId운영자 관리 account mapping예
    chatroomId, msgId, msgKey중앙 VM Relay DB예
    action token의 실제 task_id 매핑사용자 Farad아니오. opaque token만 봄
    실제 실행 결과와 transcript사용자 Farad아니오. 최소 상태만 받음
    04

    Long Poll은 어떻게 기다리는가?

    Farad가 매초 “명령 왔나요?”라고 물으면 요청이 너무 많습니다. Long Poll에서는 Farad가 한 번 질문하고 중앙 VM이 약 50초 동안 답을 보류합니다. 명령이 생기면 즉시 답하고, 아무 일도 없으면 빈 답을 돌려줍니다.

    Farad → Relay: GET /v1/commands?cursor=42&wait=50 Relay: 새 명령이 없으므로 HTTP 연결을 열어 둠 ... 17초 후 사용자가 메신저 버튼 클릭 ... Relay → Farad: { "commandId": 43, "actionToken": "opaque..." } Farad → Relay: ACK commandId=43 Farad → Relay: 다음 Long Poll 시작

    Farad 프로세스당 하나

    Schedule마다 연결을 만들지 않습니다. singleton lease를 가진 Farad가 async task 하나만 유지합니다.

    UI를 멈추지 않음

    네트워크 대기는 asyncio loop에서 일어나며 Qt 화면은 계속 반응합니다.

    신호가 아니라 배달 수단

    명령의 정본은 Relay DB입니다. 연결이 끊겨도 ACK 전 명령은 지워지지 않습니다.

    Farad는 언제 연결하는가?

    1

    앱이 시작되고 해당 계정이 singleton lease를 획득합니다.

    2

    메신저 연동 설정과 credential이 유효하면 Long Poll task 하나를 시작합니다.

    3

    정상 응답 후 즉시 다음 poll을 시작하고, 오류면 2초 → 4초 → 8초처럼 bounded backoff로 재연결합니다.

    4

    앱 종료, lease 상실, 계정 비활성화 시 poll과 pending network task를 정리합니다.

    05

    예시로 보는 전체 실행 시퀀스

    가상의 사용자 kim이 회사 PC에서 “조용한 수달”이라는 별칭으로 Schedule을 준비하고, 집에서 실행한다고 가정합니다.

    정상 경로 시퀀스카드에는 실제 Schedule 이름·task_id·prompt가 없습니다.

    카드 상태는 이렇게 바뀝니다

    READY · [실행]→ CONFIRMING · [확인] [취소]→ QUEUED→ RUNNING→ COMPLETED | NEEDS_DESKTOP

    연결이 끊겨도 명령을 놓치지 않는 이유

    재전달 시퀀스전달은 at-least-once, 실행 효과는 single-use로 한 번만
    06

    NFS와 중앙 DB는 각각 어디에 쓰는가?

    NFS가 있다고 해서 모든 상태를 NFS 파일로 만들 필요는 없습니다. NFS는 여러 호스트가 같은 파일을 볼 수 있다는 장점이 있지만, 작은 파일을 자주 열고 닫는 작업과 database lock에는 불리합니다.

    저장 위치저장할 것읽는 시점저장하지 않을 것
    NFS 운영 설정farad principal → messenger userId 매핑, CA trust 설정Relay 시작 또는 명시적 refresh사용자마다 매초 변하는 command queue
    사용자 Farad dataSchedule 정의, capability→task_id, task digest, 실행 historyFarad의 기존 store/cache 계약메신저 API credential
    VM 로컬 SQLite WALchatroomId, msgId/msgKey, command, ACK, dedupe, delivery generationcallback·Long Poll·카드 갱신 때 O(1) 조회Schedule prompt, transcript, 작업 경로, tool 결과

    왜 SQLite를 NFS 위에 두지 않는가?

    SQLite WAL은 로컬 파일 잠금과 빠른 fsync를 전제로 합니다. NFS에서는 잠금·캐시·장애 복구 의미가 서버와 mount 설정에 따라 달라질 수 있습니다. 중앙 Relay가 한 VM에서 돌기 때문에 VM 로컬 디스크의 SQLite가 단순하고 안전합니다. 나중에 Relay를 여러 VM으로 늘릴 때 PostgreSQL로 교체합니다.

    가상의 account mapping 예시

    # 운영자가 관리하는 예시. 실제 파일 형식은 구현 단계에서 확정. accounts: kim: messengerUserId: 10001234 enabled: true lee: messengerUserId: 10005678 enabled: true

    Farad 요청 본문이 messengerUserId=10001234를 직접 주장하는 구조는 피합니다. 중앙 VM이 인증서에서 확인한 kim principal을 운영 매핑에 대입해 receiver를 결정합니다.

    중앙 SQLite의 최소 테이블

    accounts / chatrooms

    인증된 principal과 메신저 사용자, 재사용할 1:1 chatroomId를 연결합니다.

    deliveries

    eventId, msgId, msgKey, 현재 card generation을 저장해 같은 카드를 갱신합니다.

    commands / action_routes

    어느 Farad에 보낼 명령인지, ACK 여부와 만료 시각을 저장합니다.

    inbound_dedup

    메신저 서버가 같은 callback을 재전송해도 효과가 한 번만 나도록 막습니다.

    07

    Schedule 실행 안전장치

    메신저 버튼은 Schedule ID를 직접 실행하는 만능 리모컨이 아닙니다. 회사 PC에서 미리 발급한 짧은 수명의 capability를 소비하는 일회용 표입니다.

    RemoteScheduleCapability capability_id task_id # Farad 로컬에만 존재 task_digest # prompt/folder/model/permission/check snapshot hash alias # 예: "조용한 수달" allowed_action # RUN_ONCE remaining_uses # 기본 1 expires_at policy_generation lease_epoch

    확인 버튼을 누른 순간 검사할 것

    누가 눌렀는가

    • 인증된 corporate principal
    • 발급 당시 chatroom과 같은가
    • 다른 사용자의 token이 아닌가

    아직 유효한가

    • single-use token인가
    • TTL과 remaining uses가 남았는가
    • 현재 app lease_epoch와 같은가

    작업이 그대로인가

    • task digest가 같은가
    • 삭제·비활성·실행 중이 아닌가
    • run limit이 남았는가

    권한이 제한됐는가

    • full access Schedule 거부
    • 저장된 allow pattern만 사용
    • 새 approval과 질문은 기다리지 않음

    원격 실행은 일반 Run now와 다릅니다

    기존 UI의 수동 run_now는 테스트와 사전 승인 용도로 check와 run limit을 우회할 수 있습니다. 메신저 원격 실행은 이 기본값을 그대로 사용하면 안 됩니다. 원격 전용 진입점에서 정책을 고정해야 합니다.

    scheduler.run_remote(task_id) 항상 적용: apply_check = true consume_run_limit = true trigger = "remote" full_access = reject permission_posture = DONT_ASK

    실패할 때 사용자에게 무엇을 보여주는가?

    상황메신저 표시실제 상세
    정상 완료“조용한 수달 · 잘 끝났어요”Farad Schedule history
    실패, 권한 거부, 질문 필요“조용한 수달 · 데스크톱 확인 필요”Farad transcript/history
    Schedule이 발급 후 수정됨“이 카드는 더 이상 사용할 수 없어요”local audit에 digest mismatch
    Farad가 꺼짐접수 전이면 카드 유지 또는 연결 안 됨 표시Relay command는 TTL까지만 보관
    중복 callback같은 카드 상태 유지dedupe + single-use token으로 no-op
    08

    구현 전에 메신저 담당자에게 확인할 것

    현재 API 설명으로 상위 구조는 정할 수 있지만 adapter 구현을 확정하려면 아래 답이 필요합니다.

    AES256의 mode, IV 위치, padding, charset, key 배포·회전, 무결성 검증(MAC/AEAD) 방식은 무엇인가?
    Adaptive Card의 Action.Submit 클릭 후 실제로 들어오는 chatMsg 전체 JSON 예시는 무엇인가?
    requestUrl을 메신저 서버가 직접 호출하는가, 아니면 Message Receiving API payload에 data를 실어 보내는가?
    Message Receiving API가 HTTP 200을 받지 못하면 재전송하는가? 횟수와 간격, 중복 event ID는 무엇인가?
    requestId와 msgId의 unique 범위는 전체 시스템인가, 연계 시스템별인가? 같은 ID 재요청은 멱등인가?
    ChatRequest timeout 후 같은 requestId/msgId로 재시도해도 중복 메시지가 생기지 않는가?
    interactive callback을 받기 위해 chatType 0을 쓰는 것이 맞는가? chatType 5 Noti에서는 callback이 지원되지 않는가?
    UpdateMessageRequest의 실제 wire field가 chatroomId인지, 문서의 chatrommId인지 확인이 필요한가?
    Adaptive Card JSON 최대 크기, action 수, 지원 element 제한, version 1.3 구현 차이는 무엇인가?
    API 인증, TLS/mTLS, source IP allowlist, rate limit, timeout, 점검 시간의 운영 계약은 무엇인가?

    권장 구현 순서

    1

    메신저 담당자와 위 wire/security 계약을 확정하고 fake server로 암복호화·card callback 샘플을 고정합니다.

    2

    중앙 Relay의 account mapping, SQLite schema, idempotent outbox/inbox, Long Poll API를 먼저 구현합니다.

    3

    Farad에 CorporateRelayTransport와 RemoteScheduleService를 추가하고 기존 OutboundGate의 닫힌 template 계약을 재사용합니다.

    4

    Schedule 발급 UI와 run_remote 안전 진입점을 연결합니다.

    5

    연결 끊김, VM 재시작, 중복 callback, token 만료, Schedule 변경, full-access 거부를 end-to-end로 검증합니다.

    최종 설계 요약 중앙 VM은 “메신저 어댑터 + durable 우체국”, 사용자 Farad는 “Schedule 정책과 실행의 단일 권위”입니다. NFS는 운영자 account mapping에만 제한적으로 쓰고, 동적인 명령 queue는 VM 로컬 SQLite에 둡니다. Farad는 실행 중일 때 프로세스당 Long Poll 하나를 유지하며, 인증서 또는 사용자별 credential로 자신의 principal을 증명합니다.
