    배포 구조 추천

    2025-08-28

    툴을 공용 디렉터리에 배포하는데 (모두 같은 os이고 커맨드로 실행 가능) 구조 추천 해줘

    좋아요. “공용 디렉터리 + 같은 OS + 커맨드 실행” 조건이면, 버전 디렉터리와 고정 심볼릭 링크(current) 를 쓰는 배치가 안전하고 관리가 쉽습니다. 아래를 그대로 템플릿으로 쓰세요.

    1) 디렉터리 구조 (권장)

    /opt/mytool/                  # 제품 루트(읽기 전용 권장)
├─ releases/                  # 버전별 배포물
│  ├─ 1.2.0/
│  │  ├─ bin/                 # 실행 스크립트(런처)
│  │  ├─ lib/                 # 앱 코드/모듈
│  │  ├─ venv/                # (선택) 파이썬/노드 등 런타임 격리
│  │  ├─ conf.defaults/       # 공용 기본 설정(배포물 포함)
│  │  └─ assets/              # 정적 리소스
│  └─ 1.1.3/
├─ current -> releases/1.2.0  # 현재 활성 버전(심볼릭 링크)
├─ conf/                      # 환경별/호스트별 오버라이드 설정(쓰기 가능)
├─ logs/                      # 공용 로그 디렉터리(쓰기 가능)
├─ run/                       # PID/소켓 등 런타임 파일(쓰기 가능)
└─ tmp/                       # 임시 파일(쓰기 가능)

    그리고 모든 사용자가 PATH 에서 접근할 수 있도록:

    /usr/local/bin/mytool -> /opt/mytool/current/bin/mytool

    포인트

    • releases : 읽기 전용. 동일 버전 재현/롤백이 쉬움

    • current : 심볼릭 링크만 바꿔 롤링 업데이트/즉시 롤백

    • conf : 장비/그룹별 차이를 안전하게 분리 (버전 교체에도 보존)

    • logs/run/tmp : 퍼미션 관리 쉬운 쓰기 영역

    2) 권한/소유권

    • 소유: root:myteam (또는 전용 시스템 사용자 mytool)

    • 디렉터리 권한:

      • /opt/mytool/releases 755 (읽기 전용)

      • /opt/mytool/conf logs run tmp 775 (팀 쓰기)

    • 새 파일의 그룹 상속을 위해 루트에 SGID 권장:

      chgrp -R myteam /opt/mytool
chmod 2775 /opt/mytool/conf /opt/mytool/logs /opt/mytool/run /opt/mytool/tmp

    3) 실행 스크립트(런처) 예시

    /opt/mytool/releases/1.2.0/bin/mytool (bash 기준)

    #!/usr/bin/env bash
set -euo pipefail

BASE_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
APP_HOME="${BASE_DIR}"
CONF_DIR="/opt/mytool/conf"
DEFAULTS_DIR="${APP_HOME}/conf.defaults"
LOG_DIR="/opt/mytool/logs"
RUN_DIR="/opt/mytool/run"
TMP_DIR="/opt/mytool/tmp"

mkdir -p "$LOG_DIR" "$RUN_DIR" "$TMP_DIR"

# (선택) 파이썬 가상환경
if [[ -d "${APP_HOME}/venv" ]]; then
  # shellcheck disable=SC1091
  source "${APP_HOME}/venv/bin/activate"
fi

# 설정 병합: conf > conf.defaults
export MYTOOL_CONFIG_DIR="$CONF_DIR"
export MYTOOL_DEFAULTS_DIR="$DEFAULTS_DIR"

exec "${APP_HOME}/lib/mytool_main" \
  --conf "$CONF_DIR" \
  --defaults "$DEFAULTS_DIR" \
  --tmp "$TMP_DIR" \
  >> "${LOG_DIR}/mytool.out.log" 2>&1

    언어별로 mytool_main 위치만 바꾸세요.

    • Python: lib/mytool_main.py 를 python lib/mytool_main.py 로 실행

    • Node: node lib/mytool_main.js

    • Go/단일 바이너리: lib/mytool_main 그대로 실행

    4) 설정 관리

    • 기본값 은 배포물(conf.defaults/)에 넣고, 환경 오버라이드 는 /opt/mytool/conf/에 둡니다.

    • 로딩 규칙: conf/가 키 충돌 시 conf.defaults/ 를 덮어씀.

    • 예:

      conf.defaults/app.yaml   # 공통
conf/app.yaml            # 서버별/그룹별 덮어쓰기
conf/secrets.env         # 환경 변수로 비밀 주입(파일 퍼미션 640)

    5) 배포/업데이트 절차 (원자적)

    1. 새 버전 디렉터리 생성 
      tar -C /opt/mytool/releases -xzf mytool-1.2.0.tar.gz

    2. (선택) 런타임/의존성 설치

      • Python: /opt/mytool/releases/1.2.0 에서 python -m venv venv && venv/bin/pip install -r requirements.txt
    3. 헬스 체크 
      /opt/mytool/releases/1.2.0/bin/mytool --version
/opt/mytool/releases/1.2.0/bin/mytool --check
    4. 트래픽/사용 공지 후 심볼릭 링크 스위치(원자적) 
      ln -sfn /opt/mytool/releases/1.2.0 /opt/mytool/current
    5. 문제 시 롤백 
      ln -sfn /opt/mytool/releases/1.1.3 /opt/mytool/current

    6) 로그/모니터링

    • 로그 파일: /opt/mytool/logs/mytool.out.log (로테이션 권장)

    • 간단한 logrotate 설정 예: 
      /opt/mytool/logs/*.log {
  weekly
  rotate 8
  compress
  missingok
  notifempty
  copytruncate
}
    • 메트릭/헬스엔드포인트 제공 가능하면 --health-port 0.0.0.0:9xxx 형태 지원 권장.

    7) 공용 PATH 연결

    ln -s /opt/mytool/current/bin/mytool /usr/local/bin/mytool
# or /usr/bin if 정책상 허용

    8) 보안/무결성

    • 릴리스 아카이브에 체크섬/서명(SHA256/GPG) 포함

    • 실행/스크립트에 set -euo pipefail 및 입력 검증

    • 비밀은 파일/환경변수/OS 비밀 스토어에서만 주입(코드/리포지토리에 넣지 않기)

    9) 팀 협업 팁

    • 릴리스 노트 : /opt/mytool/releases/1.2.0/RELEASE_NOTES.md

    • 마이그레이션 스크립트 : bin/migrate 를 두고 배포 시 자동 실행 옵션 제공

    • 호환성 체크 : --check 서브커맨드로 설정 유효성 검사

    필요하면, 사용 언어(Python/Node/Go 등) 기준으로 템플릿 압축 파일 + 설치 스크립트 도 만들어 드릴게요. 원하는 언어를 알려주시면 바로 해당 구조로 뼈대 만들어 드립니다.

    python package 에 포함된 툴이고 cli script가 있어

    좋아요! “Python 패키지에 CLI(script/console_scripts) 포함” 전제라면, 버전별 venv + 고정 심볼릭 링크(current) 방식이 가장 깔끔합니다. 의존성 충돌 없이 롤백/업데이트가 원자적으로 되고, CLI 엔트리포인트도 그대로 쓸 수 있어요. 아래를 그대로 템플릿으로 쓰면 됩니다.

    권장 디렉터리 레이아웃

    /opt/mytool/
├─ releases/
│  ├─ 1.2.0/
│  │  ├─ venv/              # 이 버전만의 가상환경 (여기에 패키지 설치됨)
│  │  └─ conf.defaults/     # 패키지 기본 설정(선택)
│  └─ 1.1.3/
├─ current -> releases/1.2.0 # 활성 버전 심볼릭 링크
├─ conf/                     # 환경/호스트별 오버라이드 설정(쓰기 가능)
├─ logs/                     # 공용 로그(쓰기 가능)
├─ run/                      # PID/소켓 등 런타임 파일
└─ tmp/                      # 임시 파일

    모든 사용자가 PATH에서 접근할 수 있도록:

    /usr/local/bin/mytool -> /opt/mytool/current/venv/bin/mytool

    mytool 는 패키지의 entry_points.console_scripts 로 만들어지는 실행파일 이름입니다.

    설치/업데이트/롤백 (step-by-step)

    0) 권한 기본값

    sudo mkdir -p /opt/mytool/{releases,conf,logs,run,tmp}
sudo chgrp -R myteam /opt/mytool
sudo chmod 2775 /opt/mytool /opt/mytool/{conf,logs,run,tmp}

    1) 새 버전 배치

    빌드 산출물이 wheel이라 가정(dist/mytool-1.2.0-py3-none-any.whl):

    VER=1.2.0
PY=python3.11                   # 운영 표준 파이썬 버전 명시
BASE=/opt/mytool
REL=$BASE/releases/$VER

sudo mkdir -p "$REL"
sudo $PY -m venv "$REL/venv"
sudo "$REL/venv/bin/pip" install --upgrade pip
sudo "$REL/venv/bin/pip" install /path/to/dist/mytool-$VER-*.whl
# (선택) 추가 의존성/플러그인:
# sudo "$REL/venv/bin/pip" install -r requirements-extras.txt

# 기본 설정이 패키지에 포함되지 않았다면
sudo mkdir -p "$REL/conf.defaults"

    오프라인/재현성 강화가 필요하면 사전 준비한 wheelhouse + constraints 를 권장:

    sudo "$REL/venv/bin/pip" install --no-index --find-links /opt/wheelhouse \
  -c /opt/wheelhouse/constraints-$VER.txt mytool==$VER

    2) 헬스 체크

    sudo -u nobody "$REL/venv/bin/mytool" --version
sudo -u nobody "$REL/venv/bin/mytool" --check || true   # 도구에 맞게

    3) 활성화(원자적 스위치)

    sudo ln -sfn "$REL" /opt/mytool/current

    4) PATH 연결(최초 1회)

    sudo ln -s /opt/mytool/current/venv/bin/mytool /usr/local/bin/mytool

    5) 롤백

    sudo ln -sfn /opt/mytool/releases/1.1.3 /opt/mytool/current
# (별도 조치 없이 즉시 반영됨)

    설정 로딩 권장 규칙

    • 기본값: /opt/mytool/current/conf.defaults/

    • 환경 오버라이드: /opt/mytool/conf/

    • 앱에서 다음 순서로 읽도록 구현(이미 구현돼 있다면 환경변수로 경로만 지정):

      • conf/ → conf.defaults/ (키 충돌 시 conf/ 우선)

    • 환경변수 예시(로그/설정/임시 경로 전달):

    export MYTOOL_CONFIG_DIR=/opt/mytool/conf
export MYTOOL_DEFAULTS_DIR=/opt/mytool/current/conf.defaults
export MYTOOL_LOG_DIR=/opt/mytool/logs
export TMPDIR=/opt/mytool/tmp

    CLI가 환경변수를 인식하지 않는다면, conf 경로를 옵션(--conf, --defaults)으로 받게 하거나, 아주 얇은 래퍼 스크립트를 /usr/local/bin/mytool 대신 둘 수도 있습니다.

    래퍼 예시(선택):

    #!/usr/bin/env bash
exec /opt/mytool/current/venv/bin/mytool \
  --conf /opt/mytool/conf \
  --defaults /opt/mytool/current/conf.defaults "$@"

    로그/운영

    • 표준 출력 리다이렉션이 필요하면 서비스 매니저(systemd/cron)에서 처리하거나, 앱 옵션으로 로그 파일 지정.

    • logrotate 간단 예:

    /opt/mytool/logs/*.log {
  weekly
  rotate 8
  compress
  missingok
  notifempty
  copytruncate
}

    보안/무결성 포인트

    • releases/는 읽기 전용(755) , conf/logs/run/tmp는 팀 쓰기(775) + SGID(2) 권장.

    • wheel 파일/의존성은 체크섬 검증(예: sha256sum -c), pip 설치 시 --require-hashes/constraints 사용.

    • 비밀은 .env나 OS 비밀 스토어로 주입(리포지토리/이미지 내 포함 금지), 권한 640.

    흔한 이슈 & 팁

    • 시스템 파이썬 업그레이드와 무관하게 동작: 버전별 venv로 고정 했기 때문.

    • 여러 CLI 엔트리포인트가 있는 패키지라면 /usr/local/bin에 필요한 것만 심볼릭 링크 추가.

    • 파이썬 버전 호환성 테스트: tox/nox로 사전 검증하고, 운영 환경 PY 버전(예: 3.11)로 빌드/런.

    • 대규모 환경이면, wheelhouse 캐시 + 사내 PyPI 미러를 쓰면 배포 속도/안정성 ↑

    필요하시면, 위 구조를 기준으로 자동 배포 스크립트(install/activate/rollback) 를 바로 만들어 드릴게요. 패키지명, CLI 이름, 파이썬 버전 알려주시면 한 번에 실행 가능한 스크립트로 제공해드릴게요.

    여러 툴이 있으면? 예를 들어 /user/myteam/RELEASE 라는 디렉터리에 배포하려고 해. 이 안에 toolchains (gcc 등 중요 빌드) bin (바이너리/링크 모아둠) installers (설치 폴더 모아둠) 이 있는 상태야. 내 툴 배포는 어떻게 하는게 좋을까

    좋아요. 이미 공용 릴리스 트리가 있고( toolchains/, bin/, installers/ ), 여기에 여러 개의 CLI 툴 을 깔끔하게 공존시키려면 “툴별 디렉터리 + 버전 디렉터리 + current 심볼릭 링크 + 공용 bin에 얇은 링크” 패턴이 가장 안전합니다.

    제안 구조 (여러 툴 공존)

    /user/myteam/RELEASE/
├─ toolchains/                    # (기존) gcc 등
├─ bin/                           # 모든 사용자가 PATH에 넣는 자리
│  ├─ mytool                      # -> ../installers/mytool/current/venv/bin/mytool
│  ├─ mytool-admin                # -> ../installers/mytool/current/venv/bin/mytool-admin (있다면)
│  ├─ othertool                   # -> ../installers/othertool/current/venv/bin/othertool
│  └─ ...
└─ installers/
   ├─ mytool/
   │  ├─ releases/
   │  │  ├─ 1.2.0/
   │  │  │  ├─ venv/              # 이 버전만의 가상환경 (패키지+의존성 설치됨)
   │  │  │  └─ conf.defaults/     # (선택) 패키지 기본 설정
   │  │  └─ 1.1.3/
   │  ├─ current -> releases/1.2.0
   │  ├─ conf/                    # 환경/호스트별 오버라이드(공용 쓰기)
   │  ├─ logs/                    # 로그
   │  ├─ run/                     # PID/소켓
   │  └─ tmp/                     # 임시
   └─ othertool/
      └─ ... (동일 패턴)

    핵심: 툴마다 자기 폴더를 갖고(installers/<toolname>), 그 안에서 버전 관리 합니다.
    공용 bin/에는 각 툴의 엔트리포인트로 향하는 심볼릭 링크 만 둡니다.

    배포/업데이트/롤백 — 표준 절차

    아래는 mytool(Python 패키지, console_scripts 제공) 기준 예시입니다.

    0) 1회 준비 (권한/링크)

    BASE=/user/myteam/RELEASE
TOOL=mytool
TOOL_HOME=$BASE/installers/$TOOL

mkdir -p $TOOL_HOME/{releases,conf,logs,run,tmp}
# 그룹/권한
chgrp -R myteam $TOOL_HOME
chmod 2775 $TOOL_HOME $TOOL_HOME/{conf,logs,run,tmp}

# 공용 bin에 얇은 링크(최초 1회)
ln -s ../installers/$TOOL/current/venv/bin/$TOOL $BASE/bin/$TOOL
# 서브 커맨드가 여럿이면 각각 링크 추가
# ln -s ../installers/$TOOL/current/venv/bin/mytool-admin $BASE/bin/mytool-admin

    1) 새 버전 설치

    wheel을 배포물로 가정(mytool-1.2.0-py3-none-any.whl):

    VER=1.2.0
PY=python3.11
REL=$TOOL_HOME/releases/$VER

mkdir -p "$REL"
$PY -m venv "$REL/venv"
"$REL/venv/bin/pip" install --upgrade pip
"$REL/venv/bin/pip" install /path/to/dist/mytool-$VER-*.whl

# (선택) 기본 설정
mkdir -p "$REL/conf.defaults"

    오프라인/재현성 필요 시:

    "$REL/venv/bin/pip" install --no-index --find-links /user/myteam/wheelhouse \
  -c /user/myteam/wheelhouse/constraints-$VER.txt mytool==$VER

    2) 헬스 체크

    "$REL/venv/bin/mytool" --version
"$REL/venv/bin/mytool" --check || true   # 도구가 지원한다면

    3) 활성화(원자적 전환)

    ln -sfn "$REL" "$TOOL_HOME/current"
# 공용 bin의 심볼릭 링크는 고정이라, 자동으로 새 버전을 가리킴

    4) 롤백

    ln -sfn "$TOOL_HOME/releases/1.1.3" "$TOOL_HOME/current"

    설정 로딩 규칙 (권장)

    • 기본값: installers/mytool/current/conf.defaults/

    • 환경 오버라이드: installers/mytool/conf/ (버전 교체에도 보존)

    • 앱에서 읽는 우선순위: conf/ → conf.defaults/

    환경변수 예:

    export MYTOOL_CONFIG_DIR=/user/myteam/RELEASE/installers/mytool/conf
export MYTOOL_DEFAULTS_DIR=/user/myteam/RELEASE/installers/mytool/current/conf.defaults
export MYTOOL_LOG_DIR=/user/myteam/RELEASE/installers/mytool/logs
export TMPDIR=/user/myteam/RELEASE/installers/mytool/tmp

    CLI가 경로 옵션을 지원한다면(권장):

    mytool --conf .../installers/mytool/conf \
       --defaults .../installers/mytool/current/conf.defaults

    여러 툴을 함께 운영할 때의 규칙

    1. 툴별 독립 venv

      • 파이썬 의존성 충돌 방지. 각 툴이 자기 installers/<tool>/releases/<ver>/venv를 사용.

    2. 공용bin/은 오직 링크만

      • 실행 파일을 두지 말고 항상 ../installers/<tool>/current/...로 링크.

      • 버전 전환 시 bin/ 손댈 필요 없음.

    3. 이름 네임스페이스

      • 충돌 가능성이 있으면 mytool 대신 myteam-mytool 처럼 prefix 부여.

    4. 도구 체인 연동

      • toolchains/(gcc 등) 경로가 필요하면, 각 툴이 런타임에만 PATH, LD_LIBRARY_PATH, CPATH, LIBRARY_PATH를 확장하도록.

      • 전역 오염을 막기 위해 래퍼를 둘 수 있음(아래 예시).

    5. 로그/런타임/임시 분리

      • 툴마다 logs/, run/, tmp/를 별도 보유(충돌 방지).

      • 로테이션은 툴별 패턴으로.

    (선택) 환경 래퍼 스크립트 패턴

    툴체인/환경변수 조합이 필요한 툴에만 bin/ 링크 대신 래퍼를 쓸 수 있습니다.

    /user/myteam/RELEASE/bin/mytool (실제 파일)

    #!/usr/bin/env bash
set -euo pipefail
BASE="/user/myteam/RELEASE"
TOOL_HOME="$BASE/installers/mytool"
VENV="$TOOL_HOME/current/venv"

# 필요 시 toolchains 경로 주입
export PATH="$BASE/toolchains/gcc-12.3.0/bin:$PATH"
export LD_LIBRARY_PATH="$BASE/toolchains/gcc-12.3.0/lib64:${LD_LIBRARY_PATH:-}"

exec "$VENV/bin/mytool" \
  --conf "$TOOL_HOME/conf" \
  --defaults "$TOOL_HOME/current/conf.defaults" \
  "$@"

    대부분의 경우엔 심볼릭 링크만으로 충분 하고, 특별한 환경 주입이 필요한 툴에만 래퍼를 씁니다.

    권한/보안 체크리스트

    • installers/<tool>/releases/* : 755 (읽기 전용)

    • installers/<tool>/{conf,logs,run,tmp} : 2775 (SGID로 그룹 유지)

    • 비밀(토큰/키)은 conf/secrets.env 등으로 분리, 640 권장.

    • wheel/requirements는 체크섬 검증(sha256sum -c), pip는 --require-hashes/constraints 사용.

    간단한 설치/전환 스크립트(템플릿)

    /user/myteam/RELEASE/installers/mytool/bin/manage.sh (관리자 전용)

    #!/usr/bin/env bash
set -euo pipefail
BASE="/user/myteam/RELEASE/installers/mytool"
PY="python3.11"

cmd=${1:-}
ver=${2:-}

case "$cmd" in
  install)
    test -n "$ver"
    REL="$BASE/releases/$ver"
    mkdir -p "$REL"
    $PY -m venv "$REL/venv"
    "$REL/venv/bin/pip" install --upgrade pip
    "$REL/venv/bin/pip" install "/path/to/dist/mytool-$ver-*.whl"
    mkdir -p "$REL/conf.defaults"
    "$REL/venv/bin/mytool" --version
    ;;
  activate)
    test -n "$ver"
    ln -sfn "$BASE/releases/$ver" "$BASE/current"
    ;;
  rollback)
    test -n "$ver"
    ln -sfn "$BASE/releases/$ver" "$BASE/current"
    ;;
  *)
    echo "usage: $0 {install|activate|rollback} <version>" >&2
    exit 1
    ;;
esac

    installers에는 gcc.zip 같은 애들 들어있는 상태야. 새폴더를 만들어도돼

    좋아요—installers/에 gcc.zip 같은 아카이브(설치 파일) 가 이미 있고, 새 폴더를 만들어도 된다면, 아카이브 보관 영역과 실제 설치/운영 영역을 분리 하는 게 가장 깔끔합니다. 즉:

    • installers/ = “보관소(archives)”

    • apps/(새 폴더) = “실제 배포된 실행 환경(버전/venv 관리)”

    • bin/ = “모든 툴의 진입점(심볼릭 링크 또는 래퍼)”

    6) 왜 이 구성이 좋은가 (요약)

    • 아카이브(installers/)와 실행환경(apps/) 분리 → 혼선 없이 안전.

    • 버전 전환/롤백이 심볼릭 링크 한 번 으로 원자적.

    • 각 툴 독립 venv → 의존성 충돌 방지.

    • bin/은 “진입점”만 모아 PATH 관리가 간단.

    • 필요 시 toolchains 주입은 래퍼로만 제한 → 전역 오염 최소화.

    CLI는 내부적으로 …/current/share/examples 를 탐색합니다.

    Python (click 예시, 요지)

    import os, shutil, subprocess, sys, click
from importlib.resources import files

EX_DIR = os.path.realpath(
    os.path.join(os.path.dirname(sys.executable), '..', '..', 'share', 'examples')
)

@click.group()
def cli(): ...

@cli.group()
def examples(): ...

@examples.command('list')
def list_examples():
    for root, dirs, _ in os.walk(EX_DIR):
        if root == EX_DIR: 
            for d in sorted(dirs):
                click.echo(d)
            break

@examples.command('path')
@click.argument('name')
def path(name):
    p = os.path.join(EX_DIR, name)
    click.echo(p)

@examples.command('run')
@click.argument('name')
@click.option('--workdir', default=None)
@click.option('--dry-run', is_flag=True)
def run(name, workdir, dry_run):
    p = os.path.join(EX_DIR, name)
    runsh = os.path.join(p, 'run.sh')
    if not os.path.exists(runsh):
        raise SystemExit(f'run.sh not found in {p}')
    workdir = workdir or os.path.join('/tmp', f'mytool-{name}')
    os.makedirs(workdir, exist_ok=True)
    # 필요 파일 복사(원본 예제는 read-only 유지)
    for item in ('input', 'config.yaml'):
        src = os.path.join(p, item)
        if os.path.exists(src):
            dst = os.path.join(workdir, item)
            if os.path.isdir(src):
                shutil.copytree(src, dst, dirs_exist_ok=True)
            else:
                shutil.copy2(src, dst)
    cmd = ['bash', runsh]
    click.echo(f'Working dir: {workdir}')
    click.echo(f'Command: {" ".join(cmd)}')
    if not dry_run:
        subprocess.check_call(cmd, cwd=workdir)

if __name__ == '__main__':
    cli()

      • share/examples/large/README.md 에서 데이터 다운로드/경로 설정 안내.

      • 내부 네트워크 미러 또는 사내 객체 저장소를 사용(체크섬 제공).

    • 캐시 디렉터리: /user/myteam/RELEASE/apps/mytool/.cache (권한 2775, 툴별 서브디렉터리).

    문서/검색 편의

    • share/examples/README.md 최상단에 목차 + 실행 난이도(★) + 예상 시간 표기.

    • 배포 스크립트에서 wheel 설치 후:

      • apps/mytool/releases/$VER/share/examples 에 예제 동봉(또는 pip install mytool[examples]).

    • 활성화(current 스위치)와 동시에 예제도 새 버전을 가리킴.

    whl을 모으는 폴더를 따로 파는건 어때

    네, 아주 좋은 생각이에요 👍

    installers/ 안에는 gcc.zip 같은 다양한 아카이브가 섞여 있어서, wheel 패키지까지 같이 두면 “런타임 설치용 파일”과 “파이썬 배포물”이 혼재하게 됩니다. 그래서 whl 전용 폴더를 따로 두는 게 깔끔 합니다.

    구조 예시 (whl 전용 폴더 추가)

    /user/myteam/RELEASE/
├─ toolchains/                   # gcc 등
├─ installers/                   # 설치 스크립트, zip, tar.gz, 기타 빌드 자원
│  ├─ gcc.zip
│  └─ ...
├─ wheels/                       # ← 새 폴더: 파이썬 wheel 아카이브만 모아둠
│  ├─ mytool-1.2.0-py3-none-any.whl
│  ├─ mytool-1.1.3-py3-none-any.whl
│  ├─ othertool-0.9.0-py3-none-any.whl
│  └─ constraints-1.2.0.txt      # (선택) 의존성 고정용 constraints 파일
├─ apps/                         # 실제 배포된 실행환경 (venv + current)
│  ├─ mytool/...
│  └─ othertool/...
└─ bin/                          # PATH에 추가되는 실행파일 링크 모음

    장점

    1. 역할 분리

      • installers/: zip, tar.gz, 설치 스크립트 등 범용 아카이브

      • wheels/: Python wheel/constraints → pip 설치 전용
        → 한눈에 봐도 어디에 무엇이 있는지 명확.

    2. 재현성↑

      • 버전별 wheel + constraints.txt 묶음 관리.

      • 설치 스크립트에서 pip install --no-index --find-links /user/myteam/RELEASE/wheels ... 하면 네트워크 없어도 동일 환경 재현.

    3. 자동화 스크립트 간결

      • 새 버전 배포 시 wheels/에만 whl 올리고 → apps/<tool>/releases/<ver>/venv에서 pip install 진행.

    4. 보안/검증

      • wheel은 hash 검증하기 쉽고, 폴더 단위로 관리 가능.

      • sha256sum -c wheels/SHA256SUMS 같은 체크도 쉽게 적용.

    설치 스크립트 흐름 예시

    BASE=/user/myteam/RELEASE
TOOL=mytool
VER=1.2.0
PY=python3.11

REL=$BASE/apps/$TOOL/releases/$VER
mkdir -p "$REL"
$PY -m venv "$REL/venv"

# 오프라인/재현성 설치
"$REL/venv/bin/pip" install --no-index \
  --find-links "$BASE/wheels" \
  -c "$BASE/wheels/constraints-$VER.txt" \
  $TOOL==$VER

    추가 팁

    • 폴더명 규칙

      • wheels/ 안에서 툴별로 서브폴더 만들어도 좋음: 
        wheels/
  mytool/
    1.2.0/
    1.1.3/
  othertool/
    0.9.0/
      • 대신 자동화 스크립트에서 find-links 경로만 유연하게 잡아주면 OK.

    • constraints.txt

      • 버전마다 기록해 두면 의존성 깨짐을 방지할 수 있음.

    • hash 검증

      • pip install --require-hashes -r requirements.txt 방식 사용 가능.

      • 또는 sha256sum으로 미리 확인.

    👉 즉, installers/는 범용 설치 리소스 보관소로 두고, Python 패키지는 wheels/ 전용 폴더를 파서 정리하는 게 장기적으로 훨씬 깔끔하고 안전합니다.

    내가 작업한걸 whl로 만드는 법? 그리고 pip 할 때 해당 경로를 참고하게 하는 법 알려줘

    1) 최소 구성 준비 (pyproject.toml)

    프로젝트 루트에 pyproject.toml 파일을 만듭니다. (예시는 mytool이라는 CLI를 만든다고 가정)

    [build-system]
requires = ["setuptools>=68", "wheel"]     # 빌드에 필요한 툴
build-backend = "setuptools.build_meta"

[project]
name = "mytool"                             # 패키지 이름 (pip에서 보이는 이름)
version = "1.2.0"                           # 버전
description = "My awesome CLI"
readme = "README.md"
requires-python = ">=3.9"
dependencies = [
  "click>=8.1.0",
]

# console_scripts: 설치 시 생성될 CLI 진입점
[project.scripts]
mytool = "mytool.cli:main"                  # mytool/cli.py 안의 main 함수를 실행

[tool.setuptools]
# 패키지 자동 탐색
packages = { find = { where = ["src"] } }

[tool.setuptools.package-dir]
"" = "src"                                  # 소스 루트: src/

# 패키지 데이터(예제/템플릿 등) 포함하려면
[tool.setuptools.package-data]
"mytool" = ["share/examples/**/*", "py.typed"]

README.md
pyproject.toml

    참고: setup.py 없이도 됩니다. (현대 표준은 pyproject.toml)

    온라인 pip도 사용하되 먼저 wheels 폴더를 찾게 하는 법

    좋은 질문이에요 👍
    “온라인 PyPI도 쓰되, 먼저 내부 wheels/ 폴더를 참고”하려면, pip 옵션을 조합하면 됩니다. 핵심은 --find-links는 ‘추가 경로’로 쓰이고, PyPI도 그대로 남겨둬야 한다는 점입니다.

    방법 1: 커맨드라인에서 옵션 조합

    pip install --find-links /user/myteam/RELEASE/wheels mytool==1.2.0

    • --find-links : 지정한 디렉터리나 URL에서 먼저 휠을 찾음

    • PyPI도 계속 조회하므로, wheels/에 있으면 그 파일을 쓰고, 없으면 PyPI에서 내려받음.

    • --no-index를 쓰지 않는 게 포인트 (그걸 쓰면 PyPI는 완전히 끊어짐).

    방법 2: requirements.txt 에 넣기

    requirements.txt 예시:

    --find-links /user/myteam/RELEASE/wheels
mytool==1.2.0
othertool>=0.9

    설치:

    pip install -r requirements.txt

    이러면 항상 먼저 /user/myteam/RELEASE/wheels를 뒤지고, 거기에 없는 패키지만 PyPI에서 가져옵니다.

    방법 3: pip 설정 파일에 반영

    팀 전체에 적용하려면 pip 설정 파일에 find-links를 추가할 수도 있습니다.

    • Linux/macOS: ~/.config/pip/pip.conf 또는 /etc/pip.conf

    • Windows: %APPDATA%\pip\pip.ini

    예시 (pip.conf):

    [global]
find-links = /user/myteam/RELEASE/wheels

    이렇게 해 두면 모든 pip install 시 자동으로 내부 wheels 경로를 먼저 탐색합니다.

    ⚠️ 주의할 점

    • --find-links는 “검색 우선순위”만 주는 것이고, 버전 선택은 pip가 합니다.
      예: mytool==1.2.0이 wheels 폴더에도 있고 PyPI에도 있어도, pip는 로컬 휠을 쓰게 됩니다.

    • 만약 로컬 휠 버전이 낮아도 반드시 쓰게 하고 싶다면, constraints 파일 을 같이 쓰는 걸 권장합니다.

    • 캐시 오염 방지를 위해 pip install --no-cache-dir 옵션을 주는 것도 방법입니다.

    👉 정리:

    • 로컬 wheels 우선, PyPI fallback → pip install --find-links /path/to/wheels package

    • 팀 전체 적용 → pip.conf에 find-links 설정

    원하시면 제가 예제 deploy.sh 스크립트를 만들어서, “wheels 폴더 우선 + PyPI fallback + constraints 체크”까지 한 번에 설치되도록 드릴까요?

    toolchains와 app의 차이?

    좋은 질문이에요. 지금까지 말씀하신 디렉터리 체계 안에서 toolchains/와 apps/는 역할이 명확히 다릅니다.

    1. toolchains/ (기반 도구 모음)

    • 정의 : 빌드·런타임에 필요한 외부 컴파일러·런타임·SDK 같은 기반 툴 을 모아두는 영역.

    • 예시

      • gcc-12.3.0/, clang-17/

      • jdk-21/ (Java 개발킷)

      • cmake-3.28/, ninja/

      • 특정 라이브러리 번들(예: CUDA, MPI)

    • 특징

      • 여러 앱/툴이 공유 해서 씀.

      • 보통 한 번 설치하면 자주 바뀌지 않음.

      • 버전별로 병렬 설치 가능 (toolchains/gcc-12.3.0, toolchains/gcc-11.4.0).

      • 환경변수(PATH, LD_LIBRARY_PATH)로 노출하거나, 앱이 실행될 때 wrapper가 경로를 추가.

    2. apps/ (실제 업무용 애플리케이션)

    • 정의 : 우리 팀이 직접 만든 도구/애플리케이션 배포물 을 설치하는 영역.

    • 예시

      • Python 툴 → apps/mytool/releases/1.2.0/venv/

      • 자체 Go/Java 프로그램 → apps/othertool/releases/...

    • 특징

      • 주기적으로 업데이트/롤백이 필요함 (버전별 venv 또는 바이너리 릴리스).

      • 각 앱은 자기 실행환경을 독립적으로 갖고(venv, config, logs).

      • bin/에 링크를 두어 사용자들이 실행.

    3. 정리 비교

    구분 toolchains/ apps/
    목적 기반 빌드·런타임 도구 최종 애플리케이션 배포
    소유자 외부/3rd-party (gcc, jdk 등) 우리 팀이 개발/배포하는 툴
    공유성 여러 앱이 공유 앱별 독립 (conf/logs/run/tmp 분리)
    변경 주기 낮음 (메이저 업그레이드 시에만) 잦음 (릴리스/핫픽스마다)
    버전 관리 여러 버전 병행 설치 (gcc-12, gcc-11) releases/<버전>/current 심볼릭 링크 방식
    사용 방식 PATH/LD_LIBRARY_PATH에 추가 bin/ 링크로 직접 실행

    4. 운영 패턴

    • toolchains/ :

      • 설치 후 잘 바꾸지 않음.

      • 필요하면 버전 병행 설치 + wrapper에서 어떤 gcc/jdk를 쓸지 선택.

    • apps/ :

      • 새 릴리스가 나올 때마다 releases/<ver> 추가 → current 업데이트.

      • 운영 중 롤백도 쉽게 할 수 있음.

    👉 한 줄 요약

    • toolchains/ = 기반이 되는 빌드/런타임 환경 (gcc, jdk, cmake …)

    • apps/ = 우리 팀이 만든 실제 배포 애플리케이션 (venv/바이너리, conf/logs 포함)

    원하시면 제가 toolchains/ 안에 버전별 gcc, apps/ 안에 Python 툴을 배치해서 wrapper 스크립트가 어떻게 두 영역을 동시에 사용하는지 예시를 적어드릴까요?

    apps 구조 추천

    좋아요—apps/는 “여러 앱을 독립적으로 운영·업데이트·롤백”하기 위한 공간이므로, 앱별 디렉터리 + 버전 디렉터리(releases) + current 심볼릭 링크 + 공용 쓰기 영역(conf/logs/run/tmp) 패턴을 권장합니다. 예제·문서까지 같은 버전에 잠그면 재현성도 보장돼요.

    기본 레이아웃(권장 템플릿)

    /user/myteam/RELEASE/
└─ apps/
   ├─ mytool/                      # 앱 단위 루트 (앱마다 1개)
   │  ├─ releases/                 # 버전별 설치물(읽기 전용)
   │  │  ├─ 1.2.0/
   │  │  │  ├─ venv/              # (Python) 이 버전 전용 가상환경
   │  │  │  ├─ bin/               # (선택) 버전 전용 보조 스크립트

    핵심 원칙

    • releases/ : 읽기 전용·재현 가능한 산출물, 버전별 병행 존재

    • current : 심볼릭 링크로 “활성 버전” 지정 → 롤백/업데이트가 ln -sfn 한 번

    • conf/ : 장비/그룹별 차이 상주(버전 교체에도 보존)

    • logs/run/tmp/ : 쓰기 가능한 운영 영역 분리

    • share/examples : 현재 버전과 동기화되는 예제/샘플 데이터

    권한/소유권(추천)

    • 소유자: root:myteam(또는 전용 사용자 apps)

    • 퍼미션:

      • apps/*/releases/** → 755 (팀 읽기 전용)

      • apps/*/{conf,logs,run,tmp} → 2775 (SGID로 그룹 상속 유지)

      chgrp -R myteam /user/myteam/RELEASE/apps

    PATH 연결(팀 공용 실행)

    팀이 PATH에 추가하는 상위 bin/에서 각 앱의 엔트리포인트로 링크:

    /user/myteam/RELEASE/bin/mytool -> ../apps/mytool/current/venv/bin/mytool

    특별히 toolchains 경로 주입이 필요한 앱만 링크 대신 래퍼 스크립트 를 둡니다(전역 오염 방지).

    앱 생명주기 스크립트(예: apps/<app>/bin/manage.sh)

    #!/usr/bin/env bash
set -euo pipefail
APP_HOME="/user/myteam/RELEASE/apps/mytool"
PY="python3.11"     # 비-Python 앱이면 생략/치환
CMD=${1:-}; VER=${2:-}

case "$CMD" in
  install)  # 새 버전 설치
    test -n "$VER"
    REL="$APP_HOME/releases/$VER"
    mkdir -p "$REL"
    $PY -m venv "$REL/venv"
    "$REL/venv/bin/pip" install --upgrade pip
    # 내부 wheels 우선 + PyPI fallback
    "$REL/venv/bin/pip" install \
      --find-links /user/myteam/RELEASE/wheels mytool=="$VER"
    mkdir -p "$REL/conf.defaults" "$REL/share/examples"
    ;;
  activate) # 활성 버전 전환(원자적)
    test -n "$VER"
    ln -sfn "$APP_HOME/releases/$VER" "$APP_HOME/current"
    ;;
  rollback) # 지정 버전으로 되돌리기
    test -n "$VER"
    ln -sfn "$APP_HOME/releases/$VER" "$APP_HOME/current"
    ;;
  health)
    "$APP_HOME/current/venv/bin/mytool" --version
    "$APP_HOME/current/venv/bin/mytool" --check || true
    ;;
  *)
    echo "usage: $0 {install|activate|rollback|health} <version>" >&2; exit 1;;
esac

    /user/myteam/RELEASE/
├─ bin/          # 사용자가 PATH에 넣는 ‘진입점’ 모음(링크/래퍼)
├─ toolchains/   # gcc, jdk 같은 기반 도구(여러 앱이 공용으로 사용)
├─ installers/   # zip/tar 등 설치 원본(보관소)
├─ wheels/       # 파이썬 wheel 아카이브 전용(내부 미니 “패키지 저장소”)
└─ apps/         # 실제 앱 설치/운영 공간(버전 관리 포함)

    1) 최상위 폴더들

    bin/

    • 역할 : 팀원들이 실행하는 진입점 을 한 곳에 모읍니다. 보통 여기에만 PATH를 추가해요.

    • 내용 :

      • 대부분 심볼릭 링크 : mytool -> ../apps/mytool/current/venv/bin/mytool

      • (필요 시) 래퍼 스크립트 : toolchains 경로를 잠깐 주입해야 할 때만 실제 스크립트를 둡니다.

    • 언제 수정? 최초 연결(링크 생성)과, 특별 환경이 필요한 앱에 한해 래퍼 작성 시.

    toolchains/

    • 역할 : gcc/clang, jdk, cmake 같은 외부 빌드·런타임 도구 를 버전별로 보관. 여러 앱이 공유 해서 사용.

    • 예시 : gcc-12.3.0/, jdk-21/, cmake-3.28/

    • 사용 방식 : 필요할 때만 앱 래퍼에서 PATH, LD_LIBRARY_PATH 등에 일시 주입. 전역 오염 방지.

    • 변경 주기 : 낮음(업그레이드 때만 추가 설치).

    installers/

    • 역할 : 각종 설치 원본 보관소(zip, tar.gz, 스크립트 등). “원본 그대로” 안전하게 저장.

    • 예시 : gcc.zip, jdk.tar.gz, 내부 배포 스크립트 등.

    • 주의 : 여기서 바로 실행/운영하지 않습니다. apps/ 아래에 설치해 사용.

    wheels/

    • 역할 : 파이썬 wheel 전용 저장소. pip가 먼저 이 경로를 조회 하도록 설정해, 내부 빌드물을 우선 사용.

    • 예시 :

      • mytool-1.2.0-py3-none-any.whl

      • (선택) constraints-1.2.0.txt, SHA256SUMS

    • 설치 예시 :

      pip install --find-links /user/myteam/RELEASE/wheels mytool==1.2.0

    (필요하면 PyPI에서도 내려받도록 --no-index는 쓰지 않음)

    apps/

    • 역할 : 앱별 실제 설치/운영 공간. 버전별 설치물과 설정·로그 등을 분리해 안정적으로 업데이트/롤백.

   │  │  ├─ bin/             # (선택) 버전 전용 보조 스크립트

    각 폴더 설명을 더 자세히:

    releases/

    • 역할 : 버전별 설치물(읽기 전용). 과거 버전까지 평행 보관 → 재현/비교/롤백이 쉬움.

    • 언제 수정? 새 버전 설치 시 새 디렉터리 추가. 기존 버전은 그대로 둠.

    releases/<ver>/venv/ (Python일 때)

    • 역할 : 해당 버전 전용 가상환경. wheel을 여기로 설치해 타 앱/버전과 의존성 충돌 방지.

    • 예시 명령 :

      python3.11 -m venv apps/mytool/releases/1.2.0/venv
apps/mytool/releases/1.2.0/venv/bin/pip install --find-links /user/myteam/RELEASE/wheels mytool==1.2.0

    releases/<ver>/lib/ (Go/단일 바이너리 등일 때)

    • 역할 : 파이썬이 아닌 앱의 실행 파일/라이브러리 위치.

    • 예시 : lib/mytool (단일 바이너리), lib/plugins/*.so

    releases/<ver>/conf.defaults/

    • 역할 : 버전에 잠긴 기본 설정. 새 버전에서 옵션이 바뀌면 여기 내용도 함께 진화.

    • 로딩 규칙(권장) : 실제 실행 시 conf/ 값이 있으면 defaults를 덮어씀.

    releases/<ver>/share/examples/

    • 역할 : 예제 입력/명령/샘플 데이터. 현재 버전과 동기화.

    • 사용자 접근 : 항상 apps/mytool/current/share/examples 경로로 접근하면 “활성 버전” 예제를 보게 됨.

    releases/<ver>/docs/

    • 역할 : 릴리스 노트, 마이그레이션 가이드, 사용 팁 등 버전 고정 문서.

    current (심볼릭 링크)

    • 역할 : “지금 서비스 중인 버전”을 가리킴.

    • 장점 : ln -sfn 한 번으로 원자적 전환/롤백 가능. 공용 bin/mytool 링크는 그대로 두고 자동 반영.

    conf/

    • 역할 : 서버/환경별 오버라이드 설정. 버전 교체에도 그대로 유지 되어 안정적.

    • 예시 : conf/app.yaml, conf/secrets.env(권한 640)

    • 로딩 우선순위 : conf/ → current/conf.defaults/ (키 충돌 시 conf/ 우선)

    logs/

    • 역할 : 앱 로그 저장(팀 쓰기 가능).

    • 예시 : logs/mytool.out.log

    • 운영 팁 : logrotate 설정으로 용량 관리.

    run/

    • 역할 : 런타임 파일(PID, unix socket, 락 파일 등)만 보관. 프로세스/서비스 매니저가 참고.

    tmp/

    • 역할 : 임시 작업 공간. 예제 실행물/중간 산출물 등.

    • 주의 : 주기적으로 정리하거나, 각각의 실행에서 자체 하위 디렉터리를 만들도록.

    bin/ (앱 내부)

    • 역할 : 관리 스크립트(예: manage.sh) 위치.

    • 예시 기능 : install <ver>, activate <ver>, rollback <ver>, health

    1. 설치 : apps/mytool/releases/1.2.0/ 생성 → venv/ 만들고 pip install

    2. 헬스체크 : releases/1.2.0/venv/bin/mytool --version/--check

    3. 전환(활성화) : current -> releases/1.2.0 로 심볼릭 링크 스위치

    4. 사용자 실행 : PATH에 넣어둔 /user/myteam/RELEASE/bin/mytool 실행

      • (링크가) apps/mytool/current/venv/bin/mytool로 이어짐 → 항상 활성 버전 동작

    5. 롤백 : current를 이전 버전으로 다시 바꿔 끝.

    SGID가 뭐야? 그리고 conf는 어떻게 읽어?

    좋은 질문이에요! 두 가지를 나눠서 설명드릴게요.

    1. SGID (Set-Group-ID)란?

    리눅스에서 파일/디렉터리에 설정할 수 있는 특수 퍼미션 비트 중 하나입니다.

    • 일반 권한 구조 : rwxrwxrwx (소유자 / 그룹 / 기타)

    • SGID 비트 : 디렉터리에 걸면, 그 디렉터리 안에서 새로 만들어지는 파일/폴더가 자동으로 부모의 그룹을 상속 합니다.

    예시:

    mkdir /user/myteam/RELEASE/apps/mytool/logs
chgrp myteam /user/myteam/RELEASE/apps/mytool/logs
chmod 2775 /user/myteam/RELEASE/apps/mytool/logs

    • 2 → SGID 비트 켜기

    • 결과: /apps/mytool/logs 아래에서 누가 파일을 만들어도 그룹이 자동으로 myteam이 됨

    👉 효과 : 팀 작업에서 “파일은 다 myteam 그룹 소유”로 맞춰지기 때문에, 팀원들이 서로 쓴 로그/설정 파일을 읽고 쓸 수 있음. SGID 없으면, 어떤 사용자가 만든 파일이 개인 그룹 소유가 되어 팀원이 못 건드리는 일이 발생합니다.

    2. conf는 어떻게 읽나?

    제가 추천한 구조에서는 앱 실행 시 두 단계 의 설정 경로가 있습니다:

    1. defaults (apps/mytool/releases/<ver>/conf.defaults/)

      • 앱 버전과 같이 배포되는 기본 설정.

      • 예: 기본 로그 레벨, 기본 포트 번호.

      • 버전업하면 내용이 바뀔 수 있음.

    2. conf (apps/mytool/conf/)

      • 운영 환경별/서버별 오버라이드 설정.

#!/bin/tcsh -f
# mytool tcsh wrapper with version selection
# place at: /user/myteam/RELEASE/bin/mytool
# chmod +x /user/myteam/RELEASE/bin/mytool

# ----- configurable -----
set BASE = "/user/myteam/RELEASE"
set TOOL = "mytool"
set APP_HOME = "$BASE/apps/$TOOL"
# 주입이 필요하면 아래 주석 풀기 (예: gcc)
# setenv PATH "$BASE/toolchains/gcc-12.3.0/bin:$PATH"
# setenv LD_LIBRARY_PATH "$BASE/toolchains/gcc-12.3.0/lib64:${LD_LIBRARY_PATH}"
# ------------------------

# usage/help
if ( "$1" == "-h" || "$1" == "--help" ) then
  echo "Usage: mytool [-v <version>] [--] <args...>"
  echo "       mytool -L           # list available versions"
  echo "       mytool -P           # print selected version path"
  exit 0
endif

# list versions
if ( "$1" == "-L" ) then
  if ( ! -d "$APP_HOME/releases" ) then
    echo "No releases dir: $APP_HOME/releases" >&2
    exit 1
  endif
  # 단순 목록(정렬은 파일명 기준)
  /bin/ls -1 "$APP_HOME/releases"
  exit 0
endif

# print selected path (for debug)
set PRINT_PATH_ONLY = 0
if ( "$1" == "-P" ) then
  set PRINT_PATH_ONLY = 1
  shift
endif

# parse -v <version>
set REQ_VER = ""
@ i = 1
while ( $i <= $#argv )
  if ( "$argv[$i]" == "-v" ) then
    @ j = $i + 1
    if ( $j > $#argv ) then
      echo "Option -v requires a version (e.g. -v 1.2.0)" >&2
      exit 2
    endif
    set REQ_VER = "$argv[$j]"
    # -v 와 그 값 제거
    set argv[$i] = ""
    set argv[$j] = ""
    # 재압축(빈 인자 제거)
    set tmp = ( $argv )
    set argv = ()
    foreach a ( $tmp )
      if ( "$a" != "" ) set argv = ( $argv $a )
    end
    break
  endif
  @ i++
end

# 결정: 타겟 버전 디렉터리
set TARGET = ""
if ( "$REQ_VER" == "" ) then
  set TARGET = "$APP_HOME/current"
else
  set TARGET = "$APP_HOME/releases/$REQ_VER"
endif

if ( ! -d "$TARGET" ) then
  echo "Selected version path not found: $TARGET" >&2
  echo "Use 'mytool -L' to list available versions." >&2
  exit 3
endif

# 실행 파일 결정 (Python 콘솔 스크립트 기준)
set EXE = "$TARGET/venv/bin/$TOOL"
if ( ! -x "$EXE" ) then
  # Go/단일 바이너리 레이아웃을 쓰는 경우 lib/mytool 시도
  if ( -x "$TARGET/lib/$TOOL" ) then
    set EXE = "$TARGET/lib/$TOOL"
  else
    echo "Executable not found: $EXE (or $TARGET/lib/$TOOL)" >&2
    exit 4
  endif
endif

# conf/defaults 경로 주입 (앱이 읽도록)
setenv ${TOOL:u}_CONFIG_DIR        "$APP_HOME/conf"
setenv ${TOOL:u}_DEFAULTS_DIR      "$TARGET/conf.defaults"
setenv ${TOOL:u}_LOG_DIR           "$APP_HOME/logs"
setenv TMPDIR                      "$APP_HOME/tmp"

# -P 모드면 경로만 출력
if ( $PRINT_PATH_ONLY == 1 ) then
  echo "$EXE"
  exit 0
endif

# 실제 실행
exec "$EXE" $argv

    Python 런처 스크립트 (버전 선택 포함)

    /user/myteam/RELEASE/bin/mytool 파일로 저장하고 실행권한 주세요.

    #!/usr/bin/env python3
# -*- coding: utf-8 -*-
"""
mytool Python wrapper with version selection and optional toolchains injection.

Place at: /user/myteam/RELEASE/bin/mytool
chmod +x /user/myteam/RELEASE/bin/mytool
"""

import argparse
import os
import sys

# ----- configurable -----
BASE = "/user/myteam/RELEASE"
TOOL = "mytool"
APP_HOME = os.path.join(BASE, "apps", TOOL)

# 필요 시 toolchains 경로 주입 (예: gcc)
INJECT_TOOLCHAINS = False
GCC_VERSION = "gcc-12.3.0"
# ------------------------

def list_versions():
    rel = os.path.join(APP_HOME, "releases")
    if not os.path.isdir(rel):
        print(f"No releases dir: {rel}", file=sys.stderr)
        return 1
    # 파일명 기준 정렬
    for name in sorted(os.listdir(rel)):
        path = os.path.join(rel, name)
        if os.path.isdir(path):
            print(name)
    return 0

def resolve_target(requested_version: str | None) -> str:
    if not requested_version:
        target = os.path.join(APP_HOME, "current")
    else:
        if requested_version in ("latest", "current"):
            target = os.path.join(APP_HOME, "current")
        else:
            target = os.path.join(APP_HOME, "releases", requested_version)
    if not os.path.isdir(target):
        raise FileNotFoundError(f"Selected version path not found: {target}")
    return target

def find_executable(target: str) -> str:
    """Prefer Python console_script in venv; fallback to lib/<tool> for non-Python apps."""
    exe = os.path.join(target, "venv", "bin", TOOL)
    if os.path.isfile(exe) and os.access(exe, os.X_OK):
        return exe
    alt = os.path.join(target, "lib", TOOL)
    if os.path.isfile(alt) and os.access(alt, os.X_OK):
        return alt
    raise FileNotFoundError(f"Executable not found: {exe} (or {alt})")

def build_env(target: str) -> dict:
    env = os.environ.copy()

    # 앱 공용/버전별 경로 주입
    env[f"{TOOL.upper()}_CONFIG_DIR"]   = os.path.join(APP_HOME, "conf")
    env[f"{TOOL.upper()}_DEFAULTS_DIR"] = os.path.join(target, "conf.defaults")
    env[f"{TOOL.upper()}_LOG_DIR"]      = os.path.join(APP_HOME, "logs")
    env["TMPDIR"]                       = os.path.join(APP_HOME, "tmp")

    # 필요 시 toolchains 주입 (전역 오염 방지: 이 프로세스에서만 반영)
    if INJECT_TOOLCHAINS:
        gcc_bin = os.path.join(BASE, "toolchains", GCC_VERSION, "bin")
        gcc_lib = os.path.join(BASE, "toolchains", GCC_VERSION, "lib64")
        env["PATH"] = f"{gcc_bin}:{env.get('PATH','')}"
        env["LD_LIBRARY_PATH"] = f"{gcc_lib}:{env.get('LD_LIBRARY_PATH','')}"

    return env

def main():
    parser = argparse.ArgumentParser(
        prog=TOOL, add_help=False,
        description="mytool launcher with version selection"
    )
    parser.add_argument("-h", "--help", action="store_true")
    parser.add_argument("-L", action="store_true", help="List available versions")
    parser.add_argument("-P", action="store_true", help="Print selected executable path and exit")
    parser.add_argument("-v", metavar="VERSION", help="Use specific version (e.g., 1.2.0). 'latest' or 'current' allowed")
    # 나머지 인자는 실제 mytool에 그대로 전달
    args, passthrough = parser.parse_known_args()

    if args.help:
        print(
            f"Usage: {TOOL} [-v <version>] [--] <args...>\n"
            f"       {TOOL} -L        # list versions\n"
            f"       {TOOL} -P [-v <version>]  # print resolved executable path\n",
            end=""
        )
        return 0

    if args.L:
        return list_versions()

    try:
        target = resolve_target(args.v)
    except FileNotFoundError as e:
        print(str(e), file=sys.stderr)
        print(f"Use '{TOOL} -L' to list available versions.", file=sys.stderr)
        return 3

    try:
        exe = find_executable(target)
    except FileNotFoundError as e:
        print(str(e), file=sys.stderr)
        return 4

    if args.P:
        print(exe)
        return 0

    env = build_env(target)

    # 실제 실행(현재 프로세스를 교체)
    os.execvpe(exe, [exe] + passthrough, env)

if __name__ == "__main__":
    try:
        sys.exit(main())
    except KeyboardInterrupt:
        sys.exit(130)

    앱별로 apps/<tool>/releases/.../venv 안에 버전 종속 venv 를 두는 것도 필요하지만, 말씀하신 “공용 깨끗한 기본 venv ”는 또 다른 용도가 있습니다.

    1. 왜 공용 venv가 유용할까?

    • wrapper 실행 환경 표준화 : 각 앱의 wrapper 스크립트가 돌아가는 최소 파이썬 환경을 항상 깨끗한 venv에 두면, 시스템 Python에 영향 안 받습니다.

    • 관리 단순화 : pip, build, 배포용 유틸, 공통 관리 스크립트만 설치해두고, 나머지는 각 앱 버전 venv에서 처리.

    • 빠른 복원 : 문제가 생기면 공용 venv만 날리고 다시 생성 → 앱 venv와 분리되어 안정적.

    2. 위치 구조 추천

   └─ test/           # (선택) 통합테스트용 환경

    • test/ : (필요 시) 통합 테스트 파이프라인에서만 사용하는 환경

    4. wrapper에서 사용하기

    Python wrapper (앞서 만든 스크립트) 상단에서 venv/base/bin/python 을 강제 지정하면 됩니다.

    BASE = "/user/myteam/RELEASE"
