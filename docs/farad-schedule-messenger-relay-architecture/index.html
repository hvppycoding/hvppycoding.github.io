Farad internal messenger relay
Scenario contract · 2026-07-15
Farad × 사내 메신저

Relay는 실행기가 아니라, 명령을 잃지 않는 우체통이다

사용자가 메신저에서 Schedule을 연달아 눌러도 Relay는 각 클릭을 독립된 명령으로 저장합니다. 실제 동시 실행 여부는 Farad가 “같은 Schedule인가?”만 보고 결정합니다.

A 다음 B서로 다른 Schedule이므로 둘 다 실행
A 다음 A첫 A만 실행, 두 번째 A는 already_running

세 구성요소의 책임을 섞지 않는다

Relay는 메신저와 통신 가능한 중앙 VM에 있고, 실제 Schedule 정의와 실행 상태는 각 사용자 호스트의 Farad에만 있습니다.

SCENARIO 01

처음 한 번만 연결한다

공용 매핑 파일은 인증 수단이 아니라 “내 Knox ID를 찾는 주소록”입니다. Linux ID는 Farad 안에서 조회에만 쓰고 Relay에는 보내지 않습니다.

  1. Farad
    현재 Linux 계정으로 공용 매핑 파일 조회자기 행의 senderKnoxId 한 건만 읽고 전체 파일은 보관하지 않습니다.
  2. Farad
    256비트 이상의 client token 생성원문은 로컬 보호 파일에 저장합니다.
  3. Relay
    {knoxId, token} 등록을 pending으로 저장token 원문 대신 hash를 저장합니다.
  4. 사용자
    메신저 봇을 열거나 말을 건다Relay가 수신 envelope의 공식 senderKnoxId를 확인합니다.
  5. Relay
    pending Knox ID가 일치하면 active 전환메신저 userId와 chatroomId도 같은 client에 연결합니다.
공용 파일을 읽을 수 있다는 사실만으로는 본인 증명이 되지 않습니다. 마지막 메신저 확인 단계가 “이 Knox 계정을 실제로 사용하는 사람”임을 확인합니다.
SCENARIO 02

Farad를 껐다 켜도 다시 매핑하지 않는다

  1. Farad
    로컬 보호 파일에서 client token 읽기공용 매핑 파일과 Linux ID는 다시 보지 않습니다.
  2. Farad
    Bearer token으로 Relay Long Poll 시작GET /commands?waitSeconds=25
  3. Relay
    token hash로 active client 조회저장된 Knox ID, messenger userId, chatroomId를 사용합니다.
  4. Relay
    대기 명령 또는 빈 응답 반환Farad는 응답 직후 다음 Long Poll을 엽니다.
Farad가 기억하는 것은 client token 하나별도 Linux ID, Knox ID, bindingId를 로컬 state에 중복 저장하지 않습니다. token이 없거나 Relay binding이 폐기된 경우에만 최초 연결을 다시 합니다.

SCENARIO 04

사용자가 A를 두 번 실행한다

Relay는 두 클릭을 안전하게 접수하지만, 실행 권위인 Farad가 두 번째 명령을 거절합니다. Relay가 임의로 실행 상태를 판단하지 않습니다.

SCENARIO 05

클릭 직후 Farad 연결이 끊긴다

Long Poll 응답 자체는 명령의 정본이 아닙니다. Relay가 먼저 SQLite에 저장하고 Farad의 ACK를 받기 전까지 보관합니다.

  1. 사용자
    Schedule A 실행 클릭메신저 RP가 action event를 Relay에 전달합니다.
  2. Relay
    commandId=301을 SQLite에 먼저 저장이 시점부터 네트워크 응답이 끊겨도 명령은 남습니다.
  3. Farad
    Long Poll 연결이 끊어짐아직 ACK가 없으므로 command는 pending입니다.
  4. Farad
    재연결 후 같은 command 수신처리 결과를 제출하고 ACK합니다.
  5. Relay
    ACK 이후에만 전달 완료 처리메신저 webhook 재전송도 inbound msgId로 중복 제거합니다.
명령 보관 만료시간은 운영 정책으로 별도 확정해야 합니다. 핵심 계약은 “persist before deliver, ACK after result”입니다.

두 종류의 token을 혼동하지 않는다

메신저 OpenAPI 인증 token과 Farad client token은 소유자와 목적이 완전히 다릅니다.

Messenger API tokenRelay VM 배포 비밀. OpenAPI의 Authorization: Bearer 헤더에 사용하며 Farad에 배포하지 않습니다.
Farad client token각 Farad 설치가 생성하는 비밀. Relay Long Poll 인증에 사용하며 Relay는 hash만 저장합니다.
actionToken한 카드 버튼을 한 동작에 연결하는 짧은 수명의 opaque 값. Schedule ID나 prompt를 포함하지 않습니다.
itemToken / runRefFarad가 실제 Schedule과 실행을 안전하게 식별하는 opaque 참조. 메신저에 내부 ID를 노출하지 않습니다.

저장 위치

Farad 사용자 호스트

  • 보호된 client token 원문
  • Schedule 정의와 실제 ID
  • 실행 상태와 single-flight
  • 세션 transcript와 상세 결과

Relay VM SQLite

  • client token hash와 Knox binding
  • messenger userId와 chatroomId
  • inbound dedupe와 action route
  • command, ACK, delivery outbox

Relay를 여기서 더 키우지 않는다

Relay는 durable message broker 경계까지만 갖고, Schedule 업무 규칙은 Farad에 남깁니다.

Relay에 필요한 것

  • POST /message 수신
  • Messenger v2 암복호화·송신
  • client 등록과 token hash 검증
  • Long Poll command queue와 ACK
  • actionToken, dedupe, delivery retry

Relay에 넣지 않을 것

  • Linux ID와 공용 매핑 파일
  • Schedule 정의·prompt·경로
  • LLM 판단과 transcript
  • 실행 가능 여부와 single-flight
  • 자유 텍스트 보관
최종 동시 실행 규칙서로 다른 Schedule은 동시에 실행할 수 있습니다. 동일 Schedule에는 활성 실행이 하나만 존재합니다. Relay는 클릭을 잃지 않고 전달하고, Farad가 이 규칙을 최종 판정합니다.
현재 확정된 설계 계약을 시나리오로 정리한 문서입니다. pairing·Long Poll·Schedule adapter는 다음 구현 단계이며, command 보관 TTL과 오프라인 사용자 표시 문구는 운영 정책 확정이 필요합니다.
