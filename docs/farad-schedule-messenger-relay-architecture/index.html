시나리오 설계 전체 구조 최초 연결 재시작 상세 메시지 흐름 A 다음 B 실행 A를 두 번 실행 Farad 오프라인 데이터 소유권 구현 범위
Farad internal messenger relay
Scenario contract · 2026-07-15
Farad × 사내 메신저

Relay는 실행기가 아니라, 명령을 잃지 않는 우체통이다

사용자가 메신저에서 Schedule을 연달아 눌러도 Relay는 각 클릭을 독립된 명령으로 저장합니다. 실제 동시 실행 여부는 Farad가 “같은 Schedule인가?”만 보고 결정합니다.

A 다음 B서로 다른 Schedule이므로 둘 다 실행
A 다음 A첫 A만 실행, 두 번째 A는 already_running

세 구성요소의 책임을 섞지 않는다

Relay는 메신저와 통신 가능한 중앙 VM에 있고, 실제 Schedule 정의와 실행 상태는 각 사용자 호스트의 Farad에만 있습니다.

SCENARIO 01

처음 한 번만 연결한다

공용 매핑 파일이나 Linux ID 전달은 필요 없습니다. Farad가 관리 명령을 한 번 실행해 현재 사용자의 Knox ID를 직접 얻습니다.

  1. Farad
    /appl/LINUX/Hyper/utils/singleid 실행인자와 shell 없이 실행하고 stdout 한 줄을 senderKnoxId로 검증합니다.
  2. Farad
    256비트 이상의 client token 생성원문은 로컬 보호 파일에 저장합니다.
  3. Relay
    {knoxId, token} 등록을 pending으로 저장token 원문 대신 hash를 저장합니다.
  4. 사용자
    메신저 봇을 열거나 말을 건다Relay가 수신 envelope의 공식 senderKnoxId를 확인합니다.
  5. Relay
    pending Knox ID가 일치하면 active 전환메신저 userId와 chatroomId도 같은 client에 연결합니다.
singleid 결과는 Farad state나 transcript에 저장하지 않습니다. 마지막 메신저 확인 단계가 “이 Knox 계정을 실제로 사용하는 사람”임을 확인하고, 이후 binding은 Relay가 기억합니다.
SCENARIO 02

Farad를 껐다 켜도 다시 매핑하지 않는다

  1. Farad
    로컬 보호 파일에서 client token 읽기singleid 명령은 다시 실행하지 않습니다.
  2. Farad
    Bearer token으로 Relay Long Poll 시작GET /commands?waitSeconds=25
  3. Relay
    token hash로 active client 조회저장된 Knox ID, messenger userId, chatroomId를 사용합니다.
  4. Relay
    대기 명령 또는 빈 응답 반환Farad는 응답 직후 다음 Long Poll을 엽니다.
Farad가 기억하는 것은 client token 하나별도 Linux ID, Knox ID, bindingId를 로컬 state에 중복 저장하지 않습니다. token이 없거나 Relay binding이 폐기된 경우에만 최초 연결을 다시 합니다.
FULL WIRE TRACE

처음 연결부터 답장 선택까지, 실제 왕복

아래는 한 사용자가 Farad를 연결하고, Schedule 목록을 열고, 하나를 실행한 뒤 “시뮬레이션 실패” 카드에서 “다시 하기”를 선택하는 전체 흐름입니다. 메신저가 제공한 API는 확정 계약으로, 아직 구현할 Farad–Relay API는 제안 계약으로 표시했습니다.

확정 계약 제공받은 Messenger v2·수신 API 명세 제안 계약 Farad와 Relay 사이에서 구현할 내부 API
① 사용자 ② Messenger RP / OpenAPI ③ 중앙 VM Relay ④ Relay SQLite ⑤ 사용자 호스트 Farad
두 Bearer token은 완전히 다릅니다. Messenger API token은 Relay가 OpenAPI를 호출할 때만 쓰고, Farad client token은 한 Farad 설치가 Relay의 Long Poll·result·event API를 호출할 때만 씁니다.
PHASE A · 01–11

최초 연결과 홈 카드

01사용자→Farad
Remote control 켜기

settings.json의 features.remoteControl=true일 때만 UI가 보입니다. 사용자가 연결을 누릅니다.

02Farad→singleid
현재 사용자의 Knox ID 조회

인자와 shell 없이 정확히 한 번 실행합니다.

/appl/LINUX/Hyper/utils/singleid
stdout: user.knox.id
Farad는 형식만 검증하고 이 결과를 state·transcript·로그에 영구 저장하지 않습니다.
03Farad→Relay
제안 계약 설치 등록
POST /v1/clients/register
Content-Type: application/json

{
  "knoxId": "user.knox.id",
  "clientToken": "<Farad가 생성한 256-bit random secret>"
}
Farad는 client token 원문만 로컬 민감 저장소에 보관합니다. Relay는 원문을 DB에 저장하지 않습니다.
04Relay→SQLite
연결 대기 상태 커밋
clients:
  token_hash = HASH(clientToken)
  knox_id = "user.knox.id"
  status = "PENDING"
  messenger_user_id = NULL
  chatroom_id = NULL
DB commit이 성공한 뒤에만 등록 API에 성공을 반환합니다.
05Farad→Relay
제안 계약 첫 Long Poll
GET /v1/commands?waitSeconds=25&limit=10
Authorization: Bearer <Farad client token>

PENDING client에는 일반 실행 명령을 주지 않고 활성화 신호만 기다립니다.

06사용자→Messenger
봇을 처음 열기

첫 진입이면 Messenger RP가 msgType=TEXT, chatMsg=INTRO 이벤트를 만듭니다.

07Messenger RP→Relay
확정 계약 수신 webhook
POST http://{relay-ip:port}/message
Content-Type: text/plain
botUserEmail: bot@example.com

AES-256-CBC → Base64 body

복호화 결과:
{
  "sender": 189473292,
  "senderKnoxId": "user.knox.id",
  "senderName": "홍길동",
  "chatType": "SINGLE",
  "chatroomId": 193802984023,
  "msgId": 23234,
  "msgType": "TEXT",
  "chatMsg": "INTRO",
  "sentTime": 134234241
}
Relay의 키 조회는 GET https://openapi.stage.samsung.net/messenger/msgctx/api/v2.0/key/getkeys이며 Authorization: Bearer …, x-device-id, x-device-type: relation, System-ID, Accept: text/plain을 보냅니다. 받은 hex string의 앞 32 bytes가 Key, 뒤 16 bytes가 IV입니다.
08Relay→SQLite
신원 연결과 홈 발송을 한 transaction으로 예약
inbound_messages(msg_id=23234)      -- dedupe
clients: PENDING → ACTIVE
  messenger_user_id = 189473292
  chatroom_id = 193802984023
commands(kind="CLIENT_ACTIVATED", status="PENDING")
deliveries(kind="HOME_CARD", status="PENDING")
이 네 변경이 모두 커밋된 뒤 Relay가 Messenger에 HTTP 200 OK를 반환합니다. 200 전에 프로세스가 죽으면 RP 재전송을 안전하게 다시 받습니다.

확정 계약 홈 Adaptive Card 발송

Authorization: Bearer <Messenger API token>
x-device-id: <registered device id>
x-device-type: relation
System-ID: <integration account id>
Content-Type: text/plain
Accept: text/plain

{
  "requestId": 1784100000001,
  "chatroomId": 193802984023,
  "chatMessageParams": [{
    "msgId": 1784100000002,
    "msgType": 19,
    "chatMsg": "{\"type\":\"AdaptiveCard\",\"$schema\":\"http://adaptivecards.io/schemas/adaptive-card.json\",\"version\":\"1.3\",\"body\":[{\"type\":\"TextBlock\",\"text\":\"무엇을 확인할까요?\",\"weight\":\"Bolder\"}],\"actions\":[{\"type\":\"Action.Submit\",\"title\":\"LLM 사용량 조회\",\"data\":{\"actionToken\":\"act_home_llm_r2\"}},{\"type\":\"Action.Submit\",\"title\":\"Farad 예약 작업 조회\",\"data\":{\"actionToken\":\"act_home_schedule_x7\"}}]}"

홈 카드의 각 Action.Submit.data에는 의미 있는 ID 대신 {"actionToken":"act_home_schedule_x7"}만 넣습니다.

10OpenAPI→Relay
발송 결과와 카드 갱신 키
{
  "result": {"code": 1000},
  "processedMessageEntries": [{
    "msgId": 1784100000002,
    "msgKey": 12393024,
    "sentTime": 1784100000123
  }]
}
Relay는 msgKey를 delivery/card record에 저장합니다. 이후 카드 변경은 수신 payload에 메아리친 msgKey가 아니라 이 저장값만 씁니다.
11Relay→Farad
대기 중 Long Poll 깨우기
200 OK
{
  "commands": [{
    "commandId": 100,
    "kind": "CLIENT_ACTIVATED"
  }],
  "hasMore": false,
  "leaseUntilMillis": 1784100030000
}

Farad는 처리 후 POST /v1/commands/100/result를 보냅니다. Relay가 이 result를 커밋하는 것이 별도 ACK를 대신합니다.

PENDING client→Messenger 신원 확인→ACTIVE client→홈 카드 표시

13Messenger RP→Relay
확정 계약 카드 클릭 webhook
POST /message
Content-Type: text/plain

복호화한 envelope:
{
  "sender": 189473292,
  "senderKnoxId": "user.knox.id",
  "chatroomId": 193802984023,
  "msgId": 23235,
  "msgType": "ADAPTIVE_CARD",

권위 있는 신원은 바깥 envelope의 sender와 chatroomId입니다. chatMsg 안의 userId·chatroomId·msgKey는 클라이언트가 되돌린 값이므로 권한 판정에 쓰지 않습니다.
14Relay→SQLite
클릭 접수 transaction
1. inbound msgId dedupe 확인/기록
2. actionToken의 sender·room·TTL·card generation 검증
3. actionToken ACTIVE → CONSUMED
4. command 101 LIST_SCHEDULES / PENDING 생성
5. 기존 홈 카드의 LOADING update delivery 생성
COMMIT
명령과 “이미 눌렀음” 상태를 같은 transaction에 저장합니다. 커밋 뒤 즉시 HTTP 200 OK를 반환합니다.
15Relay→OpenAPI
확정 계약 클릭한 홈 카드 비활성화
POST .../message/api/v2.0/message/updateMessageRequest
{
  "requestId": 1784100000101,
  "chatroomId": 193802984023,
  "chatMessageParams": [{
    "msgId": 1784100000002,
    "msgKey": 12393024,
    "msgType": 20,

}
클릭한 주요 버튼은 먼저 제거합니다. 카드 갱신이 실패해도 actionToken은 다시 열지 않고 outbox가 같은 update를 재시도합니다.
16Relay→Farad
제안 계약 Long Poll로 목록 명령 전달
200 OK
{
  "commands": [{
    "commandId": 101,
    "kind": "LIST_SCHEDULES"
  }],
  "hasMore": false,
  "leaseUntilMillis": 1784100035000
}
한 응답에 최대 10개를 줍니다. hasMore=true면 Farad가 기다리지 않고 다음 poll을 열어 나머지를 받습니다.

19Relay→SQLite
result 커밋 = command ACK
command 101: LEASED → COMPLETED
command_results(command_id=101, payload_hash=...)
action_routes(actionToken → client/viewId/itemToken/cardRef/TTL)
deliveries(kind="SCHEDULE_LIST_UPDATE", status="PENDING")
COMMIT
같은 commandId의 동일 result를 재전송해도 한 번만 반영합니다. Farad가 HTTP 응답을 못 받으면 안전하게 같은 result를 재시도할 수 있습니다.
20Relay→OpenAPI
같은 카드를 Schedule 목록으로 갱신

UpdateMessageRequest의 msgType=20으로 항목별 실행 버튼과 항상 존재하는 “뒤로”, “홈으로”를 표시합니다.

21OpenAPI→사용자
Schedule 카드 표시

사용자는 승인된 별칭과 READY/RUNNING 같은 고정 상태만 봅니다. 민감한 구체 텍스트는 카드에 들어가지 않습니다.

끊김·중복·엉뚱한 신호가 들어왔을 때

Long Poll이 끊김result가 커밋되지 않은 command는 lease 만료 후 재전달합니다. 응답을 받았다는 사실만으로 삭제하지 않습니다.
카드 update 실패선택은 이미 소비된 상태로 유지하고 delivery outbox만 재시도합니다. 버튼 동작을 다시 열지 않습니다.
같은 클릭 재전송inbound msgId와 actionToken 상태로 중복 제거하고 HTTP 200만 반환합니다. 새 command를 만들지 않습니다.
알 수 없는 keywordFarad와 Relay 양쪽 allowlist에서 거절합니다. 카드·command를 만들지 않고 원문 payload를 로그에 남기지 않습니다.
일반 TEXT 메시지자유 텍스트 내용은 업무 명령으로 해석하거나 저장하지 않습니다. 정해진 홈 카드만 다시 보여줍니다.
result 응답 유실Farad가 같은 commandId와 같은 result를 재전송합니다. Relay의 idempotent commit 때문에 Schedule이 다시 실행되지는 않습니다.

SCENARIO 05

클릭 직후 Farad 연결이 끊긴다

Long Poll 응답 자체는 명령의 정본이 아닙니다. Relay가 먼저 SQLite에 저장하고 Farad의 처리 결과가 커밋될 때까지 보관합니다.

  1. 사용자
    Schedule A 실행 클릭메신저 RP가 action event를 Relay에 전달합니다.
  2. Relay
    commandId=301을 SQLite에 먼저 저장이 시점부터 네트워크 응답이 끊겨도 명령은 남습니다.
  3. Farad
    Long Poll 연결이 끊어짐아직 result가 없으므로 command는 pending입니다.
  4. Farad
    재연결 후 같은 command 수신같은 commandId의 처리 결과를 다시 제출할 수 있습니다.
  5. Relay
    result 커밋 이후에만 전달 완료 처리메신저 webhook 재전송도 inbound msgId로 중복 제거합니다.
명령 보관 만료시간은 운영 정책으로 별도 확정해야 합니다. 핵심 계약은 “persist before deliver, result commit equals ACK”입니다.

두 종류의 token을 혼동하지 않는다

메신저 OpenAPI 인증 token과 Farad client token은 소유자와 목적이 완전히 다릅니다.

Messenger API tokenRelay VM 배포 비밀. OpenAPI의 Authorization: Bearer 헤더에 사용하며 Farad에 배포하지 않습니다.
Farad client token각 Farad 설치가 생성하는 비밀. Relay Long Poll 인증에 사용하며 Relay는 hash만 저장합니다.
actionToken한 카드 버튼을 한 동작에 연결하는 짧은 수명의 opaque 값. Schedule ID나 prompt를 포함하지 않습니다.
itemToken / runRefFarad가 실제 Schedule과 실행을 안전하게 식별하는 opaque 참조. 메신저에 내부 ID를 노출하지 않습니다.

저장 위치

Farad 사용자 호스트

  • 보호된 client token 원문
  • Schedule 정의와 실제 ID
  • 실행 상태와 single-flight
  • 세션 transcript와 상세 결과

Relay VM SQLite

  • client token hash와 Knox binding
  • messenger userId와 chatroomId
  • inbound dedupe와 action route
  • command, idempotent result, delivery outbox

Relay를 여기서 더 키우지 않는다

Relay는 durable message broker 경계까지만 갖고, Schedule 업무 규칙은 Farad에 남깁니다.

Relay에 필요한 것

  • POST /message 수신
  • Messenger v2 암복호화·송신
  • client 등록과 token hash 검증
  • Long Poll command queue와 result-as-ACK
  • actionToken, dedupe, delivery retry

Relay에 넣지 않을 것

  • Linux ID와 singleid 실행 결과
  • Schedule 정의·prompt·경로
  • LLM 판단과 transcript
  • 실행 가능 여부와 single-flight
  • 자유 텍스트 보관
최종 동시 실행 규칙서로 다른 Schedule은 동시에 실행할 수 있습니다. 동일 Schedule에는 활성 실행이 하나만 존재합니다. Relay는 클릭을 잃지 않고 전달하고, Farad가 이 규칙을 최종 판정합니다.
현재 확정된 설계 계약을 시나리오로 정리한 문서입니다. pairing·Long Poll·Schedule adapter는 다음 구현 단계이며, command 보관 TTL과 오프라인 사용자 표시 문구는 운영 정책 확정이 필요합니다.
