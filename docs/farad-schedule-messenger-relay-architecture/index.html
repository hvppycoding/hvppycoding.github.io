Farad Schedule 메신저 리모컨

사용자 호스트의 Farad와 중앙 VM Relay, 사내 메신저 API가 어떻게 나뉘어 동작하는지 설명하고, 구현을 시작할 수 있을 만큼 구체적인 통신·상태·보안 계약을 정리한 공동 설계 문서입니다.

독자: Farad 개발자 · 중앙 VM/메신저 API 담당자 설계 기준일: 2026-07-15 현재 단계: 구현 전 아키텍처 합의 문서 revision: v0.4
확정 · 현재 합의 제안 · 인터페이스 초안 미결정 · 구현 전 확인
한눈에 보기 전체 구조 핵심 시퀀스 키워드 카드 Farad ↔ Relay Relay ↔ 메신저 상태와 저장소 보안 경계 구현 범위
01

한 문장으로 이해하는 시스템

메신저는 화면과 버튼만 제공하고, 중앙 VM은 안전한 배달과 API 변환을 담당하며, 실제 Schedule 목록·실행·LLM 판단의 권위는 각 사용자 호스트의 Farad에 남습니다.
  • 첫 화면사용자가 1:1 대화방에 말을 걸면 Relay가 POST /message를 받아 📊 LLM 사용량 조회와 🗓️ Farad 예약 작업 조회를 보여 줍니다.
  • 사용자가 하는 일메신저에서 검수된 별칭으로 표시된 원격 허용 Schedule을 고른 뒤 확인하여 실행합니다.
  • Farad가 하는 일최신 Schedule 목록을 안전한 표식으로 투영하고, 선택을 재검증한 뒤 기존 Run now 경로로 실행합니다.
  • 중앙 VM이 하는 일메신저의 inbound POST /message를 수신하고, outbound API를 호출하는 유일한 Relay로서 command, ACK, 카드 ID와 일회용 토큰을 SQLite에 보관합니다.
  • LLM이 보내는 내용자유 텍스트가 아니라 상태·행동·전략 키워드만 보냅니다. 추천 전략은 v1에서 최대 1개이며 Relay가 검수된 문구와 고정 이모지로 렌더링합니다.
  • 동시 실행 규칙같은 Schedule은 한 번에 하나만 실행합니다. 서로 다른 Schedule은 동시에 실행할 수 있습니다.

02

전체 구조와 책임 경계

사용자마다 Farad가 자신의 호스트에서 실행됩니다. 사내 메신저 API에는 중앙 VM만 접근할 수 있으므로 모든 메신저 통신은 Relay를 통과합니다. Relay가 Farad의 업무 내용을 소유하지 않도록, 실제 task ID와 실행 정보는 Farad 내부에 유지합니다.

03

사용자 경험을 만드는 다섯 가지 시퀀스

1. 사용자가 말을 걸면 홈 메뉴로 응답

중앙 VM의 Relay가 http://{연계서버IP:port}/message에서 메신저 RP 서버의 POST를 기다립니다. 사용자가 1:1 대화방에 메시지를 보내면 Relay는 방·발신자·event 식별 정보를 확인하고 홈 카드 전송 의도를 SQLite에 기록한 뒤 HTTP 200을 반환합니다. 실제 카드는 HTTP 응답 body가 아니라 메신저 ChatRequest로 보냅니다.

사용자  → 메신저 RP   "안녕" 또는 임의 메시지
메신저 RP → Relay     POST http://{연계서버IP:port}/message
                         { roomInfo, senderInfo, eventId, messageType, ... }
Relay   → SQLite      inbound dedupe + HOME delivery intent 원자 기록
Relay   → 메신저 RP   HTTP 200 OK
Relay   → 메신저 API  ChatRequest(home Adaptive Card)
메신저  → 사용자      [📊 LLM 사용량 조회] [🗓️ Farad 예약 작업 조회]
자유 텍스트 처리 원칙 v1은 사용자가 쓴 문장을 명령이나 prompt로 해석하지 않습니다. 내용은 로그·SQLite·Farad·LLM으로 전달하지 않고 “홈을 열어 달라”는 신호로만 사용합니다. 카드 버튼 응답은 같은 endpoint에서 별도의 action event로 분기합니다.
Farad 원하는 기능을 선택해 주세요.
📊 LLM 사용량 조회 🗓️ Farad 예약 작업 조회
동작처리 주체Farad 연결
홈, 사용량 카드, 사용량 새로고침Relay불필요
Schedule 목록, 상세, 실행, 진행, 선택Farad + Relay필요
 
{
  "type": "Action.Submit",
  "title": "📊 LLM 사용량 조회",
  "data": {
    "requestUrl": "https://relay.example.invalid/v1/action",
    "actionToken": "opaque-single-use-token"
  }
}

버튼 payload에는 동작 이름이나 사용자·Schedule ID를 넣지 않습니다. Relay의 action_routes가 actionToken을 Relay-only 또는 Farad-required 동작으로 해석합니다. 사용량 조회에 Farad 인증이 필요 없다는 뜻은 익명 공개라는 뜻이 아니며, Relay는 메신저 sender와 chatroom을 계속 검증합니다.

class ActionScope(StrEnum):
    RELAY_ONLY = "relay_only"
    FARAD_REQUIRED = "farad_required"

route = action_routes.consume(action_token, sender, chatroom_id)
if route.scope is ActionScope.RELAY_ONLY:
    return relay_menu_service.handle(route)
return farad_command_service.enqueue(route)
현재 확정한 범위 수신 URL과 “방 정보 같은 routing 정보가 온다”는 사실만 확정합니다. 실제 필드명, 암호화·서명, event ID, 텍스트와 Adaptive Card 응답의 구분 값은 상세 수신 API 명세를 받은 뒤 adapter schema에 고정합니다.

2. 최초 1회 Farad 연결

이 연결은 Schedule 기능에만 필요합니다. 비밀 파일을 운영자가 배포하지 않고 Farad가 자기 호스트에서 긴 랜덤 credential을 만든 뒤, 사용자가 이미 로그인한 사내 메신저에서 본인 연결을 승인합니다.

Farad가 credential 생성화면이나 로그에 원문을 노출하지 않고 민감 파일에 저장
Relay에 pairing 등록짧은 만료시간과 single-use pairing ID 발급
메신저에서 본인 승인inbound sender userId와 pairing을 결합
Long Poll 시작Relay가 credential hash와 account binding을 확인
NFS의 역할 OS 계정 → 사내 메신저 ID 입력 힌트를 둘 수는 있지만 인증 수단이 아닙니다. 비밀 credential은 Farad가 직접 생성하며 NFS 공용 매핑에 넣지 않습니다.
v1 transport 가정 Farad는 설정된 고정 IP의 Relay를 신뢰합니다. 인증서·CA·공개키 pin은 넣지 않지만, 여러 사용자를 구분하고 오접속을 막기 위한 client credential과 최초 메신저 승인은 유지합니다.

3. Long Poll로 명령 받기

Farad  → Relay   GET /v1/commands?cursor=42&waitSeconds=25
Relay  → Farad   25초 안에 명령이 없으면 빈 응답
Farad  → Relay   즉시 다음 Long Poll 연결

사용자 → 메신저  Adaptive Card 버튼 클릭
메신저 → Relay   POST /message (action event + room/sender info)
Relay  → SQLite  action 소비와 commandId=43을 먼저 영속화
Relay  → Farad   { commandId: 43, kind: "LIST_SCHEDULES" }
Farad  → Relay   처리 결과 전송
Farad  → Relay   ACK commandId=43

25초는 의미 있는 업무 timeout이 아니라 proxy idle timeout보다 짧게 잡은 연결 유지 예시입니다. 실제 값은 VM 앞단의 proxy/load balancer 설정을 확인해 결정합니다.

신호를 놓치지 않는 이유 Long Poll 응답 자체가 명령의 정본이 아닙니다. Relay가 command를 SQLite에 먼저 저장하고 Farad의 ACK가 오기 전까지 다시 전달하므로, 응답 도중 연결이 끊겨도 명령은 남습니다.

4. 원격 허용 Schedule 보기 → 선택 → 실행

메신저 실행도 데스크톱 Run now와 같은 경로

scheduler.run_now(
    task_id,
    apply_check=False,
    consume_run_limit=False,
)
# 제안 controller가 task_started/task_skipped signal을 typed 결과로 변환하고
# audit origin만 "messenger"로 기록

메신저용 별도 실행 엔진이나 더 강한 임의 제한을 만들지 않습니다. 기존 run_now()가 확인하는 running/checking gate를 그대로 통과하므로 같은 Schedule은 거절되고, 다른 Schedule은 동시에 실행됩니다. 원격 선택을 기다리는 동안에도 그 Schedule은 RUNNING입니다.

5. 실행 중 진행 카드와 사용자 선택

04

버전이 있는 폐쇄형 키워드 계약

LLM은 문장이나 이모지를 만들지 않고 허용된 enum만 고릅니다. Relay가 키워드를 검수된 한국어와 고정 이모지로 렌더링하므로, 메신저로 구체적인 업무 텍스트가 흘러가는 통로를 구조적으로 닫습니다.

상태 keyword

  • succeeded → ✅ 성공했어요
  • failed → ❌ 실패했어요
  • running → ⏳ 진행하고 있어요
  • choice_required → ⚠️ 선택이 필요해요
  • desktop_required → 💻 데스크톱에서 확인해 주세요

행동·전략 keyword

  • retry → 🔄 다시 하기
  • try_different → 🛣️ 다르게 시도하기
  • diagnose → 🔍 원인을 확인하고 시도
  • stop → ⏹️ 그만하기
  • back / home → ↩️ 뒤로 / 🏠 처음으로
❌ 실패했어요 다음 동작을 선택해 주세요.
🔄 다시 하기 🛣️ 다르게 시도하기 🔍 원인을 확인하고 시도 ⏹️ 그만하기

v1 wire payload

{
  "status": "failed",
  "actions": ["retry", "try_different", "stop"],
  "strategyKeywords": ["diagnose"],
  "vocabularyVersion": 1
}

추천 전략은 배열로 보내되 v1 validator는 maxItems: 1로 제한합니다. 이후 자유 조립을 열더라도 등록된 키워드 조합만 허용하고, 임의 문자열·임의 이모지·임의 순서는 허용하지 않습니다. wire 모양은 그대로 유지됩니다.

Farad와 Relay가 같은 규칙으로 두 번 검증

class StrategyKeyword(StrEnum):
    DIAGNOSE = "diagnose"

@dataclass(frozen=True)
class RemoteChoiceRequest:
    status: StatusKeyword
    actions: tuple[ActionKeyword, ...]
    strategy_keywords: tuple[StrategyKeyword, ...]
    vocabulary_version: int

def validate(request: RemoteChoiceRequest) -> None:
    if len(request.strategy_keywords) > 1:
        raise InvalidRemotePayload("v1 allows one strategy keyword")
  • 도구 schema는 status, actions, strategyKeywords를 enum으로 선언합니다.
  • message, detail, reasonText, 파일명, 경로, 로그, 도구 이름·인자, 원문 결과 필드는 존재하지 않습니다.
  • LLM은 이모지를 고르지 않습니다. 각 keyword의 이모지와 문구는 Relay renderer에 고정됩니다.
  • 알 수 없는 값, vocabulary version 불일치, 허용되지 않은 조합은 거절합니다. 전략이 유효하지 않을 때는 일반 try_different만 표시합니다.
  • 버튼의 actionToken은 Relay가 발급하며 LLM에게 노출하지 않습니다.
왜 키워드인가? “실패했어요”, “다시 하기”처럼 누구나 같은 뜻으로 이해하는 표현은 고정 문구가 가장 안전합니다. 구체적인 제안이 필요할 때만 diagnose 같은 승인 keyword 하나를 더해 선택지를 늘립니다.
05

Farad ↔ Relay 제안 API

아래 endpoint 이름은 구현 초안입니다. 이름보다 중요한 것은 durable command, 명시적 ACK, vocabulary version, idempotency의 의미입니다. v1은 고정 Relay IP를 신뢰하는 사내망 가정을 사용하며 TLS/CA/pinning은 범위에서 제외합니다.

POST/v1/pairings제안

Farad가 생성한 client credential로 pairing을 시작합니다. Relay는 짧은 수명의 pairing ID를 만들고 메신저 승인과 결합합니다.

GET/v1/commands?cursor={n}&waitSeconds=25제안

Farad 프로세스당 하나의 Long Poll. 반환된 command는 ACK 전까지 Relay SQLite에 남습니다.

POST/v1/commands/{commandId}/result제안

LIST, SELECT, RUN command의 처리 결과를 전달합니다. 같은 idempotency key로 재요청해도 효과는 한 번이어야 합니다.

POST/v1/commands/{commandId}/ack제안

Farad가 결과를 안전하게 제출한 뒤 ACK합니다. Relay는 ACK된 command를 전달 대상에서 제외합니다.

GET/v1/keyword-vocabulary?knownVersion={v}제안

활성 keyword vocabulary snapshot을 동기화합니다. 동일 버전이면 본문 없이 유지할 수 있습니다.

POST/v1/interactions제안

진행 또는 선택 요청의 상태·행동·전략 keyword를 전송합니다. Relay는 검증 후 새 Adaptive Card를 보내거나 기존 msgKey를 갱신합니다.

LIST_SCHEDULES 응답 예시

Schedule은 로컬에서 remote_enabled=False가 기본입니다. 사용자가 원격 허용을 켜고 승인된 remote_alias_id 하나를 고른 항목만 목록에 포함합니다. 별칭은 한 사용자 안에서 구분 가능해야 하며 실제 이름에서 자동 생성하지 않습니다.

{
  "commandId": 43,
  "scheduleGeneration": 18,
  "items": [
    {
      "itemToken": "opaque-single-use-token",
      "aliasId": "QUIET_OTTER",
      "state": "ready"
    },
    {
      "itemToken": "opaque-single-use-token-2",
      "aliasId": "GREEN_FOX",
      "state": "running"
    }
  ],
  "nextCursor": "opaque-page-cursor"
}
  • aliasId는 원격 허용 시 선택한 검수된 별칭입니다. Relay는 QUIET_OTTER를 “조용한 수달”처럼 고정 문구로 표시합니다.
  • Relay에는 실제 task ID나 Schedule 이름을 보내지 않습니다.
  • itemToken은 Farad 설치, schedule generation, 만료시간에 묶인 single-use 값입니다.
  • 선택 후 실행 확인 시 Farad가 삭제·비활성·현재 실행 중 여부를 다시 검사합니다.

상태와 저장소: 중앙 DB는 VM 로컬 SQLite 하나

중앙 Relay가 한 VM에서 동작하는 v1에는 별도 DB 서버가 필요하지 않습니다. SQLite WAL을 VM 로컬 디스크에 두고, NFS에는 DB와 command queue를 두지 않습니다.

Relay의 최소 논리 테이블

accounts / credentials

messenger userId, Farad 설치 식별자, credential hash, 활성/폐기 상태를 연결합니다.

pairings / chatrooms

만료되는 pairing과 재사용할 1:1 chatroomId를 보관합니다.

commands

commandId, 대상 client, payload, cursor, ACK, 만료를 보관합니다. 미ACK command는 다시 배달합니다.

deliveries / cards

outbox delivery intent, requestId, msgId, msgKey, card generation, 시도 횟수와 마지막 전송 상태를 기록합니다.

action_routes

actionToken, scope, kind, 대상 client/runRef, card generation, 만료와 소비 여부를 관리합니다.

keyword_vocabulary

vocabularyVersion, keyword ID, 고정 문구·이모지, 허용 조합, deprecated 상태를 관리합니다.

inbound_dedup

event ID, room/sender 식별자, event kind, 처리 상태를 저장해 재적용을 막습니다. 자유 텍스트 본문은 넣지 않습니다.

navigation / safe views

현재 화면, 검수된 별칭, opaque itemToken, TTL만 짧게 보관합니다. task ID는 넣지 않습니다.

10,000개 누적을 가정한 반복 경로

  • Long Poll 조회는 대상 client와 미ACK cursor를 index로 찾고 전체 command를 스캔하지 않습니다.
  • inbound event dedupe와 action 소비는 unique index로 O(1)에 가깝게 처리합니다.
  • 카드 갱신은 chatroomId와 msgKey를 직접 조회합니다.
  • 만료 command, inbound dedupe, action route, view는 bounded batch로 정리합니다.
  • Farad Schedule 목록은 기존 index/read model을 사용하고 매 Long Poll마다 NFS 파일을 다시 읽지 않습니다.
08

보안 모델: 막는 것과 막지 않는 것을 분명히 한다

v1이 막는 것

  • LLM의 파일명·경로·로그·원문 결과 자유 전송
  • 사용자가 보낸 자유 텍스트의 저장·Farad/LLM 전달
  • 다른 사용자의 카드 action 재사용
  • 같은 action의 중복 적용
  • 만료되거나 이전 화면 generation의 선택 실행
  • 같은 Schedule 동시 실행
  • Relay DB에 전체 Schedule/prompt 저장

v1이 막지 않는 것

  • 승인 keyword 선택과 전송 시각을 이용한 의도적 은닉 통신
  • 고정 IP를 신뢰한 사내 구간의 도청·spoofing
  • 상세 수신 명세 확정 전의 application-level webhook 서명 검증
  • 사용자가 수정한 로컬 Farad binary 자체의 진위 증명
  • 승인된 단어 조합이 전달하는 업무 사실
  • 사용자 계정이나 VM 관리자 권한 탈취

보안 검증 순서

  1. POST /message의 body 크기·content type·요청 timeout을 제한하고, 운영 방화벽에서 메신저 RP 출발지만 허용합니다.
  2. 상세 명세가 제공하는 암호화·서명·sender/room 식별 규칙을 inbound adapter에서 검증합니다.
  3. event ID를 SQLite unique key로 먼저 확인하고 중복 요청은 재적용하지 않습니다.
  4. 일반 메시지는 본문을 폐기하고 room/sender를 홈 delivery route에만 사용합니다.
  5. 카드 action이면 sender가 연결된 messenger userId인지 확인하고 actionToken을 검사합니다.
  6. Relay가 Farad-required action에 대해 client credential과 account binding을 확인합니다.
  7. commandId와 actionToken의 중복 여부를 확인합니다.
  8. actionToken의 TTL, card generation, scope, 허용 action, 대상 client를 검사합니다.
  9. Farad가 itemToken을 실제 Schedule에 로컬로 해석하고 최신 상태를 재검증합니다.
  10. 진행/선택 메시지는 Farad와 Relay가 같은 keyword vocabulary로 두 번 검사합니다.
HTTP 200의 의미 “카드를 사용자에게 이미 보냈다”가 아니라 “inbound event와 필요한 delivery/command intent를 안전하게 기록했다”는 뜻입니다. 전송 실패는 outbox가 재시도하며, RP 서버의 webhook 재전송과 중복 카드를 분리합니다.
고정 IP 신뢰는 명시적인 위험 수용입니다. v1에서는 Relay IP를 설정하고 별도 인증서·CA·공개키 pin 없이 신뢰합니다. 이 선택은 운영을 단순하게 하지만 사내망 구간의 기밀성과 서버 진위를 보장하지 않습니다. 위협 모델이 바뀌면 wire schema가 아니라 transport 계층에 HTTPS 또는 pinning을 추가해야 합니다.
로컬 앱 진위의 한계 사용자가 자신의 호스트에서 Farad를 실행하고 수정할 수 있으므로 Relay가 “공식 binary 그대로”임을 증명할 수는 없습니다. Relay가 신뢰하는 대상은 메신저로 승인된 사용자와 발급된 client credential입니다.
09

구현 영향과 역할 분담

Farad scheduler를 다시 만들 필요는 없지만, 사용자 메시지 수신부터 홈 응답·Relay 연결·원격 선택까지 하나의 정식 vertical slice가 필요합니다. 핵심 위험은 inbound HTTP 요청과 outbound 카드 전송을 한 요청처럼 취급해 event를 잃거나 중복 처리하는 것, 그리고 headless scheduled agent가 안전한 원격 응답을 기다리고 재개하는 경계입니다.

Farad에서 재사용하는 것

현재 구성요소재사용필요한 보강

Farad 신규 구성요소

  • RelayTransportpairing, Long Poll, ACK, retry, shutdown, vocabulary fetch를 담당하는 async network adapter
  • RemoteScheduleControllersafe schedule projection, itemToken 검증, Run now 결과를 소유하는 application service
  • RemoteKeywordVocabularyversioned snapshot과 상태·행동·전략 keyword validation을 제공하는 bounded provider
  • ReportRemoteProgress상태 keyword를 비동기로 제출하고 전송 결과를 transcript tool result로 남기는 schedule-only tool
  • RequestRemoteChoice선택 카드를 보내고 action/timeout/abort 중 하나로 Future를 해소하는 schedule-only tool
  • Qt ↔ asyncio proxyLong Poll에서 받은 LIST/RUN command를 Qt 소유 SchedulerEngine으로 안전하게 전달
  • Credential storeFarad가 생성한 원본 credential만 좁은 권한으로 보호

중앙 VM 담당 구현 범위

  • SQLite WAL schema와 migration, unique index, TTL cleanup을 정의한다.
  • 지정된 내부 IP:port에서 POST /message를 받는 inbound HTTP listener를 운영한다.
  • 수신 API 상세 schema·암호화·서명은 MessengerInboundAdapter에 격리하고, application service에는 정규화된 room/sender/event kind만 넘긴다.
  • 일반 메시지의 본문을 adapter 경계에서 폐기하고, inbound dedupe와 HOME outbox intent를 한 SQLite transaction으로 commit한다.
  • pairing/account binding과 credential hash 검증을 구현한다.
  • Long Poll command queue를 persist-before-deliver, ACK-after-result로 구현한다.
  • CreateChatroom, ChatRequest, UpdateMessageRequest adapter를 구현한다.
  • Adaptive Card 1.3 payload와 Action.Submit action route를 구현한다.
  • keyword vocabulary 정본, 고정 renderer, 조합 validation, vocabulary version endpoint를 구현한다.
  • event ID/actionToken 중복, webhook 재전송, outbound 실패, process crash를 포함한 idempotency 테스트를 만든다.
  • requestId/msgId int64 unique ID 생성 규칙을 정하고 ms 충돌을 막는다.
  • 운영 로그에서 credential, actionToken, 내부 payload 원문을 마스킹한다.

권장 구현 단계

1 · 수신과 홈POST /message, dedupe, outbox, 홈 카드
2 · 연결과 실행pairing, Long Poll, 목록, 선택, 같은 Run now
3 · keyword 진행고정 vocabulary와 progress card/update
4 · 원격 선택RequestRemoteChoice, action, timeout, abort
5 · 운영 강화재시작, dedupe, stale action, 부하·장애 테스트

구현 전에 함께 결정할 항목

  • Relay 앞단 proxy/load balancer의 idle timeout과 Long Poll wait/client timeout 값
  • POST /message의 실제 body schema, content type, event ID, 방/발신자 필드와 TEXT/ACTION 구분 값
  • 수신 body의 암호화·서명·key 전달/회전 방식과 메신저 RP source 인증 방법
  • RP 서버의 retry 조건·timeout, 최대 body 크기, 허용 chat type과 rate limit
  • 원격 선택의 기본 TTL, 미응답 시 실패/계속/데스크톱 확인 중 어떤 정책을 적용할지
  • Adaptive Card 최대 payload, action 수, version 1.3 실제 지원 범위
  • 카드 update/recall 실패 시 새 카드 전송 여부와 사용자에게 보일 중복 처리
  • keyword vocabulary 추가·deprecated·rollback의 배포 절차
  • Relay 장애나 재시작 중 inbound/action dedupe와 outbox를 얼마 동안 보관할지
  • 고정 IP 신뢰 가정을 언제 HTTPS/pinning으로 재검토할지
현재 합의의 최종 형태 사용자가 메신저에 말을 걸면 중앙 Relay의 POST /message가 이를 받아 홈 카드를 보냅니다. 자유 텍스트는 홈 열기 신호일 뿐 Farad나 LLM의 입력이 되지 않습니다. 이후 메신저는 홈·사용량·목록·실행·진행·제한된 선택을 제공하는 안전한 리모컨으로 동작하며, 실제 실행은 기존 Run now와 같고 같은 Schedule만 single-flight입니다.
