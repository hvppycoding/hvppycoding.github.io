메신저 버튼 하나가 Farad 실행으로 이어지는 과정

사용자는 메신저에서 스케줄을 보고 실행하지만, 실제 작업은 각 사용자 호스트의 Farad가 수행합니다. 중앙 Relay와 SQLite는 그 사이에서 신호를 잃지 않고 정확한 사용자·카드·스케줄에 연결합니다.

DB는 스케줄 내용을 저장하려고 두는 것이 아닙니다.

메신저와 Farad가 서로 다른 시간에 움직여도 요청이 사라지지 않도록, Relay가 받은 이벤트·보낼 카드·대기 중인 명령·버튼의 목적지를 기록하는 작은 영속 장부입니다.

먼저 네 개의 역할만 기억하면 됩니다

Relay는 스케줄을 실행하지 않고, SQLite도 Farad의 스케줄 원본이 아닙니다. 실행 권위는 항상 사용자 호스트의 Farad에 있습니다.

메신저는 사용자 화면실제 ScheduleStore나 실행 엔진을 모릅니다.
Relay는 교환대어느 사용자에게서 온 버튼인지와 어디로 보낼 명령인지 압니다.
SQLite는 Relay의 기억프로세스가 꺼져도 처리 중이던 신호를 이어갑니다.
Farad는 실행 주체최신 노출 설정과 같은 스케줄의 중복 실행 여부를 마지막에 다시 검사합니다.

왜 메모리나 HTTP 전달만으로 끝내지 않는가

메신저 클릭 시각과 Farad가 명령을 받을 시각은 같지 않습니다. Relay가 재시작될 수도 있고, 응답만 네트워크에서 사라질 수도 있습니다. DB는 이 시간 차이와 실패 구간을 메웁니다.

DB 없이 메모리에만 두면

  • Relay 재시작 순간 대기 명령이 사라집니다.
  • Farad가 잠시 꺼져 있으면 버튼 신호를 보관할 곳이 없습니다.
  • 같은 webhook이 재전송됐는지 판단하기 어렵습니다.
  • 어떤 기존 카드를 업데이트할지 msgKey를 잃습니다.
  • 활성 Farad 인스턴스가 둘일 때 누가 명령을 가져갈지 통제하기 어렵습니다.

SQLite에 먼저 기록하면

  • Relay가 꺼졌다 켜져도 pending command를 다시 전달할 수 있습니다.
  • Farad는 Long Poll로 자기 명령을 나중에 가져갈 수 있습니다.
  • event_id로 중복 webhook을 무해하게 처리합니다.
  • 카드와 버튼 route, revision, msgKey를 정확히 연결합니다.
  • runtime lease와 generation으로 한 Farad 인스턴스만 권위를 갖습니다.
핵심: SQLite는 “스케줄 데이터베이스”가 아니라 “Relay가 이미 무엇을 받았고, 무엇을 누구에게 전달해야 하는지”를 기억하는 durable queue + outbox + routing ledger입니다.

저장하는 것과 저장하지 않는 것을 구분합니다

보안상 구체적인 작업 내용은 중앙으로 보내지 않습니다. Relay에는 메신저 동작을 완성하는 데 필요한 최소한의 식별자와 고정 keyword만 남습니다.

이번 반복 조회 버그는 왜 발생했는가

같은 스케줄은 조회할 때마다 같은 Farad token을 사용합니다. 반면 Relay는 목록을 조회할 때마다 새 카드 snapshot인 view를 만듭니다. 기존 DB가 이 두 개념을 하나의 PK로 섞었습니다.

이전 구조: 전역 PK 충돌

Relay가 Farad token 자체를 remote_items.item_token PRIMARY KEY로 사용했습니다.

첫 조회view-A + token-123 → 성공
재조회view-B + token-123 → PK 충돌

목록 commit이 실패해 LIST_SCHEDULES가 완료되지 않았고, lease 만료 후 같은 명령이 재시도되며 이후 동작도 막힌 것처럼 보였습니다.

현재 구조: 두 식별자를 분리

Farad token은 실행 target으로 보존하고, Relay row ID는 view마다 따로 만듭니다.

첫 조회hash(view-A, token-123)
재조회hash(view-B, token-123)

두 내부 ID는 다르지만 둘 다 source_item_token=token-123을 가리킵니다. 실행 버튼을 누르면 Relay는 source token만 Farad에 돌려줍니다.

왜 예전 카드의 row도 바로 지우지 않는가

메신저 대화 내역에는 예전 카드가 남아 있습니다. 사용자가 그 버튼을 늦게 누를 수 있으므로 Relay는 해당 카드가 어느 view에 속했는지 알아야 안전하게 “오래된 카드”로 거절할 수 있습니다. 30일 retention 뒤에는 관련 view·route·card를 bounded cleanup으로 제거합니다.

SQLite 테이블은 역할별로 나뉩니다

테이블이 많아 보이지만 각각 한 종류의 실패만 책임집니다. 사용자별 DB 파일을 만들지 않고 중앙 VM-local SQLite 하나에서 client ID와 index로 범위를 좁힙니다.

중간에 꺼져도 어디서 다시 시작할지 압니다

DB의 가치는 정상 흐름보다 실패했을 때 드러납니다. 각 외부 호출 전에 상태를 commit하고, lease와 idempotency key로 재시도를 통제합니다.

  1. 메신저 클릭을 저장한 직후 Relay가 종료inbound event와 command가 SQLite에 있으므로 재시작 뒤 Farad가 그대로 가져갑니다.
  2. Farad가 command를 받았지만 HTTP 응답이 유실command lease가 끝나면 같은 command ID가 다시 전달됩니다. Farad journal도 이미 처리한 결과를 재사용합니다.
  3. Messenger 카드 발송 직전에 Relay가 종료pending delivery가 outbox에 남아 delivery worker가 재시작 뒤 전송합니다.
  4. 같은 버튼 webhook이 두 번 도착event ID와 action route 상태로 duplicate를 식별해 두 번째 실행을 만들지 않습니다.
  5. Farad 인스턴스 두 개가 동시에 연결runtime lease와 generation이 한 인스턴스만 현재 권위로 인정하고 이전 generation 결과를 거절합니다.
  6. 오래된 목록 카드에서 실행 클릭view TTL과 active 상태를 확인해 새 RUN command를 만들지 않고 최신 목록으로 안내합니다.
테스트 단계의 DB 초기화: 현재는 기존 연결 이력을 보존할 필요가 없으므로 Relay를 중지하고 relay.sqlite3, -wal, -shm을 함께 삭제한 뒤 재시작해 schema v8을 새로 만들 수 있습니다. 이 경우 메신저 연결은 다시 해야 합니다.
