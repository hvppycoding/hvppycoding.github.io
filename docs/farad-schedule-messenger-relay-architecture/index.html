Farad internal messenger relay
Scenario contract · 2026-07-16
Farad × 사내 메신저

Relay는 실행기가 아니라, 명령을 잃지 않는 우체통이다

사용자가 메신저에서 Schedule을 연달아 눌러도 Relay는 각 클릭을 독립된 명령으로 저장합니다. 실제 동시 실행 여부는 Farad가 “같은 Schedule인가?”만 보고 결정합니다.

A 다음 B서로 다른 Schedule이므로 둘 다 실행
A 다음 A첫 A만 실행, 두 번째 A는 already_running

세 구성요소의 책임을 섞지 않는다

Relay는 메신저와 통신 가능한 중앙 VM에 있고, 실제 Schedule 정의와 실행 상태는 각 사용자 호스트의 Farad에만 있습니다.

SCENARIO 01

처음 한 번만 연결한다

공용 매핑 파일이나 Linux ID 전달은 필요 없습니다. Farad가 관리 명령을 한 번 실행해 현재 사용자의 Knox ID를 직접 얻습니다.

  1. Farad
    /appl/LINUX/Hyper/utils/singleid 실행인자와 shell 없이 실행하고 stdout 한 줄을 senderKnoxId로 검증합니다.
  2. Farad
    256비트 이상의 client token 생성원문은 로컬 보호 파일에 저장합니다.
  3. Relay
    {knoxId, token} 등록을 pending으로 저장token 원문 대신 hash를 저장합니다.
  4. 사용자
    메신저 봇을 열거나 말을 건다Relay가 수신 envelope의 공식 senderKnoxId를 확인합니다.
  5. Relay
    “이 Farad를 연결할까요?” 확인 카드 발송메신저 userId와 chatroomId를 후보 binding으로 저장하지만 아직 PENDING입니다.
  6. 사용자
    메신저에서 “연결하기” 선택이 클릭이 커밋된 뒤에만 client가 ACTIVE가 됩니다. “취소”를 누르면 등록을 폐기합니다.
singleid 결과는 Farad state나 transcript에 저장하지 않습니다. 현재 확보한 값이 Knox ID뿐이라면 사용자가 봇을 한 번 열어야 Relay가 숫자형 messenger userId와 chatroomId를 얻을 수 있습니다. 별도 Knox ID→messenger userId 조회 수단이 생기면 CreateChatroomRequest로 확인 카드를 먼저 보낼 수 있습니다.
SCENARIO 02

Farad를 껐다 켜도 다시 매핑하지 않는다

  1. Farad
    로컬 보호 파일에서 client token 읽기singleid 명령은 다시 실행하지 않습니다.
  2. Farad
    이번 프로세스의 임시 runtimeId 생성매 실행마다 새 UUID를 만들며 디스크에 저장하지 않습니다.
  3. Farad
    runtime lease 획득POST /v1/runtime/claim으로 현재 generation을 받습니다.
  4. Farad
    Bearer token과 generation으로 Long Poll 시작GET /v1/commands?waitSeconds=25
  5. Relay
    명령 1개 또는 빈 응답 반환Farad는 명령 result를 제출한 뒤 다음 Long Poll을 엽니다.
Farad가 영구히 기억하는 것은 client token과 relayOrigin별도 Linux ID, Knox ID, bindingId, runtimeId를 로컬 state에 중복 저장하지 않습니다. token이 없거나 Relay binding이 폐기된 경우에만 최초 연결을 다시 합니다.
RUNTIME OWNERSHIP

Farad가 두 개 떠도 하나만 명령을 받는다

NFS에서는 서로 다른 호스트의 Farad가 같은 client token 파일을 읽을 수 있습니다. 그래서 token은 사용자 연결만 증명하고, 실제 명령 수신 권위는 Relay가 발급한 runtime lease와 generation으로 한 프로세스에만 줍니다.

clientToken장기 비밀. 어떤 Messenger 사용자 연결인지 증명합니다. NFS를 통해 여러 Farad 프로세스가 같은 값을 볼 수 있습니다.
runtimeIdFarad를 켤 때마다 만드는 임시 UUID. 프로세스가 종료되면 버리며 비밀값은 아닙니다.
generationRelay가 현재 활성 runtime에 주는 fencing 번호. 모든 command·result·event는 이 번호와 묶입니다.
runtime leaseLong Poll이 정상적으로 이어지는 동안 갱신되는 짧은 수명의 소유권입니다.
AFarad A→Relay
제안 계약 runtime claim 성공

Authorization: Bearer <Farad client token>

{"runtimeId":"runtime-A"}

200 OK
{"generation":7,"leaseUntilMillis":1784100030000}
BFarad B→Relay
같은 client의 두 번째 claim 거절
POST /v1/runtime/claim
Authorization: Bearer <같은 Farad client token>

{"runtimeId":"runtime-B"}

409 Conflict
{"code":"ACTIVE_RUNTIME_EXISTS"}

Farad A가 이미 연결된 상태에서 Farad B가 켜진 경우

  1. Farad A
    runtime-A / generation=7로 lease 소유Long Poll과 event 전송이 lease를 계속 갱신합니다.
  2. Farad B
    같은 clientToken, 새 runtime-B로 claim 요청NFS의 같은 token을 읽었더라도 다른 runtime으로 구분됩니다.
  3. Relay
    409 ACTIVE_RUNTIME_EXISTS 반환B에는 command를 주지 않고 로컬 UI에 “다른 Farad가 연결 중”을 표시합니다.
  4. 사용자
    필요한 경우에만 “이 Farad로 전환 요청”Relay는 이미 연결된 Messenger 대화방에 전환 확인 카드를 보냅니다.
  5. Relay
    사용자 확인 후 generation 7 → 8A를 fence하고 B만 활성화합니다. A의 늦은 result·event는 STALE_RUNTIME으로 거절합니다.

원격 연결을 새 Farad로 전환할까요?

기존 Farad에서는 더 이상 메신저 명령을 받을 수 없습니다.

전환하기유지하기
뒤로홈으로
전환은 기존 Farad에서 이미 실행 중인 로컬 Schedule을 강제로 종료하지 않습니다. 대신 기존 Schedule 목록 actionToken과 아직 전달하지 않은 command를 폐기하고, 새 Farad에서 목록을 다시 조회합니다. 모든 Long Poll·result·event에는 X-Farad-Runtime-Id와 X-Farad-Generation을 보내며, 이전 generation은 409 STALE_RUNTIME으로 거절합니다.

명령은 한 번에 하나씩 전달한다

Messenger의 “최대 10개”와 Relay queue는 별개chatMessageParams 최대 10개는 한 번의 Messenger API 요청에 넣을 수 있는 메시지 수입니다. Relay Long Poll은 command를 1개만 돌려주며, SQLite에는 10개를 넘어도 retention 정책 범위에서 계속 쌓입니다.
command 1 전달→Farad 처리→result commit = ACK→다음 command 1 전달

처음 연결부터 답장 선택까지, 실제 왕복

아래는 한 사용자가 Farad를 연결하고, Schedule 목록을 열고, 하나를 실행한 뒤 “시뮬레이션 실패” 카드에서 “다시 하기”를 선택하는 전체 흐름입니다. 메신저가 제공한 API는 확정 계약으로, 아직 구현할 Farad–Relay API는 제안 계약으로 표시했습니다.

확정 계약 제공받은 Messenger v2·수신 API 명세 제안 계약 Farad와 Relay 사이에서 구현할 내부 API
① 사용자 ② Messenger RP / OpenAPI ③ 중앙 VM Relay ④ Relay SQLite ⑤ 사용자 호스트 Farad
두 Bearer token은 완전히 다릅니다. Messenger API token은 Relay가 OpenAPI를 호출할 때만 쓰고, Farad client token은 한 Farad 설치가 Relay의 Long Poll·result·event API를 호출할 때만 씁니다.

17Farad→Farad

SCENARIO 05

클릭 직후 Farad 연결이 끊긴다

Long Poll 응답 자체는 명령의 정본이 아닙니다. Relay가 먼저 SQLite에 저장하고 Farad의 처리 결과가 커밋될 때까지 보관합니다.

  1. 사용자
    Schedule A 실행 클릭메신저 RP가 action event를 Relay에 전달합니다.
  2. Relay
    commandId=301을 SQLite에 먼저 저장이 시점부터 네트워크 응답이 끊겨도 명령은 남습니다.
  3. Farad
    Long Poll 연결이 끊어짐아직 result가 없으므로 command는 pending입니다.
  4. Farad
    재연결 후 같은 command 수신같은 commandId의 처리 결과를 다시 제출할 수 있습니다.
  5. Relay
    result 커밋 이후에만 전달 완료 처리메신저 webhook 재전송도 inbound msgId로 중복 제거합니다.
명령 보관 만료시간은 운영 정책으로 별도 확정해야 합니다. 핵심 계약은 “persist before deliver, result commit equals ACK”입니다.

두 종류의 token을 혼동하지 않는다

메신저 OpenAPI 인증 token과 Farad client token은 소유자와 목적이 완전히 다릅니다.

Messenger API tokenRelay VM 배포 비밀. OpenAPI의 Authorization: Bearer 헤더에 사용하며 Farad에 배포하지 않습니다.
Farad client token각 Farad 설치가 생성하는 비밀. Relay Long Poll 인증에 사용하며 Relay는 hash만 저장합니다.
actionToken한 카드 버튼을 한 동작에 연결하는 짧은 수명의 opaque 값. Schedule ID나 prompt를 포함하지 않습니다.
itemToken / runRefFarad가 실제 Schedule과 실행을 안전하게 식별하는 opaque 참조. 메신저에 내부 ID를 노출하지 않습니다.
remoteDisplayName사용자가 원격 등록 때 별도로 승인한 공개용 별칭. 화면 폭 12칸(한글·한자 2칸, 영문·숫자·공백 1칸)만 허용하고 원격 등록 항목 안에서 중복을 금지하며, 실제 Schedule 이름에서 자동 생성하지 않습니다. 미지정 시 예약 작업 01을 사용합니다.

저장 위치

Farad 사용자 호스트

  • 보호된 client token 원문
  • Schedule 정의·실제 ID·실제 이름
  • 실제 Schedule과 remoteDisplayName 매핑
  • 실행 상태와 single-flight
  • 세션 transcript와 상세 결과

Relay VM SQLite

  • client token hash와 Knox binding
  • messenger userId와 chatroomId
  • itemToken과 승인된 remoteDisplayName
  • inbound dedupe와 action route
  • command, idempotent result, delivery outbox

Relay를 여기서 더 키우지 않는다

Relay는 durable message broker 경계까지만 갖고, Schedule 업무 규칙은 Farad에 남깁니다.

Relay에 필요한 것

  • POST /message 수신
  • Messenger v2 암복호화·송신
  • client 등록과 token hash 검증
  • Long Poll command queue와 result-as-ACK
