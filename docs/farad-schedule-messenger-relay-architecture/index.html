01

먼저 한 문장으로

사내 메신저의 고정 리모컨 카드에서 Schedule 모두 보기를 누르면, 실행 중인 Farad가 최신 Schedule 목록을 이모지 시그니처와 상태만 담아 페이지 단위로 보냅니다. 사용자는 하나를 고르고 확인한 뒤 실행하며, 실제 Schedule 이름·prompt·경로·결과 본문은 메신저로 나가지 않습니다.

Farad · 카탈로그 권위

전체 Schedule, 이모지 시그니처, 현재 상태와 실행 정책을 알고 있습니다. 목록 페이지와 일회용 선택 토큰을 요청 시점에 만듭니다.

중앙 VM · 우체국

버튼 요청과 응답을 내구성 있게 전달하고 카드를 갱신합니다. 전체 Schedule DB나 실행 권한의 주인이 되지는 않습니다.

메신저 · 리모컨 화면

홈, 목록, 확인, 실행 상태를 Adaptive Card 한 장으로 보여줍니다. 자유 텍스트 명령은 받지 않습니다.

02

최초 연결: 비밀값을 누가 전달하는가?

아무도 전달하지 않습니다. Farad가 256비트 랜덤 토큰을 자기 호스트에서 직접 만들고 보호 파일에 저장합니다. 사용자는 Farad에서 메신저 연결을 누르고, 본인 사내 메신저에서 이 Farad 연결을 한 번 누르면 됩니다.
Farad가 열쇠를 만듦긴 비밀 토큰은 화면에 보여주거나 복사하지 않습니다.
→
메신저로 본인 확인같은 짧은 코드와 호스트 이름을 보고 연결을 승인합니다.
→
이후 자동 인증Farad가 저장된 토큰으로 Long Poll 요청을 인증합니다.

사용자에게 보이는 절차

1

Farad에서 메신저 연결을 누릅니다. 메신저 계정 매핑이 없으면 Knox ID 같은 공개 식별자만 한 번 입력합니다.

2

Farad 화면에 BLUE-47 같은 짧은 확인 코드가 나타납니다.

3

사내 메신저로 온 카드에서 계정·호스트·요청 시각과 같은 코드를 확인하고 이 Farad 연결을 누릅니다.

4

Farad가 자동으로 연결 완료를 감지하고 Relay가 개인 대화방에 상시 리모컨 홈 카드를 만듭니다. 토큰 복사, 인증서 발급, 파일 배포는 없습니다.

최초 1회 연결 시퀀스짧은 코드는 비교용이며 실제 비밀 토큰이 아닙니다.

어디에 무엇을 저장하는가?

Farad

원본 토큰을 민감 파일에 0600으로 저장합니다. 토큰을 로그·화면·NFS 운영 매핑에 쓰지 않습니다.

중앙 VM

토큰의 단방향 hash, 연결된 messenger userId, 장치 식별자, 폐기 상태만 SQLite에 저장합니다.

사내 메신저

최초 연결 승인과 실제 sender 확인에만 사용합니다. 짧은 확인 코드는 비밀번호가 아닙니다.

서버가 진짜 중앙 VM인지는 어떻게 아는가?

토큰은 반드시 HTTPS 위에서만 사용합니다. 사용자별 인증서는 필요 없지만, Farad는 중앙 VM의 서버 인증서를 검증해야 합니다. 사내 CA를 모든 호스트가 신뢰하기 어렵다면 Farad 배포물에 Relay 서버의 공개키 지문을 넣어 고정할 수 있습니다. 공개키 지문은 공개 정보라 사용자마다 비밀 파일로 배포할 필요가 없습니다.

확정 정책 최초 연결은 Farad 1회 클릭 + 본인 메신저 1회 승인입니다. 토큰을 잃거나 호스트를 재설치하면 기존 연결을 폐기하고 같은 절차로 다시 연결합니다. 아무 신뢰 채널도 없이 최초 인증을 자동화할 수는 없으므로, 현재 환경에서는 이미 로그인된 사내 메신저를 본인 확인 수단으로 사용합니다.

04

Long Poll은 어떻게 기다리는가?

Farad가 매초 “명령 왔나요?”라고 물으면 요청이 너무 많습니다. Long Poll에서는 Farad가 한 번 질문하고 중앙 VM이 일정 시간 답을 보류합니다. 명령이 3초 만에 생기면 3초 만에 즉시 답하고, 제한 시간까지 아무 일도 없을 때만 빈 답을 돌려줍니다.

왜 예시에 50초를 쓰는가? 고정 규격이 아니라 재접속 횟수를 줄이기 위한 예시입니다. 실제 값은 사내 proxy/load balancer의 idle timeout보다 5~10초 짧게 둡니다. idle timeout이 60초면 wait=50, 30초면 wait=20~25가 적당합니다. 인프라 값을 모르는 v1은 25초처럼 보수적으로 시작합니다.
Farad → Relay: GET /v1/commands?cursor=42&wait=25 Relay: 새 명령이 없으므로 HTTP 연결을 열어 둠 ... 7초 후 사용자가 [Schedule 모두 보기] 클릭 ... Relay → Farad: { "commandId": 43, "kind": "CATALOG_PAGE", "pageCursor": null } Farad → Relay: ACK commandId=43 Farad → Relay: emoji/status 6개 + opaque action token + next cursor Farad → Relay: 다음 Long Poll 시작

Farad 프로세스당 하나

Schedule마다 연결을 만들지 않습니다. singleton lease를 가진 Farad가 async task 하나만 유지합니다.

UI를 멈추지 않음

네트워크 대기는 asyncio loop에서 일어나며 Qt 화면은 계속 반응합니다.

신호가 아니라 배달 수단

명령의 정본은 Relay DB입니다. 연결이 끊겨도 ACK 전 명령은 지워지지 않습니다.

Farad는 언제 연결하는가?

1

앱이 시작되고 해당 계정이 singleton lease를 획득합니다.

2

최초 연결이 완료되어 로컬 token과 Relay의 account binding이 유효하면 Long Poll task 하나를 시작합니다.

3

정상 응답 후 즉시 다음 poll을 시작하고, 오류면 2초 → 4초 → 8초처럼 bounded backoff로 재연결합니다.

4

앱 종료, lease 상실, 계정 비활성화 시 poll과 pending network task를 정리합니다.

06

NFS와 중앙 DB는 각각 어디에 쓰는가?

NFS가 있다고 해서 모든 상태를 NFS 파일로 만들 필요는 없습니다. NFS는 여러 호스트가 같은 파일을 볼 수 있다는 장점이 있지만, 작은 파일을 자주 열고 닫는 작업과 database lock에는 불리합니다.

저장 위치저장할 것읽는 시점저장하지 않을 것
NFS 운영 설정 (선택)OS 계정 → Knox ID 입력 힌트, Relay endpoint와 공개키 pin앱 시작 또는 명시적 refresh비밀 token, 인증의 최종 근거, 자주 변하는 command queue
사용자 Farad dataSchedule 정의와 emoji signature, 실행 history, 원본 연결 tokenSchedule store를 시작 시 적재하고 in-memory catalog index를 write 직후 갱신. token만 별도 0600 보호메신저 벤더 API credential
VM 로컬 SQLite WALtoken hash, account binding, pairing, chatroomId, msgKey, command, ACK, 짧은 catalog view/action route, dedupepairing·callback·Long Poll·카드 갱신 때 indexed 조회전체 Schedule catalog, 실제 task_id, 원본 token, prompt, transcript, 경로, tool 결과

왜 SQLite를 NFS 위에 두지 않는가?

SQLite WAL은 로컬 파일 잠금과 빠른 fsync를 전제로 합니다. NFS에서는 잠금·캐시·장애 복구 의미가 서버와 mount 설정에 따라 달라질 수 있습니다. 중앙 Relay가 한 VM에서 돌기 때문에 VM 로컬 디스크의 SQLite가 단순하고 안전합니다. 나중에 Relay를 여러 VM으로 늘릴 때 PostgreSQL로 교체합니다.

Schedule 10,000개를 매번 다시 읽지 않는 방법

[Schedule 모두 보기]를 누를 때마다 NFS의 schedule.json 10,000개를 열지 않습니다. Farad가 시작할 때 Scheduler store의 canonical task snapshot으로 정렬된 in-memory RemoteCatalogIndex를 만들고, 앱 안에서 Schedule이 생성·수정·삭제되면 그 항목만 즉시 갱신합니다. 버튼 클릭은 opaque cursor로 다음 몇 개만 읽으므로 O(page size)입니다. 외부에서 파일을 바꾼 경우에만 기존 explicit reconcile 경로에서 다시 맞춥니다.

가상의 NFS 입력 힌트 예시

# 선택 기능. 사용자의 입력을 줄일 뿐 인증 정보가 아닙니다. accountHints: kim: knoxId: kim.example lee: knoxId: lee.example

힌트가 없으면 사용자가 Knox ID를 최초 연결 때 한 번 입력하면 됩니다. 힌트나 요청 본문의 계정 문자열을 믿고 인증을 끝내면 안 됩니다. 그 계정으로 실제 전송된 카드에서, 같은 계정의 사용자가 승인한 callback이 도착해야 최종 account binding을 만듭니다.

중앙 SQLite의 최소 테이블

accounts / client_credentials

승인된 messenger userId와 Farad 설치 식별자, token hash, 폐기 상태를 연결합니다.

pairings / chatrooms

5분짜리 single-use 연결 요청과 재사용할 1:1 chatroomId를 저장합니다.

deliveries / catalog_views

msgKey, 현재 card generation과 화면에 보이는 한 페이지의 안전한 projection만 TTL 동안 저장합니다.

commands / action_routes

CATALOG_PAGE·RUN 명령의 ACK와 만료, opaque item token의 대상 Farad만 저장합니다. task_id는 저장하지 않습니다.

inbound_dedup

메신저 서버가 같은 callback을 재전송해도 효과가 한 번만 나도록 막습니다.

누가 눌렀는가

  • callback sender가 연결된 userId인가
  • 현재 control card generation과 같은가
  • 다른 Farad 설치의 item token이 아닌가

토큰이 유효한가

  • single-use이고 아직 소비되지 않았는가
  • TTL·catalog generation이 유효한가
  • 현재 app lease_epoch와 같은가

작업이 그대로인가

  • task digest가 목록 생성 때와 같은가
  • 삭제·비활성·실행 중 상태가 바뀌지 않았는가
  • run limit과 overlap policy가 허용하는가

원격 정책이 안전한가

  • full access Schedule은 데스크톱 전용
  • 저장된 allow pattern만 사용
  • 새 approval과 질문은 기다리지 않음

모든 Schedule을 보되 모두 실행하지는 않습니다

원격 실행은 일반 Run now와 다릅니다

기존 UI의 수동 run_now는 테스트와 사전 승인 용도로 check와 run limit을 우회할 수 있습니다. 메신저 원격 실행은 이 기본값을 그대로 사용하면 안 됩니다. 원격 전용 진입점에서 정책을 고정해야 합니다.

scheduler.run_remote(task_id) 항상 적용: apply_check = true consume_run_limit = true trigger = "remote" full_access = reject permission_posture = DONT_ASK

현재 API 설명으로 상위 구조는 정할 수 있지만 adapter 구현을 확정하려면 아래 답이 필요합니다.

AES256의 mode, IV 위치, padding, charset, key 배포·회전, 무결성 검증(MAC/AEAD) 방식은 무엇인가?
Adaptive Card의 Action.Submit 클릭 후 실제로 들어오는 chatMsg 전체 JSON 예시는 무엇인가?
requestUrl을 메신저 서버가 직접 호출하는가, 아니면 Message Receiving API payload에 data를 실어 보내는가?
Message Receiving API가 HTTP 200을 받지 못하면 재전송하는가? 횟수와 간격, 중복 event ID는 무엇인가?

interactive callback을 받기 위해 chatType 0을 쓰는 것이 맞는가? chatType 5 Noti에서는 callback이 지원되지 않는가?
UpdateMessageRequest의 실제 wire field가 chatroomId인지, 문서의 chatrommId인지 확인이 필요한가?

Relay와 메신저 API 사이의 인증, TLS/mTLS, source IP allowlist, rate limit, timeout, 점검 시간 운영 계약은 무엇인가?
Farad와 Relay 사이의 proxy/load balancer idle timeout은 몇 초인가? Long Poll wait와 client timeout을 각각 얼마로 둘 것인가?

권장 구현 순서

1

메신저 담당자와 위 wire/security 계약을 확정하고 fake server로 암복호화·card callback 샘플을 고정합니다.

2

중앙 Relay의 pairing/account binding, durable command, short-lived catalog view/action route, idempotent inbox/outbox와 Long Poll API를 구현합니다.

3

Farad에 token 보호 저장과 Pairing UI, CorporateRelayTransport, in-memory RemoteCatalogIndex, cursor page query를 추가합니다.

4

Schedule 모델·편집 UI에 고유 이모지 시그니처 1~3개와 기존 작업 자동 제안 흐름을 추가하고, run_remote 안전 진입점을 연결합니다.

5

10,000개 pagination, stale page, 중복 callback, Farad offline, VM 재시작, token 만료, Schedule 변경, full-access 거부를 end-to-end로 검증합니다.

최종 설계 요약 제품은 사내 메신저의 상시 Farad Schedule 리모컨입니다. 사용자는 [Schedule 모두 보기]로 최신 페이지를 요청하고, 고유 이모지 시그니처를 선택한 뒤 확인해서 실행합니다. 전체 catalog·task_id·prompt·경로·결과의 권위는 Farad에만 있고, 중앙 VM은 durable command와 현재 한 페이지의 짧은 projection만 보관합니다. 목록과 실행은 같은 Long Poll 통로를 쓰며, 실제 실행은 single-use item token을 원자 소비하고 최신 정책을 다시 검사한 뒤에만 시작합니다.
