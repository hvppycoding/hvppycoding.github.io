    HTML 디자인 에이전트 운영 프롬프트 벤치마크

    조사일: 2026-07-15
    검토 대상: 사용자 제공 HTML 기반 디자인 에이전트 지침 (원문은 재배포하지 않음)

    한 줄 결론

    이 지침은 HTML을 단순 웹페이지가 아니라 디자인 산출물의 공통 매체로 보고, 생성·미리보기·검수를 하나의 작업 계약으로 묶는 방식이 강점이다. 다만 특정 디자인 작업공간의 도구·React CDN·상호작용 프로토타입을 전제하므로, Farad에는 그 운영 세부를 옮기지 말고 매체 선택, 디자인 근거, 렌더 검수, 산출물 provenance만 채택해야 한다.

    지침의 설계 방식

    1. HTML은 구현 언어이면서 산출물 캔버스다

    하나의 HTML 문서를 랜딩 페이지에 한정하지 않고, 슬라이드, 인터랙티브 프로토타입, 모션, 디자인 비교 캔버스로 사용한다. 요청마다 역할을 UX 디자이너·발표자료 디자이너·애니메이터처럼 바꾸며, 같은 HTML도 결과물의 읽는 방식에 따라 다른 구조를 선택하게 한다.

    이는 “항상 카드형 웹페이지”가 되는 LLM 산출물을 막는 좋은 출발점이다. 특히 다이어그램·보고서·발표용 HTML이 서로 다른 독서 흐름을 가져야 한다는 점을 분명히 한다.

    2. 설계 근거를 먼저 확보한다

    새 UI를 그리기 전에 기존 코드, 디자인 시스템, 컴포넌트, 화면 자료를 찾아 시각 어휘를 읽도록 요구한다. 파일명만 보고 흉내 내는 대신 토큰·전역 스타일·실제 레이아웃을 확인하도록 한 점이 핵심이다. 자료가 없을 때도 무작정 그럴듯한 화면을 만들기보다, 필요한 맥락을 요청하게 한다.

    3. 생성 완료를 저장 성공으로 보지 않는다

    미리보기에서 열어 보고 오류를 확인한 뒤 별도 검수자가 화면·동작·레이아웃을 점검하는 루프를 둔다. 고정 크기 슬라이드는 작은 화면에서도 비율을 유지하고, 발표 위치·상호작용 상태도 다시 열었을 때 이어지게 하는 등 결과물의 실제 사용을 계약으로 다룬다.

    4. 인터랙션과 편집 피드백을 산출물에 연결한다

    화면/슬라이드에 사람이 읽는 라벨을 심고, 사용자가 특정 요소를 가리키면 소스의 대응 위치를 좁힐 수 있게 한다. 여러 디자인안은 산발적인 파일 복사보다 하나의 프로토타입에서 조정 가능한 옵션으로 관리하는 방식도 제안한다.

    5. 생성물 품질의 금지 목록을 적극 사용한다

    가짜 수치·불필요한 아이콘·빈 콘텐츠·기본 템플릿식 장식을 피하고, 콘텐츠를 채우기 위해 문단이나 섹션을 발명하지 않도록 한다. 디자인 시스템이 없을 때도 미적 방향을 의식적으로 정하라는 요구는, 모델이 관성적인 네온 그라데이션·카드 격자에 빠지는 것을 막는 장치다.

    Farad에 가져올 점

    채택할 원칙 Farad 적용
    매체보다 독서 목적을 먼저 고른다 같은 HTML이라도 standalone 보고서, Confluence HTML Embed, 슬라이드형 HTML을 별도 출력 계약으로 둔다.
    기존 시각 근거가 최우선이다 사용자가 준 사내 템플릿·브랜드·기존 페이지가 Farad 기본 언어보다 우선한다. 없을 때만 Farad의 중립적 언어를 사용한다.
    렌더 검수는 필수다 HTML은 넓은 화면과 좁은 화면, Confluence Embed는 실제 매크로, PPTX는 슬라이드 이미지로 확인한다.
    콘텐츠를 발명하지 않는다 지표·인용·고객 사례·출처를 장식용으로 만들지 않는다. 비어 있는 여백은 실패가 아닐 수 있다.
    산출물 상태를 명시한다 원본 경로, 열람 방법, 편집 가능 범위, 외부 리소스 유무, 남은 가정을 함께 남긴다.
    디자인 수정의 대상을 식별한다 슬라이드/섹션/다이어그램에 사람이 읽는 이름을 부여해 피드백을 정확히 받는다.

    Farad에는 맞지 않는 점

    원 지침의 경향 충돌 이유 Farad 대안
    새 디자인마다 다수의 질문과 여러 변형을 기본 요구 보고서·상태 공유처럼 목표가 분명한 요청까지 느려지고, 사용자의 결정 피로를 높인다. 결과가 크게 달라지는 독자·배포처·템플릿 여부만 확인하고, 나머지는 합리적으로 추론한다.
    React/Babel/CDN 기반 HTML을 일반 해법처럼 둠 사내망 생성 후 Confluence에 옮기는 환경에서 외부 네트워크·CSP·매크로 정책에 취약하다. 기본은 의존성 없는 HTML/CSS/inline SVG. JS와 외부 리소스는 명시적으로 허용된 경우에만 쓴다.
    동적 프로토타입 기능을 폭넓게 기본 제공 문서·설명 자료에는 유지보수 비용과 보안 표면만 늘어난다. 정적 문서 우선. 상호작용은 이해나 직접 조작을 실제로 개선할 때만 추가한다.
    SVG를 대체로 플레이스홀더 취급 관계를 설명하는 다이어그램에는 벡터 그림이 가장 투명하고 편집·검수가 쉽다. 관계도·흐름도에는 inline SVG를 우선하고, 장식용 이미지는 기본값으로 쓰지 않는다.
    시스템 폰트를 피하는 미적 규칙 Farad의 사내망→Confluence 배포에서는 외장 글꼴 실패가 더 큰 문제다. Pretendard가 있으면 사용하되, Noto Sans KR·Apple SD Gothic Neo·맑은 고딕 등 시스템 fallback을 기본으로 둔다.
    특정 작업공간 전용 완료·검수 절차 다른 에이전트와 도구에서 재현되지 않는다. “생성 → 렌더 → 읽기 크기 검수 → 수정”이라는 도구 중립 계약만 남긴다.

    farad-artifact에 반영할 구조

    farad-artifact/
├── SKILL.md                         # 공통 판단, provenance, 렌더 QA
└── references/
    ├── design-language.md            # 색·여백·타입·anti-pattern
    ├── standalone-html.md            # 독립 문서와 SVG
    ├── confluence-html-embed.md      # style + fragment + 선택적 JS의 격리 계약
    ├── pptx.md                       # 편집성, 서체, 렌더 QA
    └── review.md                     # 독자/핵심 주장/overflow/외부 리소스 점검

    특히 Confluence 출력은 독립 HTML 파일이 아니라 Confluence HTML Embed로 분리한다. doctype, html, head, body는 내보내지 않고, 루트 클래스 아래로 범위를 제한한 <style>과 HTML 조각, 필요할 때만 제한된 <script>을 쓴다. 외장 폰트·CDN·전역 CSS 선택자·외부 API 호출은 기본 금지다.

    권장 작업 계약

    1. 독자, 읽은 뒤의 행동, 배포처, 편집 필요성을 파악한다.
    2. 사내 템플릿·로고·문구·기존 UI가 있으면 그 권한과 사용 범위를 확인한다.
    3. 출력 타입을 standalone HTML / Confluence HTML Embed / PPTX 중 선택한다.
    4. 한 페이지·한 슬라이드·한 섹션이 전달할 주장부터 쓴 뒤 최소한의 시각 형식을 고른다.
    5. 정적 HTML/CSS와 실제 텍스트를 기본으로 만들고, 다이어그램만 inline SVG로 추가한다.
    6. 렌더된 결과에서 행간, 줄바꿈, overflow, 대비, 외부 자원 실패, AI식 장식을 확인한다.
    7. 결과 경로와 함께 사용한 템플릿·폰트·외부 자원의 provenance를 남긴다.

    최종 판단

    이 자료의 가장 큰 교훈은 “좋은 디자인 프롬프트”가 색상과 CSS 예시가 아니라 무엇을 만들지 고르고, 어떤 근거를 쓰며, 어떻게 실제 화면에서 실패를 찾을지를 정한다는 점이다. Farad는 여기에 조용한 편집적 시각 언어와 사내망 배포 제약을 더해야 한다.

    따라서 Farad v1은 거대한 디자인 작업공간을 모방하지 않는다. HTML/PPTX/Confluence라는 세 출력 계약, 시스템 글꼴 fallback, SVG 중심 다이어그램, 외부 리소스 최소화, 렌더 검수만 강하게 고정하는 것이 더 작고 신뢰할 수 있는 출발점이다.

    검토 범위

    • 사용자 제공 HTML 디자인 에이전트 지침 — 워크플로, 산출물 계약, 검수, 디자인 품질 규칙을 분석함.
    • 원문 프롬프트·도구 스키마·코드·고유 문구는 이 문서에 수록하거나 재배포하지 않음.
