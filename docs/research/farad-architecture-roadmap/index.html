    Farad 아키텍처 최종 판정과 P0/P1/P2 로드맵

    Farad 아키텍처 최종 판정과 P0/P1/P2 로드맵

    전체 보고서 인덱스

    기준일: 2026-07-13
    근거: 교차 비교, Farad 개별 감사, 현재 source/docs/tests
    설계 순서: authority → thread/process → flow → hot path → persistence → failure boundary

    1. 판정

    Farad는 재작성 대상이 아니다. 현재 중심 구조는 유지할 가치가 있다.

    • hvppyai는 HTTP/types/streaming만 소유하고 agent loop는 Farad app에 있다.
    • query_loop는 callback-inverted flat async generator다.
    • UiSession과 AsyncSession은 Qt projection과 async execution을 나눈다.
    • TurnContext와 run readiness snapshot이 한 turn의 일관성을 지키려 한다.
    • capability discovery/exposure/dispatch와 Registry/Factory/Loader가 구분돼 있다.
    • transcript, session index, scheduler, subagent가 임시 채팅이 아니라 product domain이다.
    • NFS, 10,000 entity, explicit refresh를 문서 수준의 hard contract로 이미 선언했다.

    문제는 이 방향이 틀렸다는 것이 아니라, 몇몇 current path가 그 계약을 깨거나 enforcement가 비어 있다는 것이다. 가장 중요한 결론은 다음과 같다.

    Farad의 다음 architecture phase는 기능 추가보다 계약-구현 gap을 닫는 phase여야 한다. 특히 command sandbox, storage I/O ownership, scheduler due index, refresh truth, cross-thread snapshot, HTTP client lifecycle을 먼저 고치지 않고 app-server나 더 큰 agent team을 얹으면 결함의 영향 반경만 넓어진다.

    2. 보존·수정·보류 결정

    결정 대상 이유
    보존 hvppyai에 agent loop를 두지 않는 경계 provider-neutral SDK와 app policy 분리
    보존 UiSession ↔ proxy ↔ AsyncSession 구조 native Qt/async ownership에 맞음
    보존 flat query_loop + callback/event contract 테스트와 headless reuse 가능
    보존 explicit refresh + targeted invalidation NFS, 재현성, 저사양 환경에 적합
    보존 append-only transcript와 marker twin cache/replay/context 충실도
    수정 transcript sync write/index·rewind·repair shared async loop와 NFS hot path를 block하고 corruption을 숨길 수 있음
    수정 scheduler 60초 전량 sweep Qt thread에서 누적 N에 비례
    수정 settings/endpoint/MCP refresh 5분 poll, per-turn stat, Qt periodic reconcile, blocking MCP가 explicit-refresh 계약과 불일치
    수정 permission UI snapshot read Qt가 async object를 직접 역참조하고 cold disk read 가능
    수정 model client lifecycle 교체된 owned HTTP client close 누락, readiness 중복
    추가 command execution containment permission policy 밖의 OS enforcement 없음
    추출 AsyncSession/UiSession 일부 책임 서로 다른 failure/authority가 거대 class에 집중
    보류 full app-server/remote daemon 두 번째 실제 client 요구 전에는 YAGNI
    보류 범용 distributed agent cluster local desktop/HPC 문제를 먼저 해결
    보류 workflow VM/DSL artifact-aware orchestration으로 부족한 실사용 근거가 생길 때

    명시적 non-goal

    • Farad 전체 재작성이나 query_loop의 SDK 이동
    • NFS 위 SQLite를 conversation canonical store로 채택
    • freshness를 이유로 per-turn file watch/stat을 다시 도입
    • 실제 enforcement 없이 allow/deny parser를 “sandbox”로 명명
    • 두 번째 독립 surface 전에 daemon/app-server/JSON-RPC를 선제 구축
    • 구체 workflow 없이 distributed agent team이나 범용 workflow VM을 제품 목표로 설정

    4.1 경쟁 제품에서 취할 패턴과 취하지 않을 구조

    Farad gap 참고할 패턴 Farad식 적용 그대로 복제하지 않는 것
    command containment Codex의 permission과 OS sandbox 분리, 실행 시점 enforcement ExecutionBoundary를 tool policy 뒤의 별도 application boundary로 두고 platform capability를 정직하게 노출 Rust runtime 전체, 모든 subprocess를 같은 profile로 취급, 지원 불가 플랫폼의 silent fallback
    command/event ordering Codex의 ordered Submission/Event control plane 기존 proxy/AgentEvent에 command ID, sequence, snapshot generation을 추가하고 in-process conformance test 두 번째 surface가 없는데 app-server/JSON-RPC부터 도입
    future embedding OpenCode의 transport-independent server/API 실제 headless/remote/web client 요구가 생기면 이미 검증된 application protocol에 transport를 붙임 directory-global server instance, V1/V2 이중 runtime, permissive host execution default
    workflow UX Claude Code의 permission explanation, hooks, subagent lifecycle Farad의 Qt interaction과 scheduler에 명시적 상태·failure reason을 보강 Agent SDK의 live-session subprocess topology를 Farad 전체에 복제, vendor-specific context authority, opt-in sandbox를 기본 보안으로 표현
    replay + 목록 조회 Codex의 canonical log와 query projection 분리 JSONL은 canonical, NFS-friendly derived index는 version/lag/repair state를 가짐 NFS 위 SQLite를 canonical writer로 전환하거나 10k 성능이 자동 보장된다고 가정
    provider/API breadth OpenCode의 provider/server 경계 hvppyai의 provider-neutral SDK 경계를 보존하고 app policy를 올리지 않음 provider별 semantics를 core turn state에 누적

    이 표는 소스나 내부 이름을 포팅하자는 뜻이 아니다. 비교 제품에서 검증된 경계의 이유만 취하고, Farad의 Qt·NFS·single-runtime 전제에 맞는 더 작은 계약으로 다시 설계한다.

    F-01. Agent command는 permission을 거쳐도 OS 격리되지 않는다

    현재 permission engine은 tool/input을 allow/ask/deny하는 정책 계층이다. 그러나 Bash와 child process가 기술적으로 workspace/network boundary를 넘지 못하게 하는 Seatbelt/bubblewrap/Windows sandbox 계층은 확인되지 않는다. repository의 sandbox 검색 결과는 prompt template의 Jinja sandbox 정도이며 command containment가 아니다.

    process spawn surface도 Bash 하나가 아니다.

    • core/background_shell.py
    • app/local_shell_runner.py
    • hooks/runner.py
    • core/subprocess_utils.py
    • MCP stdio connection
    • capability worker, scheduler check, updater/diagnostics 등 app-owned process

    모두 같은 risk가 아니므로 무조건 한 wrapper로 묶으면 안 된다. model 또는 untrusted extension이 인자를 결정하는 process와 Farad가 고정 argv로 띄우는 trusted support process를 분류해야 한다.

    판정: 보안 P0.

    F-02. transcript disk-first path가 asyncio loop를 동기 block한다

    AsyncSession.append_transcript_entry()는 disk-first ordering을 지키지만 async method 안에서 TranscriptStore.append_entry()를 직접 호출한다. store는 매 envelope마다 JSONL line append와 index manifest temp-write + os.replace를 수행한다. NFS round trip이 긴 순간 하나의 session뿐 아니라 같은 asyncio loop의 다른 session/MCP/tool 작업도 멈출 수 있다.

    cold open도 load_all() 뒤 max_numeric_message_id()가 다시 load_raw_all()을 호출해 transcript를 두 번 읽는다. 이것은 1회성 path이지만 긴 session/NFS에서 interactive latency와 shared loop fairness를 해친다.

    disk-first 자체는 옳다. 고쳐야 하는 것은 ordering이 아니라 어느 executor에서 어떤 projection을 매번 durability 조건으로 삼는가다.

    판정: performance/correctness P0.

    F-03. Scheduler가 Qt thread에서 60초마다 전량 task를 훑는다

    SchedulerEngine._tick()은 main-thread QTimer에서 ScheduleStore.list_tasks()를 호출한다. list는 각 schedule metadata를 stat하고 history signature도 확인한 뒤 전부 next_run_at으로 sort한다. directory path list가 cache돼도 task/history stat은 N개에 비례한다. N=10,000에서 60초마다 UI가 같은 비용을 내므로 “반복 경로 O(1) 또는 visible-only” hard gate와 정면 충돌한다.

    badge sync도 signal burst를 250ms로 coalesce할 뿐 list_tasks() 전체를 다시 호출한다. debounce는 algorithmic bound를 바꾸지 않는다.

    판정: hard-contract P0.

    F-04. Refresh authority가 세 갈래이며 run readiness도 external readiness를 기다린다

    문서는 settings·endpoint·capability external edit를 explicit refresh에서만 반영하고 ordinary turn은 last completed snapshot을 써야 한다고 명시한다. 그러나 현재 settings/endpoint는 세 갈래 freshness authority를 가진다.

    • SettingsService의 5분 QTimer가 global settings/providers mtime을 poll하고 Qt thread에서 변경 파일을 읽는다.
    • ConfigProvider.get()과 readiness/context resolve가 turn마다 folder tier를 포함해 mtime을 여러 번 본다.
    • 20분 deployment poller callback이 forced endpoint config reconcile을 Qt에서 수행한다. 현재 기본 composition에는 discovery provider가 없어서 Ollama network probe는 실행되지 않지만 tier stat, selection update, signal fanout은 남고 callback 이름은 실제 의미를 흐린다. 향후 discovery provider를 주입한다면 동기 network 구현을 worker/async boundary 없이 이 경로에 연결하면 안 된다.

    MCP도 production wiring은 refresh_mcp_for_run(wait=True)를 RunReadinessBuilder에 넣고, builder는 이를 await한 뒤 AgentRunStarted를 보낸다.

    clean turn에서는 dirty gate로 빠질 수 있지만 다음 경우에는 blocking 가능하다.

    • 첫 run (_mcp_dirty=True)
    • working folder/config/plugin/connector change 뒤
    • 이미 진행 중인 refresh를 clean turn이 wait=True로 만났을 때

    refresh_endpoints_for_run()도 ConfigProvider.refresh()를 통해 tier mtime을 turn path에서 stat한다. capability discovery 자체는 no-standing-scan과 targeted invalidation을 대체로 지키므로, 잘 된 경로까지 blanket cache rewrite로 바꾸지 말아야 한다.

    판정: contract drift P0.

    F-05. Permission snapshot read가 thread boundary를 우회한다

    write는 proxy로 asyncio loop에 schedule하지만, AsyncSessionHandleProxy의 read methods는 Qt thread에서 weakref로 AsyncSession과 그 PermissionManager를 직접 호출한다. comment는 read-only snapshot이며 cold miss disk read만 가능하다고 정당화하지만, docs/layers.md는 handoff가 proxy를 통과하더라도 asyncio half에 대한 direct call을 금지하고 Qt/async mutable state 변경을 각 thread로 제한한다.

    더 중요한 것은 UI event handler에서 cold JSON read가 생길 수 있다는 점이다. GIL 때문에 안전해 보이는 것과 authority/thread contract가 안전한 것은 다르다.

    판정: correctness P0.

    F-06. ModelSelection이 교체된 HTTP client의 수명을 닫지 않는다

    ModelSelection은 endpoint/model/settings 변경 때 _client = None으로 만든다. AsyncHvppyAI는 owned httpx.AsyncClient를 가지고 await close()가 필요하지만 shutdown은 현재 field에 남아 있는 client만 닫는다. 여러 번 선택/refresh하면 이전 pool이 GC에 맡겨지고 connection/resource leak가 될 수 있다.

    RunReadiness가 llm_client를 생성하지만 실제 turn context는 다시 client_provider(model, endpoints)를 호출하고 readiness field 사용처가 보이지 않는다. snapshot이 중복 client creation과 authority 혼선을 만든다.

    판정: resource correctness P0.

    F-07. Transcript index 실패와 rewind가 bounded-query 계약을 무너뜨릴 수 있다

    현재 index parse가 실패하면 empty index로 축소되고, 기존 chunk를 검증·재구성하거나 corruption을 surface하지 않는다. 그 뒤 새 append가 새 index를 쓰면 과거 chunk가 논리적으로 orphan될 수 있다. malformed JSONL도 마지막 불완전 tail과 중간 corruption을 구분하지 않고 건너뛴다.

    또 rewind marker가 하나라도 생기면 여러 pagination/tail path가 correctness를 위해 full logical projection으로 fallback한다. 한 번의 edit가 10,000-message session의 이후 반복 경로를 계속 O(N)으로 만들 수 있다. 따라서 index는 단순 cache라는 선언만으로 충분하지 않고, integrity state와 rewind-aware generation/interval projection, bounded rebuild가 필요하다.

    판정: silent corruption/orphan 가능성은 correctness P0, rewind의 반복 성능은 scale P1. 둘 다 F-02와 같은 projection 계약에서 설계하되 canonical transcript를 버리지 않는다.

    핵심은 새 layer 수가 아니다.

    • UI는 async object가 아니라 event로 받은 immutable snapshot만 읽는다.
    • turn은 refresh를 수행하지 않고 이미 publish된 runtime snapshot의 selection key/generation을 읽은 뒤, client lease를 정확히 한 번 acquire/release한다.
    • transcript write는 session ordering을 보존하되 event loop 밖에서 blocking I/O를 한다.
    • canonical line append와 derived index checkpoint의 durability를 분리한다.
    • scheduler timer는 전체 목록이 아니라 가장 가까운 due item만 본다.
    • command containment는 permission decision 뒤 local child process boundary를 강제한다. HTTP/SSE MCP의 원격 side effect는 local sandbox 대상이 아니며 trust, credential, permission, server policy로 다룬다.

    아래 Phase 0~6은 work package 번호이고, 실제 dependency는 §13 graph가 권위다. P0/P1/P2는 위험 우선순위다. Phase 2의 scale 작업과 Phase 3의 snapshot 작업은 Phase 0 계약 뒤 병렬 가능하며, Phase 4~5가 P1 응집도·계약, Phase 6이 P2 제품 확장을 주로 수행한다.

    6. Phase 0 — contract와 계측을 먼저 고정

    구현보다 먼저 docs/layers.md, docs/config.md, docs/architecture.md, docs/agent.md, docs/session.md, docs/scheduler.md, docs/permission.md에 아래 결정을 명시한다. 새 구조가 기존 규약 표에 안 맞으면 문서를 먼저 고치는 repository rule을 따른다. 현재 architecture Mermaid의 정의되지 않은 stale node도 이 단계에서 parse gate와 함께 바로잡는다.

    작업

    1. RuntimeSnapshot의 authority와 publish 시점을 정의한다.
    2. transcript canonical/index durability와 crash repair 범위를 정의한다.
    3. scheduler due-index authority, external edit reconcile, clock jump/timezone semantics를 정의한다.
    4. containment 대상 process taxonomy와 platform capability 상태를 정의한다.
    5. UI가 받을 permission catalog snapshot schema를 정의한다.
    6. model client owner/lease/close sequence를 정의한다.
    7. core snapshot generation 1 전 prompt admission과 optional MCP generation 0 의미를 정의한다.

    먼저 추가할 실패형 gate

    • turn start에서 config tier stat/content read가 호출되면 fail
    • standing settings timer나 deployment poller가 user endpoint config reconcile을 수행하면 fail
    • 향후 discovery provider가 wiring될 경우 Qt thread에서 network probe가 실행되면 fail
    • clean/dirty turn 모두 slow MCP future를 기다리지 않음
    • scheduler tick에서 list_tasks, glob, N개 stat, sort가 호출되면 fail
    • permission UI read가 AsyncSession weakref를 dereference하면 fail
    • hook timeout/cancel 뒤 descendant process가 남으면 fail
    • explicit discovery도 Qt/shared asyncio turn loop에서 file content를 읽으면 fail
    • model switch N회 후 생성 client N개 모두 정확히 한 번 close
    • transcript append가 asyncio heartbeat를 막지 않음
    • cold transcript materialization이 raw chunk를 한 번만 순회
    • malformed index가 silent empty history로 축소되지 않고 bounded repair/quarantine로 전환
    • rewind가 존재해도 normal pagination이 full projection fallback을 호출하지 않음

    Exit criterion

    문서와 failure-reproduction harness가 현재 gap을 재현하고, 어떤 component가 각 state를 소유하는지 표 하나로 설명된다. main branch를 red로 두지는 않는다. 각 guard는 대응 구현과 같은 tranche에서 활성화하거나, 불가피하면 명시적 temporary xfail과 제거 issue/조건을 함께 둔다.

    7. Phase 1 — correctness/security 기반 닫기

    7.1 ExecutionBoundary

    PermissionManager 안에 sandbox를 넣지 않는다. 다음 Protocol을 별도 application service로 둔다.

    ExecutionBoundary
  capabilities(profile, platform) -> ContainmentCapabilities
  prepare(request, decision, workspace) -> ExecutionPlan
  spawn(plan) -> ManagedProcess

    ExecutionPlan은 argv/shell, cwd, read/write roots, network, environment policy, process tree와 backend capability report를 담는다. Bash/background shell/user-configured hook처럼 local child argv나 input을 model 또는 extension이 통제하는 path와 stdio MCP server spawn이 이 plan을 거친다. 이미 원격에 있는 HTTP/SSE MCP의 side effect는 이 boundary가 막을 수 없다.

    현재 .git/.env hard guard는 built-in Edit/Write에만 적용되고 Bash/hook에는 동일한 불변식을 주지 않는다. containment 전까지는 UI와 문서도 이를 “Edit/Write guard”로 좁혀 표현하고 Full Access 또는 shell access를 filesystem containment로 오해하게 만들지 않는다.

    platform 후보:

    • macOS: Seatbelt profile
    • Linux/RHEL: bubblewrap 우선, user namespace/SELinux/site policy 감지
    • Windows: restricted token/Job Object/AppContainer 가능성을 spike 후 결정

    중요 계약:

    • filesystem, network, process-tree, socket/syscall capability마다 enforced / unavailable / disabled를 따로 보고한다.
    • 선택 profile의 required guarantee를 모두 만족할 때만 overall state를 enforced로 표시한다.
    • backend name, unavailable reason, profile satisfaction을 별도 field로 둔다. Job Object처럼 process-tree만 잡는 backend를 filesystem/network까지 enforced라고 표시하지 않는다.
    • backend unavailable을 sandboxed 또는 degraded-enforced라고 표시하지 않는다.
    • managed config는 fail_if_unavailable을 강제할 수 있다.
    • 사용자 선택 fallback은 unavailable 상태의 명시적 approval과 UI 경고를 남기며, 자동 fallback은 없다.
    • support process(capability worker 등)와 untrusted command를 다른 profile로 둔다.
    • network/socket allowance는 filesystem allowance와 별도다.
    • HTTP/SSE MCP는 local containment 대신 server trust, credential scope, permission과 provenance를 기록한다.

    7.2 Cross-thread permission snapshot

    async side가 mutation commit 후 PermissionCatalogSnapshot event를 내보내고 UiSession이 이를 projection으로 보관한다. dialog/list/pill은 그 snapshot만 읽는다. scope path까지 primitive/immutable data로 복사한다.

    같은 원칙으로 loop가 아직 준비되지 않았을 때 UiPostBoxProxy가 PostBox를 직접 mutate하는 fallback도 proxy-owned startup ingress queue로 바꾼 뒤 loop-ready event에서 drain한다.

    7.3 Model client lifecycle

    ModelSelection의 nullable client field를 ModelClientPool + ModelClientLease로 교체한다. pool은 현재 config generation의 client와 실제 in-flight lease가 남은 draining generation만 보유한다. endpoint 또는 credential reference가 바뀌면 old generation은 새 lease를 받지 않고 마지막 lease 반환 즉시 close()된다. shutdown은 admission을 닫고 bounded drain 뒤 남은 run을 취소한 다음 생성된 모든 client를 정확히 한 번 닫는다. pool key와 diagnostics에는 raw secret을 넣지 않는다.

    RuntimeSnapshot에는 live resource가 아니라 model selection key와 endpoint/config generation만 둔다. RunReadiness는 client를 생성하거나 보관하지 않는다. TurnCoordinator가 admission 시 TurnContextProvider를 통해 해당 generation의 lease를 정확히 한 번 acquire하고 terminal/cancel/error path에서 release한다. 현재 readiness와 context provider가 각각 client를 선택하는 이중 authority는 제거한다.

    production fallback_model이 빈 문자열인 현 상태도 제품 truth와 맞춘다. fallback을 실제 지원할 것이면 immutable selection/lease 계약으로 wiring하고, 그렇지 않으면 UI·문서에서 core scaffolding을 완성 기능으로 표현하지 않는다.

    7.4 Account-home path correctness

    HPC에서 $HOME과 passwd/NSS home이 다를 수 있다는 hard contract에 맞춰 runtime resolver, turn context, scheduler check 등 account-relative path를 expand_account_path()로 통일한다. 모든 expanduser()를 기계적으로 바꾸지 말고 user-selected arbitrary path, display normalization, account-owned storage를 분류한다. mismatched HOME fixture에서 permission/cwd/storage가 NSS home을 쓰는지 검증한다.

    Exit criterion

    • untrusted command의 containment 상태와 backend가 UI/diagnostics에 보인다.
    • managed fail-closed test가 실제 prohibited read/write/network를 막는다.
    • timeout/cancel 뒤 local child와 descendant process가 0개 남는다.
    • Qt thread가 async permission object/disk를 읽지 않는다.
    • loop-ready 이전 PostBox ingress도 async-owned state를 직접 mutate하지 않는다.
    • model switch/turn overlap/shutdown에서 client leak과 double-close가 없다.
    • mismatched $HOME 환경에서 account-owned path가 passwd/NSS home과 일치한다.

    8. Phase 2 — NFS와 10,000 entity hot path 수정

    8.1 Transcript writer lane

    권장 구조:

    1. session은 sequence를 매긴 append request를 bounded per-session writer에 보낸다.
    2. blocking append는 전용 bounded storage executor에서 수행한다.
    3. 완료를 await한 뒤 in-memory cache와 UI event를 갱신해 disk-first를 유지한다.
    4. writer failure는 해당 session turn을 실패시키되 다른 session event loop를 멈추지 않는다.

    manifest를 매 line rewrite하지 않는다.

    • chunk JSONL line이 canonical이다.
    • index는 active chunk의 last indexed byte offset/sequence를 checkpoint한다.
    • index checkpoint는 turn end, batch threshold, chunk rotation, orderly shutdown에 수행한다.
    • crash 후 최대 active chunk 하나만 incremental repair한다.
    • chunk size bound 때문에 repair cost도 bounded다.

    durability는 모호한 “저장됨” 한 단어로 표현하지 않는다.

    • 각 envelope는 canonical JSONL에 write + flush된 뒤에만 cache/UI event를 publish한다.
    • 이 baseline은 process-crash ordering이지 power-loss durability라고 부르지 않는다. terminal·clean shutdown file fsync와 새 chunk/atomic-replace 뒤 directory fsync를 추가할지는 local SSD와 대상 NFS의 p95 측정으로 Phase 0에서 결정한다. user prompt마다 무조건 fsync하는 설계를 근거 없이 고정하지 않는다.
    • 선택한 backend가 해당 보장을 제공하지 못하면 diagnostics에 durability state를 낮춰 표시하고 기록한다. 실패를 무시한 채 power-durable이라고 주장하지 않는다.
    • index는 derived data이므로 checkpoint fsync 실패가 canonical append를 되돌리지는 않지만 stale/repair required state를 남긴다.

    index load는 valid / tail-truncated-recoverable / index-missing-rebuildable / chunk-corrupt-quarantined / repair-failed-read-only 같은 integrity state를 반환한다. 마지막 partial line과 중간 corruption을 구분하고, silent empty index로 계속 append하지 않는다. rewind는 active generation 또는 visible interval을 index에 투영해 정상 pagination이 영구 full reconstruction으로 떨어지지 않게 한다. flush, file fsync, directory fsync 중 무엇을 어느 terminal/batch에서 보장할지는 NFS 비용과 함께 명문화하고 latency·crash fault-injection gate로 고정한다.

    load_all + max_numeric_message_id는 한 scan에서 transcript projection과 counters를 함께 반환하는 TranscriptLoadSnapshot으로 통합한다. rewind가 있는 경우에도 두 번째 raw scan을 만들지 않는다.

    8.2 Scheduler due index

    60초 sweep을 min-heap/generation map 기반 due authority로 교체한다.

    • startup/explicit refresh에서 schedule definitions를 한 번 reconcile
    • CRUD write 직후 해당 task만 heap/index 갱신
    • timer는 heap head까지 single-shot
    • stale heap entry는 generation token으로 O(log N) 제거
    • clock/timezone change는 bounded rebuild라는 명시적 event
    • external file edit는 explicit Refresh에서만 반영
    • badge count는 unseen_count/running_count aggregate projection으로 O(1)

    scheduler-index.json을 derived sequential index로 둘 수 있다. canonical schedule.json과 history가 우선이며 index mismatch는 startup/explicit repair에서 rebuild한다. NFS에서 file 10,000개 content를 읽지 않도록 directory signature + index + changed item stat을 사용한다.

    Exit criterion

    • synthetic 10,000 schedules에서 idle timer path의 file I/O와 sort가 0
    • one task CRUD가 O(log N) 이하이며 전체 rebuild를 호출하지 않음
    • transcript append 중 Qt/async heartbeat가 유지
    • crash/reopen 후 active chunk repair가 정해진 bound를 넘지 않음
    • NFS latency fake에서 다른 session turn이 진행 가능

    9. Phase 3 — run readiness와 explicit refresh 일치

    9.1 Last-completed snapshot

    RunReadinessBuilder.build()는 network/disk refresh를 하지 않는다. 다음 immutable data를 O(1)로 읽는다.

    • catalog generation과 active/searchable tool snapshot
    • latest completed MCP tool/server snapshot + stale/refreshing indicator
    • endpoint/runtime snapshot
    • model selection key + endpoint/config generation
    • settings path metadata(필요하다면 이미 계산된 값)

    live ModelClientLease는 snapshot에 넣지 않고 turn admission에서 acquire한다.

    9.2 Bootstrap과 prompt admission

    • settings, endpoint/model selection, builtin permission/tool처럼 model call에 필수인 core snapshot generation 1이 publish되기 전에는 prompt를 model run으로 admit하지 않는다. UI 입력을 보관할 수는 있지만 상태를 Starting runtime으로 명시한다.
    • startup의 core config read는 허용된 1회 reconcile이며, 실패하면 stale arbitrary object로 진행하지 않고 actionable error를 낸다. persisted snapshot을 재사용하려면 schema/config fingerprint 검증을 먼저 한다.
    • external MCP와 optional marketplace capability는 generation 0의 typed empty/stale snapshot으로 시작할 수 있고 background reconcile 결과를 다음 turn부터 publish한다. slow/hung MCP는 core admission을 막지 않는다.
    • 유효 endpoint/model이 없으면 prompt를 소비하지 않고 설정 복구 surface로 보낸다.

    9.3 Refresh owner

    • core bootstrap gate 뒤 optional discovery/reconcile은 window show 후 background에서 snapshot을 publish
    • SettingsService 5분 mtime timer는 제거
    • settings/UI mutation은 write 직후 affected cache와 snapshot을 직접 rebuild
    • folder switch는 folder-key registry LRU miss에만 lazy discovery
    • /reload, Customize Refresh, capability tool은 explicit full/targeted reconcile
    • ordinary turn은 refresh task가 돌아도 기다리지 않음
    • endpoint/model picker의 Refresh는 명시적 trigger에서 수행하고, 향후 Ollama discovery provider를 wiring할 경우 worker/async I/O로 실행해 Qt deployment poller에는 섞지 않음
    • “MCP required” 같은 future policy가 필요하면 turn 전체 implicit wait 대신 사용자가 선택한 readiness requirement와 bounded timeout을 별도 상태로 정의

    endpoint ConfigProvider.refresh()도 turn path에서 제거하고 readiness와 TurnContextProvider가 같은 한 번의 runtime resolution을 공유한다. in-app write는 cache reset + snapshot publish, external edit는 explicit refresh만 반영한다.

    Exit criterion

    • slow/hung MCP가 ordinary prompt persistence와 model start를 block하지 않음
    • 최초 core snapshot 전에는 model run admission이 차단되고 optional MCP generation 0은 nonblocking임
    • turn-start path의 stat/read/connect call count가 0
    • Qt periodic timer path의 local settings/endpoint reconcile count가 0
    • explicit discovery의 file content read는 전용 worker/storage lane에서만 실행됨
    • refresh 완료 전/후 turn이 각각 어떤 generation을 사용했는지 event에 기록
    • single exposure toggle은 해당 item만 patch하고 registry 전체 scan 없음

    10. Phase 4 — hotspot을 authority 단위로 분해

    파일 길이만 보고 class를 쪼개지 않는다. 서로 다른 state owner/failure boundary를 기준으로 한다.

    AsyncSession

    현재 이미 PendingInteractionStore, QueryIOBuilder, PostBoxPump, event types 같은 seam이 있다. 다음 후보를 우선한다.

    추출 후보 소유 state 추출 이유
    TranscriptRuntime active transcript snapshot, append/load sequence, counters storage failure/thread boundary가 turn policy와 다름
    TurnCoordinator active task, run IDs, trigger, terminal outcome lifecycle state machine을 독립 테스트
    GoalContinuationController reminder cadence, resume kick, goal state 일반 chat turn과 변경 이유가 다름
    ToolActivityTracker awaiting/cancel/background/abort result terminal tool invariant 한곳에

    query_loop 자체는 app-agnostic이므로 더 많은 app service를 안으로 넣지 않는다.

    UiSession

    이미 bubbles/event dispatcher가 분리됐지만 permission, stream, pending posts, duration, selection projection이 남아 있다.

    추출 후보 소유 state 원칙
    UiPermissionProjection committed snapshot + pending command IDs/optimistic display state mutation authority는 async side에만 두고 direct read 금지
    UiStreamingProjection streaming parts/rate/reset paint model과 lifecycle 일치
    UiPendingProjection pending post snapshot/reconcile PostBox delivery SSoT와 구분
    UiTurnMetricsProjection durations/context/last request 10k visible-window만 갱신

    QObject/signal root는 UiSession에 남겨도 된다. helper가 signal ownership까지 무리하게 분산하면 wiring만 복잡해진다.

    CapabilityCatalog

    catalog state, derived exposure, mutation facade, Qt signal bridge가 다른 이유로 바뀐다면 분리한다. registry list를 UI에 캐시시키거나 generic “extension manager” 하나로 skills/plugins/MCP를 평탄화하지 않는다.

    SubAgentManager admission

    active agent는 hard cap 32라 일부 linear lookup이 사실상 bounded지만 pending run은 10,000까지 허용한다. _pending_run_ids의 remove/index/count scan은 ordered dict 또는 deque+id index와 O(1) counter로 바꾸고, cancel·queue-position update가 전체 pending list를 훑으면 fail하는 guard를 둔다. 이것은 manager를 여러 wrapper로 쪼개기보다 admission authority의 자료구조를 바로잡는 작업이다.

    Exit criterion

    • 각 추출 class의 mutable state owner가 하나
    • 기존 public behavior와 event ordering 유지
    • AsyncSession/UiSession이 composition/wiring 중심으로 줄어듦
    • 새 abstraction이 실제 두 개 이상의 caller/failure path를 단순화

    11. Phase 5 — typed application protocol 강화

    app-server를 만들지 않고도 Codex/OpenCode의 장점을 취할 수 있다.

    SessionCommand

    SubmitUserText
SteerTurn
CancelTurn
ResolveApproval
ResolveQuestion
SetPermissionMode
CloseSession

    각 command는 session ID, command ID, created sequence, 필요한 snapshot generation을 가진다. 현재 proxy method를 억지로 JSON-RPC로 만들 필요는 없지만, ordering과 result/error contract는 타입으로 고정한다.

    RuntimeControlCommand

    shared runtime refresh는 특정 session actor의 command가 아니다.

    RefreshCapabilities
RefreshEndpoints
MutateSettingsOrExposure
ReconcileFolderScope

    이 command는 application-level ingress에서 ExplicitRefreshService로 들어가 새 RuntimeSnapshot generation을 publish한다. SessionCommand와 RuntimeControlCommand 사이 ordering은 generation ID로 관찰하며, shared refresh authority를 임의 session queue에 넣지 않는다.

    AgentEvent

    현재 typed event를 유지하되 다음을 명시한다.

    • run/turn/tool terminal event exactly once
    • readiness generation과 containment state
    • permission catalog snapshot commit
    • refresh started/completed/stale는 runtime metadata이며 transcript 주입 대상 아님
    • UI reconnect/re-materialize 시 authoritative snapshot을 만드는 방법

    Tool·artifact·trace conformance

    모든 model-visible tool path에 공통 prefix/terminal contract를 적용하되 execution boundary는 tool kind별로 분기한다.

    discover/dispatch capability
  → exposure snapshot
  → schema validation
  → hook/policy
  → permission
  → [in-process built-in | local child → ExecutionBoundary |
     remote MCP → trust/credential/server-policy adapter |
     stdio MCP server spawn → ExecutionBoundary]
  → bounded result 또는 artifact spill
  → transcript commit
  → terminal AgentEvent exactly once

    parallel-safe 선언이 없으면 직렬을 기본으로 하고, cancel·timeout·permission deny에서도 terminal result가 반드시 닫혀야 한다. remote MCP side effect는 local sandbox가 되지 않는다는 trust state도 event에 남긴다. large-output spill은 현재 MCP의 부분 구현을 전체 tool contract로 평탄화하되, node-local/NFS 저장 위치, secret redaction, 파일 권한, TTL/cleanup, model preview bound를 함께 결정한다. session/turn/tool/child/MCP correlation ID는 event·log·artifact metadata에 전달하되 runtime health/trace를 대화 transcript의 model context로 주입하지 않는다. plugin·skill·MCP provenance와 승인 당시 source fingerprint도 같은 audit envelope에서 조회 가능해야 한다.

    언제 server로 승격할 것인가

    다음 중 하나가 실제 requirement가 될 때만 protocol transport를 도입한다.

    • headless scheduler process
    • 두 번째 native/web client
    • remote HPC execution host
    • crash-isolated runtime daemon

    그 전에는 in-process typed boundary와 conformance test로 충분하다.

    12. Phase 6 — 제품 기능 확장

    기반이 닫힌 후에 진행한다.

    1. 알려진 미완인 workspace in-process MCP
    2. artifact-aware multi-agent orchestration의 resume/budget/merge 강화
    3. extension trust UI 제품화와, publisher identity/signing-root 요구가 생길 때의 조건부 signature
    4. plugin hook을 metadata-only로 유지할지 executable feature로 지원할지 결정; 지원 시 HookRunner와 ExecutionBoundary에 명시적으로 wiring
    5. local derived search/index와 repair diagnostics
    6. 필요 시 headless adapter/app protocol transport

    Claude Code agent teams나 Codex deep thread graph를 그대로 목표로 삼지 않는다. 실제 workflow가 shared task DAG/mailbox/peer communication을 요구하고 current orchestrate-workflow로 해결되지 않는다는 evidence가 있을 때 확장한다. cryptographic publisher signature는 publisher identity와 signing-root 운영 요구가 생길 때만 조건부로 도입한다.

    14. 리스크 레지스터

    리스크 가능성 영향 완화
    bubblewrap/user namespace가 HPC에서 금지 높음 높음 capability detection, managed fail-closed, site-approved backend
    async storage offload가 ordering을 깨뜨림 중 높음 per-session sequence/single writer/terminal flush test
    batched index가 crash 후 stale 높음(의도) 중 index를 derived로 선언, bounded active-chunk repair
    due heap이 system clock jump를 놓침 중 높음 clock-change detector와 bounded rebuild
    background refresh snapshot이 stale 정상 상태 중 generation/stale 표시, explicit refresh, old snapshot 사용 계약
    client lease가 shutdown을 지연 중 중 bounded drain 후 cancel/close sequence
    remote MCP side effect가 local sandbox 밖 높음 높음 server trust, least-privilege credential, permission, executable/endpoint provenance
    first valid runtime snapshot 부재 중 높음 core prompt admission gate와 typed optional-MCP generation 0
    hook/child descendant가 timeout 뒤 생존 중 높음 process group/Job ownership과 descendant-zero integration test
    class 추출이 wrapper만 늘림 중 중 state owner/failure boundary 없는 추출 거부
    full protocol이 조기 platform화 중 높음 transport는 실제 두 번째 surface까지 보류

    15. 지표

    architecture 개선은 LOC 감소가 아니라 다음 지표로 판정한다.

    • prompt submit → first model stream latency(p50/p95), MCP slow server 유무별
    • asyncio heartbeat max stall, transcript append/open 중
    • Qt event loop max stall, 10k schedules/session sidebar 상태에서
    • turn-start filesystem stat/content read count
    • transcript append당 NFS operations와 manifest rewrite 횟수
    • rewind 후 pagination의 full-projection fallback 횟수와 integrity repair 범위
    • scheduler idle tick file I/O/sort count
    • Qt periodic callback의 settings content read와 endpoint reconcile count; discovery wiring 시 network call count
    • client created/closed/active connection count
    • tool call terminal-event completeness
    • refresh generation mismatch/stale snapshot duration
    • session resume repair 범위와 시간

    16. 하지 말아야 할 단기 처방

    • sync transcript append에 asyncio.to_thread()만 매번 호출해 ordering과 thread 수를 운에 맡기기
    • scheduler sweep interval을 60초에서 5분으로 늘려 O(N) 문제 숨기기
    • MCP wait timeout만 줄이고 ordinary turn이 refresh에 의존하는 구조 유지
    • 5분 settings poll을 20분 deployment poller로 옮겨 timer 수만 줄이기
    • permission snapshot dict에 lock 하나만 붙여 Qt direct read 정당화
    • old client를 gc.collect()에 맡기기
    • sandbox라고 이름 붙인 allow/deny parser를 추가하기
    • AsyncSession을 파일 여러 개로만 쪼개고 state authority는 그대로 공유하기
    • SQLite를 NFS canonical store로 도입하기
    • index parse 실패를 empty history로 삼고 다음 append로 덮어쓰기
    • app-server를 먼저 만들고 protocol semantics를 나중에 정하기

    17. 최종 권고

    가장 논리적인 순서는 다음과 같다.

    계약·실패형 gate
  → [command containment + thread/resource correctness
     | transcript/scheduler의 NFS·10k hot path
     | last-completed runtime snapshot] 병렬
  → authority 단위 hotspot 분해
  → typed application protocol
  → workspace MCP와 orchestration 확장
  → 실제 필요가 생길 때 remote/app-server

    이 순서는 화려한 기능을 미루기 위한 YAGNI가 아니다. 반대로 scheduler, multi-agent, plugin, remote surface를 production level로 키우기 위해 지금 아니면 더 비싸지는 기반을 먼저 닫는 순서다.

    Farad는 OpenCode처럼 server-first일 필요도, Claude Agent SDK의 live-session subprocess topology를 전체 제품에 복제할 필요도, Codex처럼 모든 surface의 거대 Rust kernel일 필요도 없다. Farad의 승리 조건은 이미 선택한 product boundary를 정확히 지키는 것이다.

    Qt는 projection, asyncio session은 turn authority, transcript는 replay authority, derived index는 query accelerator, explicit refresh는 snapshot publisher, permission은 policy, containment는 OS enforcement. 이 일곱 문장이 코드와 테스트에서 모두 사실이면 Farad의 architecture는 비교 대상과 다른 것이 아니라 목적에 맞게 더 정확한 것이다.
