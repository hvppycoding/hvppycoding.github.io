    1. 결론

    Farad는 단순한 “LLM 채팅 GUI”가 아니다. 현재 구현은 다음 요소를 실제로 갖춘, 데스크톱 중심의 이벤트 구동 coding-agent 플랫폼이다.

    • SDK와 agent runtime을 분리한 3-패키지 구조
    • Qt 메인 스레드와 단일 asyncio 런타임 스레드 사이의 명시적 proxy 경계
    • callback inversion을 사용한 UI 비의존 query loop
    • append-only transcript, rewind, compaction, protocol normalization
    • 정책 계층이 분명한 permission/approval 시스템
    • stdio·SSE·Streamable HTTP를 포함한 MCP lifecycle과 circuit breaker
    • skill·plugin·connector·marketplace를 합성하는 capability catalog
    • session·scheduled run·subagent·background shell을 하나의 제품 안에서 다루는 runtime
    • HPC/NFS와 누적 10,000개 엔티티를 의식한 파생 인덱스·bounded cache·hot-path guard test
    • 매우 넓고 빠른 회귀 테스트군

    핵심 설계 방향은 좋다. 특히 hvppyai에 agent loop를 넣지 않은 점, query_loop를 async generator와 callback으로 평탄화한 점, UI projection을 authority로 삼지 않은 점, 외부 MCP의 readOnly annotation을 곧바로 신뢰하지 않는 점, session sidebar를 파생 인덱스로 만든 점은 경쟁 제품을 참고해 만든 흉내 수준이 아니라 Farad의 배포 환경과 제품 요구에 맞춘 독자 설계다.

    다만 “구조적 완성도”와 “프로덕션 위험이 제거됨”은 같은 말이 아니다. 현재 가장 큰 위험은 알고리즘 자체보다 경계에 몰려 있다.

    1. 단일 asyncio loop에서 transcript 파일 I/O가 동기 실행된다.
    2. SchedulerEngine의 1분 tick이 Qt 메인 스레드에서 전체 schedule 파일을 stat하고 정렬한다.
    3. 문서는 explicit refresh만 허용한다고 선언하지만 settings/endpoints는 5분 QTimer, 매-turn mtime stat, 20분 주기의 endpoint 강제 재해석을 수행한다. 현재 기본 composition에는 discovery provider가 주입되지 않으므로 이 20분 경로를 곧바로 Ollama network probe라고 부르면 안 된다.
    4. 첫 turn 또는 MCP dirty turn은 MCP reconcile 완료를 기다리므로 문서의 “non-blocking readiness”와 다르다.
    5. ModelSelection이 전역 mutable endpoint/model/client 하나를 소유하며, 교체된 client를 닫지 않는다.
    6. permission은 강한 정책 계층이지만 OS sandbox가 아니며, Bash·hook·stdio MCP는 사용자 권한으로 직접 실행된다.
    7. transcript는 flush와 atomic replace를 쓰지만 fsync, index corruption rebuild, corruption surfacing이 없다.
    8. AsyncSession·UiSession·SubAgentManager와 주요 UI class가 지나치게 커서 authority가 다시 집중되고 있다.

    따라서 최종 평가는 다음과 같다.

    Farad의 기능 폭과 runtime 분리, 상태 모델, 테스트 깊이는 상당하다. 그러나 전체 suite, field reliability, OS security와 실환경 NFS/10k benchmark 없이 상용급 운영 품질을 확정하지 않는다. “NFS·10k·explicit refresh·thread ownership·durability”라는 스스로 세운 계약도 모든 경로가 아직 일관되게 지키지는 않는다. 다음 단계는 새 기능 추가보다 I/O execution boundary, scheduler index, model-client authority, refresh truth를 바로잡는 것이다.

    2. 증거 등급과 분석 한계

    이 보고서는 작업 폴더의 00-methodology.md에 정의된 등급을 따른다.

    • [A] 현재 소스 코드와 테스트에서 직접 확인
    • [B] 저장소의 SPEC.md, docs 문서, AGENTS.md에 명시
    • [C] 실행·테스트·명령 출력으로 관찰
    • [D] A~C를 토대로 한 설계적 추론

    중요한 판정은 가능한 한 [A]를 우선했다. 문서와 구현이 다를 때는 구현을 현재 truth로 잡고, 문서 차이는 별도 표에 기록했다.

    이번 검증은 전체 test suite, ruff, mypy를 실행한 것이 아니다. 분석 영역에 직접 대응하는 1,527개 focused test를 실행했고 모두 통과했다. 따라서 “해당 회귀 테스트가 현재 통과한다”는 결론은 가능하지만, “전체 저장소가 모든 gate를 통과한다”거나 “아래 구조적 위험이 없다”는 뜻은 아니다.

    4.2 singleton과 HPC 배포

    bootstrap은 QApplication, data dir, logging/performance monitor, font/theme, app services, main window, tray/shutdown을 하나의 lifecycle로 묶는다. shared filesystem lease를 획득하지 못하면 두 번째 writer를 띄우지 않고 기존 GUI로 요청을 넘긴다. 여러 HPC node가 같은 home을 공유할 수 있다는 현실을 반영한 제품 고유 장점이다. packages/farad/farad/app/bootstrap.py:66-296 [A]

    이 구조의 장점은 session write authority가 한 GUI process로 모인다는 점이다. 단점은 GUI가 죽거나 로그인 display가 없으면 CLI agent run도 사용할 수 없다는 점이다. 현재 제품 명세가 desktop assistant 중심이므로 당장 daemon을 추가할 이유는 없다. 다만 향후 remote/headless surface를 추가한다면 기존 GUI composition root를 그대로 server로 포장하기보다 다음 세 경계를 먼저 분리해야 한다. [D]

    1. RuntimeHost: session pair, MCP, scheduler, subagent, background process lifecycle
    2. PresentationHost: QApplication, windows, tray, Qt-only signals
    3. Ingress: GUI interaction, shared-FS IPC, 선택적 future RPC

    5. layer-design 6축 판정

    축 현재 authority / contract 강점 실제 위험
    Authority transcript는 conversation truth, stores는 persistent truth, AsyncSession은 turn runtime truth, UiSession은 projection UI list를 registry truth로 캐시하지 않는 규약이 분명 ModelSelection 전역 mutable client, 큰 Session/UI manager에 authority 재집중
    Thread / process Qt main thread + 단일 asyncio QThread + child process/MCP transport proxy와 queued signal이 주 경로에 명시됨 일부 Qt→AsyncSession 직접 snapshot read, sync disk I/O가 Qt 또는 shared loop에서 실행
    Flow UI ingress → proxy → AsyncSession → query_loop → callback/tool → transcript → UI event query loop가 UI import 없이 callback inversion readiness가 turn start 전에 endpoint/MCP를 직렬 대기, 중복 runtime resolve
    Hot path 반복 경로 O(1) 또는 O(visible), explicit refresh만 O(N) 허용 session index, bounded LRU, background task counters, paging guard test scheduler 1분 O(N log N)+NFS stats, transcript initial/full rewind scan, settings per-turn stat
    Persistence append-only transcript, atomic metadata/index replace, session-derived index disk-before-UI ordering, chunk paging, schedule history append/paging fsync 없음, transcript index corruption rebuild 없음, sync I/O, marketplace source unpinned
    Failure retry/fallback scaffolding, abort synthetic tool results, MCP breaker, scheduled run phase recovery tool protocol 보존과 cancellation semantics가 강함 production fallback unwired, hook child leak 가능, MCP readiness 문서와 timeout 체감 불일치

    이 표에서 가장 중요한 해석은 “authority 모델이 잘 문서화됐다”와 “모든 호출 경로가 authority를 지킨다”를 구분하는 것이다. Farad의 정석 경로는 좋지만 edge path와 오래된 서비스가 새 계약 밖에 남아 있다.

    6. 패키지·레이어 구조

    6.1 hvppyai

    hvppyai는 agent loop를 소유하지 않고 AsyncHvppyAI, provider registry, request/response/streaming type, retry를 제공한다. provider registry는 OpenAI Chat Completions, OpenAI Responses, OpenAI Codex Responses, Anthropic 계열을 lazy resolution한다. Farad가 모든 LLM 호출에서 stream=True를 사용한다는 앱 계약과 결합된다. [A][B]

    이 분리는 경쟁 제품 대비 중요한 자산이다. provider wire format 변경은 SDK provider에, transcript·tool policy·session은 app runtime에 남길 수 있다. 단, Farad의 ModelSelection lifecycle 문제는 SDK 문제가 아니라 앱의 client ownership 문제다.

    SDK 책임 구현 증거 아키텍처 판정
    provider translation Provider Protocol이 request build, non-stream parse, SSE event parse, done 판정, auth header, per-stream state를 정의 inheritance보다 structural protocol을 택해 vendor adapter가 얇다
    provider registry openai, openai-responses, openai-codex-responses, anthropic을 문자열→lazy import로 resolve 앱이 vendor module을 직접 분기할 필요가 없다
    HTTP lifecycle caller가 client를 주입하지 않으면 자체 httpx.AsyncClient를 소유하고 close()에서만 닫음 ownership contract는 명확하지만 앱이 close를 누락하면 pool이 남는다
    retry 408/409/429/5xx, Retry-After, capped full-jitter backoff transport retry와 agent rerun을 분리할 수 있다
    streaming Farad가 stream=True, usage 포함으로 열고 content/reasoning/tool delta를 정규화 UI와 transcript가 provider-neutral event를 소비한다

    근거: packages/hvppyai/hvppyai/providers/_base.py:13-64, providers/_registry.py:10-40, _client.py:104-134, 285-314; packages/farad/farad/core/query_llm_stream.py:381-417, 735-766 [A]

    SDK가 제공하지 않는 것은 의도적으로 분명하다. session, permission, tool registry, compaction policy, scheduler, subagent는 모두 app 계층 책임이다. 이 경계 덕분에 SDK를 라이브러리로 재사용할 수 있지만, 반대로 Farad를 headless agent로 쓰려면 SDK만으로는 부족하고 app runtime composition이 필요하다. [A][D]

    6.2 hvppyterm

    hvppyterm은 pyte/PTY/preedit 기반 embeddable terminal이며 Farad에 의존하지 않는다. terminal widget을 제품에서 떼어낼 수 있고, GPL reference source를 복사하지 않는 자체 경계도 문서에 명확하다. [A][B]

    6.3 farad 4-layer

    문서는 Loader/Scanner/File Adapter → Registry/Store/Provider → Factory/Service → UI의 의존 방향을 정본으로 둔다. 실제 extension 경로도 대체로 이 형태다.

    • scanner/loader가 disk 형식을 domain def로 변환
    • registry가 folder-keyed bounded cache와 changed signal을 소유

    • AGENTS.md는 turn start mtime stat을 금지하지만 runtime_resolver는 이를 의도된 동작이라고 주석으로 정당화한다.

    5. model picker open/Refresh는 명시적 endpoint reconcile을 수행한다. 실제 network discovery provider를 연결할 때만 worker/async I/O로 분리한다.
    6. 자동 Ollama discovery가 제품 요구라면 explicit-refresh 원칙의 좁은 예외로 문서화하고 worker/async I/O로 옮긴다. 그렇지 않으면 오해를 부르는 20분 model_discovery callback과 force_discovery 명칭을 제거하거나 config reconcile로 정확히 이름 붙인다.

    9. MCP readiness의 “non-blocking” 불일치

    docs/layers.md와 docs/mcp.md는 external MCP refresh가 turn을 막지 않으며 마지막 completed snapshot으로 진행한다고 설명한다. 실제 composition은 다르다.

    • services_factory.py:701-712는 mcp_refresher를 refresh_mcp_for_run(…, wait=True)로 주입한다.
    • RunReadinessBuilder.build는 이를 await한다.
    • AsyncSession._run_turn은 readiness가 끝난 뒤 AgentRunStarted를 emit한다.
    • MCP가 first-run/dirty이면 refresh_mcp_for_run은 connector def merge, connect_all, trust/connection/liveness 처리가 idle이 될 때까지 기다린다.

    clean turn은 dirty gate로 빨리 snapshot을 반환한다. 그러나 첫 turn, folder/server config change 뒤 turn, 이미 진행 중인 refresh와 경합한 turn은 MCP timeout 범위만큼 시작이 늦어질 수 있다. 그동안 UI에는 pending 상태가 보일 수 있지만 transcript persistence와 PostBox pickup도 readiness 뒤로 밀린다. app/services.py:583-733; app/runtime/run_readiness.py:67-84; app/runtime/async_session.py:1204-1219 [A]

    이 판정은 호출 그래프 추정만이 아니다. test_services_refresh.py:618-654는 wait=True 호출이 background reconcile의 release event가 열리기 전에는 완료되지 않고, release 뒤에야 반환함을 명시적으로 검증한다. 반대로 capability hot reload의 run-start 테스트는 scan을 하지 않는다는 것을 고정한다. 즉 “capability discovery는 snapshot-only”와 “dirty MCP readiness는 blocking”이 현재 동시에 참이다. [A]

    이 선택 자체가 반드시 나쁜 것은 아니다. “첫 요청부터 최신 MCP tool schema가 필요하다”면 blocking barrier가 일관적이다. 문제는 현재 문서가 반대 semantics를 약속한다는 점이다. 제품 결정을 다음 둘 중 하나로 명시해야 한다.

    • Snapshot-first: turn은 마지막 snapshot으로 즉시 시작, background reconcile 결과는 다음 tool round/turn부터 적용
    • Readiness-first: first/dirty turn은 bounded reconcile을 기다리고 UI가 “Connecting tools” 단계를 명시

    현재 구현은 Readiness-first다. 문서는 Snapshot-first다.

    최종 종합 06 로드맵은 Snapshot-first를 선택한다. 단 core settings/endpoint/model snapshot generation 1 전에는 prompt admission을 막고, optional MCP만 typed generation-0 empty/stale snapshot으로 nonblocking 시작한다.

    10. Qt ↔ asyncio bridge

    10.1 정석 경로

    SessionPairFactory.open은 Qt thread에서 UiSession과 AsyncSession을 한 쌍으로 만들고 두 registry에 등록한 뒤, async handle로 initial transcript warm-up을 예약한다. 핵심 bridge는 다음 세 proxy다.

    • UiSessionSinkProxy: async side event를 Qt queued Signal로 전달
    • AsyncSessionHandleProxy: Qt call을 call_soon_threadsafe로 단일 asyncio loop에 예약
    • UiPostBoxProxy: UI가 외부 agent message를 async PostBox에 deposit

    AsyncRuntime은 Qt를 import하지 않고 session lookup, suspend/resume, notifier와 wake task를 loop 안에서 관리한다. AsyncLoopThread는 하나의 OS thread와 event loop를 소유한다. 이는 “GUI framework callback과 async orchestration을 한 loop에 섞지 않는다”는 좋은 구조다. app/runtime/session_pair_factory.py:95-216; app/runtime/proxies.py:46-215; app/runtime/async_runtime.py:37-205; app/runtime/runtime_thread.py:22-68 [A]

    disk-before-UI도 정석 경로에 적용된다. TranscriptAppended를 처리할 때 AsyncSession이 먼저 TranscriptStore에 append하고 cache를 갱신한 뒤 sink event를 보낸다. PostBox pickup 역시 transcript에 남긴 후 UI에 표시한다. crash 직전 UI만 보이고 disk에는 없는 대화를 줄이는 올바른 방향이다. app/runtime/async_session.py:1402-1458, 2108-2143 [A]

    10.2 예외 경로

    AsyncSessionHandleProxy의 list_permission_rules_by_scope, permission_cascade_scopes, permission_scope_paths는 async loop에 메시지를 보내지 않고 Qt thread에서 AsyncSession을 직접 dereference한다. 주석은 immutable snapshot 및 cold disk read를 허용하지만 실제로는 다음 위험이 남는다. app/runtime/proxies.py:455-483 [A][D]

    • cold permission read가 Qt를 막을 수 있음
    • async loop가 cascade list를 교체하는 시점과 읽기가 겹칠 수 있음
    • “AsyncSession은 loop-owned”라는 단순한 검증 규칙에 예외가 생김

    구현을 더 정확히 보면 PermissionManager.set_cascade()는 mutable _cascade list reference를 교체하고, Qt read는 그 list를 순회하며 각 SettingsStore.read(populate_cache=False)를 호출한다. cache hit은 lock 없는 SharedSettingsCache dict를 읽고, cold miss는 Path.is_file()·read_text()·JSON parse를 Qt thread에서 수행한다. app/runtime/ui_session.py:1298-1310; core/permission.py:475-498, 649-670; core/settings_store.py:57-76, 119-130; core/settings_cache.py:27-45, 85-119 [A]

    여기서 “반드시 torn snapshot이 생긴다”고 단정할 증거는 없다. CPython에서 list reference 교체와 dict get이 현재 사실상 원자적으로 보이는 데 기대고 있기 때문이다. 정확한 판정은 명시적 synchronization/version contract가 없고, old-or-new revision 보장도 타입으로 표현되지 않으며, cold NFS read가 UI latency에 들어온다는 것이다. 이는 correctness bug의 관측 증거가 아니라 portability·maintainability·latency 위험이다. [A][D]

    반면 mutation 완료 signal은 잘 설계됐다. UiSession은 async write의 on_done이 돌아온 뒤 snapshot을 다시 읽고 permission_rules_changed를 emit하며, 실패 시 success signal을 내지 않는다. test_ui_session.py:2613-2715가 이 post-commit ordering을 고정한다. 다만 cross-thread stress, revision 일관성, “cold UI read 중 filesystem 접근 시 fail” guard test는 찾지 못했다. [A]

    UiPostBoxProxy도 target loop가 아직 돌지 않을 때 PostBox에 직접 deposit한다. startup/shutdown edge에 한정된 fallback이지만 PostBox의 “all access async thread, no mutex” 계약과 다르다. app/runtime/proxies.py:506-564 [A]

    권고는 async owner가 commit/cascade 변경 뒤 PermissionSnapshot(revision, scopes, paths, rules)를 immutable value로 publish하고, proxy가 승인된 O(1) projection만 보관해 Qt가 disk와 AsyncSession object graph를 전혀 만지지 않게 하는 것이다. 테스트는 (1) cold UI read에서 Path.read_text 호출 시 fail, (2) 동시 revision 교체 중 old 또는 new 전체만 관찰, (3) failed write 뒤 revision/signal 불변을 고정해야 한다. PostBox는 loop ready 이전 ingress를 proxy 자체 queue에 보관한 뒤 loop가 ready해지면 drain하면 thread exception을 없앨 수 있다.

    12. Transcript와 compaction

    12.1 저장 구조와 commit ordering

    TranscriptStore는 session transcript를 100개 chat item 단위 JSONL chunk와 index.json으로 저장한다. chat entry와 rewind/compact marker를 append하고, index는 임시 파일에 쓴 뒤 replace한다. append는 파일 object를 flush한 후 반환한다. transcript cache와 UI event는 이 disk append 뒤에 갱신된다. transcript_store.py:40, 264-312, 913-917 [A]

    이 구조의 장점은 분명하다.

    • transcript가 UI widget tree와 독립된 재현 가능한 truth다.
    • normal pagination은 index의 ID range를 사용해 필요한 chunk만 읽는다.
    • tool-call/result protocol을 transcript 단계에서 보존할 수 있다.
    • resume, branch, compaction, session search가 동일 데이터를 공유한다.
    • 테스트가 “bounded chunk read”와 “비싼 fallback이 호출되면 fail”을 직접 검증한다.

    그러나 문서에서 쓰는 “durable”은 의미를 좁혀야 한다. 현재 append는 flush만 하고 fsync하지 않는다. index replace도 file 또는 parent directory fsync가 없다. 따라서 process-level ordering과 atomic rename은 제공하지만, 전원 장애·kernel crash·NFS server failure 뒤의 stable-storage durability까지 보장하지는 않는다. [A]

    NFS에서 모든 message마다 fsync하는 것은 latency가 너무 크므로 단순히 fsync를 추가할 문제는 아니다. 제품이 보장할 durability level을 다음처럼 명시해야 한다. [D]

    • 기본: disk-before-UI, process crash tolerant, power-loss best effort
    • 선택: 중요한 terminal state 또는 일정 batch마다 fsync
    • shutdown: dirty transcript/index의 bounded sync

    12.2 append hot path의 동기 I/O

    AsyncSession event dispatcher는 TranscriptAppended를 받으면 _append_persisted()를 await하지만, 그 coroutine 안의 store.append_entry(entry) 자체는 일반 동기 함수다. TranscriptStore.append_entry()는 JSONL line write/flush 뒤 index 전체를 temp file에 쓰고 os.replace()한다. abort marker append도 같은 sync 경로다. app/runtime/async_session.py:1402-1457, 2108-2194; session/transcript_store.py:246-312 [A]

    여기서 fact는 “Qt thread가 아니라 Farad의 단 하나뿐인 asyncio runtime loop에서 filesystem call이 완료될 때까지 Python thread가 막힌다”는 것이다. inference는 NFS stall 하나가 같은 loop를 공유하는 다른 session run, MCP task, PostBox wake, background orchestration의 tail latency를 함께 키운다는 것이다. async 함수 안에 있다는 사실은 sync I/O를 non-blocking으로 만들지 않는다. [A][D]

    이 경로의 correctness는 높다. test_async_session.py의 write-ordering fixture는 store append가 끝나기 전에 UI sink가 호출되지 않음을 검증한다. 따라서 수정 목표는 ordering 제거가 아니라 execution lane 이동이다. session별 serialized writer queue/thread에서 append를 수행하고, awaitable commit receipt가 돌아온 뒤에만 cache/UI event를 갱신해야 한다. fire-and-forget batch는 crash ordering을 깨므로 부적합하다. tests/test_async_session.py:149-176, 686-785 [A][D]

    12.3 initial load와 shared loop blocking

    AsyncSession._ensure_initial_state는 TranscriptStore.load_all()을 호출한 뒤 max_numeric_message_id()를 호출한다. 두 함수 모두 sync filesystem traversal이며 두 번째도 raw chunks를 다시 훑는다. resume도 load_all()을 async 함수 안에서 직접 실행한다. app/runtime/async_session.py:394-422, 1013-1020; transcript_store.py:820-829 [A]

    문서의 “Qt thread를 막지 않는다”는 표현은 절반만 맞다. Qt thread는 막지 않지만 Farad가 모든 session에 공유하는 하나의 asyncio loop를 막는다. 큰 transcript 하나를 resume하는 동안 다른 session run, background orchestration, MCP work가 지연될 수 있다. 파일이 NFS에 있으면 small-file round trip이 더 커진다. [A][D]

    개선 방향은 transcript 전체를 무조건 thread pool로 던지는 정도가 아니다.

    1. session별 serialized TranscriptIO executor를 둔다.
    2. append ordering은 그 executor queue에서 보장한다.
    3. index에 max numeric message id와 active projection checkpoint를 유지해 initial double scan을 없앤다.
    4. AsyncSession은 awaitable commit receipt를 받은 뒤 UI event를 보낸다.
    5. 여러 session I/O가 shared asyncio event loop를 막지 않되, 같은 session write 순서는 유지한다.

    12.4 rewind 뒤 성능 퇴화

    rewind marker가 하나라도 존재하면 correctness를 위해 load_tail, load_older_before, load_since, reverse iteration, last compact marker, folder marker 등 다수의 최적화 경로가 full logical transcript projection으로 fallback한다. transcript_store.py의 rewind_count 분기(예: 518-522, 609-615, 696-735) [A]

    이 선택은 잘못된 것이 아니다. edit/branch 뒤 숨겨진 entry를 pagination에 섞는 것보다 전량 projection이 안전하다. 문제는 한 번 rewind한 긴 session은 이후 계속 느린 경로를 탄다는 점이다. 10,000 message session에서 edit 한 번이 영구적인 hot-path degradation switch가 된다. [D]

    권고는 rewind-aware projection checkpoint다.

    • marker append 시 active interval 또는 generation을 index에 기록
    • chunk별 active-count/visible-ID range를 파생 metadata로 유지
    • index가 없거나 깨졌을 때만 bounded rebuild
    • full reconstruction은 explicit repair/migration에 한정

    12.5 index와 corruption

    index.json parse가 실패하면 현재 코드는 empty ChunkIndex를 반환한다. 기존 chunk를 scan해 rebuild하거나 corruption을 사용자·diagnostics에 surface하지 않는다. 그 상태에서 새 append가 0000/index를 다시 만들면 오래된 chunks가 orphan되고 논리적 history가 보이지 않을 수 있다. malformed JSONL line도 read 시 조용히 건너뛴다. transcript_store.py:232-258, 920-932 [A]

    부분 tail write를 건너뛰는 tolerance는 유용하지만, “마지막 불완전 line”과 “중간 line corruption”을 같은 방식으로 무시하면 데이터 손실을 감춘다. 다음 integrity state가 필요하다. [D]

    • valid
    • tail-truncated-recoverable
    • index-missing/rebuildable
    • chunk-corrupt/quarantined
    • repair-failed/read-only

    index는 cache이므로 version stamp 후 drop/rebuild가 가능해야 한다. rebuild가 비싸도 session open 한 번의 explicit repair lane에서 bounded progress와 취소를 제공하면 된다.

    12.6 compaction

    Farad compaction은 단순 summary append보다 정교하다.

    • last compact marker 이후 logical slice 계산
    • synthetic summary user entry 구성
    • current turn, file context, activated skill context 보호
    • provider가 reasoning replay를 지원하는지에 따른 reasoning strip
    • tool call/result protocol sanitize
    • missing result synthesis와 empty assistant 제거
    • 항상 streaming compaction
    • request/SSE observability
    • cancel/error 시 stream close
    • 일부 API error에서 stricter sanitized replay
    • sidecar와 transcript marker persistence

    관련 구현은 compaction.py, transcript_normalize.py, app/runtime/compaction_runner.py에 분산되어 있다. [A]

    강점은 “압축된 메시지가 API에 유효한가”와 “resume 후 같은 conversation context가 재현되는가”를 함께 본다는 점이다. 위험은 provider protocol, token budget, transcript marker semantics가 여러 큰 모듈에 걸쳐 있어 변경 시 implicit invariant를 놓치기 쉽다는 점이다. CompactionPlan과 CompactionCommit 같은 명시적 value object로 precondition, protected ranges, output, persisted marker를 묶으면 검증이 쉬워진다. [D]

    13. Tool execution

    13.1 tool contract

    BaseTool Protocol과 ToolContext, ToolResult가 runtime tool API의 중심이다. ToolResult는 모델에 보여줄 output, UI/diagnostic metadata, 큰 artifact reference를 구분한다. ToolExecutor의 흐름은 다음과 같다. [A]

    1. tool existence와 input schema 검증
    2. hard safety/permission 판정
    3. 사용자 approval
    4. pre-hook
    5. tool call
    6. post-hook
    7. output guard·artifact persist
    8. terminal result 생성

    unknown tool과 exception은 terminal tool result로 귀결되고, trace는 file log에 보존된다. safe concurrency가 허용된 tool만 병렬 실행하며, abort되면 이미 시작한 호출을 취소하고 모든 call id에 synthetic result를 보장한다. 이 때문에 다음 LLM request의 tool protocol이 깨지지 않는다. tool_executor.py 전반, core/query_loop.py:1111-1164 [A]

    13.2 concurrency semantics

    병렬 tool이 완료되는 순서는 달라도 query_loop는 original call order로 terminal transcript를 기록한다. 이는 replay determinism과 provider compatibility에 유리하다. 반면 side effect 자체의 실제 완료 순서는 여전히 다를 수 있으므로 “parallel safe” 분류가 correctness authority다. annotation 하나에 의존하지 말고 동일 path write, cwd mutation, session state mutation 같은 conflict key를 tool metadata로 표현할 여지가 있다. [D]

    13.3 hooks

    HookRunner는 user-configured shell command를 asyncio.create_subprocess_shell로 실행한다. TOOL_INPUT과 TOOL_OUTPUT을 environment로 전달하며 timeout 시 직접 process를 kill한다. 별도 process group을 만들지 않으므로 shell이 child/grandchild를 낳은 경우 timeout 뒤 남을 가능성이 있다. hooks/runner.py:154-240 [A][D]

    hook은 extension point로 강력하지만 permission dialog를 거치지 않는다. 즉 settings file을 수정할 수 있는 주체는 사실상 arbitrary host code execution authority를 가진다. 이는 제품이 config를 trusted input으로 본다면 허용 가능한 모델이지만, UI에서 marketplace plugin/hook을 “기능 확장” 정도로만 표현하면 trust 수준을 과소 전달할 수 있다.

    14. Permission, approval, attendance, sandbox

    14.1 permission decision pipeline

    PermissionManager의 우선순위는 대략 다음과 같다.

    1. hard guard
    2. explicit deny
    3. contextual rule
    4. explicit ask
    5. tool-specific rule
    6. explicit allow
    7. permission mode
    8. fallback

    Bash command는 compound command를 segment로 나눠 rule을 적용하고, permission scopes는 user/folder/session cascade를 갖는다. core/permission.py:690-828 [A]

    상호작용 가능성은 permission mode와 별도 attendance axis로 다룬다. scheduled/headless run에서 Ask tool은 사용자가 자리에 없으므로 즉시 deny되며, 이는 DONT_ASK와 BYPASS에서도 독립적으로 적용된다. unattended execution이 dialog에서 영원히 멈추지 않게 하는 좋은 설계다. tool_authorization.py:48-123 [A]

    외부 MCP tool은 server가 readOnlyHint를 붙여도 기본 Ask다. Farad가 소유한 internal MCP에서만 readOnly annotation을 mode auto-allow에 사용할 수 있다. MCP metadata를 trust proof로 착각하지 않는 보수적 경계다. mcp/adapter.py:179-208 [A]

    14.2 .git/.env hard guard의 실제 범위

    Edit/Write tool은 .git 및 .env 계열 path를 lexical/resolved variant로 보호하고, BYPASS보다 먼저 hard guard를 적용한다. core/permission.py:897-956 [A]

    그러나 이 hard guard는 tool name Edit/Write에만 적용된다. Bash에서 rm, sed, python, git command를 실행하거나 hook이 파일을 바꾸는 것은 막지 않는다. docs/permission.md의 “.git/.env hard safety guard가 BYPASS에서도 유지”라는 문구는 이 제한을 함께 쓰지 않아 전체 실행 경계를 보호하는 것처럼 읽힐 수 있다. [A][B]

    Bash command를 완전하게 parse해 같은 보장을 제공하는 것은 shell semantics상 어렵다. 따라서 선택지는 둘이다.

    • 문구를 “built-in Edit/Write guard”로 좁히고 Full Access/Bash는 host access라고 명확히 표시
    • 실제 immutable guarantee가 제품 요구라면 shell을 sandboxed filesystem view에서 실행

    첫 번째가 현재 architecture truth다.

    14.3 OS sandbox 부재

    소스에서 seccomp, bubblewrap, Landlock, namespace, macOS sandbox, Windows restricted token 같은 containment 구현은 발견되지 않았다. settings type은 sandbox를 future P2/P3 항목으로 명시한다. Bash/background shell은 사용자 계정 권한과 environment, cwd를 가지고 직접 subprocess를 띄운다. process group은 cancellation을 위한 것이지 filesystem/network containment가 아니다. background_shell.py:685-783; core/settings_types.py:180-185 [A]

    따라서 Farad permission의 정확한 정의는 다음과 같다.

    Farad permission은 모델이 어떤 동작을 요청할 때 UI/정책 수준에서 승인 여부를 결정하는 policy engine이다. 승인된 process를 OS에서 격리하는 sandbox는 아니다.

    Full Access UI가 삭제·시스템 변경·network 전송 위험을 명시하는 것은 정직하다. 하지만 cross-product 비교에서 Codex나 Claude Code의 sandbox/permission과 같은 축으로 점수를 매길 때 “permission feature가 있다”와 “host containment가 있다”를 분리해야 한다.

    권고는 당장 모든 플랫폼에 강제 sandbox를 구현하는 것이 아니다. 먼저 ExecutionBoundary 또는 CommandRunner Protocol을 만들어 다음 execution source를 한 authority 아래 둔다.

    • foreground Bash
    • background Bash
    • hook
    • stdio MCP
    • future local connector

    그 위에 Linux optional bwrap/Landlock profile, Windows restricted process/job policy, sandbox unavailable 시 explicit policy-only mode를 붙일 수 있다. HPC에서 bwrap 설치나 user namespace가 보장되지 않으므로 graceful capability detection이 필요하다. [D]

    15. MCP architecture

    15.1 transport와 lifecycle

    MCPManager는 external/internal server를 같은 manager 아래 두고 stdio, SSE, Streamable HTTP를 지원한다. connect_all은 server별 작업을 병렬화하고 다음 기능을 갖는다.

    • explicit trust gate
    • connection timeout과 per-call timeout
    • unchanged config liveness check
    • server-set fingerprint와 delta reconcile
    • removed/changed server stop
    • active call drain 뒤 config 교체
    • failure threshold circuit breaker
    • half-open single probe
    • expired transport/session reconnect 후 재시도
    • bounded server instruction text

    mcp/manager.py:147-309, 430 이후; mcp/connection.py:344-500 [A]

    MCPServerConnection이 anyio context lifetime을 같은 task에서 소유하는 것도 중요하다. async context manager를 다른 thread/task에서 무리하게 닫는 오류를 피한다.

    15.2 schema와 result adapter

    MCP adapter는 tool name을 normalize/truncate/hash하고, external tool은 기본 Ask로 둔다. 큰 output은 약 24k 기준을 넘으면 artifact writer가 있을 때 파일로 보존하고 모델에는 bounded result를 전달한다. mcp/adapter.py:35-93, 153-283 [A]

    내부 서버는 app-control capability를 모델에게 on-demand tool로 제공한다. runtime status를 transcript에 매 turn 주입하지 않고 models/session/capabilities tool로 조회하게 한 것은 context cache와 재현성 관점에서 좋다.

    15.3 trust와 containment

    bundled internal server는 auto-trusted이고 external server는 connect 전에 explicit trust를 요구한다. 그러나 trust는 “이 process/server와 통신하도록 허용”이지 sandbox가 아니다.

    • stdio server는 host user 권한의 local process다.
    • remote server는 전달받은 prompt/tool argument를 외부 network로 보낼 수 있다.
    • OAuth/header/env secret의 lifecycle은 connector별 설정과 process environment에 의존한다.

    여기서 Farad는 이미 중요한 방어를 한다. build_mcp_trust_request()는 server name만 저장하지 않고 transport, command, args, env, URL, headers 전체를 canonical JSON으로 만든 SHA-256 trust_key에 approval을 결합한다. config가 바뀌면 기존 승인이 자동으로 일치하지 않는다. mcp/approval.py:31-65, 108-129 [A]

    남는 한계는 config fingerprint와 executable content identity가 같지 않다는 점이다. 같은 command path가 가리키는 binary/script 내용이나 marketplace checkout이 in-place로 바뀌면 command 문자열은 그대로일 수 있다. 따라서 현재 trust를 “정의 변경 감지”로 높게 평가하되, 공급망 provenance가 필요한 install source에는 resolved commit/content digest를 추가하는 것이 맞다. [A][D]

    16. Session과 persistence

    16.1 session taxonomy

    모든 대화는 Session이고 session_type으로 AGENT, CHAT, SCHEDULED, SUBAGENT를 구분한다. root, schedule run, subagent의 디렉터리 layout은 다르지만 SessionManager가 identifier containment와 lookup을 통합한다. SessionPairFactory가 UiSession/AsyncSession pair lifecycle을 일원화한다. [A][B]

    SessionMetaStore는 session.json과 session.meta.json을 다루며 path별 lock, mtime validation, 최대 10,000 entry cache를 사용한다. write는 temp+replace다. SessionManager도 session-dir/transcript-size cache를 최대 10,000개 유지한다. session_store.py:28-50, 71-157, 187-305; session.py:366-592 [A]

    16.2 hinted lookup과 10k

    scheduled/subagent session은 type·parent 등 lookup hint가 있으면 정확한 path를 O(1)에 가깝게 찾는다. hint가 없는 cold miss는 schedule/subagent tree glob으로 갈 수 있다. 문서와 테스트는 hot path에서 hint를 잃지 않도록 fail-expensive-fallback guard를 둔다. [A]

    list_sessions는 모든 session metadata를 scan/parse/sort하는 explicit O(N) operation이다. sidebar 반복 경로는 대신 state/session_index.jsonl 파생 인덱스를 사용한다. index는 list/group에 필요한 digest를 한 sequential read로 가져오고, append delta와 mtime/size signature로 reconcile하며 self-compact한다. session_index.py:1-23, 149-270 [A]

    이것은 NFS 비용 모델을 실제 코드로 옮긴 좋은 사례다.

    • list view용 field를 index에 포함
    • content는 lazy materialize
    • stat-first validation
    • cache corruption 시 rebuild 가능한 derived state
    • UI click마다 metadata file N개를 읽지 않음

    ProjectStore도 project catalog를 한 index로 읽고 instruction body는 project별 bounded LRU에서 lazy read한다. [A]

    16.3 남은 persistence 위험

    • SessionMetaStore도 atomic replace 뒤 fsync하지 않는다.
    • unhinted cold lookup과 explicit list_sessions가 반복 경로로 새어 나오지 않도록 call-site guard가 계속 필요하다.
    • SessionPairFactory.open은 config/permission scope list 일부를 Qt에서 sync read한다.
    • session delete의 recursive removal은 unbounded지만 explicit one-shot이므로 허용 가능하다.
    • branch는 staging 후 atomic publish를 사용해 중간 상태 노출을 줄인다.

    SessionPairFactory close는 UI registry removal 뒤 async unregister를 예약하므로 문서가 말하는 완전한 원자적 pair removal과는 작은 시간차가 있다. 현재 single Qt owner에서는 실질 문제가 작지만 lifecycle invariant를 테스트로 표현하는 편이 낫다. [A][D]

    17. Skills, plugins, connectors, marketplace

    17.1 CapabilityCatalog

    CapabilityCatalog는 QObject 기반 SSOT로 builtin tools, active/searchable MCP tools, SkillTool, agent types를 합성한다. generation, derived cache, batch invalidation, scope별 invalidation, item_exposure_changed를 제공한다. UI가 registry list를 자체 cache하지 않고 catalog generation을 읽는 구조는 explicit refresh와 잘 맞는다. [A]

    노출 상태 Off / Searchable / Active는 단순 enable flag보다 좋다.

    • Active: prompt/tool schema에 바로 노출
    • Searchable: 필요 시 capability search로 찾음
    • Off: 제외

    큰 capability 집합이 매 turn tool schema와 prompt token을 폭증시키지 않게 한다.

    17.2 Skill

    Skill은 발견된 SKILL.md instruction을 shared SkillTool로 모델에 제공한다. 호출 결과는 instruction text이며 skill 자체가 Python code를 직접 실행하는 ABI는 아니다. max weighted character budget은 약 36k이고 초과 시 partial preview를 반환한다. skills/skill_tool.py:35-176 [A]

    이 모델은 instruction package와 executable tool을 구분한다는 장점이 있다. 단, skill instruction이 모델에게 Bash/MCP를 쓰게 할 수 있으므로 trust risk가 0은 아니다. Skill source provenance와 exposure를 UI에서 계속 보여줘야 한다.

    17.3 Plugin

    Plugin은 arbitrary in-process Python plugin이 아니라 skills, agent definitions, connector/MCP config, hook metadata를 묶는 data/config bundle이다. commands는 skill surface로 통합된다. plugins/models.py:38-67 [A]

    이 선택은 ABI 안정성과 app crash isolation에 유리하다. 그러나 plugin hook이 실제 settings cascade hook execution과 어디서 합쳐지는지는 현재 wiring에서 명백하지 않았다. loader가 PluginHookDef metadata를 발견·표시하는 것과 HookRunner가 settings hook을 실행하는 것은 확인했지만, 모든 plugin hook이 production turn에 자동 실행된다고 단정할 직접 연결은 찾지 못했다. 이 부분은 문서에 “discovered metadata / executable wiring” 상태를 구분해 써야 한다. [A]

    17.4 Marketplace

    Marketplace install은 많은 경우 source item을 Farad-owned immutable copy로 pin하지 않고 source path를 등록해 skills/plugins/agents를 직접 읽는다. connector도 source와 user config를 등록한다. marketplace/installer.py:153-174, 271-309, 365-388 [A]

    개발 중 즉시 갱신과 storage 절약에는 좋지만 공급망 관점에서는 다음 문제가 있다.

    • enable/trust 뒤 source path 내용이 in-place로 변경될 수 있음
    • source가 NFS/Git checkout이면 reproducibility가 약함
    • executable connector/hook command가 바뀌어도 동일 marketplace identity로 보일 수 있음
    • rollback할 설치 artifact가 없음

    최소한 install record에 source URI/path, resolved commit 또는 content digest, manifest digest, install time을 기록해야 한다. executable fingerprint가 바뀌면 trust를 다시 요구하고, instruction-only change는 provenance warning으로 좁힐 수 있다. [D]

    scanner는 unsafe relative component와 symlink containment를 방어하므로 path traversal 기본기는 갖춰져 있다. [A]

    18. Subagent와 background work

    18.1 SubAgentManager

    SubAgentManager는 agent identity/tree/roster, pending/running records, delivery, restore를 관리한다. 기본 soft concurrency 4, hard cap 32, spawn depth 1, pending run 10,000, foreground waiter 10,000 등 명시적 bound가 있다. event mutation은 async loop로 marshal되고 session/team별 background activity count는 O(1) index를 사용한다. terminal actor는 hot registry에서 evict하되 ghost metadata를 남긴다. [A]

    restore는 direct index를 사용해 hot path에서 SessionManager.list_sessions(SUBAGENT) 전량 scan을 피한다. startup cold restore만 의도적으로 scan한다. 테스트는 expensive fallback이 호출되면 fail하도록 구성되어 있다. subagents/manager.py:179-256, 488-523, 2366-2514 [A]

    남은 scale issue는 pending queue다.

    • _pending_run_ids가 list이므로 remove/index가 O(N)
    • admission의 running/pending/foreground count가 current_records()를 매번 materialize하고 반복 scan함
    • _drain_pending_queue()는 list copy를 순회하면서 원본 list에서 반복 remove()하므로 다수 admission/cleanup 시 O(N²)까지 갈 수 있음
    • max pending 10,000을 실제 지원한다면 cancellation/queue position update가 체감될 수 있음

    근거: subagents/manager.py:353-443, 1171-1187, 1923; subagents/run_registry.py:153-159 [A]

    또 하나는 skill injection 경로다. _load_skill_blocks()는 spawn 때마다 discover_all_skills(folder)를 직접 호출해 전 후보를 순회하고 shadow rank를 다시 고른다. 이 경로는 CapabilityCatalog/SkillRegistry의 folder cache와 exposure snapshot을 사용하지 않으므로, NFS discovery가 agent tool hot path에 새어 나오고 UI/catalog가 보는 selection과 subagent prompt가 보는 selection의 authority가 갈릴 수 있다. subagents/manager.py:63-90, 1028-1035 [A]

    active hard cap 32 덕분에 일부 hot actor scan은 사실상 bounded다. 반면 pending 10,000은 문서상 허용치이므로 OrderedDict/intrusive queue와 scope·status별 O(1) counters로 바꿀 근거가 있다. skill body는 spawn request가 받은 registry generation의 immutable snapshot에서 resolve해야 한다. tests는 10k queue drain 중 list.remove/전량 record materialization/skill filesystem discovery가 호출되면 fail하도록 만드는 편이 맞다. [A][D]

    round finalization도 thread 경계상 주의가 필요하다. mark_round_complete()는 MainWindow/Qt thread에서 호출되며, 그 안에서 round transcript load_since(), 최종 output/stats 계산, output file write_text(), session metadata 갱신이 동기 실행된다. timestamp가 있어 transcript read 범위는 보통 해당 round로 제한되고, output path containment도 검증되지만, 긴 round나 NFS workflow root에서는 UI를 막을 수 있다. subagents/manager.py:1436-1530, 718-779, 1741-1756 [A]

    개선 시에도 “output file이 존재한 뒤 foreground waiter를 깨운다”는 commit ordering은 보존해야 한다. Qt 밖의 serialized finalization worker가 transcript/output commit receipt를 만든 뒤 Qt에는 bounded status snapshot만 전달하는 구조가 적합하다. [D]

    18.2 BackgroundTaskManager

    background shell manager는 running dict, terminal result LRU 128, 두 lane deque, pending dict 최대 10,000, session activity counter를 쓴다. spawn/admission과 head-only drain은 대체로 O(1) 또는 freed-slot 수에 비례한다. output은 hard cap 64MiB, completion tail 8KiB이고 hard cap 도달 시 process를 종료한다. process group cancellation도 제공한다. background_shell.py:183-366, 881-1068 [A]

    session-wide cancel은 pending queue를 scan할 수 있지만 사용자가 명시적으로 session을 정리하는 one-shot 경로라면 허용 가능하다. temp-root TTL cleanup은 constructor에서 sync scan하므로 파일이 비정상적으로 많이 쌓이면 startup 영향을 줄 수 있으나 기본 위치가 local temp라는 점에서 NFS 위험은 낮다. [A][D]

    19. Scheduler

    19.1 semantics는 강하다

    SchedulerEngine은 하나의 60초 QTimer로 due run을 감지한다. overlap SKIP/QUEUE/REPLACE, missed-run policy, pre-check, one-shot, max run, auto-disable를 처리한다. ScheduleExecutor는 각 run을 독립 SCHEDULED Session으로 만들고 다음 순서를 지킨다. [A]

    1. RUNNING state를 먼저 persist
    2. unattended permission/attendance policy 적용
    3. SessionWorkflowService를 통해 일반 AsyncSession/query_loop 경로 진입
    4. hard timeout과 cancel
    5. terminal phase idempotent transition
    6. child/background teardown
    7. terminal persist retry와 orphan recovery

    scheduled run이 별도 “간이 agent loop”를 만들지 않고 일반 runtime을 재사용하는 점이 좋다. 실행 결과가 session transcript로 남아 resume·diagnostics와 같은 도구를 쓸 수 있다.

    ScheduleHistoryStore는 append-only/paged history, bounded repair lane, schedule metadata aggregate를 사용한다. 100k history에서도 reverse page가 bounded되도록 테스트한다. [A]

    19.2 10k 치명적 hot path

    반면 due detection은 현재 10k 계약을 명백히 위반한다.

    • QTimer tick은 Qt 메인 스레드에서 실행된다.
    • 매 tick ScheduleStore.list_tasks()를 호출한다.
    • list_tasks는 모든 schedule path를 순회하고 task를 정렬한다.
    • 각 task load는 schedule.json stat과 history.signature() 확인을 수행한다.
    • path listing 자체가 directory mtime cache를 쓰더라도 per-file stats는 남는다.

    관련 근거: scheduler/engine.py:58-95, 239-286; scheduler/store.py:141-158, 842-886 [A]

    warm listing cache를 전제로 정적 비용을 풀면 다음과 같다. directory listing 자체는 schedule directory signature 하나로 재사용되지만, list_tasks()는 각 task의 metadata path에 stat()을 하고 _history_signature()를 통해 history path에도 stat()을 시도한다. 그 뒤 10,000개 next_run_at을 parse/비교하고 전체 task list를 sort한다. 따라서 N=10,000 steady tick의 근사치는 directory stat 1회 + metadata stat 10,000회 + history stat 시도 10,000회 + 10,000개 due loop + O(N log N) sort다. 파일이 없거나 OS cache가 있어 실제 syscall 비용은 달라지지만, 알고리즘과 호출 수 자체는 source에서 도출된다. scheduler/store.py:930-942; scheduler/history_store.py:67-75 [A][D]

    NFS attribute cache가 있어도 UI freeze와 shared filesystem 부하를 피하기 어렵다. scheduler test는 due semantics와 cron policy를 폭넓게 검증하지만, test_scheduler.py:2060-2113 부근의 hot-path guard는 cron validator 같은 일부 비싼 fallback만 막는다. 10k steady tick에서 list_tasks, per-task stat, sort가 호출되면 fail하는 regression test는 찾지 못했다. [A]

    이 문제의 올바른 해결은 timer interval을 늘리는 것이 아니다.

    • ScheduleStore가 next_due_at, enabled, overlap에 필요한 최소 field를 단일 derived index로 유지
    • in-memory min-heap 또는 ordered due index에서 다음 시각만 조회
    • in-app schedule write 직후 해당 task만 index/heap update
    • external reconcile은 startup/explicit refresh worker에서 stat sweep
    • timer tick은 O(number of due tasks × log N)
    • UI thread에는 due id list만 전달하고 I/O/parse는 worker 또는 async service에서 수행
    • 테스트는 tick 중 list_tasks/full scan 호출 시 fail

    이것이 현재 Farad에서 가장 우선순위가 높은 성능 수정이다.

    19.3 check command

    schedule pre-check command는 max worker 2의 thread pool, timeout, bounded output을 사용해 Qt를 직접 막지 않는다. 다만 host user 권한으로 실행되는 unsandboxed command이고 Path.expanduser 사용이 남아 있다. scheduled BYPASS를 선택하면 UI도 위험을 명시하지만, unattended execution과 OS containment 부재의 결합은 운영자가 명확히 이해해야 한다. [A]

    20. Provider abstraction과 client lifecycle

    20.1 장점

    hvppyai Provider Protocol은 provider wire translation을 SDK에 캡슐화한다. Farad의 TurnContext는 model별 context window, max output, reasoning, image input, sampling, admission profile을 endpoint metadata에서 해석하고 query loop는 provider-neutral request/event를 사용한다. 주요 LLM 호출은 모두 streaming이다. [A]

    이 구조 덕분에 Farad는 특정 vendor CLI의 내부 model protocol에 제품 전체가 결박되지 않는다. GLM/Kimi/OpenAI-compatible/Ollama/Anthropic 계열을 같은 runtime semantics에 넣을 수 있다.

    20.2 ModelSelection의 전역 mutable authority

    ModelSelection은 current endpoint, current model, client 하나를 전역으로 소유한다. session turn이 다른 model을 요청하면 ensure_client_for_model이 global endpoint/model을 바꾸고 _client=None으로 만든 뒤 새 AsyncHvppyAI를 생성한다. 이전 client를 close하지 않는다. app/services.py:172-258, 374-449 [A]

    동시에 실행 중인 turn은 이미 local TurnContext에 이전 client reference를 갖고 있으므로 즉시 깨질 가능성은 낮다. 그러나 session A/B가 endpoint를 번갈아 쓰면 client와 httpx connection pool이 반복 생성되고 명시적으로 회수되지 않는다. shutdown은 현재 ModelSelection.client 하나만 닫는다. shutdown.py:308-316 [A][D]

    또한 RunReadinessBuilder가 ensure_client()로 client를 만든 뒤 TurnContextProvider가 다시 session model을 해석해 ensure_client_for_model을 호출한다. readiness의 llm_client field는 실제 query에 사용되지 않는다. global selection churn과 불필요한 client 생성 가능성을 키운다.

    repository-wide llm_client 사용 검색에서도 RunReadiness.llm_client는 생성·저장 외 consumer가 없다. 더구나 readiness는 asyncio runtime loop에서, MainWindow endpoint refresh/model picker는 Qt thread에서 같은 ModelSelection의 _endpoints, _current_endpoint, _model, _client를 만질 수 있는데 명시적 owner-thread assertion이나 lock이 없다. 현재 CPython reference assignment에 기대어 큰 사고가 안 보이는 것과 lifecycle authority가 올바른 것은 다르다. app/runtime/run_readiness.py:20-84; app/runtime/turn_context_provider.py:399-420; app/main_window/window.py:3292-3302 [A][D]

    권고는 endpoint credential/config fingerprint를 key로 한 ClientPool이다.

    • key: provider, wire API, base URL, auth identity, relevant headers, timeout/retry
    • value: ref-counted 또는 idle-TTL AsyncHvppyAI
    • TurnContext가 immutable client lease와 model을 소유
    • UI model picker selection은 default selection일 뿐 active turn authority를 변경하지 않음
    • shutdown은 pool 전체를 await close
    • endpoint config refresh는 stale key를 retire하고 active lease 종료 뒤 close

    필수 회귀 테스트는 (1) endpoint/model 교체 시 retired client가 정확히 한 번 close, (2) in-flight turn lease는 picker 변경에도 유지, (3) shutdown이 pool 전부 close, (4) readiness snapshot과 실제 TurnContext client key 일치다. 현재 provider/query tests는 넓지만 이 lifecycle 계약을 고정하는 테스트는 찾지 못했다. [A][D]

    20.3 미완 경로

    • command_bearer auth는 RuntimeError로 명시적 미구현이다. app/services.py:427-428 [A]
    • query_loop fallback machinery는 있으나 production TurnContext의 fallback_model은 빈 문자열이다. [A]
    • Model speed/health는 자동 selection에 쓰지 않고 UI와 internal MCP advisory로만 제공한다. 이는 runtime metadata를 transcript에 넣지 않는 계약과 일치한다. [A][B]

    21. UI·terminal·desktop rendering

    21.1 UI authority와 rendering 선택

    Farad UI는 browser shell이나 Electron surface가 아니라 native PySide6 widget tree다. 표준 form·panel·dialog는 QWidget/QSS를 쓰고, 대량 반복 surface에만 custom painting을 제한한다. 제품 규약과 실제 구현이 일치하는 대표 경로는 다음 둘이다. [A][B]

    • TimelineView: QAbstractScrollArea 위에 message element layout, visible-range paint, selection/hit-test/copy를 같은 text model로 처리
    • SessionListWidget: fixed-row virtual scrolling과 flyweight state로 visible row만 materialize/paint

    TimelineView는 scroll offset, search generation, selection anchor, active-effect dirty rect를 view 하나가 소유한다. 이전 transcript page는 UiSession/ChatPanel이 명시적으로 요청하고, canvas는 visible region만 다시 그린다. ui/widgets/timeline_view/timeline_view.py:203-300 및 canvas 계열 [A]

    SessionListWidget은 row마다 QWidget을 만들지 않는다. viewport height와 scroll offset에서 first/last visible row를 계산하고, busy animation도 해당 row rect만 invalidate한다. project tree도 visual-unit index를 통해 visible range를 구한다. ui/panels/sidebar_panel.py:2290-2320, 2900-2975 [A]

    이 선택은 공유 HPC·원격 X11·저사양 PC라는 배포 목표에 맞다. WebView process, DOM layout, row별 QObject explosion을 피하며, session 10,000개를 전부 widget으로 보유하지 않는다. 반면 custom canvas는 paint·hit-test·selection·accessibility가 갈라지기 쉬우므로 selection surface invariant와 회귀 테스트가 일반 QWidget보다 훨씬 중요하다. [A][D]

    21.2 hvppyterm

    hvppyterm은 Farad와 독립된 embeddable package다. PTY bytes를 즉시 전부 parse하지 않고 33ms cadence로 coalesce하며, pending burst는 callback당 64KiB만 처리하고 나머지는 zero-delay timer로 양보한다. paint는 event rect가 가리키는 visible terminal rows만 순회하고 dirty cursor rows만 invalidate한다. packages/hvppyterm/hvppyterm/widget.py:37-48, 445-503 [A]

    SidebarPanel 6,700여 lines, MainWindow 3,700여 lines, CustomizePanel 3,800여 lines, ChatPanel 2,900여 lines는 변경 충돌과 lifecycle 추론 비용이 크다. 다만 파일 길이만 보고 widget을 쪼개면 signal relay와 wrapper가 늘 수 있다. 분해 기준은 다음 authority여야 한다. [D]

    • config path, HOME mismatch, filesystem type/NFS, session index, API log corpus, capability generation, model, scheduler, crash trace, tool run을 묶는 bounded operational diagnostics snapshot

    API log write가 asyncio.to_thread()로 event loop 밖에서 수행된다는 점은 특히 중요하다. 같은 AsyncSession 안에서 transcript append는 sync로 남아 있으므로, 이미 프로젝트 내부에 “ordering은 await하되 blocking filesystem work는 thread에서 실행”하는 선례가 존재한다. app/runtime/async_session.py:1518-1595 [A]

    관측성의 빈칸도 명확하다.

    1. Qt stall monitor는 env/perf opt-in이고, 단일 asyncio runtime loop의 heartbeat/stall은 동등하게 직접 측정하지 않는다.
    2. session_id/run_id/llm_call_id는 존재하지만 log·tool·MCP·filesystem span을 하나의 trace tree로 묶는 강제 correlation contract는 없다.
    3. scheduler tick의 stat 수, ConfigProvider tier stat 수, transcript queue wait 같은 NFS budget counter가 없다.
    4. local desktop 제품이므로 분산 telemetry가 반드시 필요한 것은 아니지만, support snapshot만으로 “어느 owner thread가 몇 ms 막혔는가”를 재구성하기 어렵다.

    권고는 무거운 원격 APM을 먼저 넣는 것이 아니다. Qt와 asyncio 각각에 heartbeat를 두고, hot-path span에 owner thread·session/run id·filesystem operation count를 넣으며, diagnostics가 최근 stall과 budget violation을 bounded ring buffer로 보여주게 하면 된다. [D]

    22.3 실패가 감춰지는 곳

    • TranscriptStore index corruption은 empty index로 축소
    • malformed JSONL은 조용히 skip
    • initial transcript load failure 시 AsyncSession은 log 후 empty transcript로 진행
    • MCP readiness failure는 background task log와 snapshot 상태로 남지만 turn UI 단계 표현이 약함
    • hook timeout이 descendant process 전체 종료를 보장하지 않음
    • endpoint/settings auto refresh의 Qt blocking을 diagnostics는 interval로만 보여주고 contract violation은 표시하지 않음

    25. 우선순위 권고

    이 단독 감사의 우선순위는 최종 교차 종합을 반영한 06 로드맵이 권위다. 아래 항목도 그 최종 판정에 맞춰 P0/P1을 정규화했다.

    P0 — 다음 architecture tranche에서 반드시 처리

    Final P0-2. Scheduler next-due index

    목표는 1분 tick에서 전체 schedule read/stat/sort를 없애는 것이다.

    • schedule derived index에 due 판단 최소 field 저장
    • in-memory min-heap
    • write-through targeted update
    • startup/explicit worker reconcile
    • Qt tick에서 full list 호출 금지 guard test

    효과: NFS 10k 계약 회복, UI freeze 제거, 공유 장비 부하 감소.

    Final P0-3. Transcript I/O execution boundary

    • session별 serialized I/O executor
    • disk-before-UI commit receipt 유지
    • initial max ID/index checkpoint로 double scan 제거
    • rewind-aware projection index
    • corruption rebuild/quarantine

    효과: 한 session의 NFS I/O가 모든 async session을 막는 문제 제거.

    Final P0-4. Refresh truth 단일화

    • 5분 SettingsService timer 제거
    • ConfigProvider cached get과 explicit reconcile 분리
    • per-turn mtime stat 제거
    • 20분 endpoint 강제 재해석 callback 제거 또는 공식 예외화; 향후 network discovery를 실제 연결하면 worker화
    • readiness/runtime/TurnContext의 중복 resolve 제거
    • docs/layers.md, docs/config.md, docs/architecture.md를 구현과 동시에 수정

    효과: 팀이 같은 architecture contract를 보고 개발할 수 있음.

    Final P0-1. Security truth와 execution seam

    • permission을 “policy, not sandbox”로 문서/UI에서 일관되게 정의
    • .git/.env guard가 Edit/Write 한정임을 명시
    • Bash/background/hook과 stdio MCP server spawn을 위한 ExecutionBoundary Protocol
    • HTTP/SSE MCP의 원격 side effect는 local sandbox가 아니라 trust/credential/permission으로 구분
    • sandbox capability detection과 future platform adapter point
    • 최소 한 지원 platform adapter에서 prohibited read/write/network integration test 통과
    • hook descendant process cancellation 보강

    효과: 기능이 없는 sandbox를 암묵적으로 약속하는 위험 제거, 향후 containment 구현 기반.

    P0 — 같은 correctness/security tranche에서 계속

    Final P0-6. endpoint-keyed ClientPool

    전역 client 하나를 turn-scoped lease로 교체하고 모든 client를 lifecycle에서 close한다. immutable RuntimeSnapshot에는 live lease가 아니라 selection key/generation만 두며, RunReadiness는 client를 생성·보관하지 않는다. TurnContext admission에서 한 번 acquire/release한다. production fallback은 SPEC상 실제 지원 요구가 있으면 같은 lease 계약으로 wiring하고, 아니면 scaffold·UI·문서에서 완성 기능처럼 표현하지 않는다.

    Final P0-5. 완전한 Qt/async snapshot boundary

    permission cascade와 PostBox startup ingress의 direct access를 제거한다. immutable snapshot publication과 async request/result를 사용한다.

    Final P0-3 continuation. Transcript integrity contract

    fsync policy를 NFS 비용과 함께 명문화하고 index validation/rebuild, corruption diagnostics, read-only recovery를 추가한다.

    Final P0-4 continuation. Snapshot-first MCP readiness

    최종 제품 결정은 Snapshot-first다. core settings/endpoint/model snapshot generation 1 전에는 prompt admission을 막되, optional MCP는 typed generation-0 empty/stale snapshot으로 시작하고 slow reconcile을 기다리지 않는다. 현재 wait=True 동작은 제거한다.

    Final P0-7. NSS account-home correctness

    runtime/turn/scheduler의 account-relative path를 passwd/NSS helper로 통일하고 mismatched $HOME fixture로 permission, cwd, storage 경계를 고정한다.

    Final P0-4 continuation. cold registry scan worker화

    explicit refresh라는 시점 계약에 “disk discovery는 Qt/shared event loop에서 실행하지 않는다”는 thread 계약을 추가한다.

    P1 — 응집도·provenance·자료구조

    Final P1-1/P1-2. authority 기준으로 큰 class 분해

    AsyncSession, UiSession, SubAgentManager, MainWindow, SidebarPanel, CustomizePanel을 파일 길이가 아니라 owner/lifecycle/change reason 기준으로 나눈다.

    Final P1-5. marketplace provenance

    source identity, commit/content digest, executable fingerprint를 install record에 남기고 executable change 시 trust를 재확인한다.

    Final P1 continuation. pending queue 자료구조

    SubAgentManager pending list의 remove/index/count를 O(1) 구조로 바꾸고 10k queue guard test를 추가한다.

    P2-조건부 — headless core는 요구가 생길 때

    현재 제품이 desktop-first인 동안 별도 daemon/RPC를 미리 만들 필요는 없다. CI/remote/second UI가 roadmap에 들어올 때 RuntimeHost/PresentationHost를 분리한다.

    28. 최종 판정

    Farad는 네 제품 비교에서 “후발 GUI wrapper”로 분류하면 안 된다. 오히려 다음 영역에서는 자체 architecture가 명확하다.

    • desktop/HPC shared-filesystem deployment
    • provider-neutral SDK와 app-owned agent loop
    • transcript 중심 session truth
    • Qt/async proxy
    • capability exposure와 explicit discovery 구상
    • scheduler/subagent/background work의 제품 통합
    • NFS 파생 인덱스와 10k guard test

    반대로 경쟁 제품과 비교할 때 감점해야 할 영역도 분명하다.

    • GUI process에 runtime이 종속되어 headless surface가 약함
    • OS sandbox가 없음
    • 전역 model client authority와 lifecycle이 약함
    • refresh contract가 구현 내부에서 갈라짐
    • scheduler와 transcript에 큰 반복경로 병목이 있음
    • 대형 orchestration class로 clean boundary가 다시 뭉침

    가장 중요한 로드맵 원칙은 이것이다.

    Farad는 기능을 더 얹기 전에 스스로 선언한 authority·thread·hot path·persistence 계약을 실제 모든 경로에서 같은 의미로 만들어야 한다. Scheduler index, transcript I/O queue, refresh truth, ClientPool, ExecutionBoundary가 그 핵심이다.

    이 다섯 가지를 바로잡으면 Farad의 현재 장점은 유지하면서도 OpenCode·Claude Code·Codex와의 비교에서 “기능은 많지만 runtime foundation이 불안한 제품”이 아니라 “desktop-first라는 명확한 선택을 가진 production architecture”로 평가할 수 있다.
