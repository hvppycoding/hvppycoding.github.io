    1. 결론부터

    Claude Code의 가장 강한 아키텍처적 선택은 완성도 높은 로컬 agent runtime과 공통 agentic behavior를 제품의 중심에 둔 것이다. CLI와 Agent SDK 사이에는 CLI subprocess 재사용이 공식적으로 확인되고, 공식 문서는 IDE·Desktop·Web을 포함한 표면들이 같은 agentic loop의 행동 모델을 제공한다고 설명한다. 다만 이것은 모든 표면이 동일 코드·동일 process kernel을 공유한다는 증거는 아니다. 확인된 code reuse와 제품 수준의 behavioral parity를 구분해야 한다. B, D

    반대로 가장 큰 구조적 비용도 같은 선택에서 나온다. Agent SDK는 가벼운 라이브러리 함수처럼 보이지만 실제로는 query()마다 별도의 claude CLI subprocess를 stdio로 구동하며, 그 프로세스가 shell·working directory·로컬 JSONL session을 소유한다. 즉 Claude Code는 본질적으로 stateful process-local runtime이다. 동시에 실행 중인 Agent SDK session N개는 CLI subprocess N개를 요구하므로, 수평 확장에는 session affinity, working tree 격리, 로컬 상태 hydration, 메모리 상한이 필요하다. 저장된 과거 session N개가 process N개라는 뜻은 아니다. 공식 hosting 문서가 active execution의 이 제약을 직접 설명한다. Agent SDK hosting B

    이 보고서가 내리는 가장 중요한 판정은 “기능이 많다”가 아니다. Claude Code는 agent loop를 제품의 단일 중심 권위로 삼고, UI와 확장을 그 주위에 붙이는 데 성공했다. 다만 실행 상태와 저장 형식이 한 로컬 프로세스에 강하게 붙어 있어, 데스크톱 개인 도구로서는 장점이지만 서버·HPC·NFS 환경에서는 그대로 모방하면 안 된다. D

    2. 범위·버전·증거 경계

    2.1 현재 제품과 내부 관찰의 버전 차이

    2026-07-13에 npm registry를 확인한 결과 @anthropic-ai/claude-code의 latest는 2.1.207 (2026-07-10 게시), stable은 2.1.197(2026-06-30 게시)이었다. npm 설치는 현재 공식 README에서 deprecated로 안내되지만, registry version은 로컬 복원본과 현재 제품 사이의 간격을 확인하는 기준으로 사용했다. 같은 시점 로컬에 설치된 binary는 2.1.206이었다. 따라서 2.1.207은 모든 surface의 실제 배포 build를 뜻하지 않고 문서·복원본의 시간 간격을 표시하는 registry marker다. 공식 저장소, npm registry metadata B

    로컬 packages/claude-code-sourcemap/은 public npm package의 cli.js.map에 포함된 sourcesContent에서 복원한 2.1.88, TypeScript 1,884개 파일의 사본이다. 이 사본을 현재 위치로 옮긴 repository commit은 3815436a54de47649b612002330c505e1d369926 (2026-04-24)이다. 그러나 Claude Code 본체는 일반적인 의미의 공개 OSS 구현 계약이 아니며, 공식 repository의 license도 “All rights reserved”이다. 공식 license C

    따라서 이 보고서는 다음 규칙을 지킨다.

    • 현재 사용자 동작·지원 기능·운영 보장은 공식 문서 B를 우선한다.
    • QueryEngine, tool executor, JSONL 최적화, 전역 상태 같은 내부 구조는 2.1.88 복원본의 관찰 C로만 쓴다.
    • 복원본에 현재보다 늦게 공개된 기능의 feature-gated 코드가 있어도 현재 구현과 동일하다고 승격하지 않는다.
    • 공식 문서와 복원본이 충돌하면 현재 공식 문서를 채택하고 차이를 명시한다.
    • 비공개 코드의 테스트 체계, 배포 backend 내부, Desktop IPC 같은 확인 불가능한 부분은 추측하지 않는다.

    3. 제품 경계와 배포 형태

    3.1 제품이 최적화하는 핵심 작업

    Claude Code가 최적화하는 단위는 “한 번의 completion”이 아니라 repository를 읽고, 계획하고, 도구를 실행하고, 결과를 다시 모델에 공급하는 stateful working session이다. 공식 agent-loop 설명에서 입력은 prompt·system prompt·tools·history이고, 모델이 tool call을 내면 실행 결과를 다시 conversation에 추가해 tool call이 사라질 때까지 반복한다. 마지막에는 usage·cost·session ID를 포함한 result가 나온다. Agent loop B

    이 제품 경계는 다음 결과를 낳는다.

    1. 파일시스템과 shell은 부가 기능이 아니라 runtime state의 일부다.
    2. transcript는 단순 UI history가 아니라 resume·compaction·fork의 기초다.
    3. permission UI는 장식이 아니라 실행 state machine의 한 단계다.
    4. MCP와 skills는 prompt에 문자열을 보태는 것 이상으로 capability graph를 바꾼다.
    5. UI는 agent의 진행·대기·승인 상태를 투영해야 한다.

    4. 핵심 agent loop와 상태 머신

    4.1 공식 동작 계약

    공식 SDK 문서의 loop는 단순하지만 중요한 계약을 가진다.

    stateDiagram-v2
    [*] --> AssembleContext
    AssembleContext --> ModelStream
    ModelStream --> ToolDecision
    ToolDecision --> ExecuteTools: tool_use exists
    ExecuteTools --> AppendResults
    AppendResults --> CompactCheck
    CompactCheck --> AssembleContext: continue
    ToolDecision --> StopHooks: no tool_use
    StopHooks --> Completed: accepted
    StopHooks --> AssembleContext: hook requests continuation
    ModelStream --> Failed: terminal error / cancellation
    AssembleContext --> Limited: maxTurns or maxBudget
    Completed --> [*]
    Failed --> [*]
    Limited --> [*]

    message stream은 init/compact/info/worker shutdown 같은 system message, assistant message, tool result를 담은 user message, raw stream event, final result로 구성된다. maxTurns와 maxBudgetUsd는 무한 반복을 제한하고, final result subtype은 success, max turns, max budget, execution error, structured output retry exhaustion을 구분한다. B

    4.2 복원 소스에서 보이는 실제 loop 구조

    2.1.88 복원본에서는 QueryEngine이 “conversation 하나당 한 instance”로 message, file cache, usage, abort controller를 소유한다. submitMessage()는 같은 instance 안에서 새 turn을 시작하고, query() async generator에 위임한다.

    • packages/claude-code-sourcemap/src/QueryEngine.ts:175 — conversation lifecycle owner 설명
    • packages/claude-code-sourcemap/src/QueryEngine.ts:209 — submitMessage() 진입점
    • packages/claude-code-sourcemap/src/QueryEngine.ts:436 — API 응답 전 user message 선영속화
    • packages/claude-code-sourcemap/src/QueryEngine.ts:675 — query() stream 소비
    • packages/claude-code-sourcemap/src/query.ts:241 — queryLoop()
    • packages/claude-code-sourcemap/src/query.ts:307 — explicit while (true) state machine

    queryLoop()는 immutable params와 iteration 사이에 넘기는 mutable State를 분리한다. state에는 messages, tool context, compact tracking, max-output recovery count, turn count, 직전 transition reason이 있다. 재귀 호출 대신 state = next; continue를 사용하고 terminal reason을 return한다. C

    이 설계의 좋은 점은 다음과 같다.

    • async generator가 model stream, progress, tool result, compact boundary를 호출자에게 순차 노출한다.
    • continue reason이 명시되어 recovery path를 테스트할 수 있다.
    • 사용자 메시지를 model request 전에 transcript에 써 kill 직후에도 resume 가능성을 높인다.
    • recoverable API error를 곧바로 SDK client에 노출하지 않고 내부 recovery가 끝난 뒤 terminal error만 보낸다.
    • tool result와 attachment를 다음 iteration의 message에 합쳐 loop invariants를 한곳에서 유지한다.

    그러나 완전한 순수 state machine은 아니다. query.ts는 process-wide bootstrap state, feature gate, settings, telemetry, queue 등 많은 ambient dependency를 읽는다. 최근 구조에는 QueryDeps로 model call·microcompact·autocompact·UUID 네 가지를 주입하는 seam이 생겼지만, 주석 자체가 “scope is intentionally narrow”라고 밝힌다. packages/claude-code-sourcemap/src/query/deps.ts:1 C

    4.3 streaming tool execution

    복원본의 StreamingToolExecutor는 assistant response가 모두 끝난 뒤에만 tool을 시작하는 구조가 아니다. 완성된 tool_use block을 stream 중 파악해 schema를 검증하고 concurrency-safe call을 queue/run한다. getCompletedResults()는 앞선 concurrency-safe call이 아직 실행 중이어도 뒤에서 먼저 끝난 safe call의 결과를 내보낼 수 있다. 따라서 모든 결과의 model 선언 순서를 보존한다고 일반화하면 안 된다. 대신 unsafe call은 exclusive barrier가 되고, side-effect-sensitive context modifier는 필요한 순서로 적용된다. 이는 긴 model stream과 tool latency를 일부 겹치는 지연 최적화다.

    • packages/claude-code-sourcemap/src/services/tools/StreamingToolExecutor.ts:35
    • packages/claude-code-sourcemap/src/services/tools/StreamingToolExecutor.ts:104
    • packages/claude-code-sourcemap/src/services/tools/StreamingToolExecutor.ts:412 C

    이 최적화의 대가는 cancellation, permission wait, tool-result ordering, context modifier 병합이 훨씬 어려워진다는 점이다. 이 복잡성을 executor 한곳에 모아 둔 것은 합리적이지만, 임의의 tool이 concurrency-safe를 잘못 선언하면 안전성이 무너질 수 있어 기본값을 conservative하게 해야 한다. 실제 buildTool() 기본값은 concurrency-safe와 read-only를 모두 false로 둔다. packages/claude-code-sourcemap/src/Tool.ts:743 C, D

    5. 상태·권위·데이터 흐름

    Claude Code를 이해할 때 가장 유용한 구분은 “무엇이 어디의 권위인가”다.

    상태 실질적 권위 생명주기 비고
    현재 agent turn CLI agent-loop process memory; 2.1.88 SDK/headless에서는 QueryEngine process·session model stream과 tool execution을 직렬화
    대화 이력 로컬 project별 JSONL session 이후 유지 resume/fork/compact chain의 기반
    실제 코드 상태 working directory filesystem/git session과 독립 transcript를 resume해도 filesystem은 자동 복원되지 않음
    file checkpoint editing tool이 만든 snapshot session/checkpoint Bash나 외부 editor 변경은 포착하지 않음
    effective permission merged settings + mode + runtime prompt + hook tool call deny > ask > allow, hook은 추가 차단 가능
    context window 현재 request에 조립된 prompt/message/tool schema API request transcript 전체와 동일하지 않음
    model memory CLAUDE.md + auto memory + invoked skill context session/turn enforcement가 아니라 model context
    MCP capability 각 MCP server의 advertised state + client cache connection/session list_changed로 동적 갱신 가능
    external SessionStore 로컬 transcript의 durable mirror cross-host local-first; file state와 memory는 미러하지 않음
    background roster per-user supervisor state files machine user 각 child session transcript와 분리

    이 구조에서 JSONL은 “모든 것의 event store”가 아니다. conversation을 복구하지만 git tree, shell의 외부 side effect, MCP external state, memory files까지 transaction으로 묶지 않는다. resume은 agent의 지식 상태를 복구할 뿐 세계 상태를 원자적으로 되돌리지 않는다. 공식 SDK session 문서도 session은 conversation을 보존하고 filesystem은 보존하지 않는다고 명시한다. SDK sessions B

    6. context 조립, transcript, compaction, prompt cache

    6.1 서로 다른 네 층을 구분해야 한다

    Claude Code에서는 다음 네 대상을 같은 것으로 보면 안 된다.

    1. Raw transcript — user/assistant/tool/system record를 담은 로컬 JSONL.
    2. Active conversation chain — branch·rewind·compaction을 반영해 다음 request에 이어질 logical path.
    3. Request context — active history에 system prompt, tool definitions, CLAUDE.md, skills 등을 합친 것.
    4. Provider prompt cache — 매 request의 exact stable prefix가 이전 request와 같을 때 재사용되는 계산.

    7. 세션 저장, resume, branch/fork, checkpoint

    7.1 기본 session model

    local session은 ~/.claude/projects/<project>/...jsonl에 연속 저장된다. 공식 CLI는 --continue, --resume, /resume, session name을 제공하고, current worktree·repository·all projects 범위에서 session을 찾는다. 기본 cleanup은 30일이며 cleanupPeriodDays로 조정할 수 있다. history write를 끄려면 CLAUDE_CODE_SKIP_PROMPT_HISTORY, headless의 --no-session-persistence, SDK의 persistSession: false를 사용한다. CLI sessions, Settings B

    resume와 fork의 차이는 명확하다.

    • resume: 같은 session ID와 history 뒤에 append한다.
    • fork/branch: 기존 history를 복사해 새 session ID에서 갈라진다.
    • session-scoped permission approval은 branch에 따라오지 않는다.
    • 같은 session ID를 두 terminal에서 동시에 resume하면 message가 하나의 JSONL에 interleave될 수 있다. 공식 문서가 경고하는 실제 concurrency hazard다. B

    복원본은 단순한 배열 dump가 아니라 message별 UUID와 parentUuid를 가진 append-oriented chain을 쓴다. compact boundary는 physical parent를 끊고 logicalParentUuid로 이전 tail을 가리킬 수 있다. tool result는 해당 assistant tool-use UUID를 parent로 연결한다.

    7.3 file checkpoint는 VCS가 아니다

    Claude Code는 user prompt마다 file checkpoint를 만들고 code와 conversation을 따로 rewind할 수 있다. 그러나 checkpoint는 built-in file editing tool로 한 변경만 추적한다. Bash command, 외부 editor, concurrent process가 바꾼 파일은 추적하지 않는다. 공식 문서도 checkpoint는 version control의 대체가 아니라고 명시한다. Checkpointing B

    따라서 정확한 복구 모델은 다음과 같다.

    conversation resume != filesystem rollback
file checkpoint       != git history
session fork          != worktree isolation

    서로 다른 branch를 실제로 동시에 수정한다면 session fork와 별개로 git worktree를 사용해야 한다.

    7.4 external SessionStore

    Agent SDK의 SessionStore는 append와 load, 선택적으로 list/delete/listSubkeys를 구현한다. 중요한 운영 계약은 local-first dual write다.

    1. CLI subprocess가 먼저 local JSONL에 쓴다.
    2. SDK가 batch를 external store로 전달한다.
    3. store가 reject하면 짧은 backoff를 포함해 총 세 번까지 보내지만 timeout은 retry하지 않는다.
    4. 끝내 실패하면 mirror_error를 stream에 내보내고 agent query는 계속된다.
    5. store는 transcript만 미러하며 memory와 working-directory artifacts는 별도다.

    Agent SDK hosting, Session storage B

    가용성을 우선한 합리적인 선택이지만 external store를 audit-grade canonical log로 생각하면 안 된다. mirror_error 감시가 없으면 local은 성공하고 remote durability만 조용히 유실될 수 있다. D

    9. Permission, hooks, sandbox, 보안 경계

    9.1 permission과 sandbox는 다른 층이다

    Claude Code의 보안 구조는 다음 세 층을 구분한다.

    1. Permission policy — 어떤 tool/input을 allow, ask, deny할지 결정.
    2. Lifecycle hook — 실행 전후에 조직 정책·검증·logging을 삽입.
    3. OS sandbox — Bash와 그 child process가 실제 filesystem/network boundary를 넘지 못하게 강제.

    permission은 모든 tool에 적용될 수 있지만 policy decision이고, sandbox는 Bash descendants에 대한 OS-level enforcement다. Read/Edit 같은 in-process file tool은 sandbox가 아니라 permission path로 통제된다. Permissions, Sandboxing B

    9.2 rule과 mode

    permission rule 우선순위는 deny > ask > allow다. managed settings가 가장 높은 configuration scope를 가지며, explicit deny는 다른 scope의 allow를 이긴다. PreToolUse hook은 permission prompt 전에 실행되고 exit code 2로 tool을 막을 수 있으며, allow rule이 있어도 hook 차단을 우회하지 못한다. B

    현재 permission mode는 다음과 같다.

    mode 의미
    default / Manual read 중심, 추가 action은 prompt/rule 평가
    acceptEdits project 내부 file edit와 일부 filesystem command 자동 승인
    plan read-only 조사·계획
    auto 별도 classifier가 action 안전성을 검토해 승인 여부 결정
    dontAsk pre-approved action만 실행하고 나머지는 묻지 않고 거부
    bypassPermissions permission prompt를 우회하는 고위험 모드; explicit deny/ask 일부는 별도 계약 유지

    Permission modes B

    auto mode classifier는 hostile content, scope 이탈, destructive infrastructure action 등을 검토하지만 공식 문서도 안전 보장이 아니라고 명시한다. classifier가 unavailable이면 fail-open하지 않고 action을 막는다. Errors B

    9.3 sandbox

    native sandbox는 macOS Seatbelt, Linux/WSL2 bubblewrap와 외부 network proxy를 사용한다. 기본 write 범위는 cwd, 기본 read는 일부 deny path를 제외한 넓은 범위이며, outbound network는 allowed domain과 prompt로 통제한다. built-in proxy는 hostname을 기준으로 허용하고 TLS 내용을 검사하지 않는다. 따라서 broad domain allowlist, domain fronting, privileged Unix socket, 과도한 write path는 여전히 escape/exfiltration 위험이 있다. Sandboxing B

    native Windows에서는 이 Bash sandbox가 동작하지 않는다. PowerShell tool도 Windows sandbox 미지원을 preview limitation으로 명시한다. 따라서 Windows에서는 permission rule이나 auto classifier를 macOS/Linux의 OS-enforced containment와 같은 보안 경계로 평가하면 안 되며, 강한 격리가 필요하면 WSL2·container·VM 같은 별도 경계가 필요하다. B, D

    특히 다음을 과장하면 안 된다.

    • sandbox는 기본 활성화가 아니며 /sandbox 또는 설정으로 켜야 한다.
    • native Windows에는 동일한 OS sandbox가 없고 WSL2는 Linux 전제 조건을 따른다.
    • platform support가 없을 때 failIfUnavailable을 쓰지 않으면 경고 후 unsandboxed fallback이 가능하다.
    • dangerouslyDisableSandbox retry escape hatch는 별도 승인을 받아야 하지만 존재한다.
    • network proxy는 TLS-inspecting DLP가 아니다.
    • Docker socket 같은 Unix socket allow는 사실상 host 권한을 열 수 있다.

    9.4 trust boundary

    project는 code만 제공하지 않는다. .claude/settings.json, hooks, skills, agents, .mcp.json이 실행 행위를 바꿀 수 있으므로 cloned repository 자체가 policy input이다. Claude Code는 first-run project와 project-scoped MCP를 trust prompt로 보호하지만, headless -p에는 일부 trust verification 예외가 있다. official security 문서는 untrusted content에 대해 VM 사용까지 권고한다. Security B

    운영 배포에서 반드시 분리해야 할 secret 경계는 다음과 같다.

    • model provider credential은 secret manager 또는 outbound proxy가 주입.
    • host application의 inbound auth는 agent process 바깥 gateway가 담당.
    • external tool credential은 가능한 agent environment에 직접 넣지 않고 egress proxy가 주입.
    • multi-tenant host에서는 settingSources: [], tenant별 CLAUDE_CONFIG_DIR, cwd, auto-memory disable, egress policy가 필요.

    이는 공식 SDK hosting 문서의 권고다. B

    14. 실패 경계, 취소, retry, observability

    14.1 API retry와 timeout

    현재 Claude Code는 server error, overload, request timeout, temporary 429, dropped connection을 기본 최대 10회 exponential backoff로 retry한다. CLAUDE_CODE_MAX_RETRIES 기본값은 10, API_TIMEOUT_MS 기본값은 600,000ms다. 최악 시간은 각 retry마다 timeout window를 새로 가지므로 매우 길 수 있다. Errors, TypeScript SDK B

    background subagent에는 stream event가 없을 때 abort하는 stall watchdog이 있지만 total-runtime deadline은 아니다. top-level session도 자동 timeout이 없으므로 maxTurns, budget, application deadline을 별도로 설계해야 한다. B

    14.2 cancellation surface

    TypeScript SDK는 AbortController, streaming query의 interrupt(), stopTask(), close()를 제공한다. interrupt()는 현재 turn을 끊어도 session stream 자체를 끝내는 것과 같지 않으며 이후 새 prompt를 보낼 수 있다. Python 문서는 interrupt 직후 새 query를 보낸 경우 이전 interrupted response를 먼저 drain해야 하는 ordering 주의사항을 명시한다. TypeScript SDK, Python SDK B

    복원본 tool contract는 새 user message가 들어올 때 tool별로 cancel 또는 block을 선택하게 한다. 기본은 block이다. 이는 “abort signal 하나가 모든 side effect를 원자적으로 취소한다”는 환상을 피한다. 이미 외부 system에 적용된 MCP/Bash side effect는 abort로 rollback되지 않는다. packages/claude-code-sourcemap/src/Tool.ts:407 C, D

    14.3 failure taxonomy

    경계 동작
    model transient failure 내부 retry/backoff 후 terminal API error
    max turns/budget 명시적 result subtype, session ID/usage로 resume 가능
    prompt too long 자동 compact/recovery 후 실패 표면화
    tool validation/permission failure error tool result로 model에 되돌려 self-correction 가능
    tool runtime failure PostToolUseFailure/stream event, 다음 loop 판단
    MCP connection failure init status, remote reconnect/backoff, stdio는 수동
    external SessionStore failure local query 계속, mirror_error; durability degradation

    16.1 latency를 줄이는 잘된 선택

    • streaming response와 streaming tool start C

    16.2 한 session이 길어질 때

    append-only JSONL과 in-memory message state는 장기 session에서 증가한다. compaction은 model context를 줄이지만 raw file과 process memory의 모든 비용을 자동으로 0으로 만들지 않는다. 공식 SDK hosting 문서도 long session의 memory growth를 limitation으로 두고 process recycle 또는 session cap을 권고한다. B

    복원본은 다음을 통해 비용을 줄인다.

    • current session UUID set memoization과 resume load 재사용
    • incremental transcript dedup, parent hint로 반복 O(n) scan 회피
    • full file read 한 번으로 metadata/message map 구성
    • parent→children index를 한 번 만들어 leaf lookup O(1)
    • lite metadata는 file의 head/tail 약 64KB만 읽기

    그러나 특정 session full resume는 결국 그 JSONL의 active chain을 구성하는 O(file size/messages) 작업이고, raw file이 multi-GB가 될 가능성 자체는 남는다. C, D

    16.4 NFS/HPC 판정

    Claude Code의 기본 persistence는 사용자 home 아래 작은/큰 JSONL 여러 개와 memory/config/plugin 파일을 사용한다. local filesystem에서는 append, stat, head/tail read가 싸지만 NFS에서는 다음 비용이 증폭된다.

    • resume picker의 session별 stat round trip
    • recent 50개 각각의 head/tail content read
    • transcript append/flush와 metadata append
    • project/skill/plugin/MCP directory discovery
    • subagent별 JSONL과 metadata file
    • background supervisor roster/job state file

    공식 문서는 SDK container local disk를 전제로 설명하고 NFS 최적화 계약을 제공하지 않는다. 복원본에도 session 목록 전체를 대표하는 단일 persistent derived index와 (mtime,size) delta reconcile 계약은 확인되지 않는다. 따라서 shared HPC home/NFS에서는 CLAUDE_CONFIG_DIR를 node-local SSD로 두고 필요한 transcript만 external store에 미러하거나, session index를 별도 service로 관리하는 편이 낫다. 다만 external SessionStore는 memory와 working tree를 보존하지 않으므로 그것만으로 cross-node resume가 완성되지는 않는다.     16.5 process scale

    공식 SDK 권장 시작점은 agent instance당 1GiB RAM, 5GiB disk, 1 CPU이며 1GiB는 ceiling이 아니라 floor라고 명시한다. 동시에 실행 중인 SDK session 하나가 subprocess 하나이므로 host capacity는 대략 다음 식으로 제한된다.

    agents_per_host = (host_RAM - host_overhead) / measured_per_session_peak_RSS

    장기 session pool은 session ID로 consistent hashing해 같은 container/process로 route하거나, idle 때 내렸다가 SessionStore와 working state를 hydrate해야 한다. wide subagent fanout은 process뿐 아니라 API rate limit과 token 비용도 곱한다. Agent SDK hosting B

    17.1 좋은 경계

    복원본에서 확인되는 좋은 구조는 다음과 같다.

    • QueryEngine이 headless/SDK conversation lifecycle을 별도 class로 소유한다.

    • QueryDeps injection으로 model/compaction path를 fake할 seam을 만들었다.
    • hook/MCP/plugin으로 core fork 없이 동작을 확장한다.

    반면 bootstrap/state.ts에는 process-global mutable STATE가 있고 파일 자체가 “DO NOT ADD MORE STATE HERE”라고 경고한다. session ID, cwd, cost, model usage, telemetry, plugin, cached CLAUDE.md, feature latch 등 폭넓은 상태를 가진다. session ID와 project directory를 atomic하게 바꾸는 switchSession()은 drift bug를 줄이는 좋은 보완이지만, 전역 singleton 자체는 multi-session in-process execution과 unit isolation을 어렵게 한다. packages/claude-code-sourcemap/src/bootstrap/state.ts:31, :428, :456 C

    또한 다음 결합이 보인다.

    • core Tool type에 React renderer가 포함됨
    • 5,000-line REPL과 5,512-line messages pipeline
    • query loop가 feature gates, settings, queue, telemetry, global state를 직접 참조
    • JSONL schema와 resume optimization이 serialization key order 같은 low-level invariant에 의존

    이것은 빠르게 진화하는 단일 제품에서는 이해할 수 있는 trade-off다. 동일 팀이 UI, tool, session을 함께 바꾸면 end-to-end 최적화가 쉽다. 하지만 독립 embeddable engine, 여러 UI toolkit, 동일 process의 다중 session으로 확장할수록 비용이 커진다. Agent SDK가 session마다 child process를 쓰는 구조는 이 전역 상태 문제를 process isolation으로 우회하는 효과도 있다. D

    17.3 테스트에 관해 말할 수 있는 것과 없는 것

    복원 npm sourcemap에는 test files가 포함되어 있지 않아 공식 internal test coverage를 평가할 수 없다. 다만 source comment에는 테스트 fake를 위한 QueryDeps, transcript render fidelity test, large-session 측정, chain invariant 검증 흔적이 있다. 공식 SDK는 SessionStore conformance suite와 structured result type을 제공한다. B/C

    따라서 “테스트가 없다”는 결론은 근거가 없고, 더 정확한 결론은 다음이다.

    • public contract-level SDK testing seam은 강하다.
    • 복원본의 일부 core seam은 개선 중이다.
    • process-global state와 UI/core 혼합은 isolated test 비용을 키울 가능성이 높다.
    • proprietary current implementation의 실제 regression suite 품질은 확인 불가다. D

    18. 구조적 강점

    이 절은 앞선 B/C 근거를 종합한 D 등급의 구조 평가다.

    1. 단일 agent loop의 제품화
      model/tool/permission/session이 각각 흩어진 library가 아니라 하나의 실행 계약을 이룬다.

    2. 로컬 권위가 명확한 interactive architecture
      CLI process가 shell/cwd/transcript를 소유해 개인 개발자 workflow가 예측 가능하다.

    3. progressive disclosure의 일관성
      ToolSearch, skills, nested memory, large-output spill이 context를 무제한 선적재하지 않는다.

    4. 다층 확장 모델
      instruction은 memory/skill, deterministic policy는 hook/permission, external action은 MCP, 배포는 plugin으로 구분한다.

    5. 실패를 state로 모델링
      retry, compact, max-output recovery, max turns/budget, mirror degradation, MCP status를 구분한다.

    6. 병렬성의 보수적 규칙
      read/safe batch만 parallel, mutation은 serial, worktree가 실제 file isolation을 담당한다.

    7. HITL이 runtime에 내장
      permission, plan, question, diff, rewind, background needs-input가 같은 event 흐름에 있다.

    8. 여러 표면의 일관된 agentic behavior와 SDK의 확인된 CLI 재사용
      Agent SDK는 CLI subprocess를 재사용해 semantics 재구현을 줄인다. 다른 surface의 내부 code reuse는 공개 근거가 없으므로 behavioral parity까지만 평가한다.

    19. 구조적 약점과 리스크

    이 절도 현재 공개 계약과 2.1.88 관찰을 종합한 D 등급이며, current proprietary 내부 구조를 확정하지 않는다.

    1. 동시 active SDK session당 process 구조의 비용
      isolation은 좋지만 live session 수에 따라 memory·startup·process tree·routing 비용이 선형 증가한다. persisted session 수와는 별개다.

    2. local JSONL과 filesystem affinity
      interactive resume에는 좋지만 cross-host, NFS, 10,000 session 목록에는 별도 index/state plane이 필요하다.

    3. conversation과 world state의 비원자성
      transcript, file checkpoint, git, external MCP side effect가 하나의 transaction이 아니다.

    4. sandbox opt-in·native Windows 부재·범위 한계
      permission prompt만으로 arbitrary Bash/script의 실제 행동을 강제할 수 없고 native Windows에서는 macOS/Linux와 같은 OS sandbox 경계가 없다.

    5. Claude-specific provider coupling
      호스팅 provider는 여러 개지만 model/runtime protocol은 portable하지 않다.

    6. 확장 surface의 공급망 위험
      project settings, hook, skill, plugin, MCP가 모두 실행/context surface를 넓힌다.

    7. 전역 상태와 역사적 TUI 결합
      process isolation으로 문제를 감추지만 core-as-library 관점에서는 composition이 어렵다.

    8. compaction의 의미 손실
      raw transcript가 남아도 active model context는 summary이며 nested instruction/old skill이 탈락할 수 있다.

    9. parallel agent의 conflict 책임
      subagent/team/session 수를 늘리는 것은 쉽지만 shared file과 external resource conflict는 자동으로 해결되지 않는다.

    10. observability는 제공하되 운영 완성은 사용자 책임
      OTEL event는 풍부하지만 alert, SIEM correlation, idempotency, recovery runbook은 별도다.

    20. Farad 비교에 넘길 핵심 판정

    이 절은 Farad 구현 지시가 아니라 교차 비교 보고서가 사용할 논점이다.

    20.1 배워야 할 것

    • agent loop event protocol을 UI보다 먼저 정의해야 한다. Claude Code가 여러 표면을 유지하는 힘은 streaming message/result/event 계약에서 나온다.
    • tool pipeline을 validate → policy hook → permission → execute → post hook → bounded result로 고정하는 것이 좋다.
    • context와 transcript를 분리하고 compaction boundary가 무엇을 잃고 무엇을 재주입하는지 계약으로 써야 한다.
    • large output은 truncate보다 spill + preview + path가 낫다.
    • read parallel / mutation serial을 기본값으로 하고 tool별 safe declaration은 fail-closed여야 한다.
    • session resume와 file rollback을 다른 기능으로 표현해야 한다.
    • MCP/skills/plugins/hooks를 하나의 registry abstraction으로 평탄화하지 말고 discovery, prompt exposure, execution, policy, distribution 책임을 분리해야 한다.
    • failure subtype과 terminal reason을 UI/event에 보존해야 한다.
    • background work는 process/task owner, needs-input, attach/stop/resume 상태를 명시해야 한다.

    20.2 그대로 모방하면 안 되는 것

    • Farad desktop runtime에서 session마다 1GiB급 child CLI process를 만드는 방식.
    • NFS home에서 session file 전량 stat 후 최근 것만 읽는 목록 구조.
    • UI render method를 core Tool protocol에 포함하는 결합.
    • process-global mutable state로 여러 session을 구분하는 방식.
    • turn 사이 동적 refresh를 “항상 최신”이라는 이유로 무제한 수행하는 방식. Farad의 explicit refresh와 cache invalidation 계약을 우선해야 한다.
    • proprietary Claude-specific message semantics를 hvppyai의 provider-neutral public SDK에 누출하는 것.
    • transcript mirror를 canonical database처럼 오해하는 것.

    20.3 Farad가 의도적으로 더 잘할 수 있는 지점

    23. 최종 판정

    Claude Code는 “CLI에 LLM을 붙인 것”이 아니라 로컬 stateful agent operating environment에 가깝다. 확인 가능한 로컬 중심에는 process-owned query loop, append-oriented session, capability/permission pipeline, context compaction이 있다. CLI와 Agent SDK는 이 runtime 관계가 확인되며, Desktop·IDE·Web은 공식적으로 같은 agentic behavior를 서로 다른 deployment boundary에서 제공한다. 그 표면들의 동일 내부 engine 재사용 여부는 공개되지 않았다.

    이 구조는 개인 개발자의 실제 repository 작업, 긴 tool-use loop, 확장 생태계, human-in-the-loop에는 매우 강하다. 특히 model/tool/session/permission을 한 runtime에 응집시키고 failure를 명시적인 상태로 노출한 점은 비교 대상 중 높은 기준점이 될 가능성이 크다.

    그러나 서버형 SDK, shared HPC, NFS, 10,000-session desktop catalog의 기준으로 보면 local process와 file affinity가 명확한 한계다. 또한 Claude-specific runtime 최적화와 내부 TUI/global-state 결합은 범용 agent kernel로서의 중립성과 변경 용이성을 낮춘다.

    따라서 Farad가 취할 전략은 Claude Code를 기능 단위로 복제하는 것이 아니다. agent loop의 명시적 state, tool/permission pipeline, context/transcript 구분, progressive disclosure, failure taxonomy는 배우고, process-per-session·file-per-session scan·UI/core 결합·provider lock-in은 Farad의 authority/thread/NFS/10k 계약에 맞게 다시 설계해야 한다. D
