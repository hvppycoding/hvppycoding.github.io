    전체 보고서 인덱스

    조사 기준일: 2026-07-13 (Asia/Seoul)
    공개 소스 스냅샷: openai/codex@2b0b37abb7b29ea272fa856d6dff9221a6bd9ba8
    로컬 실행 관찰: 설치된 codex-cli 0.144.1
    분석 범위: Codex CLI/core, app-server, non-interactive interface, 로컬 sandbox, subagent/thread, tools/MCP/skills/plugins, 저장·복구 구조. 호스티드 Codex 내부 구현은 공개 계약 이상으로 추정하지 않는다.

    1. 결론부터

    Codex의 핵심은 “좋은 터미널 UI”보다 훨씬 아래에 있다. 공개 Rust 구현에서 확인되는 본체는 다음 네 가지가 결합된 이벤트 기반 thread/turn 실행 커널이다.

    1. 클라이언트가 Submission을 넣고 Event를 받는 queue-pair 계약
    2. thread마다 한 번에 하나의 active task만 허용하면서 interrupt/steer/approval을 같은 순서열로 직렬화하는 session authority
    3. 모델에 노출할 tool schema와 실제 dispatch registry를 분리한 per-step tool plan
    4. JSONL을 durable replay 원본으로, SQLite를 조회용 metadata projection으로 두는 저장 경계

    이 설계 덕분에 TUI, IDE, app-server, codex exec가 같은 엔진을 서로 다른 표면으로 사용할 수 있다. 동시에 운영 복잡도도 높다. core에 auth, model/provider, MCP, extensions, hooks, skills, permissions, sandbox, telemetry, storage, subagent graph가 한 session 수명 안에서 만나므로, 강한 타입과 세밀한 concurrency protocol이 없으면 유지하기 어려운 구조다.

    한 문장으로 평가하면 다음과 같다.

    Codex는 공개 로컬 구현에서 surface-agnostic agent runtime과 OS-enforced execution boundary, replay 가능한 thread protocol을 특히 강하게 결합한다. 대신 OpenAI 제품 생태계와 거대한 Rust workspace에 최적화되어 있어, Farad가 통째로 모방할 대상이 아니라 경계와 불변식만 선별할 대상이다.

    위 결론과 뒤의 판정표는 공개 구현 A와 공식 계약 B에서 도출한 D 등급의 비교 평가다. 메커니즘의 존재를 실제 운영 품질, 특정 규모의 성능, 비공개 제품 surface의 구현 동일성으로 승격하지 않는다.

    2. 증거 등급과 분석 한계

    이 보고서는 공통 방법론의 등급을 따른다.

    항목 근거 등급
    CLI/core/app-server 내부 구조 고정 commit의 공개 Rust 소스 A
    sandbox, cloud task, subagent의 사용자 계약 공식 Codex 문서 B
    로컬 설치 버전 codex --version 실행 관찰 C
    ChatGPT/Codex 호스티드 backend 내부 공개되지 않음 판단 보류
    Farad에 미치는 함의 A/B 근거에서 도출한 분석 D

    중요한 제한은 두 가지다.

    • 공개 저장소는 매우 빠르게 변한다. 여기서 말하는 class/module 이름과 line anchor는 위 commit에 고정한다.
    • 로컬 codex-cli 0.144.1은 실행 환경의 버전 표지일 뿐이며, 위 source commit과 binary가 byte-level 동일 build라고 단정하지 않는다.
    • Codex App/Web의 모든 backend가 이 로컬 core와 동일하게 동작한다고 단정하지 않는다. 공식 문서가 명시한 컨테이너·권한·task 계약만 제품 사실로 취급한다.

    3. 제품 표면과 공유 코어

    공개 README는 Codex CLI를 로컬 coding agent로 정의하고 IDE, desktop app, Codex Web을 별도 surface로 안내한다. 로컬 쪽에서 가장 중요한 통합 경계는 codex-core와 app-server다.

    표면 주 사용 방식 실행 위치 자동화/통합 경계
    CLI/TUI 대화형 로컬 작업 사용자 호스트 core queue/event + TUI
    IDE 편집기 안 대화·diff·승인 사용자 호스트 app-server protocol
    custom rich client / remote TUI 자체 client 또는 원격 TUI local/remote host experimental JSON-RPC app-server
    Codex app 데스크톱 planning·review·interactive work desktop product 공개 문서만으로 내부 app-server topology 미확인
    codex exec CI·script·pipeline 사용자/CI host stdout/stderr 또는 JSONL
    Codex cloud branch checkout 기반 task 관리형 container 호스티드 task 계약

    공식 문서는 app-server를 인증, 대화 이력, 승인, streamed agent event까지 필요한 rich client용 interface로 설명한다. wire는 JSON-RPC 2.0 계열이며 thread/start, turn/start 같은 명시적 method와 server notification을 갖는다. 공개 protocol은 client request, server request, notification을 타입으로 생성한다. 다만 codex app-server 명령 자체는 local development/debugging 용 experimental surface이고 변경될 수 있다. 기본 transport는 JSONL-over-stdio이며 WebSocket transport는 구현되어 있어도 공식 README가 experimental/unsupported로 명시한다. 따라서 이를 production remote API 안정성 보장으로 읽으면 안 된다. App server A, B

    VS Code extension 같은 app-server client 경로와 custom client 계약은 공개되어 있지만, Codex desktop app이 정확히 같은 app-server topology를 쓴다는 근거는 확인하지 못했다. 아래 그림도 공개 local core와 app-server만 나타내며 비공개 desktop/cloud 내부를 설명하지 않는다.

    이것은 UI가 runtime 객체를 직접 잡는 구조가 아니다. 프로토콜이 surface와 runtime 사이의 anti-corruption layer 역할을 한다.

    3.1 UI와 human-in-the-loop 계약

    공개 app-server protocol은 rich client가 임의의 core 객체를 해석하지 않게 UI projection을 구체화한다. turn/item lifecycle은 started → delta* → completed로 흐르고, turn/diff/updated는 aggregated unified diff, turn/plan/updated는 plan state를 전달한다. command/file change/permission 승인은 server-initiated request와 client decision으로 왕복하고, tool user-input과 MCP elicitation도 별도 typed request다. terminal item/completed가 최종 실행 상태의 권위다. A, B

    이 계약은 approval card, live output, diff, plan, reconnecting client를 만들기 좋은 기반이다. 그러나 proprietary Codex app의 widget/state-store/threading 구조, optimistic UI, offline cache가 이 protocol과 어떻게 연결되는지는 공개 근거가 없다. 따라서 여기서 평가하는 것은 protocol-level HITL completeness이지 desktop UI 내부 아키텍처나 실제 UX latency가 아니다. D

    4.1 Authority

    Codex 자체는 Submission sender와 Event receiver를 가진 queue pair다. 실제 mutable authority는 Session에 있다. 소스 주석은 session에 동시에 최대 한 개의 running task만 존재하며 user input으로 interrupt될 수 있다고 명시한다.

    이 단일 active-task 규칙은 단순한 구현 편의가 아니다. 다음 순서를 보장하는 핵심 불변식이다.

    • turn 시작 전에 model/permissions/environment 같은 live settings 적용
    • active turn이 있으면 새 입력을 steer 또는 pending input으로 처리
    • approval response와 interrupt가 해당 turn보다 뒤집히지 않음
    • 종료 시 task cancellation, event flush, persistence teardown 순서 유지

    SessionState는 대화 history/context manager, rate limit, 이전 turn settings, auto-compaction window, active connector selection, permissions, first-turn 상태를 가진다. 반면 SessionServices는 auth, models, MCP runtime snapshot, exec manager, hooks, approval store, skills/plugins, telemetry, state DB, thread store 같은 장수 서비스를 모은다. 즉 대화 상태와 서비스 수명은 타입 수준에서 분리되어 있지만 한 Session이 이들을 조정한다.

    4.2 Thread ownership과 process 경계

    ThreadManager는 새 thread, resume, fork, 메모리 내 thread tracking을 소유한다. parent에서 subagent를 spawn할 때 parent rollout을 flush하고 fork snapshot을 읽어 child history를 만든다. 이 때문에 multi-agent가 단순히 같은 transcript list를 공유하지 않는다.

    codex app-server는 이 runtime을 stdio·WebSocket·Unix socket transport로 노출하는 별도 OS process 경계다. TUI/exec가 core library를 직접 쓰는 것과 app-server client가 protocol을 통해 접근하는 것은 다른 topology다. protocol에는 initialize handshake, thread lifecycle, turn lifecycle, approval/elicitation, MCP, skills/plugins, model/environment method가 분리되어 있다. 이 구조의 가치:

    • app-server를 client와 독립 daemon으로 운영할 때 UI crash와 runtime lifetime을 분리할 수 있음
    • 여러 surface가 동일한 의미론을 재사용
    • schema generation으로 TypeScript/JSON client contract 생성 가능
    • server request로 승인처럼 runtime→client→runtime 왕복이 가능

    protocol이 있다고 수명 분리가 자동 보장되지는 않는다. client가 app-server child process의 수명을 소유하면 함께 종료될 수 있고, 독립 daemon·reconnect·thread recovery를 실제로 배치해야 분리가 성립한다. 반대 비용도 분명하다. versioning, experimental capability negotiation, backpressure, 인증, 연결별 초기화 상태, reconnect semantics가 모두 제품 코드가 된다. 특히 WebSocket listener는 인증이 기본 강제되지 않으므로 remote 노출 시 bearer auth와 TLS termination을 별도로 구성해야 한다. 단일 데스크톱 앱만 있는 제품에는 과할 수 있다. B, D

    4.3 Process와 resource topology

    공개 local topology에서 app-server의 ThreadManager는 여러 loaded thread/session actor를 같은 host process에서 추적한다. thread마다 active task는 하나지만 thread마다 OS process를 하나씩 만드는 구조는 아니다. shell·sandbox·MCP/remote execution은 필요에 따라 child/external process 경계를 만든다. 이 선택은 shared auth/model catalog/MCP/store service를 재사용해 active thread당 process overhead를 줄이는 대신, host process crash와 unbounded event accumulation의 blast radius를 여러 loaded thread가 공유하게 한다.

    고정 소스에는 agent thread limit과 nesting guard가 있지만 전체 app-server RSS ceiling, loaded thread eviction 정책, 10,000 active thread 보장은 확인하지 못했다. 따라서 process-per-session인 다른 runtime보다 가볍다고 추론할 수는 있어도 실제 memory curve나 저사양 HPC 적합성은 benchmark 없이 확정할 수 없다. A, D

    5. Turn 실행 로직

    run_turn의 공식 소스 주석은 loop의 의미를 직접 설명한다. 모델이 function call을 반환하면 실행 결과를 다음 sampling request에 넣고, assistant message만 반환하면 history에 기록하고 turn을 완료한다 (source).

    실제 흐름은 더 넓다.

    sequenceDiagram
    participant C as Client
    participant Q as submission_loop
    participant S as Session
    participant T as run_turn
    participant M as Model
    participant R as ToolRouter
    participant P as Persistence/Event

    C->>Q: Submission(UserInput + TurnSettings)
    Q->>S: apply settings / start-or-steer
    S->>T: spawn active task
    T->>T: context + world state + skills/plugins + compaction check
    loop until final assistant message
        T->>M: prompt/history/tool specs
        M-->>T: stream items
        alt tool call
            T->>R: typed ToolCall
            R-->>T: tool output / model-visible error
            T->>P: rollout items + events
        else assistant only
            T->>P: assistant item + turn complete
        else context threshold
            T->>T: compact and continue
        end
    end
    P-->>C: typed streamed Events

    Turn 시작 시 context/world-state를 준비하고, skills/plugins를 선택적으로 주입하고 lifecycle hook을 실행하며, context limit 전후로 compaction을 수행한다. 여기에는 서로 다른 두 수명이 있다. TurnContext는 user-visible turn 전체에서 공유되는 model/provider, approval policy, permission profile, collaboration mode, dynamic tools/extensions, config 등의 turn-scoped 값이다. 반면 StepContext는 각 model sampling request마다 캡처되는 request-scoped view다. 후자는 Arc<TurnContext>와 함께 environment snapshot, 선택 capability roots, exact MCP runtime/tool list, 관찰된 AGENTS.md를 고정한다.

    따라서 “한 sampling step이 TurnContext snapshot 하나를 쓴다”보다 “turn 설정은 TurnContext, 매 request의 동적 capability view는 StepContext”라고 구분하는 편이 정확하다. request 조립과 그 request가 광고한 tool의 실행이 같은 StepContext를 공유하므로 step consistency를 얻는다. DeferredExecutor가 켜지면 다음 sampling request의 StepContext를 캡처하면서 filesystem-derived environment/AGENTS.md/MCP state를 다시 관찰할 수 있다. 이 refresh 의미는 §11에서 따로 평가한다. StepContext source A

    Interrupt와 steer

    submission_loop는 user input만 받는 loop가 아니다. interrupt, approval answer, MCP refresh, configuration reload, compact, rollback, review, shell, shutdown을 같은 control plane에서 분기한다. 특히 settings mutation도 submission queue를 통과하도록 한 이유가 source comment에 “후속 user input과의 ordering 보존”으로 명시돼 있다.

    이것은 async agent runtime에서 매우 중요한 선택이다. UI가 session field를 직접 바꾸고 별도로 message를 보내면 어떤 설정으로 그 turn이 시작됐는지 재현하기 어렵다. Codex는 Op 자체를 ordered command로 만든다.

    6. Tool architecture

    6.1 Schema exposure와 dispatch 분리

    ToolRouter는 ToolRegistry와 model_visible_specs를 별도 field로 가진다. 따라서 “실행할 수 있는 도구”와 “이번 step에서 모델에게 광고하는 도구”가 동일 집합일 필요가 없다.

    spec_plan은 tool runtime과 hosted spec을 먼저 계획한 뒤, exposure를 Direct, Deferred, DirectModelOnly, Hidden 네 상태로 적용하고 per-step router를 조립한다. DirectModelOnly는 일반 model-visible list에는 넣되 code-mode-only session의 nested code-mode surface에서는 제외한다. 이 분리는 다음을 가능하게 한다.

    • deferred tool search: 수백 개 schema를 prompt에 항상 넣지 않음
    • code mode와 일반 function-call mode의 다른 노출
    • MCP, extension, dynamic tool을 같은 dispatch contract로 수렴
    • 모델/기능 flag/multi-agent version에 따른 schema 선택
    • 실제 handler는 등록돼 있으나 모델에는 숨기는 내부 control tool

    Farad 관점에서 이 패턴의 핵심은 enum 이름이 아니라 catalog/dispatch capability와 prompt exposure를 별도 projection으로 유지하는 것이다.

    6.2 Typed dispatch와 hook envelope

    registry는 duplicate tool name을 거부하고, payload를 tool 종류에 맞게 decode한 뒤 runtime executor를 호출한다. 공통 경계는 lifecycle accounting, pre/post hook, telemetry, terminal notification, model-visible error 변환을 묶는다. 승인·sandbox·denial retry의 공통 순서는 generic registry가 아니라 ToolRuntime을 사용하는 shell/apply-patch 계열의 ToolOrchestrator가 담당한다. 그 순서는 approval → sandbox 선택 → 실행 attempt → denial 시 escalated sandbox retry이며 approval cache로 불필요한 재승인을 피한다. MCP·hosted tool 등 다른 runtime은 별도 policy adapter와 실행 경로를 쓴다. 따라서 registry lifecycle envelope가 모든 tool의 approval을 보장한다고 일반화하면 안 되고, 적용 가능한 execution runtime에서는 ToolOrchestrator, 나머지는 각 adapter의 fail-closed 계약을 따로 검증해야 한다. ToolOrchestrator source A

    6.3 병렬 실행

    tool-call runtime은 parallel-safe tool에는 read lock, 직렬화가 필요한 tool에는 write lock을 사용한다. cancellation token과 dispatch를 race해 중단된 call도 protocol상 결과로 닫는다. “여러 tool call이 한 model response에 왔다”는 이유만으로 무조건 병렬화하지 않는다는 점이 중요하다.

    평가:

    • 강점: schema budget, 확장성, tool policy, observability가 한 경계에서 만난다.
    • 위험: spec_plan이 feature matrix의 집결지가 되어 조합 폭발을 일으킬 수 있다.
    • 필요한 검증: tool exposure snapshot test, duplicate/unknown tool fail-closed test, cancellation 뒤 terminal event 보장, unsafe tool serialization test.

    7. 권한과 sandbox

    Codex는 정책적 승인(approval)과 기술적 격리(sandbox)를 별개 층으로 정의한다. 공식 문서는 local CLI/IDE에서 기본적으로 network를 끄고, OS-enforced sandbox로 writable 범위를 workspace로 제한한다고 설명한다. macOS는 Seatbelt, Linux/WSL2는 bubblewrap 계열, Windows는 native sandbox를 사용한다 (Agent approvals & security, Sandbox).

    층 질문 대표 상태
    sandbox command가 기술적으로 무엇에 접근 가능한가? read-only, workspace-write, danger-full-access
    approval policy 경계를 넘기 전 누구에게 물을 것인가? untrusted/on-request/never/granular
    exec policy 특정 command pattern을 허용·질문·차단할 것인가? rule evaluation
    tool annotation shell 외 app/MCP side effect인가? read-only/destructive 등
    network policy 허용된 network가 어디로 나갈 수 있는가? domain/socket allow/deny proxy

    중요한 세부 계약:

    • workspace-write 안에서도 .git, .agents, .codex 같은 protected path는 재귀 read-only다.
    • non-interactive flow에서 새 승인을 표시할 수 없으면 해당 행동은 실패하여 parent workflow로 돌아간다.
    • subagent는 parent turn의 live permission/sandbox override를 상속한다.
    • cloud는 setup과 agent phase를 나누고, secrets는 setup에만 제공한 뒤 agent phase 전에 제거한다.
    • network enable과 destination policy는 별개이며, allowlist/deny 및 private destination 제약을 둘 수 있다.

    현재 확인 범위에서 이 영역은 Codex의 큰 구조적 강점이다. “모델이 허용된다고 판단했다”가 보안 경계가 아니라 실제 child process가 OS boundary 안에서 실행된다. Claude Code도 permission과 OS sandbox를 분리하므로, 최종 비교에서는 기본 활성화 여부·플랫폼 범위·degraded fallback·shell 외 도구의 적용 범위를 같은 조건에서 따로 판정한다.

    한계도 있다.

    • danger-full-access는 이 방어선을 의도적으로 제거한다.
    • sandbox는 외부 도구의 논리적 오용, 허용된 파일 안의 파괴적 수정, prompt injection을 모두 해결하지 않는다.
    • 플랫폼별 kernel/OS 기능 차이와 HPC 정책(user namespace, bubblewrap 설치 제한)이 실제 가용성을 좌우한다.

    8. Context, transcript, compaction

    Codex의 rollout은 단순 [{role, content}] 배열이 아니다. protocol의 RolloutItem에는 session metadata, model response item, inter-agent communication, turn context, world state, compacted item, EventMsg가 같은 enum과 rollout stream 안의 typed variant로 구분되어 저장된다. 따라서 UI event와 model replay가 별도 stream이라고 말할 수는 없다. 장점은 한 durable sequence에서 provenance를 보존하면서 consumer가 variant별로 필터링할 수 있다는 것이고, 위험은 replay/context 조립 코드가 EventMsg를 model-visible item으로 잘못 승격하지 않도록 invariant를 계속 지켜야 한다는 점이다. RolloutItem source A

    Compaction 계약

    CompactedItem은 단순 summary 문자열뿐 아니라 replacement history와 chain/window 식별 정보를 가질 수 있다. turn loop는 sampling 전에 threshold를 검사하고, model token limit에 닿으면 mid-turn compaction 후 이어갈 수 있다.

    이 설계가 지키려는 것은 세 가지다.

    1. 현재 모델에 넣는 context가 window를 넘지 않음
    2. durable rollout과 현재 compacted prompt가 어떻게 연결되는지 추적 가능
    3. resume/fork가 단순 최종 텍스트보다 풍부한 history·window·fork provenance를 복원

    그러나 이것은 실행 세계 전체의 checkpoint가 아니다. resume/fork가 in-flight approval, 실행 중인 child process/tool call, 외부 MCP side effect, 현재 filesystem을 원자적으로 되살린다는 보장은 없다. 위험은 compaction implementation이 prompt replay semantics의 일부가 된다는 점이다. summary 품질뿐 아니라 tool call/result pairing, event filtering, subagent message, world-state 기준선과 window chain을 테스트해야 한다. A, D

    9. 저장과 조회

    ThreadStore는 create/resume/append/flush/load/read/list/search/update metadata/archive/delete를 제공하는 storage-neutral trait이다. local 구현의 주석은 저장 전략을 명확히 선언한다.

    rollout JSONL은 SQLite 없이도 읽을 수 있는 durable replay format이고, SQLite는 빠른 list/read를 위한 queryable metadata index다.

    (source)

    flowchart LR
    TURN[Turn / rollout append] --> REC[Live recorder]
    REC --> JSONL[Canonical JSONL]
    TURN --> META[Metadata patch]
    META --> DB[(SQLite projection)]
    DB --> LIST[list / search / fast read]
    JSONL --> RESUME[resume / replay / repair]
    DB -. unavailable or stale .-> REPAIR[rebuild/compat path]
    JSONL --> REPAIR

    이중화처럼 보이지만 authority는 비대칭이다.

    • 대화 실행 사실: JSONL canonical
    • 목록/검색/정렬 metadata: SQLite projection
    • SQLite 부재·손상·구버전: JSONL/name-index compatibility path

    이는 append-heavy transcript를 유지하면서 목록·검색 때 전량 JSONL scan을 피하기 위한 합리적 구조다. 하지만 구조만으로 N=10,000 latency, projection lag, crash 후 repair 비용이 입증되지는 않는다. 두 projection의 consistency와 bounded rebuild가 새 운영 책임이 된다. SQLite를 원격 NFS canonical store로 그대로 쓰는 것이 안전하다는 뜻도 아니다. Farad에 적용한다면 로컬 derived index 여부와 NFS locking, rebuild bound를 별도로 설계하고 계측해야 한다.

    구체적으로 SQLite-backed state는 기본적으로 CODEX_HOME 아래에 있고 CODEX_SQLITE_HOME 또는 sqlite_home으로 별도 위치에 둘 수 있다. source는 SQLite에 WAL mode와 busy timeout을 설정한다. 따라서 NFS home 사용자가 SQLite만 node-local path로 분리하는 것은 가능하지만 canonical rollout JSONL까지 자동으로 옮겨지는 것은 아니다. state-DB-only list path도 존재하지만 일반 list/read에는 JSONL compatibility·metadata repair path가 남는다. 공식 문서와 source에는 NFS consistency 보장, 파일당 round-trip 상한, 10,000개 rebuild 시간, crash 중 projection lag의 최대치가 없다. A, B, D

    10. Multi-agent 구조

    공식 문서는 subagent를 별도 agent thread로 정의하며, main thread가 결과 요약을 수집한다. 현재 local release는 직접 요청 또는 AGENTS/skill 지시로 delegate할 수 있고, agent마다 model/reasoning/instruction을 달리 설정할 수 있다. child는 기본적으로 parent permission mode를 상속한다 (Subagents).

    공개 core에서 중요한 것은 UI의 “agent 카드”가 아니라 다음 구조다.

    • agent graph가 parent/child thread 관계를 추적
    • spawn 전 parent rollout flush
    • child는 fork된 history snapshot에서 시작
    • inter-agent communication도 Op/rollout item으로 기록
    • thread limit와 nesting depth로 자원 폭발 제한
    • 완료/interrupt/close가 명시적인 lifecycle operation

    장점:

    • noisy exploration을 main context에서 격리
    • parallel read/test/review latency 단축
    • 결과와 child transcript를 별도 감사 가능

    비용:

    • token/compute 증가
    • 동시 write conflict와 shared workspace race
    • child approval이 inactive thread에서 발생할 수 있음
    • parent summary가 child evidence를 손실할 수 있음
    • graph shutdown, orphan recovery, max concurrency가 runtime correctness가 됨

    따라서 “subagent 수가 많다”는 것 자체는 성숙도 지표가 아니다. isolation, ownership, completion protocol, budget, artifact merge가 더 중요하다.

    11. 확장 모델: AGENTS, skills, plugins, MCP, hooks

    Codex는 여러 확장 메커니즘을 서로 다른 역할로 둔다.

    메커니즘 주 역할 runtime 영향
    AGENTS.md directory-scoped project instruction prompt/context assembly
    skill 반복 가능한 지식·workflow·script/assets 선택적 instruction/resource 주입
    plugin skill/MCP/app/hook 등의 배포 묶음 discovery/install/trust surface
    MCP 외부 tool/resource/prompt 연결 tool registry + connection lifecycle
    hook lifecycle 전후 정책·automation dispatch/session envelope
    extension/dynamic tool typed runtime 확장 per-step tool plan

    turn loop는 user mention, skill snapshot, plugin snapshot, MCP tools, extension contributors를 바탕으로 이번 turn에 넣을 대상을 결정하고 실제 주입된 항목을 기록한다. tool spec planner는 direct/deferred 노출까지 조절한다. 즉 discovery, selection, prompt exposure, dispatch가 하나의 list로 뭉개져 있지 않다.

    보안상 주의할 점:

    • skill script와 plugin은 사실상 code execution/supply-chain surface다.
    • MCP OAuth credential과 app-server client auth는 다른 trust boundary다.
    • tool schema의 annotation을 신뢰하더라도 실제 sandbox/approval enforcement가 최종 경계여야 한다.
    • file watcher/hot reload가 실행 중 snapshot을 깨뜨리지 않도록 publish 시점이 필요하다.

    11.1 Config·instruction·memory 경계

    공식 계약에서 AGENTS.md는 global → repository root → cwd 방향으로 합쳐지고 가까운 directory guidance가 뒤에 와 override한다. 각 directory에서는 AGENTS.override.md가 우선하며 합산 기본 한도는 32 KiB다. 일반 제품 문서는 이 instruction chain을 CLI run/TUI session 시작에 한 번 만든다고 설명한다. mandatory rule은 memory가 아니라 checked-in AGENTS.md나 문서에 둬야 한다.     11.2 Refresh와 snapshot 경계

    고정 소스의 기본 경로와 feature-gated 경로가 다르다. explicit config reload와 MCP refresh는 ordered submission으로 들어가며 publish된 service snapshot을 바꾼다. 한편 under-development이고 기본 off인 DeferredExecutor가 켜지면 매 sampling request의 StepContext를 캡처할 때 environment snapshot과 filesystem-derived AGENTS.md, capability roots, MCP runtime/tool list를 다시 관찰할 수 있다. request 안에서는 fixed snapshot을 공유하지만 turn 전체가 frozen이라는 뜻은 아니다. A

    이는 Farad의 explicit refresh 계약과 직접 다르다. NFS 홈에서 이 feature path를 모방하면 한 turn의 반복 sampling 횟수만큼 filesystem/network discovery 비용이 들어갈 수 있으므로, Farad에는 request consistency만 가져오고 per-request refresh는 가져오지 않는 편이 맞다. 실제 Codex의 해당 경로에 대한 NFS round-trip bound는 공개 benchmark로 확인하지 못했다. D

    12. Provider와 모델 계층

    공개 config와 core에는 model_provider, model catalog, OpenAI-compatible base URL, OSS provider 같은 abstraction이 있다. 하지만 제품 경험, 인증, 기능 최적화는 OpenAI/ChatGPT가 중심이다. 따라서 “provider interface가 존재한다”와 “모든 near-frontier provider가 동등한 first-class experience다”는 다른 주장이다.

    Codex가 모델 특성에 따라 다르게 처리하는 예:

    • context window와 auto-compact threshold
    • reasoning effort/summary/verbosity
    • tool mode와 supported feature
    • collaboration mode와 agent role/model override
    • model upgrade/compatibility handling

    이 정도의 model capability matrix는 강력하지만, feature condition이 turn/tool planner 전역으로 퍼지면 testing burden도 크게 늘어난다.

    13. 성능과 concurrency

    확인되는 구조적 장치

    • bounded submission queue로 producer 폭주에 backpressure
    • thread당 하나의 active task로 대화 순서 안정화
    • event channel로 UI와 model loop decoupling. 다만 현재 core event channel은 async_channel::unbounded()이므로 submission 입력의 backpressure가 end-to-end event backpressure를 뜻하지는 않음
    • service snapshot을 ArcSwap으로 publish하여 MCP/hooks 등의 read path 경량화
    • per-tool parallel-safety lock
    • cancellation token을 turn/tool/process lifecycle에 전달
    • state-DB-only metadata path로 전체 JSONL scan을 피할 수 있는 list/search 경로
    • tool schema direct/deferred 분리로 context cost 제어
    • app-server WebSocket ingress에 bounded queue

    여전히 검증이 필요한 hot path

    • 매우 긴 rollout의 resume/compaction 비용
    • 수천 thread와 깊은 agent graph에서 list/search/shutdown bound
    • MCP server가 많을 때 refresh/reconcile 비용
    • deferred tool search 자체의 latency와 정확도
    • core의 unbounded event channel과 app-server slow client 사이의 memory bound, drop/reconnect semantics
    • parallel subagent가 같은 worktree를 수정할 때 충돌 제어

    Rust와 Tokio 선택은 이 구조에 적합하지만, 언어만으로 bounded behavior가 보장되지는 않는다. queue capacity, lock granularity, store index, lifecycle invariant가 실질적인 성능 설계다.

    13.1 테스트 가능성과 변경 용이성

    공개 source에는 tool exposure의 spec_plan_tests.rs, dispatch의 router_tests.rs, session/approval/ sandbox tests, thread-store list/search/metadata-sync tests, app-server protocol schema와 integration suite가 분리되어 있다. typed protocol code generation, storage-neutral ThreadStore, tool runtime trait, in-memory test stores는 변화 지점을 격리하는 좋은 seam이다. A

    다만 test file의 존재는 production quality의 충분조건이 아니다. 이 조사에서는 전체 coverage, mutation/fuzz 결과, production provider backend, hosted surface와 local core의 conformance, 10,000 thread 부하, crash/rebuild chaos test 결과를 확인하지 않았다. 큰 feature matrix와 central SessionServices composition root 때문에 cross-product regression 비용은 여전히 높다.     13.2 Observability·privacy·cost 경계

    local core와 app-server에는 typed lifecycle event, structured tracing, configurable OpenTelemetry, token/rate-limit update가 있다. 이는 turn/tool/thread correlation과 UI 진행 상태, 운영 계측을 만들기 좋은 instrumentation이다. 그러나 exporter 설정, prompt/tool payload 기록 범위, redaction, retention, hosted product의 데이터 처리 정책은 서로 다른 계약이다. 공개 Rust source만으로 hosted request가 어디에 얼마나 저장되는지 또는 privacy가 보장된다고 추론하지 않는다.     token usage는 비용 관찰에는 유용하지만 stable한 per-thread hard budget으로 확인되지 않았다. source의 rollout-budget 기능은 under-development/default-off이므로 비용 폭주 방지의 보편 계약으로 평가하지 않는다. 실제 provider pricing과 organization quota도 runtime architecture 밖의 변동 요소다. A, D

    14. Failure와 recovery boundary

    실패 containment/recovery 단위 평가
    model stream 오류 sampling/turn retry 또는 terminal error event turn 경계가 명시적
    tool 오류 model-visible tool result/error 대화 loop를 반드시 crash시키지 않음
    command cancellation cancellation token + aborted terminal result dangling call 방지 필요
    client disconnect app-server connection/thread 분리 reconnect 계약이 중요
    SQLite 부재/손상 canonical JSONL compatibility/repair 좋은 authority 분리
    MCP startup 실패 required 여부에 따라 fail/continue policy가 명시적
    subagent 실패 child terminal state → parent summary parent가 부분 실패를 보존해야 함
    approval 불가 noninteractive에서는 action fail 암묵적 승인보다 안전
    process crash append된 rollout에서 resume 마지막 partially written record 처리 필요

    가장 좋은 점은 실패가 대부분 typed event/item 또는 thread state로 표면화된다는 것이다. 가장 어려운 점은 경계 수가 많아 “정상 종료의 정확한 순서” 자체가 correctness가 된다는 것이다.

    15. 공식 cloud 실행 계약

    공식 문서가 공개한 cloud task 흐름은 다음과 같다.

    1. container 생성과 선택 branch/commit checkout
    2. setup script 및 cache resume 시 maintenance script
    3. agent phase internet policy 적용
    4. AGENTS.md를 포함한 repository instruction 아래 command/edit/test loop
    5. final answer와 diff, 이후 PR 또는 follow-up

    setup phase에는 dependency 설치를 위한 network를 허용할 수 있고, secret은 setup에만 제공한 뒤 agent phase 전에 제거한다. container cache는 후속 task latency를 줄인다 (Cloud environments).

    이 계약은 로컬 thread runtime과 다른 deployment boundary다. cloud backend 내부 class 구조나 queue가 공개 core와 같다고 추정하지 않는다.

    17. 가장 강한 설계 결정

    1. Ordered command plane: user input, settings, interrupt, approval을 같은 submission ordering에 둔다.
    2. Single active turn per thread: mutable conversation authority를 명확히 한다.
    3. Turn/step context 분리: turn-scoped 설정과 request-scoped capability snapshot을 구분한다.
    4. Schema exposure ≠ dispatch registry: prompt cost와 capability를 독립적으로 관리한다.
    5. Sandbox ≠ approval: UX 정책과 OS security boundary를 혼동하지 않는다.
    6. JSONL canonical + query index projection: replay를 보존하면서 목록 조회의 전량 scan을 피할 구조다. N=10,000 성능은 별도 검증 대상이다.
    7. Typed app protocol: surface가 runtime 내부 객체에 종속되지 않는다.
    8. Subagent as thread, not callback: 별도 history/lifecycle/permission을 가진 실행 단위다.

    18. 주요 약점과 설계 부채 위험

    18.1 거대한 composition root

    SessionServices와 spawn arguments가 수많은 subsystem을 한 session에 조립한다. 명시적 dependency라는 장점과 동시에, session creation이 모든 feature 조합을 아는 central composition root가 되는 위험이 있다.

    18.2 feature matrix 폭발

    model capability × client surface × sandbox platform × tool mode × MCP/plugin/skill × collaboration mode의 조합이 크다. type safety만으로 의미적 조합 버그를 막지는 못한다.

    18.3 projection consistency

    JSONL과 SQLite가 분리되어 있는 만큼 stale index, crash 중 metadata patch, repair 시 bound, schema migration이 운영 책임이다.

    18.4 protocol evolution cost

    app-server가 좋아질수록 experimental negotiation, old client compatibility, notification ordering, connection authentication이 복잡해진다.

    18.5 생태계 trust surface

    plugin/skill/MCP/hook/connector가 늘수록 discovery UX보다 provenance, permission, credential separation, side-effect annotation의 신뢰가 더 중요해진다.

    18.6 제품 중심 provider abstraction

    OpenAI 외 provider hook이 존재해도 최신 model behavior와 hosted surface는 OpenAI 중심으로 진화한다. 다중 provider가 제품의 핵심인 Farad에는 그대로 적용할 수 없다.

    18.7 명시적 미확인 경계

    다음은 이 보고서에서 확정하지 않는다.

    • Codex app/Web/cloud backend가 고정 commit의 local core 또는 app-server를 그대로 사용하는지
    • proprietary desktop의 process/IPC, state store, Qt/Electron/native UI threading topology
    • app-server experimental protocol과 WebSocket transport의 장기 compatibility/SLA
    • 모든 MCP/hosted/dynamic tool에 shell과 동일한 approval·OS sandbox가 적용되는지
    • resume/fork가 in-flight process, approval, external side effect를 복원하는지
    • 10,000 thread의 list/open/search/rebuild latency, RSS curve, loaded-thread eviction 상한
    • NFS 위 JSONL·SQLite의 consistency, lock, round-trip, crash recovery 보장
    • local memory ranking/consolidation 품질과 장기 file schema
    • hosted request의 retention/privacy 또는 local test suite와 production backend의 conformance

    이 항목들은 “공개 소스가 없으니 약하다”는 점수가 아니라 판정 범위 밖이다. 교차 비교에서는 공식 행동 계약 또는 재현 가능한 benchmark가 생길 때만 승격해야 한다.

    19. Farad가 가져갈 것과 가져가지 말 것

    이 절은 비교 결론이 아니라 Codex 단독 분석에서 보이는 후보이며, 최종 우선순위는 Farad 판정 및 로드맵에서 다른 제품과 함께 결정한다.

    가져갈 가치가 큰 불변식

    • turn 설정 변경과 user input의 ordered command contract
    • TurnContext의 per-turn 설정과 StepContext의 per-request capability snapshot 분리
    • prompt exposure와 dispatch registry의 분리
    • transcript canonical + bounded metadata projection
    • UI/runtime 사이 typed application event protocol
    • subagent parent flush/fork/lifecycle state와 permission inheritance
    • cancellation 뒤에도 terminal event/result를 반드시 남기는 규칙
    • policy approval과 OS enforcement를 별도 계층으로 두는 보안 모델

    조건부로 가져갈 것

    • app-server: 두 번째 surface나 remote/headless 요구가 구체화될 때
    • SQLite projection: local derived index + NFS authority/repair 계약을 먼저 설계한 뒤
    • tool deferred search: schema 수가 실제 prompt budget을 압박할 때
    • 깊은 multi-agent graph: 실제 workflow가 artifact-aware orchestration으로 부족할 때

    그대로 가져오면 안 되는 것

    • Rust workspace의 crate 분할 수를 architecture maturity로 모방
    • OpenAI model capability matrix를 Farad provider 정책으로 hardcode
    • Linux bubblewrap 전제를 RHEL/HPC 운영에 검증 없이 강제
    • desktop-only 제품에 protocol/server/daemon을 선제 도입
    • SQLite를 NFS canonical state로 사용

    21. 최종 판정

    Codex의 설계 수준을 결정하는 것은 기능 개수가 아니다. 실행 순서, state ownership, OS boundary, tool exposure, durable replay, client protocol을 각각 독립 계약으로 만든 뒤 한 turn에 조립했다는 점이 핵심이다.

    Farad가 Codex와 경쟁하려면 Codex의 모든 surface를 따라갈 필요는 없다. 오히려 Farad가 이미 강한 provider 중립성, native desktop UX, scheduler, HPC/NFS 운영 계약을 유지하면서 다음 세 축만 Codex 수준으로 끌어올리는 편이 논리적이다.

    1. runtime command/event와 per-turn/per-request snapshot 수명의 명문화
    2. policy 승인 밖의 실제 command containment
    3. canonical transcript와 대규모 query projection의 검증 가능한 복구 계약

    이 세 축은 “나중에 기능을 더 넣기 위한 추상화”가 아니라, 현재 agent가 실제 파일과 프로세스를 다루고 session이 누적되는 순간부터 필요한 production foundation이다. 이 최종 권고는 A/B 근거를 Farad 조건에 적용한 D 등급의 판단이며, §18.7의 미확인 항목을 성능·제품 사실로 간주하지 않는다.
