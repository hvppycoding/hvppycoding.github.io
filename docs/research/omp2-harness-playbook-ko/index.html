    OMP2 하네스 아키텍처 읽기: The Harness Playbook 해설과 실제 코드

    한눈에 보기 · 읽는 시간 약 15분 · 2026-11-04 정리
    원문: The Harness Playbook — Can Bölük, Stencil (2026-09-02)
    코드 기준: can1357/oh-my-pi, omp2 브랜치, 2f92f3b (2026-09-04)
    문서 성격: 저작권자의 글을 문장별로 옮긴 전문 번역이 아닌 한국어 재구성 해설. 원문의 주장, 코드로 확인한 내용, 해석·제안을 구분했다.

    먼저 세 줄로

    1. 에이전트 하네스는 LLM API를 반복 호출하는 루프가 아니라 상태, 실행, 정책, 확장, UI를 책임지는 시스템 소프트웨어다.
    2. OMP2의 해법은 하나의 세션 정본(Session DOM + Journal), 여러 턴의 제어권을 갖는 Director, 공통 실행·취소·관측 계약, 모델별 차이를 흡수하는 추론 계층, 상태에서 파생되는 UI다.
    3. 이 개념은 단순한 미래 구상만이 아니다. OMP2의 2026-09-04 코드에서 해당 Rust 크레이트와 Python API, 단위·통합 테스트를 확인했다. 다만 코드의 존재 ≠ 전체 제품의 안정화·실행 검증 완료다.

    길을 잃지 않기 위한 개념 지도

    용어 책임 피하려는 문제
    Journal 사건·변경의 내구성 있는 이력, 분기와 복구 메시지만 저장하고 실행 상태는 잃어버림
    Session DOM Journal을 반영한 현재 세션의 구조화된 정본 메시지·TODO·작업·확장 상태가 각각 별도 정본
    Controller / Actor Controller가 상태 소유, Actor는 이를 구독·표시 TUI가 제어 상태까지 소유
    Director 여러 턴에 걸쳐 루프 제어, 다음 호출·종료·계속 실행 결정 Plan·Goal·강제 도구 모드가 서로 충돌
    ConVar 타입·범위·상속·지속성을 지닌 설정/제어 값 계층마다 중복 setter와 설정값
    Tool State Stream 입력·진행·결과·진단·취소를 한 호출 상태에 묶음 execute/preview/render 간 정보 복제
    Job 도구·서브에이전트·백그라운드 프로세스의 수명 관리 실행 종류마다 다른 spawn/poll/kill 구현
    Dynamic Tool Bus 긴 꼬리 도구를 안정된 발견/호출 표면 뒤로 숨김 상시 도구 스키마가 매 턴 비용을 증가
    Structured Renderer 같은 세션 상태를 TUI·웹·원격 UI로 투영 문자열 재파싱, UI별 별도 상태

    전체 그림을 추상화하면 다음과 같다.

            사용자 요청 / 원격 클라이언트 / 확장
                       │
                       ▼
           Controller / Agent Kernel
             ├─ Director stack (턴 제어)
             ├─ ConVar / Policy (설정·권한)
             ├─ Inference (모델/제공자 호환)
             └─ Tool / Job (실행·취소·한도)
                       │
                 Journal + DOM
                 기록 → 상태화
                       │
            ┌──────────┼──────────┐
            ▼          ▼          ▼
           TUI       원격 UI     검사/테스트
          (Actor)     (Actor)       (Actor)

    핵심 관계: Journal은 기록의 내구성을 맡고, DOM은 그 기록을 해석한 현재 상태를 표현한다. UI는 상태를 보는 창이고, Director는 실행을 계속할지 결정하는 제어자다. 역할이 다르므로 전부 하나의 거대한 객체로 합치자는 뜻은 아니다.

    01. 설계 범위: 하네스는 네 가지 제품을 동시에 견뎌야 한다

    저자는 로컬에서 여러 에이전트를 함께 실행하는 multiplexed workspace, 휴대전화 등에서 원격 에이전트를 다루는 remote driver, 세션을 관찰하는 spectator, 신뢰하지 않는 입력을 자동 처리하는 software factory를 출발점으로 삼는다.

    로컬 TUI만 상정하면 화면 객체가 세션의 주인이 되고, 중요한 상태는 프로세스 메모리에 남으며, 문제가 생기면 사람이 수습한다는 가정이 들어간다. 반대로 위 네 환경을 모두 고려하면 다음 경계가 필요해진다.

    1. 하나의 권위 있는 세션: 재개, 되돌리기, 분기, 복제, 검사가 동일한 상태에서 출발한다.
    2. 신뢰할 수 있는 제어 계층: 승인·정책·모델 호출·세션 소유권은 호스트에 둔다.
    3. 유한한 작업: 실행 시간, 결과 크기, 취소와 종료 가능성이 도구의 기본 계약에 포함된다.
    4. 명시적인 모델 호환성: 제공자 차이는 호출부에 퍼진 조건문이 아니라 규칙과 데이터로 관리한다.
    5. UI는 투영: TUI와 원격 화면은 동등한 상태 구독자이지 또 다른 정본이 아니다.

    원문의 나머지 개념은 이 다섯 요구를 구현하기 위한 수단이다. 원문 1장.

    02. 상태: 메시지를 저장하는 것과 세션을 복원하는 것은 다르다

    기존 방식의 결함

    채팅 메시지가 JSONL에 남아도 실행 상태가 보장되지는 않는다. 예를 들어 계획 모드의 활성 여부, TODO, 재시도 횟수, 서브에이전트 등록, 확장이 가진 임시 Map 등이 메모리에 별도로 있으면 과거 메시지로 이동하는 작업과 실행 상태를 과거로 돌리는 작업이 서로 어긋난다.

    저자는 Pi의 공식 확장 예제를 살펴보고, 분기 전환·재개 시 상태가 어긋나는 사례를 제시한다. 예컨대 턴 카운터가 모듈 변수에 있을 경우 rewind 후 메시지와 카운터가 불일치하고, 도구가 동적으로 추가되었다면 rewind 시 도구가 남아 있지만 재시작 시 사라질 수 있다. 이는 개별 확장 개발자의 부주의만이 아니라, 올바른 상태 소유 방식을 기본으로 제공하지 않는 API 문제다.

    OMP2의 구조

    세션은 개념적으로 <session><meta/><body/><queues/></session> 형태의 materialized DOM으로 표현된다. 메시지, 도구 호출, 작업 큐, 영속 확장 상태가 이 트리 안에 존재한다. Journal은 변경 이벤트를 보관하고 DOM은 이벤트를 적용해 현재 상태를 만든다.

    그 결과 rewind·fork·resume·원격 구독을 각각 별도 코드로 특별 처리하지 않고 같은 상태 변경과 재구성 문제로 다룰 수 있다. 실행 객체는 인덱스나 캐시를 가질 수 있지만 세션 정본을 별도로 소유하면 안 된다.

    코드 확인

    • crates/dom/README.md: DOM의 고정 루트, 원자적 트랜잭션, 스냅샷·패치 스트림을 명시.
    • crates/journal/README.md: .oms Journal, 콘텐츠 주소 기반 blob, 잘린 꼬리 복구, 분기 선택의 책임을 명시.

    읽을 때 주의할 점: DOM은 상태 모델이고 Journal은 지속 기록이다. 하나의 물리적 파일에 모든 데이터를 직접 넣는다는 의미가 아니다. 저장 매체, 스냅샷 전략, 실제 재생 성능은 별도 검증 대상이다. 원문 2장.

    03. 런타임: 실행을 맡길 수는 있지만 권한은 넘기지 않는다

    제어 호스트와 샌드박스

    신뢰하지 않는 작업 공간에서 코드를 돌릴 때 에이전트 엔진 전체를 VM에 넣으면 상태, 인증, 정책, 호스트 도구에 접근하는 통로가 복잡해진다. OMP2의 제안은 반대다. 호스트가 모델·정책·기록·승인·한도를 소유하고, 샌드박스는 제한된 실행 요청만 수행하도록 한다.

    여기서 결과 크기 제한은 단순 UX 옵션이 아니다. 신뢰하지 않는 프로세스가 수 GB를 반환해 호스트 메모리나 모델 컨텍스트를 잠식하지 못하도록 하는 안전 경계다.

    도구 호출은 하나의 상태 스트림

    기존에 흔한 renderCall → execute → renderResult는 한 작업의 프리뷰·실행·표시를 세 개의 분리된 인터페이스로 만든다. 파일을 중복 읽거나, 실행 결과 문자열에서 구조화된 정보를 다시 파싱하거나, 진행 상태를 별도 채널에 저장하게 된다.

    OMP2는 한 호출에 입력, 결과, 진단, 실행 시간, 상태를 붙이고 실행 중에는 구조화된 패치를 내보낸다. 모델이 읽는 결과와 사람이 보는 결과는 이 상태에서 각각 만들어진다. 실행이 끝나면 확정된 변경이 기록된다.

    Job과 취소

    백그라운드 셸, 서브에이전트, 별도 프로세스, 오래 걸리는 도구 호출은 모두 작업 ID, 상태, 출력, 신호, 취소라는 공통 관심사를 가진다. 따라서 도구마다 각자의 poll/kill/list를 복제하기보다 공통 Job 감독 계층을 둔다.

    취소 요청을 전달하는 것만으로 충분하지 않다. 도구가 취소 신호를 무시해도 프로세스·worker·격리 실행 단위에서 실제로 종료시킬 수 있어야 한다.

    코드 확인: crates/agent/src/jobs.rs에는 Tool / Subagent / Process 구분과 DOM에서 재구축하는 Job 감독 인덱스가 있다. 이는 실제 구현 단서이지만 모든 취소 경로가 운영 환경에서 검증되었다는 뜻은 아니다. 원문 3장.

    04. 제어 계층: Hook과 Director는 다르다

    Hook은 하나의 이벤트, 모델 호출, 턴에 관여한다. 반면 Director는 여러 턴 동안 에이전트의 행동과 사용자에게 제어를 반환할 시점을 결정한다.

    Plan Mode와 Goal Mode를 단순한 boolean 플래그로 처리하면, 어느 모드가 현재 루프를 소유하는지, 둘을 중첩할 수 있는지, 외부 모드로 언제 돌아가는지를 각 기능이 따로 처리해야 한다.

    OMP2에서는 세션 DOM에 존재하는 Director 스택을 통해 제어한다.

    Base → TodoReminder → Goal → Plan → ForceTool(write)
                                └─ 가장 안쪽 Director부터
                                   종료 후보를 판정

    모델 호출 전에는 바깥쪽에서 안쪽으로 요청을 준비하고, 턴 종료 후보가 생기면 안쪽에서 바깥쪽으로 판단을 전달한다. Director는 계속 실행, 사용자에게 반환, 하위 Director 진입, 자신 종료, 오류 종료 등을 결정한다. 하위 Director가 끝나면 상위 Director가 다시 종료 후보를 받는다.

    중요한 점은 모든 모드를 동시에 허용한다는 뜻이 아니다. 충돌하는 제어 자원(예: 모드, 루프, 특정 도구 선택)은 명시적으로 소유권을 판정할 수 있어야 한다.

    ConVar는 이와 다른 축이다. 모델·테마·실행 정책 같은 설정의 타입, 기본값, 저장 여부, 상속·복제 규칙을 선언한다. 즉 Director = 행동 제어, ConVar = 제어 값이다.

    코드 확인

    • crates/agent/src/director.rs: DOM-backed 스택, 제어 자원 Slot, Verdict.
    • crates/agent/src/directors/mod.rs: Plan·Goal·ForceTool·TodoReminder·Compaction·Autoresearch 등 등록.
    • crates/agent/tests/directors/kernel.rs: 계속 실행, 제어 우선순위, claim 충돌·승계 관련 테스트.
    • crates/py/python/omp/convars.py: Python에서 ConVar 선언·조회·변경 관찰 API.

    이 장은 Farad 같은 하네스에서 Plan/Goal/Bot/재시도/강제 도구 호출이 커질 때 특히 참고할 만하다. 원문 4장.

    05. 추론 계층: 모델에 대한 지식을 코드의 조건문으로 흩뜨리지 않는다

    모델과 제공자는 stream()이라는 단일 함수만 다르게 구현하는 존재가 아니다. 도구 강제 호출, 사고 모드, strict JSON, 캐시, 토큰 계산, 검색, 압축, 이미지와 음성 기능의 지원 형태가 다르다.

    저자가 지적하는 실패는 예외 규칙 하나하나가 틀렸다는 것이 아니다. 각자 맞는 예외가 여러 호출부에 중복으로 등장하고 서로 영향을 주는 구조다.

    OMP2의 방향은 모델/호스트별 특징을 KDL 등 구조화된 카탈로그로 관리하고, 규칙 충돌을 사전에 검출하는 것이다. 지원 정보가 없으면 무조건 불가능하다고 단정하기보다 알 수 없음을 표현할 수도 있어야 한다.

    예를 들어 "다음 턴에서 write를 반드시 호출"이라는 요구를 받았을 때:

    1. Director가 원하는 의도를 선언한다.
    2. 추론 계층은 해당 모델의 호환성·비용을 조회한다.
    3. 부작용 없는 soft prompt·native 설정부터 적용하고, 미이행 시 제한된 재시도로 강화한다.
    4. 끝내 만족시키지 못하면 조용히 무시하지 않고 실패를 알린다.

    스키마가 조금 틀린 도구 인자도 의미가 명확하다면 정규화할 수 있지만, 원래 모델 출력과 복구 사실은 관측 가능해야 한다. 오류를 감추는 관용성과 의미를 바꾸는 관용성은 구별해야 한다.

    코드 확인: crates/catalog/compat/ 아래 모델 계열·제공자별 KDL 규칙을 확인했다. 원문 5장.

    06. 도구 표면: 항상 보여 주는 도구는 적고 깊어야 한다

    상시 노출된 도구 스키마는 실제로 호출되지 않아도 요청 프리픽스와 토큰 생성에 영향을 준다. 원문은 특정 과제·샘플에서 핵심 도구 수를 줄이자 벽시계 시간이 개선된 측정을 제시한다. 이 수치를 다른 모델이나 업무의 일반적 성능 보장으로 읽어서는 안 된다.

    해법은 두 갈래다.

    첫째, 오래 살아남을 기본 도구는 깊은 의미를 제공한다. Read는 텍스트 파일만 읽는 것이 아니라 디렉터리, PDF, 문서, 데이터베이스, 이미지, 압축 파일, URL 등을 "이 리소스를 추론 가능한 표현으로 변환한다"라는 하나의 의미 아래 다룬다.

    둘째, 긴 꼬리 도구는 안정된 발견 표면 뒤에 둔다. OMP의 dyn은 추가 도구를 찾고 인자를 조회하고 실행하게 해 주며, 매번 모델의 최상위 도구 목록을 바꾸지 않도록 한다. 비슷한 작업을 여러 단계로 수행하는 경우 브라우저·컴퓨터처럼 제한된 코드 실행 표면을 둘 수도 있다.

    그 밖의 관련 원칙은 도구 인자에 의도(intent) 제공, 도구 계약 버전 표시, 명령문을 구조적으로 해석하여 실제 위험한 효과에 도달하는 순간 승인 판단이다. 문자열 정규식으로 Bash 전체를 승인·거절하는 방식과 구분된다.

    적용 시에는 도구를 무조건 합치는 대신 하나의 일관된 의미가 있는가, 캐시와 권한 경계가 유지되는가를 확인해야 한다. 원문 6장.

    07. 인터페이스: UI를 문자열 조립의 부작용으로 만들지 않는다

    원문은 ANSI가 섞인 문자열 배열을 계속 감싸고, 자르고, 다시 분석하는 TUI 렌더링의 비용을 프로파일링으로 보여 준다. 한 사례에서 렌더링 시간이 267초에서 90밀리초로 줄었다고 설명하지만, 이것은 해당 측정 조건의 결과다.

    OMP2는 의미가 있는 컴포넌트와 스타일링된 텍스트의 스트림을 기반으로 하여 렌더링 단계에서의 반복 파싱과 할당을 줄이려 한다. 같은 세션 상태를 TUI, 원격 화면, 서브에이전트 검사기가 서로 다른 방식으로 표시할 수 있다.

    여기서 흥미로운 세부 문제는 터미널의 scrollback이다. 터미널 위쪽으로 밀려 들어간 문장은 다시 쓰기 어렵다. 그러므로 화면을 계속 바꾸는 진행 표시(mutable)와 끝에만 추가되는 스트리밍 텍스트(append-only)는 기록에 확정하는 시점이 달라야 한다.

    Mutable 블록:   active → final → commit
                중간 스냅샷은 화면용

Append-only:    active ───────→ final → commit
                확정된 접두 행은 미리 history에 반영 가능

    저자는 이 불변 조건을 TLA+ 모델로 검토한 내용을 부록에 제공한다. UI 자동화에서 중요한 또 하나의 제안은 에이전트가 화면을 검증할 수 있도록 파괴적이지 않은 디버그 프로토콜을 먼저 제공하라는 것이다. 레이아웃 트리, 포커스, 합성 입력, 오프스크린 렌더 등으로 "테스트했다"의 의미를 고정하자는 취지다.

    이 장은 GUI에도 유효한 사고방식을 제공하지만, 터미널 scrollback의 불변 조건을 Qt 위젯/웹뷰에 그대로 이식해야 한다는 뜻은 아니다. 원문 7장.

    08. 기술 스택: 코드 생성 에이전트에게도 언어 관례가 중요하다

    저자는 모델이 코드를 생성하는 환경에서는 언어의 문법·표준 라이브러리뿐 아니라 프로젝트 관례의 균질성, 타입 검사, 실행 모델이 결과를 크게 좌우한다고 본다.

    OMP2는 Rust를 엔진에, 내장 Python을 확장 SDK에 선택했다. Rust는 상태·동시성·프로토콜 계층에서 강한 타입과 컴파일 시 검증을 주고, Python은 확장 기능을 쉽게 작성하고 AST를 조사하며 원격 실행 기능을 제공할 수 있다.

    다만 저자의 TypeScript에 대한 강한 평가는 경험에 기반한 주장이다. Rust/Python 조합이 모든 에이전트나 GUI 애플리케이션에 유일한 정답이라는 뜻은 아니다. 언어 선택보다 중요한 질문은 현재 문제가 어떤 계약과 경계에서 발생하는가다.

    코드 확인: crates/py/python/omp/extensions.py는 Python 확장에서 Director와 DOM Component를 선언하는 데코레이터를 제공한다. 원문 8장.

    09. 결론: 복잡성을 제거하는 대신 소유자를 정한다

    글이 주장하는 것은 "무조건 추상화를 많이 만들자"가 아니다. 구현이 어려운 공통 문제를 하네스 코어가 끝까지 해결하면, 사용자는 단순한 API로 접근할 수 있다.

    반대로 실측 없이 도입한 추상화는 무게만 더한다. 올바른 일반화는 공통 문제를 한 번 해결하지만, 잘못된 일반화는 모든 호출자에게 새 의무를 만든다.

    한 문장으로 요약하면: 정본을 통일하고, 제어권을 명시하고, 실행의 한계를 강제하고, 모든 출력은 검증 가능한 구조로 남겨라.

    부록에서 확인할 것

    부록 A — 상태 복원 실패 사례: 공식 Pi 확장에서 나타난 체크포인트·플랜 모드·턴 카운터·동적 도구·분기/북마크 문제를 코드 위치와 함께 제시한다. "메시지를 저장했다"와 "이전 세션을 재구성할 수 있다" 사이의 간극을 이해하기 좋다.

    부록 B — Elastic Speculative Slots: 터미널 출력에서 mutable/append-only 블록을 언제 확정할지, viewport와 scrollback의 불변 조건을 어떻게 검증할지 TLA+ 모델을 제공한다. 전체 하네스 일반론보다 좁은 렌더링 프로토콜의 형식 검증 사례다.

    그래서 OMP2에는 실제로 구현되어 있는가?

    다음은 2026-09-04의 omp2 커밋 2f92f3b에 한정한 소스 검토다. 코드와 테스트 파일은 확인했지만, 이 조사에서 직접 빌드·테스트·실사용 검증을 실행하지는 않았다.

    개념 확인한 근거 판정 범위
    Session DOM crates/dom/ 구현 존재
    Journal / 복구 crates/journal/ 구현·테스트 존재
    Director 스택 director.rs · 테스트 구현·테스트 존재
    Built-in Director directors/mod.rs Plan/Goal/ForceTool 등 등록 확인
    Job 감독 jobs.rs Tool/Subagent/Process 구조 확인
    모델 호환 규칙 crates/catalog/compat/ 데이터·컴파일 계층 존재
    Python 확장 API omp/extensions.py · 통합 계약 테스트 등록·계약 테스트 존재
    ConVar API omp/convars.py 선언·조회·관찰 API 존재

    확인하지 않은 것: 전체 크레이트 빌드 성공, 모든 OS의 샌드박스 동작, 원격 다중 클라이언트 환경의 복구 정확도, TUI 렌더의 재현 성능, 운영 환경에서의 안정성, 원문 발표 이후의 구현 완성도. 이 항목은 문서의 존재만으로 완료 판정하지 않는다.

    추가로 PHILOSOPHY.md는 철학을 더 발전시킨 문서다. 특히 구조화된 결과를 정본으로 두고 모델 프롬프트와 UI를 투영한다, 모델이 보는 도구 계약에 버전을 붙인다, 투기적 작업과 실제 효과의 경계를 나눈다는 원칙을 강조한다. 이 부분은 Playbook과 함께 읽을 가치가 높다.

    Farad와 같은 에이전트에 가져올 때의 우선순위

    아래는 원문이나 OMP2의 공식 로드맵이 아닌 적용 제안이다. Farad의 실제 변경 범위는 기존 코드·테스트·저장 계약을 별도로 확인한 뒤 결정해야 한다.

    우선순위 먼저 확인할 문제 바람직한 접근
    1. 상태 정합성 재개/분기 후 메시지 외 TODO, 모드, 작업 상태가 일치하는가 정본과 파생 상태를 구분하고 복원 계약 테스트 작성
    2. 여러 턴의 제어권 Plan/Goal/Bot/강제 호출/자동 계속 실행이 누가 종료 결정을 갖는가 Hook과 루프 소유자를 구분하고 충돌·중첩 정책 명시
    3. Tool/Job 수명 취소 후 실제 프로세스가 종료되는가, 결과가 중복 표시·저장되지 않는가 출력·취소·확정·진단의 공통 계약 정리
    4. 호환성 데이터 모델 이름별 예외가 호출부 곳곳에 중복되는가 의도와 구현을 분리하고 규칙 우선순위 테스트
    5. UI 투영 스트리밍 결과·메시지·도구 출력이 여러 UI에서 일치하는가 화면별 별도 상태 대신 구조화된 상태 투영
    6. 도구 목록 기본 도구 수가 실제 성능·캐시에 부담을 주는가 실측 후 상시 도구와 동적 발견 도구를 분리

    무조건 가져오지 않을 것: XML이라는 표현 형식 자체, Rust 재작성, 특정 TUI 알고리즘, OMP2의 도구 이름·승인 정책. 중요한 것은 이름이나 기술 스택을 모방하는 것이 아니라 실패 모드와 책임 경계를 해결하는 것이다.
