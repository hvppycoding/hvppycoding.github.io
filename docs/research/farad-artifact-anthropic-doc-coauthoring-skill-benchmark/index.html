    Anthropic doc-coauthoring 스킬 벤치마크

    조사일: 2026-07-14
    대상: Anthropic Skills — doc-coauthoring 원문
    참고: Anthropic Skills 저장소

    한 줄 결론

    doc-coauthoring은 예쁜 산출물을 만드는 스킬이 아니라, 독자가 실제로 이해하고 행동할 수 있는 문서를 공동으로 만드는 절차다. Farad Artifact에는 독자·목적을 먼저 고정하고 완성본을 낯선 독자로 검증하는 원칙만 얇게 흡수하되, 긴 대화식 문서 집필 프로세스 전체를 HTML·Confluence·PPTX 생성의 필수 관문으로 만들지는 않는 편이 맞다.

    무엇을 해결하려는 스킬인가

    이 스킬은 문서, 제안서, 기술 명세, 의사결정 문서처럼 구조화된 글을 작성하려는 요청에서 작동한다. 사용자가 가진 배경지식과 문서 독자가 알아야 할 내용 사이의 간극을 줄이고, 초안의 문장 품질보다 “처음 읽는 사람이 필요한 답을 얻는가”를 최종 기준으로 둔다.

    중심 흐름은 세 단계다.

    1. Context Gathering: 문서 종류, 주 독자, 읽은 뒤의 기대 효과, 템플릿·형식, 제약을 먼저 확인한다. 이어서 사용자가 정리하지 않은 정보도 자유롭게 쏟아내도록 하고, 빈칸을 겨냥한 5–10개의 질문으로 이해를 보정한다.
    2. Refinement & Structure: 구조를 합의하고 헤더와 placeholder가 있는 뼈대를 만든다. 가장 불확실한 핵심 섹션부터, 질문 → 5–20개 후보 발상 → 유지/삭제/통합 선택 → 누락 확인 → 초안 → 국소 편집 순으로 작성한다. 요약은 뒤로 미룬다.
    3. Reader Testing: 기존 대화 맥락이 없는 새 에이전트에게 문서와 현실적인 독자 질문만 주어 답하게 한다. 오해, 암묵적 전제, 모순을 찾으면 해당 섹션으로 돌아가 고친다.

    잘 설계된 부분

    1) 산출물보다 독자의 의사결정/행동을 먼저 묻는다

    초기 질문의 “누가 읽는가”와 “읽고 어떤 영향이 생겨야 하는가”는 서식 선택보다 앞선다. 같은 기술 내용도 운영 승인용 Confluence 페이지, 팀 설계 리뷰용 HTML, 발표용 PPTX에서 필요한 정보 밀도와 순서가 달라진다는 점을 정확히 겨냥한다.

    2) 정보 덤프를 허용한 뒤 구체 질문으로 수렴한다

    사용자에게 처음부터 잘 정리된 브리프를 요구하지 않는다. 팀 논의, 대안이 탈락한 이유, 조직 사정, 일정 압박, 의존성까지 받아 놓고 부족한 사실만 질문한다. 작성자가 이미 아는 배경을 누락해 문서가 얇아지는 문제에 효과적이다.

    3) 전체 재출력 대신 placeholder의 국소 교체를 쓴다

    뼈대를 먼저 파일/artifact에 만들고, 섹션을 확정할 때만 str_replace로 바꾼다. 긴 문서를 매번 통째로 재생성해 문체·링크·확정 문장이 흔들리는 위험을 줄이는 실용적인 편집 계약이다.

    4) “읽히는가”를 독립 QA 단계로 만든다

    최종 검토가 단순 교정이 아니라 fresh reader test다. 예상 질문 5–10개, 모호성·전제·모순 점검, 실패한 질문에 대한 역수정을 명시한다. 이 메커니즘은 LLM다운 그럴듯한 문장이나 장식적 슬라이드를 잡는 데도 유효하다.

    5) 사용자가 절차를 건너뛸 권한을 남긴다

    초대하되 강요하지 않으며, 자유 형식 작성을 선택하면 전환한다. 절차가 부담스러울 때 더 빨리 가는 방법도 제시한다. Farad처럼 실무 속도를 중시하는 제품에서 중요한 태도다.

    Farad Artifact에 가져올 것

    farad-artifact는 문서 공저 스킬과 분리된 표현/배포 스킬로 두고, 아래만 기본 계약으로 채택하는 것을 권한다.

    채택 항목 Farad식 적용
    목적·독자·결과 질문 생성 전 최소 브리프: audience, reader action, format, distribution을 확인한다. 모르면 합리적 가정을 한 줄로 밝힌다.
    주장 우선 구조 HTML/Confluence는 결론·결정·근거·다음 행동 순으로, PPTX는 슬라이드마다 하나의 주장과 필요한 증거만 둔다. 요약 슬라이드/요약문은 본문 결론이 정해진 뒤 쓴다.
    구조적 scaffold 산출 전 콘텐츠 outline과 페이지/슬라이드 수를 짧게 제시하고, 생성물에는 실제 제목·캡션·출처 자리만 남긴다. [To be written]을 최종 배포물에 남기지 않는다.
    국소 수정 “2번 슬라이드의 비교표만 고쳐라”처럼 수정 범위를 유지한다. 기존의 확정된 톤·레이아웃·내용을 전체 재생성하지 않는다.
    독자 QA 완료 전 5초 스캔, 핵심 질문, 출처/링크, 정보 계층, overflow를 검사한다. 필요하면 별도 fresh-review 에이전트로 ‘이 문서가 답하는 질문’을 시험한다.
    접근성 점검 이미지·SVG 다이어그램에는 의미 있는 캡션 또는 대체 텍스트를 제공한다. Confluence에 붙일 때 특히 필요하다.

    독자 테스트의 질문은 포맷별로 다르게 둔다.

    • HTML: “첫 화면에서 무엇을 결정/이해해야 하는가?”, “다이어그램만 보고 흐름을 설명할 수 있는가?”
    • Confluence: “업무자가 다음 행동과 담당자를 바로 찾을 수 있는가?”, “접힌 맥락 없이도 링크와 표가 뜻하는 바를 알 수 있는가?”
    • PPTX: “발표자가 말하지 않아도 슬라이드 제목만으로 논지가 이어지는가?”, “하나의 슬라이드에 경쟁하는 주장이 없는가?”

    Farad Artifact에 그대로 넣지 말 것

    필수 3단계 대화 흐름

    원문의 5–10 질문, 5–20개 브레인스토밍, 섹션별 반복 큐레이션은 큰 RFC에는 좋지만, 한 번에 배포할 HTML/PPTX를 만들려는 요청에는 마찰이 크다. Farad Artifact는 브리프가 충분하면 곧바로 제작하고, 불명확할 때만 질문 모드로 승격해야 한다.

    파일 편집 도구 계약

    create_file/str_replace와 매 수정 후 artifact 링크를 제공하라는 지시는 Claude의 환경·도구에 맞춘 구현 세부다. Farad에는 작업 폴더 파일 작성, 렌더/열기, 검증 결과 보고라는 자체 계약으로 번역해야 하며 특정 도구명을 베끼면 안 된다.

    외부 협업 도구 탐색의 기본 실행

    Slack·Teams·Drive·SharePoint 연결을 발견하면 문맥을 읽어 오는 흐름은 유용하지만, Farad에서는 권한·MCP 승인·명시적 refresh 원칙이 우선이다. 사용자가 지정하고 승인한 연결만 읽으며, “관련 자료를 찾아보겠다”는 추정 검색을 기본값으로 두지 않는다.

    대화 기록을 문서 부록으로 권하는 관행

    작성 대화를 링크하라는 최종 팁은 감사 맥락에는 쓸 수 있지만, 일반 배포 artifact의 기본값으로는 잡음과 민감정보 노출 위험이 있다. 필요한 경우에만 별도 결정 기록/출처로 관리한다.

    권장 스킬 구조에서의 위치

    farad-artifact는 결과물의 정보 설계·시각 톤·포맷별 생성·렌더 QA를 맡는다. 장문의 설계 문서나 합의 형성 자체가 목표일 때만 별도 farad-doc-coauthoring 또는 대화형 작성 모드가 이 스킬의 흐름을 사용할 수 있다. 즉 공저는 artifact의 선행 선택지이고, artifact는 공저의 하위 기능이 아니다.

    최소 시작 프롬프트는 다음 네 줄이면 충분하다.

    누구를 위한 자료인가?
    읽은 사람이 무엇을 이해하거나 결정해야 하는가?
    HTML, Confluence, PPTX 중 어느 형식으로 배포하는가?
    반드시 담을 사실·자료·제약은 무엇인가?

    답이 이미 요청에 있으면 다시 묻지 않고, 해당 가정을 출력물의 제작 메모에 짧게 기록한다. 이렇게 하면 원 스킬의 독자 중심 품질 기준은 지키되, Farad가 피하려는 과도한 절차와 ‘LLM이 진행을 지휘하는 느낌’은 만들지 않는다.
