    Anthropic frontend-design Skill 벤치마크

    조사일: 2026-07-14
    원문: SKILL.md · skill directory

    한 줄 요약

    이 스킬은 새 웹 UI를 만들거나 기존 UI의 시각 방향을 다시 잡을 때, 템플릿 같은 결과를 피하고 해당 과제에만 맞는 의도적 디자인 결정을 하게 하는 디자인 리드용 지침이다. 산출물 제작 스킬이라기보다, 구현 전에 미적 판단의 근거를 강제하는 품질 가드에 가깝다.

    발동 범위와 전제

    메타데이터의 범위는 “새 UI 구축 또는 기존 UI 재설계”이며, 주안점은 시각 방향·타이포그래피·기본 템플릿처럼 보이지 않는 선택이다. 모델은 소규모 디자인 스튜디오의 디자인 리드처럼 행동하고, brief가 모호하면 먼저 다음을 확정한다.

    1. 구체적인 주제 또는 대상
    2. 독자
    3. 페이지의 단 하나의 일

    그 뒤 사용자 선호, 제품 맥락, 과거 산출물을 단서로 쓰고, 대상의 실제 재료·도구·관습·용어에서 시각적 방향을 찾으라고 한다. 즉 유행하는 스타일을 먼저 고르는 것이 아니라 콘텐츠의 성격에서 디자인 언어를 도출한다.

    핵심 설계 원칙

    • 첫 화면은 “hero section”이 아니라 주장(thesis)이다. 제목·사진·데모·상호작용 중 대상의 특징을 가장 정확히 드러내는 하나를 택한다.
    • 타이포그래피는 정보를 실어 나르는 중립 요소가 아니라 성격을 만드는 요소다. 표시용/본문용/데이터용 역할을 나누고, 크기·두께·폭·자간을 의식적으로 정한다.
    • 번호, eyebrow, divider, label 같은 구조 장치는 콘텐츠의 실제 구조를 표현할 때만 쓴다. 예를 들어 01/02/03은 진짜 순서가 필요할 때만 허용된다.
    • 모션은 장식이 아니라 목적에 맞는 한 번의 연출이어야 하며, 산발적인 효과는 AI 생성물 같은 인상을 키울 수 있다고 경고한다.
    • 문구도 디자인 재료다. 사용자가 알아보는 대상과 행동으로 이름 짓고, 구체적·능동적·일관된 문구를 쓰며, 오류와 빈 상태는 다음 행동을 명료하게 안내한다.

    작업 흐름

    원문은 “brainstorm → explore → plan → critique → build → critique again”의 두 단계 작업을 요구한다.

    1. 코드 전 디자인 계획

    먼저 짧은 계획을 만든다.

    • Color: 이름 붙인 4–6개 hex 토큰
    • Type: 최소 두 역할의 서체와 사용 목적
    • Layout: 한 문장 설명과 ASCII wireframe으로 비교 가능한 배치안
    • Signature: 이 과제의 내용을 구현하면서도 기억될, 단 하나의 고유 요소

    2. 일반성 점검 후 구현

    계획의 각 요소가 “비슷한 요청이면 언제나 나올 답”인지 자문하고, 그렇다면 해당 brief에 맞는 선택으로 고친다. 수정 이유까지 분명히 한 뒤에만 코드에 들어가며, 색·타이포 판단은 수정된 계획에서만 파생한다. 구현 중에는 CSS specificity 충돌(예: 범용 section 규칙이 CTA 규칙을 덮는 문제)을 조심하도록 명시한다.

    3. 절제와 QA

    대담함은 한 곳에만 쓰고 나머지는 조용하고 규율 있게 유지한다. brief에 기여하지 않는 장식은 삭제한다. 품질 하한으로 mobile responsive, 키보드 focus, reduced motion을 요구하고, 가능하면 스크린샷으로 스스로 비평한다. 이는 미학 지침이면서 구현 완료 정의이기도 하다.

    ‘AI 같은 디자인’ 방지 장치

    원문은 다음 세 가지가 최근 AI 생성 디자인의 반복적 기본값이라고 콕 집는다.

    1. 크림색 배경 + 강한 serif + 테라코타 포인트
    2. 거의 검정 배경 + acid green/vermillion 포인트
    3. 신문 지면형 hairline rule + 0 radius + 조밀한 칼럼

    이 자체를 금지하지는 않는다. brief가 요구하면 따라야 하지만, 방향이 비어 있을 때 남는 자유를 이 기본값에 쓰지 말라는 뜻이다. 또한 “기억될 한 가지(signature)”를 제외하면 장식을 덜어 내는 self-critique와, 실제 콘텐츠·실제 행동에 맞춘 문구 규칙이 generic 함을 줄이는 핵심 장치다.

    Farad Artifact에 채택할 점

    farad-artifact는 이 스킬을 그대로 복제하기보다 아래를 품질 계약으로 흡수하는 것이 좋다.

    1. 산출 전 brief 고정: 독자, 매체(standalone HTML / Confluence / PPTX), 전달할 단일 결론, 읽은 뒤 할 행동을 먼저 적는다.
    2. 콘텐츠 우선 정보 구조: 다이어그램·표·강조 상자는 실제 이해 비용을 줄일 때만 둔다. 섹션 번호나 장식용 label은 실제 순서·분류가 있을 때만 쓴다.
    3. 작은 token sheet: 배경/표면/본문/보조/강조/선 색, 제목·본문·코드의 역할, 간격·radius를 짧게 선언해 HTML·SVG·PPTX 사이의 일관성을 지킨다.
    4. 하나의 signature, 나머지는 절제: artifact 한 편의 핵심 도식, 한 장의 비교표, 한 장의 핵심 숫자처럼 메시지를 고정하는 요소 하나만 강하게 하고, 그 외에는 여백과 위계로 읽힘을 만든다.
    5. 제작 후 자가 검토: 흐름, line wrap/overflow, 다이어그램의 화살표·범례·텍스트 가독성, 모바일 또는 슬라이드 투사 환경, 링크와 파일 경로를 확인한다. HTML은 screenshot/브라우저, PPTX는 렌더 결과로 검사한다.
    6. 문구 계약: 과장된 홍보 문구·빈 수식어 대신 구체적 제목과 능동형 설명을 사용한다. 한 행동/상태는 전 문서에서 같은 이름으로 부른다.

    Farad 톤과 충돌하거나 수정할 점

    원문 방향 Farad Artifact의 조정
    매 brief마다 “식별 불가능할 수 없는” 강한 시각 정체성과 실제 aesthetic risk Farad는 신뢰·가독성·일관성을 우선한다. 위험을 의무화하지 말고, 정보 전달상 이득이 있을 때만 제한적으로 허용한다.
    개성 강한 display/body 서체 조합 Farad의 배포 환경과 한글 가독성을 고려해 Pretendard 계열 본문, JetBrains Mono 코드 등 검증된 역할 서체를 기본으로 한다. 새 폰트는 배포 가능성과 필요성이 확인될 때만 사용한다.
    hero의 기억성, 상호작용·애니메이션 가능성 Confluence·PPTX에서는 재현성이 낮고, HPC/저사양 환경의 장식은 비용이 크다. 정적 HTML+inline SVG를 기본으로 하고 모션은 원칙적으로 제외한다.
    단일 강한 aesthetic signature Farad artifact에서는 시각적 쇼피스보다 핵심 주장 또는 다이어그램을 signature로 삼는다. 네온, glow, 과도한 gradient, glass/blur는 금지 목록에 가깝게 둔다.
    4–6색 palette의 페이지별 고유성 매체 간 동일성 때문에 Farad의 중립 팔레트와 소수의 의미 있는 강조색을 기본으로 한다. 프로젝트마다 새 색 체계를 발명하지 않는다.

    권고

    frontend-design은 계획 → 일반성 비평 → 구현 → 시각 QA라는 골격을 farad-artifact에 가져올 가장 좋은 선례다. 다만 “독특함”을 디자인 목표로 두지 말고, Farad에서는 주제에 정확하고, 조용하며, 재사용 가능한 시각 언어를 목표로 재정의해야 한다. 스킬 본문에는 anti-generic 검사와 함께 anti-spectacle 검사(네온/glow/무근거 gradient/불필요한 모션/장식성 카드·배지)를 명시하고, HTML·Confluence·PPTX별 검증 경로를 별도 체크리스트로 둔다.
