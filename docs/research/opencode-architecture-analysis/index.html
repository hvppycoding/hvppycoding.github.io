    1. 결론부터

    OpenCode의 본질은 단순한 터미널 챗봇이 아니다. 한 coding-agent runtime을 HTTP/OpenAPI 경계에 두고 TUI, 비대화형 CLI, 웹, 데스크톱, IDE, ACP, SDK가 공유하도록 만든 provider-neutral client/server 제품이다. 이 선택은 비교 대상 중에서도 특히 표면 확장성과 임베딩 가능성이 좋다. 75개 이상의 provider, MCP, LSP, plugin, custom tool, skill, command를 같은 server authority 아래 수용한다.

    그러나 2026-07-13의 고정 commit은 완성된 단일 architecture가 아니다. 현재 표준 요청은 여전히 SessionPrompt 중심의 V1 loop와 JSON message/part projection을 사용하고, 동시에 packages/core의 공용 EventV2 substrate는 V1 lifecycle 변경도 durable event로 append하고 같은 transaction에서 JSON message/part projection을 갱신한다. 그 위에 typed session projection, input admission, context epoch, 새 runner를 갖춘 V2가 이식되고 있다. V2에는 compaction continuation과 durable replay API까지 구현돼 있지만, durable multi-node ownership, bounded retry, 완전한 tool resolution과 cancellation settlement는 아직 남아 있다. 따라서 OpenCode를 평가할 때 현재 primary인 V1 runtime과 공용 durable 기반 위에서 더 강한 실행 의미론으로 이동 중인 V2를 합쳐서 이미 완성된 단일 runtime으로 서술하면 안 된다.

    한 문장으로 요약하면 다음과 같다.

    OpenCode는 개방형 provider·extension ecosystem과 다중 client/server spine이 매우 강하고, typed Effect lifecycle, V1/V2 공용 durable event/projector, typed V2 runtime으로 재구성 중인 야심찬 제품이다. 반면 현재 hot path는 매 agent step마다 전체 transcript를 다시 읽으며, 권한은 host sandbox가 아닌 사용자 승인 정책이고, 무제한 cache/queue와 문서-구현 불일치 때문에 장시간 server·공유 HPC/NFS 환경에는 그대로 적용하기 어렵다.

    핵심 판정은 다음과 같다.

    • 가장 강한 자산: 하나의 headless core와 OpenAPI/SDK로 여러 surface를 지탱하는 경계, 폭넓은 provider·extension 호환성, SQLite와 typed Effect resource lifecycle, V1/V2 공용 durable event+projection transaction과 V2 typed runtime 방향.
    • 가장 큰 구조 위험: V1/V2 이중 architecture 전환기라 session runtime, typed/JSON projection과 API 의미론이 중복되고 primary runtime이 여전히 큰 SessionPrompt orchestration에 모여 있다.
    • 가장 큰 보안 위험: permission parser와 승인 UX를 containment로 오해하기 쉽다. shell과 plugin은 사용자 계정 권한으로 직접 실행되고, 현재 소스의 plan·explore agent는 문서가 암시하는 read-only보다 훨씬 강한 권한을 갖는다.
    • 가장 큰 규모 위험: V1이 provider turn마다 전체 message/part history를 hydrate한 뒤 compaction view를 계산하고, instance cache·event queue·background-job registry에 명시적 bound가 없다.
    • Farad가 가져올 것: server/API anti-corruption layer, typed generated client, keyset pagination, durable event projection, resource scope/finalizer, tool-output truncation, provider adapter.
    • Farad가 거부할 것: per-turn instruction file/network read, in-process arbitrary plugin trust, whole-instance reload, unbounded SSE/cache, 문서상의 read-only를 shell allow로 구현하는 방식.

    분석의 제한도 명시한다.

    1. 공식 저장소의 기본 개발 브랜치는 빠르게 변한다. 함수와 line anchor는 모두 위 SHA에 고정했다.
    2. 공식 문서는 배포 시점이 commit과 완전히 일치하지 않는다. 특히 보안·운영 판정에서는 문서보다 고정 소스를 우선한다.
    3. source inspection으로 algorithm과 bound는 판정했지만, 이 보고서를 위해 별도 10,000-session benchmark나 NFS fault injection을 실행하지는 않았다. 해당 성능·운영 결론은 구조 기반 추론(D)이다.
    4. OpenCode Zen 같은 hosted service의 비공개 backend는 공개 client 계약 이상으로 추정하지 않는다.

    3. 제품 경계와 surface

    OpenCode는 MIT 라이선스의 공개 coding agent이며, 사용자가 보는 shell/TUI가 전부가 아니다. 현재 저장소와 공식 문서에서 확인되는 surface는 다음과 같다.

    표면 역할 runtime과의 연결
    opencode TUI 기본 대화형 terminal UI 기본값은 Worker 안 server에 RPC fetch; 명시한 network flag가 있으면 HTTP
    opencode run script/CI용 비대화형 실행 같은 session/server service를 CLI adapter가 사용
    opencode serve headless server HTTP + SSE + OpenAPI 3.1
    opencode web browser UI 포함 server HTTP server + web app
    Desktop beta Electron native shell loopback sidecar 또는 외부 server에 연결
    IDE extension editor context와 terminal launch 독립 engine이 아니라 TUI/server 조작·context 전달 중심
    opencode acp editor/agent client protocol stdio JSON-RPC ACP adapter + 내부 server
    JS/TS SDK 자동화·임베딩 server OpenAPI에서 생성된 typed client

    공식 Server 문서는 headless HTTP server와 /doc의 OpenAPI 3.1, SDK 생성을 명시한다. index.ts는 TUI, attach, run, serve, web, ACP 등 command를 한 binary에 등록한다. ACP adapter는 acp.ts, desktop sidecar는 desktop/src/main/server.ts와 sidecar.ts에 구현되어 있다 [A/B].

    현재 desktop은 과거의 인상과 달리 Tauri가 아니라 Electron이다. 고정 commit의 packages/desktop/package.json은 Electron 42.3.3을 사용한다. utility-process sidecar가 loopback에서 random password로 server를 띄우고 renderer는 shared SolidJS app을 사용한다. 외부 URL과 WSL 연결도 별도 path로 다룬다 [A].

    이 surface 전략의 architecture적 의미는 크다. UI가 provider SDK와 tool object를 직접 소유하는 것이 아니라 server protocol에 의존하므로 새 client를 추가할 때 runtime을 복제하지 않는다. 반대로 API authentication, directory routing, reconnect, SSE consistency, schema version transition이 모두 제품의 핵심 correctness 문제가 된다.

    4.1 기본 TUI의 실제 process topology

    공식 문서는 “TUI를 시작하면 임의 hostname/port의 server를 띄운다”고 설명한다. 그러나 고정 commit의 기본 path는 더 흥미롭다. tui.ts#L210-L252는 TUI parent가 Bun Worker를 만들고 http://opencode.internal이라는 synthetic URL을 쓴다. worker.ts#L24-L43는 요청을 Server.Default().app.fetch(request)에 직접 전달하고 GlobalBus event를 RPC로 parent에 forward한다 [A].

    즉 기본 TUI에는 UI와 runtime을 같은 OS process의 Bun Worker로 분리하되 TCP listener를 열지 않는 worker-isolated direct-fetch topology가 있다. 사용자가 hostname/port 같은 network flag를 주거나 serve를 실행할 때 real listener가 열린다. 이 선택은 기본 local 실행의 port 충돌·노출을 줄이면서 server/client 경계를 유지한다. 문서의 “random port”는 현재 source와 drift한다.

    Worker는 shutdown 때 scoped resource를 dispose하고, reload signal에서는 config를 invalidate한 뒤 모든 instance를 dispose한다. lifecycle은 분명하지만 reload granularity는 process 전체에 가깝다. Farad의 항목별 explicit refresh/delta reconcile과는 다른 비용 모델이다.

    4.2 headless·desktop topology

    opencode serve는 Effect HTTP listener를 열고 선택적으로 mDNS를 광고한다. server layer는 graceful close 후 강제 close fallback을 갖는다. 기본 bind는 127.0.0.1:4096이고 Basic auth는 password 환경변수가 있을 때만 활성화된다. serve.ts#L15-L17와 web.ts#L40-L42는 password가 없으면 실행을 거부하지 않고 warning만 출력한다 [A].

    Electron desktop은 별도 utility process sidecar를 loopback에 띄우고 random password를 주므로 일반 serve보다 안전한 기본값이다. renderer crash와 agent server lifetime도 분리된다. 그러나 외부 server 연결을 허용하므로 remote transport의 TLS, auth, directory authority는 사용자 운영 책임으로 남는다.

    5.1 directory routing은 server authority의 일부다

    workspace-routing.ts#L69-L88는 session이 있으면 그 session location을 우선하고, 아니면 directory query, x-opencode-directory header, 마지막으로 server cwd를 사용한다. 정규화한 directory별로 InstanceStore가 service graph를 boot하고 동시 boot를 coalesce한다 [A].

    이는 multi-workspace server를 자연스럽게 지원하지만 보안 함의도 있다. Basic-auth credential을 가진 remote client는 directory를 선택하고 file, PTY, shell, session endpoint를 호출할 수 있다. 이 middleware 층에는 per-project ACL이나 tenant isolation이 없다. 따라서 server password는 단순 UI login이 아니라 해당 OS 사용자로 접근 가능한 workspace와 command 실행 전반의 capability로 취급해야 한다 [D].

    5.2 instance cache와 lifecycle

    InstanceStore는 normalized directory를 key로 Map을 유지하고 concurrent initialization을 Deferred로 합친다. dispose, reload, dispose-all은 있지만 capacity나 idle TTL eviction은 없다. Effect service 쪽 instance-state.ts#L24-L35도 ScopedCache capacity를 Number.POSITIVE_INFINITY로 둔다 [A].

    짧게 실행하는 local TUI에서는 큰 문제가 아닐 수 있다. 하지만 하나의 headless server로 수천 개 directory를 오래 방문하면 config, plugin, MCP, LSP 등 per-instance object가 명시적 dispose 전까지 누적될 수 있다. long-lived server에는 LRU/idle disposal 또는 운영상 주기적인 recycle이 필요하다 [D].

    6.1 loop orchestration

    prompt.ts#L1081-L1347의 runLoop는 다음 책임을 한 loop에 조정한다 [A].

    1. session을 busy로 표시하고 compacted transcript view를 계산한다.
    2. 마지막 user/assistant, unfinished tool/task, step count와 overflow를 판정한다.
    3. 첫 step에서 title 생성, 종료 시 summary 같은 auxiliary work를 fork한다.
    4. subtask/compaction marker를 처리한다.
    5. agent와 model, step limit을 선택하고 새 assistant record를 만든다.
    6. built-in/custom/MCP tool registry를 resolve한다.
    7. skill 목록, environment, instruction system text, MCP instructions, model messages를 병렬 조립한다.
    8. plugin hook으로 message/parameter/system을 변환한다.
    9. SessionProcessor에 streaming step을 맡기고 continue/break/compact를 결정한다.
    10. run 뒤 오래된 tool output pruning을 비동기로 수행한다.

    SessionRunState.ensureRunning은 같은 process의 같은 session에서 active loop를 하나로 직렬화한다. 이미 실행 중이면 caller가 그 run에 join하고, abort는 그 실행을 interrupt한다. distinct session은 동시에 실행될 수 있다 [A].

    이 구조는 central coordinator가 있어 의미를 찾기 쉽지만 SessionPrompt가 context, tools, plugin, compaction, background task, termination을 동시에 아는 큰 orchestration module이 되었다. V2가 이를 typed core service로 분해하려는 이유가 소스 주석에 직접 드러난다.

    6.2 streaming과 tool settlement

    기본 provider 실행은 Vercel AI SDK의 streamText다. session/llm.ts#L280-L324는 AI SDK 내부 retry를 maxRetries: 0으로 두고, OpenCode의 외부 retry schedule이 whole stream을 관리하게 한다. experimental native @opencode-ai/llm path도 있지만 지원되지 않는 경우 AI SDK로 fallback한다 [A].

    processor.ts는 stream 중 text/reasoning delta, tool pending/running/completed/error, snapshot, patch, usage와 finish reason을 message part로 증분 저장한다. tool call은 AI SDK가 병렬 dispatch할 수 있으며, 동일 tool과 동일 input이 3회 반복되면 doom_loop permission을 물어 무한 반복을 human-in-the-loop로 끊는다 [A].

    좋은 점은 model의 최종 답이 올 때까지 메모리에서만 기다리지 않는다는 것이다. client는 SSE로 progress를 받고 DB에서 projection을 다시 읽을 수 있다. V1의 message/part lifecycle update는 공용 EventV2 durable log에 먼저 append되고 같은 transaction에서 mutable JSON projection으로 반영된다. 반면 message.part.delta 같은 고빈도 live delta와 legacy SSE transport는 비영속이므로 둘을 durable lifecycle event와 구분해야 한다.

    7. V2 architecture: checklist보다 앞섰지만 recovery 경계는 남음

    V2는 V1도 사용하는 공용 durable event/projector substrate 위에서 packages/core와 typed @opencode-ai/server API를 중심으로 다음 요소를 도입한다.

    • aggregate별 monotonic sequence를 가진 durable event와 projector
    • typed session_message projection과 context epoch
    • session_input의 admitted/promoted sequence로 queue/steer를 영속 표현
    • one-local-owner run coordinator
    • runner history를 latest compaction/baseline 이후로 제한
    • tool call 기록과 local settlement를 분리한 execution service
    • wait/queue/steer 등 새로운 API 의미론

    동시에 server entry는 legacy V1 API와 V2 API layer를 한 Effect graph에 mount한다 (httpapi/server.ts) [A].

    새 runner의 header checklist는 설계 의도를 보여 주지만 일부 항목이 실제 code path보다 늦게 갱신된 stale self-documentation이다. packages/core/src/session/runner/llm.ts#L44-L86는 완료와 미완을 체크리스트로 기록하지만, 판정은 아래 implementation과 함께 해야 한다 [A].

    완료된 핵심:

    • local active-run drain과 step limit
    • message translation과 한 provider turn streaming
    • assistant/reasoning/tool event의 durable 기록
    • 기록된 local tool call을 eager start하고 모두 settlement할 때까지 대기
    • active provider turn 중 들어온 user steering의 continuation
    • step 시작·종료 snapshot capture와 changed-files 기록
    • 자동/overflow compaction 후 다음 provider turn continuation
    • finite durable history와 after sequence 기반 replay-then-live event consumer

    남은 핵심:

    • clustered 환경의 durable multi-node ownership
    • durable busy/retry/idle/interrupted/failure status
    • interruption attachment replacement
    • bounded provider retry와 repeated-tool-call policy
    • built-in/MCP/plugin/structured-output tool의 완전한 resolution
    • incremental snapshot/patch/retry notice parity, scoped progress/plugin integration과 cancel settlement
    • durable final execution status와 restart-safe continuation ownership
    • streamed delta coalescing과 covering projection index 최적화
    • title/summary/cleanup의 bounded execution

    compaction.ts와 runner의 ContinueAfterCompaction/ContinueAfterOverflowCompaction transition은 checklist와 달리 compaction continuation을 구현한다. 또한 typed protocol의 GET /api/session/:sessionID/history와 GET /api/session/:sessionID/event?after=<seq>는 각각 finite durable page와 replay-then-live durable SSE를 제공한다 (groups/session.ts, handlers/session.ts) [A].

    따라서 V2는 단순 계획이 아니라 compaction continuation과 durable replay까지 동작하는 migration architecture다. 다만 durable event replay와 durable execution recovery는 같지 않다. owner lease, terminal/busy/retry status, bounded retry, restart-safe continuation이 남았으므로 foundation과 current recovery/ownership 점수를 분리해야 한다 [D].

    8. 저장 모델과 event 흐름

    8.1 SQLite가 local authority다

    기본 DB filename은 installation channel에 따라 달라진다. latest·beta·prod channel은 XDG data directory 아래 opencode.db를 쓰고, 그 밖의 channel은 opencode-<channel>.db를 쓴다. OPENCODE_DB는 :memory:, absolute path, 또는 XDG data directory 기준 relative filename을 받을 수 있다. 구현상 node-local DB 배치 수단은 있지만 공식 deployment contract로는 충분히 문서화되지 않았다. DB initialization은 database.ts에서 journal_mode=WAL, synchronous=NORMAL, busy_timeout=5000, 약 64 MiB negative cache_size, foreign key를 설정한다 [A].

    session/sql.ts는 전환기의 이중 저장 모델을 그대로 보여준다 [A].

    table 역할
    session project/workspace/parent/directory/title/version/share/summary/cost/tokens/revert/permission/agent/model/timestamps
    message V1 message info를 JSON data로 저장, session/time/id index
    part V1 text/reasoning/tool/file/snapshot/patch/step/retry 등 JSON part, message/session index
    todo session todo projection
    session_message V2 typed/event-projected row, per-session sequence unique 및 type/sequence index
    session_input queue/steer input, admitted/promoted sequence
    session_context_epoch baseline/snapshot과 baseline sequence

    session row에 workspace와 directory를 저장하므로 resume request가 다른 current directory에서 와도 원래 instance로 route할 수 있다. parent ID를 통해 subagent/fork tree도 표현한다.

    8.2 durable event와 projection

    packages/core/src/event.ts는 aggregate owner/sequence와 exact event ID/type/data를 저장하고, 같은 SQLite immediate transaction에서 projector를 적용한 뒤 publish한다. replay 시 event payload와 projected result의 일치도 검증한다. session/projector.ts는 V1/V2 projection을 갱신한다 [A].

    구체적으로 V1 schema의 session.created/updated/deleted, message.updated/removed, message.part.updated/removed도 { durable: { aggregate: "sessionID", version: 1 } }로 정의되고, V1 session service가 EventV2Bridge를 통해 publish한다. 따라서 JSON row는 mutable serving model이지만 그 lifecycle 변경의 commit source는 durable event다. 별도 durable option이 없는 message.part.delta 같은 live delta는 이 보장에서 제외된다 (schema/src/v1/session.ts, opencode/src/session/session.ts, event-v2-bridge.ts) [A].

    이는 미래의 recovery와 audit에 좋은 기반이다. command가 commit되기 전에 client event가 먼저 나가는 문제를 줄이고, aggregate sequence가 order의 권위가 된다. EventV2Bridge는 여기에 directory/workspace/project context를 붙여 legacy GlobalBus 소비자와 durable-event 소비자를 연결한다.

    하지만 현재 client event transport와 durable log를 동일시하면 안 된다. handlers/event.ts#L31-L72는 연결마다 Queue.unbounded를 만들고 10초 heartbeat와 location-filtered event를 SSE로 보낸다. SSE encoding에 replay 가능한 durable sequence를 id로 제공하거나 Last-Event-ID로 resume하는 계약은 이 legacy route에 없다 [A].

    따라서 disconnect 후 client correctness는 “놓친 event를 replay”가 아니라 REST/DB의 authoritative projection을 refetch하고 SSE를 다시 구독하는 방식이어야 한다 [D]. V2가 durable event를 갖고 있어도 legacy client transport가 자동으로 exactly-once가 되는 것은 아니다. 반면 새 typed V2 route는 after aggregate sequence 이후의 durable history를 먼저 replay한 뒤 live event로 전환한다. 즉 replay primitive의 부재가 아니라 legacy client transport가 그것을 사용하지 않는 이중 API 상태가 정확한 판정이다 [A/D].

    8.3 unbounded event path

    legacy SSE는 client별 unbounded queue를, core event service는 aggregate/global unbounded PubSub를 사용한다 (event.ts#L175-L189) [A]. Core에는 capacity를 넘으면 SubscriberOverflowError로 종료하는 opt-in allBounded(events, capacity) dropping-queue helper도 있다. 그러나 고정 commit의 legacy SSE route는 이를 사용하지 않는다 [A]. 로컬 TUI처럼 consumer가 빠르고 연결 수가 작다는 전제에서는 간단하다. 느린 remote consumer나 event 폭주 시 메모리 backpressure가 없고 connection별로 누적될 수 있다. long-running multi-client server의 shipping default/integration에는 bounded queue, coalescing, overflow 후 snapshot/refetch signal이 더 필요하다 [D].

    9. transcript, context와 compaction

    9.1 append되는 내용과 model view는 다르다

    V1의 message/part는 text, reasoning, tool lifecycle, file, snapshot, patch, step, retry, subtask, compaction까지 세밀하게 보존한다. compaction은 과거 row를 삭제하지 않고 synthetic compaction user part와 summary: true인 assistant summary를 추가한다. 이후 model에 보이는 view만 summary와 최근 turn으로 재구성한다 [A].

    session/compaction.ts의 주요 정책은 다음과 같다.

    • model limit overflow 시 자동 compaction
    • 기본적으로 최근 2개 turn을 원문으로 유지
    • 사용 가능한 context의 약 25% 또는 2,000~8,000 token 범위의 preserve budget
    • 이전 summary가 있으면 새 summary 입력에 포함
    • summary 입력의 media 제거와 tool output 축약
    • summary 후 작업이 남아 있으면 synthetic continue message 추가
    • 오래된 tool output은 최근 약 40,000 token을 보호하고, 최소 약 20,000 token 절감이 있을 때 prune
    • skill tool output은 prune 대상에서 보호

    이 설계는 transcript 재현성과 model-context 비용을 분리한다는 점에서 좋다. 원문과 tool lifecycle을 DB에 남기므로 UI, resume, share가 summary text만 보는 구조는 아니다.

    9.2 V1의 치명적인 read amplification

    compact model view와 DB hot path도 구분해야 한다. MessageV2.page는 base64 cursor의 {id,time}을 이용한 keyset pagination을 하고, 한 page의 parts를 batch hydrate한다. 이 자체는 좋은 구현이다 [A].

    그러나 같은 파일의 stream helper는 50개씩 모든 page를 순회해 full transcript를 메모리에 materialize하고, filterCompactedEffect#L574는 그 전체를 읽은 뒤 compacted view를 filter/reorder한다. V1 runLoop는 provider/tool step마다 이 함수를 호출한다 [A].

    세션에 message/part가 N개 누적되고 한 user request가 K개의 model/tool step을 만든다면 history 조립만 대략 O(KN)이다. compaction 이전 row도 DB에서 읽은 후 버린다. 이는 Farad의 “누적 10,000개에서 turn hot path는 O(1) 또는 visible/active window” 계약과 정면으로 충돌한다 [D].

    session 전체 조회, fork의 prefix clone, share 최초 sync도 full transcript를 hydrate할 수 있다. 이들은 명시적 1회성이라 turn마다 반복되는 것보다는 낫지만, 10k 규모에서는 pagination·background copy·bound가 필요하다.

    9.3 V2 context epoch가 해결하려는 것

    V2의 history.ts는 latest compaction/context baseline의 sequence 이후만 index query한다. context-epoch.ts는 instruction/context baseline과 snapshot을 byte-stable하게 저장해 context 변경을 명시적으로 reconcile한다 [A].

    이는 두 문제를 함께 개선하는 올바른 방향이다.

    1. 과거 compaction 이전 row를 매 step 읽지 않아도 된다.
    2. live instruction이 바뀌었을 때 같은 session의 resume context가 조용히 변하는 대신 baseline change를 기록할 수 있다.

    다만 retained context window 자체는 여전히 materialize되며, V2 runner의 durable status/owner와 restart recovery는 남아 있다. 따라서 “10k 문제가 이미 해결됐다”가 아니라 “해결 가능한 schema와 query path가 생겼다”가 정확하다 [D].

    10. permission model과 실제 security boundary

    10.1 정책 평가 자체는 이해하기 쉽다

    공식 Permissions 문서의 기본 모델은 allow, ask, deny와 pattern rule이다. 여러 rule 중 마지막으로 match한 rule이 이기므로 broad default 뒤에 narrow exception을 둘 수 있다. tool은 실행 전 ctx.ask()를 통해 permission service에 요청하고, 사용자는 once, always, reject로 답한다 [B].

    소스도 이 구조를 그대로 구현한다. permission/index.ts#L28-L37는 마지막 matching rule을 선택한다. 이 V1 service에서 pending request와 always approval은 permission/index.ts#L42-L174의 per-directory InstanceState map/array에만 저장된다. 같은 instance의 여러 session이 approval을 공유하지만 reload/dispose/process restart 때 소멸한다. reject하면 같은 session의 pending request도 함께 reject하고, instance finalizer는 남은 deferred를 실패시킨다 [A].

    V2 permission은 의미가 다르다. pending request는 여전히 local Map이지만, always reply에 request.save resource가 있으면 project-scoped rule을 SQLite permission table에 저장하고 이후 평가에 병합한다. saved rule의 list/remove API도 있다 (core/src/permission.ts, permission/saved.ts) [A].

    장점:

    • permission name과 path/command pattern을 분리해 세밀한 policy를 만들 수 있다.
    • deny는 prompt가 아니라 tool execution 앞의 deterministic gate다.
    • once/always의 UX가 단순하며 동일 session의 중복 ask를 해소한다.
    • subagent session에도 parent session row의 explicit deny와 external-directory rule을 전달한다.

    한계:

    • V1 always는 이름과 달리 disk policy가 아니며 해당 directory instance 수명에만 남는다.
    • V2 saved always와 달리 V1 approval memory는 reload/dispose/restart 후 복구되지 않는다. V2에서도 pending interaction과 save resource가 없는 reply는 process-local이다.
    • rule match는 authorization decision일 뿐 OS-level isolation이 아니다.

    10.2 기본 권한은 “deny by default”가 아니다

    현재 native agent 기본값은 agent.ts#L119-L136에 명확하다 [A].

    • "*": "allow"
    • doom_loop: ask
    • workspace 밖 directory: ask, 일부 temp/skill/reference path allow
    • question/plan transition: deny 후 agent별 override
    • 일반 read: allow
    • .env와 .env.*: ask
    • .env.example: allow

    즉 OpenCode의 안전성 기본은 “모든 위험 tool을 먼저 묻는다”가 아니라 대부분 허용하고 몇 개의 민감 action/pattern만 ask/deny다. 조직 환경에서는 project/global/managed config로 permission을 명시적으로 강화해야 한다.

    10.3 plan과 explore는 기술적으로 read-only가 아니다

    현재 source의 중요한 security drift다.

    • plan agent는 edit/write/apply-patch 계열을 deny하고 plan Markdown 경로만 예외로 둔다. 그러나 bash를 ask/deny로 override하지 않으므로 global "*": allow를 상속한다 (agent.ts#L156-L180). shell로 rm, redirect, script를 실행하면 filesystem을 바꿀 수 있다.
    • explore agent는 먼저 "*": deny를 두지만 bash를 명시적으로 allow한다 (agent.ts#L196-L217). 설명과 prompt가 탐색 전용이어도 shell capability는 임의 side effect를 낼 수 있다.

    따라서 문서의 “plan은 command 전에 묻는다”, “explore는 read-only”를 security invariant로 사용할 수 없다. 모델이 지시를 따를 것이라는 behavioral expectation과 tool-level effect safety는 다르다. read-only agent를 보장하려면 shell을 deny하거나 read-only command broker/OS sandbox를 따로 둬야 한다 [D].

    10.4 shell permission parser는 containment가 아니다

    tool/shell.ts#L257-L310는 tree-sitter Bash/PowerShell AST를 parse하고 알려진 command argument와 path를 scan해 shell pattern 및 external_directory permission을 요청한 뒤 host shell을 직접 spawn한다 [A].

    이 방식은 raw string prefix match보다 낫다. git -C, file argument 등 정적 command 구조를 더 잘 분류하고 workspace 밖의 명시적 path를 별도로 물을 수 있다. 그러나 다음은 막지 못한다.

    • shell expansion, command substitution, script 내부의 동적 path
    • parser가 의미를 모르는 executable 자체의 side effect
    • network, process, credential, device 접근
    • workspace 안에서의 destructive command
    • allow된 interpreter가 실행하는 다음 단계 code

    OpenCode의 shell은 container, chroot, seccomp, macOS Seatbelt 같은 OS sandbox 안에서 실행되지 않는다. permission은 사용자 승인과 audit UX이지 악성/오작동 code의 capability containment가 아니다 [D].

    10.5 plugin·custom tool도 같은 host authority를 쓴다

    local JS/TS plugin과 NPM plugin은 runtime process 안에서 import된다. plugin context에는 SDK client, directory/worktree와 Bun shell $가 주어지며 hook/custom tool은 사용자 계정 권한으로 실행된다. custom tool도 arbitrary language를 shell로 감쌀 수 있고, 같은 이름이면 built-in을 override할 수 있다 (Plugins 문서, Custom Tools 문서, tool/registry.ts) [A/B].

    따라서 .opencode와 config plugin 목록은 단순 prompt data가 아니라 executable supply-chain boundary다. NPM plugin auto-install, Bun dependency installation, local plugin import에 signing이나 separate process sandbox는 없다. 신뢰하지 않는 repository를 열 때는 config/plugin/tool/command 파일을 code execution surface로 봐야 한다 [D].

    10.6 subagent 권한 전파

    subagent-permissions.ts#L4-L26는 child session에 parent session row에 저장된 explicit deny와 external-directory rule을 전달하고, child가 별도로 허용하지 않으면 nested task와 todowrite를 deny한다 [A].

    이 범위에는 parent agent의 native/default rule과 agent-level deny가 포함되지 않는다. 해당 restriction은 parent agent 자신만 지배하고 child의 주 capability는 child agent 자체 permission이 결정한다. 따라서 이는 일반적인 “parent hard deny 보존”이나 capability-subset lattice가 아니라 session policy의 deny 일부 보존 + child-specific policy다. Parent agent의 shell deny만 믿고 delegation의 side effect를 막을 수는 없다 [A/D].

    11. agents, subagents와 background work

    OpenCode agent config는 primary/subagent/all mode, prompt, model/variant, temperature/top-p, provider options, step limit, permission rules를 지정한다. native source에는 build, plan, general, explore와 hidden compaction, title, summary가 있다 [A]. 공식 문서가 언급하는 Scout는 고정 commit의 native registry에 존재하지 않는다.

    11.1 foreground subagent

    tool/task.ts는 parent ID를 가진 child session을 만들고 선택한 subagent, title, permission을 설정한다. task_id를 다시 주면 기존 child session을 resume할 수 있다 [A].

    이 설계의 좋은 점:

    • child 대화를 별도 session/transcript로 유지해 parent context를 무한히 오염시키지 않는다.
    • parent-child relation이 DB에 남아 UI에서 tree로 탐색할 수 있다.
    • task result만 parent tool output으로 돌아오므로 orchestration boundary가 분명하다.
    • 동일 child resume를 protocol로 지원한다.

    기본 task는 foreground에서 child가 끝날 때까지 기다린다. 서로 다른 child session과 V1 tool call은 동시에 실행될 수 있지만, 한 session의 active run은 local SessionRunState가 직렬화한다.

    11.2 background subagent는 experimental·process-local이다

    background mode는 OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS flag 뒤에 있다. core의 background-job.ts#L114-L123는 registry가 scoped, process-local이고 intentionally non-durable라고 주석으로 명시한다 [A].

    완료 후 synthetic parent prompt로 결과를 주입하고 parent loop를 다시 깨울 수 있으나:

    • process restart나 scope close 시 running job과 status를 잃는다.
    • active execution은 interrupted된다.
    • completed/error/cancelled entry도 map에 남고 instance disposal 전 자동 retention bound가 없다.
    • durable session row가 있어도 scheduler/job ownership 자체가 복구되는 것은 아니다.

    따라서 이는 편리한 local concurrency이지 durable workflow engine이 아니다. 장시간 task, 예약 실행, 다중 process recovery에는 Farad scheduler처럼 별도의 persisted run state와 lease/recovery policy가 필요하다 [D].

    11.3 V2 concurrency 의미

    V2 local execution service는 기록된 tool call들을 eager start해 병렬 settlement하고, 같은 session의 runner는 하나로 조정한다. 서로 다른 session은 concurrent하다. 그러나 runner TODO가 multi-node ownership을 남겨 둔 만큼 두 server process가 같은 DB/session을 실행하는 clustered correctness는 현재 보장으로 간주하면 안 된다 [A/D].

    12. provider와 model abstraction

    공식 Providers와 Models 문서는 AI SDK 및 Models.dev를 통한 75개 이상의 provider와 local model 지원을 설명한다 [B]. 소스의 provider/provider.ts는 다음 source를 merge한다 [A].

    • Models.dev catalog
    • config에 선언한 provider/model
    • auth/environment credential
    • internal provider plugin과 provider별 option transform
    • custom provider SDK
    • whitelist/blacklist, variant, capability normalization

    SDK module은 필요할 때 dynamic import한다. model family에 따라 reasoning, message, tool schema, cache/usage metadata를 normalize하고, GPT 계열에는 apply_patch, 다른 계열에는 edit/write 같은 tool 구성을 선택한다. 이 덕분에 사용자는 provider를 바꿔도 session/tool UX를 유지할 수 있다.

    trade-off는 명확하다. provider-specific quirk와 AI SDK version 변화가 Provider/transform layer에 계속 축적된다. “provider-neutral”은 복잡성이 없다는 뜻이 아니라 복잡성을 adapter 중앙으로 옮겼다는 뜻이다. 이 중앙화는 테스트 가능성에는 유리하지만 변경 반경이 크다 [D].

    Models.dev catalog는 disk snapshot/cache/network source를 병합하고 cross-process file lock으로 갱신한다. process 안에서는 장기 cache하며 주기적으로 약 60분마다 refresh하고 disk freshness는 약 5분을 본다 (models-dev.ts) [A].

    좋은 점:

    • provider package를 모두 startup에 import하지 않는다.
    • model capability와 variant를 catalog data로 관리한다.
    • auth/env/config의 우선순위를 한 service가 해석한다.
    • AI SDK retry를 끄고 OpenCode가 status/event와 함께 retry를 제어한다.

    주의할 점:

    • provider adapter는 핵심 변경 hotspot이다.
    • catalog freshness와 runtime config freshness의 정책이 서로 다르다.
    • 모델별 tool 선택·prompt transform이 늘면 behavior matrix가 폭발할 수 있다.
    • OpenCode의 일반 목적 portability와 달리 Farad는 GLM/Kimi 주력 모델의 품질을 먼저 보장하면서 adapter contract만 개방하는 편이 운영상 단순하다 [D].

    13. tools와 execution semantics

    13.1 registry

    tool/registry.ts는 built-in, custom/plugin, MCP tool을 model/agent/config/permission에 맞춰 resolve한다. permission이 전역 deny인 tool은 model-visible schema에서도 숨길 수 있고, model family에 맞춰 edit primitive를 선택한다 [A].

    OpenCode tool model의 장점은 schema 노출과 execution context가 한 registry에서 결합된다는 것이다. tool context는 session/message/call ID, abort signal, metadata update, permission ask를 받는다. processor는 tool lifecycle을 part로 저장하므로 UI, resume, usage accounting이 일관된다.

    13.2 output bound와 cancellation

    shell은 기본 timeout을 두고 abort/timeout 때 process group을 종료한 뒤 3초 후 force kill한다. 출력이 line/byte limit을 넘으면 bounded preview만 model에 보내고 전체 output을 XDG data directory의 tool-output에 저장한다. 기본 limit은 2,000 line/50 KiB이고 tool_output config로 조정할 수 있다 (shell.ts#L533-L594, truncate.ts) [A].

    이는 중요한 production discipline이다.

    • stdout 폭주가 context와 UI를 무한히 점유하지 않는다.
    • 전체 artifact를 잃지 않고 model-visible result만 제한한다.
    • abort가 단순 flag가 아니라 child process kill까지 연결된다.
    • tool metadata가 preview/exit/truncation path를 보존한다.

    full artifact에는 고정 7일 retention과 약 1분 뒤 시작해 매시간 반복하는 cleanup이 구현돼 있다. 남는 운영 쟁점은 XDG data가 local인지 NFS인지, secret-bearing output의 접근권한, retention 설정 가능성, cleanup 전 crash residue다. 또한 child가 detached descendant를 별도로 만들거나 remote side effect를 낸 경우 local process kill만으로 transaction rollback은 되지 않는다.

    13.3 revert는 tool side effect 전체의 transaction이 아니다

    OpenCode는 session snapshot/diff와 undo/revert UX를 제공하지만 이것은 Git/worktree file change에 초점을 둔다. 이미 실행한 network call, package publish, database mutation, process side effect까지 일괄 보상하는 distributed transaction이 아니다. “세션을 revert했다”와 “모든 tool side effect가 없어졌다”를 구분해야 한다 [B/D].

    14. config, instruction과 refresh semantics

    14.1 config precedence

    공식 Config 문서와 source의 merge path를 합치면 precedence는 낮은 쪽에서 높은 쪽으로 대략 다음과 같다 [A/B].

    1. remote .well-known organization config
    2. global user config
    3. OPENCODE_CONFIG가 가리키는 config
    4. project config
    5. .opencode directory의 구성
    6. OPENCODE_CONFIG_CONTENT inline config
    7. managed config file
    8. macOS MDM managed preference

    일반 remote org config는 default 성격이라 local/project가 override할 수 있고, managed layer가 실제 enforcement 위치다. enterprise policy라면 이 둘을 혼동하면 안 된다.

    config는 per-instance service에서 cache된다. explicit invalidation/reload는 가능하지만 runtime hot path에서 매번 full discovery하지는 않는다. 반대로 reload signal은 config 한 항목의 dependency closure만 갱신하기보다 instance들을 dispose/reboot하는 넓은 경계다.

    14.2 instruction은 provider turn마다 I/O를 다시 할 수 있다

    session/instruction.ts는 global/project AGENTS.md, Claude-compatible fallback, configured glob/path, remote URL instruction을 조립한다. file read는 제한된 concurrency로, remote URL은 timeout과 제한된 concurrency로 가져온다. V1 runLoop는 provider step의 context assembly에서 Instruction.system()을 다시 호출한다 [A].

    로컬 developer UX에서는 외부 편집을 즉시 반영하는 장점이 있다. 그러나 다음 비용이 있다.

    • 한 user turn 안의 여러 provider/tool step에서도 path discovery와 content read가 반복될 수 있다.
    • 작은 instruction file이 여러 개인 NFS에서는 file별 read round-trip이 hot path가 된다.
    • remote URL latency/failure가 prompt assembly에 들어온다.
    • resume 결과가 같은 transcript라도 live file/URL 변화에 따라 달라질 수 있다.

    V2 context epoch가 byte-stable baseline을 저장하는 이유가 이 문제와 연결된다. Farad의 explicit refresh + transcript marker contract와 비교하면 V1 OpenCode는 freshness를 더 높이고 reproducibility와 NFS predictability를 더 적게 보장한다 [D].

    15. skills, commands와 plugins

    15.1 skills

    OpenCode는 project/global .opencode, Claude-compatible .claude, agent-compatible .agents, custom path와 remote index에서 skill을 발견한다. frontmatter를 parse하고 description을 model에 광고하며, model이 skill tool로 선택하면 본문과 일부 연관 file을 context에 넣는다 (Agent Skills 문서, skill/discovery.ts, skill/index.ts) [A/B].

    여기서 “on demand”의 정확한 의미가 중요하다. model context에는 description만 먼저 노출되고 본문은 tool 선택 후 들어가므로 token 측면에서는 on demand다. 그러나 discovery 시점에는 여러 directory를 scan하고 SKILL.md frontmatter/본문을 읽어 object로 보유한다. 즉 disk I/O까지 lazy인 것은 아니다 [A]. shared NFS에서 수백 개 skill을 두면 startup/instance boot 비용이 커질 수 있다 [D].

    중복 이름은 warning 후 우선순위에 따라 하나가 이긴다. remote skill index는 cache version을 staging한 뒤 atomic swap해 partial update를 줄인다. 다만 versionless file의 freshness와 cache invalidation은 명시적 운영 고려가 필요하다.

    15.2 commands

    custom command는 Markdown/JSON으로 prompt template, argument, agent/model, subtask 여부를 정의한다. $ARGUMENTS, positional argument, @file, ! shell interpolation을 지원한다 (Commands 문서) [B].

    강력하지만 ! command는 prompt macro expansion 전에 host command를 실행한다. command file도 단순 문서가 아니라 executable trusted config다. repository clone 후 command를 실행할 때 review가 필요하다.

    15.3 plugins와 hook failure boundary

    plugin/index.ts는 local/NPM plugin을 instance init에서 deterministic order로 import하고 hook을 등록한다. config, auth, event, dispose, tool-before/after, chat params/system/messages, shell env, compaction 등 넓은 interception surface를 제공한다 [A].

    평가:

    • 확장성: 매우 높다. tool 추가뿐 아니라 core flow를 좁은 hook으로 바꿀 수 있다.
    • 변경 용이성: built-in core를 fork하지 않고 organization behavior를 넣을 수 있다.
    • failure isolation: 낮다. 일반 hook은 같은 process에서 await되며 exception이 host flow를 실패시킬 수 있다. event hook은 fire-and-forget 성격이라 ordering/completion을 보장하기 어렵다.
    • 보안: 낮다. arbitrary code이며 별도 capability manifest나 sandbox가 없다.
    • 성능: hook 수와 I/O가 provider/tool hot path에 직접 추가될 수 있다.

    --pure로 외부 plugin을 끌 수 있는 escape hatch는 유용하지만, 안전한 extension architecture는 process isolation, declared capability, timeout/circuit breaker, deterministic ordering, versioned API를 더 요구한다 [D].

    16. MCP architecture

    OpenCode는 local stdio와 remote Streamable HTTP를 지원하고, remote가 필요하면 SSE fallback을 쓴다. OAuth와 RFC 7591 dynamic registration을 지원하며 token은 mcp-auth.json에 제한된 file mode로 저장한다 (MCP 문서) [A/B].

    16.1 lifecycle과 catalog

    mcp/index.ts는 per-instance service다. enabled server들을 instance initialization에서 연결하고 client/status를 보유한다. close notification과 tool-list-change를 감시하며 finalizer가 client와 descendant process를 정리한다 [A].

    tool definition은 catalog에 cache하고 tool-list-change notification으로 좁게 다시 가져온다. prompt, resource, resource template는 별도 OpenCode tool로 list/read한다. MCP instruction이 있으면 permission을 통과한 MCP tool이 하나 이상 노출될 때 system context에 넣는다.

    mcp/catalog.ts는 pagination을 최대 1,000 page로 제한하고 duplicate cursor를 감지한다 [A]. 무한/악성 pagination을 막는 좋은 bound다. tool name은 server_tool 형태로 sanitize하고 tool schema의 추가 property를 막으며 progress가 오면 timeout을 갱신한다.

    16.2 capability와 제한

    현재 구현은 tools, prompts, resources, resource templates를 client 관점에서 지원한다. roots capability는 있지만 sampling, elicitation, MCP task는 source에 TODO/commented 상태다 [A]. resource attachment는 지원 MIME과 약 10 MiB size로 제한한다.

    운영상 주의:

    • instance boot 시 여러 enabled server connect를 시작하므로 server 수가 많으면 startup burst가 난다.
    • 많은 MCP tool schema는 model context 자체를 크게 만든다. 공식 문서도 이를 경고한다.
    • config 변경의 delta reconcile보다 instance reload가 넓은 경계다. tool-list-change는 좁지만 server config refresh는 별개다.
    • remote MCP는 제3자 server와 data/tool authority를 공유하는 trust boundary다.
    • 문서/schema의 기본 timeout 5초와 current source의 30초가 어긋난다. 운영 SLO는 source 기준으로 검증해야 한다.

    Farad가 가져올 가치가 큰 부분은 bounded pagination, duplicate-cursor guard, progress-aware timeout, resource MIME/size bound, tool-list-change의 narrow invalidation이다. 시작 때 모든 MCP를 병렬 연결하고 whole instance reload로 바꾸는 방식은 Farad의 explicit delta reconcile과 맞지 않는다 [D].

    16.3 LSP는 file-triggered process service다

    OpenCode의 LSP는 MCP와 별개의 per-instance process subsystem이다. 고정 source의 lsp.ts#L112-L136는 client, server definition, broken root/server pair, spawning promise를 instance state로 소유하고, hover/definition/reference/implementation/symbol/call-hierarchy/diagnostic API를 제공한다 [A].

    공식 LSP 문서 기준 built-in LSP는 기본 disabled이며 lsp: true로 명시적으로 켠다. 자동 server download도 OPENCODE_DISABLE_LSP_DOWNLOAD=true로 끌 수 있다. 문서가 language server의 높은 메모리, stale state, version/project 편차를 직접 경고하고 lint/typecheck CLI가 더 나은 경우를 인정하는 점은 운영적으로 정직하다 [B].

    모든 language server를 무조건 startup에 띄우지는 않는다. file extension과 root detector가 맞는 file을 처음 touch할 때 process를 spawn하고, 같은 root/server의 concurrent spawn은 promise로 합친다. 실패한 root/server key는 instance 수명 동안 broken으로 기억하고, finalizer는 열린 client들을 shutdown한다 (lsp.ts#L198-L297) [A]. read는 warm-up 실패를 본래 read 실패로 승격하지 않고, edit/write 뒤에는 diagnostic을 model output에 붙인다. 이는 optional enrichment의 failure를 core file operation과 분리한 좋은 경계다.

    반면 broken은 자동 backoff/retry state가 아니라 process-local suppression이고, root별 LSP client 수에 capacity bound가 없다. monorepo에서 root가 매우 많이 생기거나 오래 사는 headless instance에서는 process 수가 누적될 수 있다. Farad가 유사 기능을 도입한다면 lazy spawn과 finalizer는 채택하되, root/client LRU, explicit retry, resource budget, crash status를 함께 계약해야 한다 [D].

    17. UI와 human-in-the-loop

    OpenCode의 UX를 “TUI 하나”로 평가하면 현재 제품을 놓친다. 실제로는 OpenTUI 기반 terminal surface와 SolidJS 기반 shared app surface가 같은 server event/message authority를 서로 다른 projection으로 표현한다. shared app은 browser와 Electron desktop에서 재사용되고, session-ui와 ui package가 message part·diff·dock·primitive를 제공한다 [A].

    17.1 client는 authority가 아니라 projection이다

    웹/데스크톱 app의 session store는 server projection을 page로 읽고 SSE delta를 병합한다. initial message page는 2개, 과거 history prepend는 200개이며, cursor가 있으면 사용자가 위로 올라갈 때 더 가져온다 (server-session.ts#L21-L26, server-session.ts#L599-L703) [A]. HTTP page를 가져오는 동안 도착한 live delta, optimistic message, 제거 event를 잃지 않도록 touched/retained/ carried-delta marker를 병합한다. 이 부분은 단순 REST fetch보다 훨씬 성숙하다.

    SSE disconnect가 exactly-once transport를 제공하지 않으므로 client correctness의 실제 형태는 다음과 같다.

    flowchart LR
    DB[(Server SQLite projection)] -->|keyset page / item fetch| STORE[Client normalized store]
    SSE[SSE best-effort deltas] --> MERGE[Generation-aware merge]
    OPT[Optimistic local item] --> MERGE
    MERGE --> STORE
    STORE --> PROJ[Timeline projection]
    PROJ --> VIRT[Virtual visible rows]
    GAP[Reconnect / stale cache] -->|bounded refetch| DB

    즉 현재 shared app의 legacy path에서는 event가 invalidation·low-latency update이고 REST projection이 복구 기준이다. 이는 합리적이지만 legacy server event queue에는 overflow signal이나 replay cursor가 없으므로 reconnect code가 누락을 감지할 수 있다는 전제가 중요하다. Typed V2 API에는 durable after replay stream이 있으나 이 app path의 복구 계약으로 아직 통합되지 않았다 [A/D].

    17.2 긴 timeline의 화면 비용은 잘 다뤘다

    message-timeline.tsx#L401-L445는 TanStack virtualizer로 visible range와 작은 overscan만 DOM에 두고, active row와 resize 중 visible row만 pin한다. measurement/tool-open cache도 session 16개로 제한한다 (message-timeline.tsx#L531-L535) [A]. scroll anchor, prepend history, variable-height reasoning/tool/diff row까지 별도 logic으로 다룬다.

    다만 DOM virtualization과 data-model 복잡도는 별개다. timeline projection은 현재 client에 적재된 message를 순회해 messageByID, assistant-parent map, row/index map을 만든다 (projection.ts#L19-L96) [A]. 따라서 현재 loaded window에서는 대략 O(N) projection이고, 10,000 turn을 전부 prepend한 뒤의 live delta가 항상 O(visible)이라고 증명되지는 않는다. 초기 page와 virtual DOM 덕분에 일반 open path는 bounded지만 “사용자가 전체 history를 로드한 장시간 tab”은 별도 stress 대상이다 [D].

    17.3 permission과 question은 독립 interaction protocol이다

    permission request는 단순 modal이 아니라 session 실행을 멈추는 typed HITL interaction이다. shared app의 session-permission-dock.tsx는 permission 설명과 exact pattern을 보여주고 Deny / Allow always / Allow once를 구분한다 [A]. TUI는 tool별 상세 preview를 제공하며, 현재 V1 interaction의 “always”가 OpenCode restart까지만 유효하다는 문구도 명시한다 (permission.tsx#L138-L170) [A]. 이는 project-scoped saved rule을 제공하는 V2 permission API와 구별해야 한다.

    질문은 single/multi select, 여러 tab, custom answer, reject를 지원한다. web app은 답변 도중 component가 unmount되어도 process-local cache로 draft를 유지하고, failed mutation은 toast로 되돌린다 (session-question-dock.tsx#L64-L129, session-question-dock.tsx#L209-L247) [A].

    HITL UX의 장점:

    • 질문과 permission이 transcript text parsing이 아니라 typed request/reply다.
    • child session의 pending request도 parent surface가 모아 보여 줄 수 있다.
    • keyboard/TUI와 mouse/web 양쪽에 동등한 승인·질문 경로가 있다.
    • permission pattern과 tool context를 사용자에게 노출한다.
    • retry status, countdown, provider-specific action도 별도 typed UI로 표현한다.

    주의할 점:

    • app과 TUI 모두 auto-approve mode를 제공한다. 이것은 containment가 아니라 prompt를 자동으로 once 승인하는 client policy다.
    • web app의 auto-respond 중복 방지 map은 1,000개/1시간으로 잘 제한되지만, 승인 authority는 server의 process-local pending request다. V2의 saved rule도 pending interaction 자체를 durable하게 만들지는 않는다 (permission.tsx#L104-L139) [A].
    • client가 끊긴 채 permission이 pending이면 run은 기다린다. 별도 unattended timeout/attendance policy는 이 permission UX 자체에는 없다.
    • V1 “always”가 reload/dispose/restart 뒤 사라지는 것은 안전한 쪽으로 fail하지만 durable automation에는 예측 불가능성을 만든다. V2에서는 save resource가 있는 project rule만 restart 뒤 유지된다.

    17.4 UI cache에는 실제 bound가 있다

    server cache와 달리 shared app에는 명시적인 retention guard가 여러 개 있다 [A].

    client state bound/정책 source
    workspace child stores 최대 30, idle 20분, active/pinned/booting 보호 types.ts#L143-L146
    hydrated session caches LRU 성격 40, active/inflight/HITL 보호 session-cache.ts#L11-L65
    session info seen set 2,048 server-session.ts#L24-L27
    recent root overflow 최근 4시간 중 최대 50 추가 유지 types.ts#L145-L146
    timeline measurement cache 16 session message-timeline.tsx#L531-L535
    permission auto-response dedup 1,000개, 1시간 TTL permission.tsx#L104-L119

    이것은 OpenCode를 단순히 “전부 unbounded”라고 부르면 틀린 이유다. 정확한 판정은 현재 app projection은 상당히 bounded하고 virtualized되어 있지만, server instance/event/background registry와 V1 model hot path는 같은 수준의 bound를 아직 갖지 못했다이다.

    18. failure, recovery와 observability

    18.1 failure matrix

    실패 현재 처리 복구 기준 남는 위험
    provider 429/5xx/transient error OpenCode-owned exponential retry, retry status/event 같은 active process/run retry 횟수·전체 deadline이 명시적으로 bounded되지 않음
    context overflow auto compaction 또는 terminal error transcript + summary compaction 자체 실패·두 번째 overflow 처리 제한
    user abort stream interrupt, tool을 interrupted error로 settlement persisted message/part 외부 side effect rollback 불가
    shell timeout process group terminate 후 force kill tool error + truncated artifact detached/remote side effect는 남음
    plugin hook exception caller flow 실패 가능 log/restart/config 수정 process isolation/circuit breaker 없음
    MCP/LSP connect failure status/broken state, instance finalizer reconnect 또는 reload durable retry state 없음
    legacy client SSE disconnect reconnect + projection refetch SQLite/REST projection legacy route에는 replay cursor/overflow indicator 없음; V2 replay API는 별도
    server crash 중 stream DB에 마지막까지 저장된 part session reopen/manual continuation V1 active ownership·retry status는 비영속
    SQLite crash transaction/WAL recovery local DB WAL을 NFS에 놓는 topology는 부적합
    background subagent 중 crash child session 일부는 남을 수 있음 수동 inspection job registry·continuation ownership 유실

    18.2 provider retry는 visible하지만 총량 bound가 없다

    retry.ts#L26-L66는 Retry-After/retry-after-ms를 존중하고, header가 없으면 2초부터 배가해 30초에서 cap한다. processor는 retry 때 session status에 attempt, message, next timestamp, action을 넣어 TUI/app이 countdown과 조치 링크를 보여준다 (processor.ts#L627-L681) [A].

    그러나 schedule에는 maximum attempt나 total elapsed deadline이 없다. retryable 조건이 계속 유지되면 사용자가 abort하거나 process가 종료될 때까지 기다릴 수 있다. interactive local UX에는 친절하지만, CI·scheduler·unattended task에는 retry budget이 있어야 한다 [D].

    18.3 cancellation cleanup은 세심하지만 transaction은 아니다

    processor cleanup은 열려 있는 text/reasoning을 종료하고, tool completion을 짧게 기다린 후 남은 call을 interrupted: true error로 저장하며 assistant 완료 시각까지 기록한다 (processor.ts#L540-L597) [A]. session cancel은 연결된 running background job tree도 찾아 취소한다. 이 덕분에 UI에는 영원한 pending tool보다 명시적인 interrupted state가 남는다.

    하지만 이는 runtime record settlement다. file snapshot/revert가 가능한 영역 밖의 network, database, package publish, credential 사용은 보상되지 않는다. security·workflow 설계에서 “abort가 성공했다”를 “side effect가 원자적으로 취소됐다”로 번역하면 안 된다 [D].

    18.4 restart recovery의 현재 한계

    V1 SessionStatus와 SessionRunState는 instance-local map이며 finalizer가 active runner를 cancel한다 (status.ts#L21-L48, run-state.ts#L35-L68) [A]. message/part는 durable하지만 “이 session은 retry 중이며 어떤 continuation을 누가 재개해야 하는가”는 durable lease/state machine이 아니다. process가 죽으면 새 process는 transcript를 보여 줄 수 있어도 active run을 자동으로 정확히 이어서 실행한다고 보장할 수 없다.

    V2는 durable event replay consumer, admitted input, context epoch, tool/compaction continuation까지 구현해 in-process recovery 기반을 강화했다. 그러나 durable status, multi-node owner lease, interruption replacement, bounded retry와 process restart 뒤 continuation ownership은 여전히 미완이다. 따라서 현재 recovery grade는 durable transcript/event replay: 강함 / durable execution restart: 약함으로 둘로 나눠야 한다 [A/D].

    18.5 관측성

    OpenCode server는 기본적으로 XDG log directory의 opencode.log에 구조화된 key/value line을 append하고, 각 process에 짧은 run ID를 붙인다. log level과 stderr mirror를 환경변수로 제어한다 (logging.ts) [A]. OTLP endpoint가 있으면 logs와 traces를 내보내고 service version, channel, client, run/instance ID를 resource attribute로 설정한다 (otlp.ts#L36-L76) [A]. app error boundary는 build에서 활성화된 경우 Sentry report를 보낼 수 있다.

    좋은 점:

    • Effect span과 structured annotation이 service call에 일관되게 붙는다.
    • run ID로 한 process의 file log/OTLP를 묶을 수 있다.
    • model usage, tool part, retry status, message error가 사용자 projection에도 남는다.
    • debug command와 HTTP log endpoint가 현장 진단 surface를 제공한다.

    한계:

    • session/turn/tool 전반에 강제되는 단일 trace/correlation ID 계약은 report에서 확인되지 않았다.
    • permission decision과 arbitrary plugin/shell side effect를 immutable audit log로 보존하는 별도 보안 ledger는 없다.
    • file log rotation/retention/size bound는 이 logging layer에 드러나지 않는다.
    • OTLP export failure와 backpressure가 제품 SLO로 문서화되어 있지 않다.
    • V1 status는 durable하지 않으므로 “마지막 관측 상태”와 crash 이후 authority가 갈릴 수 있다.

    18.6 server, sharing과 credential trust boundary

    headless API는 session/message만이 아니라 file, shell, PTY, config, MCP/LSP까지 넓게 노출한다. default loopback bind는 합리적이지만 0.0.0.0 bind와 password 부재도 warning만 하고 계속 실행하며, Basic auth 자체는 TLS가 아니다. directory selector에 per-project ACL/root allowlist가 보이지 않으므로 remote credential은 사실상 해당 OS user의 file/shell workspace capability다 [A/D]. 외부 network에서는 사용자별 daemon, TLS reverse proxy/VPN, 강한 secret, OS user 격리, workspace allowlist가 필요하다.

    공식 Share 문서의 URL sharing도 별도 exfiltration boundary다 [B]. 첫 share는 session, full message/part, diff와 사용 model metadata를 읽어 외부 service에 sync하고, 이후 event는 entity key별로 1초 coalesce한다 (share-next.ts#L124-L145, share-next.ts#L274-L299) [A]. 민감 조직은 managed config로 share를 disable해야 하며, 최초 full sync는 큰 session에서 별도 O(N) DB/CPU/network spike다.

    provider credential과 MCP OAuth token은 일반 config와 분리하고 0600으로 쓴다 (auth/index.ts#L79-L88, mcp/auth.ts#L70-L81) [A]. 좋은 기본이지만 OS keychain/encrypted vault가 아니라 filesystem bearer secret이므로 shared account, backup, home ACL은 여전히 trust boundary다.

    19.2 local SSD에서는 SQLite 선택이 타당하다

    WAL, synchronous=NORMAL, indexes, batch part hydration, keyset message cursor는 single-user local tool에 실용적인 조합이다. JSON file 수천 개보다 transaction, search, concurrent UI read가 쉽고, current app의 page loading과 잘 맞는다. V2가 event와 projection을 같은 SQLite transaction에 넣는 것도 local crash consistency를 개선한다 [A/D].

    19.3 DB를 NFS에 두는 것은 별도 문제다

    OpenCode의 기본 topology는 XDG data directory의 SQLite DB를 authority로 삼고 WAL을 강제한다. SQLite 공식 WAL 문서는 WAL이 shared-memory 때문에 network filesystem에서 작동하지 않는다고 명시한다 [B]. 따라서 $XDG_DATA_HOME이나 home이 NFS인 HPC에서 이 DB를 그대로 공유 배치하는 것은 지원 topology로 간주하면 안 된다.

    OPENCODE_DB absolute path로 DB 자체를 node-local disk에 둘 수는 있다. 다만 이 flag가 HPC 배포 지원계약으로 문서화되거나 자동 강제되는 것은 확인하지 못했다. 또한 DB를 옮겨도 V1 instruction/skill/config discovery가 NFS workspace를 반복 읽을 수 있다. 특히 provider step마다 instruction glob/file/URL을 재조립하는 path는 file 수 × network round trip 비용을 turn latency에 넣는다. OpenCode의 default freshness는 Farad의 explicit refresh/NFS index 계약과 비용 모델이 다르다 [D].

    19.4 10,000 session과 10,000 message를 분리해야 한다

    • 10,000 session: 반환 행은 기본 100으로 bounded지만 SessionTable에는 time_updated 또는 (project_id, time_updated) 계열 index가 없다. LIMIT는 candidate 전량 scan/sort 비용을 막지 않으므로 첫 화면 latency는 조건부·미검증이다. title %search%, child 전량 조회, server instance cache와 client 전역 상태 merge까지 EXPLAIN QUERY PLAN과 heap benchmark가 필요하다.
    • 한 session에 10,000 message/part: app은 처음 2개만 가져와 화면 open을 방어한다. 그러나 user가 history를 모두 load한 뒤 projection은 누적 window를 다루고, 더 중요하게 V1 agent step은 처음부터 full transcript를 읽는다. 현재 primary runtime은 이 규모 계약을 만족한다고 볼 수 없다.
    • 10,000 directory: app child store는 30개로 제한되지만 server InstanceStore와 Effect scoped cache는 capacity/idle TTL이 없다. long-lived headless server는 별도 eviction 없이는 부적합하다.
    • 10,000 events/slow consumer: legacy SSE queue와 default core PubSub가 unbounded이고 bounded helper가 shipping route에 연결되지 않아 backpressure 증명이 없다.
    • 10,000 background jobs: registry가 non-durable이고 retention bound도 없으므로 scheduler 용도가 아니다.

    19.5 performance tests가 증명하는 것과 못 하는 것

    app에는 별도의 high-volume Playwright suite가 있고 timeline virtualization, streaming delta, tab switch, review pane, geometry/scroll stability를 진단한다. default streaming scenario는 320 history turn, 160 delta, 30× CPU throttle를 사용한다 (performance README, session-timeline-benchmark.spec.ts) [A].

    그러나 README가 직접 밝히듯 suite는 normal CI discovery에서 제외되고, machine-dependent performance budget을 assert하지 않는다. 320-turn renderer stress는 좋은 관측 도구지만 server V1의 10,000-message turn latency, NFS cold start, slow SSE consumer heap, 10,000 directory instance retention을 증명하지 않는다.

    • app: shared browser/Electron product state와 screens

    • opencode: shipping binary와 현재 V1 runtime/adapters

    특히 server schema에서 generated client를 검사하는 방식은 client/server drift를 CI에서 잡을 수 있다. Effect LayerNode graph는 service dependency와 scope/finalizer를 central composition root에 드러낸다 (app-runtime.ts#L58-L109) [A].

    현재 약점은 이 그림이 아직 target과 current를 동시에 담는다는 것이다. session/model/provider/tool의 상당한 V1 구현은 여전히 packages/opencode에 있고 V2는 core/server/client/sdk-next에 중복 진화한다. legacy SDK와 next client, legacy live event transport와 shared durable replay API, JSON message/part와 typed projection이 동시에 존재한다. 공용 EventV2 substrate가 storage commit path 일부를 통합했어도 runtime/API/serving model은 이중이다. migration 중에는 불가피하지만, 두 path의 behavior parity와 제거 기준이 없으면 “새 layer를 추가했지만 old authority는 계속 남는” 장기 이중화가 된다 [D].

    21. 구조적 강점

    1. 다중 surface를 가능하게 한 server spine. TUI와 desktop을 따로 구현하면서도 agent loop를 복제하지 않는다. OpenAPI/SDK/ACP가 외부 embedding 경계를 만든다.
    2. provider portability를 adapter 문제로 중앙화. 인증, model capability, reasoning, cache usage, tool variant를 한 layer에서 normalize한다.
    3. typed resource lifecycle. Effect scope/finalizer가 MCP, LSP, instance, DB, runner, process cleanup을 composition graph에 드러낸다.
    4. transcript와 UI tool lifecycle의 높은 관측 가능성. text/reasoning/tool/patch/retry를 part로 증분 보존해 client가 final answer만 보는 black box가 아니다.
    5. HITL을 protocol로 승격. permission과 question이 surface마다 재해석 가능한 typed interaction이다.
    6. client-side large-history engineering. keyset page, optimistic/live merge, virtual timeline, cache bound, scroll-anchor regression test가 실제 제품 품질을 만든다.
    7. extension breadth. MCP, LSP, skill, command, plugin, custom tool, ACP가 모두 실제 surface다.
    8. 공용 durable substrate와 V2가 현재 부채를 정확히 겨냥. V1 lifecycle까지 포함한 durable sequence와 event+projection transaction, V2 input admission, context epoch, post-baseline history, compaction continuation과 replay API는 복구·성능 문제에 맞는 방향이다.
    9. local-first inspectability. MIT source, SQLite, file logs, documented HTTP API라 운영자가 내부 상태를 조사할 수 있다.
    10. 실용적인 output/cancellation guard. shell timeout, process-group kill, configurable output truncation, full artifact 보존과 7일 cleanup은 production coding agent에 필요한 기본기다.

    refresh는 누가 시작하는가? user/app mutation의 targeted invalidation; 외부 file은 explicit reload

    23.3 Farad 우선순위 제안

    1. P0: permission과 containment를 분리해 명세화. shell/tool runner의 실제 OS boundary, network, workspace outside, child process, plugin trust를 capability matrix와 platform별 test로 만든다. OpenCode의 가장 큰 교훈은 승인 UX가 좋아도 containment는 자동으로 생기지 않는다는 점이다.
    2. P0: runtime/UI protocol conformance. command, event, question, permission, tool lifecycle ID를 typed application protocol로 고정하고 Qt가 runtime object를 직접 만지지 못하게 한다.
    3. P1: active-window session query. compaction 이전 transcript를 turn마다 읽지 않는 index/cursor/hint contract와 “비싼 fallback 호출 시 fail” test를 강화한다.
    4. P1: bounded registries. folder/session/MCP/subagent/scheduler/notification queue마다 capacity, TTL, pin, overflow semantics를 문서와 test에 둔다.
    5. P1: crash semantics. persisted transcript, persisted run record, restartable operation을 분리하고, terminal/interrupted/orphan settlement와 수동 resume UX를 정의한다.
    6. P1: provider adapter contract. GLM/Kimi streaming, reasoning, usage, tool call, retry metadata를 같은 conformance suite로 검증한다.
    7. P2: external surface는 증거가 생길 때. CLI/automation/remote UI 요구가 구체화되면 OpenCode처럼 stable application protocol에서 server/SDK를 파생한다. 지금부터 network daemon을 authority로 둘 필요는 없다.

    26. 최종 판정

    26.1 축별 평가

    아래 5단계 평가는 절대 성능 점수가 아니라 고정 commit의 architecture maturity를 압축한 D등급 판단이다. 5가 “모든 환경에서 최고”라는 뜻은 아니며, 0.5 단위도 측정 오차가 있는 정량값이 아니다. 다른 제품 보고서의 판정과 산술 비교하거나 합산하지 않는다.

    축 평가 이유
    client/server 경계·임베딩 5/5 HTTP/OpenAPI/SDK/ACP와 여러 surface가 같은 core를 공유
    provider portability 5/5 광범위 adapter와 model capability normalization
    extension breadth 5/5 MCP/LSP/skill/plugin/custom tool/command가 실제 통합
    interactive UX/HITL 4.5/5 TUI+desktop/web, typed permission/question, virtual timeline
    local transcript persistence 4.5/5 V1 lifecycle부터 durable append+transactional projection, V2 typed history/replay; live delta는 비영속
    durable execution/recovery 3/5 V2 compaction/tool continuation과 replay는 구현, active owner/status/restart continuation은 미완
    security containment 2/5 approval policy는 좋지만 host sandbox가 아니며 agent policy drift
    long-session hot path 2/5 V1 step당 full transcript, V2 해결 방향은 아직 migration 중
    long-lived server boundedness 2.5/5 client bounds와 core helper는 있으나 shipping cache/legacy queue/job은 unbounded
    observability 3.5/5 structured log + OTLP + rich parts, audit/retention/correlation 빈칸
    HPC/NFS 적합성 1.5/5 SQLite WAL/NFS 및 repeated workspace reads가 Farad 비용 모델과 충돌
    architecture 일관성 3/5 목표 구조는 좋지만 V1/V2 dual path 전환기

    26.2 use-case별 결론

    use case 적합도 조건
    개인 개발자의 local poly-provider coding agent 매우 높음 trusted account/repo, local DB
    TUI·desktop·web·IDE를 함께 쓰는 개발 workflow 매우 높음 server auth와 directory trust 이해
    coding agent를 SDK/HTTP로 임베드 높음 API drift와 current V1/V2 상태 고정 필요
    untrusted repository를 zero-trust로 실행 낮음 외부 container/sandbox를 별도로 강제해야 함
    다중 tenant 장기 headless service 낮음~조건부 ACL, isolation, bounds, backpressure, durable owner 보강 필요
    crash-safe durable workflow/scheduler 낮음~조건부 current background/runner를 workflow engine으로 간주하면 안 됨
    shared-home HPC/NFS desktop assistant 낮음 DB node-local 분리와 workspace I/O redesign 없이는 부적합

    OpenCode를 Farad의 직접 blueprint로 삼는 것은 맞지 않는다. 제품 authority와 배포 비용 모델이 다르기 때문이다. 하지만 server/API anti-corruption layer, generated typed contract, keyset history, virtual UI, typed HITL, provider adapter, bounded output+retention, Effect-style resource finalizer, V1/V2 공용 durable event projection과 V2 replay API는 매우 좋은 설계 참고점이다.

    최종 결론은 §1과 일치한다. OpenCode는 현재 가장 개방적이고 surface가 넓은 coding-agent platform 중 하나이며, UI/client engineering은 이미 상당히 강하다. 동시에 primary V1 agent hot path, host-level security boundary, durable execution recovery, long-lived server resource bound는 그 야심에 아직 못 미친다. V2는 compaction continuation과 durable replay까지 이미 실체가 있지만, stale checklist의 문구만으로 구현을 과소평가하거나 반대로 owner lease·restart continuation까지 완성됐다고 과대평가해서는 안 된다. Farad는 OpenCode의 경계와 관측성을 배우되, explicit refresh, NFS-aware persistence, 10k hot-path bound, UI/async thread ownership, attendance와 permission의 분리라는 자체 강점을 버리면 안 된다.
