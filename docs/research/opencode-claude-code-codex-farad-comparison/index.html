    OpenCode · Claude Code · Codex · Farad 아키텍처 교차 비교

    전체 보고서 인덱스

    조사 기준일: 2026-07-13
    전제: 이 문서는 네 제품을 한 줄짜리 기능표로 환산하지 않는다. 각 제품의 최적화 대상, state authority, 실행 경계, 저장 비용이 다르므로 “어디에 쓰느냐”를 포함해 판정한다.
    세부 근거: OpenCode · Claude Code · Codex · Farad

    1. 최종 요약

    네 제품은 같은 “coding agent”라는 이름 아래 서로 다른 시스템을 만들었다.

    제품 실제 정체성 가장 강한 축 가장 큰 구조 리스크
    OpenCode provider-neutral HTTP agent server와 여러 client surface 개방형 provider·server/API·SDK·확장성 V1/V2 이중 구조, 현 V1의 history read amplification, host-level 격리 부재
    Claude Code 여러 surface를 가진 Claude 중심 workflow 제품; local CLI/SDK는 process-local runtime agent loop 완성도, context/permission/hook, 장기 자율 workflow Claude 결합, local surface의 process/file affinity, opt-in sandbox, 공개되지 않은 current 내부
    Codex typed thread/turn kernel과 여러 OpenAI client surface ordered command/event protocol, OS sandbox, replay/index, subagent lifecycle 매우 큰 Rust composition/feature matrix, OpenAI 중심, protocol 운영 복잡도
    Farad provider-neutral native desktop agent application native Qt product와 엄격한 explicit-refresh/HPC/NFS 설계 계약; 구현 위반 존재 command containment 부재, runtime/UI hotspot, 확인된 문서-실행 drift와 hot-path 위반

    이 결과는 “Codex 1등, Claude 2등” 같은 단일 순위로 요약할 수 없다.

    • provider와 embeddable server가 우선이면 OpenCode가 가장 자연스럽다.
    • 개발자 개인의 가장 깊은 terminal workflow는 Claude Code가 강하다.
    • 지원 플랫폼의 기본 local command containment와 surface-independent runtime protocol은 Codex가 기준점이다. 이것이 remote MCP나 모든 side effect까지 자동 격리한다는 뜻은 아니다.
    • 멀티 provider native desktop, scheduler, shared HPC/NFS 운영은 Farad가 가장 명시적인 설계 대상으로 삼았지만, current hot path가 그 목표를 아직 모두 충족하지 않는다.

    Farad에 대한 결론도 “다 갈아엎어야 한다”가 아니다. Farad는 이미 callback-inverted async loop, Qt/async 분리, per-turn snapshot, append-oriented transcript, capability exposure, explicit refresh를 갖고 있다. 부족한 것은 agent loop 자체보다 OS enforcement, 몇 개 authority 경계의 구현 일치성, 누적 hot path의 실증, 거대 session projection 책임 분해다.

    2. 비교 전제와 버전 경계

    제품 분석 기준 구현 투명성 주의할 점

    Codex openai/codex@2b0b37a… + 공식 문서 local core/app-server 공개 Apache-2.0 호스티드 backend를 local core와 동일시하지 않음

    Claude Code만 구현 증거의 등급이 다르다. 따라서 내부 모듈 품질 비교에서 Claude의 내부 구현 평가는 현재 공개 제품 계약보다 불확실성이 크다. 반대로 OpenCode와 Codex의 공개 소스가 있다는 이유만으로 호스티드 서비스까지 공개됐다고 보지 않는다.

    이 그림에서 가장 큰 차이는 UI toolkit이 아니다. 아래의 “권위”는 저장·filesystem까지 포괄하는 전역 권위가 아니라 실행 중인 한 run/turn을 순서화하는 active-run authority를 뜻한다.

    • OpenCode는 active run을 server/session runtime이, conversation을 SQLite가, 실제 side effect를 filesystem/host process가 소유한다.
    • Claude Code의 확인 가능한 local CLI/SDK에서는 current turn을 session process가, conversation을 JSONL이, code state를 working tree가 소유한다. Desktop/Web 내부 authority는 판단 보류다.
    • Codex는 active turn을 thread/session queue consumer가, conversation을 JSONL rollout이, 목록 조회를 SQLite projection이 소유한다.
    • Farad는 async active-run authority와 Qt projection authority를 나누고, transcript와 session index에 서로 다른 영속 책임을 둔다.

    5. Active-run authority와 thread/process ownership

    여기서 active-run owner와 저장 자원을 혼동하면 “세션 10,000개 = 프로세스 10,000개” 같은 잘못된 비교가 생긴다.

    제품 historical persisted loaded/runtime-resident concurrently active execution
    OpenCode SQLite session/message/part directory-scoped instance cache와 session state 같은 session의 run state 하나
    Claude Code JSONL session 파일 재개하거나 열린 session state 실행 중 Agent SDK/agent-view session별 local process
    Codex JSONL rollout + SQLite metadata projection ThreadManager가 연 thread/session thread별 active task 최대 하나
    Farad chunked transcript + session metadata/index 앱이 연 UiSession/AsyncSession projection session별 turn task 최대 하나

    이 표의 loaded 비용과 historical 목록 비용, active CPU/process 비용은 각각 따로 측정해야 한다.

    5.1 OpenCode: directory-scoped server authority

    OpenCode client는 directory/session을 지정하고 server가 해당 normalized directory의 Effect service graph를 선택한다. 같은 session의 run은 SessionRunState가 하나로 직렬화한다. 장점은 client를 추가해도 runtime이 하나라는 점이다. 단점은 server credential이 사실상 해당 OS user가 볼 수 있는 directory와 command 전반의 capability가 된다는 점과, long-lived instance cache에 명시적 LRU/TTL이 없다는 점이다.

    5.2 Claude Code local CLI/SDK: process isolation으로 단순화

    확인 가능한 local CLI는 conversation owner와 cwd, tools, state를 한 local process에 묶는다. SDK도 가벼운 in-process library라기보다 session별 CLI subprocess를 띄우는 방식이다. 이 선택은 singleton과 ambient state를 process boundary로 격리해 개인 workflow를 단순화한다. 하지만 동시에 실행 중인 SDK/agent-view session 수만큼 memory, process tree, routing, local disk affinity가 늘어난다. 과거에 저장된 session 수가 process 수로 직결되는 것은 아니다. process-global state의 세부 구현은 2.1.88 sourcemap 관찰(C)이며 현재 2.1.207 내부나 Desktop/Web topology와 같다고 단정하지 않는다.

    5.3 Codex: ordered queue를 소비하는 thread/session

    Codex의 Submission in / Event out은 가장 명확한 control plane이다. settings update, input, interrupt, approval, refresh가 같은 queue ordering을 타며 session에는 active task가 하나뿐이다. client가 mutable session field를 직접 고치지 않으므로 “어떤 설정으로 이 turn이 시작했는가”를 replay하기 쉽다.

    5.4 Farad: UI projection과 async execution 분리

    Farad는 UiSession이 Qt-thread 화면 상태와 signal을, AsyncSession이 transcript projection, turn task, permission rendezvous, tool cancellation을 소유한다. proxy와 queued signal이 두 thread를 연결한다. 이는 native GUI에 적합한 명시적 ownership이다. current Claude Code 전체 제품과 내부 응집도를 직접 우열 비교할 공개 근거는 없다. 단, boundary를 우회해 Qt가 async-side mutable object를 직접 읽거나, async loop가 동기 disk I/O를 수행하면 장점이 즉시 사라진다. 따라서 문서가 아니라 각 call path의 thread ownership test가 중요하다.

    판정

    • 가장 명시적 ordering: Codex
    • 다중 client 권위: OpenCode
    • 확인 가능한 local surface에서 가장 단순한 process isolation: Claude Code
    • rich desktop에 맞는 이중 projection: Farad

    Farad는 Codex queue를 그대로 복제할 필요는 없다. 다만 submit/start/steer/cancel/approve/settings snapshot의 ordering을 현재 proxy/event contract에 명시하고 테스트할 필요가 있다.

    6. Agent loop와 상태 머신

    네 제품의 기본 loop는 모두 model stream → tool decision → execute → append result → continue다. 차이는 loop가 무엇까지 소유하느냐다.

    제품 loop owner iteration state terminal/recovery 특징
    OpenCode SessionPrompt + SessionProcessor DB message/parts + run state compaction/subtask/plugin/tool을 중앙 조정; V2로 이전 중
    Claude Code query loop (QueryEngine/queryLoop는 2.1.88 관찰 C) message state, compact/recovery/turn/budget 공식 행동 계약은 세밀, 내부명은 현재 미확인
    Codex Session/run_turn turn-scoped TurnContext + request-scoped StepContext, history, active task ordered Op, compaction, tool routing, typed events
    Farad AsyncSession/query_loop TurnState, TurnContext, callbacks flat async generator, terminal/transition event, abort invariant

    Farad와 2.1.88 sourcemap에서 관찰한 Claude Code의 flat async generator는 구조적으로 가깝다(C). 현재 2.1.207이 같은 내부 구현을 유지한다는 뜻은 아니다. Farad의 query_loop는 app-layer class를 import하지 않고 callback으로 system prompt, model, permission, compaction, tool execution을 받는다. 이것은 테스트성과 SDK/app 경계를 지키는 좋은 선택이다.

    OpenCode의 현재 V1은 매 step에서 DB의 compacted view를 다시 materialize한다. DB authority와 client projection은 좋지만 loop hot path가 누적 history에 비례한다. 진행 중 V2는 context epoch 이후만 읽는 방향으로 이를 고치려 한다.

    Codex의 특별한 강점은 loop 내부가 아니라 loop로 들어오는 control operation의 ordering이다. turn configuration은 TurnContext가 고정하고, 각 model sampling request에 보이는 environment, capability root, MCP runtime/tool list, AGENTS.md는 StepContext가 같은 request view로 묶는다. Claude/Farad도 active turn 하나를 지키지만, Codex는 live settings mutation까지 command stream에 넣어 재현성을 높인다. 단 DeferredExecutor가 켜진 Codex는 sampling request 경계에서 filesystem-derived state를 refresh할 수 있으므로, 이 freshness 정책은 Farad의 explicit-refresh 계약과 같지 않다.

    7. Context, transcript, compaction, world state

    7.1 공통된 좋은 방향

    네 제품 모두 다음 사실을 인정한다.

    raw transcript != active conversation chain != model request context != UI projection
    • raw transcript는 감사와 resume를 위한 장기 기록이다.
    • compaction은 raw history를 없애는 대신 model view를 대체한다.
    • skills/instructions/tool schema/world state는 request마다 별도 규칙으로 합쳐진다.
    • UI streaming placeholder는 durable conversation authority가 아니다.

    7.2 제품별 차이

    OpenCode의 현재 primary V1은 SQLite의 mutable message/part JSON projection에 상세 tool lifecycle을 보존하고 compaction summary를 추가한다. lifecycle 변경은 이미 공용 EventV2 durable log에 append되고 같은 transaction에서 projection되며, 고빈도 message.part.delta와 legacy SSE만 비영속이다. 진행 중인 V2는 durable substrate를 새로 만드는 것이 아니라 typed session message/input/context projection, context epoch, 새 runner/API를 얹는다. V2는 compaction continuation과 replay-then-live API도 구현했지만 durable execution ownership, bounded retry, plugin/MCP parity 등은 남아 있다. V1은 과거 row를 읽은 뒤 버리는 read amplification이 약점이다.

    Claude Code는 append-oriented JSONL chain, resume/fork, file checkpoint를 제공한다. prompt cache를 위해 stable prefix를 적극 관리하고, snip/microcompact/context collapse/autocompact 및 large output spill을 조합한다. 하지만 session JSONL과 working tree는 원자적 transaction이 아니며, compaction summary가 nested instruction이나 오래된 skill 세부를 잃을 수 있다.

    Codex는 rollout item에 response, inter-agent communication, turn context, world state, compaction을 타입으로 구분한다. JSONL을 durable replay 원본으로 두고 SQLite는 조회 projection이다. 원본과 index authority가 가장 명료하다.

    Farad는 append-only transcript, chunked storage, marker twin, per-turn reminder, runtime metadata의 on-demand tool 분리를 명시한다. working_folder_meta 같은 byte-stable marker는 변경된 대화성 context만 transcript에 남겨 재현성과 prompt cache를 동시에 지킨다. 중요한 질문은 disk append와 in-memory/UI projection 사이 failure ordering, 큰 transcript의 active-window read가 실제 반복 경로에서도 bounded인지다.

    판정

    • 가장 세밀한 개인 coding context 최적화: Claude Code
    • 가장 명시적인 replay/index authority: Codex
    • provider/server DB projection: OpenCode
    • NFS와 대화 재현성을 함께 명세한 방향: Farad

    8. Tool architecture와 capability exposure

    공통 pipeline

    model-visible tool path는 대체로 다음 단계로 수렴한다. hook, permission, spill, persistence는 제품과 tool 종류에 따라 optional이며, local OS containment는 generic execute와 별도 경계다.

    flowchart LR
    DISC[Discover/load] --> CAT[Catalog]
    CAT --> EXP[Per-turn exposure]
    EXP --> MODEL[Model schema]
    MODEL --> VAL[Validate input]
    VAL --> POLICY[Optional hook + permission]
    POLICY --> ROUTE[Tool-kind adapter]
    ROUTE --> INPROC[In-process built-in]
    ROUTE --> LOCAL[Local child process]
    LOCAL --> CONTAIN[OS containment when available]
    ROUTE --> REMOTE[Remote MCP trust/transport]
    INPROC --> BOUND[Bound/spill result]
    CONTAIN --> BOUND
    REMOTE --> BOUND
    BOUND --> EVENT[Persist + event]

    차이는 각 칸을 얼마나 명시적으로 분리했는가다.

    • Codex는 dispatch registry와 model_visible_specs를 타입상 분리하고 Direct/Deferred/DirectModelOnly/Hidden exposure를 per-step plan으로 만든다.
    • Farad는 Registry/Factory/Loader와 CapabilityCatalog, Off/Searchable/Active exposure, run readiness snapshot을 분리한다.
    • Claude Code는 ToolSearch, skill lazy body, streamed tool executor, conservative concurrency flag로 prompt와 wall time을 줄인다.
    • OpenCode는 built-in/custom/MCP tool을 provider adapter 위에 조합하고 output truncation을 갖지만, current V1 resolver와 V2 tool execution이 전환 중이다.

    병렬성

    • Claude Code와 Codex는 safe/read tool만 병렬, mutation은 직렬이라는 fail-closed 기본에 가깝다. Claude의 schema/call/permission/concurrency/result/TUI render 결합은 2.1.88 관찰(C)이고 현재 내부는 공개되지 않았다.
    • OpenCode는 underlying AI SDK/tool declaration과 Effect concurrency를 사용하므로 tool별 안전성 및 shared filesystem 충돌 검증이 중요하다.
    • Farad도 parallel dispatch와 per-tool cancellation을 갖지만, concurrency declaration과 terminal event invariant가 모든 built-in/MCP path에서 동일한지 회귀 테스트가 필요하다.

    판정

    schema budget과 dispatch separation의 기준점은 Codex다. Farad는 이 분야에서 뒤처진다기보다 이미 유사한 product-specific 구조를 갖는다. 추가 abstraction보다 catalog/exposure/readiness의 동일 snapshot 사용과 국소 invalidation을 입증하는 것이 우선이다.

    9. Permission과 실제 command containment

    이 축에서는 용어를 엄격히 구분해야 한다.

    제품 policy decision OS/process enforcement 기본 함의
    OpenCode wildcard allow/ask/deny, tool-specific parser 내장 host sandbox 확인 안 됨 승인은 있으나 shell/plugin은 host user 권한
    Claude Code mode/rules/hooks/classifier macOS Seatbelt/Linux·WSL bubblewrap sandbox, opt-in; native Windows 미지원 지원 OS에서 켜면 강함; unavailable 시 fail-open 가능 unless configured
    Codex approval/exec rules/tool annotation platform-native sandbox가 local 기본 policy와 기술 경계를 가장 명확히 분리
    Farad scoped PermissionManager와 tool checks agent command용 OS sandbox 없음 정책은 강하지만 arbitrary child process containment가 없음

    왜 이것이 최우선 격차인가

    permission parser는 model과 user 사이의 의사결정이고 sandbox는 kernel/OS가 child process를 막는 기술 경계다. Bash tool이 python -c, compiler, git hook, package script를 실행할 수 있다면 개별 Read/Edit tool의 semantic guard는 우회 가능하다. plugin hook과 MCP stdio server도 별도 process surface다.

    OpenCode 내부에서도 기억 범위가 다르다. V1 always는 directory instance 메모리라 restart에 사라지지만, V2 always는 save resource가 있을 때 project-scoped SQLite rule로 영속될 수 있다. 반면 pending approval은 여전히 process-local이다. 따라서 “approval UI가 있다”와 “durable project policy가 있다”도 분리해 봐야 한다.

    OpenCode와 Farad는 이 구분에서 가장 취약하다. Claude는 지원 OS에서 sandbox가 있지만 기본 활성화가 아니고 dependency가 없을 때 명시적으로 fail-closed를 설정하지 않으면 unsandboxed fallback이 가능하다. native Windows에서는 같은 sandbox가 동작하지 않으므로 permission만으로 동일한 격리를 얻었다고 보면 안 된다. Codex는 지원 플랫폼의 기본 local agent-command containment에서 protected path와 network policy까지 가장 강하다. danger-full-access, platform/backend 차이, remote MCP side effect 때문에 이 판정을 “제품의 모든 보안”으로 확대해서는 안 된다.

    Farad가 취할 방향은 “Codex와 동일한 bubblewrap 명령”이 아니다. RHEL 8.10 공유 HPC, user namespace 제한, Windows를 전제로 다음을 먼저 계약해야 한다.

    • filesystem/network/process-tree/socket별 enforced / unavailable / disabled를 표시하고, 선택 profile의 required guarantee를 모두 만족할 때만 overall enforced로 표시
    • permission posture와 containment capability를 직교 상태로 유지
    • Bash, background shell, user-configured hook, stdio MCP child 중 어느 local process가 경계 대상인지 inventory
    • backend가 없을 때 fail-closed가 필요한 managed policy와 사용자 선택형 fallback 구분
    • workspace write/read/network/socket/process-tree 규칙과 platform adapter

    HTTP/SSE MCP의 원격 side effect는 local OS sandbox로 격리할 수 없다. 이 경로는 permission, server trust, credential scope와 provenance로 통제해야 한다. 현재 Farad skill은 instruction package이고 plugin hook은 metadata discovery와 executable wiring이 분리돼 있으므로 둘을 현행 local spawn surface로 과장하지 않는다.

    10. MCP, skills, plugins, hooks

    네 제품 모두 이 확장 primitive를 갖지만 의미는 다르다.

    primitive 올바른 책임 잘못된 평탄화의 위험
    instruction/rule file model context enforcement로 오해
    skill lazy procedural context + assets/scripts 항상 prompt에 전부 주입
    MCP external capability/resource connection local built-in tool과 lifecycle을 동일시
    hook deterministic lifecycle policy/automation core business logic을 hook에 숨김
    plugin 위 primitive의 배포 단위 설치가 곧 신뢰라는 가정

    Claude Code는 이 구분을 가장 풍부한 제품 계약으로 제공하고, Codex는 per-step planner와 typed extension으로 이를 core에 통합한다. OpenCode는 provider/plugin 생태계와 server extension이 강하지만 arbitrary JS plugin이 host process 권한을 공유한다. Farad는 4-layer Registry/Factory/Loader, marketplace, exposure, explicit refresh와 delta MCP reconcile을 갖고 명세상 NFS 비용을 가장 엄격히 제한한다. settings/endpoint/MCP current path가 그 명세를 실제로 위반한다는 감사 결과를 함께 봐야 한다.

    Farad의 차별점은 “항상 최신”이 아니라 명시적 refresh와 write-after-invalidate다. Claude/OpenCode의 turn-time refresh나 file watch를 무조건 이식하면 NFS file-content round trip과 재현성이 나빠진다. 현재 감사에서는 capability discovery는 이 계약을 대체로 지키지만, settings/endpoint는 5분 mtime timer, per-turn tier stat, 20분 poller의 endpoint config reconcile이라는 세 freshness 축을 동시에 가지고 있었고 first/dirty MCP turn도 blocking reconcile을 기다렸다. 기본 composition에는 discovery provider가 없어 20분 경로가 Ollama network probe를 실행하지는 않지만, Qt callback의 stat·selection·signal fanout은 남는다. 따라서 이 축에서 Farad의 점수는 “좋은 명세”가 아니라 확인된 계약-구현 gap을 반영해야 한다.

    11. Multi-agent, background work, scheduler

    제품 child 단위 context 관계 file isolation interactive owner durable schedule
    OpenCode child session/task parent-linked, foreground/background 기본 shared directory; 별도 격리 미확인 server process, experimental job 근거 없음
    Claude Code subagent/session/team member 기본 fresh context, fork는 parent 상속 + result/mailbox shared FS 또는 worktree CLI process/per-user supervisor/cloud local /loop는 process-bound; cloud 별도
    Codex child agent thread parent rollout flush + fork snapshot shared workspace/environment policy ThreadManager/agent graph 본 조사 증거로 판단 보류
    Farad subagent/runtime task/scheduled session session/task artifact와 event product policy에 따름 app runtime persistent scheduler store

    Claude Code는 subagent, independent agent view, experimental team, worktree를 서로 다른 primitive로 분리한 점이 좋다. 현재 일반 subagent는 최대 depth 5까지 nested delegation을 지원하고, fork만 다시 fork할 수 없다. 다만 team은 experimental이고 resume/file-conflict 제약이 있으므로 durable team workflow로 과대평가하지 않는다. Codex는 child를 별도 thread로 만들어 lifecycle과 permission inheritance를 명시적으로 기록하지만, 이것만으로 장기 durable team workflow가 입증되지는 않는다. OpenCode는 server session tree가 자연스럽지만 background job은 process-local·non-durable이고 V2 durable multi-node ownership은 아직 진행 중이다.

    Farad의 scheduler는 부가 CLI loop가 아니라 앱의 제품 기능이라는 점이 차별점이다. 그러나 scheduler가 Qt timer에서 10,000 item을 주기적으로 stat/sort하거나 UI thread에 I/O를 올리면 이 차별점이 오히려 가장 큰 운영 병목이 된다. scheduler의 authority, due index, executor thread, run idempotency를 별도로 감사해야 한다.

    12. Provider abstraction

    OpenCode

    가장 폭넓고 제품 정체성 자체가 provider neutral이다. AI SDK/native adapter와 model catalog, provider config가 runtime의 중심이다. 장점은 선택권이고, 비용은 provider별 tool/reasoning/stream/error normalization의 거대한 compatibility matrix다.

    Claude Code

    Bedrock/Vertex/Foundry와 gateway를 지원해도 메시지 의미론과 최적화는 Claude 모델 중심이다. 이는 제품 품질에는 장점이지만 범용 kernel의 중립성은 낮다.

    Codex

    model provider interface와 OSS endpoint가 있으나 auth, model catalog, 최신 기능과 hosted surface는 OpenAI 중심이다. OpenCode 수준의 동등 provider experience라고 보기는 어렵다.

    Farad

    hvppyai를 HTTP/types library로 제한하고 agent loop를 app 계층에 둔다. GLM/Kimi 같은 near-frontier provider를 first-class로 취급해야 하므로 이 경계는 유지할 가치가 크다. provider capability 차이를 SDK에 agent policy로 hardcode하지 말고 turn/readiness adapter에서 해석해야 한다.

    판정

    두 질문을 분리해야 한다.

    • 검증된 provider breadth: 75+ provider와 adapter matrix를 운영하는 OpenCode가 선두다.
    • core semantic coupling과 architecture neutrality: Farad의 hvppyai/app 경계가 강하다. 다만 GLM/Kimi first-class 목표가 OpenCode급 breadth나 모든 provider parity를 입증하지는 않는다.

    13. UI와 human-in-the-loop

    제품 UI의 강점 구조상 주의점
    OpenCode TUI/Web/Electron/IDE가 API를 공유 SSE gap refetch, remote auth, client/server version
    Claude Code terminal workflow와 permission/diff/plan 밀도 local CLI 및 2.1.88 관찰(C)의 TUI/core render 결합·process-local state; Desktop/Web 내부 미확인
    Codex TUI/IDE/App에서 thread/subagent/approval 공유 app-server protocol evolution과 connection state
    Farad persistent sidebar, timeline, scheduler, settings, native terminal Qt thread I/O, huge projection class, signal fanout

    Farad가 가장 잘할 수 있는 것은 Claude/Codex CLI를 픽셀 단위로 복제하는 일이 아니다. long-lived session, multiple provider, schedule, permission, context usage, subagent 상태를 저사양 desktop에서 지속적으로 이해 가능하게 투영하는 것이다. 이 우위는 runtime authority를 UI가 침범하지 않을 때만 유지된다.

    14. Persistence, NFS, N=10,000

    14.1 local SSD와 NFS는 다른 문제다

    OpenCode의 SQLite WAL, Claude의 JSONL+stat, Codex의 JSONL+SQLite는 local disk에서 합리적이다. 하지만 NFS에서는 SQLite locking, WAL, file-per-item content read, 대량 concurrent stat가 전혀 다른 비용과 실패를 낳는다.

    Farad의 공식 비용 모델은 다음을 요구한다.

    • 반복 경로는 누적 entity 수에 대해 O(1) 또는 visible-only
    • list data는 단일 derived index와 mtime/size delta 검증
    • content read는 changed file에만
    • 전체 reconcile은 startup/명시 refresh처럼 bounded one-shot
    • external change 감지는 polling/watch가 아니라 explicit reconcile

    14.2 제품별 판정

    • OpenCode V1은 한 긴 transcript에서 agent step마다 O(N) history materialization이라 가장 직접적인 hot-path 문제가 있다. session list는 반환 수가 제한돼도 time_updated compound index가 없어 후보 scan/sort 비용은 10k에서 미검증이다. SQLite WAL도 shared NFS canonical DB로는 별도 검증이 필요하다. OPENCODE_DB로 node-local path를 지정할 구현상 완화책은 있으나 공식 배포 계약은 약하다.
    • Claude Code는 2.1.88 sourcemap 관찰(C)에서 resume list가 O(N) stat/sort 후 recent item만 content read했다. local SSD에는 합리적일 수 있지만 현재 2.1.207 구현으로 단정할 수 없고, 그 관찰 경로는 Farad의 10k 반복 계약에는 맞지 않는다.
    • Codex는 JSONL canonical과 SQLite query index 분리가 좋은 구조적 참고다. 다만 10,000 thread latency, fallback/rebuild bound, stale projection repair 비용을 보장하는 증거는 이번 조사에서 확인하지 못했다. Farad는 SQLite/WAL을 NFS canonical store로 그대로 복제하지 말고 node-local derived projection 또는 자체 index를 써야 한다.
    • Farad는 명세가 가장 엄격하지만 실제 source의 scheduler/session-open/turn-start 경로가 이를 지키는지는 별도 성능 gate로 증명해야 한다. 실제로 scheduler의 60초 Qt-thread 전량 stat/sort, sync transcript append와 cold double scan, rewind 뒤 full projection fallback이 확인됐다. “문서에 O(1)”은 증거가 아니다.

    15. Failure, cancellation, recovery, observability

    성숙한 agent runtime은 실패를 예외 문자열 하나로 만들지 않는다.

    실패 축 좋은 계약
    model retryable/terminal, rate limit, output limit, context limit 분리
    tool pending/running/completed/error/cancelled와 terminal result 보장
    approval request identity, timeout/cancel, noninteractive fail behavior
    process process tree kill, late output suppression, cleanup finalizer
    transcript append ordering, partial record repair, resume boundary
    client disconnect 뒤 authoritative refetch/replay
    MCP per-server status, required/optional, reconnect/backoff, delta refresh
    subagent child terminal state, orphan cleanup, parent partial result

    Codex는 typed event/item과 cancellation token, thread lifecycle가 가장 체계적이다. 다만 core submission channel은 512로 bounded인 반면 event channel은 unbounded라서 느린 consumer와 event burst의 memory backpressure는 별도 운영 리스크다. Claude Code는 continue/terminal reason, tool state, hook failure, retry taxonomy가 매우 풍부하다. OpenCode는 DB projection과 Effect finalizer, 공용 durable event substrate가 강하지만 legacy SSE queue/backpressure와 V2 미완 경계가 있다. Farad는 AgentEvent/TerminalReason, synthetic abort result, UI event dispatcher와 run measurement를 갖지만 모든 cancellation path에서 terminal event와 disk state가 닫히는지 감사가 중요하다.

    16. 테스트 가능성과 변경 용이성

    좋은 경계

    • OpenCode: typed schema/OpenAPI, Effect service/layer, public source/tests
    • Claude Code: 공식 SDK conformance surface; async generator·narrow QueryDeps는 2.1.88 관찰(C)
    • Codex: Rust types, storage trait, protocol schema, router/registry separation
    • Farad: Protocol/dataclass, query callback inversion, UI proxy, 4-layer contract, fail-on-expensive-fallback tests

    변경 비용이 집중된 곳

    • OpenCode: V1 SessionPrompt와 V2 migration overlap
    • Claude Code: 2.1.88에서 관찰한 QueryEngine/query/TUI/global state/message/session hotspot(C); current 2.1.207 내부는 미확인
    • Codex: Session spawn/services/tool spec feature composition
    • Farad: AsyncSession, UiSession, CapabilityCatalog, session/scheduler path

    LOC 자체가 결함은 아니다. 위험은 서로 다른 변경 이유가 한 module에 모여 independent test seam 없이 같이 바뀌는 것이다. Farad의 분해 기준은 “파일이 길다”가 아니라 authority와 failure boundary가 다른 책임을 추출하는 것이어야 한다.

    GLM/Kimi 중심 native desktop Farad provider-neutral SDK + rich Qt product OpenCode desktop

    “Farad(목표)”라는 표현은 의도적이다. 해당 계약을 문서화했다는 것과 current implementation의 모든 경로가 지킨다는 것은 다르다. 개별 Farad 감사에서 위반이 나오면 release gate로 고쳐야 한다.

    18. 무엇을 누구에게서 배울 것인가

    가져올 pattern 기준 제품 Farad식 번역
    typed client/runtime anti-corruption layer Codex, OpenCode 우선 in-process command/event Protocol; 두 번째 surface 전에는 server 보류
    ordered control plane Codex turn input/settings/approval/cancel ordering 명문화
    tool pipeline과 lazy disclosure Claude, Codex 기존 catalog/readiness/exposure invariant 강화
    durable event + projection Codex, OpenCode EventV2/V2 typed projection transcript canonical, bounded derived index와 repair 계약
    context epoch/byte-stable baseline OpenCode V2, Farad marker twin external context 변경을 transcript에 재현 가능하게 기록
    output spill + preview Claude Code NFS 비용과 민감정보 정책을 포함한 bounded artifact store
    resource finalizer/scope OpenCode Effect, Codex cancellation Python async context/lifecycle owner를 명시
    subagent as first-class lifecycle Codex, Claude parent snapshot, child terminal state, artifact merge
    OS sandbox + separate approval Codex, Claude RHEL/Windows adapter와 honest capability state

    Codex의 request-scoped refresh는 이식 대상이 아니다. Farad에서는 StepContext처럼 한 요청의 tool과 context view를 일치시키는 snapshot 불변식만 가져오고, 그 snapshot을 만들기 위해 매 sampling request마다 filesystem을 refresh하는 정책은 가져오지 않는다.

    19. 의도적으로 모방하지 않을 것

    • OpenCode의 모든 client/server 복잡도를 단일 Qt 앱에 선제 도입
    • Agent SDK의 live-session subprocess topology와 2.1.88에서 관찰한 process-global state
    • Codex의 crate 수와 모든 OpenAI product surface
    • local SSD 기준 SQLite/JSONL operation을 NFS에 그대로 적용
    • per-turn file watch/rescan을 “freshness”라는 이유로 도입
    • agent 수·plugin 수·hook event 수를 성숙도 지표로 삼기
    • 문서상의 read-only/permission을 OS enforcement로 표현
    • compaction summary를 raw transcript 대체 원본으로 사용

    20. Farad의 현재 위치

    Farad는 다른 세 제품과 배포 형태·언어·공개 범위가 달라 단순 규모 순위를 매길 수 없다. 다만 다음 contract는 비교 대상보다 더 엄격하다.

    • SDK에는 agent loop를 두지 않음
    • UI와 async execution authority 분리
    • 모든 app LLM call streaming
    • explicit refresh와 국소 invalidation
    • NFS content-read 비용 명시
    • 누적 10,000 entity 반복 경로 제한
    • transcript context와 runtime metadata 분리
    • Session 통일, scheduler와 subagent도 session projection에 통합

    따라서 전략은 feature parity가 아니라 계약-구현 gap closing이어야 한다. 특히 다음 네 질문이 release 수준의 판정 기준이다.

    1. agent-generated process가 permission decision 밖의 실제 OS 경계를 갖는가?
    2. turn/session/scheduler 반복 경로가 10,000 entity에서 정말 bounded인가?
    3. Qt와 asyncio가 서로의 mutable authority를 직접 읽지 않는가?
    4. explicit refresh라고 문서화한 capability가 실제 turn start를 불필요하게 block하지 않는가?

    구체적인 우선순위와 exit criterion은 Farad 판정 및 로드맵에 둔다.

    21. 최종 판정

    네 제품의 architecture를 한 문장씩 줄이면 이렇다.

    • OpenCode: server를 중심으로 가장 넓게 열려 있으나 runtime migration과 current hot path의 빚이 크다.
    • Claude Code: 가장 깊게 제품화된 workflow이며, 확인 가능한 local CLI/SDK에서는 Claude·process·local-file 결합을 대가로 낸다.
    • Codex: 가장 강한 protocol·sandbox·replay kernel이지만 그만큼 composition과 platform 복잡도가 크다.
    • Farad: 올바른 desktop/HPC 계약을 상당수 이미 세웠으나, 이제 문서가 아닌 enforcement와 hot-path evidence로 그 계약을 증명해야 한다.

    Farad가 승리할 수 있는 경로는 OpenCode의 provider openness, Claude의 workflow semantics, Codex의 runtime/security invariants를 모두 복제하는 것이 아니다. 현재 product differentiator인 native desktop, provider neutrality, scheduler와 선언된 explicit-refresh/NFS/10k 설계 계약을 바로잡아 유지하면서 Codex 수준의 실행 경계, Claude 수준의 tool/failure semantics, OpenCode 수준의 surface-independent application contract를 필요한 만큼만 흡수하는 것이다.
