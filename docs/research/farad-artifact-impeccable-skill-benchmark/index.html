    Impeccable Skill 벤치마크

    조사일: 2026-07-14
    대상: pbakaus/impeccable

    한 줄 평가

    Impeccable은 HTML artifact 생성기라기보다, AI가 만든 화면의 상투성을 발견하고 실제 브라우저 결과로 고치는 UI 품질 시스템이다. Farad에는 그 중 검토 기준의 명문화, 생성 뒤 렌더 검수, 더 조용하게 만드는 개선 명령이 특히 유효하다. 반대로 브랜드마다 과감한 시각 연출을 권하는 부분과 상시 hook은 Farad 자료 만들기의 기본값으로는 과하다.

    무엇으로 구성됐나

    단일 $impeccable 스킬이 23개 하위 명령을 라우팅한다. 새 프로젝트에서는 init이 제품 독자·용도·목소리·금지 레퍼런스와 색·타입·컴포넌트를 PRODUCT.md, DESIGN.md로 기록한다. 이후 명령은 이 문서와 기존 코드의 토큰·컴포넌트를 먼저 읽는다. 이는 단일 거대 프롬프트보다 "판단에 필요한 공통 맥락"과 "포맷별 실행법"을 분리한 구조다.

    범주 대표 명령 의도
    제작 craft, shape, document, extract 만들기 전 UX를 정하고, 기존 코드에서 디자인 시스템을 추출
    평가 critique, audit 디자인 판단과 결정적 규칙 검사를 분리
    정제 polish, quieter, distill, typeset, layout 품질·밀도·타이포·리듬을 목적별로 조정
    확장 bolder, colorize, animate, delight, overdrive 더 강한 시각성·움직임을 의도적으로 추가
    운영 live, pin, hooks 브라우저 변형 비교, 단축 진입점, 편집 후 detector 실행

    polish는 디자인 시스템을 먼저 찾아 토큰·간격·컴포넌트·흐름 관례를 확인하게 한다. 이탈을 "토큰 부재 / 이미 있는 공용 요소 미사용 / 정보 구조 불일치"로 나누는 점이 좋다. 예쁜 장식을 덧붙이는 일을 polish라고 부르지 않고, 기존 시스템 안에서 일관된 결과가 되는지를 묻는다.

    비평과 anti-pattern 방식

    이 프로젝트의 핵심은 "AI slop"을 막연한 취향이 아니라 재검토 가능한 금지·경고 항목으로 바꾼 것이다. README 기준 46개의 결정적 detector rule과 LLM 비평을 병용한다. CLI는 파일·디렉터리·URL을 검사하고 JSON 출력을 제공하며, 브라우저 확장과 hook도 같은 규칙을 쓴다.

    대표적인 금지 항목은 보라색 gradient, gradient text, 과한 glow와 glass 카드, 카드 안의 카드, 무의미한 hero metric, 모든 섹션의 작은 대문자 eyebrow, 장식용 01/02 번호, 지나치게 큰 radius, border와 넓은 shadow를 동시에 쓴 ghost card, 장식 격자·stripe 배경, 손그림 풍 SVG다. 접근성 측면에서는 색 배경 위 회색 글자, 낮은 contrast, 작은 touch target, 잘린 제목, heading 순서도 잡는다.

    좋은 점은 단순히 "하지 말라"가 아니라 대체 수단을 제시한다는 것이다. 예를 들어 강조는 gradient text 대신 굵기·크기·단색으로, 카드의 색 띠는 전체 border·옅은 배경·선행 숫자·생략으로 바꾸게 한다. quieter와 distill을 독립 명령으로 둔 것도 Farad의 목적과 잘 맞는다. 결과물이 "멋져 보이려는 장치"로 독해지면 제거하고, 정보 계층·가독성·여백을 다시 세우는 방향이다.

    다만 이 규칙은 웹 제품 UI와 2026년의 특정 생성 모델 습관을 겨냥한다. 예를 들어 기본 폰트·따뜻한 중립 배경을 넓게 경계하고, 새 브랜드에는 OKLCH와 색 전략 선택을 강하게 요구한다. Farad의 기술 문서·Confluence 페이지·PPTX에는 잘 읽히는 중립 배경이나 system font가 합리적일 수 있다. 따라서 표면적 CSS 탐지 규칙을 그대로 복사하지 말고, Farad에서 실제로 싫은 결과의 예시와 이유로 다시 정의해야 한다.

    브라우저·시각 QA 흐름

    critique는 한 대상에 두 평가를 요구한다. A는 디자인 디렉터 관점의 계층·정보 구조·인지 부하·정서적 흐름·Nielsen heuristic 평가이고, B는 detector와 브라우저 증거다. 가능하면 둘을 서로 결과를 보지 않는 별도 에이전트로 수행해 detector가 주관 평가를 선입견으로 고정하지 않게 한다. 검사 결과는 스냅샷으로 남겨 다음 polish의 우선순위 입력으로 쓴다.

    보이는 대상은 브라우저가 가능할 때 실제로 열어 봐야 한다. 로컬 서버는 background로 시작하되 종료 방법을 기록하고, detector overlay가 실제 삽입·실행된 경우에만 이를 주장한다. live는 HMR 개발 서버 또는 static HTML 위에서 요소를 고르고, 서로 다른 세 가지 HTML/CSS 변형을 즉시 바꿔 보게 한다. 사용자가 선택하면 임시 variant를 정리해 실제 소스에 반영하고, 중단 시에는 append-only journal로 복구한다.

    이것은 "코드를 썼다"와 "읽히는 결과물을 만들었다"를 분리하는 강한 운영 계약이다. 다만 live mode는 dev server, 장기 polling, 임시 파일과 browser injection을 필요로 한다. 한 장짜리 HTML·정적 GitHub Pages·PPTX 결과를 만들 Farad Skill에는 비용이 너무 높다.

    Farad 자료 만들기에 이식할 것

    1. 작은 공통 맥락 파일: farad-artifact에는 포맷 지시와 분리된 references/farad-style.md를 둔다. 독자, 사용 맥락, 주장 한 줄, 한국어/영어, tone, 금지 패턴, 색·폰트·여백·diagram 원칙을 정의한다. 프로젝트 전역 PRODUCT.md를 매번 만들 필요는 없다.
    2. 제작 전 content brief: 출력 형식(standalone HTML / Confluence-ready / PPTX), 독자, 독자가 취할 결정·행동, 주장, 근거와 필요한 diagram만 먼저 확정한다. visual은 내용 관계를 설명할 때만 쓴다.
    3. Farad 전용 quietness check: "모든 섹션에 카드·아이콘·eyebrow·번호를 반복했는가", "accent가 정보 의미 없이 쓰였는가", "decorative SVG/gradient/glow가 주장보다 눈에 먼저 들어오는가", "제목·본문·표·diagram의 읽기 순서가 분명한가"를 생성 후 체크리스트로 둔다.
    4. 포맷별 렌더 검수: HTML은 지정 viewport screenshot과 링크·overflow 확인, PPTX는 slide render와 겹침·잘림 확인, Confluence는 raw HTML을 전제하지 않고 대상 인스턴스에서 허용된 macro/Markdown/첨부 SVG 경로를 확인한다. detector의 수치 결과는 보조 증거일 뿐, 완료 판정은 아니다.
    5. 명시적 정제 동사: 처음부터 수십 개 명령을 만들지 말고 create, review, quieten 또는 자연어 동등 요청만 둔다. 특히 "이 자료를 더 조용하게 / 덜 LLM처럼"은 제목·여백·강조·장식만 다시 평가하는 재사용 가능한 흐름이 된다.

    가져오지 않을 것

    • 모든 artifact에 animation, delight, overdrive, 강한 색 전략을 권하는 구조. Farad는 읽기·검토·공유가 목적이며, 움직임은 일반 HTML 기본값이 아니다.
    • 편집 뒤 자동 hook으로 anti-pattern을 매번 경고하는 방식. Farad의 explicit refresh 원칙과도 맞지 않고, 산출물 생성 한 번에 불필요한 마찰을 만든다. 사용자가 요청하거나 최종 QA 때만 실행한다.
    • 검토마다 두 에이전트를 필수로 쓰는 계약. 독립 검토는 큰 발표 자료나 외부 배포 페이지에서 선택적으로 유용하지만, 단일 다이어그램·짧은 Confluence 자료에는 과도하다.
    • 여러 브라우저 변형과 장기 polling을 요구하는 live mode. 필요해지면 Farad UI Lab 같은 별도 설계 작업에만 적용할 수 있다.

    결론

    Impeccable은 Farad Artifact의 디자인 언어 그 자체가 아니라, 그 언어가 흐트러졌는지 확인하는 검토 레이어로 참고하는 것이 맞다. 기본 생성은 차분한 Farad 토큰과 정보 구조를 따르고, Impeccable에서 배운 "명시적 anti-pattern + 실제 렌더 검수 + quieter/distill 재정제"를 완료 기준으로 이식한다. 이렇게 하면 화려함을 억제하면서도 밋밋한 자동 생성물로 흘러가는 것을 막을 수 있다.
