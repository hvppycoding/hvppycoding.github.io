    HyperRun(hrun) hmodels 사이트 셋업 예시

    개요

    한 사이트가 hmodels로 LLM provider 두 곳을 제공하는 셋업이다. hmodels는 아래 파일을 읽기만 하고, 카탈로그에 적힌 모델만 사용자에게 보인다. 앱은 hrun hmodels resolve로 "내가 쓸 모델·주소·키 위치"를 받아 직접 호출한다.

    provider 무엇 모델 키 보는 앱
    corp-gpu (예시 이름) 사내 GPU 클러스터 GLM 4.6 (chat), BGE M3 (임베딩) corp-kam (예시 이름): KAM이 사용자마다 발급 모든 앱
    myrouter (예시 이름) 외부 유료 LLM 라우터 Qwen3 235B, gpt-oss 120B (chat) myrouter (예시 이름): 모두 같은 고정 키 oh-my-cli만
    호출 보이는 provider
    hrun hmodels resolve --app oh-my-cli corp-gpu, myrouter
    다른 앱, 셸 corp-gpu
    • 예시 이름: corp-gpu, corp-kam, myrouter, oh-my-cli(앱), ai-pilot(그룹), 주소의 *.alpha.internal·*.example.com. default는 "모든 앱"을 뜻하는 예약어다.
    • 모델 id는 실제 모델 이름이지만 각 서버가 쓰는 정확한 id로 바꿔 적는다. 토큰 수와 점수는 예시 값이다.

    파일 트리

    $HYPERRUN_ROOT/hmodels/
├── providers.json             카탈로그 시작점 (형식 표시만)
├── providers.d/               provider 하나당 파일 하나, 0644
│   ├── corp-gpu.json          사내 GPU 클러스터 (예시 이름)
│   └── myrouter.json          외부 라우터 (예시 이름)
├── private/                   0750 hmodels-ops, 사용자는 못 읽음
│   ├── corp-kam.json          KAM 등록 (예시 이름)
│   └── myrouter.json          고정 키 (예시 이름)
├── speed.json                 속도, 측정 job이 씀 (없어도 됨)
└── stats.json                 벤치 점수, 사람이 씀 (없어도 됨)

<사용자 home>/.hrun/tools/hmodels/groups/<프로젝트 그룹>/keys/
├── corp-kam.json              내 키 (KAM 발급, 자동 생성)
└── myrouter.json              내 키 (고정 키 사본, 자동 생성)

    hmodels/providers.json

    카탈로그의 시작점. provider 내용은 모두 providers.d/에 있어 형식 표시만 남는다.

    { "protocol": 1, "document": "catalog", "endpoints": [] }
    • protocol: 형식 버전. 항상 1
    • document: 파일 종류. 항상 "catalog"
    • endpoints: 형식상 필요한 빈 목록

    hmodels/providers.d/corp-gpu.json

    사내 GPU 클러스터(vLLM) provider. chat 모델 하나와 임베딩 모델 하나를 제공하고, 사용자마다 KAM이 발급한 키로 요청한다. 모든 앱이 본다. 모델은 운영에 필요한 값만 적은 보통 형태다.

    {
  "protocol": 1,
  "document": "catalog",
  "endpoints": [
    {
      "id": "corp-gpu",
      "title": "사내 GPU 클러스터",
      "base_url": "http://llm-gw.alpha.internal:8000/v1",
      "credential": "corp-kam",
      "apps": ["default", "oh-my-cli"],
      "models": [
        {
          "id": "glm-4.6-fp8",
          "title": "GLM 4.6",
          "kind": "chat",
          "chat": {
            "context_window": 202752,
            "max_output_tokens": 32768,
            "supports": ["tools", "streaming", "reasoning"],
            "reasoning": { "off": { "chat_template_kwargs": { "enable_thinking": false } } },
            "wire": { "chat_template_kwargs": { "enable_thinking": true }, "reasoning_replay": "preserved" }
          }
        },
        {
          "id": "bge-m3",
          "title": "BGE M3",
          "kind": "embedding",
          "embedding": {
            "dimensions": 1024,
            "max_input_tokens": 8192,
            "max_batch": 64,
            "normalized": true,
            "similarity": "cosine"
          }
        }
      ]
    }
  ]
}

    provider 항목

    • id: provider 이름. 앱 설정·사용자 숨김 설정·speed.json이 이 이름으로 가리킨다
    • title: 화면에 보이는 이름
    • base_url: 요청 주소. 끝에 /를 붙이지 않는다
    • credential: 쓸 키의 이름 → private/corp-kam.json
    • apps: 이 provider를 보는 앱. default는 모든 앱. oh-my-cli도 적는 이유는 myrouter.json 참고
    • models: 이 provider의 모델 목록. 여기 적힌 것만 존재한다

    모델 공통

    • id: 요청에 그대로 보내는 모델 이름
    • title: 화면에 보이는 이름
    • kind: chat / embedding / rerank. 이 값과 같은 이름의 블록 하나만 쓴다

    chat 블록 (GLM 4.6)

    • context_window: 서버가 받는 최대 문맥 토큰 수
    • max_output_tokens: 한 번에 출력할 수 있는 최대 토큰 수
    • supports: 할 수 있는 것 (tools 도구 호출, streaming, reasoning 추론, json_schema, vision 등)
    • reasoning.off: 추론을 끌 때 요청에 더할 값. 있으면 "끌 수 있다"는 뜻. vLLM은 chat_template_kwargs로 끈다
    • wire.chat_template_kwargs: 평소 요청에 붙일 값 (여기선 추론 켜기)
    • wire.reasoning_replay: 지난 턴의 추론을 다음 요청에 다시 보낼지. preserved 전부 / interleaved 도구 호출 중인 턴만 / off 안 보냄

    embedding 블록 (BGE M3)

    • dimensions: 벡터 차원
    • max_input_tokens: 입력 하나의 최대 토큰 수
    • max_batch: 한 요청에 넣을 수 있는 입력 개수
    • normalized, similarity: 벡터 DB 설정과 맞춰야 하는 값. 틀려도 에러 없이 검색 품질만 나빠진다

    hmodels/providers.d/myrouter.json

    외부 유료 LLM 라우터 provider. chat 모델 둘을 제공하고, 모두 같은 고정 키를 쓴다. oh-my-cli만 본다. Qwen3 235B는 chat 항목을 모두 쓴 최대형 예시이고, gpt-oss는 보통 형태다.

    {
  "protocol": 1,
  "document": "catalog",
  "endpoints": [
    {
      "id": "myrouter",
      "title": "외부 LLM 라우터",
      "base_url": "https://api.myrouter.example.com/v1",
      "credential": "myrouter",
      "apps": ["oh-my-cli"],
      "models": [
        {
          "id": "qwen/qwen3-235b-a22b",
          "model": "qwen3-235b-a22b",
          "title": "Qwen3 235B",
          "description": "사내 클러스터가 바쁠 때 쓰는 외부 모델. 비용 발생",
          "kind": "chat",
          "visibility": "hidden",
          "visible_to": ["ai-pilot"],
          "quantization": "fp8",
          "maker": "qwen",
          "size": "235B-A22B",
          "chat": {
            "context_window": 131072,
            "max_output_tokens": 16384,
            "context": { "supported_windows": [32768, 65536, 131072], "default_window": 65536 },

              "effort_overrides": {
                "low":    { "extra_body": { "reasoning": { "effort": "low" } } },

          "title": "gpt-oss 120B",
          "kind": "chat",
          "chat": {
            "context_window": 131072,
            "max_output_tokens": 32768,
            "supports": ["tools", "streaming", "reasoning"],
            "reasoning": { "supported_efforts": ["low", "medium", "high"], "default_effort": "medium" }
          }
        }
      ]
    }
  ]
}

    provider 항목

    • apps: oh-my-cli만. 어떤 앱 이름을 적은 provider가 하나라도 있으면 그 앱은 자기 이름이 적힌 provider만 본다. 그래서 corp-gpu에도 oh-my-cli를 적었다
    • 나머지는 corp-gpu와 같다

    최대형 모델 (Qwen3 235B) — 위에서 설명한 항목 외에

    • model: 가중치 이름. 같은 가중치를 여러 곳에서 서빙해도 stats.json 점수 한 줄로 묶인다. 없으면 id와 같다
    • description: 모델 선택 화면의 설명
    • visibility: hidden이면 기본으로 숨김. 사용자가 직접 켜야 보인다 (유료라서)
    • visible_to: 이 그룹(ai-pilot, 예시 이름)의 사용자에게만 존재한다. 그 밖의 사용자는 켤 수도 없다
    • quantization, maker, size: 정보 표시용
    • context.supported_windows: 화면의 문맥 창 선택지. 서버 최대보다 작게 잘라 부하를 줄일 때 쓴다
    • context.default_window: 사용자가 고르지 않았을 때의 문맥 창
    • reasoning.off: 추론 끄기. 라우터는 body의 reasoning.enabled로 끈다
    • reasoning.supported_efforts: 추론 강도 선택지
    • reasoning.default_effort: 고르지 않았을 때 보낼 강도
    • reasoning.effort_overrides: 강도를 요청의 어디에 실을지. 라우터는 최상위 reasoning_effort 대신 body의 reasoning.effort로 받는다
    • params: 운영자가 맞춘 기본값. temperature, top_p, stop, n, frequency_penalty, presence_penalty만 허용
    • wire.extra_body: 모든 요청 body에 더할 값 (여기선 "내 데이터 학습에 쓰지 마")
    • wire.max_tokens_field: 최대 출력 필드 이름. max_tokens 또는 max_completion_tokens. 틀리면 400
    • wire.always_send_max_tokens: 사용자가 제한을 안 줘도 최대 출력 필드를 항상 보낸다
    • wire.reasoning_replay: off = 지난 추론을 다시 보내지 않는다
    • 여기 없는 chat 항목 하나: wire.chat_template_kwargs — vLLM 같은 자체 서버용이라 corp-gpu의 GLM에 있다

    gpt-oss 120B

    • reasoning에 off가 없다 → 항상 추론한다. 강도만 고른다
    • effort_overrides가 없다 → 강도를 최상위 reasoning_effort로 보낸다

    hmodels/private/corp-kam.json (0640 hmodels-ops)

    KAM 등록 하나. 사용자가 처음 쓸 때 helper(hmodels-issue)가 이 토큰으로 KAM에 그 사용자의 키를 요청한다. 사용자는 이 파일을 못 읽는다.

    {
  "protocol": 1,
  "document": "credential",
  "credential": "corp-kam",
  "issuer": "kam",
  "kam_url": "http://kam.alpha.internal/v1/keys",
  "kam_token": "<bootstrap token>"
}
    • credential: 이름. 파일 이름과 같아야 한다
    • issuer: kam = 사용자마다 발급
    • kam_url: 발급 요청 주소
    • kam_token: KAM 등록 토큰

    hmodels/private/myrouter.json (0640 hmodels-ops)

    고정 키. 사용자마다 이 키를 그대로 복사해 간다.

    {
  "protocol": 1,
  "document": "credential",
  "credential": "myrouter",
  "issuer": "static",
  "key": "<myrouter API key>"
}
    • issuer: static = 고정 키
    • key: 라우터 키. 바꾼 뒤에는 이 키를 쓰는 provider에 "key_policy_rev": 2처럼 숫자를 올려야 사용자가 새 키를 받아 간다

    hmodels/speed.json (측정 job이 씀, 없어도 됨)

    모델별 현재 속도. 모델 선택 화면의 속도 표시와 정렬에 쓰인다.

    {
  "protocol": 1,
  "document": "speed",
  "models": [
    { "endpoint": "corp-gpu", "model": "glm-4.6-fp8",          "status": "ok",   "window_s": 900, "output_tps_p50": 78 },
    { "endpoint": "corp-gpu", "model": "bge-m3",               "status": "ok",   "window_s": 900, "items_per_s": 420 },
    { "endpoint": "myrouter", "model": "qwen/qwen3-235b-a22b", "status": "slow", "window_s": 900, "output_tps_p50": 12 }
  ]
}
    • endpoint: provider의 id
    • model: 모델의 id (요청 이름). 철자가 정확히 같아야 붙는다
    • status: ok / slow / down
    • window_s: 몇 초 동안 잰 값인지. 없으면 그 줄은 무시된다
    • output_tps_p50: chat의 초당 출력 토큰
    • items_per_s: 임베딩의 초당 처리 개수

    hmodels/stats.json (사람이 씀, 없어도 됨)

    모델별 벤치 점수. 모델 선택 화면의 점수 막대에 쓰인다.

    {
  "protocol": 1,
  "document": "stats",
  "models": [
    { "model": "glm-4.6-fp8",         "scores": { "intelligence": 64, "agentic": 41 } },
    { "model": "qwen3-235b-a22b",     "scores": { "intelligence": 57 } },
    { "model": "openai/gpt-oss-120b", "scores": { "intelligence": 61, "agentic": 38 } }
  ]
}
    • model: 모델의 가중치 이름(model). 카탈로그에 model이 없으면 id를 쓴다. 그래서 Qwen은 qwen3-235b-a22b, 나머지는 id 그대로다
    • scores: 정수 점수. intelligence, agentic 두 축

    앱에서 쓰는 법 (oh-my-cli 예시)

    앱은 hmodels를 import하지 않는다. 명령 하나를 실행하고 JSON을 읽는다. 앱이 고칠 수 없는 도구면 환경변수로 받는 방법도 있다.

    방식 명령 언제
    resolve hrun hmodels resolve --app oh-my-cli --kind chat --all --json 앱 코드를 고칠 수 있을 때. 모델 목록·설정·키 위치를 받는다
    exec hrun hmodels exec --app oh-my-cli --kind chat -- oh-my-cli ... 코드를 못 고치는 도구. OPENAI_BASE_URL·OPENAI_API_KEY를 환경변수로 넣어 실행한다

    resolve 흐름

    oh-my-cli 시작 / 주기적으로
  └─ hrun hmodels resolve --app oh-my-cli --kind chat --all --json
       ├─ 키 파일이 없으면 이때 자동 발급 (KAM) 또는 복사 (고정 키)
       └─ JSON: endpoints{base_url, credential, headers}, models[...], keys_dir
  └─ 모델 고르기: models[0]이 운영자가 정한 기본, hidden: true는 목록에서 숨김
  └─ 키 읽기: keys_dir/<credential>.json 의 "key"
  └─ 요청: base_url + Authorization: Bearer <key> + headers + 모델 설정(params, wire, reasoning)
  └─ 401이면: hrun hmodels refresh --app oh-my-cli --credential <credential> 후 키를 다시 읽고 한 번 재시도

    import json, os, subprocess
from openai import OpenAI

r = json.loads(subprocess.check_output(
    ["hrun", "hmodels", "resolve", "--app", "oh-my-cli", "--kind", "chat", "--all", "--json"],
    timeout=60))
models = [m for m in r["models"] if not m.get("hidden")]
m = models[0]                                    # 운영자가 정한 순서의 첫 번째가 기본
ep = r["endpoints"][m["endpoint"]]
key_file = os.path.join(r["keys_dir"], ep["credential"] + ".json")

def key():                                       # 401 뒤에도 다시 읽는다
    with open(key_file) as f:
        return json.load(f)["key"]

chat = m.get("chat") or {}
wire = chat.get("wire") or {}
client = OpenAI(base_url=ep["base_url"], api_key=key(), default_headers=ep.get("headers"))
body = dict(wire.get("extra_body") or {})
if wire.get("chat_template_kwargs"):
    body["chat_template_kwargs"] = wire["chat_template_kwargs"]
kwargs = dict(chat.get("params") or {})
if wire.get("always_send_max_tokens") and chat.get("max_output_tokens"):
    kwargs[wire.get("max_tokens_field", "max_tokens")] = chat["max_output_tokens"]
client.chat.completions.create(
    model=m["id"],
    messages=[{"role": "user", "content": "hello"}],
    extra_body=body or None,
    **kwargs,
)

    추론 강도를 고르게 하려면 chat.reasoning을 본다: supported_efforts가 있으면 선택지를 띄우고, 고른 강도에 effort_overrides 항목이 있으면 그 extra_body를 body에 더하고, 없으면 reasoning_effort=<강도>를 보낸다. 끄면 off의 값을 더한다.

    exec 흐름 (코드를 못 고치는 도구)

    hrun hmodels exec --app oh-my-cli --kind chat --model glm-4.6-fp8 -- oh-my-cli chat

    hmodels가 키를 준비하고 OPENAI_BASE_URL, OPENAI_API_KEY, HMODELS_MODEL을 환경변수로 넣은 뒤 그 명령을 실행한다. 도구가 다른 이름을 쓰면 --env MY_TOOL_KEY=key --env MY_TOOL_URL=base_url로 바꿔 넣는다. 한계: headers는 넣지 못하고, 오래 도는 프로세스는 키 교체를 모른다.

    키 만료와 갱신

    hmodels는 만료 시각을 보고 미리 갱신하지 않는다. 게이트웨이가 401로 거절할 때만 새로 받는다. KAM 키는 실제 사용량이 있으면 서버 쪽에서 계속 연장되고, 그 연장은 파일에 반영되지 않아서 파일상 "만료"는 정상 상태이기 때문이다.

    상황 동작
    평소 (resolve, refresh) 키 파일이 있으면 그대로 쓴다. 네트워크·KAM 호출 없음
    키 파일이 없음 (처음 사용, 새 프로젝트 그룹) 그 자리에서 발급(KAM) 또는 복사(고정 키)
    요청이 401 앱이 refresh --app oh-my-cli --credential <이름> → 새 키 → 한 번 재시도
    운영자가 고정 키를 바꿈 provider에 key_policy_rev를 올린다 → 각 사용자의 다음 resolve에서 새 키
    KAM 장애 재시도 간격 5분부터 두 배씩 최대 1시간. 그동안 기존 키(없으면 fallback 키)를 쓰고 degraded 표시
    며칠 안 쓴 사용자 키가 실제로 죽어 있다 → 첫 요청의 401로 위 경로를 탄다. 사용자에게 묻지 않는다
    • 같은 credential을 60초 안에 두 번 새로 받지 않는다. 여러 앱이 동시에 401을 받아도 KAM 호출은 한 번이다.
    • 앱 쪽 규칙은 둘뿐이다: 키는 파일에서 읽고(캐시해도 401 뒤엔 다시 읽기), 401엔 refresh --credential 후 한 번만 재시도.
    • exec로 띄운 오래 도는 프로세스는 키 교체를 모른다. 재시작해야 한다.

    필요해지면 더하는 것

    • provider: headers(요청마다 붙일 헤더, 예 "X-User-Id": "${user}"), visibility(provider 전체 기본 숨김), key_policy_rev(고정 키를 바꿨을 때)
    • 임베딩: matryoshka_dims·supports_dimensions_param(차원 줄이기), input_type(질의·문서 접두어)
    • rerank 모델: max_documents, score_range, wire.path 등
    • stats.json: 벤치 버전 선언(benchmarks)
