    HyperRun(hrun) 사용자 가이드

    2026-06-21

    HyperRun

    HyperRun is a small tool/runtime/environment router for closed internal networks. Users run commands such as:

    hrun python -V
hrun pip list
hrun mycli a b c

    HyperRun chooses the visible network runner, loads a small common dispatch layer, and then executes the command wrapper for the requested internal tool.

    Execution Flow

    /appl/bin/hrun
  -> /user/aegis/RELEASE/bin/run_hrun
     or
     /user/llmsol00/RELEASE/bin/run_hrun
  -> $HYPERRUN_ROOT/core/current/bin/hrun-core
  -> command wrapper
  -> real tool

    Example on A network:

    /appl/bin/hrun
  -> /user/aegis/RELEASE/bin/run_hrun
  -> /user/aegis/RELEASE/apps/hrun/core/current/bin/hrun-core
  -> /user/aegis/RELEASE/apps/hrun/commands/python
  -> /user/aegis/RELEASE/apps/hrun/toolkits/python/current/commands/python
  -> real Python

    Terms

    HYPERRUN_ROOT is the HyperRun deployment root, for example /user/aegis/RELEASE/apps/hrun.

    HYPERRUN_DATA_DIR is the user's HyperRun data root. The core dispatcher uses an explicit absolute HYPERRUN_DATA_DIR when set, otherwise ~/.hrun (the home from getent). In shared mode the release run_hrun makes ~/.hrun a symlink into the per-user shared dir.

    HYPERRUN_COMMAND_NAME is the command the user typed, for example python, pip, or mycli.

    HYPERRUN_TOOL_ID is the logical tool id. It defaults to the command name, but wrappers can change it. For example pip belongs to the python tool.

    HYPERRUN_TOOL_HOME is the only writable home HyperRun guarantees for a tool:

    $HYPERRUN_DATA_DIR/tools/<tool_id>

    HYPERRUN_APP_HOME is intentionally not used.

    Network Selection

    The C++ /appl/bin/hrun binary is a thin router and the only component that knows the real A/B paths. It selects the visible runner, exports the network values, and execs the release run_hrun; it does no data-directory, user, or subcommand handling.

    Default compiled paths:

    A runner: /user/aegis/RELEASE/bin/run_hrun
A root:   /user/aegis/RELEASE/apps/hrun

B runner: /user/llmsol00/RELEASE/bin/run_hrun
B root:   /user/llmsol00/RELEASE/apps/hrun

    Selection policy:

    • If A runner exists and is executable, use A.
    • If A runner does not exist, check B.
    • If B runner exists and is executable, use B.
    • If A and B are both visible, A wins.
    • If a visible runner exists but is not executable, exit 126.
    • If no runner exists, exit 127.

    Use HYPERRUN_TRACE=1 to print the selected network and runner to stderr.

    The router can also compile root-specific API defaults. When A is selected it exports the compile-time HYPERRUN_API_KEY_A/HYPERRUN_BASE_URL_A values as the runtime variables HYPERRUN_API_KEY and HYPERRUN_BASE_URL; when B is selected it uses the B values. They are exported only when the compiled value is non-empty.

    Build

    make build
make test

    The router is C++11 and POSIX API only. It does not use std::filesystem or an external JSON library.

    Supported Make overrides:

    make build \
  HYPERRUN_RUNNER_A=/user/aegis/RELEASE/bin/run_hrun \
  HYPERRUN_ROOT_A=/user/aegis/RELEASE/apps/hrun \
  HYPERRUN_API_KEY_A=... \
  HYPERRUN_BASE_URL_A=https://api-a.example/v1 \
  HYPERRUN_SHARED_DATA_ROOT_A=/user/aegis/RELEASE/userdata \
  HYPERRUN_RUNNER_B=/user/llmsol00/RELEASE/bin/run_hrun \
  HYPERRUN_ROOT_B=/user/llmsol00/RELEASE/apps/hrun \
  HYPERRUN_API_KEY_B=... \
  HYPERRUN_BASE_URL_B=https://api-b.example/v1 \
  HYPERRUN_SHARED_DATA_ROOT_B=/user/llmsol00/RELEASE/userdata

    HYPERRUN_SHARED_DATA_ROOT_* is optional (empty by default). When compiled in, the selected network puts each user's data under a shared tree at <root>/<user>/.hrun instead of $HOME/.hrun. See User Data Directory.

    For RHEL7-style deployment, STATIC_LIBS=1 can add -static-libstdc++ -static-libgcc.

    Install

    Install the common router:

    sudo make install-hrun

    Install a network root. The script takes explicit paths and does not hardcode A/B paths.

    sh packaging/install-network.sh \
  --runner-path /user/aegis/RELEASE/bin/run_hrun \
  --root /user/aegis/RELEASE/apps/hrun \
  --version v0.1.0

sh packaging/install-network.sh \
  --runner-path /user/llmsol00/RELEASE/bin/run_hrun \
  --root /user/llmsol00/RELEASE/apps/hrun \
  --version v0.1.0

    The install layout keeps versioned releases and flips current symlinks:

    $HYPERRUN_ROOT/core/current -> releases/v0.1.0
$HYPERRUN_ROOT/toolkits/python/current -> releases/v0.1.0

    Rollback is a symlink change.

    User Data Directory

    HyperRun does not require initialization or a user config file. The core dispatcher (hrun-core) uses an explicit absolute HYPERRUN_DATA_DIR when set, otherwise ~/.hrun (the home from getent passwd, falling back to $HOME), and creates the standard writable layout there (with the process default umask; no forced permission modes):

    $HYPERRUN_DATA_DIR/
  tools/
  commands/
  desc/
  docs/
    commands/
  env/
    global.env
    profiles/
      user.env
      agent.env
    tools/

    hrun config prints the data directory candidate resolved by the core dispatcher and whether it exists. The command does not create the data directory; normal command dispatch does. HyperRun does not create tools/python, tools/pip, or tools/mycli in advance. Tool homes are lazy-created by wrappers through hrun_enter_tool.

    Shared data root

    When HYPERRUN_SHARED_DATA_ROOT is compiled into the router (per network), the release run_hrun creates a per-user directory under it and links ~/.hrun to that directory; the core then just uses ~/.hrun:

    HYPERRUN_SHARED_DATA_ROOT=/user/aegis/RELEASE/userdata
  -> HYPERRUN_DATA_DIR = .../userdata/<user>/.hrun   (real directory)
  -> ~/.hrun           -> .../userdata/<user>/.hrun   (symlink)
    • The real data dir is the shared per-user directory; ~/.hrun is a best-effort symlink to it, so both paths work. An existing real ~/.hrun is never replaced (HyperRun warns and keeps using the shared path).
    • When HYPERRUN_SHARED_DATA_ROOT is not set, ~/.hrun is the data directory itself (a plain directory) — no symlink.
    • The username comes from id -un (effective UID; not affected by $USER); the home (~) is read from getent passwd, falling back to $HOME. If the resolved home is not an absolute path, the ~/.hrun symlink step is skipped.
    • An explicit HYPERRUN_DATA_DIR always wins, so users can still opt out.

    Examples:

    hrun python
  HYPERRUN_COMMAND_NAME=python
  HYPERRUN_TOOL_ID=python
  HYPERRUN_TOOL_HOME=$HYPERRUN_DATA_DIR/tools/python

hrun pip
  HYPERRUN_COMMAND_NAME=pip
  HYPERRUN_TOOL_ID=python
  HYPERRUN_TOOL_HOME=$HYPERRUN_DATA_DIR/tools/python

hrun mycli
  HYPERRUN_COMMAND_NAME=mycli
  HYPERRUN_TOOL_ID=mycli
  HYPERRUN_TOOL_HOME=$HYPERRUN_DATA_DIR/tools/mycli

    HyperRun does not force a structure inside HYPERRUN_TOOL_HOME. A tool may create config, cache, logs, tmp, or sessions if it needs them.

    Core Commands

    User-facing examples:

    hrun doctor
hrun config
hrun list
hrun which python
hrun env python
hrun docs python
hrun python -V
hrun pip list
hrun --profile agent python job.py

    Core built-ins:

    help
version
config
doctor
list
which <command>
env <command>
docs [--path] <command>
--profile <profile> <command> [args...]

    Command search order:

    1. $HYPERRUN_DATA_DIR/commands/<command>
2. $HYPERRUN_ROOT/commands/<command>

    User commands can override system commands.

    Profiles And Env

    Profile default is user. Override with:

    hrun --profile agent python job.py

    Load order:

    $HYPERRUN_ROOT/env/global.env
$HYPERRUN_DATA_DIR/env/global.env
$HYPERRUN_ROOT/env/profiles/<profile>.env
$HYPERRUN_DATA_DIR/env/profiles/<profile>.env

    Env files are not sourced. HyperRun safely parses only:

    KEY=value
KEY="value with space"
KEY='value with space'
export KEY=value
KEY=${OTHER_ENV}/suffix
KEY=${OTHER_ENV:-default}
# comment

    Keys must match [A-Za-z_][A-Za-z0-9_]*.

    Variable expansion is deliberately limited:

    • ${VAR} expands from the current process environment.
    • ${VAR:-default} uses default when VAR is unset or empty.
    • Variables defined earlier in the same env file are available to later lines.
    • Single quotes are literal and do not expand variables.
    • Double quotes and unquoted values expand ${VAR} forms.

    Unsupported syntax is rejected:

    BAD=$BASE/bin
BAD=$(some command)
BAD=`some command`
BAD=$((1 + 2))
BAD=${VAR/pattern/repl}
BAD=${VAR:=value}
BAD=${VAR:?message}

    Undefined ${VAR} without a :-default is an error. This catches misspelled settings early.

    Load order matters. Global and profile env files can use HYPERRUN_ROOT and HYPERRUN_DATA_DIR; tool env files can also use HYPERRUN_TOOL_HOME because wrappers call hrun_enter_tool before loading tool env.

    Docs And Descriptions

    Descriptions:

    $HYPERRUN_DATA_DIR/desc/<command>.desc
$HYPERRUN_ROOT/desc/<command>.desc
HYPERRUN_INSPECT=describe <wrapper>

    Command docs:

    $HYPERRUN_DATA_DIR/docs/commands/<command>.md
$HYPERRUN_ROOT/docs/commands/<command>.md
HYPERRUN_INSPECT=docs <wrapper>

    Use:

    hrun docs python
hrun docs --path python

    Python Toolkit

    Python and pip share one tool home:

    HYPERRUN_TOOL_ID=python
HYPERRUN_TOOL_HOME=$HYPERRUN_DATA_DIR/tools/python

    Python executable selection:

    1. HYPERRUN_PYTHON_EXE
2. HYPERRUN_PYTHON_RHEL7 / HYPERRUN_PYTHON_RHEL8 / HYPERRUN_PYTHON_RHEL9
3. $HYPERRUN_ROOT/runtimes/python/rhel7/current/bin/python3.9
   $HYPERRUN_ROOT/runtimes/python/rhel8/current/bin/python3.11
   $HYPERRUN_ROOT/runtimes/python/rhel9/current/bin/python3.11

    Wheelhouse selection:

    1. existing PIP_FIND_LINKS
2. HYPERRUN_WHEELHOUSE
3. HYPERRUN_WHEELHOUSE_RHEL7 / RHEL8 / RHEL9
4. $HYPERRUN_ROOT/wheelhouse/<platform-tag>

    User overrides belong in:

    $HYPERRUN_DATA_DIR/env/tools/python.env

    Example:

    HYPERRUN_PYTHON_RHEL8=${HYPERRUN_ROOT}/runtimes/python/rhel8/current/bin/python3.11
HYPERRUN_WHEELHOUSE_RHEL8=${HYPERRUN_ROOT}/wheelhouse/rhel8-cp311-manylinux_2_28-x86_64
PYTHONUSERBASE=${HYPERRUN_TOOL_HOME}/userbase

    Adding Tools

    A toolkit provides wrappers, env defaults, descriptions, and docs:

    toolkits/<tool>/
  commands/<command>
  env/<tool>.env
  desc/<command>.desc
  docs/commands/<command>.md
  docs/README.md
  docs/env.md
  VERSION

    Wrappers should call:

    hrun_enter_tool <tool_id> [command_name]

    The mycli template shows this pattern. To add system commands after installing a toolkit, run:

    sh packaging/sync-system-commands.sh --root "$HYPERRUN_ROOT" --manifest commands.tsv

    Security Rules

    • Do not hardcode A/B paths outside the C++ router build constants.
    • Do not add a separate user config file for the data root; use $HOME/.hrun.
    • Do not use eval, system("..."), popen, or shell string execution.
    • Do not source user env files.
    • Preserve args with "$@".
    • Validate command/profile/tool names.
    • Do not create HYPERRUN_APP_HOME.
    • Use HYPERRUN_TOOL_HOME for tool writable state.
    • Do not force detailed structure inside HYPERRUN_TOOL_HOME.
