    ComfyUI 소스 코드 관리 조언

    2025-09-17

    ComfyUI를 회사 내부의 Workflow Manager 툴로 patch해서 쓰려고 해. 그래서 소스 코드를 바꾸거나 커스텀노드, 템플릿 등을 건드려야 해. 그런데 한 편으로는 외부에서 개발되는 ComfyUI의 신규 기능들도 지속해서 integration하고 싶어. 이런 경우 소스 코드를 어떻게 관리하면 좋을까? 기본적인 환경은 git을 사용하고 있어.

    좋은 질문이에요. “우리만의 워크플로 매니저로 커스터마이즈”하면서도 “업스트림(ComfyUI)의 신기능은 계속 받아오기” — 이 두 마리 토끼를 잡으려면 코어 수정 최소화 + 경계(업스트림 vs 사내 코드) 명확화 + 재현 가능한 버전 고정 이 핵심이에요. 아래처럼 단계별로 설계하면 깔끔하게 굴러갑니다.

    1) 기본 원칙 (요약)

    1. 코어 수정은 최후의 수단. 가능하면 전부 Custom Node/패키지/템플릿 으로 빼고, ComfyUI 코어는 그대로 둡니다.

    2. 경계 분리. 업스트림과 사내 코드를 서로 다른 리포지토리/브랜치 로 분리합니다.

    3. 버전 핀(Pin). “이 릴리스는 업스트림 커밋 X + 내부 노드 버전 Y” 같은 조합을 태그로 고정 합니다.

    4. 정기 통합은 자동화. 업스트림 갱신 → 테스트 → 통합 결과 PR까지 자동으로 열리게 CI 구성.

    2) 추천 리포 구성 (가장 실무적인 구조)

    A. 배포/운영용 래퍼(Wrapper) 리포

    • 이름 예: company/comfyui-stack

    • 용도: 단일 진입점. 여기서 업스트림 ComfyUI와 내부 노드/템플릿을 서브모듈(submodule) 또는 서브트리(subtree) 로 묶어 버전을 고정 합니다. Docker/컨테이너, 런처 스크립트, 테스트, 릴리스 태깅 등도 여기서.

    B. 업스트림 ComfyUI (그대로 or Fork)

    • 업스트림: comfyanonymous/ComfyUI (읽기 전용 remote: upstream)

    • 꼭 코어를 건드려야 하면 프라이빗 Fork company/ComfyUI를 사용해 패치 브랜치(아래 4절)를 운용합니다.

    • 가능하면 코어 PR을 업스트림에 올려 패치 부채 줄이기.

    C. 내부 커스텀 노드/확장

    • 예: company/comfyui-nodes-internal

    • 내용: custom_nodes/company_* 하위로 로딩되도록 구성.

    • 의존성 고정(requirements.txt/pip-tools), 간단한 단위/스모크 테스트 포함.

    D. 워크플로 템플릿/프리셋

    • 예: company/comfyui-workflows

    • JSON 워크플로 모음 + 각 템플릿이 요구하는 노드/코어 최소 버전 명시(README/메타파일).

    왜 이렇게?

    • 업스트림과 내부 코드를 물리적으로 분리 하면 충돌/리스크가 급감합니다.

    • 래퍼 리포가 “조합을 고정”하므로, 재현 가능한 배포/롤백이 쉬워집니다.

    3) submodule vs subtree (간단 비교)

    • submodule : 각 리포 독립 히스토리 유지, 정확한 커밋 고정 에 최적. 단, 사용자가 git submodule update를 신경 써야 함.

    • subtree : 체크아웃이 단순, CI가 편함. 대신 업스트림/내부 히스토리 섞임 과 업데이트 절차가 약간 수동.

    실무에선 정밀 고정이 중요한 코어(ComfyUI)는 submodule , 템플릿은 subtree 또는 동일 리포 도 편합니다.

    4) 코어 패치가 “불가피”할 때의 Git 전략 (두 가지)

    (옵션 1) 포크 + 패치 스택(rebase) 방식

    • 브랜치 구조:

      • main(또는 master): 업스트림을 미러링 (직접 커밋 금지)

      • internal/patches: 우리 패치 얇은 커밋 스택 (가능하면 작은 토픽 브랜치 묶음)

    • 업스트림 갱신 루틴: 
      git remote add upstream https://github.com/comfyanonymous/ComfyUI.git
git fetch upstream
git checkout main
git reset --hard upstream/<UPSTREAM_BRANCH>   # 업스트림 미러
git checkout internal/patches
git rebase upstream/<UPSTREAM_BRANCH>         # 패치 스택 올려타기
# 충돌 해결 → 테스트 → 푸시
git push --force-with-lease

    • 장점: 히스토리 깔끔, 충돌 원인 추적 쉬움.

    • 단점: rebase 숙련 필요.

    (옵션 2) 포크 + 머지 기반 방식

    • internal/integration 브랜치에 주기적으로 업스트림을 머지 : 
      git fetch upstream
git checkout internal/integration
git merge --no-ff upstream/<UPSTREAM_BRANCH>

    • 장점: rebase 스트레스 적음.

    • 단점: 히스토리에 머지 커밋이 쌓여 분석이 다소 어려움.

    Tip: 어떤 방식을 쓰든 git config --global rerere.enabled true(충돌 학습)로 반복 충돌 자동 해결 을 켜 두세요.

    5) “코어 수정 회피” 테크닉 (현실 팁)

    • 후킹/확장점 재활용 : 가능하면 노드/매크로/템플릿/스크립트 레벨로 해결.

    • 런칭 래퍼로 설정 주입 : 코어 파일을 직접 고치지 말고, 환경변수/런처 스크립트 로 경로/옵션을 주입.

    • Monkey-patch는 최소화 : 꼭 필요하면 단일 파일 에 모아두고, 업스트림 변경 시 영향 범위를 한곳에서 확인.

    6) 버전 고정 & 릴리스 절차 (Step-by-step)

    1. 래퍼 리포 에 서브모듈 핀: 
      git submodule add https://github.com/comfyanonymous/ComfyUI vendor/comfyui
git submodule add git@github.com:company/comfyui-nodes-internal.git custom_nodes/company
git commit -m "Add ComfyUI + internal nodes as submodules"

    2. KNOWN-GOOD 조합 을 태그:

      • 예: comfy-stack-2025.09.17 → 특정 업스트림 커밋 + 내부 노드 커밋 조합

    3. Docker 이미지 나 패키징 스크립트에서 해당 커밋을 체크아웃 → 재현 가능 빌드.

    4. CHANGELOG : “업스트림 커밋/태그, 내부 변경, 마이그레이션 노트”를 짧게 기록.

    7) 업스트림 자동 통합 파이프라인 (권장 CI 형태)

    • 주기 트리거(예: 매주):

      1. 업스트림 최신 커밋 확인

      2. 포크의 internal/patches를 최신으로 rebase/merge 시뮬레이션

      3. 스모크 테스트 :

        • 서버 부팅, 주요 내부 노드 로딩

        • 핵심 워크플로 2~3개 실행(샘플 이미지/텍스트 아웃풋 비교)

      4. 성공 시 래퍼 리포에서 서브모듈 커밋 bump PR 자동 생성

      5. 사람이 PR 리뷰 후 머지 & 새 태그 발행

    • 실패하면 CI가 충돌/테스트 실패 리포트 를 남기고 종료(사람이 개입).

    8) 워크플로(템플릿) 호환성 관리

    • 각 템플릿 폴더에 metadata.yaml(예시)로 요구사항 명시: ```yaml requires: comfyui: ">=0.0.0,<0.1.0" # 또는 커밋/태그 SHA nodes: - company-nodes: ">=1.4.0" tested_with:
      • comfyui_commit: ""
      • company_nodes_commit: "" notes: "노드 X 파라미터가 2025-09에서 변경됨" ```
    • 마이그레이션 스크립트 : 필드명 변경/삭제를 자동 변환하는 작은 Python 유틸을 템플릿 리포에 둡니다.

    9) 팀 합의 가이드(충돌 줄이는 코딩 규칙)

    • 금지 파일 목록 정하기: “여긴 절대 손대지 말기”. (예: 코어 로더/스캐너)

    • 기능 플래그 : 내부 변경은 COMPANY_FEATURE_X=1 식으로 켜고 끌 수 있게.

    • 커밋 규칙 : “문제 → 접근 → 변경점 → 리스크/롤백 방법”을 커밋 메시지에 짧게.

    • 테스트 샌드박스 : 내부 노드 당 최소 1개 워크플로 스모크 테스트 유지.

    10) 처음 세팅할 때(실행 예시)

    # 0) 래퍼 리포
git clone git@github.com:company/comfyui-stack.git
cd comfyui-stack

# 1) 업스트림과 내부 노드 서브모듈 추가
git submodule add https://github.com/comfyanonymous/ComfyUI vendor/comfyui
git submodule add git@github.com:company/comfyui-nodes-internal.git custom_nodes/company
git commit -m "Add submodules"

# 2) 업스트림 기본 remote 설정(선택: 포크도 같이)
cd vendor/comfyui
git remote add upstream https://github.com/comfyanonymous/ComfyUI.git
git fetch upstream
# 필요 시 포크 remote도 추가: origin=company/ComfyUI
cd ../..

# 3) 로컬 실행 스크립트
./scripts/dev_up.sh    # venv 생성, 요구 패키지 설치, ComfyUI 실행 등

    언제 어떤 선택을?

    • 코어 안 건드려도 된다 → 가장 좋음 : “업스트림 그대로 + 내부는 전부 커스텀 노드/템플릿” 모델.

    • 코어도 손대야 한다 → 포크 운용하되, 패치 스택을 얇고 주제별로 유지 + 가급적 업스트림에 PR로 환원.

    • 분산 배포가 중요 → 래퍼 리포에서 정확한 커밋 조합 을 서브모듈로 고정하고, 태그/릴리스 노트를 운영.

    필요하시면, 현재 보유한 수정 사항을 기준으로 “코어 수정 분리 설계(어떤 걸 커스텀 노드로 뺄지 / 꼭 남겨야 할 코어 패치는 무엇인지)” 체크리스트 만들어 드릴게요. 구성 중 막히는 포인트(예: submodule/subtree 적용, CI 샘플 워크플로, Docker 빌드 스크립트)도 바로 템플릿으로 드릴 수 있습니다.

    사내는 보안망이기 때문에 업스트림이 불가능해. 그리고 ComfyUI 자체 코드뿐만 아니라 Comfy_templates 등 패키지도 설치하던데 지금은 .venv/lib/site-packages에서 해당 패키지를 찾아서 코드를 수정했어 - 우리가 원하는 템플릿만 보이게 하기 위해

    좋아요. “외부 네트워크가 막힌 사내 망(air-gapped) + 우리가 원하는 동작으로 커스터마이즈 + 업스트림의 변화는 배치로 주기 반입”이라는 전제로, site-packages를 직접 고치는 방식은 그만 두고 다음처럼 구조화하세요. 아래는 바로 실행 가능한 단계별(최소마찰) 설계입니다.

    1) 전체 전략 한 장 요약

    • 분리 : 업스트림 스냅샷(미러) ↔ 사내 커스터마이징(오버레이/포크) ↔ 배포 조합(스택 리포)을 분리.

    • 고정 : “조합(업스트림 커밋들 + 내부 패키지 버전들)”을 태그/락파일 로 고정.

    • 무수정 원칙 : .venv/lib/site-packages 직접 수정 금지. 대신 포크/오버레이/플러그인 으로 덮어쓰기.

    • 오프라인 공급망 : 외부에서 번들(wheelhouse + 소스 tarball + git 스냅샷) 만들어 들여와 내부 PyPI/깃에 업로드.

    • 자동화 : 미러 갱신 → 테스트 → 스택 리포 서브모듈 bump PR까지 사내 CI 로.

    2) 리포지토리 구성 (권장)

    1. 스택(래퍼) 리포 : company/comfy-stack

      • 역할: 단일 진입점. 내부 Git의 하위 리포들을 submodule 로 고정.

      • 포함물: vendor/ComfyUI(업스트림 미러), vendor/ComfyTemplates(업스트림 미러), overlays/*(사내 포크/오버레이), wheels/(오프라인 설치용), Docker/런처/테스트, STACK.lock(커밋/버전 고정).

    2. 업스트림 미러 리포(읽기 전용) : mirror/ComfyUI, mirror/ComfyTemplates, …

      • 외부에서 정기 수집한 깨끗한 스냅샷 만 저장(사내에서 수정 금지).

    3. 사내 포크/오버레이 리포(쓰기 가능) : company/ComfyUI-internal, company/ComfyTemplates-internal, company/comfy-nodes-internal

      • 필요한 최소 패치만 얇게 유지(토픽 브랜치/패치스택).

      • 가능하면 “새 기능”은 커스텀 노드/플러그인/템플릿 쪽으로.

    배포는 항상 comfy-stack에서: 서브모듈 커밋을 특정 SHAs로 핀하고, 태그 stack-YYYYMMDD로 릴리스.

    3) 업스트림 반입(외부→내부) 파이프라인

    외부(인터넷 가능 환경)에서:

    1. 지정 리비전 체크아웃 → git 아카이브(또는 bare mirror) 생성

    2. 파이썬 의존성 wheelhouse 빌드: 
      pip wheel -r requirements.txt -w wheelhouse/ --no-cache-dir
    3. bundle/ 구조로 묶기: 
      bundle/
  repos/
    ComfyUI.tar.zst
    ComfyTemplates.tar.zst
  wheels/
    *.whl
  MANIFEST.json   # 커밋 SHA, 버전, 해시
  RELEASE_NOTES.md
    4. 해시/서명 생성 후 보안 반입(오프라인 매체).

    내부(사내망)에서:

    • mirror/* 리포에 가져와 push

    • 내부 PyPI(devpi/Nexus/Artifactory 또는 단순 파일서버)에도 wheels/ 업로드

    4) 오프라인 설치 표준(재현 가능한 빌드)

    • constraints 파일 로 버전 고정 + 내부 PyPI/파일서버 만 사용: 
      pip install --no-index --find-links file:///srv/pypi/simple \
            --find-links ./wheels \
            -r requirements.txt \
            -c constraints.txt

    • 가급적 소스가 아닌 wheel만 사용(컴파일 변동 최소화).

    • venv 생성/업데이트는 스택 리포의 스크립트로 통일: 
      ./scripts/bootstrap.sh   # venv 만들고 wheelhouse에서 설치

    5) “site-packages 직접 수정”의 대체 3가지

    (A) 포크로 덮어쓰기(정석)

    • ComfyTemplates 같이 우리가 바꾸려는 패키지를 사내 포크 로 유지(company/ComfyTemplates-internal).

    • 배포 시엔 포크 빌드한 wheel 만 설치(원본 대신).

    • 버전 표기 예: 1.4.2+company.3 (PEP440) → pip가 “우리 빌드”를 선택.

    • 장점: 가장 명시적이고 추적 가능. 단점: 포크를 꾸준히 rebase/merge 해야 함.

    (B) 오버레이(모듈 경로 우선) 방식

    • 스택 리포에 overlays/comfy_templates/처럼 원본과 동일 모듈명 디렉터리를 두고, 런처에서 PYTHONPATH 앞쪽에 추가: 
      export PYTHONPATH="$REPO_ROOT/overlays:$PYTHONPATH"
python -m comfy.launch

    어떤 걸 고를까?

    • 서브모듈/상대 import가 많다 → A(드롭인 교체) 권장. 가장 튼튼.

    • 빠른 스위치/실험 이 필요 → B(sitecustomize) 또는 C(shim)

    • “pip로만 배포, git 없이 개발/테스트”라는 현재 조건에도 A/B/C 모두 적용 가능 합니다.

    1. 업스트림 wheel 제거 or 우선순위 통제(우리 wheel만 설치되도록).

    2. constraints.txt로 버전 핀 고정.

    3. 스모크 테스트 : 서버 부팅, 템플릿 로딩, 대표 워크플로 1~2개 실행.

    4. 문제시 번들 교체/ENV 스위치 로 즉시 롤백.

    짧은 답: 굳이 “전체 클론”까지는 필수는 아니지만 ,
    main.py를 건드리지 않고 import comfyui_templates를 우리 구현으로 바꾸려면 “드롭인 교체(drop-in replacement)” 패키지 가 가장 안전합니다. 이건 두 방식이 있어요:

    1. 완전 포크(클론) 기반 드롭인 교체 ← 가장 튼튼 (서브모듈/하위패키지 import가 많을 때 권장)

    2. 얇은 대체(래퍼/alias) 기반 드롭인 ← 바꿀 게 적을 때 빠름 (서브모듈 import가 적을 때)

    아래에 각각 “언제/어떻게”를 단계별로 정리할게요.

    1) 언제 “완전 클론(포크) → 우리 패키지”가 맞나?

    • comfyui_templates가 하위 패키지/서브모듈 을 많이 쓰거나, 내부에서 상대 import가 복잡함

    • 업스트림과 동일한 디렉터리 구조 를 유지해야 안전함

    • 장기적으로 업스트림 변경에도 호환성 스트레스 최소화 가 우선

    이때는 외부 환경(인터넷 가능)에서 업스트림을 한 번 클론해 토대 삼고, 우리 리포/우리 wheel 로 빌드해 반입하는 게 정석입니다. 사내망에서는 pip install만으로 우리 버전이 로드되죠.

    실전 절차(권장)

    1. 외부에서 업스트림 comfyui_templates 가져오기 → 우리 변경(템플릿 필터/정책 반영).

    2. 배포 이름 그대로 빌드

    장점: 서브모듈 import, 패키지 데이터(템플릿 파일) 포함, 엔트리포인트 등 모든 케이스를 안정적으로 커버.

import os

def _load_allowlist():
    p = os.getenv("COMFY_TEMPLATES_ALLOWLIST")
    if not p or not os.path.exists(p):
        return None
    with open(p) as f:
        return {ln.strip() for ln in f if ln.strip() and not ln.startswith("#")}

try:
    # 1) 원본 모듈 "그대로" 로드
    import comfyui_templates as ct

    # 2) 글로벌 레지스트리/리스트를 필터링 (데이터 구조에 맞게 수정)
    allow = _load_allowlist()
    if allow and hasattr(ct, "registry") and hasattr(ct.registry, "templates"):
        ct.registry.templates[:] = [t for t in ct.registry.templates if getattr(t, "name", None) in allow]

    # 3) 특정 함수만 래핑(필요할 때만)
    if hasattr(ct, "build_index"):
        _orig_build_index = ct.build_index
        def build_index(*args, **kwargs):
            res = _orig_build_index(*args, **kwargs)
            if allow and isinstance(res, dict) and "templates" in res:
                res["templates"] = [t for t in res["templates"] if t.get("name") in allow]
            return res
        ct.build_index = build_index

    # 4) 클래스 메서드만 부분 교체도 가능
    if hasattr(ct, "Template") and hasattr(ct.Template, "render"):
        _orig_render = ct.Template.render
        def render(self, *a, **k):
            # 필요시 정책 체크/로깅 추가
            return _orig_render(self, *a, **k)
        ct.Template.render = render

except Exception:
    # 실패해도 앱 동작은 막지 않음(로그는 필요시 추가)
    pass

    장점

    • main.py와 원본 패키지 그대로 사용 → 나머지 함수·클래스는 전부 원본을 그대로 씀

    • 우리는 “필요한 부분만” 갈아끼움 → 모든 함수 재구현 불필요

    • 롤백도 간단(패키지 제거/ENV 해제)

    요지: “alias”라고 표현했던 건, 실제로는 원본을 import한 뒤 일부 심만 바꾸는 런타임 패치 를 의미합니다.

    선택 2) 프록시 모듈(얇은 래퍼)로 “오버라이드 + 나머지는 위임”

    조금 더 분리하고 싶다면, sitecustomize에서 프록시 모듈 을 만들어
    sys.modules['comfyui_templates']에 꽂아 넣고, 겹치는 심만 오버라이드 ,
    나머지 속성 접근은 원본으로 위임 하게 만들 수 있어요.

    # sitecustomize.py (프록시 버전 — 필요할 때만)
import types, sys, importlib

try:
    _orig = importlib.import_module("comfyui_templates")  # 원본 로드
    proxy = types.ModuleType("comfyui_templates")

    # 1) 기본 위임(__getattr__)으로 모든 심을 원본으로 전달
    def __getattr__(name):
        return getattr(_orig, name)
    proxy.__getattr__ = __getattr__

    # 2) 여기서 필요한 것만 덮어쓰기
    if hasattr(_orig, "build_index"):
        _orig_build_index = _orig.build_index
        def build_index(*a, **k):
            res = _orig_build_index(*a, **k)
            # ...필터/추가정책...
            return res
        proxy.build_index = build_index

    # 3) 교체
    sys.modules["comfyui_templates"] = proxy

except Exception:
    pass

    주의

    • 이 방식은 속성 접근 은 잘 위임하지만, import comfyui_templates.subpkg 같은 서브모듈 import 까지 전부 대리하려면 추가 훅이 필요할 수 있습니다. 이런 경우엔 선택 1(원본 in-place 패치)가 훨씬 간단하고 안전합니다.

    언제 “완전 드롭인 교체(우리 패키지로 대체)”가 필요한가?

    • 원본 내부 구조가 자주 바뀌고, 우리가 여러 서브모듈까지 광범위 수정 해야 할 때

    • 서브모듈 import/패키지 데이터/엔트리포인트 등 패키지 전체 동작을 통째로 관리 하고 싶을 때

    그럴 때만 업스트림과 동일한 import 이름으로 우리 wheel 을 빌드해 “완전 교체”하면 되고,
    그 외 대부분의 필터/정책 주입 요구 는 위의 선택 1 로 충분합니다.

    요약 (현실 적용)

    • “모든 함수를 우리가 다시 만들 필요 없다.”

    • 가장 단순/탄탄한 해법 : company-comfy-policies wheel에 sitecustomize.py를 넣고,
      거기서 원본comfyui_templates를 import → 필요한 함수/데이터만 패치.

    • 템플릿 노출 제어처럼 선택적 필터링 은 전역 레지스트리/로딩 함수 한두 곳만 건드리면 끝.

    원하시면, 위 sitecustomize.py를 여러분 환경(레지스트리 구조/함수명)에 맞춰 딱 맞는 버전 으로 작성해 드릴게요.

    잘 이해가 안돼 아직도. 엄청 작은 예시로 알려줘. 예를 들어 hello world를 프린트 하는 모듈을 패키지를 hello man 으로 바꾼다든지

    좋아요—진짜 초미니 데모 로 보여줄게요.
    포인트는 두 가지예요.

    1. 모듈을 통째로 바꿔치기(Alias)

    2. 원본을 그대로 쓰되, 필요한 함수만 덮어쓰기(Monkey-patch)

    아래 예시는 main.py가 절대 수정되지 않는다 는 가정입니다.

    데모 1) “모듈 통째로 교체” (alias 방식)

    파일 배치

    ./main.py
./man.py
./sitecustomize.py    # 파이썬은 시작할 때 이 모듈을 자동 import함

    코드

    man.py

    def greet():
    print("Hello, man")

    main.py ← 수정 금지(여기서는 ‘hello’라는 모듈을 쓴다고 가정)

    import hello
hello.greet()

    sitecustomize.py ← 여기서 “hello”라는 이름을 “man”으로 바꿔치기

    import importlib, sys
sys.modules['hello'] = importlib.import_module('man')

    실행

    python main.py
# 출력: Hello, man

    왜 되나?
    파이썬은 시작 시 sitecustomize를 자동 로드해요(기본 옵션에서).
    여기서 sys.modules['hello']에 우리가 원하는 모듈(man)을 꽂아두면,
    main.py의 import hello가 그걸 그대로 가져옵니다.

    데모 2) “원본은 유지, 함수만 갈아끼우기” (monkey-patch 방식)

    파일 배치

    ./main.py
./hello.py
./sitecustomize.py

    코드

    hello.py ← 원래 구현(건드리지 않는다고 가정)

    def greet():
    print("Hello, world")

    main.py ← 수정 금지

    import hello
hello.greet()

    sitecustomize.py ← 시작 시 원본을 로드해서 필요한 함수만 교체

    import hello as _hello

def _new_greet():
    print("Hello, company!")

_hello.greet = _new_greet

    실행

    python main.py
# 출력: Hello, company!

    핵심: 모든 함수를 다시 만들 필요 없음.
    원본 hello를 그대로 import한 뒤 딱 필요한 심만 교체 하면 됩니다.

    실전 팁 (ComfyUI에 대입하면)

    • 예를 들어 main.py가 import comfyui_templates를 한다면,

      • 데모 1 패턴 : sys.modules['comfyui_templates'] = importlib.import_module('company_templates')

      • 데모 2 패턴 : import comfyui_templates as ct 후 ct.build_index = our_build_index 같이 일부만 교체

    • 이 파일(sitecustomize.py)은 휠(wheel)로 패키징 해서 pip install만으로 배포할 수 있어요.
      설치만 되면 파이썬이 알아서 로드해줍니다(옵션 -S로 실행하지 않는 한).

    필요하면, 위 예시를 바로 패키지(휠) 형태 로 빌드하는 pyproject.toml 틀도 만들어 줄게요.
