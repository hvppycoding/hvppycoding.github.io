여백은 요소의 것이다

문서용 HTML을 만들 때 흔히 컴포넌트 카탈로그부터 짠다. 그러면 소제목이 앞 문단에 달라붙고, 그 증상을 마진으로 하나씩 때우게 된다. 왜 그렇게 되는지와, 규칙 세 줄로 끝나는 대안을 정리한다.

대상: 문서·리포트용 HTML을 직접 짜는 사람범위: 순수 CSS

증상

튜닝을 마친 스타일시트인데도 소제목 위 여백이 자리에 따라 달라진다. 아래는 같은 스타일시트를 브라우저에 올려 실제로 잰 값이다.

구간실측 여백
문단 → 문단 (기준)16px
섹션 첫 자식으로 놓인 소제목36px
문단 다음에 온 소제목0px

0px이 예외처럼 보이지만 사실은 반대다. 한 화면을 넘는 문서에서 소제목은 대부분 문단 뒤에 온다. 즉 깨진 쪽이 기본 경로다.

원인 하나 — 여백이 래퍼에 있다

카탈로그식 스타일시트는 보통 이렇게 생겼다.

.doc__section       { padding-top: 36px; }
.doc__section-title { margin: 0 0 14px; }

제목의 위 여백은 0이고, 그 자리를 섹션 래퍼의 padding-top이 대신 만든다. 이 구조는 제목이 래퍼의 첫 자식일 때만 성립한다. 같은 섹션 안에서 문단 뒤에 제목을 하나 더 쓰는 순간 위 여백은 그냥 사라진다. 래퍼는 제목이 어디 있는지 모르기 때문이다.

여백을 래퍼에 두면, 그 여백은 위치에 대한 가정을 함께 갖는다. 가정이 깨지는 곳이 바로 문서의 본문이다.

원인 둘 — 카탈로그는 산문을 모른다

클래스로만 짠 스타일시트에는 정의된 컴포넌트만 존재한다. 정작 문서를 이루는 것은 평범한 태그다.

  • ul·ol — 브라우저 기본 들여쓰기는 본문 측정폭을 40px 넘겨 튀어나간다
  • 인라인 code — 배경도 없고 한글 본문보다 커 보인다
  • pre — 패딩도 넘침 처리도 없는 맨 텍스트가 된다
  • blockquote — 의도 없는 들여쓰기처럼 읽힌다

모델이든 사람이든, 카탈로그에 없는 요소를 쓸 때 길은 둘뿐이다. 맨 태그를 써서 브라우저 기본값과 충돌하거나, 클래스를 새로 만들며 margin: 0 0 N 패턴을 복사해 위 여백을 다시 0으로 만들거나. 두 길 다 지저분한 쪽으로 간다.

고침 — 리듬 세 줄

여백을 요소로 되돌리면 규칙이 세 줄로 수렴한다.

.doc > * + *                    { margin-top: 16px; }
.doc > :is(h1,h2,h3,h4)        { margin-bottom: 0; }
.doc > h2                      { margin-top: 52px; }
.doc > h3                      { margin-top: 34px; }
.doc > :is(h1,h2,h3,h4) + *    { margin-top: 14px; }

첫 줄이 모든 형제 사이를 채우고, 나머지가 제목만 덮어쓴다. 제목은 이제 자기 여백을 직접 들고 다니므로 문서 어디에 나와도 같은 값을 갖는다.

위를 아래보다 넓게

제목의 위 여백을 아래의 두세 배로 준다. 그래야 제목이 아래 내용에 붙어 읽히고, 앞 문단과 다음 절 사이에 애매하게 떠 있지 않는다. 위아래가 같으면 제목은 어느 쪽에도 속하지 않는 줄이 된다.

margin-bottom 하나에 기대지 않기

아래 여백만으로 리듬을 만들면 인접 마진 상쇄가 엔진과 인쇄에서 다르게 동작하고, 래퍼 다음 첫 요소는 아무 여백도 못 받는다. 형제 규칙(* + *)은 그 두 문제를 함께 피한다.

클래스가 아니라 요소를 스타일한다

문서는 p, ul, li, a, code, pre, blockquote, table, hr로 쓰인다. 이 태그들을 루트 아래에 스코프해서 전부 스타일하면, 본문을 쓸 때 클래스가 필요 없어진다.

.doc :is(ul, ol) { margin: 0; padding-left: 1.6em; }
.doc li + li     { margin-top: 7px; }
.doc code        { padding: 0.14em 0.4em; border-radius: 5px;
                   background: var(--inset); font-size: 0.875em; }

클래스는 태그로 표현되지 않는 것에만 남긴다. 키커, 메타데이터 줄, 경계가 있는 노트, 푸터 크레딧 정도면 충분하다.

넓은 표는 스스로 스크롤하게

표를 블록으로 만들면 내용만큼만 넓어지고 넘칠 때 자기 안에서 가로로 스크롤한다. 래퍼 div가 필요 없어진다.

.doc table { display: block; width: max-content;
             max-width: 100%; overflow-x: auto; }

예외 — 호스트 CSS를 통제할 수 없을 때

Confluence HTML Macro처럼 남의 페이지 안에 조각으로 들어가는 경우는 이야기가 다르다. 호스트가 ID 셀렉터와 !important로 p·td·li의 타이포그래피를 직접 덮어쓰는데, 상속값은 어떤 직접 규칙에도 진다.

조각으로 배포할 때

텍스트를 가진 컴포넌트마다 font-size와 line-height를 !important로 직접 선언하고, 모든 셀렉터를 고유한 루트 클래스로 스코프한다. 이 갑옷은 비용이지 미덕이 아니다. 내 페이지를 통째로 소유하는 문서라면 지불할 이유가 없다.

점검표

스타일시트를 넘기기 전에 이 정도만 확인하면 된다.

  1. 문단 다음에 온 소제목의 위 여백이 섹션 첫 소제목과 같은가
  2. 제목의 위 여백이 아래 여백보다 뚜렷하게 큰가
  3. 목록·인용·인라인 코드·코드 블록이 전부 스타일을 갖는가
  4. 본문 마크업에 여백을 때우려고 넣은 클래스나 인라인 style이 없는가
  5. 넓은 표가 페이지를 넓히지 않고 자기 안에서 스크롤하는가

여백이 틀렸다면 그 자리에 마진을 더할 게 아니라, 그 요소의 규칙이 틀린 것이다.
