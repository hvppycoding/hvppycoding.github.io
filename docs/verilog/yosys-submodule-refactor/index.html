    Yosys submodule refactor

    2025-08-18

    Verilog Netlist가 주어지고, 이 중 하나의 모듈 내의 인스턴스들을 묶어서 새로운 하나의 내부 모듈로 만드는 것을 자동화하고 싶어. 일반적인 프로그래밍에서는 함수의 일부분을 묶어서 새로운 함수로 정의하고 이걸 사용하는 식으로 refactoring 하는 것과 유사할 것 같아. 어떻게 하는게 좋을까?

    GPT-5 Pro 요청

    Reasoned for 6m 20s

    좋은 아이디어예요. 이건 소프트웨어에서 “Extract Function(함수 추출)” 리팩토링에 해당하는 “Extract Submodule(서브모듈 추출)” 작업이고, 자동화 관점에서 보면 다음 두 가지 경로가 현실적입니다.

    • 현존 도구 활용(추천): Yosys의 submod 패스를 이용해 선택한 인스턴스 묶음을 자동으로 새 내부 모듈로 뽑아내고, 원래 모듈 안에는 그 새 모듈의 인스턴스 1개만 남기는 방법. submod는 경계 포트(입출력/인아웃)를 자동으로 만들어 줍니다. yosyshq.readthedocs.io

    • 직접 스크립팅: PyVerilog/SpyDrNet 같은 파서·넷리스트 라이브러리로 경계 신호를 계산해서 새 모듈 선언/인스턴스 치환을 생성하는 파이프라인을 짜는 방법. PyPIBYU ScholarsArchive

    아래에 단계별로 정리해 드릴게요.

    A안: Yosys로 “서브모듈 추출” 자동화 (가장 빠르고 안정적)

    0) 전제

    • 입력은 넷리스트(구조적 Verilog) 혹은 always/assign이 섞인 RTL이어도 됨. 다만 submod는 프로세스나 메모리(미변환 상태) 가 남아있는 모듈에선 동작하지 않으므로, 먼저 이를 셀로 변환합니다. yosyshq.readthedocs.io

    1) 설계 적재 & 전처리

    tcl

# extract.ys
read_verilog -sv your_design.sv
hierarchy -check -top TOP            # TOP은 최상위 모듈
# 프로세스/메모리를 넷리스트 셀로 변환 (submod 요구사항)
proc; memory; opt                    # 필요시 memory_map 등 추가
    • proc, memory 변환은 submod가 요구하는 “프로세스/메모리 없음” 조건을 만족시키기 위한 필수 단계입니다. yosyshq.readthedocs.io+1

    2) 묶을 인스턴스 선택(Selection)

    Yosys의 selection 프레임워크 로 원하는 인스턴스만 골라 집합을 만듭니다.

    tcl

# 대상 모듈 컨텍스트로 진입
cd TARGET_MODULE                      # = select -module TARGET_MODULE 와 동일 :contentReference[oaicite:4]{index=4}

# 선택 집합 만들기 (예: 이름으로 3개를 고르는 간단 예)
select -set grp c:U_ALU0 c:U_ALU1 c:U_ALU2

# 또는 패턴/타입·전후방 콘 확장으로 자동 수집도 가능
# 예: 어떤 결과 신호 out_bus의 조합논리 입력 콘을 모두 포함
# select -set grp o:out_bus %ci.*:+
    • select -set <name>로 **이름 붙인 선택(@ )** 을 저장할 수 있어 이후 명령에서 재사용이 쉽습니다. `c:`(셀 이름), `t:`(셀 타입), `i:/o:/x:`(포트), `%ci/%co/%x`(입출력 콘/연결 확장) 등 강력한 문법을 제공합니다. [yosyshq.readthedocs.io](https://yosyshq.readthedocs.io/projects/yosys/en/0.47/cmd/select.html)

    3) submod 실행으로 새 내부 모듈 만들기

    tcl

# 선택한 셀 묶음을 새 모듈 'ALU_blk'로 추출
submod -name ALU_blk @grp

# 잔여 청소 및 출력
clean
write_verilog -noattr refactored.sv

    • submod -name는 선택(selection) 그 자체 를 묶어 새 모듈을 만들고, 원래 모듈의 해당 부분을 그 새 모듈 인스턴스 1개로 치환 합니다.

    • 경계에 걸린 신호는 자동으로 입력/출력/인아웃 포트 가 생성되며, 내부만 쓰는 배선은 새 모듈 내부로 들어갑니다.

    • 옵션 팁:

      • -copy: 원본 모듈을 수정하지 않고 복사본만 생성 합니다.

      • -hidden: 생성 포트에 프라이빗 이름을 써서 이후 flatten; clean으로 원상복귀가 쉬운 구조를 만듭니다. yosyshq.readthedocs.io

    • 필요하면 rename/autoname으로 생성된 포트/셀 이름을 정리할 수 있습니다. yosyshq.readthedocs.io+1

    참고: submod는 셀에 (* submod="블록명" *) 속성을 미리 달아두고 한 번에 실행하는 방식도 지원합니다. (여러 그룹을 서로 다른 속성값으로 지정 가능) yosyshq.readthedocs.io

    4) 등가성 검증(선택)

    변환 전후가 동작 동일한지 Yosys 등가검증 으로 체크하면 안전합니다.

    tcl

# 모듈 이름 충돌 방지를 위해 원본 top을 top_gold로 바꿔 읽고,
# 리팩토링된 파일을 함께 읽은 후 등가검증
read_verilog -sv original.sv
rename TOP TOP_gold
read_verilog -sv refactored.sv

equiv_make TOP_gold TOP equiv_top
hierarchy -top equiv_top
equiv_simple
equiv_status -assert
    • equiv_make / equiv_simple / equiv_status 조합으로 빠르게 동작 등가를 확인합니다. 리셋 시나리오가 중요하면 SAT 기반 옵션을 더 줄 수 있습니다. yosyshq.readthedocs.io+1Stack Overflow

    요약: Yosys submod는 “선택→추출→치환”까지 한 방에 처리하며, 전처리(proc; memory 등)만 지키면 매우 강력하게 동작합니다. 공식 문서에 동작 조건/옵션이 잘 정리되어 있습니다. yosyshq.readthedocs.io

    B안: 파서/넷리스트 라이브러리로 직접 구현 (세밀 제어가 필요할 때)

    Yosys로 충분하지 않거나 포트 네이밍/파라미터/슬라이스 결합 등을 더 세밀하게 통제하려면 Python으로 파이프라인을 짤 수 있습니다.

    1. 파싱 & 전개

      • Verilog 파싱(AST 또는 엘라보레이션된 넷리스트).

      • 후보: PyVerilog(AST/코드생성 포함), SpyDrNet(구조적 넷리스트 그래프), 혹은 Verilator+Netlist Paths(XML 경로 질의) 등. PyPIBYU ScholarsArchivenetlist-paths.readthedocs.io

    3. 경계 계산

      • 각 인스턴스 포트 연결을 스캔하여 내부 전용 배선 vs 경계 배선 분리.

      • 경계 배선은 드라이버 방향 을 분석해 포트 방향 결정:

        • 내부→외부로 구동: output

        • 외부→내부로 구동: input

        • 양방향/트라이스테이트/다중 드라이버: inout (필요 시 구조 변경)

      • 비트 슬라이스 /부분접속이 섞이면 동일 넷의 비트들을 모아 일관된 포트 폭 으로 리패키징.

    4. 새 모듈 생성

      • 포트 목록(이름/방향/폭)과 내부 인스턴스/배선을 구성.

      • 인스턴스 파라미터를 어떻게 가져갈지 결정(모듈 파라미터화 vs 인스턴스 고정값).

    5. 원래 모듈 치환

      • 선택한 인스턴스를 제거하고 새 모듈의 단일 인스턴스 로 치환.

      • 경계 배선을 새 인스턴스 포트에 연결.

      • 미사용 배선/인스턴스 청소.

    6. 코드 생성 & 검증

      • AST→Verilog 코드 생성(PV: ast_code_generator) 후 시뮬레이션/등가성 확인.

    주의 포인트(현실 이슈)

Reasoned for 6m 25s

좋은 질문이에요. **`define`/`include`는 Verilog “전처리(preprocess)” 단계**에서 처리되므로, Yosys 같은 도구를 쓸 때는 **소스를 읽기(`read_verilog`) 전에** “어디서 헤더를 찾을지(-I)”와 “어떤 매크로를 켤지(-D)”를 지정해 두는 게 핵심입니다. 아래를 **순서대로** 설정하면 됩니다.

* * *

## 1) `include` 파일은 어디서 찾게 하나요? → `-I` 옵션/디폴트 경로

  * Yosys는 기본적으로 **현재 작업 디렉터리** 와 **`include`를 적은 파일이 있는 디렉터리**에서 헤더를 찾습니다. 필요하면 `-I`로 검색 경로를 추가하세요. [Stack Overflow](https://stackoverflow.com/questions/33380477/yosys-cant-open-include-file)

  * `read_verilog`에는 `-I <dir>` 옵션이 있습니다. 여러 개를 줄 수 있어요. [YosysHQ Docs](https://yosyshq.readthedocs.io/projects/yosys/en/0.43/cmd/read_verilog.html)

> 예시

    tcl

    공통적으로 SystemVerilog+인클루드 경로를 기본 옵션으로 등록

    verilog_defaults -add -sv -I rtl/include -I third_party/ip/include

    이후 read_verilog는 위 옵션을 자동 승계

    read_verilog rtl/top.sv rtl/core/*.sv

    
  * 위에서 쓴 `verilog_defaults`는 **이후의 모든`read_verilog` 호출에 기본 옵션을 붙여주는** 명령입니다. 흐트러지기 쉬운 스크립트에 특히 유용합니다. [YosysHQ Docs](https://yosyshq.readthedocs.io/projects/yosys/en/0.32/cmd/verilog_defaults.html?utm_source=chatgpt.com)

* * *

## 2) `define`은 어디서 정의하나요? → 헤더 or 도구 옵션(빌드타임 제어)

선택지는 두 가지입니다.

**A. 소스 안에서 헤더로 관리 (`.vh`/`.svh`)**
```verilog
// rtl/include/defs.svh
`define USE_FOO 1
`define DATA_W  32

    // 각 파일 상단에서
`include "defs.svh"
    • 헤더를 쓴다면 1) 위의 -I로 경로만 잡아주면 됩니다. 디폴트 경로 동작도 참고하세요. Stack Overflow

    B. 빌드/합성 스크립트에서 정의(추천: 변형 관리 쉬움)

    • 1회성: read_verilog -D NAME[=VALUE] 로 그 호출에만 매크로를 건 겁니다. YosysHQ Docs

    • 여러 파일/여러 번 읽을 때 공통 적용:

      • verilog_defines -D NAME=VALUE로 글로벌 매크로 테이블 에 추가 → 이후 read_verilog 호출에 반영됩니다. -U, -reset, -list로 해제/초기화/조회도 가능. YosysHQ Docs

      • 또는 verilog_defaults -add -D NAME=VALUE로 기본 옵션 에 실어주기. YosysHQ Docs

    예시 ``` tcl

    (1) 전처리 기본 옵션: SV + include 경로

    verilog_defaults -add -sv -I rtl/include -I third_party/ip/include

    (2) 매크로 전역 테이블 세팅

    verilog_defines -reset verilog_defines -D ASIC=1 -D DATA_W=32

    (3) 소스 읽기

    read_verilog rtl/top.sv rtl/core/*.sv

    (4) (필요시) 테스트벤치만 따로 SIM 매크로 켬

    verilog_defines -D SIM=1 read_verilog tb/tb_top.sv verilog_defines -U SIM

## 3) 디버깅 팁 (전처리 문제 추적)

  * `read_verilog -ppdump`로 **전처리 결과물** 을 덤프해 보면 `include`/`define`이 제대로 먹었는지 즉시 확인할 수 있습니다. [YosysHQ Docs](https://yosyshq.readthedocs.io/projects/yosys/en/0.43/cmd/read_verilog.html)

  * 현재 등록된 매크로는 `verilog_defines -list`로 확인합니다. [YosysHQ Docs](https://yosyshq.readthedocs.io/projects/yosys/en/0.33/cmd/verilog_defines.html?utm_source=chatgpt.com)

* * *

## 4) 알아두면 좋은 기본 매크로

  * `read_verilog`는 모드에 따라 **`SYNTHESIS` 또는 `FORMAL`**을 자동 정의하고, 항상 **`YOSYS`** 매크로도 정의합니다. 의도치 않은 `ifdef` 분기 유발 여부를 체크하세요. (필요하면 `-nosynthesis`로 억제) [YosysHQ Docs](https://yosyshq.readthedocs.io/projects/yosys/en/0.43/cmd/read_verilog.html)

* * *

## 5) 한눈에 정리

  * 헤더 파일을 코드에서 `include`할 거면: **경로만`-I`로 보강** (필요시 `verilog_defaults`로 고정). [YosysHQ Docs+1](https://yosyshq.readthedocs.io/projects/yosys/en/0.43/cmd/read_verilog.html)

  * 빌드별로 기능 스위치를 켜고 끄려면: **매크로를 스크립트에서`-D`로 관리** (`verilog_defines`/`verilog_defaults` 활용). [YosysHQ Docs+1](https://yosyshq.readthedocs.io/projects/yosys/en/0.33/cmd/verilog_defines.html?utm_source=chatgpt.com)

  * 기본 탐색 경로: **현재 디렉터리 + 포함하는 소스의 디렉터리**. 모자라면 `-I` 추가. [Stack Overflow](https://stackoverflow.com/questions/33380477/yosys-cant-open-include-file)

원하시면, 현재 프로젝트의 디렉터리 구조(예: `rtl/`, `include/`, `tb/`)와 켜고 싶은 매크로 이름을 알려주시면, **바로 실행 가능한`.ys` 스크립트**를 만들어 드릴게요.

<p class="chat--user" markdown="1">

yosys script를 미리 작성해두고 실행하는 방법 알려줘

</p>

Yosys 스크립트는 보통 `.ys` 확장자를 가진 **Tcl-스타일 명령어 모음 파일** 입니다. 미리 작성해두고 실행하는 방법은 다음 단계로 진행하면 됩니다.

* * *

## 1\. 스크립트 파일 작성

예를 들어 `extract.ys`라는 파일을 만들고 다음과 같이 작성합니다:

    tcl

    extract.ys

    1) 소스 읽기

    verilog_defaults -add -sv -I rtl/include -D ASIC=1 read_verilog rtl/top.sv rtl/core/*.sv

    2) 계층 정리

    hierarchy -check -top TOP

    3) 전처리 (submod 실행 조건 만족)

    proc; memory; opt

    4) 묶을 인스턴스 선택 + submod

    cd TARGET_MODULE select -set grp c:U_ALU0 c:U_ALU1 c:U_ALU2 submod -name ALU_blk @grp

    5) 마무리 및 출력

    clean write_verilog -noattr refactored.sv

    
* * *

## 2\. Yosys에서 실행하기

터미널에서 다음 명령으로 실행할 수 있습니다:
```bash
yosys -s extract.ys

    • -s 옵션은 스크립트 파일을 읽어서 그대로 실행 한다는 뜻입니다.

    • 실행이 끝나면 같은 디렉터리에 refactored.sv가 생깁니다.

    3. 대화형 모드에서 실행하기 (대안)

    만약 중간에 결과를 확인하거나 명령을 추가로 입력하고 싶다면:

    yosys

    으로 들어간 뒤, 프롬프트에서:

    tcl

script extract.ys

    라고 치면 스크립트를 실행합니다. 실행 중간에도 추가 명령을 계속 입력할 수 있습니다.

    4. 팁

    • 스크립트를 여러 개 만들어두고 yosys -s로 원하는 것만 실행하면, 합성·리팩토링·검증 단계를 각각 독립적으로 관리할 수 있습니다.

    • 로그를 저장하고 싶으면:

    yosys -s extract.ys | tee yosys.log

    처럼 하면 됩니다.

    👉 혹시 지금 프로젝트 디렉터리 구조(예: rtl/, include/, tb/)와 Top 모듈 이름을 알려주시면, 그에 맞는 실행 가능한extract.ys 예시를 만들어 드릴까요?

    tranif, mos 레벨이 있으니 yosys가 못 읽네

    아 네—tranif*, nmos/pmos 같은 스위치/트랜지스터 레벨 primitive 는 Yosys가 정식 지원하지 않아서 그대로는 못 읽습니다. 보통은 두 가지 우회 로 처리합니다. 아래를 “차근차근” 따라가면 됩니다.

    1) 가장 안전한 방법: “스위치 쓰는 모듈을 블랙박스”로 만들기

    스위치/트랜지스터가 들어있는 모듈(대개 PAD, ESD, 전력게이팅 블록 등)을 검출해서 I/O만 동일한 빈 껍데기 모듈 로 치환하고, 나머지 디지털 부분만 Yosys에 넘깁니다.

    (1) 블랙박스 대체 모듈 만들기

    예: io_pad.sv 안에 tranif1 등이 있다면, Yosys용으로는 다음처럼 빈 정의를 준비합니다.

    // tools/yosys_blackboxes/io_pad__bb.sv
`ifdef YOSYS
module io_pad (
  inout  wire PAD,
  input  wire dout,
  input  wire oe_n,
  output wire din
);
  // 내용 없음: Yosys에서는 인터페이스만 유지
endmodule
`endif

    (2) Yosys 스크립트에서 블랙박스 우선 로드

    tcl

# extract.ys
verilog_defaults -add -sv -D YOSYS -I rtl/include -I tools/yosys_blackboxes

# 1) 블랙박스 먼저 (라이브러리 모드로 인터페이스만 인지)
read_verilog -lib tools/yosys_blackboxes/io_pad__bb.sv

# 2) 나머지 RTL/넷리스트 읽기
read_verilog rtl/top.sv rtl/**/*.sv

hierarchy -check -top TOP
proc; memory; opt

# 이후 당신이 하려던 submod 등 처리...

    • -lib로 읽으면 본문은 무시 하고 포트만 있는 셀 로 취급합니다.

    • 이렇게 하면 스위치가 들어있는 모듈은 “그냥 셀”이고, 내부 디지털은 그대로 작업 가능합니다.

    팁: 스위치가 들어있는 모듈들이 여러 개라면, 동일 패턴으로 여러 개의 블랙박스 파일 을 준비해 read_verilog -lib로 한 번에 읽어두세요.

    2) 가벼운 근사치(shim)로 “합성 가능한 형태”로 바꾸기

    만약 그 모듈 내부를 Yosys로도 통째로 리팩토링 하고 싶다면, 스위치 primitive를 합성 가능한 삼상버퍼/할당 으로 “근사치” 치환합니다. (스위치가 진짜 양방향을 엄격히 요구하면 부정확해질 수 있으니 주의!)

    (1) shim 헤더 작성

    아래처럼 매크로로 primitive 토큰을 대체 합니다. Yosys에서는 텍스트 전처리(-D YOSYS)를 켜 두고 이 헤더를 include시키면, 원본의 tranif1 (...) 같은 구문이 자동으로 bufif*나 assign으로 바뀝니다.

    // tools/yosys_shims/switch_shims.svh
`ifndef __YOSYS_SWITCH_SHIMS_SVH__
`define __YOSYS_SWITCH_SHIMS_SVH__

`ifdef YOSYS
  // 단방향으로 근사 (많은 패드/패스게이트는 한쪽만 읽도록 설계됨)
  // tranif1(out, in, en) : en=1일 때 전도
  `define tranif1(out,in,en)  bufif1 (out, in, en)
  // tranif0(out, in, en) : en=0일 때 전도
  `define tranif0(out,in,en)  bufif0 (out, in, en)

  // rtranif*는 저항성 전도지만, 합성엔 의미가 없으니 동일 근사
  `define rtranif1(out,in,en) bufif1 (out, in, en)
  `define rtranif0(out,in,en) bufif0 (out, in, en)

  // nmos/pmos도 enable 조건만 남긴 근사치
  `define nmos(out,in,g)      bufif1 (out, in, g)     // g=1일 때 전도
  `define pmos(out,in,g)      bufif0 (out, in, g)     // g=0일 때 전도

  // 순수 전달소자(tran/rtran)는 합성 의미가 모호하므로 금지/경고 처리
  `define tran(a,b)           $error("tran not supported in Yosys shim")
  `define rtran(a,b)          $error("rtran not supported in Yosys shim")
`endif

`endif

    왜 가능한가요?
    전처리는 “토큰 대체”이기 때문에, 소스가 tranif1 (A,B,EN);라고 써 있어도 -D YOSYS가 켜진 상태에서 위처럼 define tranif1(...)가 있으면 텍스트가 bufif1 (A,B,EN)으로 치환됩니다.

    (2) 소스에 한 줄 추가

    스위치 primitive를 쓰는 파일 상단에 다음을 넣습니다.

    `include "switch_shims.svh"  // Yosys에서만 실질 치환됨

    (3) Yosys 스크립트에서 전처리 활성화

    tcl

# extract.ys
verilog_defaults -add -sv -D YOSYS -I tools/yosys_shims -I rtl/include
read_verilog rtl/top.sv rtl/**/*.sv
hierarchy -check -top TOP
proc; memory; opt
# ... submod 등 작업

    한계: tranif*는 본래 양방향 전도 입니다. 위 근사는 한쪽 방향만 살아있다 고 가정합니다. 내부에서 진짜로 양방향로직이 필요하면(드문 케이스) 이 방법은 정확성이 떨어집니다. 그런 모듈은 1번 방식(블랙박스)이 더 낫습니다.

    3) 어느 방법을 고를까? (결정 가이드)

    • PAD, 아날로그 믹스드, 전력스위치 처럼 스위치가 “물리 레벨 의미”를 가지는 블록 → 블랙박스(방법 1) 권장.

    • 단순 패스게이트 MUX 처럼 기능이 명확 하고, 내부를 Yosys로도 만지고 싶다 → shim 근사(방법 2) 후 등가성/시뮬 확인.

    4) 검증 루틴(권장)

    • 시뮬레이터(iverilog 등)로 원본 vs shim/블랙박스 버전을 동일 테스트벤치로 돌려 파형 비교.

    • 또는 Yosys의 등가검증(equiv_*)으로 핵심 디지털 경로가 보존됐는지 확인.

    • 블랙박스 경계의 포트 동작은 계약(Contract) 테스트 로 체크(예: PAD OE/IN/OUT 동작).

    5) 바로 가져다 쓸 수 있는 최소 예시

    (A) 블랙박스 방식

    tools/yosys_blackboxes/io_pad__bb.sv
extract.ys

    tcl

# extract.ys
verilog_defaults -add -sv -D YOSYS -I rtl/include -I tools/yosys_blackboxes
read_verilog -lib tools/yosys_blackboxes/io_pad__bb.sv
read_verilog rtl/top.sv rtl/**/*.sv
hierarchy -check -top TOP
proc; memory; opt
# cd/ select/ submod ...
write_verilog -noattr out/refactored.sv

    (B) shim 치환 방식

    tools/yosys_shims/switch_shims.svh
extract.ys

    tcl

# extract.ys
verilog_defaults -add -sv -D YOSYS -I tools/yosys_shims -I rtl/include
read_verilog rtl/top.sv rtl/**/*.sv
hierarchy -check -top TOP
proc; memory; opt
# cd/ select/ submod ...
write_verilog -noattr out/refactored.sv

    그리고 스위치 쓰는 소스에:

    `include "switch_shims.svh"

    필요하시면, 당신 프로젝트의 파일/모듈 이름 을 알려주지 않아도 됩니다—위 두 템플릿을 그대로 놓고 경로만 맞추면 동작합니다.
    그래도 더 깔끔히 하고 싶다면, 스위치가 들어간 “모듈 목록”만 알려주세요. 그 목록을 기준으로 블랙박스 세트 나 맞춤 shim 을 바로 만들어 드릴게요.
